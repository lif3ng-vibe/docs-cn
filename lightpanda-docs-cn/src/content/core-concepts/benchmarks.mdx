# 基准测试

Lightpanda 公布了三组与无头 Chrome 对比的基准测试：

- **[大规模爬取](#大规模爬取)**：跟随一个 933 页演示站上的所有链接。
- **[单页自动化](#单页自动化)**：通过 CDP 反复执行“加载并提取”循环。
- **[AI agent 任务完成率](#ai-agent-任务完成率)**：AssistantBench 与 GAIA 上的任务准确率。

三组测试中 Lightpanda 均优于 Chrome。每节数字的来源都在文中注明。确切的命令与原始输出见[复现这些结果](#复现这些结果)。

## 测量方法

爬取与单页基准追踪峰值内存（通过 `smem`，采用 PSS 以免共享页面被重复计算）、CPU 利用率（通过 `ps aux`）和实际耗时（wall-clock），运行期间每 100ms 采样一次。两项测试都跑在一台全新安装 Ubuntu 的 AWS m5.xlarge 实例上，对比 Lightpanda 与 Chrome。

AI agent 基准的评分方式不同：每个任务的最终答案会与已知正确答案比对，而不是截图比对——反正 Lightpanda 也没有渲染出来的页面可供截图。

## 大规模爬取

来源：demo 仓库中的 [Crawler Benchmark, BENCHMARKS.md](https://github.com/lightpanda-io/demo/blob/main/BENCHMARKS.md#crawler-benchmark)。

该基准爬取 [demo-browser.lightpanda.io/amiibo](https://demo-browser.lightpanda.io/amiibo/)——一个演示用商品目录，从索引页出发跟随指向子页面的每一个链接，共 933 个 URL。一个使用 [chromedp](https://github.com/chromedp/chromedp) 的 Go 程序通过 CDP 驱动整个爬取，因此两个浏览器经受的是同一套客户端代码。

Chrome 用一个浏览器开多个标签页，因为大多数人用普通浏览器扩展自动化就是这么做的。Lightpanda 无法在单个进程里开多个标签页，于是改为运行多个进程，每个进程占一个端口。这与两个浏览器在生产环境中实际的部署方式一致，而不只是同进程内的对比。

<Callout type="info">
  Chrome 会在同一浏览器的多个标签页之间共享大量基础设施（渲染进程、V8 堆）。Lightpanda 的进程则完全独立。下表的对比是标签页数对进程数，因为那是各自浏览器扩展时所用的单位。
</Callout>

| 并行标签页 / 进程数 | Lightpanda 耗时 | Lightpanda 内存峰值 | Chrome 耗时 | Chrome 内存峰值 |
| --- | --- | --- | --- | --- |
| 1 | 0:51.68 | 27.2M | 1:22.83 | 1.3G |
| 2 | 0:29.79 | 31.7M | 0:53.11 | 1.3G |
| 5 | 0:11.70 | 43.9M | 0:45.66 | 1.6G |
| 10 | 0:06.76 | 63.7M | 0:45.62 | 1.7G |
| 25 | 0:04.81 | 123.0M | 0:46.70 | 2.0G |
| 100 | 0:05.23 | 410.2M | 1:09.37 | 4.2G |

在 25 个并行任务——两个浏览器都接近各自最佳吞吐量的位置——Lightpanda 用 4.81 秒、123MB 内存完成，而 Chrome 需要 46.70 秒、2.0GB：约快 9 倍、省 16 倍内存。Chrome 的耗时在超过 5 个标签页后趋于平稳，因为它的标签页共享进程、开始互相争抢资源。Lightpanda 则持续提升到 25 个进程，因为每个进程完全隔离，机器仍有余量。

![内存峰值随并行标签页/进程数的扩展：100 个进程时 Lightpanda 保持在 500MB 以下，Chrome 则爬升超过 4GB](https://cdn.lightpanda.io/website/assets/images/docs/benchmarks-crawler_memory_scaling.png)

## 单页自动化

来源：demo 仓库中的 [Campfire e-commerce Benchmark, BENCHMARKS.md](https://github.com/lightpanda-io/demo/blob/main/BENCHMARKS.md#campfire-e-commerce-benchmark)。

爬取衡量的是获取和跟随链接。该基准衡量的是脚本需要加载页面、等待网络请求、再把数据读回来之后发生的事——大多数抓取与测试代码背后的模式。它使用一个[自制的电商演示页](https://demo-browser.lightpanda.io/campfire-commerce/)，通过两个 XHR 请求加载商品详情和评论，页面由本地 Web 服务器提供，以排除网络延迟对结果的影响。一个 [Puppeteer](https://pptr.dev/) 脚本通过 CDP 连接，把同样的加载并提取任务重复 100 次。

| 浏览器 | 单次平均耗时 | 总耗时（100 次） | 内存峰值 | CPU 峰值 |
| --- | --- | --- | --- | --- |
| Lightpanda | 16ms | 1,698ms | 21.2M | 4.6% |
| Chrome 143.0.7499.109 | 185ms | 18,551ms | 402.1M | 158.6% |

同样的 100 次运行，Lightpanda 约快 11 倍，峰值内存约省 19 倍。原因见[架构总览](/core-concepts/architecture-overview)。

## AI agent 任务完成率

来源：[agent-benchmarks](https://github.com/lightpanda-io/agent-benchmarks) 仓库 README 的[当前结果](https://github.com/lightpanda-io/agent-benchmarks#current-results)与[跨框架对比](https://github.com/lightpanda-io/agent-benchmarks#cross-framework-comparison-lightpanda-vs-agent-browser-vs-browser-use-claudemcp)两节。

爬取与页面加载基准衡量的是原始速度，但说明不了 AI agent 是否真的完成了任务。运行 `lightpanda agent`——内置的 agent 循环，不经过任何 MCP 或 CDP 往返——在 AssistantBench 的 33 题验证集和 GAIA Level 1 的 53 题验证集上，搭配 Claude Sonnet 4.6、单题超时 1800 秒，取得 AssistantBench 69.7%、GAIA 83.0% 的严格准确率，两者均零超时。按 token 用量计算的单题成本：AssistantBench 1.94 美元，GAIA 0.34 美元。

为了分离这个结果究竟来自引擎还是工具面，Lightpanda 还用同一个 Claude Sonnet 4.6 会话经 MCP 对阵另外三种配置：[agent-browser](https://github.com/vercel-labs/agent-browser) 驱动 Chromium、agent-browser 改用 Lightpanda（而非 Chrome）作为引擎，以及 [browser-use](https://github.com/browser-use/browser-use) 驱动 Chromium。行与行之间只有浏览器及其工具面在变。

| 测试集 | Lightpanda MCP | agent-browser + Chromium | agent-browser + Lightpanda | browser-use（Chromium） |
| --- | --- | --- | --- | --- |
| AssistantBench（严格） | 66.7% | 57.6% | 57.6% | 39.4% |
| GAIA Level 1（严格） | 86.8% | 84.9% | 81.1% | 47.2% |

无论 agent-browser 驱动 Chrome 还是 Lightpanda，AssistantBench 的准确率都一样（两者均为 57.6%），因此与 Lightpanda 自家 MCP 工具面（66.7%）的差距来自工具本身，而非其下的引擎。GAIA 上，把 agent-browser 底下的引擎换成 Lightpanda 会损失几个点的准确率（81.1% 对 84.9%），出问题的是那些只有纯文本输出会漏掉内容、而渲染页面能呈现的页面。
