# 架构总览

Lightpanda 是一款用 Zig 构建的无头浏览器，为机器驱动而生，而非供人浏览。它最核心的取舍是：没有渲染引擎，也从不把页面绘制到屏幕上。

它通过网络层获取页面，再运行 JavaScript 引擎，在内存中的 DOM 与 Web API 之上执行页面脚本，同时砍掉了让普通浏览器变得沉重的图形管线。一个原生二进制即可通过多个入口暴露这套引擎——从 CDP 服务器到内置 AI Agent。

## 为什么没有渲染引擎

普通浏览器会运行一条渲染管线，把页面变成给人看的像素：样式解析、布局、绘制与合成。机器几乎不需要这些像素。客户端通过协议（通常是 Chrome DevTools 协议，CDP）发送命令，然后读回页面的结构，也就是 DOM。屏幕上的画面无关紧要。

Lightpanda 砍掉了渲染管线，保留下来的正是自动化所需的组件——也就是本页下方详述的那几部分：

- **控制面**。你驱动它的各个入口：`fetch`、`serve`（CDP，或 WebDriver classic 与 BiDi）、`agent`、`mcp`，以及 Cloud 上的 HTTP API。
- **网络层**。通过 HTTP 获取主文档及其子资源。
- **HTML 解析器**。把获取到的 HTML 变成 DOM。
- **JavaScript 引擎**。执行页面脚本。Lightpanda 使用 V8，与 Chrome 同款引擎。
- **Web API 与 DOM**。脚本读取和修改的内存中文档。

<Callout type="info">
  由于 Lightpanda 不做渲染，它不会计算真实的视觉布局。元素尺寸可以由 CSS 和 HTML 属性较准确地估算，但元素位置是基于 DOM 深度和兄弟顺序模拟出来的，并非真实布局（[`calculateDocumentPosition`](https://github.com/lightpanda-io/browser/blob/main/src/browser/webapi/Element.zig#L1411-L1468)）。`Page.captureScreenshot` 返回的是占位图片，不是真实渲染结果。需要真实像素时，请改用完整的浏览器。
</Callout>

## 各部分如何协作

Lightpanda 以单个原生二进制的形式发布，运行时只有一个进程。该进程持有整个运行期共享的状态（即 `App`），并按需创建浏览器实例。每个浏览器实例拥有一个 V8 isolate，以及在其中运行的页面层级结构。

### 入口

这些入口背后运行的是同一套引擎。每个入口都是一种不同的驱动方式，在[本地与 Cloud](/core-concepts/local-vs-cloud#功能覆盖) 上的可用性也各不相同：

- [`fetch`](/run-locally/commands#fetch-命令) 加载一个或多个 URL，并把结果以 HTML 或 Markdown 的形式输出到 stdout。它是一次性命令，不涉及服务器。
- [`serve`](/run-locally/commands#serve-命令) 默认在 `9222` 端口启动 CDP 服务器。[Puppeteer](/usage/cdp/puppeteer)、[Playwright](/usage/cdp/playwright)、[chromedp](/usage/cdp/chromedp) 等客户端通过 Chrome DevTools 协议连接。这是大多数自动化使用的模式。传入 `--protocol webdriver` 则改用 [WebDriver BiDi](/usage/bidi/selenium)。
- [`agent`](/usage/agent) 启动一个交互式 AI Agent，用自然语言浏览网页，并能录制可复现的脚本。
- [`mcp`](/usage/mcp) 通过 stdio 启动 Model Context Protocol 服务器，让 LLM 宿主把浏览器当作工具使用。
- [HTTP API](/usage/api) 是一个 `POST /api/fetch` 端点，单次请求即可返回页面的 HTML 或 Markdown，无需 CDP 脚本。它相当于 Cloud 版的本地 `fetch` 命令。

面向 Agent 的各模式在同一套引擎之上叠加不同厚度的浏览器层。用 `serve` 时，你的客户端通过 CDP 驱动引擎；用 `mcp` 时，二进制文件还额外承载工具服务器；用 `agent` 时，整个循环都在二进制内，模型与引擎之间不再隔着任何协议。

### 浏览器引擎

在入口之下，是一套驱动页面的对象层级。它把贯穿整个进程的状态与限定在一次浏览会话内的状态区分开来。

`App` 在启动时创建一次，持有上文所示的进程级服务，其下的所有对象都从这些服务借用资源。其中两个值得点名：arena 池（一组共享的内存 arena，参见[内存模型](#内存模型)）与遥测（匿名使用统计，调试构建中默认关闭，也可通过 `LIGHTPANDA_DISABLE_TELEMETRY` [禁用](/run-locally/installation/nightly-builds#遥测)）。

- **Browser** 包裹一个 V8 isolate。isolate 与线程绑定，因此浏览器在单个线程上创建和使用。它还持有一个浏览器专属的 HTTP 客户端，并从 `App` 的池中借用 arena。一个浏览器包含一个会话。
- **Session** 是一组浏览上下文（browsing context）。它持有 Cookie 存储（cookie jar，即该会话的 cookie 仓库）与 Web Storage（`localStorage` 和 `sessionStorage`）——也就是比单次导航活得更久的状态。这部分按会话隔离，与 `App` 的 SQLite 存储后端分开。
- **Page** 是标签页级容器，容纳一棵 frame 树：一个顶层浏览上下文，拥有根 frame 以及其下所有 iframe。
- **Frame** 是一个文档 frame（主 frame 或 iframe）。它拥有脚本所操作的 DOM（`Document`）与 Web API（`Window`）。

Cookie 和权限属于会话，因此页面导航时依然保留。isolate 属于浏览器，因此跨页面存活，但绝不跨线程。

**网络层**。构建在 [libcurl](https://curl.se/libcurl/) 之上，获取主文档与子资源，管理 Cookie 存储，传入 `--obey-robots` 时还可遵循 `robots.txt`。

**HTML 解析器**。解析工作委托给 [html5ever](https://github.com/servo/html5ever)——Servo 项目中符合规范的 Rust 解析器。Lightpanda 在 `src/browser/parser/` 中通过 C ABI 调用它，并根据解析器回调构建 DOM 树。这就是从源码构建浏览器时除了 Zig 还需要 Rust 工具链的原因。

**JavaScript 引擎**。Lightpanda 在 V8 上运行页面脚本，没有重新实现 JavaScript。`src/browser/js/` 中的 Zig 代码是对 V8 C++ API 的薄封装：isolate、context、value、promise、module。脚本接触到的 Web API 对象用 Zig 实现，因此 `document`、`window`、`fetch` 背后是原生代码，而不是更多的 JavaScript。启动快得益于 V8 启动快照：构建期嵌入二进制的一份序列化、预初始化的 V8 堆。每次启动时 V8 直接加载它，而不必从零重建内置对象，省去了 isolate 预热的大部分开销。

**Web API 与 DOM**。它们以 Zig 原生实现，按领域分组：DOM（`Document`、`Element`、`Node`）、事件、`fetch` 与网络、`Crypto`、观察者（mutation、intersection、resize）以及存储。覆盖范围是部分的，并随时间不断扩大。Lightpanda 实现的是无头自动化会用到的那批 API，而非整个 Web 平台。各 API 领域当前的通过率见 [web-platform-tests 仪表盘](https://perf.lightpanda.io/wpt)。哪些 API 已存在，以 browser 仓库中的 `src/browser/webapi/` 为准。脚本调用这些 API 时执行的是编译好的 Zig 代码，这正是 DOM 密集型页面在时间和内存上都便宜的原因。

## 内存模型

内存占用小且可预测是 Lightpanda 的标志性特质之一，因此引擎如何管理内存也是其架构的一部分。砍掉渲染管线去掉了最大的一笔开销，而分配器设计则让剩下的部分在负载下依然有界。

调试构建使用一个在退出时检测泄漏的分配器，自定义测试运行器会让任何只分配不释放的测试直接失败。发布构建则直接使用 C 分配器。

与单次请求或导航绑定、生命周期短暂的对象分配走 arena。arena 是一整块区域，你可以把许多小对象分配进去，最后一次性整体释放，而不必逐个追踪。Lightpanda 在 `App` 上维护一个进程级的 arena 池：页面加载时借用一个，页面销毁时归还。这样单页开销平稳且可预测，清理也只需一次 free。
