# AI 智能体的上下文工程

## 核心原则

**找出规模最小、信号最强的 token 集合，让期望结果发生的可能性最大化。**

---

## 上下文工程与提示工程

**提示工程（prompt engineering）**：撰写并组织 LLM 指令，以获得最优结果（一次性任务）

**上下文工程（context engineering）**：在推理过程中跨多轮对话持续篮选并维护最优的 token 集合（迭代过程）

上下文工程管理的内容包括：

- 系统指令
- 工具
- Model Context Protocol（MCP）
- 外部数据
- 消息历史
- 运行时数据检索

---

## 问题所在：上下文腐烂

**关键洞察**：LLM 有一份"注意力预算"，会随上下文增长而逐渐耗尽

- 每个 token 都要关注其余每个 token（n² 量级的关系）
- 上下文越长，模型准确率越低
- 模型在更长序列上的训练经验更少
- 必须把上下文当作边际收益递减的有限资源

---

## 系统提示词：找准"合适的高度"

### 恰到好处的区间

**过度具体** ❌
- 硬编码的 if-else 逻辑
- 脆弱易碎
- 维护复杂度高

**过于空泛** ❌
- 只有高层指导，缺少具体信号
- 错误地假设双方共享上下文
- 缺乏可执行的方向

**恰到好处** ✅
- 具体到足以有效引导行为
- 灵活到足以提供强有力的启发式规则
- 用最少的信息完整勾勒出预期行为

### 最佳实践

- 使用简单、直接的语言
- 划分出界限清晰的段落（`<background_information>`、`<instructions>`、`## Tool guidance` 等）
- 用 XML 标签或 Markdown 标题搭建结构
- 从最简提示起步，根据失败模式逐步补充
- 注意：最简 ≠ 短小（一开始就要提供充分的信息）

---

## 工具：少而清晰

### 设计原则

- **自成一体**：每个工具只服务一个明确的用途
- **对错误健壮**：优雅地处理边界情况
- **极其清晰**：预期用法毫无歧义
- **省 token（token-efficient）**：返回相关信息而不臃肿
- **参数可描述**：输入名无歧义（如 `user_id` 而非 `user`）

### 关键规则

**如果连人类工程师都无法在给定情境下明确说出该用哪个工具，就不能指望 AI 智能体做得更好。**

### 需要避免的常见失败模式

- 覆盖过多功能的臃肿工具集
- 用途相互重叠的工具
- 在"该用哪个工具"上存在模糊的决策点

---

## 示例：求多样，而非穷尽

**该做** ✅
- 精选一组多样的代表性示例
- 有效展示预期行为
- 想想"一张图胜过千言万语"

**不该做** ❌
- 堆砌一长串边界情况
- 试图穷举每一条可能的规则
- 用包罗万象的场景让人不堪重负

## 上下文检索策略

### 即时上下文（智能体推荐方案）

**思路**：维护轻量级的标识符（文件路径、查询语句、链接），在运行时动态加载数据

**优点**：

- 避免上下文污染（context pollution）
- 支持渐进式披露（progressive disclosure）
- 贴近人类认知（我们不会事无巨细全记在脑子里）
- 依托元数据（文件名、目录结构、时间戳）
- 智能体逐步发现所需上下文

**代价**：

- 比预先计算好的检索更慢
- 需要恰当的工具引导，避免钻进死胡同

### 推理前检索（传统 RAG）

**思路**：在推理之前，用基于嵌入（embedding）的检索把上下文先取出来

**适用场景**：交互过程中不会变化的静态内容

### 混合策略（两全其美）

**思路**：预先取回一部分数据，其余部分按需自主探索

**例子**：Claude Code 先加载 CLAUDE.md 文件，再用 glob/grep 做即时检索

**经验法则**："先用最简单的办法把它做成"

## 长程任务：三种技术

### 1. 压缩

**是什么**：在临近上下文上限时把对话压缩为摘要，再以摘要为起点重新开始

**实现方式**：

- 把消息历史交给模型做压缩
- 保留关键细节（架构决策、bug、实现要点）
- 丢弃冗余输出
- 带着压缩后的上下文与最近访问的文件继续工作

**调优过程**：

1. **先**：把召回做到最大（把所有相关信息都覆盖到）
2. **再**：提高精度（剔除多余内容）

**见效最快的抓手**：清掉旧的工具调用和结果

**最适合**：需要大量来回交互的任务

### 2. 结构化笔记（智能体记忆）

**是什么**：让智能体把笔记写到上下文窗口之外的持久位置，之后再取回使用

**例子**：

- 待办清单
- NOTES.md 文件
- 游戏状态记录（宝可梦例子：追踪 1,234 步的训练过程）
- 项目进展日志

**优点**：

- 以极小的开销获得持久记忆
- 跨工具调用保持关键上下文
- 支撑长达数小时的连贯策略

**最适合**：有清晰里程碑的迭代式开发

### 3. 子智能体架构

**是什么**：让专职的子智能体在干净的上下文窗口里处理聚焦的任务

**工作方式**：

- 主智能体统筹高层计划
- 子智能体承担深入的技术工作
- 子智能体可以大规模探索（消耗数万 token）
- 只返回精炼摘要（1,000–2,000 token）

**优点**：

- 关注点清晰分离
- 可并行探索
- 详尽的上下文保持隔离

**最适合**：复杂的研究与分析任务

## 快速决策框架

| 场景 | 推荐方案 |
|----------|---------------------|
| 静态内容 | 推理前检索或混合策略 |
| 需要动态探索 | 即时上下文 |
| 长期来回交互 | 压缩 |
| 迭代式开发 | 结构化笔记 |
| 复杂研究 | 子智能体架构 |
| 模型快速进步 | "先用最简单的办法把它做成" |

---

## 核心要点

1. **上下文是有限的**：把它当作一种自带注意力预算的宝贵资源
2. **整体性思考**：把对 LLM 可见的完整状态纳入考量
3. **保持极简**：上下文越多不一定越好
4. **迭代推进**：每次把内容传给模型，都是在做一次上下文篮选
5. **为自主性而设计**：模型在持续进步，要让它们聪明地行动
6. **从简起步**：先以最简配置测试，再按失败模式逐步补充

---

## 需要避免的反模式

- ❌ 把所有东西都塞进提示词
- ❌ 编造脆弱的 if-else 逻辑
- ❌ 构建臃肿的工具集
- ❌ 用穷举式的边界情况充当示例
- ❌ 一厢情愿地认为更大的上下文窗口能解决一切
- ❌ 在长程交互中忽视上下文污染

---

## 切记

> "即便模型持续进步，在长程交互中保持连贯性的挑战，仍将是构建更有效智能体的核心命题。"

上下文工程会不断演化，但核心原则始终不变：**提高你 token 预算中的信噪比**。
