<Aside type="note" title="需求">
处于工作状态，查询某个东西——一个取值、一个选项、一项限额、一个名字。读者从侧面进来（搜索、锚点链接、智能体的检索），抓走事实就走人。他们的开场问题是：*"确切的取值是什么？*"本配方覆盖**散文侧的参考**——配置文件、CLI 标志、事件类型、限额、设置。从 spec 编译出的 API 参考是另一条工作流；两者共享同一条纪律：事实只有一个来源，而且读者不必打开页面就能预测它的形状。
</Aside>

## 何时使用

当内容是对某一个界面（surface）的事实罗列时（一种文件格式、一条命令、一组类型或限额），就写参考。它不是：

- **操作指南**。参考负责描述；绝不负责指导。如果条目里开始长出"要做这件事，先……"的句子，就把它们抽成操作指南并放链接。
- **概念**。参考中立而完整；观点和取舍住在概念页里。开头允许的*散文*只有一句定位句加一个概念链接——条目级的概念与操作指南链接则是应有之义（见链接与时效性）。
- **垃圾场。**"杂项"式的参考页是事实走失的地方。每个参考页只覆盖一个叫得出名字的界面；它的结构映照产品的结构，读者才能在两边平行导航。

这一类型的两条铁律是**完整性**（缺一个条目对参考的破坏，就像词典缺一个词）和**统一性**（每个条目以相同顺序回答相同的问题）。

## 标题与描述

- **标题：该界面的名字，按读者会搜索的写法。**"hookline.config.js" · "CLI commands" · "Event types" · "Limits"。当光杆名词有歧义时可以加"reference"（"Retry policy reference"）。
- **描述公式：**"*该界面*接受的每一种*条目类型*，并列出*事实类别*。"——例如"Every field hookline.config.js accepts — type, default, and constraints."（hookline.config.js 接受的每个字段——类型、默认值与约束。）

## 脚手架生成此页

安装这份配方——你的编码智能体会读取完整的骨架和清单，并把它们适配到你的产品上：

<PackageManagers pkg="@cloudflare/nimbus-docs" type="dlx" args="add content-reference" />

脚手架的定义行按界面自适应：

| 界面 | 定义行包含 |
|---|---|
| 配置字段 | type · default · required · range/constraints |
| CLI 标志 | long form as heading, alias inline (`--verbose` · alias `-v`) · value syntax · default · repeatable? |
| 事件/webhook 类型 | payload schema link · when it fires · delivery guarantees that differ from the default |
| 限额/配额 | value · scope (per key? per account?) · what happens at the limit · adjustable? |

## 组件建议

- **表格**是标志性组件。强烈建议在条目上方放一张速查表，让常见查询零滚动。只用简单表格；合并单元格和靠排版传义会同时毁掉扫读和抽取。
- **条目级定义行**（type · default · constraints）按固定顺序——加粗或加徽章的样式保持一致。
- **不适合**：Steps、Cards、提示块（需要警告提示块的事实，通常应该作为约束*写进*条目本身）、藏起条目的标签页或手风琴（折叠面里的条目，对"搜索-抓取"型读者和对抽取都不可见）。

## 结尾

参考页没有结尾——它在最后一个条目之后停住（如果该系列有固定尾巴，再加上尾巴）。没有"后续步骤"页脚：拿到取值的读者早已离开，没拿到的读者需要的是页首的概念链接，不是页脚。

## 阈值

- **要么完整，要么明确划定范围——没有中间态**。该界面接受的每个条目都在场；如果某个子集被有意放在别处，第一行就说明在哪里。
- **条目描述散文 ≤ 3 句，保持中立**——配一个结构化的泄压阀：超出这个量的事实（每个取值的语义、相互作用、警告）放进条目下的列表或子表，而不是写成更多散文。
- **一页一个界面**，粒度由界面自身的接缝决定（拆分时，一个顶层配置节或一个子命令本身就是界面）。条目到了 30 个左右，就是考虑沿接缝拆分的信号；但一页长文配稳定锚点同样是合理且对智能体友好的选择。绝不按字母顺序拆。

## 链接与时效性

*只要存在*，就把每个条目链到解释它的概念和演练它的操作指南——并保持条目锚点稳定；参考页锚点是文档站上被引用最多的 URL。这里的事实有且只有一个来源：如果条目重复了住在代码或 schema 里的值，就改为生成——机器真相的人工维护副本是漂移的可靠来源。没有机器来源的人工维护事实页（限额、配额）要带一个可见的最近验证日期（frontmatter 里的 `lastVerified`）；生成的页面继承其来源的时效性。

## 智能体须知

- 参考是智能体消费最多、而不完整时幻觉最严重的类型——缺失的条目会被读成"不存在"。完整性就是抗幻觉属性。
- 每个条目必须自含：标题带上完整的点分路径（`retry.max_attempts`，而不是"Retry"标题下的"max_attempts"），让被检索出的内容块自带身份。
- 范围和默认值写成机器可核查的值，绝不说"一个合理的数字"。
- `.md` 版本无需特殊处理，*正因为*本配方禁止把条目藏进标签页/手风琴——保持这样；生成的 Markdown 包含完整的参考页。

## 检查清单

仅供参考——供作者或智能体自查，绝非构建关卡：

- [ ] 条目上方有速查表（界面 ≥ 约 5 个条目），由生成产出或有意识维护
- [ ] 每个条目都在场，或在第一行声明了范围排除
- [ ] 每个条目遵循同一套内部模板，标题层级一致
- [ ] 定义行带有 type · default · required · constraints（按界面种类适配）
- [ ] 描述中立；超出的事实放列表/子表，不写成散文
- [ ] 条目标题带完整的自标识名称（点分路径）
- [ ] 排序已声明或不言自明；锚点在多次编辑间保持稳定
- [ ] 单一事实来源已写明（或页面就由它生成）；人工维护的事实页带 `lastVerified`
- [ ] 无步骤、无观点、没有任何内容藏在折叠组件里
