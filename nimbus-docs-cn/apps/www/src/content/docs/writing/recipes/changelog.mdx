<Aside type="note" title="需求">
处于工作状态，查阅信息——读者在维护一个昨天还好好的集成（即长期缺人疼的"维护"任务）。他们的开场问题是：*"改了什么？会不会弄坏我？我该怎么办？"*不传达变更的文档，到下个季度就必然是错的，而且按时间表准时变错——对智能体来说赌注更高，因为更新日志正是修正模型过时先验的地方。
</Aside>

## 何时使用

每个产品一份更新日志（或每个版本划分清晰的界面一份）。两个承重的区分：

- **记录 vs. 政策**：带日期的变更条目住在这里；版本机制如何运作、如何迁移，住在各自的页面上，并从每条破坏性条目链接过去。
- **两种体裁，按读者检索的依据来选：**
  - **以日期为头**——适用于持续交付的产品界面。按发布日期分节；条目以变更为题。
  - **以版本为头**——适用于有版本的产物（一个 SDK、一个具名 API 版本）：按版本分节（`## [2.14.0] — 2026-06-18`，库再加一个 `Unreleased` 小节）。下面的条目规则适用于*每个版本小节之内*。维护者的问题"2.13 到 2.14 之间改了什么？"在以日期为头的日志里无法回答——只要读者会固定版本，就以版本为头。

更新日志不是：

- **提交记录**。更新日志是写给人看的（现在也是写给智能体的）——经过策展、以收益为先的条目，不是合并信息的倾倒场。一个变更如果不值得解释，就不值得列出。
- **发布营销**。发布帖负责说服；更新日志条目负责告知。如果发布帖存在，从条目链接过去——不要用它取代条目。
- **迁移指南**。条目只说*某处会坏*并链出去；迁移的分步操作是操作指南（大迁移则用专门的迁移指南）。

## 标题与描述

- **页面标题：**"Changelog"——固定且符合预期的字符串。
- **条目标题：变更本身，具体而自含。**"Retry backoff is now configurable per endpoint"（重试退避现在可按端点配置）——而不是"Improvements to delivery"（什么也没说），也不是光秃秃的版本号（版本是节的头，不是条目的头）。
- **描述公式（页面）：**"*产品*的每一处值得注意的变更，带日期，标记破坏性变更。"

## 组件建议

- **节标题（日期或版本）+ 条目子标题**是结构。**破坏性标记以粗体置于条目正文开头**（`**Deprecated · Breaking, effective 2026-09-18**`）——这是扫描者和 feed 阅读器看到的第一眼，同时不污染标题的锚点。渲染页面上，标题行还可以放一个 Badge 组件来呼应它。
- **类别标签**（六个标准类别：Added / Changed / Deprecated / Removed / Fixed / Security）作为统一的粗体前缀——它们让页面可以被人眼和机器筛选。
- **不适合**：Steps（迁移步骤住在被链接的指南里）、Cards、截图（改为链接展示新 UI 的文档——更新日志里的截图会永远烂在原地）。

## 结尾

更新日志没有结尾；它只会累积。契约在*顶部*（政策链接、订阅渠道）和每条条目（链到描述新状态的页面）。已发布的条目绝不被*悄悄*改写：如果某条条目后来发现写错了——比如漏标了破坏性变更——就修订原条目，*并*另发一条带日期的更正条目，让按版本扫描的升级者和按时间线阅读的人都能看到。

## 阈值

- **条目正文 ≤ 3 句**。更深的内容住在被链接的详情页、迁移指南或发布帖里。
- **改变已记载行为的条目，链接到更新后的文档页**。Fixed 和 Security 条目在相关页面存在时链接到对应的参考或故障排除页——文档从未记载过的行为的修复无处可指，这没问题。
- **每条破坏性/弃用条目都要带上：影响谁、该做什么、一个日期**。三者缺一，就没到可发布的程度。

## 链接与时效性

更新日志是站点的时效层——条目深链进稳定的文档锚点，这也是参考页锚点永不挪窝的又一个理由（[参考配方](/writing/recipes/reference)）。发布条目和更新它链接的页面是*同一个*动作，不是两个：一条宣告某字段存在、而参考页还没收录它的条目，记载的是一个不存在的产品。条目标题本身就是别人会引用的永久链接——用同一条稳定性规则对待它们。

## 智能体须知

- 更新日志是**先验修正面**：被弃用的东西还活在训练数据里，Deprecated/Removed 条目正是阻止智能体继续推荐它们的机制。把它们写成智能体可以直接执行的平铺陈述："`attempt_count` is deprecated; use `attempt`."
- 日期用 ISO 格式（`2026-06-18`）；"上个月"在被检索出的内容块里毫无意义。
- 每条条目自含：完整的字段名、完整的特性名——被单独检索出的条目必须能独立成立。
- 个性永远不能取代事实。没有具体信息的俏皮话，是读者和智能体都无法据以行动的空话；想要笔调，就加在事实*之后*，而不是取而代之。

## 检查清单

仅供参考——供作者或智能体自查，绝非构建关卡：

- [ ] 体裁经过明确选择：以日期为头（持续交付的界面）或以版本为头（固定版本的产物，库加 Unreleased）
- [ ] 条目以变更为题、自含、按时间倒序
- [ ] 已分类：Added / Changed / Deprecated / Removed / Fixed / Security
- [ ] 破坏性标记置于条目正文开头，附影响谁 + 该做什么 + 日期
- [ ] 弃用公告与移除分属两条独立条目；绝不悄悄处理
- [ ] 改变行为的条目链接到更新后的文档页（Fixed/Security 在目标存在时链接）
- [ ] 条目正文 ≤ 3 句；先讲影响再讲机制；深度内容放被链接的页面
- [ ] 发布时被链接的文档页已同步更新
- [ ] 更正会修订原条目，并追加一条带日期的更正条目
- [ ] 订阅渠道（至少 RSS）链接在顶部；条目锚点稳定
