<Aside type="note" title="需求">
处于工作状态，动手执行——读者想要能复制改造的、能跑的代码。他们的开场问题是：*"给我看 X 的能跑的代码。"*不是要一份操作流程（操作指南），也不是要一堂课（教程）：而是展示一件事*怎么做*的代码——这和"如何去做的指引"是两回事——这是文档缺口里"可复制代码"的那一半。在智能体时代，这是杠杆最高的类型：两类读者形象都从代码示例起步，而智能体会把示例原封不动地粘进代码库。
</Aside>

## 何时使用

当**代码本身就是内容**时写示例——一个值得整段照搬的模式、集成或配置。它不是：

- **操作指南**。操作指南是一份*流程*——跨界面（控制台、CLI、代码）的一串动作，最后有验证。示例是一份*清单*——读者的唯一动作就是复制和改造。如果代码要跑通，读者还必须在代码之外做事，要么把这些压缩成一行前提说明，要么去写操作指南。
- **参考**。参考是完整而中立的，按产品的界面编排索引。示例是选择性、有立场的，按读者的目标编排索引。参考展示 `send()` 接受的每个字段；示例只展示批量发送用到的那三个。
- **教程**。没有叙事、没有教学、没有部分划分。示例默认读者有能力，然后让路。

这一类型的两条铁律：

1. **完整且可运行**。import 齐全、配置齐全、不省略任何行——一段"你需要自行调整"的片段不是示例，是家庭作业。复制粘贴必须产出页面展示的结果。
2. **经过测试**。跑不起来的示例代码比没有更糟——它带着产品的名字在读者的编辑器里报错。能上 CI 就上 CI；无论如何都盖上 `lastVerified`。

## 标题与描述

- **标题：目标加上技术栈。**"Verify signatures **in a Next.js route handler**" · "Debounce webhook bursts **with Redis**"。技术栈限定语是这一类型的标题信号——操作指南陈述与界面无关的目标（"Rotate a signing secret"）；示例则点明代码所处的环境，因为代码就是内容。（这是对操作指南标题语法的有意放宽：祈使动词与操作指南一致，技术栈后缀负责消歧。）绝不叫"Example 3"或"Miscellaneous snippets"。
- **描述公式：**"*代码做什么*，*用的是什么技术栈*。"——例如"Verify Hookline signatures in a Next.js route handler, rejecting replays."（在 Next.js 路由处理器中验证 Hookline 签名，拒绝重放。）

## 脚手架生成此页

安装这份配方——你的编码智能体会读取完整的骨架和清单，并把它们适配到你的产品上：

<PackageManagers pkg="@cloudflare/nimbus-docs" type="dlx" args="add content-example" />

**食谱形态**。多个相关示例可以共用一页：页面取一个**名词短语式的类别标题**（"Signature verification"签名验证、"Batching"批量处理），每个 `##` 条目沿用脚手架安装的单页骨架（去掉 frontmatter）——目标行、前提行、代码、展示结果、How-it-works。页面上唯一一个 `lastVerified` 指其*验证时间最早*的条目。当某个条目的代码超过一屏，就把它拆成独立页面。新增相关示例优先加到类别页；开新页面需要新的类别，或某个条目已经长大。

## 组件建议

- **带标题的代码块**（`title="app/api/hooks/route.ts"`）是标志性组件——文件名是承重上下文。多文件示例用 Code groups；如果实情允许，单文件更好。
- **代码内的注释**承载使用现场的提示（`// rejects deliveries signed >5 min ago`）——这是唯一一处代码注释胜过散文的地方，因为它们能在复制粘贴后幸存。
- **不适合**：Steps（这里没有操作可执行）、Cards、手风琴（藏起来的代码既搜不到也取不出）、语言 Tabs *除非每个标签页都维护并测试过*——没测过的标签页就是躲在测过的示例后面的坏示例。

## 结尾

**展示结果 → How it works（需要时）→ 另见**。没有验证小节（那是操作指南的招式——这里的展示结果和测试承担了这份职责），也没有"后续步骤"的旅程（读者为代码而来，带着代码离开）。

## 阈值

- **每个示例一个目标**。标题检验：如果需要"和"，就拆。
- **解释的体量不得超过代码**。当 How-it-works 开始需要成段而不是列表时，说明一个概念或操作指南正想破壳而出——改成链接。
- **只处理该模式针对的错误，其余任其抛出**。开头就说清错误约定，免得各条目在光秃主路径和生产级加固之间摇摆。写上目标并不需要的防御性代码，是化了妆的散文。
- **食谱页：每个条目用同一套内部模板**，按目标编排索引，最想要的排最前。

## 链接与时效性

链到模式背后的概念，链到解释每个魔法值的参考；并从相关的操作指南*回链*到示例（"只想拿代码？→"）。时效性就是这个类型的全部信誉：示例是被测试过的工件，每次发版只要碰到它们的 API 就重跑（可能的话上 CI），盖上 `lastVerified`——一整本编译不过的食谱，是"产品无人维护"所能发出的最响亮信号。

## 智能体须知

- 智能体会原样搬走示例，所以**完整即正确**：一个被省略的 import 会变成别人代码库里一个被幻觉出来的 import；代码里一个 `...` 会变成任何东西。
- 把前提写成页面上的可核查事实（版本、环境变量）——智能体没法从你项目渲染出的截图里推断它们。
- 全程使用真实值；占位符只出现在尖括号 `<angle-brackets>` 里，且只在真实值不可能存在的地方。
- How-it-works 列表是检索黄金：它把不显然的行和它的原因装进同一块内容，这正是阻止智能体"化简"承重部分（`req.text()` → `req.json()`）的关键。凡是依赖特定厂商行为的条目都要显式标记，让改造示例的智能体知道该复查什么。

## 检查清单

仅供参考——供作者或智能体自查，绝非构建关卡：

- [ ] 标题是目标加技术栈（食谱页：名词短语类别）；一个目标
- [ ] 前提用一行写成可核查事实（版本、环境）
- [ ] 粘贴即完整可运行——import 齐全、零省略、严格设置下能过类型检查
- [ ] 有展示结果：粘贴的代码产出什么，以及如何触发它
- [ ] 真实值；占位符只在尖括号里
- [ ] How-it-works 只覆盖不显然的行；依赖特定厂商行为的假设已标记
- [ ] 错误处理只限于该模式针对的范围
- [ ] 变体是链接而不是附加清单；食谱条目共用一套内部模板
- [ ] 已对照当前版本测试（可能的话上 CI）；盖了 `lastVerified`（食谱页：取最早的条目）
