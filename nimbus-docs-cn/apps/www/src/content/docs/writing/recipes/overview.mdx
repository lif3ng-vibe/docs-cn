<Aside type="note" title="需求">
读者刚刚抵达——可能来自搜索、某个链接或侧边栏——还不知道这个产品区是不是自己要找的，也不知道该往哪儿走。他们的开场问题是：*"这是什么？从哪儿开始？"*这一类型服务于学习和工作开始之前的"评估与定位"时刻。它与快速上手一起，构成每个产品区必备的两类页面。
</Aside>

## 何时使用

每个产品或主要产品区只有一篇概览——也就是侧边栏对应栏目展开后落地的那一页。**范围说明**：本配方针对*产品区*概览。横跨多个区的文档站*首页*是一个更轻量的变体：路由纪律相同，但定位段落缩短为一句标语，可用性/CTA 栏位通常也不适用。概览不是：

- **概念页**。概览说出产品做什么；概念页解释怎么做、为什么。如果某一段开始解释架构或权衡，把它挪到概念页并放个链接。
- **光秃秃的目录**。没有定位信息的一串链接，不过是把侧边栏复制进了一个页面。
- **营销页**。读者已经点进文档了。说清楚它做什么、给谁用就够了，别推销。如果营销内容不得不挨着文档存在，把它对智能体隔离开，而不是混进正文。

要守住的平衡：**用足以定位的文字量（一段话）完成导引，然后就是纯路由。**

## 标题与描述

- **标题：产品或区域名，名词形式。**"Hookline"或"Endpoints"——不要"Hookline documentation"，不要动名词形式，也不要"Introduction"。
- **描述公式：**"*它是什么*——*它为谁做什么*。"——例如"Hookline delivers your application's webhooks — signed, retried, and observable."（Hookline 交付你应用的 webhook——带签名、会重试、可观测。）

## 组件建议

- **Cards / CardGrid** 是标志性组件——概览是唯一把卡片当作正文内容的类型，因为路由*本身就是*正文。卡片文字保持"一个名字加一句话"；一张解释型的卡片就是装在盒子里的概念段落。在 `.md` 版本中，卡片会摊平成"链接+描述"列表——写那一句简介时，要让它在两种形态下都成立。
- 当网格逼你注水凑字，或某个分组确实要突破约 5 个链接的上限时，**链接列表**胜过卡片——列表在数量大时更好扫读。
- **不适合**：Steps（这里没有任何操作）、代码块（这里没有要查的东西——导语行里的行内代码没问题）、手风琴折叠（藏起内容的概览，等于藏起自己的地图）。

## 结尾

当相邻区域确实容易与本区混淆时，以**相关**（Related）收尾——每条一行，说清区别。没有什么需要辨析时，就以最后一个能力分组结束页面。无论如何，不要"后续步骤"小节：整页就是后续步骤。

## 阈值

- **导语正文 ≤ 1 段**（外加可选的成效列表）。更长了，说明解释性内容在渗入。
- **3–5 个能力分组，每组 ≤ 约 5 个链接**——整页大约两到三屏。超过这个量，产品区需要的是子概览（导航页模式），而不是更长的概览。
- **按读者任务分组**（"Send events""Secure"），绝不按内部团队或功能开关命名。

## 链接与时效性

这一页上的每个链接都是承重墙——这里的死链或过期路由会把读者困在大门口。该区域上新页面时，把它加进来（或决定不加）是发布工作的一部分。把最近一次全量路由核查记录在 frontmatter 里（`lastUpdated` 或一条 `lastVerified` 注记），让过期可见，而不是靠人发现。

## 智能体须知

- 本页是某个范围化 `llms.txt` 的人类可读对应物——职责相同、形态相同：名字、一行摘要、带描述的分栏链接。写卡片的一句话简介时，要让它在 Markdown 版本里也能当链接描述用；智能体就是根据它们决定抓取什么。
- 被问到"Hookline 是什么"时，智能体引用的就是那段导语——让它独立成篇、自成一体且准确。

## 检查清单

仅供参考——供作者或智能体自查，绝非构建关卡：

- [ ] 标题是产品/区域名，名词形式，不带"documentation"
- [ ] 一段导语（外加可选的成效列表）；走错门的读者在这里就能意识到
- [ ] 可用性若随套餐/地区/阶段而异，需写明
- [ ] 快速上手 CTA 排在所有链接之首
- [ ] 分组按读者任务命名；卡片只路由，不做解释
- [ ] 存在易混淆的相邻区域时提供"相关"，并附一行辨析
- [ ] 每个链接都可解析；该区域的新页面已收录（或明确决定不收录）
- [ ] 无步骤、无代码块、没有任何内容藏在手风琴里
