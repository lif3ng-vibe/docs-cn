<Aside type="note" title="需求">
处于工作状态，动手执行——是在恢复，不是在推进。读者手里有一条错误字符串或一个症状，会把它粘进搜索框（他们的智能体也会）。他们的开场问题是：*"为什么会出现这个？怎么让它停下？"*错误是内容，不是例外——而且这是人类搜索与智能体检索完美对齐的类型，因为两者都按精确字符串匹配。
</Aside>

## 何时使用

故障排除内容住在两个地方，本配方两者都覆盖：

- **内联在失败发生的页面上**——默认形式。在操作指南里用一个"What if……"提示块，或在特性页结尾放一个 FAQ 折叠。内联形式保持同样的内部结构，只是压缩：

  > **登录时如果报 `Error: no workspace selected` 怎么办？**
  > CLI 已完成认证，但没有指向任何工作区。运行 `hookline workspace use <name>` 后重试。

- **每个产品区一篇专门的故障排除页**，当内联条目超过约 5 条，或同一个失败横跨多个页面时。

它不是：

- **操作指南。**操作指南奔着目标去；故障排除从失败中恢复。"Set up delivery alerts"（设置投递告警）是指南，即使它牵涉问题。
- **错误参考。**如果产品有稳定的错误*码*，一套完整的逐码目录就是参考材料（每码一条、模板统一——见[参考配方](/writing/recipes/reference)）；故障排除页覆盖症状、多成因问题，以及错误码捕捉不到的叙事型"它很慢/它时好时坏"的情况。小产品可以两者合一；但要说明哪页管什么。
- **全局 FAQ。**有已知答案的问题，应该放在本该回答它的页面上。故障排除页按*失败*组织，不按*问题*组织。

## 标题与描述

- **条目标题：逐字的症状——理想情况是确切的错误消息。**"Error: signature timestamp outside tolerance"在搜索、检索和侧边栏扫读中都胜过"Signature problems"。长消息：保留有辨识度的子串，裁到大约 70 个字符，用 ASCII `...` 标记截断处。消息类型（"Error:""Warning:"）留在标题里。没有消息的症状型条目改用可观察的措辞："Deliveries succeed but arrive twice."（投递成功但到达两次。）
- **页面标题：**"Troubleshooting *区域*"——例如"Troubleshooting delivery"（故障排除：投递）。
- **描述公式：**"*区域*常见失败的修复办法，按症状索引。"

## 组件建议

- **逐字消息放进围栏代码块**——它是搜索、读者和检索的匹配目标。展示一个真实、具体的实例，可变取值也照放（`skew 512s > 300s` 展示了机理；稳定的子串仍能匹配搜索）。绝不转述错误；绝不省略它的辨识部分。
- **加粗的 Cause/Fix/Verify 标签**（或固定的三件套子标题）——统一的内部顺序，才能让惊慌的读者直接跳到 Fix。
- **手风琴**适合内联形式（特性页结尾的 FAQ 式）；在专门的页面上，条目保持展开——藏起来的症状搜不到，而这一页存在的意义就是被扫读。
- **不适合：**Cards、营销腔、不给修复的安抚（"这通常无害"——那就接着说什么时候不是）。

## 结尾

专门页面以**Still stuck?（还是没解决？）**收尾——附一条"先收集这些信息"清单的升级路径。这是该类型的诚实条款：暗示自己完备的故障排除页，会用它漏掉的那一个失败把读者困在原地。

## 阈值

- **内联到约 5 条，然后开专门页面**——并在原内联处留下一个链接。
- **最常见的失败排最前；丢数据的失败可以插队。**排序就是分诊。
- **每个变通办法都要写明代价和永久替代方案。**把变通当修复写，技术债就是这样被文档固化的。

## 链接与时效性

每条 Cause 都链到解释机理的概念；每个多步 Fix 都链到（或本身就是）一篇操作指南。用支持工单和社区提问喂养这一页——它是唯一一份待办清单会自己生长的类型——并在产品修复了底层失败后修剪条目：给已不存在的问题写的修复，只会让读者去找一个已经消失的设置。对照当前版本全面核查一遍时，盖上页面的 `lastVerified` 日期。

## 智能体须知

- 这是智能体按精确字符串检索的类型——围栏代码块里逐字的错误就是全部胜负手。展示一个真实具体的实例；稳定的子串承担匹配。省略号（ASCII `...`）只允许出现在长消息的*标题*里，且绝不落在辨识部分上。
- 把 Cause → Fix 组织成智能体可直接执行的陈述；"检查你的配置"不是修复，`hookline test-event --endpoint <id>` 才是。
- 让每条条目完全自含——条目 N 被检索时，不会带着条目 N−1，也不会带着页面引言。

## 检查清单

仅供参考——供作者或智能体自查，绝非构建关卡：

- [ ] 条目标题是逐字消息或可观察症状（长消息裁剪到有辨识度的子串，约 70 字符）
- [ ] 带消息的条目都在围栏代码块里以一个具体实例展示它；纯症状条目在第一行写明可观察行为
- [ ] 固定内部顺序：Symptom → Cause → Fix（→ Verify）；多成因条目让每个成因与它的确认方法和修复配对
- [ ] 变通办法有标注、有代价说明，并与永久修复配对
- [ ] 最常见的失败排最前；丢数据的失败插队
- [ ] 专门页面以 Still stuck? + 先收集这些信息清单收尾
- [ ] Cause 链到概念；多步修复链到操作指南
- [ ] 底层失败修复后条目已修剪；全面核查时盖上 `lastVerified`
