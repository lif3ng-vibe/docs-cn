# WorkflowAgent

`@ai-sdk/workflow` 中的 `WorkflowAgent` 专为构建**持久、可恢复的智能体**而设计，运行在[工作流](https://vercel.com/docs/workflow)之内。它提供与 [`ToolLoopAgent`](/docs/agents/building-agents) 相同的智能体循环，并新增了自动状态持久化、工具 schema 序列化，以及可在工作流步骤边界间存续的内置工具审批流程。

## 为什么需要持久化智能体？

标准的 `ToolLoopAgent` 完全在内存中运行——一旦进程崩溃，所有进度都会丢失。对于会进行多次工具调用的生产级智能体而言，这会带来以下问题：

- **有状态**——长时间运行的智能体循环需要跨进程边界持久化状态
- **可恢复性**——某一步骤失败时，你希望从上一个检查点重试，而不是从头再来
- **人机协作**——需要用户审批的工具必须能暂停智能体并稍后恢复
- **可观测性**——每次工具调用都作为独立的工作流步骤运行，可在仪表盘中查看

`WorkflowAgent` 通过在工作流内运行来解决这些问题，其中每次工具执行都是一个具有自动重试能力的持久化步骤。

## 何时用 WorkflowAgent 还是 ToolLoopAgent

|                         | ToolLoopAgent             | WorkflowAgent                                    |
| ----------------------- | ------------------------- | ------------------------------------------------ |
| **包**                  | `ai`                      | `@ai-sdk/workflow`                               |
| **运行时**              | 内存中                    | 工作流                                           |
| **持久性**              | 崩溃后丢失                | 可在重启后存续                                   |
| **工具重试**            | 手动                      | 自动（借助工作流步骤）                           |
| **人工审批**            | 内置                      | 内置，且可在挂起后存续                           |
| **`generate()` 方法**   | 可用                      | 可用，模型调用为持久化的非流式调用               |
| **`stream()` 方法**     | 可用                      | 主 API                                           |
| **流式输出**            | `streamText` 返回值       | 通过 `writable` 参数写出 `ModelCallStreamPart`   |

如果使用场景较简单、不需要持久化，请使用 `ai` 包中的 [`ToolLoopAgent`](/docs/agents/building-agents)。

## 安装

```bash
npm install @ai-sdk/workflow workflow@5
```

`@ai-sdk/workflow` 需要 Workflow 5，并依赖 `ai` 包和 `zod` 这两个 peer 依赖。`workflow` 包提供 Workflow DevKit 运行时（`getWritable`、`'use workflow'`、`'use step'`）。

## 创建 WorkflowAgent

通过实例化 `WorkflowAgent` 类并传入模型、指令和工具来定义一个智能体：

```ts
import { WorkflowAgent } from '@ai-sdk/workflow';
import { tool } from 'ai';
import { z } from 'zod';

const agent = new WorkflowAgent({
  model: 'anthropic/claude-sonnet-5.5',
  instructions: 'You are a helpful assistant.',
  tools: {
    weather: tool({
      description: 'Get weather for a location',
      inputSchema: z.object({
        location: z.string(),
      }),
      execute: async ({ location }) => ({
        location,
        temperature: 72,
      }),
    }),
  },
});
```

### 模型解析

`model` 参数接受两种形式：

```ts
// String — AI Gateway model ID
new WorkflowAgent({ model: 'anthropic/claude-sonnet-5.5' });

// Provider instance
import { openai } from '@ai-sdk/openai';
new WorkflowAgent({ model: openai('gpt-6-astra') });
```

## 在工作流中使用智能体

`WorkflowAgent` 旨在运行在工作流函数之内。关键集成点如下：

1. 用 `'use workflow'` 标记你的函数
2. 将 `getWritable()` 传给智能体的 `stream()` 方法
3. 从你的 API 路由启动工作流

### 端到端示例

```ts filename="workflow/agent-chat.ts"
import { WorkflowAgent, type ModelCallStreamPart } from '@ai-sdk/workflow';
import { convertToModelMessages, tool, type UIMessage } from 'ai';
import { getWritable } from 'workflow';
import { z } from 'zod';

export async function chat(messages: UIMessage[]) {
  'use workflow';

  const modelMessages = await convertToModelMessages(messages);

  const agent = new WorkflowAgent({
    model: 'anthropic/claude-sonnet-5.5',
    instructions: 'You are a flight booking assistant.',
    tools: {
      searchFlights: tool({
        description: 'Search for available flights',
        inputSchema: z.object({
          origin: z.string(),
          destination: z.string(),
          date: z.string(),
        }),
        execute: searchFlightsStep,
      }),
      bookFlight: tool({
        description: 'Book a specific flight',
        inputSchema: z.object({
          flightId: z.string(),
          passengerName: z.string(),
        }),
        execute: bookFlightStep,
      }),
    },
  });

  const result = await agent.stream({
    messages: modelMessages,
    writable: getWritable<ModelCallStreamPart>(),
  });

  return { messages: result.messages };
}
```

```ts filename="app/api/chat/route.ts"
import { createModelCallToUIChunkTransform } from '@ai-sdk/workflow';
import { createUIMessageStreamResponse, type UIMessage } from 'ai';
import { start } from 'workflow/api';
import { chat } from '@/workflow/agent-chat';

export async function POST(request: Request) {
  const { messages }: { messages: UIMessage[] } = await request.json();

  const run = await start(chat, [messages]);

  return createUIMessageStreamResponse({
    stream: run.readable.pipeThrough(createModelCallToUIChunkTransform()),
  });
}
```

### 消息转换

`WorkflowAgent.stream()` 接受的是 `ModelMessage[]`，而不是 `UIMessage[]`。当从客户端（通过 `useChat`）接收消息时，请先做转换：

```ts
import { convertToModelMessages, type UIMessage } from 'ai';

export async function chat(messages: UIMessage[]) {
  'use workflow';

  const modelMessages = await convertToModelMessages(messages);

  const result = await agent.stream({
    messages: modelMessages,
    // ...
  });
}
```

### 可写流

`ToolLoopAgent` 中你消费的是返回的流；而 `WorkflowAgent` 会把原始的 `ModelCallStreamPart` 数据块写入由工作流运行时通过 `getWritable()` 提供的 `writable` 流。在响应边界处，使用 `createModelCallToUIChunkTransform()` 把它们转换为 `UIMessageChunk` 对象再交给客户端：

```ts
import { createModelCallToUIChunkTransform } from '@ai-sdk/workflow';
import { createUIMessageStreamResponse } from 'ai';

// Convert raw model stream parts → UI message chunks
return createUIMessageStreamResponse({
  stream: run.readable.pipeThrough(createModelCallToUIChunkTransform()),
});
```

该 transform 还会转发 `WorkflowAgent` 在重试时发出的 `reset-step` 事件。
客户端会在处理重试输出之前，先移除失败的模型调用步骤中不完整的部分。

## 使用 WorkflowChatTransport 实现可恢复的流式

工作流函数可能超时，也可能被网络故障中断。`WorkflowChatTransport` 是 [`ChatTransport`](/docs/ai-sdk-ui/transport) 的一个实现，可自动处理这些中断——它会检测流是否在缺少 `finish` 事件的情况下结束，并重新连接以从中断处继续。

```tsx filename="app/page.tsx"
'use client';

import { useChat } from '@ai-sdk/react';
import { WorkflowChatTransport } from '@ai-sdk/workflow/client';
import { useMemo } from 'react';

export default function Chat() {
  const transport = useMemo(
    () =>
      new WorkflowChatTransport({
        api: '/api/chat',
        maxConsecutiveErrors: 5,
      }),
    [],
  );

  const { messages, sendMessage } = useChat({ transport });

  // ... render chat UI
}
```

该 transport 要求你的 POST 端点返回 `x-workflow-run-id` 响应头，并在 `{api}/{runId}/stream` 处提供一个用于重连的 GET 端点：

```ts filename="app/api/chat/route.ts"
import { createModelCallToUIChunkTransform } from '@ai-sdk/workflow';
import { createUIMessageStreamResponse, type UIMessage } from 'ai';
import { start } from 'workflow/api';
import { chat } from '@/workflow/agent-chat';

export async function POST(request: Request) {
  const { messages }: { messages: UIMessage[] } = await request.json();
  const run = await start(chat, [messages]);

  return createUIMessageStreamResponse({
    stream: run.readable.pipeThrough(createModelCallToUIChunkTransform()),
    headers: {
      'x-workflow-run-id': run.runId,
    },
  });
}
```

```ts filename="app/api/chat/[runId]/stream/route.ts"
import { createModelCallToUIChunkTransform } from '@ai-sdk/workflow';
import { createUIMessageStreamResponse } from 'ai';
import type { NextRequest } from 'next/server';
import { getRun } from 'workflow/api';

export async function GET(
  request: NextRequest,
  { params }: { params: Promise<{ runId: string }> },
) {
  const { runId } = await params;
  const startIndex = Number(
    new URL(request.url).searchParams.get('startIndex') ?? '0',
  );
  if (!Number.isSafeInteger(startIndex) || startIndex < 0) {
    return Response.json(
      { error: 'startIndex must be a non-negative safe integer' },
      { status: 400 },
    );
  }

  const run = await getRun(runId);
  const readable = run
    .getReadable({ startIndex: 0 })
    .pipeThrough(
      createModelCallToUIChunkTransform({ uiStartIndex: startIndex }),
    );

  return createUIMessageStreamResponse({
    stream: readable,
    headers: {
      'x-workflow-run-id': runId,
    },
  });
}
```

`WorkflowChatTransport` 计数的是 `UIMessageChunk` 对象，而持久化的
`WorkflowAgent` 流存储的是原始的 `ModelCallStreamPart` 对象。如上所示，从索引
`0` 起重放原始流，并在 `createModelCallToUIChunkTransform()` 中应用非负的 UI
游标。负数起始索引要求数据流本身已经存储 `UIMessageChunk` 对象，无法用于这种
从原始流到 UI 流的转换。

完整 API 参考请见 [`WorkflowChatTransport`](/docs/reference/ai-sdk-workflow/workflow-chat-transport)。

## 工具即工作流步骤

用 `'use step'` 标记工具的 execute 函数，使其成为持久化的工作流步骤。这样每次工具调用都能获得：

- **自动重试**——失败的工具调用会自动重试（默认：3 次）
- **持久化**——结果可在进程重启后存续
- **可观测性**——每次工具调用在工作流仪表盘中呈现为一个独立步骤

```ts
async function searchFlightsStep(input: {
  origin: string;
  destination: string;
  date: string;
}) {
  'use step';
  const response = await fetch(`https://api.flights.example/search?...`);
  return response.json();
}

async function bookFlightStep(input: {
  flightId: string;
  passengerName: string;
}) {
  'use step';
  const response = await fetch('https://api.flights.example/book', {
    method: 'POST',
    body: JSON.stringify(input),
  });
  return response.json();
}
```

未标记 `'use step'` 的工具仍可使用，但会被当作普通的内存函数运行，没有持久化保障。

## 工具审批

对 `WorkflowAgent` 而言，人工审批通过在工具定义上设置 `needsApproval` 来配置。
这是 `WorkflowAgent` 特有的；对于 `generateText`、`streamText` 和
`ToolLoopAgent`，请改用 `toolApproval`。当工作流工具设置了 `needsApproval`
时，智能体会暂停并向可写流发出审批请求。工作流随之挂起，直到用户批准或拒绝：

```ts
const agent = new WorkflowAgent({
  model: 'anthropic/claude-sonnet-5.5',
  tools: {
    bookFlight: tool({
      description: 'Book a flight',
      inputSchema: z.object({
        flightId: z.string(),
        passengerName: z.string(),
      }),
      needsApproval: true, // Always require approval
      execute: bookFlightStep,
    }),
    cancelBooking: tool({
      description: 'Cancel a booking',
      inputSchema: z.object({ bookingId: z.string() }),
      // Conditional approval based on input
      needsApproval: async input => {
        return input.bookingId.startsWith('VIP-');
      },
      execute: cancelBookingStep,
    }),
  },
});
```

由于工作流是持久化的，审批请求可在进程重启后存续——用户数小时后再批准，智能体也能恢复运行。

### 签名的工具审批

客户端提供的消息历史在重放到工作流之前可能被篡改。对于执行敏感操作的工具，
请配置 `experimental_toolApprovalSecret` 来对审批请求进行身份验证：

```ts highlight="4"
const agent = new WorkflowAgent({
  model: 'anthropic/claude-sonnet-5.5',
  experimental_toolApprovalSecret: {
    environmentVariable: 'TOOL_APPROVAL_SECRET',
  },
  tools: {
    bookFlight: tool({
      description: 'Book a flight',
      inputSchema: z.object({ flightId: z.string() }),
      needsApproval: true,
      execute: bookFlightStep,
    }),
  },
});
```

智能体会对审批 ID、工具调用 ID、工具名称和已验证的输入进行 HMAC 签名。当已批准
的消息历史被重放时，签名缺失或无效都会阻止工具执行。该签名在持久化的模型调用流、
`createModelCallToUIChunkTransform()`、`addToolApprovalResponse()` 和
`convertToModelMessages()` 中均得到保留。

请使用至少 32 字节的高熵密钥，并让每个可能发起或恢复审批的 worker 都能获取同一
密钥。在用旧密钥签署的审批仍处于待处理状态期间，保持旧密钥可用；更换密钥会使这些
待处理的审批失效。

`WorkflowAgent` 只把环境变量名传入签名与验证步骤。每个步骤都从自己的本地环境中
读取密钥，原始值绝不出现在步骤参数、持久化流数据、回调或遥测事件中。请在每个
worker 上都配置该环境变量，并且不要把密钥值放入 `runtimeContext` 或 `toolsContext`。

你也可以在 `agent.stream()` 中提供 `experimental_toolApprovalSecret`。
流级别的取值会覆盖构造函数中的默认值。

## 循环控制

与 `ToolLoopAgent` 不同，`WorkflowAgent` 不会应用默认的步骤上限。省略 `stopWhen`
时，它会一直运行，直到模型停止调用工具或满足其他自然终止条件。

<Note>
  反复调用工具的模型可以进行无限次模型调用。当你需要限制执行时间和成本时，
  请配置显式的停止条件。
</Note>

控制智能体可以执行的步骤数：

```ts
import { isStepCount } from 'ai';

const result = await agent.stream({
  messages,
  stopWhen: isStepCount(10), // Stop after 10 LLM calls
});
```

省略 `stopWhen` 本身就能让 `WorkflowAgent` 一直运行到完成工具调用为止。你也可以
用 `isLoopFinished()` 把这一意图显式表达出来：

```ts
import { isLoopFinished } from 'ai';

const result = await agent.stream({
  messages,
  stopWhen: isLoopFinished(),
});
```

对 `WorkflowAgent` 而言，`isLoopFinished()` 等价于省略 `stopWhen`。请谨慎使用，
因为持续调用工具的模型可能无限运行并产生可观成本。参见
[`isLoopFinished()`](/docs/reference/ai-sdk-core/loop-finished)。

## 结构化输出

使用 `Output` 将智能体响应解析为带类型的对象：

```ts
import { Output } from '@ai-sdk/workflow';
import { z } from 'zod';

const result = await agent.stream({
  messages,
  output: Output.object({
    schema: z.object({
      sentiment: z.enum(['positive', 'neutral', 'negative']),
      summary: z.string(),
    }),
  }),
});

console.log(result.output); // { sentiment: 'positive', summary: '...' }
```

## 配置选项

`WorkflowAgent` 接受与 `ToolLoopAgent` 相同的生成设置（`temperature`、`maxOutputTokens`、`topP` 等），外加工作流专属选项。

### runtimeContext 与 toolsContext

在智能体循环中传递服务端状态，而不把它放进提示词。请用这两者替代之前的 `experimental_context` 选项。

- `runtimeContext` 是贯穿 `prepareStep`、生命周期回调和 `onEnd` 的共享智能体状态。把它当作不可变值对待；在 `prepareStep` 中返回新值，即可为当前及后续步骤更新它。
- `toolsContext` 是以工具名为键的按工具映射。每个工具的 `execute` 只能看到自己的已验证条目，即 `context`。声明了 `contextSchema` 的工具会在执行前针对该 schema 校验自己的条目。

```ts filename="workflow/agent-chat.ts"
import { WorkflowAgent } from '@ai-sdk/workflow';
import { tool } from 'ai';
import { z } from 'zod';

const agent = new WorkflowAgent({
  model: 'anthropic/claude-sonnet-4-6',
  tools: {
    weather: tool({
      description: 'Get the weather for a city.',
      inputSchema: z.object({ city: z.string() }),
      contextSchema: z.object({
        defaultUnit: z.enum(['celsius', 'fahrenheit']),
      }),
      execute: async ({ city }, { context }) => ({
        city,
        unit: context.defaultUnit,
      }),
    }),
  },

  // Shared agent state — available in `prepareStep`, lifecycle callbacks, and `onEnd`.
  runtimeContext: {
    tenantId: 'tenant_123',
    requestId: 'req_abc',
    plan: 'enterprise',
  },

  // Per-tool context — each tool sees only its own validated entry.
  toolsContext: {
    weather: { defaultUnit: 'celsius' },
  },

  prepareStep: ({ runtimeContext }) => {
    if (runtimeContext.plan === 'enterprise') {
      return { temperature: 0.2 };
    }
    return {};
  },
});
```

`runtimeContext` 和 `toolsContext` 也可以按调用传给 `stream()`，此时会覆盖构造函数级别的默认值。

由于 `WorkflowAgent` 运行在 Workflow 运行时之中，上下文值可能会跨工作流与步骤边界被持久化并重放。请保持 `runtimeContext`、`toolsContext` 以及从 `prepareStep` 返回的任何上下文值都可序列化。使用字符串、数字、布尔值、数组、普通对象、日期、URL、Map、Set 等 Workflow 支持的结构化数据。不要把函数、类实例、symbol、`WeakMap`、`WeakSet`、数据库客户端或 SDK 客户端放入上下文。请改为传递标识符或配置数据，并在步骤函数内重建不可序列化的资源。

这一点不同于 `ToolLoopAgent`——后者在内存中运行，可以在单个进程的生命周期内承载更丰富的 JavaScript 值。对于 `WorkflowAgent`，把上下文当作持久化数据来对待，才能保证工作流重放与步骤执行的可靠性。

### experimental_sandbox

当工具需要执行环境时，传入一个沙箱会话。沙箱以 `experimental_sandbox` 的形式提供给
工具描述和 `execute` 函数，也提供给 `prepareStep`，你可以在那里为当前步骤覆盖它：

```ts
const agent = new WorkflowAgent({
  model: 'anthropic/claude-sonnet-5.5',
  tools: {
    shell: tool({
      description: 'Run a shell command in the sandbox.',
      inputSchema: z.object({ command: z.string() }),
      execute: async ({ command }, { experimental_sandbox }) => {
        if (!experimental_sandbox) {
          throw new Error('Sandbox is not available');
        }

        return experimental_sandbox.run({ command });
      },
    }),
  },
  experimental_sandbox: sandbox,
});

await agent.stream({
  messages,
  writable: getWritable(),
  experimental_sandbox: requestSandbox, // Overrides the constructor default.
});
```

`experimental_sandbox` 是一个活的运行时句柄，不是持久化上下文。不要把它存入
`runtimeContext` 或 `toolsContext`。如果某个工具作为单独的工作流步骤运行，
请传递可序列化的沙箱标识符或配置，并在该步骤内重新接驳。

### prepareCall

在智能体循环开始前调用一次。用它基于运行时上下文来变换模型、指令或其他设置：

```ts
const agent = new WorkflowAgent({
  model: 'anthropic/claude-sonnet-5.5',
  prepareCall: async ({ model, tools, messages }) => {
    return {
      instructions: `Current time: ${new Date().toISOString()}`,
    };
  },
});
```

### prepareStep

在每个步骤（LLM 调用）之前调用。用它来修改设置、管理上下文或动态注入消息：

```ts
const agent = new WorkflowAgent({
  model: 'anthropic/claude-sonnet-4-6',
  prepareStep: async ({ stepNumber, experimental_sandbox }) => {
    if (stepNumber > 5) {
      return { toolChoice: 'none' }; // Force text response after 5 steps
    }
    if (experimental_sandbox) {
      return { temperature: 0.2 };
    }
    return {};
  },
});
```

`prepareCall` 和 `prepareStep` 也可以在 `stream()` 中按调用传入。

## 生命周期回调

智能体提供用于日志记录、可观测性和自定义遥测的生命周期回调。所有回调都可在构造函数中定义（智能体级别），也可在 `stream()` 中定义（按调用）。两者都提供时会都触发（构造函数的先触发）：

```ts
const agent = new WorkflowAgent({
  model: 'anthropic/claude-sonnet-5.5',

  onStart({ messages }) {
    console.log(`Agent started with ${messages.length} messages`);
  },

  onStepStart({ stepNumber }) {
    console.log(`Step ${stepNumber} starting`);
  },

  onToolExecutionStart({ toolCall }) {
    console.log(`Calling tool: ${toolCall.toolName}`);
  },

  onToolExecutionEnd({ toolCall, success, durationMs }) {
    console.log(`Tool finished: ${toolCall.toolName}`, {
      success,
      durationMs,
    });
  },

  onStepEnd({ usage, finishReason }) {
    console.log('Step done:', { finishReason });
  },

  onEnd({ steps, totalUsage }) {
    console.log(`Completed in ${steps.length} steps`);
  },
});
```

对于具体的工具集，`WorkflowAgentToolExecutionStartEvent` 和
`WorkflowAgentToolExecutionEndEvent` 会保留每个工具名称与其输入、上下文和输出
类型之间的对应关系。TypeScript 可以直接收窄嵌套的 `toolCall`；当你需要按工具
名称收窄关联的 `toolContext` 或 `output` 字段时，请使用 `Extract` 或用户自定义
类型守卫。

工具输入回调（`onInputStart`、`onInputDelta` 和 `onInputAvailable`）同样会被
`WorkflowAgent` 保留。模型调用运行在持久化步骤内，而回调函数则留在工作流上下文
中，因为任意函数无法跨越步骤边界。因此，`WorkflowAgent` 会在模型步骤期间记录回调
事件，并在该步骤完成后、工具执行与步骤生命周期回调之前，按顺序重放它们。它们不会
与模型生成并发运行，也无法提供进行中的取消或背压。每个回调在 `contextSchema`
校验之后，会收到所属工具的 `toolsContext` 条目。

对于高度碎片化的工具输入，`onInputDelta` 的重放数据会成为持久化模型步骤结果的
一部分。只有在确实需要每个生成的增量时才配置 `onInputDelta`；否则请省略它，
以避免保留增量重放数据。

已弃用的 `experimental_onStart` 和 `experimental_onStepStart` 名称为向后兼容
而继续可用。当在同一个构造函数或 `stream()` 调用中同时提供稳定名称与实验名称时，
会使用稳定回调。

## 类型推断

为类型安全的客户端组件推断 UI 消息类型：

```ts
import { WorkflowAgent, InferWorkflowAgentUIMessage } from '@ai-sdk/workflow';

const myAgent = new WorkflowAgent({
  // ... configuration
});

export type MyAgentUIMessage = InferWorkflowAgentUIMessage<typeof myAgent>;
```

## 从 `DurableAgent` 迁移

`WorkflowAgent` 取代了 Workflow DevKit 的 [`DurableAgent`](https://workflow-sdk.dev/docs/api-reference/workflow-ai/durable-agent)。两者核心思想相同——都是运行在工作流之内的持久化智能体循环——但 `WorkflowAgent` 把该类移入了 AI SDK，收紧了类型定义，并引入了一等公民式的工具审批。如果你目前在使用 `DurableAgent`，请按以下步骤切换。

### 修改导入与类名

`DurableAgent` 由 `workflow/ai` 导出。`WorkflowAgent` 及其辅助工具由 `@ai-sdk/workflow` 导出。

```diff
- import { DurableAgent } from 'workflow/ai';
+ import { WorkflowAgent, type ModelCallStreamPart } from '@ai-sdk/workflow';

- const agent = new DurableAgent({
+ const agent = new WorkflowAgent({
    model: 'anthropic/claude-sonnet-5.5',
    instructions: 'You are a helpful assistant.',
    tools: { /* ... */ },
  });
```

在 `workflow` 之外再安装新包：

```bash
npm install @ai-sdk/workflow workflow@5
```

### 写入 `ModelCallStreamPart` 而非 `UIMessageChunk`

`DurableAgent` 会把 `UIMessageChunk` 对象直接写入 `getWritable()` 返回的可写流。`WorkflowAgent` 写入的是更底层的 `ModelCallStreamPart` 形状，并把转换留到响应边界处的 transform 中完成。这使持久化流保持 provider 形状，避免把 UI 协议固化到工作流负载里。

```diff
  // Inside the workflow
  await agent.stream({
    messages,
-   writable: getWritable<UIMessageChunk>(),
+   writable: getWritable<ModelCallStreamPart>(),
  });
```

```diff
  // Inside the route handler
+ import { createModelCallToUIChunkTransform } from '@ai-sdk/workflow';

  return createUIMessageStreamResponse({
-   stream: run.readable,
+   stream: run.readable.pipeThrough(createModelCallToUIChunkTransform()),
  });
```

### 用 `stopWhen` 替换 `maxSteps`

`DurableAgent` 直接接受 `maxSteps`。`WorkflowAgent` 使用 AI SDK 共享的 `stopWhen` 条件，因此同一套停止逻辑可以作用于 `ToolLoopAgent`、`generateText` 和 `streamText`。

```diff
+ import { isStepCount } from 'ai';

  await agent.stream({
    messages,
-   maxSteps: 10,
+   stopWhen: isStepCount(10),
  });
```

完整停止条件列表参见[循环控制](/docs/agents/loop-control)。

### 用 `output` 替换 `experimental_output`

```diff
+ import { Output } from '@ai-sdk/workflow';

  await agent.stream({
    messages,
-   experimental_output: Output.object({ schema }),
+   output: Output.object({ schema }),
  });
```

返回值现在位于 `result.output`（此前是 `result.experimental_output`）。

### WorkflowAgent 中对人机协作工具使用 `needsApproval`

在 `DurableAgent` 中，工具审批是在工具的 `execute` 函数内部调用 Hook 来实现的。`WorkflowAgent` 把审批升级为一等公民的工具属性——由智能体发出审批请求、挂起工作流，并在用户响应后自动恢复。

```diff
  bookFlight: tool({
    description: 'Book a flight',
    inputSchema: z.object({ flightId: z.string() }),
+   needsApproval: true,
-   execute: async (input) => {
-     const approved = await waitForApprovalHook(input);
-     if (!approved) throw new Error('Denied');
-     return bookFlightStep(input);
-   },
+   execute: bookFlightStep,
  }),
```

`needsApproval` 也接受异步函数，便于按输入决定是否需要审批（见上文
[工具审批](#工具审批)）。

### `uiMessages` / `collectUIMessages` 已移除

设置 `collectUIMessages: true` 时，`DurableAgent.stream()` 会返回累积的 `uiMessages`。而 `WorkflowAgent.stream()` 改为在 `result.messages` 上返回 `ModelMessage[]`。

持久化时，请把 `UIMessage[]` 作为事实来源保存，并在传给智能体之前调用 [`convertToModelMessages`](/docs/reference/ai-sdk-ui/convert-to-model-messages)——这正是[聊天机器人消息持久化](/docs/ai-sdk-ui/chatbot-message-persistence)中描述的模式。由于没有内置的 `ModelMessage` → `UIMessage` 转换，如果之后需要在 UI 中渲染对话，请避免把 `result.messages` 作为唯一副本持久化。

```diff
  const result = await agent.stream({
    messages,
    writable: getWritable<ModelCallStreamPart>(),
-   collectUIMessages: true,
  });

- return { uiMessages: result.uiMessages };
+ return { messages: result.messages };
```

### 非流式生成

当需要不经过流式的完整结果时，使用 `agent.generate()`：

```ts
export async function summarize(modelId: string, text: string) {
  'use workflow';

  const agent = new WorkflowAgent({
    model: modelId,
    instructions: 'Summarize the text briefly.',
  });
  const result = await agent.generate({ prompt: text });
  return { text: result.text, usage: result.usage };
}
```

Generation uses the provider's `doGenerate()` method and the same durable tool loop as streaming. It defaults to a maximum of 20 steps, while `stream()` remains unbounded unless you set `stopWhen`. Generation failures reject; stream model errors retain their existing `result.error` behavior.

The generated result uses core's final-step text and all-step content, tool results, warnings, and usage semantics. `responseMessages` contains generated messages only. `output` defaults to text and supports constructor or per-call output specifications. End callbacks run before complete-output parsing.

Use result getters inside the workflow, then return selected serializable fields through `run.returnValue`. Returning the whole result class is not supported. See the [generate reference](/docs/reference/ai-sdk-workflow/workflow-agent#generate) for options and remaining differences.

#### Approval round trips without streaming

Both `generate()` and `stream()` return approval requests even when no writable is provided. For generation, keep `result.responseMessages`, display the requested tool and input to the user, then append their decision to the next call:

```ts
const pending = await agent.generate({ messages });
// Persist these messages and collect the user's decision outside the workflow.
const continuation = [...messages, ...pending.responseMessages];

// In a later workflow invocation, using the same tool definitions:
const resumed = await agent.generate({
  messages: [
    ...continuation,
    {
      role: 'tool',
      content: [{ type: 'tool-approval-response', approvalId, approved }],
    },
  ],
});
```

Use the `approvalId` from the returned `tool-approval-request` and the user's `approved` decision. Preserve the request signature and original tool-call input when storing the conversation. Configure `experimental_toolApprovalSecret` with the same environment-variable reference for both invocations. Secrets are resolved inside durable signing and verification steps.

Local tools execute only after approval validation; denied tools produce an execution-denied result. Provider-executed approvals are forwarded to the provider. Tools that wait on Workflow hooks can also suspend and resume during generation.

#### Deadlines, cancellation, and replay

Inside a workflow, `timeout` sets an absolute deadline for model calls. Each model step checks it before dispatch, before SDK retry attempts, and after the provider returns. The same deadline remains in effect after a tool suspends and resumes. SDK `maxRetries` governs model retries; the durable model step does not add another retry layer. Expiration before dispatch rejects with `TimeoutError`; expiration during SDK retry backoff rejects with `AbortError`. Neither starts a new retry.

A model deadline does not cancel a tool waiting on a Workflow hook. The run can remain suspended after that deadline. Once the hook resumes, any subsequent model call fails before dispatch if the deadline has expired. To stop the suspended run, use the Workflow runtime's `run.cancel()` API. Cancellation does not undo external side effects that already happened.

Workflow reuses completed durable model and tool steps on replay. Put external side effects inside step functions and use the external service's idempotency mechanism where necessary: completed-step replay does not guarantee exactly-once effects for an interrupted attempt.

Generated files and result getters are available inside workflow code. Return the data the caller needs, for example:

```ts
return {
  text: result.text,
  files: result.files.map(file => ({
    data: file.uint8Array,
    mediaType: file.mediaType,
  })),
  usage: result.usage,
  responseMessages: result.responseMessages,
};
```

The generated result class itself is not a supported `run.returnValue` shape. Request and response bodies are omitted unless explicitly enabled with `include`; available response headers, timestamps, IDs and provider metadata are retained. Workflow uses its existing callback shapes and preparation rules, and reports model response timing rather than complete tool/step timing. It does not implement ToolLoopAgent's `callOptionsSchema` abstraction or core's live streaming readers and HTTP response helpers.

### Replace `experimental_context` with `runtimeContext` and `toolsContext`

`WorkflowAgent` no longer accepts `experimental_context`. Split the value into shared agent state (`runtimeContext`) and per-tool state (`toolsContext`); each tool's `execute` then receives only its own validated entry as `context`. See [runtimeContext and toolsContext](#runtimecontext-and-toolscontext) for the full shape.

```diff
  const agent = new WorkflowAgent({
    model: 'anthropic/claude-sonnet-5.5',
    tools: { weather: weatherTool },
-   experimental_context: { tenantId: 'tenant_123', apiKey: 'sk-...' },
+   runtimeContext: { tenantId: 'tenant_123' },
+   toolsContext: { weather: { apiKey: 'sk-...' } },
  });
```

### Everything else

Other options carry over with the same names: `prepareStep`, `onStart`, `onStepStart`, `onStepEnd`, `onEnd`, `onError`, `toolChoice`, `activeTools`, `timeout`, `repairToolCall`, `experimental_sandbox`, and the usual generation settings (`temperature`, `maxOutputTokens`, `topP`, …). `WorkflowAgent` additionally adds `prepareCall` (runs once before the loop) and the `onToolExecutionStart` / `onToolExecutionEnd` lifecycle callbacks documented above. The deprecated `experimental_onStart` and `experimental_onStepStart` aliases remain available for backwards compatibility.
