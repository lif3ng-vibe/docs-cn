# GitHub Copilot Harness

GitHub Copilot harness 适配器通过 Agent Client Protocol（ACP）将 `HarnessAgent` 连接到
[GitHub Copilot CLI](https://github.com/github/copilot-cli)。适配器将 ACP 安装、会话、
流式、工具、审批与生命周期管理委托给
`@ai-sdk/harness-acp`。

<Note>
  Harness 包目前处于**实验性**阶段。随着这一早期 API 的进一步打磨，各版本之间可能出现破坏性变更。
</Note>

## 安装

<InstallPackages packages="@ai-sdk/harness @ai-sdk/harness-github-copilot @ai-sdk/sandbox-vercel" />

ACP harness 会在首个会话启动时，在沙箱内安装锁定的 GitHub Copilot CLI 版本。它绝不会使用宿主上或全局安装的 Copilot CLI。启动命令会禁用 GitHub Copilot 的自动更新，从而在该次自举（bootstrap）中保持安装版本固定不变。

## 导入

```ts
import {
  createGitHubCopilot,
  githubCopilot,
} from '@ai-sdk/harness-github-copilot';
```

`githubCopilot` 等价于使用默认配置的 `createGitHubCopilot()`。

## 基本用法

```ts
import { HarnessAgent } from '@ai-sdk/harness/agent';
import { githubCopilot } from '@ai-sdk/harness-github-copilot';
import { createVercelNetworkSandboxSession } from '@ai-sdk/sandbox-vercel';

const agent = new HarnessAgent({
  harness: githubCopilot,
  model: 'gpt-5.5',
});

const sandboxSession = await createVercelNetworkSandboxSession({
  runtime: 'node24',
  ports: [4000],
  template: await agent.getSandboxTemplate(),
});
const session = await agent.createSession({ sandboxSession });

let exitCode = 0;
try {
  const result = await agent.stream({
    session,
    prompt: 'Check the test failures and fix the production code.',
  });

  for await (const part of result.stream) {
    if (part.type === 'text-delta') {
      process.stdout.write(part.text);
    }
  }
} catch (err) {
  exitCode = 1;
  console.error(err);
} finally {
  await session.destroy();
  await sandboxSession.destroy();
  process.exit(exitCode);
}
```

要将该智能体（agent）与 Vercel Sandbox 一起使用，请在宿主环境中提供 `VERCEL_OIDC_TOKEN` 以及[身份验证](#身份验证)小节中列出的变量之一。

会话支持多回合、附着与分离（attach/detach）、冷停止与恢复、回合挂起与继续，以及通过共享 ACP 桥接生命周期进行的 `stopWhen` 切片。

## 适配器设置

使用 `createGitHubCopilot()` 配置运行时：

```ts
const harness = createGitHubCopilot({
  auth: 'ai-gateway',
  reasoningEffort: 'high',
  port: 4001,
  startupTimeoutMs: 180_000,
});
```

配置项：

- `auth`：选择 `auto`、`direct` 或 `ai-gateway` 身份验证模式，也可以传入一个隔离的身份验证环境。默认为 `auto`，即存在网关凭据时选择 AI Gateway，否则使用直接 GitHub Copilot 身份验证。
- `credentialForwarding`：可选的同步或异步回调，在 harness 适配器将每个凭据转发进沙箱进程之前对其进行定制。它会收到本应转发的凭据值（真实凭据或掩码值）以及用于暴露该凭据的环境变量名。该回调只控制转发进沙箱进程的值，不会限制 harness 适配器能在宿主进程中发现、读取或以其他方式访问哪些凭据。
- `reasoningEffort`：具备推理能力的模型的推理力度（reasoning effort）。支持的取值为 `none`、`minimal`、`low`、`medium`、`high`、`xhigh` 和 `max`。省略时，GitHub Copilot 使用其配置的默认值。
- `mcpServers`：以服务器名为键的 ACP 原生 stdio、HTTP 或 SSE MCP 服务器定义。
- `port`：覆盖 ACP 桥接端口。
- `portEndpoint`：当沙箱会话无法直接暴露端口时，ACP 桥接所用的宿主端点。
- `startupTimeoutMs`：等待 ACP 桥接启动的最长时间。
- `reconnect`：已建立的桥接 WebSocket 连接断开后的重连时机。`maxElapsedMs` 控制总的重试窗口（包括连接建立与退避延迟），默认为 30 秒；`initialDelayMs` 默认为 50 毫秒，`maxDelayMs` 默认为 2 秒。这些重试采用指数退避，与 `startupTimeoutMs` 相互独立。当沙箱、桥接进程或桥接端点永久不可用时，重试无法恢复。
- `mintBridgeToken`：同步函数，接收沙箱 id 并返回 ACP 桥接身份验证 token。默认情况下，适配器会生成一个随机的 32 字节 token。自定义实现必须返回具备足够保密性的 token。

`reasoningEffort` 对所启动的 GitHub Copilot 服务器是固定的，并应用于它创建的每个会话。

适配器会锁定 GitHub Copilot CLI、可执行文件、启动命令与 ACP 版本。这些实现细节无法通过
`createGitHubCopilot()` 覆盖。

## 身份验证

GitHub Copilot 支持直接 GitHub 身份验证与 AI Gateway 身份验证。请设置以下环境变量中的一个或多个：

- `COPILOT_GITHUB_TOKEN`
- `GH_TOKEN`
- `GITHUB_TOKEN`
- `VERCEL_OIDC_TOKEN`
- `AI_GATEWAY_API_KEY`
- `AI_GATEWAY_BASE_URL`

如果没有设置适用的凭据环境变量，除非选择了 AI Gateway 身份验证，否则适配器会尝试从宿主系统解析原生订阅（subscription）。

使用直接身份验证时，GitHub Copilot 会按所列顺序检查三个 GitHub token 变量。细粒度个人访问令牌（fine-grained personal access token）需要 **Copilot Requests** 权限；经典个人访问令牌不受支持。使用 AI Gateway 时，适配器使用 `VERCEL_OIDC_TOKEN` 或 `AI_GATEWAY_API_KEY`，并遵循 `AI_GATEWAY_BASE_URL`。

当沙箱支持请求变换时，适配器只把每个凭据代理给匹配的出站请求。其他沙箱在应用 `credentialForwarding` 之后仍保留直接的凭据转发。

当宿主在运行时才解析凭据时，可以传入身份验证环境：

```ts
const gatewayHarness = createGitHubCopilot({
  auth: {
    AI_GATEWAY_API_KEY: await resolveGatewayToken(),
    AI_GATEWAY_BASE_URL: 'https://ai-gateway.vercel.sh',
  },
});
```

所提供的记录会取代宿主环境用于身份验证发现。适配器不会把它的凭据加入 `process.env`，也不会把它们的值包含在持久化的 ACP 生命周期身份中。

当两类凭据都可用时，可以强制指定某一身份验证路线：

```ts
const directHarness = createGitHubCopilot({ auth: 'direct' });
const gatewayHarness = createGitHubCopilot({ auth: 'ai-gateway' });
```

AI Gateway 模型请求不需要 GitHub 身份验证，但内置的 GitHub MCP 能力需要。

## 沙箱

GitHub Copilot 通过 `@ai-sdk/harness-acp` 在沙箱内运行。它要求网络沙箱至少暴露一个端口：

```ts
const sandboxSession = await createVercelNetworkSandboxSession({
  runtime: 'node24',
  ports: [4000],
  template: await agent.getSandboxTemplate(),
});
```

首个会话需要网络出站（egress）能力来安装 GitHub Copilot CLI。后续的模型、GitHub、Web 与 MCP 请求同样需要网络访问。

## 内置工具

适配器将 `bash`、`grep` 与 `glob` 映射为对应的通用 harness 工具。

其他工具仍以其原生 GitHub Copilot 名称可用，包括
`read_bash`、`stop_bash`、`list_bash`、`view`、`create`、`edit`、`web_fetch`、
`skill`、`sql`、智能体工具以及 `task`。GitHub 与用户配置的 MCP 工具保持动态。

当 GitHub Copilot 发送权限请求时，共享 ACP harness 会应用所配置的 Harness `permissionMode`。`allow-reads` 会批准读取操作，`allow-edits` 还会批准文件修改，`allow-all` 则批准每个请求。在 `allow-edits` 下，shell 执行仍需要审批。

## 已知限制

- ACP v1 不为每个原生工具事件暴露稳定的编程名称。适配器使用标准的 title、kind 与 schema 匹配，未匹配的工具保持动态。
- ACP v1 不暴露模型步骤边界或按步骤的用量。当 GitHub Copilot 未提供总量时，适配器会推断边界并报告未知的按步骤用量。
- ACP v1 没有可移植的手动压缩（compaction）或回合中途转向（steering）API。
- ACP v1 没有可移植的内置工具过滤 API。支持过滤宿主工具，但过滤 GitHub Copilot 内置工具会抛出不支持能力（unsupported-capability）错误。
- GitHub Copilot 目前不支持内置工具审批请求。在此适配器中请使用
  `permissionMode: 'allow-all'`。由宿主执行的 AI SDK 工具审批仍然可用。
- GitHub Copilot ACP 不暴露结构化输出的元数据映射，因此不支持基于 schema 的结构化输出。
- GitHub Copilot ACP 不暴露任何提问工具，因此不支持 `askUserQuestions`。
- GitHub Copilot CLI 不会通过 ACP 为任何模型呈现推理内容。`reasoningEffort` 控制的是推理深度而非可见性：输出推理摘要所需的参数，永远不会通过 ACP 的 `session/new` 与
  `session/set_config_option`（仅限 `mode`、`model`、`reasoning_effort`、
  `allow_all` 与 `agent`）暴露给客户端。设置该参数的唯一代码路径位于 GitHub Copilot 的交互式终端 UI 中，而它在无头的 `--acp --stdio` 模式下不会运行。
- 自定义 `headers` 不受原生支持，只能通过沙箱外部的请求变换来应用。因此当提供的是不具备该能力的沙箱时，自定义 `headers` 无法传入，会被忽略。
