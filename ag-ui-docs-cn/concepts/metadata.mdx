---
title: "元数据"
description: "为事件、消息与工具调用附加额外信息"
---

元数据是协议认可的附加信息携带方式——token 用量、追踪 ID、结束原因，以及你的应用需要随对话一起携带的任何东西。

在它出现之前，生产方把未声明的属性挂在事件上，指望消费方把它们透传下去。这正是 1.0 中移除“未知属性透传给订阅者”的原因：元数据用一个被声明、有类型、消费方必须承载的机制取代了它。

## 挂在哪里

四个位置，全部可选：

| 携带 `metadata`    | 说明                                                                               |
| ------------------ | ---------------------------------------------------------------------------------- |
| 每个事件           | 在基础事件上声明一次，因此所有事件类型都拥有它                                       |
| 每条消息           | 全部七种角色：developer、system、assistant、user、tool、activity、reasoning          |
| 每次工具调用       | 工具调用不是消息——见[工具调用](#工具调用)                                            |
| 每条恢复条目       | 它是请求字段，不会有东西合并进来——见[恢复条目](#恢复条目)                            |

## 形态

这个对象**按键开放**。键下允许任意 JSON 值，包括 `null`。对放进去的内容没有 schema 约束。

```typescript
{
  type: EventType.TEXT_MESSAGE_END,
  messageId: "msg_123",
  metadata: {
    "ag-ui": { usage: { input: 1200, output: 340 } },
    finishReason: "stop",
    traceId: "abc-123",
    retries: 0,
    labels: ["experimental"]
  }
}
```

对象本身**要么缺省、要么是对象，绝不能是 `null`**。空对象是合法的，表示“无话可说”，与省略它等价。

<Note>
  生产方绝不会发出 `"metadata": null`：在所有官方 SDK 中，没有值的可选字段会直接从 JSON 中省略。TypeScript 客户端强制执行这一点，并拒绝 `null` 的元数据对象——与某些更早的可选字段不同，元数据没有需要容忍的旧式生产方。注意其中的不对称：键下的 `null` **值**是有意义的数据，始终保留；只有顶替整个对象的 `null` 才是非法的。
</Note>

## 保留键

`ag-ui` 键保留给 AG-UI 自用。其余所有键都归你使用。

运行时没有任何机制会拒绝向 `ag-ui` 写入——强制限制会与按键开放的原则相悖——但请把它视为禁区，因为 AG-UI 可能在未来版本中把自己的值放在那里。

## 合并进消息

一条消息由一串事件组装而成，而有价值的值往往到最后一刻才确定：提供方要等生成结束才知道自己的 token 用量。因此消费方会随着事件序列的到来，**把每个事件的元数据合并进该事件构建的消息**。

这描述的是从事件流组装消息的客户端，例如 TypeScript 客户端。.NET 客户端不组装 AG-UI 消息——见下文 SDK 说明。

规则是按键合并、后写者胜：

```typescript
// TEXT_MESSAGE_START    metadata: { source: "openai", stage: "start" }
// TEXT_MESSAGE_CONTENT  metadata: { stage: "content" }
// TEXT_MESSAGE_END      metadata: { stage: "end", usage: { output: 340 } }

message.metadata
// { source: "openai", stage: "end", usage: { output: 340 } }
```

`source` 保留了下来，因为后续没有人再设置它。`stage` 停留在最后写入的值上。`usage` 只在末尾出现——这正是设计的意义所在。

### 值是整体替换，从不混合

合并从不递归。持有数组或对象的键会被整体替换：

```typescript
// earlier: { tags: ["a", "b", "c"] }
// later:   { tags: ["z"] }
// result:  { tags: ["z"] }        not ["a", "b", "c", "z"]
```

这条规则对 `ag-ui` 同样适用。如果你需要向嵌套结构中添加内容，请发送完整的新值。

### 哪些不会合并

不构建消息的事件，其元数据只留在事件自身上，永远不会到达消息：

- `RUN_STARTED`, `RUN_FINISHED`, `RUN_ERROR`
- `STEP_STARTED`, `STEP_FINISHED`
- `STATE_SNAPSHOT`, `STATE_DELTA`
- `RAW`, `CUSTOM`
- `REASONING_START`, `REASONING_END`, `REASONING_ENCRYPTED_VALUE`

`MESSAGES_SNAPSHOT` 是特例：其中的消息自带元数据、随消息一起到达，因此事件自身的元数据不会合并进其中任何一条。

<Tip>
  把运行级别的汇总放在 `RUN_FINISHED` 上完全可以，而且常常是正确的做法——只是要从事件上读取它们，别指望出现在某条消息上。如果想让它们落在特定消息上，请放在该消息的 `*_END` 事件上。
</Tip>

## 工具调用

工具调用事件——`TOOL_CALL_START`、`TOOL_CALL_ARGS`、`TOOL_CALL_END`——合并进**工具调用**本身，而不是拥有它的助手消息。

```typescript
assistantMessage.toolCalls[0].metadata
// { provider: "anthropic", latencyMs: 84 }
```

原因在于多个工具调用可能共享同一个父助手消息。若把它们的元数据都折叠进父消息，结果就会取决于这些调用恰好交错出现的顺序——而流转换是允许改变这个顺序的。让每次工具调用拥有自己的元数据，就消除了共享的目标，无论流如何处理，结果都一致。

`TOOL_CALL_RESULT` 则不同：它会创建一条工具消息，因此其元数据会像其他构建消息的事件一样合并进那条消息。

## 恢复条目

`RunAgentInput.resume` 中的每个条目——运行以中断结果结束后客户端回传的、针对每个中断的响应——都携带自己的元数据。它存放关于该响应的信封数据，例如证明人类决策未被篡改的签名，或路由键；智能体所要的答案则放在 `payload` 中。

恢复条目是请求字段，不是从事件流组装出来的东西，因此**没有合并语义**——不会有任何东西累积进去。完整的恢复契约见[中断](/concepts/interrupts#恢复运行)。

## 传输层

在 JSON 之上——也就是 SSE 所承载、所有 SDK 读写的东西——元数据就是一个普通对象，每种值形态都能精确往返：null、数组、嵌套对象、字符串与数字。

二进制 protobuf 格式把它承载为 `google.protobuf.Struct`，其值类型有真正的 null 分支，因此键下的 `null` 会被原样保留而非近似处理，缺省的对象也能与空对象区分开。在那里有两条注意事项，而且都不是元数据特有的：

- **并非每个事件都有 protobuf 表示**。线格式只覆盖一部分事件类型——工具结果、活动、推理以及已废弃的 thinking 事件都没有对应的 protobuf 消息，因此它们根本无法跨越这条传输层，带不带元数据都一样。.NET 编码器会直接拒绝它们；TypeScript 编码器会产出一个随后又被解码端拒绝的空负载。无论哪种方式，事件都到不了对面，所以不要依赖二进制传输层来传这些事件。
- **数字是 IEEE-754 双精度浮点数**。`google.protobuf.Value` 把所有数字都建模为 double，超过 2^53 的整数在往返后会丢失精度。这是格式本身的属性，对 `state` 以及所有其他动态负载同样适用。

不同编码器之间不保证逐字节一致的输出：`Struct` 是一个 `map<string, Value>`，而 protobuf 的 map 条目顺序并无规范。能保证的是双方解码出相同的值。实际上，TypeScript 与 .NET 编码器对跨语言测试套件中的每个样例都恰好输出相同的字节——套件里对此有断言——但请不要依赖这一点。

## SDK 参考

<Note>
  元数据在每个 SDK 中都按键开放，因此类型刻意保持宽松。保证内容可被 JSON 序列化是你自己的责任——函数或 `bigint` 在类型层面能通过，到编码时就会失败。
</Note>

**TypeScript**——事件、消息、工具调用与恢复条目上都有 `metadata?: Record<string, any>`。如果你要自己组装消息，可以从 `@ag-ui/core` 导入 `mergeMetadata(existing, incoming)`，以及表示保留键的 `AGUI_METADATA_KEY`。

**Python**——`metadata: Optional[Dict[str, Any]]`。基础模型在所有序列化路径上都会省略未设置的可选字段，因此缺省的对象会被省略，而不会输出成 `null`——无需 `exclude_none=True`。`Metadata` 与 `AGUI_METADATA_KEY` 可从 `ag_ui.core` 导入。

**.NET**——`BaseEvent`、`AGUIMessage`、`AGUIToolCall` 与 `AGUIResume` 上都有 `JsonElement? Metadata`，保留键则由 `AGUIMetadata.ReservedKey` 提供。

它是一个**线级字段**。它在 JSON 与 protobuf 中都能忠实往返，因此读取 `RunAgentInput` 的服务端或解码事件流的客户端看到的都是完整无损的，`AGUIMessage.Metadata` 也会把它带在 `MESSAGES_SNAPSHOT` 内的消息上。它刻意不出现在 `Microsoft.Extensions.AI` 的 `ChatMessage` 上，与 `encryptedValue` 和 `AGUIToolMessage.Error` 的既有行为保持一致。

如果你通过 `AGUIChatClient` 消费事件流，请注意这在实践中的含义：`EventStreamConverter` 不会为 `TEXT_MESSAGE_START`、`TEXT_MESSAGE_END`、`TOOL_CALL_START` 或 `TOOL_CALL_ARGS` 发出 `ChatResponseUpdate`，因此这些事件上的元数据——包括上文建议放在 `TEXT_MESSAGE_END` 上的用量——也不会到达 `RawRepresentation`。请从原始事件流读取，而不是从高层聊天客户端读取。

## 压缩

TypeScript 客户端中的 `compactEvents` 会把一段流式事件压缩成更少的事件，用于存储或重放，并有意重排它们，让每条流的事件保持在一起。

元数据本身没有引入新的顺序敏感性：每个合并目标都是唯一的——每条消息有自己的，每次工具调用也带自己的，而不是折叠进可能共享的父消息——因此合并到同一目标的两个事件绝不会彼此乱序。

不过，压缩的重排在一般意义上并不保持语义，这一点早于元数据就存在。打断某条流的事件会在该流之后发出，因此在消息中途到达的 `MESSAGES_SNAPSHOT` 会在该消息自身的事件之后重放，并覆盖它们产出的结果——被追加的内容与被合并的元数据都一样。如果你依赖严格的重放等价性，请避免把快照与未结束的流交错在一起。
