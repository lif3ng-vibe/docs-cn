# 消息

消息构成了 AG-UI 协议中通信的主干。它们承载用户与 AI 智能体之间的对话历史，并提供一种标准化的信息交换方式——无论底层使用的是哪家 AI 服务。

## 消息结构

AG-UI 消息采用供应商中立的格式，在保持结构一致的同时，兼容不同的 AI 提供方。应用因此可以在不同 AI 服务（如 OpenAI、Anthropic 或自定义模型）之间切换，而无需改动客户端侧的实现。

基本的消息结构如下：

```typescript
interface BaseMessage {
  id: string // Unique identifier for the message
  role: string // The role of the sender (user, assistant, system, tool, reasoning)
  content?: string // Optional text content of the message
  name?: string // Optional name of the sender
  encryptedContent?: string // Optional encrypted content for privacy-preserving state continuity
  metadata?: Record<string, any> // Optional extra information attached to the message
}
```

`role` 判别字段可以取 `"user"`、`"assistant"`、`"system"`、`"tool"`、`"developer"`、`"activity"` 或 `"reasoning"`。具体的消息类型在这个基本形态上扩展各自需要的字段。

每种消息类型都携带 `metadata`——一个按键开放的可选对象，随消息由事件逐步构建而累积。工具调用也携带自己的元数据。规则见[元数据](/concepts/metadata)。

> `encryptedContent` 字段支撑保护隐私的工作流：敏感内容（如推理链）可以在多轮之间传递而不暴露原始内容。这对零数据保留（ZDR）合规和 `store:false` 场景尤其有用。

## 消息类型

AG-UI 支持多种消息类型，以覆盖对话中的不同参与者：

### 用户消息

从终端用户发给智能体的消息：

```typescript
interface UserMessage {
  id: string
  role: "user"
  content: string | ContentPart[] // Text or multimodal input from the user
  name?: string // Optional user identifier
}

type ContentPart =
  | TextPart
  | ImagePart
  | AudioPart
  | VideoPart
  | DocumentPart

interface DataSource {
  type: "data"
  value: string
  mimeType: string
}

interface UrlSource {
  type: "url"
  value: string
  mimeType?: string
}

interface FileSource {
  type: "file"
  value: string // a handle the provider issued; opaque, never fetched
  provider?: string // who issued it, e.g. "openai"
  mimeType?: string
}

type PartSource = DataSource | UrlSource | FileSource

interface TextPart {
  type: "text"
  text: string
}

interface ImagePart {
  type: "image"
  source: PartSource
  metadata?: Record<string, unknown>
}

interface AudioPart {
  type: "audio"
  source: PartSource
  metadata?: Record<string, unknown>
}

interface VideoPart {
  type: "video"
  source: PartSource
  metadata?: Record<string, unknown>
}

interface DocumentPart {
  type: "document"
  source: PartSource
  metadata?: Record<string, unknown>
}
```

> 在 Python 中，先前的 `BinaryInputContent` 模型已废弃，作为兼容路径暂时仍可使用。

这一结构让传统的纯文本输入照常可用，同时支持在同一消息中携带更丰富的负载，例如图片、音频片段或上传的文件。

### 助手消息

从 AI 助手发给用户的消息：

```typescript
interface AssistantMessage {
  id: string
  role: "assistant"
  content?: string // Text response from the assistant (optional if using tool calls)
  name?: string // Optional assistant identifier
  toolCalls?: ToolCall[] // Optional tool calls made by the assistant
  encryptedContent?: string // Optional encrypted content for state continuity
}
```

### 系统消息

提供给智能体的指令或上下文：

```typescript
interface SystemMessage {
  id: string
  role: "system"
  content: string // Instructions or context for the agent
  name?: string // Optional identifier
}
```

### 工具消息

工具执行产生的结果：

```typescript
interface ToolMessage {
  id: string
  role: "tool"
  content: string // Result from the tool execution
  toolCallId: string // ID of the tool call this message responds to
  error?: string // Optional error message if the tool execution failed
  encryptedValue?: string // Optional encrypted reasoning for state continuity
}
```

要点：

- `toolCallId` 把结果关联回最初的工具调用
- 用 `error` 表示工具执行失败
- 用 `encryptedValue` 附加加密的思维链，记录智能体如何解读或处理该工具结果

### 活动消息

只存在于前端的结构化 UI 消息。用于进度、状态，或任何不应发送给模型的自定义视觉元素：

```typescript
interface ActivityMessage {
  id: string
  role: "activity"
  activityType: string // e.g. "PLAN", "SEARCH", "SCRAPE"
  content: Record<string, any> // Structured payload rendered by the frontend
}
```

要点

- 通过 `ACTIVITY_SNAPSHOT` 和 `ACTIVITY_DELTA` 发出，支持实时、可更新的 UI（清单、步骤、搜索进行中等）。
- **仅限前端**：绝不转发给智能体，因此无需过滤，也不会让 LLM 困惑。
- **可定制**：自定义 `activityType` 与 `content`，并渲染配套的 UI 组件。
- **可流式更新**：对长时间运行的操作可以随时间持续更新。
- 通过把自定义事件转化为可持久保存的消息对象，帮助实现持久化/恢复。

### 开发者消息

用于开发或调试的内部消息：

```typescript
interface DeveloperMessage {
  id: string
  role: "developer"
  content: string
  name?: string
}
```

### 推理消息

表示智能体内部推理或思维链过程的消息：

```typescript
interface ReasoningMessage {
  id: string
  role: "reasoning"
  content: string // Reasoning content (visible to client)
  encryptedValue?: string // Optional encrypted reasoning for state continuity
}
```

<Tip>
  与活动消息不同，推理消息用来表示智能体的内部思考过程，可以出于隐私考虑加密，并且会在后续轮次回传给智能体做进一步处理。
</Tip>

要点：

- 通过 `REASONING_MESSAGE_START`、`REASONING_MESSAGE_CONTENT` 和 `REASONING_MESSAGE_END` 事件发出。
- **可见性控制**：内容可以对用户可见（作为摘要），也可以完全加密。
- **加密值**：用 `REASONING_ENCRYPTED_VALUE` 事件把加密的思维链附加到消息或工具调用上，而不暴露内容。
- **状态延续**：加密的推理条目可以在多轮对话之间传递，而不暴露原始思维链。
- **隐私优先**：在保留推理能力的同时，支持 `store:false` 与零数据保留（ZDR）策略。
- **与助手消息分离**：推理与最终响应分开保存，避免污染对话历史。

流式事件的生命周期见[推理事件](/concepts/events#reasoning-events)。

## 供应商中立

AG-UI 消息在设计上是供应商中立的，可以轻松地与各 AI 提供方的专有格式相互映射：

```typescript
// Example: Converting AG-UI messages to OpenAI format
const openaiMessages = agUiMessages
  .filter((msg) => ["user", "system", "assistant"].includes(msg.role))
  .map((msg) => ({
    role: msg.role as "user" | "system" | "assistant",
    content: msg.content || "",
    // Map tool calls if present
    ...(msg.role === "assistant" && msg.toolCalls
      ? {
          tool_calls: msg.toolCalls.map((tc) => ({
            id: tc.id,
            type: tc.type,
            function: {
              name: tc.function.name,
              arguments: tc.function.arguments,
            },
          })),
        }
      : {}),
  }))
```

有了这层抽象，无论底层是哪家 AI 服务，AG-UI 都能充当统一的接口。

## 消息同步

消息可以通过两种主要机制在客户端与服务端之间同步：

### 完整快照

`MESSAGES_SNAPSHOT` 事件提供对话中所有消息的完整视图：

```typescript
interface MessagesSnapshotEvent {
  type: EventType.MESSAGES_SNAPSHOT
  messages: Message[] // Complete array of all messages
}
```

典型使用场景：

- 初始化对话时
- 连接中断之后
- 发生重大状态变更时
- 为确保客户端与服务端同步

### 流式消息

对于实时交互，新消息可以在生成的同时流式送达：

1. **开始一条消息**：表示一条新消息正在创建

   ```typescript
   interface TextMessageStartEvent {
     type: EventType.TEXT_MESSAGE_START
     messageId: string
     role: string
   }
   ```

2. **流式传输内容**：内容就绪时分块发送

   ```typescript
   interface TextMessageContentEvent {
     type: EventType.TEXT_MESSAGE_CONTENT
     messageId: string
     delta: string // Text chunk to append
   }
   ```

3. **结束一条消息**：表示消息已完整
   ```typescript
   interface TextMessageEndEvent {
     type: EventType.TEXT_MESSAGE_END
     messageId: string
   }
   ```

这种流式方式带来即时反馈的灵敏用户体验。

## 消息中的工具集成

AG-UI 消息以优雅的方式集成工具使用，让智能体能够执行操作并处理结果：

### 工具调用

工具调用内嵌在助手消息中：

```typescript
interface ToolCall {
  id: string // Unique ID for this tool call
  type: "function" // Type of tool call
  function: {
    name: string // Name of the function to call
    arguments: string // JSON-encoded string of arguments
  }
}
```

带工具调用的助手消息示例：

```typescript
{
  id: "msg_123",
  role: "assistant",
  content: "I'll help you with that calculation.",
  toolCalls: [
    {
      id: "call_456",
      type: "function",
      function: {
        name: "calculate",
        arguments: '{"expression": "24 * 7"}'
      }
    }
  ]
}
```

### 工具结果

工具执行结果以工具消息的形式表示：

```typescript
{
  id: "result_789",
  role: "tool",
  content: "168",
  toolCallId: "call_456" // References the original tool call
}
```

这构成了清晰的工具使用链条：

1. 助手发起一次工具调用
2. 工具执行并返回结果
3. 助手可以引用并响应这个结果

## 流式工具调用

与文本消息类似，工具调用也可以流式传输，实时呈现智能体的动作：

1. **开始一次工具调用**：

   ```typescript
   interface ToolCallStartEvent {
     type: EventType.TOOL_CALL_START
     toolCallId: string
     toolCallName: string
     parentMessageId?: string // Optional link to parent message
   }
   ```

2. **流式传输参数**：

   ```typescript
   interface ToolCallArgsEvent {
     type: EventType.TOOL_CALL_ARGS
     toolCallId: string
     delta: string // JSON fragment to append to arguments
   }
   ```

3. **结束一次工具调用**：
   ```typescript
   interface ToolCallEndEvent {
     type: EventType.TOOL_CALL_END
     toolCallId: string
   }
   ```

这样，前端就能在智能体构建推理的过程中，逐步展示正在被调用的工具。

## 实际示例

下面是一个带工具使用的完整对话示例：

```typescript
// Conversation history
;[
  // User query
  {
    id: "msg_1",
    role: "user",
    content: "What's the weather in New York?",
  },

  // Assistant response with tool call
  {
    id: "msg_2",
    role: "assistant",
    content: "Let me check the weather for you.",
    toolCalls: [
      {
        id: "call_1",
        type: "function",
        function: {
          name: "get_weather",
          arguments: '{"location": "New York", "unit": "celsius"}',
        },
      },
    ],
  },

  // Tool result
  {
    id: "result_1",
    role: "tool",
    content:
      '{"temperature": 22, "condition": "Partly Cloudy", "humidity": 65}',
    toolCallId: "call_1",
  },

  // Assistant's final response using tool results
  {
    id: "msg_3",
    role: "assistant",
    content:
      "The weather in New York is partly cloudy with a temperature of 22°C and 65% humidity.",
  },
]
```

## 结语

AG-UI 的消息结构在保持供应商中立的同时，支撑起精细复杂的对话式 AI 体验。通过把消息的表示、同步与流式传输标准化，无论底层是哪家 AI 服务，AG-UI 都为人与智能体的交互通信提供了一致的实现方式。

这套系统既能支撑简单的文本往来，也能支撑复杂的基于工具的工作流，同时在实时响应与高效数据传输之间取得平衡。
