协议中几乎所有东西都携带 OPTIONAL 的 `metadata` 对象——事件、消息、工具调用、工具、中断、resume 条目。它是协议未建模内容的开放通道：提供方名称、延迟、结束原因、token 计数、追踪 key，以及应用想让数据捎带的任何东西。

## 取值

`metadata` 按 key 开放。key 下允许任意 JSON 值，包括 `null`——这里的 `null` 是有意义的数据。对象本身要么缺省、要么是对象，MUST NOT 为 `null`。

未知的元数据 key 协议上合法，不算无法识别的内容：[处理模型](/spec/1.0/basic/processing)从不剥离它们，任何 key 都如此。

## key

`ag-ui` key 为协议自用而保留。其余 key 都是应用空间；生产者 SHOULD 给自创的 key 加上厂商或应用名前缀，这样两个扩展同一条流的各方才不会相撞。

## 合并

一个流式条目由多个事件组装而成，而那些有意思的值——token 用量、结束原因——要到结尾才知道。因此元数据是累积的，而不是在条目开启时定型：消费者 MUST 把组成条目的每个事件的元数据合并起来，逐 key 进行，每个 key 都由最后写入者胜出。

合并 MUST NOT 递归。key 的值被整体替换，因此 key 下的对象或数组是整个换掉，而不是与之前的值掺和。

## 各事件元数据的落点

合并需要一个目标，而目标是事件所构建的那个东西——不总是消息：

| 事件 | 合并到 |
| --- | --- |
| `TEXT_MESSAGE_START` / `CONTENT` / `END` | 该文本消息 |
| `REASONING_MESSAGE_START` / `CONTENT` / `END` | 该推理消息 |
| `TOOL_CALL_START` / `ARGS` / `END` | **工具调用本身**——而不是拥有它的那条助手消息 |
| `TOOL_CALL_RESULT` | 它创建的那条工具消息 |
| `ACTIVITY_SNAPSHOT` / `ACTIVITY_DELTA` | 该活动消息——已累积的元数据会在替换型快照下存活（[活动](/spec/1.0/events/activity)） |
| chunk（`*_CHUNK`） | 其合成事件所合并到的目标（[chunk 元数据](/spec/1.0/basic/patterns/streaming#chunk-metadata)） |
| 其余一切（`RUN_*`、`STEP_*`、快照、`RAW`、`CUSTOM` 等） | 不合并——见下文 |

<Note>
  工具调用的元数据落在调用上而非其父消息上，是有意为之。一条助手消息可以拥有多个工具调用，把它们的元数据并入父消息，会让结果取决于调用交错发生的顺序。每个调用保留自己的元数据，才让这一切保持无歧义。
</Note>

不构建持久条目的事件没有合并目标：它的元数据就是事件自己的，对中间件以及任何观察流的东西可见，协议不再另行指派去处。消费者 MAY 把它呈现出来——比如把一次运行的 `RUN_FINISHED` 元数据放进自己的记账——但没有规则要求这么做。

## 存储型元数据

消息、工具调用、工具、中断与 resume 条目把 `metadata` 作为自己的普通存储字段携带。除上面列出的事件之外，没有东西会合并进它们；[运行输入](/spec/1.0/basic/run-input)中某个工具的元数据，或某个中断的元数据，只是随其载体一起旅行的数据。

## 数据类型

[`Metadata`](/spec/1.0/schema#metadata) 由 [schema 参考](/spec/1.0/schema)定义，每个载体的条目都在其中列出了自己的 `metadata` 字段。
