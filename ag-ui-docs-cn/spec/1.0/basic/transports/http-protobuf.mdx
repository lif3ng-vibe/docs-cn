title: "HTTP + Protobuf"
description: "二进制绑定：同样的 POST，返回一串以长度前缀分帧的 protobuf 帧——1.0"
---

这是二进制绑定，供想要紧凑线上格式的消费者使用。它完全共享 [SSE 绑定](/spec/1.0/basic/transports/http-sse)的请求一侧——运行输入是同样的 JSON POST——差别只在响应。

## 协商

- 想用本绑定的客户端在自己的 `Accept` 头中、在 `text/event-stream` 旁边加上 `application/vnd.ag-ui.event+proto`。准入即是选择加入——通配范围（`*/*`、`application/*`）同样准许该媒体类型——因此无法消费 protobuf 的客户端 MUST 发送指名自己所能消费内容的显式 `Accept`，而不是通配或降序条目：两种媒体类型之间的相对质量值（q 值）不予考虑。
- 支持本绑定的生产者，只要客户端的 `Accept` 以正的质量值准许该媒体类型，SHOULD 就以它作答；否则 MUST 以 SSE 作答。不支持本绑定的生产者会忽略该媒体类型——这正是客户端 MUST 时刻准备好接收 SSE 的原因。
- 响应的 `Content-Type` 恰为 `application/vnd.ag-ui.event+proto`；消费者以这个头选择自己的解析器。

## 分帧

响应体是一串帧，每帧一个协议事件：

- 一帧是一个 4 字节长度头——无符号 32 位大端整数——后跟恰好那么多字节的一个已编码事件。
- 帧之间直接相接，没有分隔符。消费者 MUST 容忍帧被传输层分块切开、以及一个分块内含多帧的情形。
- 在帧中途结束的响应体是一次[被截断的运行](/spec/1.0/basic/transports#truncation)。

## 线上 schema

protobuf 消息定义与各 SDK 一样，由同一份 [JSON Schema](/spec/1.0/schema-files) 生成；线上 schema 不是第二个事实来源。跨实现的一致性是一致性验证面的一部分：一组规范事件钉死编码后的字节，每个一方官方编码器 MUST 逐字节复现这组测试样例库（corpus）。（这组样例就是保证——拿到同一*语义*值的两个编码器，仍可能以不同顺序排列开放 JSON 对象的条目，而 protobuf 的 map 编码会把它暴露出来。）

语义在二进制线上格式允许的范围内尽量贴近 SSE 绑定：

- 从帧中解码出的事件，进入与从 SSE 解析出的事件相同的[处理管线](/spec/1.0/basic/processing)——同样是中间件在前、强制执行在后。
- 线上 schema 以开放负载承载的材料——`RUN_FINISHED.outcome`、元数据、状态、`rawEvent`——在解码后存活并到达该管线：经由本绑定到达的无法识别 outcome，会由强制执行剥离并给出警告，与 SSE 上完全一致，绑定 MUST NOT 在解码时拒绝它。
- 其余方面，二进制线上格式天然更窄。比本构建的线上 schema 更新的*字段*，会被 protobuf 解码本身静默跳过——"剥离并警告"的行为只有在 JSON 线上格式上才完全可观察。同样的收窄也覆盖线上 schema 未建模的、协议上合法的开放成员：JSON Patch 操作的扩展成员在 JSON 线上格式 MUST 保留，在这条线上则无法存活。
  信封分支比本构建更新的*事件*，没有类型字符串可以传递，绑定会丢弃该帧并给出警告——与强制执行给出的答案相同，只是在传输层说出。
- 字节无法按消息解码的帧是格式错误的传输材料，对流而言是致命的。而只是在中途结束的响应体不是：那是一次[被截断的运行](/spec/1.0/basic/transports#truncation)。

## 错误

与 [SSE 绑定](/spec/1.0/basic/transports/http-sse#errors)相同：流开始前的拒绝是 HTTP 错误状态；流内的失败是 `RUN_ERROR`，作为与其他帧无异的又一帧传输。
