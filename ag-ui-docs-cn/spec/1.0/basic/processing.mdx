有两样东西表面上相似，却绝不能混淆：协议未描述的内容，以及协议描述了但取值有误的内容。前者是协议得以生长的方式；后者是一个 bug。

## 规则

**无法识别的内容不是错误；已知值的格式错误才是。**

- 本实现不识别其类型的事件，MUST NOT 中止运行。
- 事件上未被描述的属性，MUST NOT 中止运行。
- 实现不识别的联合成员——一种新类型的内容部分、它发布之后才命名的 outcome——MUST NOT 中止运行。
- 协议确实描述了的字段，携带被 schema 拒绝的值，MUST 视为致命：消费者 MUST 让运行失败，而不是修复、强转或忽略该值。

这样规定是有意非对称的。实现发布之后才新增的事件类型是预期之内的事——发送方更新，较旧的一方没有理由说它无效。但装着数字的 `messageId` 不是更新的协议；它是缺陷，悄悄把它强转的消费者会把缺陷掩盖起来，直到它以更难诊断的形式浮出水面。

## 所有传输层给出同样的裁决

这些规则约束的是协议，而不是某种线上格式。支持多种传输层的消费者，MUST 对同一事件、无论它经由哪条路径到达，都给出同样的裁决：一条流若以 JSON 形式存活，MUST 以 protobuf 形式同样存活；若失败，MUST 以同样方式失败——除非二进制编码本身无法表达裁决所依据的差异，即本页下文点名的两种情形（无法命名的信封变体，以及 protobuf 会物化出来的"缺省"）。

这给读取方能自行决定的事情划了界。把字节变成事件是读取方的全部职责——一帧字节映射不到任何事件的帧是解码失败，这个判断理应归读取方。而成功读出的事件是否携带实现认识的东西，则不归它管：这个问题属于所有传输层共享的那一个阶段。一个还顺带做校验的读取方，会让自己的传输层比其他传输层严格得多，于是生产者对 content type 的选择就决定了运行能否存活。

二进制的情形需要一项通融。文本读取方可以把未知类型的事件传递下去，因为类型以字符串传输，共享阶段可以按名字丢弃它。二进制读取方做不到：一个它编译时未曾见过的信封变体没有名字可以传递。这样的帧 MUST 被丢弃并给出警告，而不是让运行失败——这正是共享阶段会给出的同样答案，只不过写给了一个无法推迟判断的传输层。

<Note>
  凡是二进制编码不给字段留存在位的地方，它就无法遵守这一点。在 protobuf 中，必填标量与必填列表都在此列：生产者省略的必填字符串会以空字符串到达，必填数组会以空数组到达，而同一事件以 JSON 形式会因格式错误被拒绝，在这里却被接受。schema 本就禁止省略它们，因此这改变的是有缺陷生产者的诊断方式，而不是符合规范的实现可以发送什么。
</Note>

## 消费者如何处理无法识别的内容

把事件暴露给应用代码的消费者，MUST NOT 把无法识别的内容当作协议描述过的东西交付出去。读过之后，这样的消费者 MUST 在以下做法中选一：

- **丢弃**：如果整个事件的类型无法识别。消费者 SHOULD 发出指名该类型的警告。
- **剥离**：如果是一个本已有效的事件上的未知属性或无法识别的联合成员。消费者 SHOULD 发出指名被移除路径的警告。

消费者 MUST NOT 让被剥离的属性存活到应用代码收到的值里，也 MUST NOT 让被丢弃的事件到达应用代码。

这只在 schema 封闭对象之处适用——也就是 schema 描述协议自有对象的所有地方。schema 有意保持开放的对象，其未描述的成员根本不算无法识别的内容，MUST 保留。JSON Patch 操作就是这样的情形：RFC 6902 第 4 节要求操作忽略而非拒绝它未定义的成员，因此带着多余 `value` 的 `remove` 也是合法补丁，会完整到达。在那里做剥离的消费者删除的是符合规范的数据，它发出的警告也是无的放矢。

这条规则约束的是管线，而不是解析器。只负责解析事件的库层——比如各 SDK 里生成的模型——有意保留未知属性，让位于其上的中间件仍能看到它们。提供这种解析器却没有强制执行阶段的 SDK，尚未满足本条规则；今天指的是 Python 与 .NET，它们的模型宽松解析，应用代码之前没有任何剥离阶段。

<Note>
  参考实现尚有一处未满足：schema 是封闭字符串值集合的字段——例如消息的 `role`——是作为叶子检查的，因此那里无法识别的取值是致命错误而非被剥离。.NET 的转换器以同样方式拒绝未知的 role 或 outcome。上面的规则才是协议的要求；这两处都是与规则的差距，而不是对规则的放宽。
</Note>

剥离会层层深入，移除什么取决于无法识别的值所在的位置：

- 在**可选**位置上：移除该字段，周围的一切照常存活。
- 在**必填**位置上：改为移除*包含*它的那个值。来源类型闻所未闻的媒体部分会被整体移除——留下一个没有来源的部分，等于把一个校验器必须视为格式错误的东西递给它，把一次新增变成了致命错误。
- 在**列表**内部：丢弃无法识别的元素，列表本身存活。

## 中间件的位置

中间件——消费者安装的、用于翻译、观察或改写流的任何东西——MUST 在强制执行之前运行；强制执行 MUST 在校验之前、在应用代码看到任何东西之前运行。

```
producer → compatibility boundary → middleware → enforcement
         → chunk expansion → verification → application
```

兼容性边界是协议已退役形态的常开翻译器。它 MUST 最先看到流，因为退役形态可能是一个 chunk，更早遇到它的阶段要么在它上面失败，要么把它变成边界再也认不出的东西。中间件*链* MAY 在自己的各阶段之间展开 chunk，让每个阶段都收到 start/content/end 形式——参考实现的链式辅助工具正是这么做的。因此中间件 MUST 为两种形式都做好准备：它看到什么，取决于它在链中的位置。

阶段之间的展开会收窄一条保证，而且这一收窄是明说的、不是藏着掖着：展开合成的事件只携带协议定义过的内容，因此 chunk *之上*的无法识别字段只有在上述规范顺序下才能存活到强制执行——并挣得它们的警告。提前展开的链会无声地丢掉它们。符合规范的生产者从不发出这类字段，所以丢掉的东西是来自更新协议版本的内容，穿过了提前展开的链。展开之所以存在的目的——交付 delta、开头字段、元数据、`rawEvent`、归因——会完整携带；chunk 的 `timestamp` 则不会，因为合成的事件不是那个 chunk，它和未知字段一样，只在规范顺序下、在展开之前被裁决。

chunk 本身就是一个事件，MUST 按事件来裁决：无论哪个阶段先遇到格式错误的 chunk——规范顺序上的强制执行，还是提前展开的中间件链中的展开——都 MUST 拒绝它而不是修复它，且 MUST NOT 把强制执行会拒绝的格式错误已知值规范化、设默认值或掩盖起来。用一个默认值顶替格式错误 role 的消费者，让同一个生产者缺陷在明发时是致命的、以 chunk 形式发送时却不可见，于是生产者碰巧用了哪种形式，竟决定了它的 bug 是否曾被报告。

校验 MUST 在展开之后运行，因为它检查的东西——消息与调用在继续之前已开启、在结束之后关闭——只有当 chunk 变成它所代表的事件之后才存在。

这个顺序在两个方向上都承重：

- 中间件 MUST 在强制执行移除内容之前看到它。垫片（shim）存在的意义就是翻译当前协议未描述的形态；如果强制执行先剥离了那个形态，垫片收到的事件就再无可翻译之物，运行将丢掉无人能找回的数据。
- 应用代码 MUST NOT 看到强制执行会移除的内容。一旦翻译器们得到了机会，仍然无法识别的就是无法识别的，到此为止。

消费者 MUST 在每条为应用代码产出事件的路径上执行这一顺序，包括重连与回放。跳过强制执行的路径是保证上的一个洞，不是优化。

## 发出的内容

同样的边界也适用于消费者发送的东西。在传输前的最后一刻，消费者 MUST 从运行输入中移除无法识别的内容，SHOULD 对移除的东西给出警告，且 MUST 在任何东西发出之前把格式错误的已知字段视为致命。

接收运行输入的生产者 MUST 对它施加同样的非对称规则：无法识别的内容不会使输入无效，格式错误的已知字段才会。

## 生产者不得做的事

生产者 MUST NOT 发出协议未描述的事件类型，并指望消费者会忽略它。无法识别的事件之所以存活，是为了协议能够新增它们，而不是为了让生产者借流夹带私有信令；`CUSTOM` 与 `RAW` 就是为这个目的而存在、且由 schema 描述的。
