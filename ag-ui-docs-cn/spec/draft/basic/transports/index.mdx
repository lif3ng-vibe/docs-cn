协议语义在每种传输层上完全相同。传输层是一个**绑定**：它定义[运行输入](/spec/draft/basic/run-input)如何投递、事件如何分帧与编码、流如何终止或失败。它不定义事件是什么意思——[事件模式](/spec/draft/basic/patterns)与[处理模型](/spec/draft/basic/processing)在每种绑定上都一样。

## 绑定契约

绑定 MUST 提供：

- 运行事件的**有序、完整投递**，按生产者发出的顺序。协议的顺序就是到达顺序；能重排或丢事件的传输层，若没有一层把两者还原，就无法承载 AG-UI。
- **开启交换的 `RunAgentInput` 的投递**，先于任何事件。继续[携带后续运行](/spec/draft/events/lifecycle#一条流上的多次运行)的流——回放线程——不为它们投递进一步的输入：那些运行是生产者在重述历史，每个 `RUN_STARTED` MAY 携带自己的 `input` 回显。
- 消费者能据此与截断区分开的**终止信号**：在终止事件之后干净结束的流是一次已关闭的运行，没有终止事件就断掉的连接是一次被截断的运行。
- **被拒输入的错误路径**——结构无效的 `RunAgentInput` 在 `RUN_STARTED` 之前、在流之外被拒绝。

认证与授权是绑定与应用的属性，不是协议的属性：AG-UI 不定义任何凭据，绑定承载其通道所使用的任何东西（HTTP 认证、进程环境身份，或什么都不用）。

## 标准绑定

1. [HTTP + 服务器推送事件（SSE）](/spec/draft/basic/transports/http-sse)：运行输入是一个 HTTP POST；事件以携带 JSON 的 SSE 帧流回。
2. [HTTP + Protobuf](/spec/draft/basic/transports/http-protobuf)：同样的 POST，经协商返回以长度前缀分帧的 protobuf 二进制响应。

两种绑定共享请求一侧；差别只在响应编码，由内容协商选定。讲 HTTP 的实现 MUST 支持 SSE 绑定；protobuf 绑定是 OPTIONAL 的。

## 截断

流在没有终止事件的情况下结束，消费者得到的就是一次被截断的运行：生产者可能还在继续，但这个消费者永远看不到余下的部分。被截断的运行没有 outcome。消费者 MUST NOT 为它合成 `RUN_FINISHED`，也 MUST NOT 把它报告为已成功；运行在断点之前交付的一切仍然算已交付。除此之外要不要、又如何把截断呈现出来——让运行悬而未决，还是抛出一个合成的失败——是消费者的事；重跑就是一次带着新 `runId` 的新运行。

## 自定义传输层

实现 MAY 经由其他通道承载 AG-UI——WebSocket、消息总线、进程内管道。自定义传输层 MUST 保全事件模型、事件模式与处理规则，并 MUST 满足上述绑定契约。它 SHOULD 把自己的分帧、输入投递、终止与错误信号写成文档，以便互通。

承载 JSON 的自定义传输层 SHOULD 完全按 SSE 绑定的方式分帧——每帧一个事件对象——而不是另造信封：SSE 绑定的分帧就是协议的 JSON 分帧，只有它的 HTTP 机械部分才是 HTTP 特有的。
