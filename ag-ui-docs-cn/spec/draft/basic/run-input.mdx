事件从生产者流向消费者。恰好只有一条消息朝反方向流动：`RunAgentInput`，每次开启交换时发送一次。生产者对对话的全部了解都经由它到达。它请求的运行是这次交换的最后一个；回放线程历史的流会[无需再次输入](/spec/draft/basic/transports#the-binding-contract)地携带更早的运行。

[schema](/spec/draft/schema#runagentinput) 定义它的形态；本页说明每个字段带来的义务。生产者 MAY 把输入回显在 `RUN_STARTED.input` 上，让未发起该请求的消费者也能看到智能体被要求做什么。

## 身份

`threadId` 指名对话，`runId` 指名本输入所请求的运行；两者都是 REQUIRED。流上的每次运行都在其边界事件上携带输入的 `threadId`——`RUN_STARTED` 与 `RUN_FINISHED`，这两个承载身份的事件——且每次运行的两个边界事件 MUST 在 `runId` 上一致。被请求的运行回显本输入的 `runId`；被回放的运行则携带自己的。`parentRunId` 是 OPTIONAL，指名派生本次运行的那次运行——当一个智能体把另一个智能体作为独立运行启动时出现。

## `protocolVersion`

在 schema 中为 OPTIONAL，因为缺省标识的是协议还没有版本号年代的参与者——但实现本版本的消费者 MUST 在此声明自己所讲的版本，除非它确知对端早于该字段存在而省略这个成员，以免冒旧解析器拒绝的风险。生产者在 `RUN_STARTED` 上以自己的声明作答；规则见[版本管理](/spec/draft/basic/versioning#version-negotiation)。

## `messages`

REQUIRED。迄今为止的对话，按顺序排列。生产者 MUST 把它当作呈现给自己的完整历史——协议没有更早轮次可以借道的旁路通道。

消息类型及其内容形态——包括多模态的 [`ContentPart`](/spec/draft/schema#contentpart)，以 URL、内联数据或[提供方文件句柄](#提供方文件句柄)的形式在用户消息、以及应答[前端工具调用](/spec/draft/events/tool-calls#frontend-tools)的工具消息上承载文本、图像、音频、视频与文档——都是 schema 的管辖范围。另有两条行为规则：

- 无法使用某个内容部分的生产者——比如把图像交给没有视觉能力的模型——MUST NOT 因此让运行失败。跳过用不上的部分并继续，才是符合规范的行为；在降级的*发出*路径上丢失内容是另一回事，需要给出警告（[版本管理](/spec/draft/basic/versioning)）。
- 活动消息永远不会回到生产者：消费者 MUST 在发送前把它们从 `messages` 中剥离。它们是消费者用来渲染的材料，不是智能体据以续接的对话。

### 提供方文件句柄

媒体部分的 `source` 说明其字节在哪里：内联携带（`data`）、可按 URL 获取（`url`），或已经在模型提供方那里、以提供方签发的句柄指称（`file`）——OpenAI 或 Anthropic 的文件 id、Gemini 的文件 URI、只有该提供方能读取的存储 URL。[`file` 来源](/spec/draft/schema#filesource)之所以存在，是因为句柄既不是前两者中的任何一个：它不携带字节，也不是除签发它的提供方之外任何人能获取的，把它放进 `url` 等于邀请所有其他对端来试。

- `file` 来源的 `value` 是不透明的。对端 MUST NOT 获取它、解析它或从中读出 scheme；要么把句柄交给提供方，要么不用这个部分。
- `provider` 指名谁签发了句柄（在生产者知道的情况下）。它是 OPTIONAL——智能体本来就知道自己在和哪个提供方通信——若给出，SHOULD 是 [`TokenUsage.provider`](/spec/draft/schema#tokenusage) 所用的小写厂商 id，让对端在发送前就能判断该句柄是否为自己可用的。
- 拿到无法解析句柄的生产者——别人的提供方的、未知提供方的、已过期的——就处于上文第一条规则已覆盖的情形：它 MUST NOT 让运行失败，跳过该部分并继续，且 SHOULD 说明这一点。句柄的生命周期由提供方决定；想携带过期时间的生产者可以放在该部分的 `metadata` 里。
- 来源分支是一个封闭集合：`type` 不被对端识别的来源会校验失败，而不是被透传。这正是这个分支放进 1.0、而不是留到后续次要版本的原因——按 1.0 构建的消费者永远不可能把它转发下去。

## `tools`

OPTIONAL。应用自己的工具——即*前端工具*——为本运行提供给智能体：名称、描述，以及工具接受参数时的参数 schema。执行它们的是应用，而不是智能体；调用一个工具就会把控制权交回运行边界之外，这一往返由[工具调用](/spec/draft/events/tool-calls#frontend-tools)规定。

缺省的列表与空列表含义相同：没有工具。生产者 MUST 把缺失的 `tools` 完全当作空的来对待，消费者 MAY 省略空列表而不发送 `[]`。

## `context`

OPTIONAL。应用希望进入智能体上下文的信息，以"描述–值"对的形式。它生来就是要被*注入*的：生产者 SHOULD 把每一条都提供给模型，作为本次运行接地（grounding）的一部分。怎么给——系统提示词、一段开场白，或框架处理上下文的任何方式——是生产者的事；协议只说 context 是给模型看的，不是给传输层记账用的。

缺省与为空含义相同，与 `tools` 完全一致。

## `state`

OPTIONAL。本次运行起始的状态——消费者最后认可的值，通常就是上一次运行的[状态事件](/spec/draft/events/state)留下的东西。`state` 缺省表示空对象：还没有任何共识，而 `{}` 就是什么都没有。发出状态增量的生产者，其增量 MUST 以这个值为基准计算，直到自己的第一个快照将其替换。

## `forwardedProps`

OPTIONAL。透传给智能体、不作改动的应用专属通道。可以是任意 JSON 值，但整体为 `null` 除外——那表示字段被省略。负载内部的 null 值原样保留。协议不为该负载附加任何含义，中间方 MUST NOT 改动它。

## `resume`

OPTIONAL。对结束上一次运行的那些中断的应答，用于本次运行从中断处延续的情形。各条目及其义务由[中断与恢复](/spec/draft/basic/patterns/interrupt-resume)规定。

## 错误处理

生产者无法解析的输入，或格式错误的输入——某个已知字段携带了 schema 拒绝的值——会在 `RUN_STARTED` 之前被拒绝，走传输层的错误路径：运行从不开始，也就不存在可供 `RUN_ERROR` 传输的流。拒绝以何种方式投递，是各[传输层绑定](/spec/draft/basic/transports)的事。

输入中无法识别的成员不算格式错误。[处理模型](/spec/draft/basic/processing)的非对称规则对这个方向同样适用：生产者遇到自己无法识别的输入内容时，剥离它、给出警告并继续运行，这样新版消费者的输入才不会在旧版生产者那里被弹回。
