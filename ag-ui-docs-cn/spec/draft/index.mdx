AG-UI 是一个开放协议，用于规范智能体（agent）与面向用户的应用之间的通信方式：一次请求进入，输出一条有序的类型化事件流，承载用户所见智能体的一切——文本、工具调用、推理、共享状态、进度。

本规范定义协议的权威要求，其依据是 [`schema.json`](/spec/draft/schema.json) 中的 JSON Schema，并以易读的形式呈现为 [Schema 参考](/spec/draft/schema)。

实现指南、概念与示例请参阅[文档](/introduction)。

本文档中的关键词 "MUST"、"MUST NOT"、"REQUIRED"、"SHALL"、"SHALL NOT"、"SHOULD"、"SHOULD NOT"、"RECOMMENDED"、"NOT RECOMMENDED"、"MAY"、"OPTIONAL" 仅当（且只在）以全大写形式出现时，才按 [BCP 14](https://datatracker.ietf.org/doc/html/bcp14) [[RFC2119](https://datatracker.ietf.org/doc/html/rfc2119)] [[RFC8174](https://datatracker.ietf.org/doc/html/rfc8174)] 所述进行解释。

## 本文档是什么

JSON Schema 只描述事件长什么样。它无法描述事件可能以何种顺序到达、实现遇到无法识别的内容时该如何处理、以及何时必须发出警告。这些规则才是协议本身，本文档正是对它们的陈述。

权威的划分是有意为之且绝对的：

- **[schema](/spec/draft/schema) 是结构上的权威**。哪些字段存在、哪些是必填、各字段是什么类型、判别字段（discriminator）可以取哪些值。本文档提及某个字段，只是为了赋予某条规则以意义——绝不复述字段的形态。若两者在结构上不一致，以 schema 为准，本文档视为有误。
- **本文档是行为上的权威**。顺序、生命周期、归因（attribution）、错误处理、兼容性。这些都不是 schema 能表达的。若某个实现与本文档中的规则相悖，则该实现有误。

## 角色

每条规则都指明它约束谁。有两个角色承担义务：

- **生产者**（producer）指发出事件流的一方——智能体、代理、桥接器、测试替身。
- **消费者**（consumer）指读取事件流的一方——客户端 SDK、UI、录制器、另一个代理。

同时承担两种角色的参与者，两组规则都对其生效，且在两个方向上各自独立适用。

## 一致性

当实现满足适用于其扮演角色的每一条 MUST 与 MUST NOT 时，即为符合规范。SHOULD 级别的规则描述优秀实现的做法；偏离 SHOULD 是一个需要给出理由的决策，而不算违规。

一致性按流逐一判定。生产者只要发出过一个格式错误的运行（run），就不符合规范，无论它在其他运行中表现如何。

## 总览

协议可分解为每个实现都要讲的基础部分，以及生产者在有内容要表达时才发出的特性：

- **[事件模型](/spec/draft/basic)**——信封结构、通用字段、标识符。
- **[运行输入](/spec/draft/basic/run-input)**——从应用流向智能体的那条唯一消息。
- **[元数据](/spec/draft/basic/metadata)**——附着在一切之上的开放通道，以及它的合并方式。
- **[事件模式](/spec/draft/basic/patterns)**——流式、快照–增量、中断–恢复。
- **[传输层](/spec/draft/basic/transports)**——HTTP + SSE、HTTP + Protobuf，以及自定义绑定必须满足的契约。
- **[处理模型](/spec/draft/basic/processing)**——中间件先于强制执行；无法识别的内容原样保留，已知值格式错误则为致命错误。
- **[版本管理与兼容性](/spec/draft/basic/versioning)**——与更旧、更新的对端通信，以及内容丢失时需要承担什么。
- **[事件流](/spec/draft/events)**——八大事件族。

## 安全与信任保障

AG-UI 把模型输出转化为应用执行的动作：工具调用变成操作，状态事件变成写入，流式内容变成用户读到的东西。随之而来的是协议无法在线上格式（wire）层面强制执行、但实现者必须正视的义务。

### 关键原则

1. **用户同意与控制**。运行什么由应用决定。在执行有副作用的[工具调用](/spec/draft/events/tool-calls)之前，应用 SHOULD 先取得用户的明确同意；对并非用户批准的操作，MUST NOT 声称已获用户批准。
2. **模型输出是不可信输入**。工具参数、工具结果、[状态](/spec/draft/events/state)内容与[透传](/spec/draft/events/passthrough)负载都跨越信任边界。应用 MUST 校验自己据以行动的数据，并且 MUST NOT 把流式内容渲染为可执行的标记。
3. **数据双向流动**。每次运行中，状态与消息都会经由消费者往返一圈。生产者 SHOULD NOT 在其中放置机密；消费者 SHOULD 以与对话同等的保密级别对待推理内容与加密产物。

### 实现指南

协议本身无法强制执行这些原则。实现者 SHOULD 为重要操作构建同意流程，在每个信任边界校验 schema 与语义，将渲染与执行隔离，并记录足够多的日志，以便审计智能体代表用户做了什么。

## 范围

本文档规定的是协议本身：事件流、运行输入，以及交换双方的义务。它不规定任何具体集成在收到事件之后如何处理、智能体框架应当如何组织，也不规定 UI 应当如何渲染任何东西。

AG-UI 由三个一方官方 SDK 维护——TypeScript、Python 和 .NET——本文档的每条规则对三者同等适用。其他语言绑定由社区维护；当它们声称符合规范时，同样受本文档约束，但本文档的任何内容都不源自它们。
