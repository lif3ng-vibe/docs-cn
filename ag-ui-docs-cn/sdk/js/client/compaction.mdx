# compactEvents

`compactEvents` 在保留语义的前提下，精简事件数组中冗长的流式序列。可以在持久化之前用它压缩日志，或简化服务器推送事件（SSE）流的后续处理。

```ts
import { compactEvents, EventType, type BaseEvent } from "@ag-ui/client"

const compacted: BaseEvent[] = compactEvents(events)
```

## API

```ts
function compactEvents(events: BaseEvent[]): BaseEvent[]
```

## 功能说明

- 文本消息：将同一 `messageId` 的 `TEXT_MESSAGE_START` → `TEXT_MESSAGE_CONTENT*` → `TEXT_MESSAGE_END` 归为一组，把所有 `delta` chunk 拼接成单个 `TEXT_MESSAGE_CONTENT` 事件。
- 推理消息：以相同方式把同一 `messageId` 的 `REASONING_MESSAGE_START` → `REASONING_MESSAGE_CONTENT*` → `REASONING_MESSAGE_END` 归组为单个 `REASONING_MESSAGE_CONTENT` 事件。`REASONING_START`、`REASONING_END` 与 `REASONING_ENCRYPTED_VALUE` 原样透传。
- 工具调用：将同一 `toolCallId` 的 `TOOL_CALL_START` → `TOOL_CALL_ARGS*` → `TOOL_CALL_END` 归为一组，把所有 `delta` chunk 拼接成单个 `TOOL_CALL_ARGS` 事件。
- 交错事件：出现在某一对 start/end 之间的任何事件，都会被移到该序列之后，使流式块保持连续。每个块都停留在其流开始的位置，因此相互重叠的流会保持它们开启时的先后顺序。增量不会跨越 `MESSAGES_SNAPSHOT` 合并，快照本身停留在它到达的位置。
- 透传：所有其他事件（状态、自定义等）原样保留。

## 示例

压缩前：

```ts
[
  { type: EventType.TEXT_MESSAGE_START, messageId: "m1", role: "assistant" },
  { type: EventType.TEXT_MESSAGE_CONTENT, messageId: "m1", delta: "Hello" },
  { type: EventType.TEXT_MESSAGE_CONTENT, messageId: "m1", delta: " " },
  { type: EventType.CUSTOM, name: "thinking" },
  { type: EventType.TEXT_MESSAGE_CONTENT, messageId: "m1", delta: "world" },
  { type: EventType.TEXT_MESSAGE_END, messageId: "m1" },
]
```

压缩后：

```ts
[
  { type: EventType.TEXT_MESSAGE_START, messageId: "m1", role: "assistant" },
  { type: EventType.TEXT_MESSAGE_CONTENT, messageId: "m1", delta: "Hello world" },
  { type: EventType.TEXT_MESSAGE_END, messageId: "m1" },
  { type: EventType.CUSTOM, name: "thinking" },
]
```

推理消息与工具调用的压缩方式与之类似，分别作用于 `REASONING_MESSAGE_CONTENT` 与 `TOOL_CALL_ARGS` chunk。

## 适用场景

- 持久化事件历史（用更少的帧表达同样的含义）
- 为分析或导出准备快照
- 减少测试或调试输出中的噪音

## 元数据

把一连串增量事件折叠起来时，它们的[元数据](/concepts/metadata)也会逐个 key 合并、后写者胜，因此压缩后的流会产生与原始流相同的元数据。在首个增量之后到达的元数据——无论来自后续增量，还是来自重放过的 start——都会按到达顺序随折叠后的事件一起输出，因为压缩会把 start 放在它前面发出。

压缩会移动事件，使每条流的事件聚在一起并停留在该流开始的位置，因此重放时会按原始顺序创建消息。两个并行工具调用即使 end 的到达顺序与 start 相反，它们在助手消息 `toolCalls` 数组中的顺序也保持不变，并各自携带自己的元数据。打断某条流的事件会在这条流之后发出，但 `MESSAGES_SNAPSHOT` 例外：它会重述消息，因此各条开启中的流在其之前交付的内容会先于它发出、其余内容在其后发出，并且任何增量都不会跨越它合并。

## 注意事项与限制

- 该工具只关注消息流与工具调用流。它不会修改状态事件（`STATE_SNAPSHOT`/`STATE_DELTA`），也不会生成消息快照。
- 背景知识与更宏观的模式（分支、规范化）参见 [Serialization（序列化）](/concepts/serialization)。
