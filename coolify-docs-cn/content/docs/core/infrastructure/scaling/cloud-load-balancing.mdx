# 云端负载均衡

云端负载均衡器接收发往你公网域名的流量，并把每个请求转发到其中一台应用服务器。健康检查（health check）让负载均衡器可以停止向无法处理请求的实例发送流量。

应用实例由 Coolify 部署和管理；负载均衡器、后端目标、TLS 设置、健康检查、DNS 和网络规则则由你在基础设施提供商处配置。

## 开始之前

- 完成[多服务器部署](/core/infrastructure/scaling/multi-server-deployments)，并在每台服务器上验证应用。
- 创建一个健康检查端点，在实例就绪可接收流量时返回成功响应。
- 决定负载均衡器是直接连接到映射的主机端口，还是经由每台服务器上的 Coolify 代理（Proxy）连接。
- 如果提供商支持内网，把负载均衡器和应用服务器放在同一私有网络中。
- 决定 TLS 在哪里终结。常见做法是在云端负载均衡器上终结 TLS，再通过私有网络以 HTTP 把流量送到应用服务器。

下面的示例使用 `app.example.com` 作为公网域名、负载均衡器上的 `443` 端口、`/health` 作为健康检查路径。请替换为你应用的实际值。

## 选择负载均衡器访问每台服务器的方式

| <span className="inline-block min-w-40">接入路径</span> | 适用场景 | 权衡 |
| :--- | :--- | :--- |
| <span className="whitespace-nowrap">直接主机端口</span> | 负载均衡器只服务一个应用，或你想绕过每台应用服务器上的代理 | 需要主机端口映射和严格的防火墙规则；主机端口映射会禁用该应用的 Coolify 滚动更新 |
| <span className="whitespace-nowrap">Coolify Proxy</span> | 应用服务器承载多个域名，或你想使用 Coolify 管理每台服务器上的路由 | 多一跳代理，且要求负载均衡器保留请求的 Host 名称 |

在每台应用服务器上映射相同的主机端口。例如 `8080:3000` 把每台服务器上的 `8080` 端口映射到应用容器的 `3000` 端口。

1. 打开应用的 **Configuration**（配置）> **General**（通用）。
2. 把映射添加到 **Ports Mappings**（端口映射）。
3. 从 **Domains**（域名）中移除公网域名，因为请求将绕过 Coolify 代理。
4. 重新部署应用，并从能访问该服务器的网络测试 `http://<server-address>:8080`。
5. 在负载均衡器中把每台服务器地址和 `8080` 端口添加为后端目标。

<Callout type="warning" title="限制被映射的端口">
映射的主机端口可能把应用直接暴露出去。请配置提供商防火墙或服务器防火墙，让该端口只接受来自负载均衡器或其私有网络的流量。
</Callout>

让部署到每台服务器上的应用保持相同的 HTTP 域名。负载均衡器终结公网 TLS，连接每台服务器的 `80` 端口，并转发原始的 `Host` 头，这样 Coolify 代理才能选择正确的路由。

1. 打开应用的 **Configuration** > **General**。
2. 把 **Domains** 设置为带 `http://` 协议的负载均衡域名，例如 `http://app.example.com`。
3. 把应用重新部署到每台服务器。
4. 在负载均衡器中把每台服务器地址和 `80` 端口添加为后端目标。
5. 配置负载均衡器在向应用服务器发送请求时保留 `Host: app.example.com`。

在把服务器加入负载均衡器之前，先从能访问该服务器的网络测试每条代理路由：

```bash
curl --header 'Host: app.example.com' http://<server-address>/health
```

这条路径不要添加主机端口映射。请求必须由 Coolify 代理接收，并通过其 Docker 网络转发给应用容器。

## 配置负载均衡器

在基础设施提供商处创建负载均衡器，然后配置：

1. 一个监听 `443` 端口的公网监听器，并配备 `app.example.com` 的证书。
2. 一个包含所有应用服务器及上述所选端口的后端池。
3. 针对 `/health` 的 HTTP 健康检查，使用相同的后端端口。走 Coolify 代理路径时，把健康检查配置为发送 `Host: app.example.com`。
4. 适合你流量特点的转发策略或算法。
5. 仅当应用尚无法把会话状态保存在共享存储中时，才可选配会话保持（sticky session）。

具体名称因提供商而异。请确认健康的响应会让服务器进入轮换、失败的响应会将其移出。

## 将 DNS 指向负载均衡器

在你的 DNS 提供商处，把 `app.example.com` 指向负载均衡器提供的公网地址或主机名。不要把公网解析记录指向某一台应用服务器。

等待 DNS 变更生效，然后打开 `https://app.example.com`，确认证书有效。

## 验证流量与故障转移

1. 在负载均衡器控制台确认所有后端目标都是健康状态。
2. 向 `https://app.example.com` 发送多个请求，并查看各服务器上的应用日志，确认有多个实例在接收流量。
3. 再从 **Configuration** > **Servers** 停掉其中一台服务器上的应用。
4. 确认负载均衡器把该后端标记为不健康，且公网域名仍能通过其他服务器继续响应。
5. 重新部署被停用的服务器，确认它重新回到健康的后端池。

## 运维注意事项

- 在 Coolify 中增删应用服务器不会自动更新云端负载均衡器。请保持其后端池与应用的 **Servers** 页面同步。
- 把会话、上传文件、队列、缓存和其他共享状态保存在应用容器之外。
- 把后端端口的访问限制在负载均衡器和必要的管理网络内。
- 除了监控各台服务器，还要从基础设施外部监控公网端点。
- 在依赖这套方案保障可用性之前，请演练整机故障，而不仅仅是停掉容器。

提供商专属示例请阅读 [Hetzner 上的负载均衡](/knowledge-base/hetzner-loadbalancing)。如果想用自定义 Traefik 配置代替提供商管理的负载均衡器，请阅读 [Traefik 负载均衡](/core/networking/proxy/traefik/load-balancing)。
