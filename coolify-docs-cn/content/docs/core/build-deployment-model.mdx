# 构建与部署模型

Coolify 将源代码、Docker 配置或现有镜像变成已连接服务器上运行中的容器。

具体路径取决于 Coolify 是构建镜像、从镜像仓库拉取镜像,还是应用 Docker Compose 定义。Coolify 负责协调部署,而 Docker 则在你的基础设施上构建并运行工作负载。

本页聚焦应用。数据库和一键服务使用各自的 Docker 生命周期,并不遵循此处描述的每一条构建路径。

<CoolCallout icon={ArrowsRight} title="简要版">

每次部署都是一个排队的操作。Coolify 解析请求的源码或镜像,准备运行时配置,启动所需的容器,并根据可用的替换路径更新运行中的应用。

最终结果是一组连接服务器上的标准 Docker 资源。Coolify 就是部署和管理这些资源的开源控制平面。

</CoolCallout>

## 什么会触发部署

一次应用部署会把 Coolify 中保存的配置与某个触发器结合起来,例如 **Deploy**、**Redeploy**、Git webhook 或 API 请求。

应用源码决定了 Coolify 在启动容器之前是否需要构建。

## Coolify 如何准备镜像

每个应用容器都从 Docker 镜像开始。Coolify 可以从应用源码创建该镜像,也可以使用镜像仓库中已有的镜像。

  ]}

对于使用 Nixpacks、Railpack、Static 或 Dockerfile 的 Git 部署,Coolify 会查找带有请求提交标签的镜像。如果该镜像已存在于本地或已配置的镜像仓库中,且构建配置没有变化,Coolify 会跳过构建并复用该镜像。

当你需要 Coolify 在不使用 Docker 构建缓存的情况下重新构建镜像时,可使用 **Force deploy (without cache)**。

服务器角色决定一台机器能否构建、能否部署,还是两者兼备。仅部署(deployment-only)的服务器从不在本地构建。专用构建服务器会把构建负载从部署服务器上分离出去。使用构建服务器需要提供镜像仓库中的镜像名称,以便部署服务器能拉取构建完成的镜像。服务器与镜像仓库的具体要求参阅[构建服务器](/core/infrastructure/servers/build-servers)。

## Coolify 如何替换运行中的容器

对于基于源码的应用,Coolify 会先完成镜像构建,再去更动运行中的容器。源码构建失败时,当前应用版本会继续运行。

构建完成之后,或在 Coolify 准备好现有镜像引用与运行时配置之后,替换行为取决于应用类型和配置。

当滚动更新需要验证新容器是否就绪时,请配置[健康检查](/applications/configuration/health-checks)。如果没有配置健康检查、镜像也没有自带健康检查,Coolify 就无法在将新容器视为可用之前测试应用的就绪状态。

在应用页面打开 **Deployments** 可以查看每次部署的状态及其日志。应用运行起来之后,使用 **Logs**、非 Swarm 服务器上的 **Terminal**,以及应用生命周期操作来管理容器。

## 部署之间什么会保留

容器是可替换的。持久化数据必须存放在容器可写文件系统之外,这样新容器才能使用同一份数据。

- **构建时配置**影响镜像,可能需要重新构建。
- **运行时配置**在容器启动时应用,因此当只有运行时设置发生变化时,Coolify 可以复用同一镜像。
- **持久化卷与挂载文件**位于可替换的容器文件系统之外,并会附加到新容器的定义上。
- **未挂载的容器数据**不是持久化的,当 Coolify 替换或移除容器时可能丢失。

镜像、容器、卷和网络之间的关系参阅[Docker 与容器](/core/docker-and-containers)。
