# 数据库的工作原理

Coolify 把控制平面中的数据库定义，与所连服务器上的数据库容器和持久化存储组合在一起。

数据库定义包含所选的引擎和镜像、凭据、部署目标、存储、网络、健康检查、备份和资源设置。Docker 负责运行容器，并把数据库文件存入挂载的卷（volume）。

## 一键数据库在 Coolify 中的工作方式

一键数据库由 Coolify 中针对特定引擎的辅助逻辑创建。该逻辑会应用该引擎的默认值、生成凭据、创建独立数据库记录、创建默认持久化存储，并把你带到数据库的配置页面。资源创建阶段不会启动数据库容器；你先检查生成的设置，再从 Coolify 部署。

资源会关联到某个项目和环境，然后放置到所选的服务器和 Docker 网络目标上。Coolify 会把构建服务器排除在选择之外，因为它们并不用于承载运行中的数据库资源。

受支持的引擎决定了生成的镜像、连接端口、数据路径、凭据、健康探测、连接 URL 格式、SSL 行为，以及是否可用 Coolify 感知数据库的备份流程。例如，PostgreSQL 会在你选好服务器和目标后提供镜像选项；MySQL、MariaDB、MongoDB、Redis、Dragonfly、KeyDB 和 ClickHouse 则使用各自引擎的创建默认值。

## 从创建到数据库运行

1. 在项目和环境中，从 **New Resource**（新建资源）> **Databases**（数据库）选择引擎。
2. 选择数据库应运行的服务器和网络目标。
3. 在 **General**（常规）下检查生成的资源，包括镜像、凭据、端口、连接 URL 和引擎专属设置。
4. 在 **Persistent Storage**（持久化存储）下确认持久化存储。
5. 选择 **Start**（启动）。Coolify 会将启动操作加入队列，在配置了机密管理器时解析其中的凭据，然后准备容器、挂载卷和目标网络，并启动数据库。
6. Docker 运行配置好的健康检查。健康的数据库即可接受能够到达其网络的应用和客户端的连接。

部署后，资源会继续留在项目中。你可以用它的配置和操作页面修改设置、查看日志、打开终端、重启或重新部署。

SQLite 应用通过挂载同一服务器上数据卷中的数据库文件来连接，而不是使用内部 URL。参见 [SQLite](/databases/sqlite)。

## Coolify 管理哪些内容

Coolify 管理资源定义，并在所选服务器上协调 Docker 操作。视引擎和设置而定，它可以管理：

- 数据库镜像和生成的容器配置
- 生成的凭据以及 **General** 中显示的连接 URL
- 默认持久化卷和引擎数据路径
- 目标网络，以及可选的主机端口或公开 TCP 代理
- Docker 健康检查和资源限制
- 引擎支持范围内的 SSL 证书与连接设置
- 受支持引擎的计划数据库备份

Coolify 不会把一键数据库变成集群。复制、分片、故障转移、引擎级用户、表结构迁移和大版本升级仍属于数据库引擎的职责。

## 容器是可以替换的

当镜像或生成的配置变化时，Coolify 可以重建数据库容器。命名卷独立于容器存在，因此常规的容器替换不会删除数据库文件。默认数据路径因引擎而异，对 PostgreSQL 还会因镜像大版本而异。

只写入容器文件系统的数据不受保护。除非已核实数据位置并有备份，否则不要删除或更改数据库的持久化存储挂载。

修改镜像标签或生成的配置，并不等于执行了一次安全的数据库升级。在生产环境更换大版本之前，请先取得经验证的备份并遵循引擎的升级流程。

## 应用如何连接

同一 Coolify 目标网络上的应用应使用数据库的 **Internal URL**（内部 URL）。该 URL 包含生成的凭据、数据库名、容器名和引擎端口。

| 连接位置 | 用法 |
| :--- | :--- |
| 同一目标网络 | **General** 中的 **Internal URL**。 |
| 其他服务器或外部客户端 | 配置好的端口映射，或 **Public access（公开访问）> Access > Public through TCP proxy** TCP 代理，加上生成的公开连接信息。 |

Coolify 默认不发布数据库端点。对外暴露前，先阅读[网络访问](/databases#网络访问)。

## 健康检查反映数据库就绪状态

数据库健康检查是 Docker 健康检查，不是备份，也不是数据完整性检查。在 **Healthcheck** 下配置 **Interval (seconds)**（间隔）、**Timeout (seconds)**（超时）、**Retries**（重试次数）和 **Start period (seconds)**（启动等待期）。健康检查通过只说明配置的探测命令通过了，并不确认应用查询或复制配置是否正确。

## 备份因引擎而异

Coolify 为 PostgreSQL、MySQL、MariaDB、MongoDB、ClickHouse 和 SQLite 运行感知数据库的计划备份。面板恢复适用于 PostgreSQL、MySQL、MariaDB、MongoDB 和 SQLite。ClickHouse 备份需要在该导入流程之外恢复。Redis、Dragonfly 和 KeyDB 有持久化存储，但不提供计划备份或面板恢复流程。

备份目的地可以是本地存储，也可以是 S3 兼容的存储桶。备份独立于运行中的数据库卷：它为你提供一份可以存放在数据库服务器之外的恢复产物。

计划、保留策略和存储见[配置数据库备份](/databases/backups)；受支持的导入流程见[恢复数据库](/databases/restore)。

## 控制平面与数据库服务器

Coolify 是控制平面（control plane），负责保存资源配置并协调操作。所连的服务器是工作负载机器，负责存储 Docker 卷并运行数据库容器。

只要 Docker、服务器、网络和数据库保持健康，即使 Coolify 控制平面暂不可用，运行中的数据库容器也能继续提供服务。新的 Coolify 操作则需要控制平面可用。
