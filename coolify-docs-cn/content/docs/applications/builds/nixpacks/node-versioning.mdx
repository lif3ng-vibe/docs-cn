# Nixpacks 中的 Node.js 版本

Nixpacks 支持选择 Node.js 的主版本。构建所用的 Nix 软件包归档决定了具体的次版本和补丁版本。

## 选择主版本

在仓库中只保留一个版本的唯一事实来源：

```json
{
  "engines": {
    "node": "22"
  }
}
```

Nixpacks 也能读取 `.nvmrc` 或 `.node-version`。

或者，在 Coolify 中添加一个构建变量：

```dotenv
NIXPACKS_NODE_VERSION=22
```

保持 **Build time**（构建时机）为 **Available during build**（构建期间可用），然后重新部署并查看构建日志，确认解析出的版本。

## 为什么版本范围无法固定补丁版本

`22`、`22.x`、`>=22` 这类取值只会选择兼容的主版本，并不会告诉 Nixpacks 该使用哪个 nixpkgs 归档。

选定的归档里包含一个特定的 Node.js 软件包。因此即便应用里的版本设置没有变，一次构建也可能解析出 Node.js `22.13.1`、`22.14.0` 或其他 `22.x` 版本。

## 固定 nixpkgs 归档

当应用必须固定使用某个 nixpkgs 提交的软件包集合时，在应用源码目录中添加 `nixpacks.toml`：

```toml
[phases.setup]
nixpkgsArchive = '51ad838b03a05b1de6f9f2a0fffecee64a9788ee'
```

该值是 [NixOS/nixpkgs repository](https://github.com/NixOS/nixpkgs?utm_source=coolify.io) 中一个完整的提交 SHA。示例提交中包含 Node.js `22.13.1`。

重新部署并查看 Nixpacks 构建日志，确认从固定归档中选出的 Node.js 版本。

<Callout type="warning" title="固定归档会改变整个软件包集合">

一个 nixpkgs 提交控制的远不止 Node.js。固定归档还可能改变构建使用的系统库和其他软件包。在把归档变更推向生产环境之前，先测试镜像和应用。

</Callout>

当部署要求运行时完全可复现时，请使用带精确基础镜像标签或 digest 的 [Dockerfile](/applications/builds/dockerfile)。

## 查找归档提交

要为所需的 Node.js 版本定位一个 nixpkgs 提交：

1. 打开 [NixOS/nixpkgs repository](https://github.com/NixOS/nixpkgs?utm_source=coolify.io)。
2. 找到 Node.js 版本定义文件，例如 `pkgs/development/web/nodejs/v22.nix`。
3. 打开该文件的历史记录，找到引入所需版本的提交。
4. 确认该修订中的 `version` 和源码哈希。
5. 把完整的提交 SHA 复制进 `nixpacks.toml`。
6. 在非生产环境中部署，并在构建日志中验证解析出的 Node.js 版本。

例如，提交 [`51ad838b03a05b1de6f9f2a0fffecee64a9788ee`](https://github.com/NixOS/nixpkgs/commit/51ad838b03a05b1de6f9f2a0fffecee64a9788ee) 把 Node.js 22 软件包从 `22.12.0` 更新到 `22.13.1`。

Nixpacks 的相关设置请阅读上游的 [nixpkgs archive configuration](https://nixpacks.com/docs/configuration/file#nixpkgs-archive?utm_source=coolify.io)。
