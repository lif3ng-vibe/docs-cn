# 滚动更新

对于 Nixpacks、Railpack、Static、Dockerfile 和 Docker Image 类型的应用，Coolify 可以在当前容器继续运行的同时启动替换容器。

**Docker Compose 应用不支持滚动更新**。Docker Compose 使用自己的服务协调过程，而不是 Coolify 应用层的滚动更新流程。

<Callout type="warning" title="滚动更新并不保证零停机">

Coolify 可以让新旧容器并存、等待健康检查通过，并为旧容器留出停止时间。但应用自身仍需准确报告就绪状态、优雅地处理关闭，并在两个版本同时运行期间保持兼容。

如果应用不配合这一流程，滚动更新期间请求仍可能失败。

我们近期会发布一篇详细指南，介绍如何让应用为接近零停机的部署做好准备。

</Callout>

## 滚动更新的工作方式

对于符合条件的应用部署，Coolify 会：

1. 在不停止当前容器的情况下启动替换容器
2. 如果 Coolify 或镜像中配置了健康检查，等待替换容器的健康检查通过
3. 替换容器变得不健康时，保留当前容器
4. 替换容器被认定就绪后，停止并移除当前容器

没有健康检查时，Coolify 会把成功启动的容器视为就绪。在停止当前容器之前，它无法判断应用是否已完成初始化、能否正确处理请求。

## 应用需要处理什么

容器由 Coolify 控制，但切换过程对用户是否安全，取决于应用本身。

| <span className="inline-block min-w-52 whitespace-nowrap">应用责任</span> | 为什么重要 |
| :--- | :--- |
| 准确报告就绪状态 | 在应用能够处理真实请求、所需依赖可用之前，健康检查必须保持失败。 |
| 优雅关闭 | Docker 会要求旧容器停止。应用应停止接受新请求，完成或安全放弃进行中的请求，并在配置的宽限期内退出。 |
| 保持版本兼容 | 新旧版本会同时运行。在该重叠期内，数据库迁移、API、队列、缓存和共享文件必须同时兼容两个版本。 |
| 支持并行实例 | 会话和必要的状态不应只存在于单个容器中。调度器、队列消费者等后台任务必须能容忍两个版本短暂并行。 |

健康检查只能证明其命令或端点所检测的内容。例如，一个始终返回 `200` 的端点，可能在应用尚未真正就绪时就把容器标记为健康。

要配置能代表应用就绪状态的 HTTP 或命令检查，请参阅[健康检查](/applications/configuration/health-checks)。

## 配置优雅关闭

打开 **高级 > 运维**（Advanced > Operations），将 **Stop Grace Period (seconds)**（停止宽限期，秒）设置为应用收到终止信号后所需的最长时间。

默认值为 30 秒。Coolify 接受 1 到 3600 秒之间的取值。

加大宽限期可以给旧容器更多时间完成在途工作，但不会给应用增加优雅关闭的行为。应用必须自己处理终止信号并正确退出。

## 会阻止滚动更新的设置

新旧容器必须能够同时运行。只要出现下列任一情况，Coolify 就会先停止当前容器：

| 条件 | 容器为何无法并存 |
| :--- | :--- |
| 在宿主机上发布了端口 | 两个容器无法绑定同一个宿主机端口。 |
| **Container naming** 设为 **Consistent name (no rolling updates)** | 两个容器会使用相同的 Docker 容器名。 |
| 配置了 **Custom Container Name** | 两个容器会使用相同的自定义名称。 |
| `--ip` 或 `--ip6` 指定了自定义 IP | 两个容器会需要同一个网络地址。 |
| 部署属于 pull request 预览 | 预览部署不使用 Coolify 应用层的滚动更新路径。 |

可选的自动生成 **Container Name Prefix**（容器名前缀）会保留部署专属的时间戳，不会禁用滚动更新。参见[容器命名](/applications/configuration/advanced#容器名前缀)。

当 Coolify 检测到上述任一情况时，部署日志会说明不支持滚动更新的原因。在启动替换容器之前先停止当前容器，会在替换容器启动期间造成中断。

## Docker Compose 与 Docker Swarm

Docker Compose 应用不使用 Coolify 应用层的滚动更新流程。Coolify 执行 `docker compose up`，由 Docker Compose 协调 Compose 文件中定义的服务。

Docker Swarm 应用使用 `docker stack deploy` 并采用 start-first 的服务更新策略。副本替换和路由由 Docker Swarm 控制，因此其行为取决于 stack 配置以及每个副本中的应用。

这两种部署方式本身都不保证零停机。应用的健康检查、关闭处理、状态管理与兼容性表现依然关键。

## 测试完整的切换过程

在把滚动更新当作可用性保障之前，请用接近生产的流量进行测试：

1. 配置一个健康检查：应用启动期间保持失败，只有能处理请求时才通过
2. 确认应用能处理终止信号，并在 **Stop Grace Period (seconds)** 内完成请求
3. 部署一个向后兼容的改动，同时持续请求应用的关键端点
4. 打开部署日志，确认出现了 **Rolling update started**、**New container is healthy** 和 **Rolling update completed**
5. 确认整个部署期间测试请求始终成功
6. 核查后台任务、会话、数据库写入和持久化数据是否始终正确

如果新容器在 Coolify 移除旧容器之前就已转为健康，说明容器并存已生效。只有在切换期间用户请求和应用任务也始终成功，才能确认做到了零停机。

## 排查被打断的更新

如果当前容器在替换容器启动之前就停止了，请在部署日志中排查是否存在宿主机端口映射、一致或自定义容器名、自定义 IP 或预览部署。

如果替换容器启动了，但部署失败：

1. 查看报告的健康检查状态和日志
2. 确认健康检查命令存在于镜像内，并且访问的端口或路径正确
3. 确认应用在健康检查重试耗尽之前完成启动
4. 核查新旧版本能否同时使用相同的数据库、队列、存储和外部依赖

如果替换容器转为健康后请求仍然失败，请收紧就绪检查，并核实应用的优雅关闭处理。容器健康检查通过本身并不能证明切换做到了零停机。
