项目会变，Impeccable 的安装却可能停在原地。Doctor 检查保存的上下文、配置和钩子，找出诸如文件格式过旧、设置不起作用、钩子指向缺失脚本之类的问题。

## 检查你的项目

在你的 AI 编码工具里：

```text
/impeccable doctor
```

也可以直接问："这个项目的 Impeccable 安装里，有什么过时了？"

**工作原理：**

1. **检查安装。** Doctor 检查产品记录、视觉记录、配置、已保存的页面简报和设计钩子。
2. **修复机械性问题。** 它应用不需要设计或产品决策的迁移，并报告改了什么。
3. **解释剩下的发现。** 它给出具体的修复方案，或指向需要你输入的命令。若无需关注任何内容，你会得到一条简短的确认。

Doctor 负责维护安装本身。它不会在修复过程中重新设计界面，也不会改写你产品的定位。

## 一条可行动的发现

下面这个例子里，项目文件夹被改名了，配置却还指向旧名字：

**磁盘上的文件夹**

```text
apps/
└── store/
```

**保存的项目根目录**

```json
"projectRoots": [
  "apps/old-name"
]
```

> **Doctor 发现：配置的文件夹不存在。** Impeccable 目前把仓库根目录当作活动项目。改动设置之前，先确认它应该指向哪个文件夹。

来自一次在小示例项目上的真实诊断。此处仅概述该发现；Doctor 没有改动配置。

### 哪些会被自动修复

发现的类别描述的是下一步动作，而不是问题有多严重：

| 类别 | 会发生什么 |
|---|---|
| **机械性** | Doctor 应用一条明确的迁移，比如把设计伴随文件从已废弃的位置移走，并报告这一改动。 |
| **值得了解** | 它解释这条发现并给出修复建议。你的工作可以继续。 |
| **需要一条命令** | 它指出缺口，并推荐诸如 init 或 document 的命令。该命令在你发起时才运行。 |

过时的文件格式可能有机械性修复；而判断文件是否仍然符合你的产品或设计，需要审阅其内容。

## 会话开始时的提示

会话开始时，Impeccable 还会运行一次轻量检查。它可能标记：较旧的产品记录格式、需要刷新的设计伴随文件、无法识别的配置键，或者原生应用文件搭配着仅面向 Web 的上下文。

这些提示不会阻塞你的任务。同一条发现在每个项目里至多每周展示一次。想要更完整的报告（包括损坏钩子的检查，以及视觉记录上次更新之后的变动），随时运行 Doctor。

### 只在我要求时才显示报告

在 `.impeccable/config.json` 里设置 `"stalenessCheck": false`，即可在项目级关闭会话开始提示。在环境里设置 `IMPECCABLE_NO_STALENESS_CHECK=1`，可做一次仅限当前会话的覆盖。

即便关闭了这些提示，你仍然可以运行 `/impeccable doctor`。

## 参考细节

### 检查哪些文件和设置？

- **PRODUCT.md：**较旧的 schema 版本、已废弃的字段，以及记录的平台与原生构建文件之间的冲突。schema 版本描述的是文件格式；Impeccable 发布一个新的补丁版本本身并不会让记录过时。
- **DESIGN.md 与 .impeccable/design.json：**视觉记录里的缺口、过时的伴随文件 schema、比记录更旧的伴随文件，以及已废弃的文件位置。DESIGN.md 遵循外部的 design.md 格式，不带 Impeccable 的产品 schema 戳。
- **配置：**无法识别的顶层或 detector 键、已不存在的被忽略规则 ID、已消失的精确忽略文件路径，以及匹配不到任何文件夹的项目根模式。适用时，Doctor 还会检查保存的视觉稿/代码工作流选择。
- **设计钩子：**缺失的脚本路径，以及已安装钩子与其启用状态之间的冲突。
- **已保存的页面简报：**其关联文件或路由已找不到的记录。

如果规则注册表不可用，报告会说明它无法校验被忽略的规则 ID。

### 代码改动多，就意味着 DESIGN.md 错了吗？

有一项检查会统计自 DESIGN.md 上次编辑以来，视觉源码目录里的提交数。这个数字是"值得去看一眼"的理由，不是记录有错的证据。

想知道具体变了什么，可以让 Impeccable 把记录与你当前的令牌和组件做对比。用 [document](/docs-cn/impeccable/docs/document)) 更新视觉记录，或用 [init](/docs-cn/impeccable/docs/init)) 重新梳理产品上下文。

### 包含多个应用的项目

指明要检查的应用：

```text
/impeccable doctor --target apps/store
```

不给目标时，报告描述的是仓库根目录。它也会列出哪些应用拥有自己的产品与设计记录、哪些继承自仓库。

继承通常是有用的。当应用之间差异明显时再检查它：原生应用继承 Web 产品记录，可能收到错误的平台指引。当某个应用需要独立的产品上下文时，给它单独的 PRODUCT.md。

### 这是更新 Impeccable 本体的方式吗？

更新已安装的工具版本请用更新命令：

```bash
npx impeccable update
```

Doctor 检查的是项目已保存的安装与当前版本期望之间的差距。可用的工具更新会单独提示。
