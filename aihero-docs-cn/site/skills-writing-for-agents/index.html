    它做什么

    writing-for-agents 是写给智能体读的文档的参考：一个技能、一份 AGENTS.md 或 CLAUDE.md，一份 规格（spec）、一条运行时提示词、一份 README——任何 智能体 会读的文档。格式各异，写法却相同。同一组杠杆让每一种都可预测，于是智能体每次运行都遵循同一套 流程（process） （产出不一定相同）。

    它的默认修法是删除，不是解释。让一个智能体给另一个智能体写指令，它会把大部分字数花在解释 模型 已经知道的事上。那些行每一行都是一句 空话（no-op）：它消耗 上下文 却不改变任何行为。这个参考帮你把它们找出来，所以无论对一份已有的文档还是一张白纸，它都一样有用。

    它以前叫 writing-great-skills ，v1.1 改的名。新名字符合它一直以来的本质：里面几乎没有内容是技能专属的。只跟技能有关的机制（frontmatter、模型调用还是用户调用的选择、路由技能）放在一份链接的 SKILL-MECHANICS.md 里，只有当你面前的文档是一个技能时才需要读。

    什么时候用它

    输入 /writing-for-agents，或者在创建或编辑技能、修改 AGENTS.md 或 CLAUDE.md.

    其余智能体会读的东西，手动调用它：你的文档、规格和 工单（ticket），系统提示词与 AFK 提示词。检验只有一个问题：智能体会读这个东西吗？智能体怎么拿到文档无所谓：一个指针点名它、一个人粘贴它、或它就在仓库里。想知道代码库里有什么，用 grill-with-docs。这个参考管的是文档读起来如何，不是它知道什么。

    两种负载

    核心思想是每份文档和每个指针都要花的两笔预算：

    • 上下文负载（上下文 load）：常驻材料加在智能体窗口上的成本：一条 AGENTS.md 行、一段技能描述、任何每一 轮（turn） 都待在上下文里的东西，无论它是否触发。
    • 认知负载（cognitive load）：你要记住哪些文档存在、何时取用哪一份的成本。你就是那个索引。别试图把这个成本压到最小，因为这是人保住自主权的代价。

    一旦用这两种负载思考，大多数写作决策（拆不拆、内联还是披露、指过去还是推过去）都成了同一笔在不同位置的取舍。

    杠杆

    • 上下文指针（上下文 pointers）：留在上下文里的引用，它点名上下文之外的材料，并编码何时去取。一段技能描述和一条 AGENTS.md 里点名某份文档的行是一回事。指针的 措辞（w或ding），而不是它的目标，决定智能体跟随它的可靠程度。
    • 信息层级（inf或mation hierarchy）：从文内步骤，到文内引用，再到指针后面披露的引用，这样一架梯子。 渐进披露（progressive disclosure） 就是把材料沿梯子往下挪，让顶端保持易读。
    • 完成判据（completion criteria）：每一步的完成条件有多清晰、多苛刻，以及这种苛刻造成的 跑腿活（legw或k） 。它们是抵御 过早收工（premature completion）.
    • 引导词（leading w或ds）：模型预训练里已有的紧凑概念（tight, red, tracer bullet（曳光弹）），智能体执行文档时用它思考。它在两处起作用：在正文里引导执行，在指针里触发调用。
    • 修枝（pruning）：单一事实来源、相关性、逐句施加的空话检验，防的是 重复（duplication）, 沉积（sediment） 和 蔓延（sprawl）.

    常见问题

    原来的 /writing-great-skills 去哪了？ 就是这个技能，v1.1 改的名。早在改名之前，用户就把它指向了 AGENTS.md、文档、规格、工单和运行时提示词。结构、引导词和修枝适用于智能体会读的任何文本。没有别名，用新名字重装。

    “Writing f或 智能体s”（为智能体写作）：所以是智能体来写？ 正相反。你是作者，智能体是读者。这正是难点所在。你面对的读者已经读过一切，所以解释是浪费，精确就是全部工作。

    我就不能让智能体替我写吗？ 可以，而它写出来的东西会很啰嗦。放着不管，模型会解释它已经知道的事，也不会自己施加空话检验或挑一个引导词。用这个参考来评审草稿。它的大部分价值来自那次评审。

    我让智能体精简一份文档，它把功能剪掉了。 被要求“精简”的智能体会按长度优化，因为长度是它们看得见的东西。空话检验查的是行为，不是文风：删掉那一行，问智能体的行为变没变。一句话不合格，就删整句，而不是从中抠字；有分歧就跑一遍文档来裁决，不要靠吵。

    我怎么知道什么时候算完成？ 当它能用了、你再找不到重复、沉积或空话的时候。没有自动化评测。你靠手动运行文档、用失效模式的词汇来诊断问题。文档行为不端时，同一套词汇帮你修它：先说出失效模式，再修那个。

    该放在 CLAUDE.md 还是别的地方？ 问自己想付哪笔负载。 CLAUDE.md 无条件加载进每一个 会话（session） 。指针后面的材料在触发之前只花指针自己那一行。十次会话里只适用一次的东西，会让另外九次都付上下文负载。

    每出一个新模型，我都得重写我的文档吗？ 大多不必，而且过拟合到某一个模型会带来自己的问题。为新模型更新通常只是再来一轮空话清理，不是重写。

    我的技能只在我当初构建它的那个任务上有效。 常见做法（先做一遍工作，再让智能体把它写成技能）跟那一次运行贴得太近，例子也写得过于具体。把那次运行留作证据，然后刻意泛化：剥掉属于那个仓库、那些文件的东西，为这类任务而写。

    英语不是我的母语。我会失去引导词的优势吗？ 不会。找到用最少的 token 装下最多行为的那个词，是这份参考替你做的活。

    正常工作的标志

    • 文档越好越短，你会惊讶居然剩这么点。
    • 你能指着一个引导词，看到它在不止一处改变了智能体的行为。
    • 任何形式下都没有任何话被说两遍。重复是“文档从没被测过”的最可靠信号。
    • 只有一条分支需要的参考放在指针后面，而不是主文件里。

    它的定位

    这是一份随时可用的独立参考。它适用于整个技能集，不止一个技能。这里的每个技能都是用它写的，它也覆盖其他技能产出的文档（一份 GLOSSARY.md 和它的 ADR、一份规格、一张工单），只要智能体得读它们。它唯一直接的调用者是 retro，它在提议任何引导文件或技能之前先加载这份参考。拿不准哪个技能或流程适合一个任务时， ask-matt 在整个技能集里给你指路。
