    它做什么

    ask-matt 是本仓库全套技能之上的路由器。你描述自己身处的处境（一个无法启动的想法、一堆涌进来的 bug 报告、一场 会话 跑了很久的会话），它就会点出合适的技能或技能序列，以及这条序列里人的决策落在何处。

    它只推荐，然后停止。它不追问、不写 规格（spec）、不开文件、也不触发它刚点名的技能；你得到的是下一步该输入什么，而输入的人是你。它还是一张手工维护的仓库技能地图，而不是对你已装内容的扫描，所以它不会把你路由到你自己的技能或其他作者的技能上。

    什么时候用它

    调用方式是输入 /ask-matt，智能体不会自己主动调用它。

    你的处境路由器给你的回复
    有一个想法，不知道从哪开始主流程的头部，以及这次构建是否小到可以跳过规格
    从别人那里涌来的 bug 和请求通往 triage 的上匝道，以及为什么 工单 是你自己生成的，不该上那条道。
    两个看起来可互换的技能两者的分界线——通常是一条具体的判据，不是口味问题。 grill-me 还是 grill-with-docs 取决于你是否身处一个工作目录； grill-with-docs 还是 wayfinder 取决于工程是否装得进一个会话
    一场拖长的会话，和一次关于 上下文阶段边界上五个选项的有序决策树
    你已经选定的技能没有有用的回复。直接调用那个技能。

    前置条件

    路由器点名技能，但不安装技能。它指到的一切都得已安装，推荐才有可操作性，而且它只认识本仓库里被推广的那些技能。

    依赖工单追踪器的路线（triage、 to-spec, to-tickets, implement）则假设 setup-matt-pocock-skills 已经在仓库里配置好了工单追踪器（issue tracker）。哪怕这还没发生，路由器也会推荐它们。

    是流程，不是技能

    这个技能的领头词是 流程（flow），一条 贯穿 技能的路径，而不是单个技能。你说出自己的处境，路由器就把你放到某条流程上的一步。这与“这里是匹配你关键词的技能”是完全不同的答案。路线有五种，技能本身对它们有完整描述：

    • 主流程，从想法到上线。追问、规格、工单、实现（一次一张工单，或用 implement-规格（spec）并行跑完整个任务图），评审，然后 retro——它把这次构建教给我们的东西回馈进智能体的环境。它有两条分支。一是原型绕道，用于问题需要可运行的代码才能定论的时候。二是规格与工单拆分，只有当构建跨多个会话时才值得付出这个成本。
    • 上匝道，用于那种先产生工作、再汇入主流程的处境：涌进来的 bug 报告、坏了的东西，或是太雾太大、单个会话装不下的工程。
    • 代码库健康，是维护，不是特性开发。 improve-codebase-architecture 勘察代码寻找加深机会，它找到的每一个机会都会作为一个想法重新进入主流程。
    • 独立技能，它们挂在每条流程之外，单独使用：原型、问卷、调研运行。
    • 底层还有一个词汇层，也就是当问题出在词而不是流程时，其他技能拉进来的那两份参考。

    阶段边界

    这个技能的另一个关键理念是 阶段边界（phase boundary）。阶段是会话里的一段工作（ 追问、实现、QA），而两者之间的边界是唯一适合问“这份上下文怎么办”的地方。阶段中途没什么可决定的：要么继续，要么把剩下的拆给 子智能体.

    选项何时选它
    继续下一个阶段需要原样保留这一段，或者你还剩有 聪明区（smart zone） 。它是唯一能把会话保留为 一手来源的招，所以先把它排除掉
    /clear你身后的一切都可抛弃。这是最便宜的选项，但选错了无法撤销
    h和off有东西必须随身携带：新的 harness、新目录、一位同事、一个中途分叉的支线任务
    子智能体任务收得足够紧，你 离开键盘（AFK）
    /compact以上皆非。这是默认项，决策树常常到此为止

    人们常搞错其中两项，所以路由器给的是顺序，而不只是清单。 /handoff 看起来是在上下文窗口之间移动的通用方式，但它不是。它给你的只有可移植性。 /compact 是树上的最后一个选项，而不是第一个，因为排在它前面的四个选项都更便宜或更精确。

    常见问题

    难道就没有一张按正确顺序排好的技能清单吗？

    人们在 README 里不断要这样一份清单。这个技能就是那份清单。一张静态表格只会说 wayfinder → to-spec → to-tickets → implement → code-review → retro ，然后在大多数处境下出错。重要的部分是那些分支：有没有代码库、构建是否跨会话、谈话能否定夺这个问题。代价是路由器靠手工维护，所以会落后于仓库。 /grilling 早在路由器点名它之前就已发布。

    它告诉我一半的技能没装。

    这是一个已知 bug，尚未修复。路由器带你经过的大多数技能设置了 disable-model-invocation: true，意思是 harness 把它们排除在注入智能体上下文的技能清单之外。智能体把那份清单当成全集，报告它们缺失。在一个被报告的会话里，它宣称整条规格与工单流程不存在，转而路由到裸的 /grilling 和 /tdd。插件的二十七个技能里有十六个带这个标记，所以这是常态而非边角。它们其实装好了。照样输入斜杠命令，或者去查 .claude-plugin/plugin.json——那才是“装没装”的权威。

    它描述了某个技能的行为，但那个技能并不那么干。

    这也是一个真 bug，同样未修复。路由器根据它自己对每个技能的一行摘要作答，而不是根据技能本身。一份详细的报告在单个会话里追踪到三起，其中包括建议跳过 to-规格（spec） ——唯一依据是“把对话变成一份规格”这句摘要。路由器从头到尾没打开过 to-spec/SKILL.md。每一次都只有在用户反驳之后它才去核实，从不主动核实。跳过 to-spec 让一次真正的接缝检查泡了汤，产出的工单也低估了工作量。当路由器对另一个技能的陈述会影响你的行动时，让它先打开那个 SKILL.md 再说。这条同样适用于地图完全没有覆盖的问题，比如该不该用 计划模式：那个答案是 模型的推断，不是这里写下来的东西。

    为什么它是散文，而不是带编号的清单？

    这个抱怨有道理。有一个未决 issue 主张大部分路由是确定性的，叙事形式让它难以扫读。没什么能阻止你要求压缩版：说“直接给我序列”，你就会拿到序列。散文承载的是条件性的部分：分支在哪、哪里需要人来决策、步骤之间在哪清空或压缩上下文。扁平清单丢掉的恰恰是这些。

    它能路由到我自己的技能或其他作者的技能吗？

    不能。有三个独立的提案要求做一个读取你本地 skills/ 目录、从已安装内容里推荐的路由器。 ask-matt 不是那个东西。它是一套技能的地图，手工维护，对你自己写的或从别处装的技能一无所知。

    它让我去改一个 SKILL.md。

    这个建议往往是对的，但改动很少能留住。有人问它怎么让 implement 去关工单，得到的答案是往技能里加一行，他立刻看出了问题。 npx skills update 会覆盖那个文件，而插件安装是只读的。常设行为放进你自己的 CLAUDE.md 还是 AGENTS.md，或在调用时说明。你在提示词里做的改动能挺过更新。人们就这样把流程指向 Linear 而不是 GitHub，或者问它哪些未关工单可以并行跑。

    它点名了一个我没有的技能，或者漏掉了我有的。

    先去 changelog 查一下有没有改名，再断定它没了。 writing-great-skills 变成了 writing-f还是-agents ，没有留别名； to-prd 变成了 to-规格（spec）, 和 pathfinder 变成了 wayfinder。有四个技能被彻底裁撤，并入吸收它们的技能： ubiquitous-language, design-an-interface, qa 和 request-refactor-plan。如果它漏掉了一个你有的技能，那是上面说过的路由器自身的滞后。

    正常工作的标志

    • 它以点出该输入什么收尾，然后就停在那里，而不是自己动手开工。
    • 它给出的路线会提到在哪清空或压缩上下文、哪里该由你评审，而不只是一串技能名。
    • 两个技能相近时，它会说是哪个、以及为什么另一个不适合你。
    • 它对另一个技能行为的任何断言，都会在轨迹里体现为它读过那个技能的 SKILL.md.
    • 你在它递回的内容里认出的是自己的处境，而不是最接近的通用场景。

    它的定位

    ask-matt 是一个 独立路由器（st和alone router） ，架在整套技能之上。它永远不会是链条中的一步。它指向每条链条，其他文档页都回链到它，免得每页重画那张图。从这里你最常落到 grill-with-docs——主流程的头部——或者 triage——为送上门的工作而非你开启的工作准备的上匝道。

    它是 二手来源 ，描述它覆盖的那些技能。当路由器与某个 SKILL.md 不一致时，以 SKILL.md 为准。
