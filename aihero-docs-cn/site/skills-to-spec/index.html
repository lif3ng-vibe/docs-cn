    /to-规格（spec） 技能

    把一场谈定了的对话写成一份规格。

    Matt Pocock

    然后输入 /to-spec （在你的编码智能体里）。

    它做什么

    to-spec 把你刚结束的那场对话变成一份 规格（spec），并作为单个 issue 发布到你的工单追踪器。

    它不访谈你。你调用它时，决策已经做完。所以它综合已知的东西（来自对话串、代码库、你的 GLOSSARY.md 和 ADR），不会开启新一轮提问。规格记录你已经做过的决策，不是用来做新决策的地方。

    什么时候用它

    调用方式是输入 /to-spec； 智能体 不会自己主动调用它。

    当构建大到超出一个智能体 会话（session） 的容量、必须拆到多个会话时用它。触发条件就这一条：

    你所在的位置该运行什么
    你还什么都没决定grill-with-docs 先跑
    已决定，且工作装得进一个 上下文窗口（context window）implement：跳过规格
    已决定，且工作横跨多个会话/to-spec，然后 to-工单（ticket）
    A wayfinder 地图已清空/to-spec #<map_issue>

    前置条件

    to-spec 把规格作为 issue 发布，所以 setup-matt-pocock-skills 必须先为这个仓库配置好追踪器和分诊标签词汇。哪种追踪器都行：GitHub 这样的真实追踪器，或者放在 .scratch/下的本地 markdown 文件（零额外配置）。

    规格是一份决策记录

    规格之所以存在，是因为上下文窗口会结束。在 追问（grilling）的时候你已经敲定了很多事：方案的形状、你争论过才定下的选择、你刻意拒绝的东西。所有这些都装在你即将清空的一场对话里。规格把它们保住。

    所以规格不验证、也不决定任何东西。它用你项目自己的词汇记录你决定过的事，让一个全新的会话能接手工作，而不用你重新解释一遍。如果规格写出了你从没说过的东西，那就是缺陷。

    先接缝，后行文

    在写任何东西之前， to-spec 会先勾出 接缝（seam） ——这个特性将在哪些接缝处被测试——并跟你确认。它优先用已有接缝而不是新开接缝，并选它能选到的最高接缝。一个变更的理想接缝数是一。

    其他技能之后会用到这些谈定的接缝。 tdd 只在你们事先谈定的接缝上工作。 code-review 对照规格评审 diff，所以一条没人同意过的接缝会以评审发现的形式冒出来。这两条关联都要经过这份文档。这就是为什么你要在这里认真对待接缝对话，别把它留给实现阶段。

    常见问题

    原来的 /to-prd 去哪了？ 就是这个技能，v1.1 改的名。现在全套统一只用“规格（规格（spec））”这一个词，旧的 to-prd slug 已失效，请用新名字重装。旧词汇被这一对词取代： 规格（spec） 和 工单（ticket）。规格是终点和敲定终点的那些决策。 工单（ticket） 则是到达终点的步骤。如果你改变方向，删掉没做完的工单，留下规格。

    为什么规格会被打上 ready-for-agent 标签？我可不想有智能体照着它实现。 这个标签的意思是“无需再分诊”：文档已经完整到智能体可以直接照着干。它标记的是一份输入，不是一张工作指令单。但 AFK 轮询 ready-for-agent 的 AFK 智能体看不见这个区别。它们会试图一趟把整份规格建完，而不是领取工单切片。这是该技能被报告最多的问题。在它改变之前，在你的 AFK 智能体提示词里明确排除父规格，或者在 /to-tickets 跑过之后把标签摘掉。

    为什么不从追问直接到 /to-tickets ，跳过规格？ 很多时候你应该这么做。只有多会话的工作才配得上规格这一步。它的价值在于工单是用完即弃的，规格不是。每张工单按一个全新上下文窗口的容量来定大小，随后被删除或关闭，而规格留下来，作为记录其背后推理的唯一地方。单会话的变更里，这给不了你任何东西，你还为一个额外的综合步骤付了代价，而 模型 在这一步可能跑偏。从追问直接到 /implement.

    我刚画完一张 wayfinder 地图。该喂给它什么？ 把主地图 issue 喂给它，即 /to-spec #<map_issue>，而不是一张张单独的决策工单。 wayfinder 产出的是散布在地图上的决策，不是可交付物。 to-spec 把它们收敛成一份能据以构建的文档。如果你把地图直接喂给 /implement，这一步就丢了。

    规格是给我评审的，还是只给智能体看的？ 主要是给智能体的，读起来也是那样：完整、密集、满是引用。接缝和超出范围这两节要读。在这两个地方，错误的决策现在抓住最便宜、以后发现最贵。确实有人抱怨通读太累，而且没有摘要模式。但如果规格让你吃惊，那是追问做得太浅，不是规格太长。

    工单开跑之后，规格要冻结，还是让智能体重写？ 没有任何东西让它保持同步。实践中它是一份“你当时知道什么”的快照，实现第一次教给你新东西时它就过时了。工作上线之后把它当一次性文件。你的 GLOSSARY.md 和 ADR 才是设计来长期保存的文件。实现过程中学到的、值得长期保留的东西，放那里，不要改规格。

    我做的是重构或模块边界，不是特性。模板合适吗？ 不太合适，这是已知局限。模板重度依赖用户故事，而用户故事不适合架构性工作。你最终会围绕那些其实关于接口和不变量的决策，写没人要的故事。改用 implementation-decisions 和 testing-decisions 两节。把需要长期保留的架构决策通过 grill-with-docs记录成 ADR，不要写进规格。

    它会检查追踪器上的相关工作吗，或者引用它遵守的 ADR 吗？ 都不会。它会读并遵循它所涉领域的 ADR，但不会链接它们。它动笔之前也不会在追踪器里搜重叠的 issue，所以规格可能跟别人已经报的工作重复，而没有任何东西提醒你。如果那个领域很热闹，先自己搜一遍追踪器。

    /to-tickets 读不了我的规格：一直被截断。 追踪器 issue 可能无法完整返回一份很大的规格，又没有本地副本可替代。要避免这一点，不要 清空（clearing） 或 压缩（compaction） 对话——在两者之间 /to-spec 和 /to-tickets。让它们跑在同一个窗口里， /to-tickets 就永远不必再取一遍规格。

    正常工作的标志

    • 它开始动笔，而不是对你开启新一轮提问。
    • 动笔之前先把接缝亮给你看，并且提议的接缝能少则少。
    • 它用你项目的名词，而不是泛泛的产品管理套话。
    • 里面每个决策你都记得是自己做的。它没有为了填满某一节而编造任何东西。
    • 超出范围一节列的是真东西。你拒绝过的那些，往往是整页最有用的几行。

    它的定位

    to-spec 是主构建链上的一步，但只在它的多会话分支上：

    grill-with-docs → to-spec → to-tickets → implement → code-review → retro

    上游， grill-with-docs 做决策，这个技能只负责记录；一张画完的 wayfinder 地图从这里汇入链条。下游， to-工单（ticket） 把规格切成曳光弹（tracer bullet）式的工单，交给 implement 去构建。拿不准哪个技能或流程合适时， ask-matt 给你指路。
