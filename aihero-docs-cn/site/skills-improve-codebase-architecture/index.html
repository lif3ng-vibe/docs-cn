    它做什么

    improve-codebase-architecture 对一个代码库进行勘察，寻找 加深（deepening）机会。这些地方是一个浅模块（接口的复杂度几乎不亚于它所隐藏之物）本可以变成深模块之处。它把发现写成一份自包含的 HTML 报告，然后 追问（grilling） 你，陪你把你选定的那一个过一遍。

    它从不改动代码。整趟运行只产出一场对话和你系统临时目录里的一个 HTML 文件。重构你稍后再做，在单独的 会话里、走正常构建流程完成。这让它是一次勘察，而不是重构工具，所以你可以对一个还没准备好动手的代码库运行它。

    两道过滤器防止报告沦为泛泛的清理建议。第一，每个候选都必须通过 删除测试（deletion test）：如果你删掉这个模块，它的复杂度是会退到更小的接口背后，还是散落到各调用方？只有前一种情况才配得上一张卡片。第二，除非你指定某个具体区域，它会先读最近的提交历史，把扫描聚焦在经常变动的路径上。没人碰的代码里的加深，是永远收不回本的重构。

    什么时候用它

    调用方式是输入 /improve-codebase-architecture； 智能体 不会自己主动调用它。

    它不是主构建循环中的一步。你周期性地运行它，为改进代码库排入更多工作。人们在四种情况下使用它：

    处境用法
    日常维护每隔几天、或有空闲时运行一次，免得结构在特性之间悄悄劣化。
    大型构建之前把它指向 规格（spec） ，问“我们怎样才能让这次变更变容易？”这是对它最有效的提示词。
    存量代码审计对一个庞大、无结构或 氛围编程（vibe coding）写出来的 仓库运行它，摸清它现在的形状。
    遗留测试工作在给不可测试的代码写测试之前，先用它找到缺失的接缝（seam）。

    它与同门技能容易混淆之处：

    • 要设计一个你已经选定的模块，用 codebase-design。这个技能负责找出该动手的模块，而 codebase-design 才是你设计它的地方。
    • 对于大到单个会话装不下的整场工程，用 wayfinder.
    • 对于“这个具体东西坏了”，用 diagnosing-bugs。当真正的结论是缺一条能锁死 bug 的好接缝时，它会把你送回这里。

    前置条件

    运行它没有任何前置条件。如果有 GLOSSARY.md ，或 docs/adr/ 里的 ADR 存在，它会读取它们，并使用你领域自己的名词。这样候选读起来就是“把 Order intake 模块加深”，而不是“重构 FooBarH和ler”。

    它写在两个地方。报告写到 <tmpdir>/architecture-review-<timestamp>.html（仓库之外）。在追问循环期间，它会往 GLOSSARY.md里添加或打磨术语，文件不存在就创建。它还会主动提出把被否决的候选记录成一份 ADR，免得以后的运行再次提出它。

    深度，以及追踪深度的报告

    这个技能建立在一个理念上： 深度（depth）。深模块把大量行为藏在一个小而稳定的接口背后。浅模块则通过一个几乎与其底层代码一样宽的接口暴露实现。报告寻找三种形式的浅：

    • 只为可测试性而抽出的纯函数，而真正的 bug 出在调用方如何使用它们（没有 局部性（locality）).
    • ）。把行为泄漏到自身 接缝（seam）之外的模块。.
    • 不打开五个文件就无法理解的概念。

    对每一种，它都提出能修复它的加深方案。

    每个候选是一张卡片，写明所涉文件、摩擦点、一份平实的解决方案、以 局部性（locality） 和 杠杆（leverage）衡量的收益、一张前后对比图，以及一个强度徽章。

    徽章对你的意义
    Strong删除测试干净利落地通过，摩擦也是真实的。认真对待这些。
    Worth exploring说得通的加深，但收益取决于代码接下来往哪走。
    Speculative为完整起见而收录。其中大多数你可以无视。

    报告以一个 首选推荐（Top recommendation）收尾——即它会最先动手的那个候选。然后技能停下来，问你想深入哪个候选。此时你什么都没决定，代码也没有任何改动。

    选定一个候选之后会发生什么

    当你选定一个候选，一场 追问 会话随之展开：涵盖约束条件、接缝背后放什么、哪些测试得以保留，以及加深后的接口该长什么样。那场会话的产出是一个决策，而不是一个 diff。从这里开始走正常流程：把决策交给 to-规格（spec），再到 to-工单，再到 implement.

    常见问题

    它就一个想法拷问了我一个小时，而不是给我看选项。能关掉吗？

    可以。调用时说明即可（“别拷问我，只给我报告”）。这是关于该技能最常见的抱怨。一位用户曾喜欢它是“获得彻底改进分析的便捷方式”，但在加入追问循环之后，觉得它“接近不可用”。在他们的会话里，它提出一个单一方案，然后问上“几十上百个问题”。设计意图是报告先行，追问只针对你选定的候选展开。但较弱的 模型 会直接跳到对其第一个想法的访谈。该话题下的效果因模型而异。这是一个未决 是sue，技能也还没有文档化的“免追问”模式。

    报告打开时是没有任何样式的原始 HTML，图也没有。怎么回事？

    报告从 CDN 加载 Tailwind 和 Mermaid，所以打开它需要网络。如果有东西拦下了这些脚本，页面会无报错地挂掉。在被报告的案例里，一个安全 hook 要求 SRI 哈希。智能体加上了哈希，但 CDN 给浏览器的字节与给 curl 的不同——而计算哈希的正是它——于是浏览器拦截了脚本。离线和锁死的环境有同样的问题。智能体看不见它，因为它从不渲染页面。变通办法是要求改用内联 CSS 和手绘 SVG 图，放弃 CDN 方案。这是一个未决 是sue。

    它给了我十二个候选。在同一个会话里逐个处理，还是新开一个？

    每个会话处理一个候选。如果你在一场对话里处理多个， 上下文窗口（context window） 会同时被报告、追问、领域模型编辑和代码改动塞满。报告只是个临时文件，所以要带走的是候选，不是文件。选一个，追问它，然后把决策交给 /to-spec。把其余的变成 工单 ，以后再单独拾起。选定的改进放进一份规格，而不是直接进入实现。这个问题常被问起，技能本身也没有为它文档化任何工作流。

    该怎么给它提示词？

    用你接下来要构建的东西给它提示词。如果一场大构建将至，把它指向规格并问“我们怎样才能让这次变更变容易？”不带提示词的运行会自己找热点。日常维护这样没问题，但给个方向能让报告变得可执行。

    在大型遗留代码库上好使吗？

    部分好使。它在缺一致结构的大型既有代码库上表现不错，也是任何一次性结构整治之后推荐的维护工具。但项目已经失控的用户报告它“有点帮助，但似乎还是不够”。一位手里有八年遗留代码库的开发者报告模型原地打转，尽管同一个技能在整洁仓库上能产出干净的图。目前还没有专门针对这种场景的 /refactor 技能。如果代码库没有共享词汇，先运行 grill-with-docs 来建立一个。这通常会让这个技能的产出好得多。

    它与 /codebase-design?

    /codebase-design 有何不同？它是参考资料，不是会话驱动器。它提供词汇（模块、接口、深度、接缝、适配器、杠杆、局部性），而这个技能使用这些词汇。如果你把 /codebase-design 当作任务丢给一个全新智能体，它会以一种已知的方式失败。它没有自己的流程可循，于是智能体自创一个，重新探索代码，跑上很长时间才问你任何问题。运行这个技能，让它去用那个技能。

    它会告诉我代码库没问题吗？

    很少，开始前先知道这一点。这个技能存在的意义就是输出发现，所以它倾向于产出候选，而不是得出“没问题”的结论。用强度徽章来校正这一点。如果报告里每个候选都是 Speculative，那就是技能一无所获。

    在 Codex 或其他 harness 里好使吗？

    部分好使。探索步骤点名了 Claude Code 的 Agent 工具并直接带上 subagent_type=Explore 参数。一个 harness 没有那个工具，可能会跳过并行探索，而不是用自己的等价物。技能仍会运行，但扫描没那么彻底。有人提议过一份 harness 中立的重写，但尚未合并。

    在 TypeScript 里到底怎么实现深模块？

    这个技能没有附带一个好答案。人们常想要一份 TYPESCRIPT.md （针对这些原则给出具体文件与模块布局的指南），但它并不存在。技能告诉你加深属于哪里、接缝背后该放什么。把它变成包或目录结构得靠你自己。

    正常工作的标志

    • 候选用你领域的概念命名，而不是生造的类名：“Order intake 模块”，而不是“FooBarH和ler”。
    • 候选位于你最近编辑过的文件里，而不是仓库里没人碰的角落。
    • 运行期间没有任何代码改动。唯一的新文件是临时目录里的 HTML 报告。
    • 报告之后它会停下，问你要哪个候选。它不会自顾自继续。
    • 每张卡片把收益解释为局部性或杠杆，并说明哪些测试会变简单，而不只是“这样更干净”。
    • 当你以一个持久理由否决某个候选时，它会主动提出记一份 ADR，下次运行不再提出。

    它的定位

    improve-codebase-architecture 是 周期性维护。每隔几天运行一次，在任何链条之外，用于把工作排进队列，而不是执行工作。它的邻居们：

    • codebase-design 掌握每个候选都要用到的深度与接缝词汇。
    • 追问 在你选定一个候选后带你走决策树。
    • domain-modeling 在你做决策的同时让 GLOSSARY.md 和各份 ADR 保持最新。

    它的产出是一个想法，回流到主构建流程的 grill-with-docs 或 to-规格（spec）处。主流程末端的对应物是 retro。这个技能改进智能体工作的代码，而 retro 则在构建之后改进它周围的环境（检查、标准、引导文件）。至于什么处境该配哪个技能， ask-matt 是横跨全套技能的路由器。
