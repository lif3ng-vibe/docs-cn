    人们对 /grill-me 和 /grill-with-docs 的 9 个常见误解

    掌握使用 /grill-me 或 /grill-with-docs 时最常见的 9 个错误。学习范围管理、模型选择与规划策略。

    Matt Pocock

    这款 /grill-with-docs 技能已成为 计划模式（plan mode） 在智能体工作流中的热门替代品。然而，很多人难以有效使用它。这个技能的原理是不停地向你提问，直到你们达成共识，但 这需要你自己具备良好的规划能力.

    这些技能不是要取代工程师——它们的设计目的是辅助你。本指南的目标是帮你理解九种最常见的失败模式，从而驾驭它们。

    理解问题：低保真 vs 高保真

    当你进入一场 追问（grilling） 会话，你的目标是回答关于你要构建之物的问题。但问题与问题并不平等。

    问题类型定义示例可追问？
    低保真不需要详细原型或图片就能回答的问题"这个路由该挂在哪个 URL？"✓ 是
    高保真需要放大细看的图片或原型才能回答的问题"用起来时这个 UI 该是什么感觉？"✗ 否

    表单字段布局是高保真问题的典型例子。把表单字段拆到多个页面，还是用一个巨大的表单？要恰当回答，你真的需要看到原型或把整个东西做出来。

    处理不可追问的问题

    第一个主要失败模式：在追问会话里试图回答高保真问题。

    当你碰到一个不可追问的问题——需要更高保真度才能理解的东西——使用 交接（handoff） 模式：

    1. 在第一个会话（蓝色会话）里继续追问低保真问题
    2. 碰到高保真问题时，交接给一个原型会话
    3. 在那个独立会话里构建或做原型，以更好地理解问题
    4. 交回原来的追问会话，继续处理可追问的问题

    这个模式长这样： 追问 → 原型 → 再追问。它让你能回答高保真问题，又不打断追问的心流。

    选对范围

    范围——你在追问的东西有多大——绝对关键。

    如果范围太大，会出现两个问题：

    问题 1：隐藏的高保真问题 在你确知可行的东西之上构建，总比没完没了地向未来规划容易。当人们试图给 AI 排上好几天的任务时，结果往往很差，因为他们不是建立在自己理解的坚实基础上。

    问题 2：上下文窗口限制 你可能以近乎空的 上下文窗口（context window）起步，但随着你不停追问，你会撞上模型的"愚钝区"——对大多数最先进模型来说大约在 120k token。一旦越过这个阈值，模型的注意力关系开始紧绷，决策质量开始下滑。

    拆解大范围

    别在一个巨大的范围上追问，让智能体提前把它拆开：

    1. 从一个大范围开始
    2. 让智能体把它拆成更小、可追问的块
    3. 在每个较小范围上分别追问
    4. 在这些独立会话里回答完所有问题

    这让你安稳待在"聪明区"里，避免在会话中途撞上上下文窗口的墙。

    主动，而非被动

    许多漫长的追问会话之所以失败，是因为人们对智能体太过被动。记住： 这是一场对话，不是一场访谈.

    智能体提问，但 你 需要：

    • 想清楚你要去哪
    • 理解范围
    • 让事情保持在正轨上
    • 主动引导对话

    如果你太被动，智能体会用 540 个问题轰炸你，并用那些保真度过低的需求把范围炸开。

    但要有个平衡。太过主动意味着在低保真细节上无休止追问，而你其实该去写代码了。如果只是一直规划一直规划而不构建，你就是在过度追问。

    找到中间地带：积极参与引导会话，同时知道何时该停止规划、开始实现。

    保住你的设计决策

    这是一个关键却常被忽视的失败模式。追问时，你创造了一个极其宝贵的产物： 一个装满设计决策的上下文窗口.

    等你追问完，你已经做出了价值几百 token 的、关于系统该如何工作的选择。这是纯金。

    你的选项：

    • 如果还有上下文预算：直接在同一个会话里实现，不做交接
    • 如果上下文快用完了：用 /2PRD 技能创建一份 PRD（产品需求文档）作为交接产物

    千万别 为了写一份 PRD 就清空上下文、从头再来。那是在扔掉你全部的设计工作。追问会话中的每一个决策都有价值，要么变成代码，要么写进交接产物存档。

    用聪明的模型来追问

    用"笨"模型做追问是常见错误。为什么这很重要：

    追问时，你依赖两种知识来源：

    知识类型来源可靠性何时重要
    上下文知识你传入的文件、提示词、工具结果非常可靠实现阶段
    参数化知识模型的训练数据与参数可靠性较低，但有创造性追问阶段

    追问时，你依赖的是模型的 参数化知识（parametric knowledge） ——它对系统和应用的内在理解——来提出你可能没想到的东西。如果你想到了，早就作为上下文传进去了。

    笨模型给不出好点子。 你需要一个参数量大的模型——通常是大型前沿模型——才能得到有创意的建议和发人深省的问题。

    不过，实现阶段可以用更小的模型，因为那里的信息大多是上下文知识（你的详细计划、代码库等）。

    并行跑多个追问会话

    最后，一个简单而有力的技巧： 并行追问多个会话.

    具体这样操作：

    1. 你在会话 A 里追问
    2. 智能体问你一个问题
    3. 你回答它
    4. 趁智能体思考时，切到会话 B
    5. 在那里回答问题
    6. 会话 A 就绪，切回来
    7. 重复

    这就像同时打理两个 Slack 会话串。你其实并没有重度切换上下文——你只是在管理几场独立的对话。

    好处：

    • 你的吞吐量翻倍
    • 更少时间完成更多规划
    • 多条设计决策同时推进

    大多数人舒服的上限是两个会话。如果一个会话在跑调研这类长任务，你可能应付得来三个。追问水平提高后，可以加大并行度。

    刚接触追问工作流？从 /grill-with-docs 开始——动手前先在文档上对齐。

    要点回顾

    • 追问的核心是问题。 低保真问题可追问；高保真问题需要做原型
    • 范围很重要。 选择更小的范围，避免撑爆上下文窗口
    • 保持主动。 引导对话，同时知道何时停止规划、开始写代码
    • 留住价值。 追问中做出的每个决策都应记录在某个地方
    • 用聪明的模型。 你需要参数化知识才能得到有创意的建议
    • 并行运行。 理解了每个会话各自在做什么之后，就能在它们之间高效切换

    你对这些失败模式理解得越好，就越能有效地用追问会话在编码之前完成设计。
