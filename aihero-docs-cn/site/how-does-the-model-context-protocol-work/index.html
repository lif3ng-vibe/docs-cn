    Model Context Protocol 是如何工作的？

    了解 Model Context Protocol（MCP）的工作原理：它如何通过流畅的客户端-服务器通信与 JSON-RPC 2.0 协议连接宿主与服务器。

    Matt Pocock

    现在我们已经大致了解 MCP 的用途和它有趣的地方，接下来真正看看它是如何工作的。

    要理解它的工作原理，我们得先看懂 Anthropic 发布的一张图，它展示了 MCP 的架构：

    我们来逐步解释这张图。

    MCP 宿主与客户端

    MCP 宿主（host）是访问 MCP 服务器的程序。它可能是 Claude Desktop, Cursor, Windsurf或任何其他支持 MCP 的应用。

    这个宿主大概率会使用某种 LLM。该 LLM 将能够调用 MCP 服务器中定义的工具。

    在这个宿主上，你会运行多个客户端——每个客户端都与单个 MCP 服务器保持连接。当宿主启动时（也就是你启动 Cursor 时），每个客户端都会连接到一个 MCP 服务器。

    所以，你可以用一个宿主带多个客户端，每个客户端与不同的服务器交互。

    你也可以构建自己的客户端——我们可能会在以后的视频里讲到。现在可以先看看 MCP 的文档.

    MCP 服务器

    MCP 服务器是运行宿主想要调用的工具的服务器。

    这个服务器可以在本地运行，也可以在远程服务器上运行。

    需要注意的一点是，服务器可以使用与宿主完全不同的语言。就像一个应用的前端和后端可以用不同语言编写一样，宿主和服务器也可以如此。

    传输层与协议

    客户端通过传输层（transport）连接到它的服务器。传输层负责在客户端和服务器之间传递消息。

    目前支持两种传输层。你可以通过 stdio 通信，也就是通过终端。或者通过 HTTP 与 server-sent events（服务器推送事件）通信。如果你想在远程机器上运行服务器，后者会很有用。稍后我们会介绍这两种方式。

    那么，通过这个传输层传递的消息究竟长什么样呢？这就要说到协议了。

    它是客户端和服务器可以互相发送的一组 JSON 结构，基于 JSON-RPC 2.0。它们看起来像这样：

    type Request = {

      jsonrpc: "2.0";

      id: number | string;

      method: string;

      params?: object;

    };

    

    type Response = {

      jsonrpc: "2.0";

      id: number | string;

      result?: object;

      error?: {

        code: number;

        message: string;

        data?: unknown;

      };

    };

    请求包含 method （服务器应执行的方法），以及 params （应传给该方法的参数）。

    响应包含 result （方法成功时），或者 error （失败时）。

    两者都有一个 id ，用于把请求和响应配对；还有一个 jsonrpc 字段，用来记录底层 jsonrpc 协议的版本。

    一次通信示例

    为了加深理解，我们来看一个例子。假设我们有一个名为 createGitHubIssue 的工具，它会在 GitHub 上创建工单（issue）。

    我们会跳过一些前置步骤——MCP 客户端初始化连接——直接从客户端向服务器发送请求开始。

    1. 列出工具

    // Client sends...

    {

      "jsonrpc": "2.0",

      "id": 1,

      "method": "tools/list"

    }

    这是一个列出服务器上所有可用工具的请求。服务器会返回一个工具列表：

    // ...server sends back:

    {

      "jsonrpc": "2.0",

      "id": 1,

      "tools": [

        {

          "name": "createGitHubIssue",

          "description": "Create a GitHub issue",

          "inputSchema": {

            "type": "object",

            "properties": {

              "title": { "type": "string" },

              "body": { "type": "string" },

              "labels": {

                "type": "array",

                "items": { "type": "string" }

              }

            }

          }

        }

      ]

    }

    注意服务器是如何返回工具的名称、描述以及该工具所需输入的。输入是一个 JSON schema，描述了 title、body 和 labels。

    2. 调用工具

    客户端决定调用该工具，并发送请求：

    // Client sends...

    {

      "jsonrpc": "2.0",

      "id": 2,

      "method": "tools/call",

      "params": {

        "name": "createGitHubIssue",

        "arguments": {

          "title": "My Issue",

          "body": "This is the body of my issue",

          "labels": ["bug"]

        }

      }

    }

    这里描述了 name （要调用的工具名称），以及应传给它的 arguments （参数）。

    服务器返回工具的执行结果：

    // ...server sends back:

    {

      "jsonrpc": "2.0",

      "id": 2,

      "content": [

        {

          "type": "text",

          "text": "Issue 143 created successfully!"

        }

      ],

      "isError": false

    }

    它返回一个内容部分（content parts）数组。这些内容部分可以是 text ——如上例所示——也可以是 image （用于图片）和 resource （用于二进制数据）。它还会返回一个可选的 isError 标志。

    如果 工具调用 出错了，返回的对象会稍有不同：

    // ...if error, server sends back:

    {

      "jsonrpc": "2.0",

      "id": 2,

      "content": [

        {

          "type": "text",

          "text": "Error creating issue: Unauthorized"

        }

      ],

      "isError": true

    }

    这告诉客户端：该工具调用没有成功。

    结语

    这就是 MCP 工作方式的基本结构：一个宿主运行多个客户端，客户端连接到服务器，客户端和服务器通过传输层和协议进行通信。
