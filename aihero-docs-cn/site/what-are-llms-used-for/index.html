    LLM 能用来做什么？

    了解何时该用 LLM 处理结构化、分类等数据任务，何时又该选择确定性系统。

    Matt Pocock

    在深入 LLM 的世界、探究它们如何工作之前，我们首先要知道要去往哪里。

    如今 LLM 到底被用来做什么？它们有什么用处？你能用它们构建什么？

    在这篇文章中，我们会探索 LLM 的各种应用。我们也会看看哪些东西不该用 LLM 来构建——那些更适合确定性工具的事情。

    适合用 LLM 的场景……

    非结构化数据 -> 结构化数据

    大多数公司都掌握着大量非结构化数据。它们可能是客服通话记录、客户邮件、发票，甚至只是会议笔记。

    这些数据很难处理：难以搜索、难以分析，也难以阅读。

    举个例子，我的一位朋友开始读博，研究历史上鹰的迁徙模式。这些鹰如何移动的数据，记录在 19 世纪古老且非结构化的日志里。尽管这些日志被仔细归档并数字化，通读它们仍是极其耗时的任务。

    解决方案？用 LLM 把这些日志转换成表格数据。LLM 可以读取日志、理解其中的模式，并把它们转换成结构化格式。这种结构化格式随后便可用于分析、可视化和进一步研究。

    这也许是 LLM 最常见、最强大的用例。过去几十年，世界积累了海量数据。LLM 正在让这些数据变得可检索、可获取。

    这是一个共同主题——LLM 常被用于那些雇人来干并不现实（或成本太高）的数据任务。这为处理以往无法触及的数据打开了新的可能。

    标注与分类

    LLM 的另一项常见任务是分类。可以给它们一个输入，让其为它打上标签，这有助于更有效地组织和理解数据。

    一个引人注目的例子来自 《The Prompt Report》。在他们的案例研究中，他们试图检测“可能自杀个体所写文本中预示危机级自杀风险的信号”。他们使用了 r/SuicideWatch 这个 subreddit 的数据，而 LLM 必须与专家的分析相匹配。

    在给定文本时，LLM 需要判断其中是否包含“狂乱的绝望”（frantic hopelessness）或“被困”（entrapment）的成分。它会回复“positive”（即文本包含风险信号）或“negative”。

    分类系统在机器学习里由来已久。它们通常需要大量数据来训练。LLM 让这个过程变简单了：只需一个简单的提示词，就能让它的行为变成一个分类器。非常有用。

    LLM 的近期进展也意味着，从它们那里获取结构化数据变得更容易了。可以看看 这个分类示例 ，它来自 Vercel AI SDK 教程。

    问答

    LLM 的另一个常见用例是充当问答机。你可以给 LLM 一个问题，它会基于自己的训练数据给你一个回答。

    然而，把 LLM 当知识库用有几个缺点。它们的训练数据有时间截止点，因此拿不到最新信息。它们的回答常常无法注明来源，这让人难以核实其准确性。

    因此，把 LLM 连接到外部数据源是一种常见模式。

    这个外部数据源可以是数据库、搜索引擎或任何 API。LLM 可以调用外部服务（借助 工具（tools））来获取最新的信息。

    这并非万无一失——需要细致的工作来确保 LLM 不产生幻觉、不提供错误信息。但以聊天机器人或搜索引擎形式存在的问答服务，是 LLM 的一个常见用例。

    DeepResearch——如今 Perplexity、Google、OpenAI 等家都提供的常见产品——就是一个很好的例子。它是一种从一条简单查询生成整篇学术风格报告的模式。

    智能体

    LLM 能够访问外部工具，这让很多人非常兴奋。这意味着 LLM 可以用来在这个世界上 做事情 ，而不只是生成文本。

    这种模式常被称为“智能体（agent）”——一个能在世界上采取行动、响应用户输入、并与其他系统交互的系统。

    可以想象一个编码智能体像团队成员一样——可以通过 Slack 联系，能写代码、部署到生产环境，并与用户沟通。

    这与诸如 Devin.

    然而，智能体还没有迎来自己的爆发时刻——至少不像聊天机器人那样。在用户体验方面，智能体尚未找到自己的最终形态。

    不适合用 LLM 的场景……

    朴素的聊天机器人

    用 LLM 搭聊天机器人看起来非常诱人。搭建起来很简单：给 LLM 一条提示词，让它能访问对话历史，就可以开张了。

    “与我们的文档对话。”“与我们的支持机器人对话。”“与你的搜索结果对话。”朴素的聊天机器人只是套在 LLM 外面的一层薄壳，仓促拼凑起来，好让产品显得更有互动性。

    然而，把聊天机器人推向生产环境是个极其困难的问题。一不小心，它们就会惹恼用户、损害你的品牌。让聊天机器人只回应相关问题而不跑题，是出了名的难。

    大型模型提供商（OpenAI、Anthropic、Google 等）都内置了护栏（guardrail），防止模型说出有损品牌的话。但可能发生的对话面实在太广——你能想到的任何对话——这些护栏恐怕永远不会完美。一个著名的例子是 Google 的 Gemini 让用户去死。

    只需要一个执着的用户，就能越狱你的聊天机器人，让它说出不当言论。没有妥当的防护措施，别上线聊天机器人。

    确定性系统

    AI 系统的一条好经验法则是：“能用确定性方式构建的，就应该用确定性方式构建。”

    LLM 是概率性系统。它们的设计目标是从许多可能的选项中，一遍又一遍地为一段文本选出下一个词。根据下一个词的选取方式（即它们的“采样策略”），同一个输入可能产生不同的输出。

    然而，这种设计也让它们容易出现几种失败模式：

    • 幻觉（hallucination）：生成没有现实依据的文本
    • 谄媚（sycophancy）：过度迎合用户的观点，而不是提供平衡的回答

    这些失败模式可以设法绕开，但需要精心的设计与测试。这就是说：如果能用确定性方式构建系统，就应该这么做。

    确定性系统在测试、调试和维护上要容易得多。它们上线生产更安全，运行通常也更快、更便宜。

    结语

    确定性系统不会消失。它们在构建、测试和维护上比 AI 应用容易无数倍。在这个人人拿 LLM 砸向每个问题的时代，能够嗅出 何时不该用它 是一项宝贵的技能。

    对任何任务，确定性系统都应该是你的默认选择，直到你撞上一道只能靠 LLM 解决的障碍。

    但 LLM 确有一席之地。我们把到目前为止看到的 LLM 用例分成两类。

    第一类是 雇人来干成本高得离谱的任务:

    • 把非结构化数据转换成结构化数据
    • 标注与分类

    第二类是 对确定性系统来说过于复杂的任务:

    • 问答
    • 文本生成
    • 智能体

    所以，落入这两类的任何任务，都是 LLM 的良好候选。
