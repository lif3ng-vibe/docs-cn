    它做什么

    grilling 是这样一套访谈循环：在任何人动手之前，对一份计划、一个决策或一个想法做压力测试。它把话题绘制成一棵 设计树（design tree）：每个决策都分叉出挂在它下面的决策，然后逐个分支访谈你，直到没有任何假设处于未言明状态。

    它不会一次只问一个问题，也不会一口气把所有问题全抛出来。每一 轮（round） 会问整条 前沿（frontier）：即前置条件都已敲定的全部决策，仅此而已。两个问题只要其中一个依赖另一个，就绝不会同轮出现；一个还悬在未决答案上的问题，属于更晚的轮次。你的回答敲定决策，前沿向外推进，下一轮问的正是因此解锁的问题。十三个问题通常落在约三轮里，而不是十三轮。

    何时使用

    输入 /grilling，或者 智能体 会在任务匹配时自己调用它。它是唯一一款 技能 属于 grilling 家族、由模型调用的，所以你很少亲手输入它。通常是一个你 确实 输入过的技能替你运行它。

    直接输入 /grilling 得到的是纯粹访谈，别无其他。当你想要更多时：

    你手头的情况该用什么
    你不在一个工作目录里grill-me：同一场 会话，只是换了一个智能体绝不会自己触发的名字
    你在一个工作目录里grill-with-docs：同一场会话，而且它会沿途写入 GLOSSARY.md 和 ADR。
    工作量大于一个会话的容量wayfinder：它绘制一张地图，并在决策工单内部运行追问
    一个靠谈话谈不定的问题：某样东西该长什么样、该是什么感觉prototype：把一次性版本搭出来，然后带着答案回来
    你自己的某个技能需要一场访谈从中调用 /grilling ，而不是再写一场新访谈

    轮次、前沿，以及谁说了算

    这项技能建立在三个概念之上。

    所谓 设计树（design tree） 就是话题的模型：决策之下挂着决策。而 前沿（frontier） 则是所有前置条件均已敲定的决策集合：也是智能体此刻唯一能问的问题。一场 轮（round） 就是一整条前沿，问得完整，答得也完整。

    在一轮之内，每个问题都有固定格式：编号和标题放在 ❓后面，然后是正文，然后智能体的推荐答案单独放在 ➡️ 开头的行里。这种格式让你可以按编号回答一整轮（“1 同意，2 第二个选项，3 不同意，理由如下”），而不用把问题引述回来。这个格式有一个已知问题。推荐答案有时会 反驳 问题本身的措辞，所以同意推荐答案等于对问题回答“不”。出现这种情况时，就回答推荐答案，并说明这一点。

    这套设计的另一半是事实与决策的分工。事实归技能自己管。当一个前沿问题需要 环境 才能敲定的东西时，智能体会派一个 子智能体 去查明，而不是来问你。这一轮不会等那项调研；只有依赖它的问题才等。决策归你，智能体必须等你。一个运行 grilling 却自己回答自己决策的智能体，已经破坏了这项技能。前沿清空时会话就结束。智能体随后会等你确认理解已经共享，然后才对谈定的内容采取行动。

    前沿有一个局限。智能体凭判断选出前沿，而不是从图里算出来。所以它可能把两个问题放进同一轮，事后才发现其中一个答案本该改变另一个。唯一的防线是告诉它。这会在下一轮重新打开受影响的分支。

    常见问题

    我能改回一次只问一个问题吗？ 可以，而且很大一部分用户就是这么做的。把下面这句加进你的全局 CLAUDE.md:

    When grilling, ask one question at a time.

    并非所有人都偏好按轮提问的默认方式。阅读慢、使用第二语言工作、或靠顺序格式帮助专注的用户反馈，一次一个问题对他们更有效。这个退出选项是受支持的设置，不是变通手段。

    原来的 /batch-grill-me 去哪了？ 并入了这个技能。按轮提问曾短暂作为独立技能发布，随后移进了 grilling 本体，所以所有构建在该原语之上的技能（grill-me, grill-with-docs, triage, wayfinder）都一并获得了它。没有 batch-grill-me 可装，也没有单独的顺序提问技能； CLAUDE.md 那一行就是改回一次一个问题的办法。

    一口气问一整轮，肯定会漏掉我前面的回答本会引出的问题。不是吗？ 这是对轮次最常见的反对意见，而前沿正好回答了它。一轮只包含互不依赖的问题，所以一轮中的任何答案都不可能让该轮的另一个问题失效。你的回答仍会改变其后的一切，因为智能体每一轮都从头推算。你确实有所损失，但没有“全部问题一次问完”暗示的那么多。见上文前沿的局限。

    它问完问题就开始动手构建了。 确认关卡就是为这个准备的。你说理解已经共享，技能才算完成，而不是前沿清空就算完成。更弱更快的 模型 仍然会跳过这道关卡。用户报告这种情况最常出现在低用力度或非前沿模型上，它们把“访谈到共享理解为止”塌缩成几个问题加一份提纲。如果你的模型也这样，可靠的修法是在你自己的 AGENTS.md 或 CLAUDE.md 里加一句：未经许可不得开始实现。

    它自己回答了自己的问题，而不是来问我。 这是运行中的缺陷，也正是技能文本要把事实与决策分开的原因。最常发生的情况是另一个技能运行 grilling 来解决一张工单，而智能体把那个任务当成了继续推进的许可。同样的约束也是没有异步模式的原因。有人要求一个变体：读一个 GitHub issue 并发布一份汇总的决策备忘录——那是另一个技能，因为一场无人回答的追问会话产出的是智能体的意见，而不是你的。

    我能给问题数设上限吗？ 不能，而且设上限是被有意排除在外的。有的计划三个问题就够，有的要五十个；固定上限要么砍掉难的情形，要么在简单的情形里显得武断。预期的控制手段是平实的语言。让它收尾，或者停下来、就地接受当前的计划。如果一场会话跑得特别长，原因通常是范围太大；把工作拆开，逐块追问。

    我单独安装了 grill-me ，但什么也没发生。 grill-me 是一个单行技能，正文全部内容就是“运行一场 /grilling 会话”，所以它也需要把这个技能装上。对 grill-with-docs也一样，它额外还需要 domain-modeling。安装整套技能可以避开这个问题；选择性安装就意味着要把原语也一并装上。

    grill-with-docs 跑了，但它从未加载 grilling. 这是一个真实缺陷，仍未修复，用户在不同 harness（框架） 和模型上都有报告。一个技能点名另一个技能，并不能可靠地让那个技能加载，而 grill-with-docs 点了两个名。迹象是：会话一口气把所有问题问完，没有任何推荐答案。这说明模型在即兴发挥一场访谈，而不是运行这一场。直接问智能体它是否加载了 grilling 和 domain-modeling 通常就能恢复。

    生效判据

    • 一轮以编号列表的形式到来，每个问题的推荐答案单独放在一行 ➡️ 里，而且你可以按编号回答一整轮。
    • 一轮之中，没有任何问题需要先回答同轮的另一个问题。
    • 后面的轮次会问第一轮问不了的东西。
    • 它会自己去查事实（读文件、派子智能体），而不是把查得到的东西拿来问你。
    • 后台运行的调研不会卡住这一轮；只有依赖它的问题才等待。
    • 它最后会停下来请你确认理解已经共享，而不是直接开工。
    • 问题数保持很高，轮数保持很低。

    适用位置

    grilling 是一个 原语（primitive），不是你日程表上的一个步骤：它是访谈技巧的唯一权威出处，集中放在一处，让每个需要访谈的技能都来取用它，而不是各自发明一场访谈。 grill-me 和 grill-with-docs 是它的两个由用户调用的大门，而 grill-with-docs 是主构建链条的起点，位于 to-spec. wayfinder 运行它来解决决策工单， triage 用它把一份模糊的报告追问成可执行的一份，而 improve-codebase-architecture 则在你选定一个加深（deepening）候选后带你走一遍设计树。当你拿不准哪个入口合适时， ask-matt 会为你指路。
