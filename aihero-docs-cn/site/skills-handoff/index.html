    /h和off 技能

    把一场长会话写成文档，让另一个智能体能接着干。

    Matt Pocock
    源码下一页

    安装此技能

    $npx skills@latest add mattpocock/skills --skill=handoff

    然后输入 /handoff 于你的编码智能体中。

    它做什么

    handoff 把你所在的对话压缩成一份 交接文档（h和off document）：一个 markdown 文件，写进操作系统的临时目录而不是工作区，一个全新的 智能体 读它就能接手工作。

    它给你的是 可移植性（portability），而不是压缩，所以这项技能比听起来要窄。只有当工作需要 移动时你才需要一个文件：移到新的 harness（框架）、新的目录、同事那里，或一个你想分叉出去的支线任务。什么都不移动时，你不需要交接。留在 会话, /clear、一个 子智能体 和 /compact 就能覆盖常规的阶段收尾场景，而 /compact 覆盖它的次数比这项技能更多。

    何时使用

    使用方式是输入 /handoff；智能体不会自己主动调用它。附上一句说明下一个会话是干什么用的，技能就会为那个目的撰写文档。

    触发场景有四个，也只有四个：

    情境为什么需要文件
    更换 harness（框架）（Claude → Codex）新 harness（框架） 看不见旧的 上下文
    搬到另一个目录或仓库原型目录是最常见的情形
    把工作发给同事他们需要读得懂的东西
    把阶段中途发现的支线任务分叉出去你继续干活；第二个智能体接下分叉

    其他一切情况（同一个 harness（框架）、同一个目录、你已经完成 追问（grilling） 、正要转入实现），用 /compact. ask-matt 手里有那棵给阶段边界上全部五个选项排序的树。

    分叉才是人们跳过的用法

    这项技能的描述读起来像会话恢复：写一份总结，在这里结束，在那里继续。照那样读，它就像一个更差的 /compact，所以人们跳过它。分叉场景才是值得记住的用法。你 留在自己的会话里 ，把积累起来的上下文复制一份，交给一个并行工作的第二个智能体。

    绕道 prototype 用的就是这一招。你正深陷一场设计对话，撞上一个只有跑代码才能敲定的问题，而你不想把辛苦攒下的线程花在查明它上。交接给一个原型会话，拿到答案，把答案递回来，再从原线程引用它。工作跨越两次，你的原始对话保持活跃，而且什么都不用重新解释。

    阶段边界上五个选项中的三个，各自保全的东西不同： /compact 保全你的意图， /clear 什么也不保全， /handoff 保全的是工作移动的能力。

    什么跟着走，什么不跟

    文档携带活跃线程（正在进行什么、为什么、接下来是什么），外加一节 建议技能（suggested skills） ，点名下一个智能体该取用哪些技能。技能在写文件之前会先隐去机密信息。

    它有意不携带任何已经写下来的东西。文档用路径或 URL 引用规格、计划、ADR、issue、提交与 diff，从不复制它们。这让文件保持小巧，也让敲定的细节只留在一个地方，而不是两份渐行渐远的副本。

    常见问题

    交接还是压缩？ /compact ，除非有东西要移动。留在同一个任务上是压缩，不是交接。当 harness（框架） 和目录都没变、而你又要留在决策圈内时，阶段边界的那棵树大多数时候终点是 /compact ，大多数时候如此。 /handoff 并不更会总结。它的优势在于结果是一个文件，你能把它带去 /compact 到不了的地方。

    那 compact、clear 和 h和off 的实际区别到底是什么？ 三者各自保全的东西不同。 /compact 压缩当前这份上下文，在一个全新窗口里继续，所以你的意图得以延续。 /clear 清空窗口，从零开始。当你身后的一切都可弃之时，这是正确选择；如果不是，你无法撤销它。 /handoff 写一个可携带的文件，让工作在搬到别处后依然存活。三者都会把一份 一手来源（primary source） （对话的原本样貌）变成一份 二手来源（secondary source） （它的摘要）。继续不换窗是唯一不这么做的选项，所以你先把它排除。

    我的交接文件去哪了？ 它去了临时目录，这是该技能被报告最多的问题。技能把它解析为 $TMPDIR，否则 /tmp (%TEMP% 是 Windows 上的写法），但路径很长。继续下一步之前，先要回路径并保存好。用临时目录是有意的，因为交接是一份在途文档，不是你要长期维护的产物。临时目录也不持久，下一个问题会解释。

    我的交接文件在两次会话之间消失了。 有些环境会在会话之间清空临时目录（被报告的是 Codex），重启也会清空 /private/tmp。如果下一个会话不会在一小时内启动，或者要在不同的 harness（框架） 下启动，请在文件一写完就亲自把它复制到耐存的地方。文档所 指向的东西同理：如果交接里引用了临时目录中的其他文件，下一个智能体就找不到了。

    我到底该怎么把它交给下一个智能体？ 开一个全新会话，把路径指给它：读这个文件，然后继续。要指向文件，而不是把摘要粘进 shell 命令。摘要里含有反引号或 $(...) 时，它会被 shell 搅坏 claude "<summary>"。常见结果是无声截断而非报错，于是新智能体拿着一份不完整的任务简报开工，而没有任何东西提醒你。

    这和 /branch, --fork-session，或内置的 /handoff? 它们相似，但不相同。 /branch 在这里并不是随集发布的技能； /handoff 才是正式名称。分叉继承上下文的精确副本；这项技能产出的是一次 有针对性 的压缩，瞄准一个言明的下一步任务，落在一份文件里。分叉够用的场合（同一台机器、同一个 harness（框架）、同一个目录），分叉更省事。当目的地是分叉到不了的地方，文件是更好的选择。

    什么东西该放进 CLAUDE.md 而不是交接文档？ 问自己：它下个月还成立吗。 CLAUDE.md 是关于项目的常驻上下文，无论相不相关都会载入每个会话。交接关于一件在途的工作，一旦那件工作落地就没用了。如果你在不断重复解释同一个事实，它属于 CLAUDE.md。一个做到一半的任务属于交接。

    它记下了是什么，却没记下为什么。 这是个中肯的批评，人们经常提起。两件事有帮助。附上用途说明（告诉它下一个会话是干什么的），这样技能保留的就是与 那件事 相关的推理，而不是把它压平。另外，警惕会话从未验证过的自信断言，比如“X 还没建”或“Y 已经完成”。下一个智能体会信任文档、不去复核，于是一个被写成事实的猜测，就成了后续一切的错误前提。交接之前先读一遍文档，把仅凭假设的东西降级处理。

    它为什么是技能而不是斜杠命令？ 两种都行，只是适用情境不同。作为技能，它和这里的其他东西走同一条安装与更新通道，因此可以分享。阻止智能体自行触发它的是它的 frontmatter，而不是机制本身。

    生效判据

    • 文档只占对话的一小部分，规格、issue 和 diff 以路径和 URL 的形式出现在其中，而不是被复制的文本。
    • 不用打开原始会话，冷读这份文档也知道下一步做什么。
    • 全新的智能体直接开工，而不是要你重新解释一遍 setup。
    • 在分叉场景里，你回来时原始会话分毫未变。
    • 建议技能一节点名的，正是你自己也会伸手去拿的那个技能。
    • 里面没有任何密钥、token 或密码。

    适用位置

    handoff 是一个 随时可取用的独立技能。它在会话之间工作，而不是构建链条内部。它是个窄工具，你会比阶段边界上的其他四个选项更少用到它。与它关系最近的是 prototype，因为原型住在自己的目录里，出去再回来的这一趟正是这项技能服务的动作。当你站在边界上，拿不准该继续、清空、交接、委派还是压缩时， ask-matt 手里有给这五个排序的树，并能把你路由到技能集的其余部分。
