    AI 工程师思维

    学习如何通过定义清晰的成功指标、建立数据驱动的持续改进文化，构建成功的 LLM 应用。

    Matt Pocock

    用 LLM 做开发，需要你对软件开发的基本认知来一次转变。你不再设计输入映射到可预测输出的确定性系统，而是在与本质上不可预测的概率性系统打交道。要交付一款出色的应用，你需要清晰地定义成功标准，并基于真实用户数据建立持续改进的文化。

    把 LLM 应用推向生产环境很难

    把一个 demo 跑起来相对简单，但把 LLM 应用推向生产环境就是另一回事了：

    这段旅程始于我所说的“只凭感觉谷”（Vibes-Only Trough）。你的应用已经能和 LLM 配合工作，用几个例子测过，似乎表现符合预期。但一旦放到真实用户面前，他们会以你从未想过的方式使用它。自然语言的灵活性意味着用户能把你的系统推到远超预期用例的地步，暴露出你无法预料的边界情况与失败模式。

    这正是系统化评测登场的地方。沿着“数据驱动坡”（Data-Driven Slope）向上走，你会建立正式的评测框架、收集数据、度量性能。你不再凭感觉，而是在用数据驱动关于应用性能的决策。

    但这条路不会一帆风顺。你做实验时，应用质量会剧烈波动。有些改动让事情变好，有些则更糟。

    别慌——这种波动本就是游戏的一部分。诀窍在于系统化地追踪这些变化，并从每一次迭代中学习。这也是我们需要一种新开发方法的原因：它拥抱 LLM 的概率本质，同时保持严谨的评测实践。

    定义你的成功标准

    管理这种概率本质的第一步，是定义你的应用怎样才算成功。在传统软件里，成功标准往往一目了然——登录系统要么能用要么不能。但对 LLM 应用来说，成功很少是非黑即白的。

    假设你在构建一个给客户评论分类的情感分析系统。“成功”是什么样子？你需要与你的应用目标相符的具体、可度量的标准：

    • 准确率：在多个行业中与人类专家情感标签达成 92% 的一致
    • 响应时间：95% 的分类在 500ms 内完成
    • 置信度评分：90% 的高置信度预测（>0.9）应与人类判断一致

    关键是让这些标准具体、可度量。不要用模糊的“表现良好”，也不要定 100% 准确率这种不可能的目标，而是基于行业基准给出具体数字。即便是“代码质量”这类主观指标也可以量化——比如“95% 的生成函数首次运行即通过全部单元测试”。

    没有清晰、可度量的成功标准，你永远不知道自己的改动是在变好还是变坏。而在 LLM 应用这个概率世界里，那只会让你无休止地微调却没有真正的进展。

    想深入了解如何制定有效的成功标准，请看 Anthropic 的指南： 为 LLM 应用定义成功.

    数据是你最有价值的资产

    你的应用表现，不会好于你收集到的关于它实际使用情况的数据。但光收集数据还不够——你需要在自己的组织里建立数据驱动的文化。这意味着基于真实指标而非直觉做决策，并用这些数据对照你的成功标准进行度量。

    每一次用户交互都是可以用来改进应用的数据点：

    • 改进提示词：用成功与失败的响应来打磨你的提示词工程
    • 微调模型：收集高质量的用户交互，为模型微调制作训练数据
    • 追踪成功率：监测用户觉得哪些功能或响应最有帮助
    • 发现边界情况：借助失败来识别并处理意外场景

    对传统开发者来说这可能很陌生。大多数人的工作是写代码、测试、发布。但做 LLM 应用，你会花大量时间盯着表格、追踪指标。这活儿不光鲜，却必不可少。最好的 AI 工程师拥抱这种数据驱动的心态，哪怕它意味着要做枯燥的事。

    可以从简单的反馈机制起步，比如点赞/点踩按钮，然后随着你弄清哪些指标最重要，再逐步搭建更完善的数据收集。听说某个最大的代码生成平台有一个专门的 Slack 频道，每次有人点踩都会提醒开发者去排查。每一次负面的交互都是学习机会。无法度量，就无法改进。

    结语

    构建 LLM 应用需要思维方式的根本转变：从确定性系统走向需要持续评测的概率性系统。一个残酷的事实是：你的应用第一版不会太好——你还没有足够的数据。但这没关系。当你基于真实用户数据建立起持续改进的文化，真正的魔法才会发生。

    关键不是消灭不确定性（对 LLM 来说这不可能），而是通过系统化评测去理解和管理它。成功来自定义清晰、可度量的标准，并把每一次用户交互都当作学习机会。这对传统开发者可能很陌生，却是 AI 工程的必修课。

    在下一篇文章里，我们会深入讲讲如何构建评测系统——也就是我们所说的“评测（eval）”——它们能帮你理解和管理应用的概率本质。我们会探讨如何建立系统化的方法来度量性能、追踪改进，并就应用的发展做出数据驱动的决策。
