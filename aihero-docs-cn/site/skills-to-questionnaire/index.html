    /to-问卷（questionnaire） 技能

    把悬而未决的问题变成一份由别人来填的文档。

    它做什么

    to-questionnaire 把你一个人定不下来的决策变成一份 问卷（questionnaire）：一份 Markdown 文档，交给那个掌握你所缺信息的人，让他异步填好，或者你们俩在会上一起过一遍。

    它追问你的是 发送（send），从来不是主题本身。围绕主题的访谈毫无意义——正因为不懂主题，你才要写信给别人。所以它只问你永远答得上来的两件事（这文档要发给谁、你要对方回什么），并把文档里的每个问题都对准两者之间的 差距（gap） 。

    什么时候用它

    调用方式是输入 /to-questionnaire； 智能体 不会自己主动调用它。

    当一个决策卡在某个人脑子里的知识上时用它：客户、领域专家、掌握业务规则的高管、一个你不在其团队的同事。该用哪个技能，取决于答案在哪里：

    答案在……该用
    你自己脑子里，还没理清grill-me
    代码库grill-with-docs
    别人脑子里to-questionnaire
    还没在任何人的脑子里，问题需要先有个东西可以对着反应prototype

    最常见的情况是一场 追问（grilling） 会话卡住了，因为它提出的有些问题不该由你来答。在同一个对话里运行 /to-questionnaire ，把那些问题先放到线下，再把答案带回来继续。

    问的是发送，不是主题

    访谈只有两个来回，然后就停。

    • 发给谁？ 对方的角色、专长、与你的关系。这决定了文档的语气，以及它要承载多少背景。外部客户需要引导；队友不需要。
    • 你要对方回什么？ 你一个人定不下来的具体决策或事实。它会变成成稿文档的核对清单。你点名的每一项，都会有一个问题对准它。

    之后全是写作。技能把文件写到 to-questionnaire-<slug>.md （当前目录下）。没有安装、没有工作区、没有任何要配置的东西。

    这份文档

    这份文档是一份 探底问卷（discovery 问卷（questionnaire）），因为缺上下文的是你，有上下文的是收件人。这决定了它的形态：

    • 一行目的说明，写明哪个决策依赖它；一节简短的背景介绍，给完全不了解你背景的收件人。
    • 问题按 最重要在前（most-imp或tant-first） 排序，并按主题分成小节，因为异步意味着你可能只有一次机会。
    • 一个问题只问一件事，绝不复合，下面留一个答案占位，并且只在可能被误读的问题上才有一行 “为什么问这个”（why this matters） 说明。
    • 明确允许回答“我不知道”，因为标出来的不确定有用，而一个读起来像事实的自信猜测没用。
    • 结尾一个兜底问题：还有什么我们没问、但你认为我们该知道的？

    这份文档刻意不是两样东西。它不是 分支式（branching）。问题是一份扁平的、分组清单，不是“你答了 A 就跳过 D 节”的树。它也不是 多收件人（multi-收件人（recipient）） 。一次运行只为一个人产出一份文档。

    常见问题

    它会读我的追问会话、从中提取问题吗？ 不会把它当作自己的一个步骤。该技能没有摄入阶段。它问发送，然后起草。追问会话之后它能好使，是因为你在 同一个对话里运行，于是 会话（session） 已经在 上下文 里，起草时可以取用。如果你在新会话里启动它，它对追问一无所知，主题得你在回答“你要对方回什么？”时自己再讲一遍。

    缺的答案不全在同一个人手里。它能按收件人拆分吗？ 不能。第一步问的是 那 一个（单数）收件人，整个文档的语气和背景都对着他调。如果三个人各掌握答案的三分之一，就跑三次，一人一次。有人要求出一份按职能或角色路由问题的文档，但没有做出来。

    问题之间有依赖吗：它会根据前面的答案跳过某些小节吗？ 不会。依赖式问题的设计探索过，没有上线。产出是一份静态文档：按主题分组、最重要在前、每个问题都有效。对它的反对是有道理的。一个 模型 在拿到真实答案之前就规划两三个以上问题的模型，规划得很糟，而一份分支式文档必须在每个答案之前把所有问题都规划好。

    要是收件人也不知道呢？ 文档会让他们直说。它明确要求“我不知道”和部分答案。标出来的不确定比猜测更有价值，因为一个模糊的答案和一个自信的错误答案，回到你的上下文里看起来一模一样。

    它会把它发送到什么地方吗（Slack、工单追踪器、邮件）？ 不会。它在当前目录写一个 Markdown 文件并告诉你路径。怎么送由你：贴进一张 工单（ticket）、丢进一个 Slack 讨论串、附在一封邮件里，或者投到共享屏幕上现场一起过。这四种人们都手动干过。

    这不就是 /grill-me 的批量模式吗？ 不是。 grill-me 本来就在 按轮（rounds）提问。它一次问出全部悬而未决的前沿问题，再根据你的答案重新计算，所以“一次给我所有问题”这个需求它已经满足了。 to-questionnaire 在另一条轴上不同。它关心的是答案在谁的脑子里，而不是问题怎么送达。想自己更快答出来，用 grill-me。想从别人那里把答案拿出来，用这个。

    不用技能，我直接让智能体干这个不行吗？ 行，它出现之前很多人就是这么干的： OPEN_QUESTIONS.md 文件、发给客户的表格、每个未答问题一张“需要更多信息”的工单。这个技能买给你两样东西：访谈永不漂移到主题上，以及文档产出的形态连非技术收件人都能填。如果你已经有一套好使的自家格式，那不需要它。

    正常工作的标志

    • 它问收件人、问你要对方回什么，然后就不再问。如果它问起主题本身，这个技能就出错了。
    • 你点名的每一项“我要对方回的”，都能在文件里追到一个问题。
    • 这些问题读起来是对准 收件人（recipient） 知道的东西去的，而不是你自己的悬而未决问题被原样抄了一遍。
    • 你可以把文件交给一个没参与对话的人，他会知道自己为什么收到它、什么时候要回。
    • 收回来的答案可以直接作为新一轮追问的输入，而不是又一批新问题。

    它的定位

    to-questionnaire 是一个随时可用的独立技能。你把它用在自家知识到头、下一步该去问别人而不是跑另一个技能的地方。这多半发生在流程中间：规划卡在了一件不由你决定的事上。

    它的邻居是 grill-me，两者的差别在答案住在哪。追问从你这里拿答案；问卷从别人那里拿。把收回来的东西喂给新一轮追问，或者喂给 grill-with-docs 或 to-spec （如果这份工作要走向构建）。拿不准当下该用哪个技能时， ask-matt 给你指路。
