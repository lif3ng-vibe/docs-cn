    我的 AI 开发 7 阶段

    掌握使用 Claude Code 进行 AI 辅助开发的 7 个阶段。学会运用调研、原型、PRD 等手段交付生产级质量的代码。

    Matt Pocock

    我总结出了七个 AI 开发阶段，能稳定地带来出色的交付成果。这些阶段无论你用的是 Ralph 循环, GSD, Spec Kit还是其他任何 AI 编码方法，都同样适用。

    具体如何实现由你决定，但这七个阶段代表了成功的 AI 辅助开发工作流中的一种通用模式。

    本指南写给相信基础功底在 AI 时代依然重要的工程师。它不是给氛围编程（vibe coding）玩家看的，而是为认真对待 AI 工程、想构建经久耐用的应用的人准备的。

    阶段 1：想法

    每个项目都始于一个想法——你启动这套流程的原因。它可能是：

    • 一个你想开发的完整应用
    • 某个具体功能或 bug 修复
    • 一次代码库重构

    想法可大可小，随你需要。这套流程既适用于大型项目，也适用于狭窄聚焦的任务。

    打磨你的想法

    在进入调研或原型之前，先迭代式地打磨想法。我用了一个 /grill-me 技能（skill） ，它会通过一连串提问把概念充实得更具体。

    这种早期打磨有助于在投入时间做调研或原型之前，先厘清需求、暴露假设。

    阶段 2：调研（可选）

    如果你的想法涉及外部依赖或艰难的探索环节，就加入一个调研阶段。

    例如，如果你要对接 Stripe 或某个少见的 API，就创建一个 RESEARCH.md 资产，把所有相关信息缓存在仓库里，让智能体（agent）随时可查。

    为什么调研很重要

    智能体常常在全新的上下文窗口（context window）中工作。如果探索起来很费劲（外部 API、难以获取的文档），把这类信息缓存到一个 research.md 文件里，能省去重复探索，并提升智能体的表现。

    重要： 调研资产通常只在本次冲刺或功能开发期间有效。留存太久，调研会过时，还可能把智能体带偏。

    阶段 3：原型

    当你需要把自己的品味施加到成果上时，原型至关重要。在这个阶段，你还在探索要构建什么、它该如何运转。

    在一次性的路由上做出多个变体，让 LLM 向你展示不同的做法。经过几次会话迭代，找出最佳方案。

    适用于：

    • UI 设计与行为
    • 软件架构决策
    • 测试外部服务集成

    尽早做原型，能让你把胜出的设计提交进代码库，供智能体在实现阶段使用。等到写 PRD 时，具体示例比抽象描述更有价值。

    阶段 4：产品需求文档（PRD）

    调研和原型完成后，就该认真描述目的地了。此时你应该已经清楚最终的终态。

    聚焦于用户会看到什么、它会如何表现，而不是实现细节。PRD（产品需求文档）描述的是终态，而不是旅程。

    在撰写 PRD 的过程中，让智能体在每个决策点上追问（grill）你，以此敲定设计。把整棵决策树走一遍，发掘边界情况和需求。我用了一个 /write-a-prd 技能（skill） ，它正是专为此流程打造的。

    阶段 5：实施规划（看板）

    把 PRD 拆解成实施计划。看板是一份带阻塞关系的工单（ticket）列表，描述了所需的全部工作。

    虽然你也可以创建一份单一的顺序计划，但看板能实现高效的并行化。找出所有无阻塞的工单，为每张工单启动一个智能体。我用一个 /prd-to-issues 技能（skill） 来自动完成这一拆解。

    GitHub issues 对 PRD 和看板都很好用，只是缺少内置的阻塞关系。 Linear 如果你需要这个功能，它是更好的选择。

    阶段 6：执行

    运行编码智能体来执行看板上的所有工单。真正的代码就是在这一步写出来的。

    多数情况下，一个智能体按顺序逐张处理工单就够了。不过，如果看板结构良好，你可以同时在无阻塞工单上运行多个智能体来实现并行。

    我用的是 Ralph 循环，它与这套设置配合得很好。Ralph 循环能让智能体自主工作，同时通过自动化测试和验证维持代码质量。

    离开键盘运行（AFK）

    只要准备妥当（调研、原型、看板和 PRD），你就可以离开键盘运行执行循环，并获得出色的结果。

    关键在于确保你的智能体拥有所需的全部上下文：

    • 外部依赖的调研资产
    • 体现设计模式的原型代码
    • 写清需求的 PRD
    • 带验收标准、定义清晰的工单

    这些就位之后，智能体无需人类时刻干预，就能做出有依据的决策。

    阶段 7：质量保证

    执行完成后，让智能体为 人工审查制定一份 QA 计划。这份计划应列出要验证的具体测试场景、边界情况和验收标准。

    QA 通常会暴露问题或改进机会，从而产生更多看板工单，进入又一轮执行循环。这是正常且健康的——你会多次迭代第 5 到第 7 阶段，直到产品足够精良。

    每一轮迭代都应让你更接近生产质量：

    1. 智能体创建 QA 计划
    2. 人工审查并测试实现
    3. 人工发现 bug、UX 问题或改进点
    4. 创建新工单
    5. 回到执行阶段

    代码评审与人的参与

    QA 包括由人来阅读生成的代码，以确保质量、可维护性和正确性。这一步并非总是必要（尤其是在灰盒架构下），但对生产系统来说是一道重要的质量关卡。

    重点关注：

    • 逻辑错误或边界情况
    • 安全漏洞
    • 性能问题
    • 代码的可维护性与可读性
    • 是否遵循项目既有模式

    这七个阶段构成了与 AI 智能体高效协作的核心框架。

    总结

    阶段目标关键交付物
    1. 想法明确你要构建什么问题陈述
    2. 调研（可选）探索外部依赖research.md 资产
    3. 原型（可选）验证设计与 UX 想法可运行的原型
    4. PRD记录终态产品需求
    5. 看板把工作拆成工单带依赖关系的任务列表
    6. 执行完成真正的实现可运行的代码
    7. QA验证已完成的工作QA 计划与反馈

    随着新模式的涌现，这套框架可能还会演进。代码评审值得特别关注——它既可以融入执行流程，也可以在 QA 阶段内扩展。
