    AI 技能更新日志

    v1.1：/wayfinder、/改为-spec、/改为-工单（ticket）、追问改进，以及更多

    Matt Pocock

    经过一段漫长的开发期，skills 仓库的 1.1 版终于可以合并了。这个版本包含惊人的大量变更：全新的追问（grilling）方案、对现有技能的一批更新，以及两个主流程技能的改名。

    与其在这里概括一切，不如直接深入看这些变更。

    如何迁移

    由于这个版本包含技能的改名与合并，你需要更新自己的安装。技能安装器不会自动处理这些变化。

    运行以下命令获取所有新技能：

    npx skills add mattpocock/skills

    这让你可以自由挑选想要的技能。完成后，检查一遍你的 skills 目录，确保没有旧技能残留。

    新的公开文档页面在：

    • docs/engineering/to-spec.md
    • docs/engineering/to-tickets.md

    重大改名： /to-spec 和 /to-tickets

    两个大概最让人恼火的变更——但有非常充分的理由——是技能改名。这些名字困扰我很久了，因为它们没有准确反映我们实际在构建的东西。

    从 /to-prd 改为 /to-spec

    原 /to-prd 技能已改名为 /to-spec。这里的关键认识是：我们创建的东西其实并不是 PRD（产品需求文档）。PRD 描述的是产品本身的事，而我们允许非产品内容混了进来。我们真正在构建的是规格（spec）——一个宽泛得多的词，可以是技术的、非技术的，或两者的混合。

    "spec" 现在是整个技能套件中贯穿始终的术语。你可能仍把这个文档叫 PRD，但 "spec" 是我们今后使用的统一语言。

    从 /to-plan 和 /to-issues 改为 /to-tickets

    两个技能合并成一个： /to-plan 和 /to-issues 现在统一为 /to-tickets。旧名字感觉偏向 GitHub 和 Linear 这些用 "issue" 做术语的平台。但我们实际操作的概念更通用：你有一份规格，规格之下是工单——真正落实并创建这份规格的旅程。

    /to-tickets 会把计划、规格或对话拆成一组 工单（ticket）——曳光弹式的垂直切片，每个都声明自己的 阻塞边（blocking edges）。这一个产物根据你的追踪器配置有两种用法：

    • 本地文件 (tickets.md）——边写成文字，你手动自上而下逐个处理
    • 真实追踪器 ——边变成原生的阻塞链接，于是阻塞已完成的工单就处于最前线，多个智能体可以并行工作

    盼了这么多年名字终于对了，这份清晰让我由衷高兴。

    追问技能的改进

    接下来一组变更修复了大家在使用 /grill-me 和 /grill-with-docs时遇到的 bug。两者都依赖一个核心的追问参考技能，教 LLM 如何有效地追问一个人。

    三个关键修复

    1. 更清晰的提问指引

    原先的指引说"一次问多个问题让人晕头转向"。即便有这条指令，模型偶尔还是会无视它、一口气问好几个。所以我把 为什么 不能一次问多个问题说得更明白了。

    2. 实施前的确认闸门

    在结尾加了一步确认："在我确认我们已达成共识之前，不要执行计划。"很多人反馈追问会话结束后模型就直接跳进实现。这道闸门防止了这种情况。

    3. 防止自我追问

    在一些奇怪的场景里，模型会自己追问自己——探索代码库并在没有人类输入的情况下自问自答。这在 Fable 上尤其常见。为了修复，我加了引导词来区分两类信息：

    类型定义示例
    事实通过探索代码库发现的东西代码模式、现有实现
    决策需要用户来决定的事架构选择、特性范围

    只加了几句话、调整了几处顺序，技能的一致性就大为提升。这些微调显著减少了大家报告的怪异问题。

    完整的开发生命周期流程

    我加了几个新技能，把追问过程从主要是一个规划练习，变成一套正式的软件开发生命周期。很多人问我："技能该搭配的主流程是什么？"就是它：

    流程：从追问到部署

    1. 从追问开始

    不直接用计划模式，而是让一个智能体就你的目标追问你。这里用到两份配套文档：

    • 一份术语表，帮助智能体更好理解你的领域
    • 架构决策记录（ADR），用来捕捉那些不那么显然的东西

    2. 生成规格

    追问的产出进入一份规格，它定义你的目的地——这个特性或项目要做到哪里。

    3. 拆成工单

    然后用 /to-tickets把这份规格拆成一张张工单。这把开发工作分散到多个智能体会话，每个会话专注一张工单。

    4. 实现每张工单

    用 /implement 技能实现每张工单，它简单得出奇：

    Implement the work described by the user in the spec or tickets.

    Use TDD where possible at pre-agreed seams.

    Run type checking regularly.

    Single test files regularly.

    Full test sweep once at the end.

    原 /implement 技能主要依赖智能体的先验知识和你的 agents.md 文件教它的东西。我差点没为它建技能，因为实在太简单，但大家一直问"流程是什么？"所以现在你有一个明确的终点：有了工单之后，在单独的编码会话里逐张实现即可。

    5. 代码评审

    实现完成后， /implement 技能会调用 /code-review 在提交前评审工作。

    带重构异味的代码评审

    代码评审技能在两条轴上评审代码，每条轴用一个子智能体（sub-agent）：

    轴目的细节
    标准轴（St和ards）是否符合编码标准读取 codingstandards.md 或你仓库里的类似文件
    规格轴（Spec）相对需求的正确性代码是否忠实实现了来源规格或工单？

    两者都以并行子智能体运行，逐一走过代码的每个部分。

    这个技能妙而新的地方在于：我一直在重读 Martin Fowler 的 《重构》（Refac改为ring） ，意识到智能体的训练里早已深深嵌入代码异味的知识。你要做的只是点出这些概念。举几个例子：

    • 天书命名（mysterious name）
    • 重复代码（duplicated code）
    • 依恋情结（feature envy）
    • 数据泥团（data clumps）
    • 基本类型偏执（primitive obsession）
    • 重复 switch（repeated switches）
    • 发散式变化（divergent change）
    • 夸夸其谈通用性（speculative generality）
    • 消息链（message chains）
    • 中间人（middleman）

    当你这样描述时，智能体会接上这些术语："对，我发现了消息链，需要移除它们。我发现了一个中间人情况，需要修掉。"

    我测了几个星期，它在提升代码质量上出奇地有用。最妙的是什么？加起来真的很便宜——大约只有 10 行指引。

    为大型计划引入 Wayfinder

    接下来是我真正兴奋的技能：一种全新的规格启动与塑形方式。它叫 /wayfinder，设计上用来取代 /grill-with-docs 在许多场景中的地位。

    什么时候用 Wayfinder

    /wayfinder 适用于要规划的东西太多、单个智能体会话装不下的情形。你要么冲出智能体的聪明区（smart zone），要么撞上它的上下文窗口上限。你需要把它拆成多个部分才能想清楚要去哪。

    概念如下：

    一个松散的想法到来了，大到单个智能体会话装不下，还裹在迷雾里。从这里到目的地的路还没显形。这个技能把路径绘制成仓库工单追踪器上的一张共享地图，然后逐张处理工单，直到路线清晰。

    Wayfinder 如何工作

    Wayfinder 创建一张以 GitHub issue 形式保存的地图，每个决策的大小以一个智能体会话为限。决策之间以阻塞关系相连，前置未解决，依赖它的决策就无法做出。

    这是一个来自 S和castle 仓库的例子，调研是否引入 AI SDK 作为依赖：

    工单类型：

    • 调研 ——一个 AFK 任务，让智能体做调研并汇报发现
    • 追问 ——一场用于做决策的追问会话
    • 原型 ——一个快速原型，提升讨论的保真度
    • 任务 ——配置、开通资源或其他不需要追问的工作

    为什么原型很重要

    我一直主张在到达规格之前多做原型。思路是：造一个便宜、粗糙、具体的产物去回应——提纲、粗略观点、stub 或 UI 逻辑代码——以此提升讨论的保真度。

    在以下情况使用原型：

    • "该长什么样？"是关键问题
    • "该有怎样的行为？"是关键问题

    对几乎所有触及前端代码的工作这都是必备。我强烈推荐在 /wayfinder 的任何前端工作中使用它。

    Wayfinder 完成之后

    所有工单关闭后，这些信息都会存到地图上，原始工单作为一手来源。然后你可以照常把这张地图变成一份规格。

    Wayfinder 的美妙之处在于：不必再用 /grill-with-docs来管理会话焦虑——操心交接（h和off）和聪明区——一切都替你管理好了。你只需关掉一个会话，打开下一张 Wayfinder 工单。一切都保存在 GitHub 里，可协作、可在团队内共享。

    配套技能：调研与原型

    为支持 Wayfinder 工作流，新增了两个技能。

    原 /research 技能

    原 /research 技能小而顺手：

    • 起一个后台智能体去做调研，它阅读时你可以继续干活
    • 对照一手来源调研问题
    • 把发现写进一个简单的 Markdown 文件
    • 按仓库既有约定，把它存到仓库本来就放这类笔记的地方

    任何时候需要做一轮调研又不想打断你的心流，就用它。

    原 /prototype 技能

    原 /prototype 技能现在改为模型调用，Wayfinder 可以自己调用它。它在两种类型中让你选择：

    类型目的用例
    逻辑原型测试行为和逻辑后端 API、业务逻辑
    UI 原型测试外观和交互前端组件、用户流程

    两者反应很不一样，能帮你在敲定规格之前探索设计空间。

    TDD 技能更新

    最后一项变更回应了大家的呼声：能够把 /tdd 技能交给 AFK 智能体并直接开跑。

    旧方案

    旧的 /tdd 技能会推荐一组步骤并请你逐条确认。这很别扭，因为它不符合大多数人实际使用 TDD 的方式——他们希望智能体自主工作。

    新方案

    原 /tdd 技能现在只是参考资料。它不规定具体步骤，只给出关键顺序：

    1. Red - Write failing tests

    2. Green - Make tests pass

    3. Refactor - Improve code (moved out of the loop)

    关键变化：重构不再属于 TDD 循环。它现在放到代码评审阶段处理，让实现保持专注、更干净。这样实现会话就不会被重构负担压垮。

    需要注意什么

    • /to-spec 取代了 /to-prd ——更新任何相关流程或文档
    • /to-tickets 取代了 /to-plan 和 /to-issues ——两者现已统一
    • 新工作流 ——考虑采用新流程：追问 → 规格 → 工单 → 实现 → 代码评审
    • 处处 Wayfinder ——试试用 /wayfinder 代替 /grill-with-docs 来处理更大的规划任务
