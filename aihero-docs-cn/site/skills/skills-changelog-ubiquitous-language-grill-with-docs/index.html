    技能 Changelog：统一语言（ubiquitous language）-> /grill-with-docs

    Matt Pocock

    坐拥 46.6k 星标，我的 技能仓库（skills repo） 已经变成我工程思考的精华合集。我现在会定期发布技能变动的更新，这些视频就像一份 changelog，让你随时掌握变化。

    这些技能专为你下载到自己的环境里立即上手而设计。它们代表我在自己的工作中每天使用的方法与技术。

    仓库结构变更

    第一个重大变化是仓库结构。技能现在被组织成几个明确的类别：

    类别用途
    效率技能在通用工作流工具中就有用的技能，不特定于代码
    工程技能主体合集——我每天使用、并建议认真学好的技能
    杂项技能偶尔使用的技能；它们在仓库中的最终归属还未定
    已弃用正在被淘汰或被更新替代品取代的技能
    个人技能我个人在用的技能，分享出来供参考启发，而非核心用法

    现在你可以放心忽略 misc 与 deprecated 这两个文件夹。

    重大变更与新功能

    /ubiquitous-language -> /grill-with-docs

    这个 /ubiquitous-language 技能已被弃用，并合并进一个强大的新技能： /grill-with-docs.

    变化了什么：

    • 它不再创建 ubiquitous-language.md 文件，而是创建一个 context.md 文件
    • 把追问（grilling）会话与文档撰写合并在一个阶段完成
    • 支持多个限界上下文（bounded contexts），这是领域驱动设计（DDD）的常见模式

    这意味着你可以：

    • 系统的不同部分使用不同的上下文（例如订单 对比 计费）
    • 各自拥有自己的 context.md 和共享语言
    • 无需在整个应用层面强求单一的统一语言

    /grill-with-docs 对比 /grill-me:

    特性/grill-with-docs/grill-me
    最适用于代码库通用场景（生活、工作、创作项目）
    输出context.md、架构决策记录（ADR）灵活的文档
    所在位置工程文件夹效率文件夹

    /grill-me 完全没变，只是被重新归置了。甚至有人用它为母亲写悼词，效果非常好。

    /grill-with-docs ——架构决策记录（ADR）

    /grill-with-docs 现在包含 ADR（架构决策记录）。当以下三个条件同时成立时，就应该写一份 ADR：

    1. 很难逆转
    2. 没有上下文会觉得意外
    3. 它是真实权衡的结果

    你与 AI 在这些非显而易见的决策上对齐，能防止 AI 反复提出同一个坏主意。

    /improve-codebase-architecture ——新增 LANGUAGE.md

    /improve-codebase-architecture 迎来一次大升级：为讨论代码库改进配备了一套完整的语言定义。

    该技能现在用精确的术语描述架构概念。例如：

    **`Module`**

    

    Anything with an interface and an implementation. Deliberately scale-agnostic - applies equally to a function, class, package, or tier-spanning slice.

    

    **`Interface`**

    

    Everything a caller must know to use the module correctly. Includes the type signature, but also invariants, ordering constraints, error modes, required configuration, and performance characteristics.

    

    **`Implementation`**

    

    What's inside a module - its body of code. Distinct from Adapter: a thing can be a small adapter with a large implementation (a Postgres repo) or a large adapter with a small implementation (an in-memory fake).

    拥有这套共享语言，能避免啰嗦的对话，并让你与 AI 就“好的代码库长什么样”保持一致。

    /setup-matt-pocock-skills ——工单追踪器（issue tracker）灵活性

    技能现在可以配合 任意 工单追踪器（issue tracker）使用，而不只是 GitHub Issues。

    此前： 像 /to-issues 这样的工程技能，此前专门针对 GitHub Issues 调校。

    现在： 技能会说“把 issue 发布到工单追踪器”，可它怎么知道是哪一个？

    答案是一个新技能： /setup-matt-pocock-skills.

    它通过创建一个 CLAUDE.md 文件来搭建每个仓库的配置，内容包括：

    • 你的工单追踪器位置
    • 分诊标签
    • 领域文档路径

    自定义追踪器： 既然这些是由 LLM 驱动的智能体（agent），你可以接入任何自定义工单追踪器，甚至未受支持的工具。

    设置流程长这样：

    Set up Matt Pocock Skills

    → Install all engineering skills

    → Pick the skills you want

    → Run: matt-pocock set-up-matt-pocock-skills

    最终生成的 CLAUDE.md 极简而干净：

    issues live at: github/issues at mattpocock.sandcastle

    issue tracker: logged in here

    这是渐进披露（progressive disclosure）——智能体只在需要时才取用这份配置。

    新的实验性技能

    /diagnose

    /diagnose 用于修复棘手的 bug。每次调试时都运行它。

    流程：

    1. 搭建一个反馈回路
    2. 在该回路中复现 bug
    3. 对 bug 提出假设（给出按可能性排序的假设列表）
    4. 埋点观测（加日志以观察行为）
    5. 实施修复

    注意： 目前 AI 在这些阶段会过于急躁地抢跑。这项技能仍在调校中。

    /triage

    /triage 用于分诊那些并非由你创建的工单，通常是积压（backlog）里的工单。

    用例： 你的 PM 添加了一些关于想要功能的模糊描述；triage 会把它们整理清楚。

    工作原理： 使用一台带类别角色和状态角色的状态机。

    类别角色：

    • bug ——有东西坏了
    • enhancement ——新功能或改进

    状态角色：

    • needs-triage ——维护者需要评估
    • needs-info ——等待报告者补充更多信息
    • ready-for-agent ——规格完备，AFK 智能体随时可开工
    • ready-for-human ——需要人工实现
    • wontfix ——不予处理

    每张经过分诊的工单都恰好获得一个类别角色和一个状态角色。我在自己的开源仓库上就是这么用的，效果非常好。我可以随手写下模糊的描述，生成澄清评论，让工单达到 AI 可接手的状态。

    获取更多更新

    所有技能更新以及榨干智能体价值的技巧，都发布在 aihero.dev/skills。这是一个专为技能打造的定制通讯（newsletter）。

    感谢一路跟随。希望你喜欢这些更新，就像我享受制作它们一样。回头见！
