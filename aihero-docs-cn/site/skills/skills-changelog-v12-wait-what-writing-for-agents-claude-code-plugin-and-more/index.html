    AI 技能 Changelog

    v1.2：/wait-what、/writing-for-agents、Claude Code 插件与更多

    Matt Pocock

    我的技能 1.2 版发布了。它把技能打包成 Claude Code 插件，为每个技能加上 Codex 元数据，并把整套技能放到一个文档站点： aihero.dev/skills。三个技能新加入插件，一个更名，六个被移除。

    完整的变更集见 v1.2.0 发布。本页说明对你的影响。

    每个技能都有 Codex 元数据

    每个 SKILL.md 现在都伴有一个 agents/openai.yaml 文件。这个 sidecar 承载 Codex 的 UI 元数据（interface.display_name, interface.short_description），整套技能无需生成副本即可在两个 harness 中使用。

    那个文件里关键的一行是 policy.allow_implicit_invocation: false，它是 disable-model-invocation: true。每个用户调用的技能现在都带着它，所以在你键入 $skill之前，Codex 会把这个技能挡在智能体（agent）的上下文之外。在此版本之前，用户调用 / 模型调用的区分只在 Claude Code 成立，Codex 上并不成立。

    AGENTS.md 是一条指向 CLAUDE.md的符号链接，所以 Codex 读到的是同一份仓库指令。

    aihero.dev/skills 上的文档

    从 /skills 开始，读一读那些分组。主流程依次是 /grill-with-docs → /to-spec → /to-tickets → /implement → /code-review。左侧面板是每个技能的完整参考。

    每个页面都有一个 常见问题 栏目，内容来自人们实际问过我的问题 wiki；还有一个 如果奏效，你会看到 栏目。术语首次出现时会链接到 AI 编码词典，比如工单（ticket）的链接就指向我对 ticket 的定义。你可以用这些文档来学技能，也可以用来理解 AI 编码的原理。

    破坏性变更： /writing-great-skills → /writing-for-agents

    请用新名称重新安装。没有别名，旧名称已不复存在。

    这次更名跟随其范围扩张。这套参考现在覆盖智能体会消费的任何文档：技能、 AGENTS.md, CLAUDE.md，以及通过指针触达的文档——不再只是技能。用它把一个不堪重负的 AGENTS.md 拆分成多个技能，避免前置堆积。

    随之而来的是三个结构性变化：

    • GLOSSARY.md 被合并进 SKILL.md。每个术语只保留一份权威论述。
    • 技能专属的机制（frontmatter、模型调用 vs 用户调用、路由技能、调用切分）移到 SKILL-MECHANICS.md.
    • 该技能是模型调用的。当你创建或编辑技能，或修改 AGENTS.md / CLAUDE.md.

    修剪（pruning）部分新增一个术语： 缓存（cache）。环境是事实来源： package.json 脚本、配置文件、目录布局、 --help 输出。复述这些内容的文档只是一次查询的缓存，只有当查询本身代价高昂时，它才配占用上下文载荷。要缓存的是智能体“看”不到的东西：没有写下来的约定、某个选择背后的原因、任何配置都供认不出的边界情况。查一个文件、跑一条命令就能得到答案的事，留给环境去做，那样它们永远不会过时。

    新增： /wait-what

    一个纠正模型啰嗦的单词指令。当一条消息没能传达到位时，立刻输入它。智能体会重新表达：补上一点上下文、改用 ASD-STE100 简明技术英语，以及来自你 CONTEXT.md的统一语言。用户调用，全文只有三行。

    其机制就在名字本身。简洁类技能会因膨胀而失败——一个 400 行的技能仍然治不住模型的啰嗦——所以这个技能只有一个精准的引导词，别无其他。描述 输出 (/tldr, /no-fluff的名字（比如“再简短点”）会让模型删词，让你离要点更远。说出 听者的 状态，则一举要到了两样东西：更少的词， 以及 你此前缺失的上下文。

    它只修复一条消息，防不了下一条。黑话的解药是用 /grill-with-docs预先建立的共享语言。当你还没有这种语言时，就用 /wait-what 。

    新增： /wizard

    /wizard 从 in-progress/ 毕业进入 工程 分组，并且是模型调用的。

    它会生成一个交互式 bash 脚本，引导人工完成手动流程、第三方配置、一次性迁移或 A→B 状态转换。脚本会打开每个 URL，告诉你点哪里，捕获你粘贴进去的值，并把它们写入 .env 文件和 GitHub Actions secrets。它是一个确定性脚本，所以你输入的任何密钥都不会到达智能体。

    用户体验由捆绑的 template.sh预先解决：带剩余时间的进度显示、确认关卡、跨平台打开 URL（包括 WSL）、隐藏式密钥输入、幂等的 .env upsert， gh secret / gh variable 写入时的优雅降级，以及结尾的跳过项摘要。标记之上的部分 STAGES 是固定的库代码，永远不会手改。这项技能的职责是划定流程范围并编写它的各个阶段。

    模型调用意味着智能体一遇到只有人类才能执行的步骤，就会拿起 /wizard ，而不是把一串编号步骤倾倒进聊天。手动键入 /wizard 的行为与之前完全一致。技能描述列出了四个触发分支（开通基础设施、配置凭据或 CI 密钥、走一遍陌生的第三方控制台、一次性迁移或切换），以及一个明确的非触发场景：智能体自己能执行的步骤不要调用它。智能体能做的工作，就该由智能体来做。 /wizard 专门负责那些你不会交给智能体的点击、审批和控制台操作。

    新增： /to-questionnaire

    /to-questionnaire 从 in-progress/ 毕业进入 效率 分组。

    它把一个你独自答不了的决策，变成一份给唯一能答之人的 Markdown 问卷。可以异步填写，也可以在会上一起过一遍。我是在一次 /wayfinder 会话中造出它的，话题是花园办公室：智能体在追问（grilling）我，但该问的人是我太太。问卷放进了 Google Doc，我们过了一遍，答案再回到智能体手里。

    它的标志性设计是：它追问的是 发送对象，而不是主题本身。普通的追问会话审问的是话题，而这恰恰是你在此答不出来的部分。所以这场访谈只问问卷发给谁、你需要拿回什么，然后把每个问题都对准这两者之间的落差。

    /ask-matt 把它定位为 /grill-me的反向操作：去挖掘别人，而不是你自己。

    变更： /grilling 改为按轮次提问

    /grilling 它从一次一个问题改为逐轮推进。同样 13 个问题，大约 3 轮问完，而不是 13 个回合。

    该技能把这项工作映射为一棵 设计树（design tree）：每个决策都分叉出挂在它下面的决策。 前沿（frontier） 是所有前置条件已经落定的决策——也就是它现在就能问、不必去猜还没听过的答案的问题。它把整个前沿作为一轮编号问题一口气问出，然后根据你的答案重新计算前沿，再问下一轮。答案依赖另一个尚未解决的问题，归入更晚的轮次。前沿清空，会话结束。

    环境能回答的事实交给子智能体（子智能体）去办，所以调研从不阻塞某一轮。一次正在进行的探索是一个未落定的前置条件：只有它下游的问题需要等待，前沿的其余部分照常发问。决策权始终在你手里。

    每一轮中的每个问题都使用同一个固定格式：

    ❓ **Q1** - **<question title>**: <question body, might be multiple paragraphs, including multiple choices>

    

    ➡️ <your recommended answer>

    一轮读起来就是一份一眼可扫的编号清单，每条推荐与其问题分开。你按编号回答（“Q1 同意，Q2 同意，Q3 改一下”），很适合语音听写。

    /grill-me, /grill-with-docs 以及 /triage 也按轮推进前沿。想退回一次一问的方式，出口也没变：在你的全局 CLAUDE.md.

    /grilling 的措辞也改为通用版本。“This plan” 变成 “this”，“enact the plan” 变成 “act on it”，“exploring the codebase” 变成 “exploring the environment”。技法本身没变。现在它读起来就是对任何计划、决策或想法的压力测试。

    变更： /prototype 产出一个可分享的 HTML 文件

    逻辑分支现在产出一个单文件的自包含产物：纯 HTML、CSS 和 JS，无需构建、无需服务器，取代了原来的终端应用。非开发者双击即可打开，用自己的领域语言驱动它：带标签的状态面板、随时可用的自由试玩按钮，以及分页式的 引导式演练，每个都是带有序按钮的场景。可移植的纯逻辑模块依然可以提升进真实代码。HTML 壳只是用完即弃的草稿。

    一次性不再意味着删除。 /prototype 的输出会被捕获为可运行的证据，存放在一条 prototype/<name> 分支上，实施 issue 里留有指向它的上下文指针。main 只保留经过验证的决策，探索过程仍可寻回。答案（结论加问题）仍然记录在 issue、ADR 或提交里。

    变更： /wayfinder 工单是决策工单

    人们会把 /wayfinder 工单当成普通的实施工单——构建中待执行的一小块。 /wayfinder 则把它们用作 决策工单（decision tickets）：其解决本身就是一个决策的问题。技能描述、开头第一行、README 简介和文档页现在都会介绍这个术语。术语确立之后，“ticket” 仍是日常用词，而且 CONTEXT.md 会记录 决策工单（Decision ticket） 这个领域术语。

    调研工单不再被搁置到单独的会话。调研仍是一种真实的工单类型，因为它是下游决策真正共同依赖的阻塞点。变化的是它的解决方式。调研是 AFK 的，所以绘图不会停下来读它：创建完工单后，绘图会话为每张调研工单派出一个 /research 子智能体，并行清空它们，把发现记录在一条 research/<name> 分支上并附上下文指针。调研工单是“每会话一张工单”的唯一例外。

    变更： /ask-matt 路由

    路由器新增 阶段边界（phase boundaries）。阶段是会话内的一块工作（追问、实现、QA），两条阶段之间的边界，正是你决定如何处置已建立上下文的地方。原来只有两条的章节，现在是一棵按顺序列出全部五个选项的决策树： 继续, /clear, /handoff, 子智能体, /compact。理由披露在 PHASE-BOUNDARIES.md。随之而来是三个修正：

    • /handoff 被高估了。 它适用面很窄。只有当某些东西需要 迁移——新的 harness、新的目录、一位同事，或阶段中途分叉的支线任务。
    • /compact 是默认项，不是第一顺位。 它排在树的最底部。从这里起步，你会得到一个对摘要抹平掉的一切都“自信地搞错”的会话。
    • 少了两个分支。 先排除 继续 ，它是唯一能把对话本身保留为一手来源（primary source）而非其摘要的选项。 子智能体 能接手任何范围收得足够紧、可以 AFK 运行的任务。

    上下文卫生的逃生通道现在写的是 /compact 而不是 /handoff，聪明区（smart zone）的数字也从约 12 万 token 调整为约 15 万。

    /wayfinder 路由修正了人们在最重流程上最常犯的两个错误。 对它伸手过度: /wayfinder 比一次单纯的追问更慢更重，所以它只留给那些真正塞不进单个会话的想法。范围划得好的功能属于 /grill-with-docs. 在交接处迷路：当地图清空， /wayfinder 它只负责交接，不负责构建。在 /to-spec处汇入主流程——它会把地图上互相关联的决策收敛成一份可执行的计划。只有当工作量确实很小时，才直接用 /implement 。

    /grilling 以及 /resolving-merge-conflicts 此前不在路由器里，现在已经加入。 /grill-me 会从 /grill-with-docs 分岔出来，依据是你是否已在工作目录。

    变更：若干小事

    • /improve-codebase-architecture 的探索步骤增加了一个 YAGNI 范围过滤器。它不再均匀扫描仓库。你指个方向，它就顺着去；否则它会读最近约 20 条提交信息，把探索偏向活跃开发的路径。没人碰的代码里的加深（deepening）机会，是一笔你永远无法兑现的重构，所以报告不再去整理休眠的角落。
    • /setup-matt-pocock-skills 变得更友好。只有当 /triage 已安装时才会问分诊标签，而且只作为一条建议回答“是”的问题。外部 PR 作为需求入口不再设问，该开关出厂默认关闭。除非仓库呈现 monorepo 信号，领域文档默认单上下文。本地 Markdown 工单是每张工单一个文件，放在 .scratch/<feature>/issues/<NN>-<slug>.md之下，规格文件则是 spec.md.
    • 这次 /to-prd → /to-spec 更名已经完成。 “Spec” 是交付文本中唯一的叫法。 /to-spec 去掉了“你可能知道它叫 PRD”的开场白， /code-review 改说源头的 issue/规格，GitHub 与 GitLab 追踪器模板也不再往它们接触的每个仓库写进“PRDs”字样。

    移除：六个技能

    这六个都不在 Claude Code 插件里，但都可以通过 skills.sh安装——它提供仓库里的每一个技能。其中四个被一个干得更好的技能吸收：

    • /ubiquitous-language → /domain-modeling，它维护整个领域模型，而不是从一次对话里倒出一份术语表。
    • /design-an-interface → /codebase-design。什么也没丢：design-it-twice 技法就内置于那个技能，作为 DESIGN-IT-TWICE.md.
    • /qa → /triage 以及 /to-tickets.
    • /request-refactor-plan → /to-spec 以及 /improve-codebase-architecture.

    另外两个从来只属于我，绑定在我自己的机器上。 personal/ 分组随它们一同退场： /edit-article 以及 /obsidian-vault.

    skills/deprecated/ 保留为一个空分组。 skills/in-progress/ 保持不变，并且现在如实描述它的定位：一个 beta 通道，有意发布，可通过 skills.sh 一次安装一个技能。
