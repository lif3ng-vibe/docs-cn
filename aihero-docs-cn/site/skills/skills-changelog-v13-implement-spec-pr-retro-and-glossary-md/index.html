    v1.3：/implement-规格（spec）、/pr、/retro 与 GLOSSARY.md

    Matt Pocock

    我的技能 1.3 版发布了。写代码变便宜了，读代码没有。所以这次发布围绕的是代码周边的一切：三个技能从 in-progress/ 毕业进入 工程 分组，一个技能被删除，还有一个文件重命名需要你动手。

    完整的变更集在 v1.3.1 发布。本页说明对你的影响。

    如何更新

    如果你是通过 /plugin install安装的，更新会自动送达。否则：

    npx skills update

    然后检查你的技能文件夹。如果 resolving-merge-conflicts 还在，就删掉它。更早的更新并不总会把已删除的技能移除。

    破坏性变更： CONTEXT.md → GLOSSARY.md

    技能读写领域文档的约定更名为： CONTEXT.md 现在改为 GLOSSARY.md， CONTEXT-MAP.md 现在改为 GLOSSARY-MAP.md。技能只认新名字。如果是 /grill-with-docs 或 /domain-modeling 给你生成过其中某个文件，把它挪个位置：

    git mv CONTEXT.md GLOSSARY.md

    git mv CONTEXT-MAP.md GLOSSARY-MAP.md

    在团队里，把这件事放进一个所有人都拉取的提交里完成。如果有人在文件挪动之前就更新了技能，他们的智能体（agent）会另起一份新的空 GLOSSARY.md ，与旧文件并存。

    旧名字来自 DDD 的 限界上下文（bounded context）。除了名字之外，我仍在践行 DDD，但 CONTEXT.md 这个旧名字太含糊了。它不能让智能体在恰当时机拉入文件，还让人困惑。而且这个文件后来也萎缩到只剩一份术语表。所以现在名字直接说明它是什么。行为没有任何变化，改的只是文件名。

    受影响的技能： domain-modeling, grill-with-docs, improve-codebase-architecture, setup-matt-pocock-skills, triage, tdd, diagnosing-bugs, ask-matt, codebase-design, wait-what 和 pr.

    主循环

    主流程的前半段没有变化： /grill-with-docs → /to-spec → /to-tickets。它最终产出一份 规格（spec） 和一组 工单（ticket）。三个新技能构成后半段：

    • /implement-spec 接下规格和工单，把全部工作构建出来。
    • /pr 拿到结果，写一份人类能快速评审的 PR 描述。
    • /retro 回顾这次会话并修改仓库，让下一次运行更好。

    新增： /implement-spec

    /implement 还在。它做单张工单，调度员是你。 /implement-spec （用户调用）一次运行构建整份规格，全程在一条 集成分支（integration branch）上完成：每张工单的工作都落到这同一条分支上，一张接一张，在靠近 main 之前一气呵成。

    消化一组工单有三种方式：

    1. 手动循环。 你说“实现工单一”，等它跑完，清空上下文，再说“实现工单二”。f或 循环就是你本人。这可不太好玩。
    2. 确定性循环。 脚本读取每张工单，对其运行 /implement 。这是我推荐大多数人使用的方式。它每次都以同样的方式运行，可靠且便宜。但搭建和调优需要耐心。 S和castle 就是其中之一。
    3. 智能体循环。 由智能体代替人类做保姆工作。这就是 /implement-spec.

    智能体循环不如确定性循环。但在你的软件工厂尚未调校到位之前，它是开始 AFK 工作的好办法，而且我对它的依赖远超预期。现在之所以可行，是因为子智能体可以再派生自己的子智能体。

    这些工单不是一张步骤清单。它们是 一张带阻塞关系的任务图， /to-tickets 负责写下这些关系。所以始终存在一个 前沿（frontier）：不被任何工单阻塞的那些工单。运行流程：

    1. 读取规格和工单，并在自己的子智能体里探索代码库。
    2. 创建集成分支。
    3. 为每张前沿工单启动一个实现者子智能体，各自在自己的 w或ktree 里。每个都用 /tdd.
    4. 一个合并者子智能体把完成的工单落上集成分支。前沿随之推进，新工单获得实现者。
    5. 任务图完成后，它调用 /code-review （作用于整个集成分支），并启动一个修复者。

    目标是集成分支，不是 PR。只有当你的工单追踪器（issue tracker）通过 PR 收尾工作，或者你主动要求时，才会开出草稿 PR。

    两处毛边。结果是 一根大分支，对此还没有好答案。你可以用堆叠 PR（stacked PRs），但我不想把它做成 GitHub 专属。而且 w或ktree 并不能消除冲突，只是把冲突推迟到合并时：两张工单可能用两个名字添加同一个字段。

    把它当作“实现一份规格”的初级版本，并在此基础上搭建你自己的流程。

    新增： /pr

    对要进 main 的工作来说，PR 仍是主要瓶颈。 /pr （模型调用）让人类评审尽可能快、尽可能简单。它做的全部事情，就是给智能体一份 PR 描述模板，分三节。

    摘要 是一幅图，不是一段文字：用最小的视觉元素把改动讲清楚。可以是伪代码、调用树、文件树、Mermaid 或 diff 草图。这些视觉形式来自 Dex H或thy 的 show-me 技能，已在该技能的 CREDITS.md.

    证据 是一幅 改造前 加一幅 改造后：一个曾经失败、现在通过的测试。如果你不要求硬证据，智能体很容易说“应该没问题，我读过代码了”。一旦你要求，它往往会多跑一个测试或多截一张图。证据就是你学会信任智能体输出的方式。

    合并风险 回答两个问题：

    • 单向门还是双向门？ 双向门是能走回去的改动：revert 那个提交，你就回到起点。单向门则对外部世界产生了实际影响。一次迁移删掉了一列。一次回滚撤不回已发出的批量邮件。
    • 爆炸半径。 一旦出问题，会坏掉多少东西？一个按钮，还是你库的每一个使用者。

    合并风险告诉你该把评审时间花在哪。爆炸半径小的双向门：扫一眼。单向门：慢慢读。把规格交给智能体，而不只是 diff，它才能做好这个判断。

    那份 v1.3 发布 PR 就是用这个技能写的。

    它是我见过最可靠的模型调用技能之一。在 Opus 5.5 上，智能体每次写 PR 描述它都会加载，你完全不用操心。如果你已经有一套 PR 描述技能，可以从中挑你喜欢的。

    新增： /retro

    我的技能对你要求很高。一直以来，改进仓库的人是你：保持 AGENTS.md 精简、让技能保持锋利、添加好的 lint 规则、让代码易于导航。我在自己的仓库上一直是手工做这些，所以我把它们打包成了一个技能。

    /retro （用户调用）是 retro规格（spec）tive（复盘）的缩写。对一次编码会话运行它——当前的或更早的都行——它会建议修改智能体的 环境，而不是代码。它读取真实的会话，所以能看到智能体对你隐藏的问题。智能体的抱怨远没有达到应有的程度。它硬着头皮往前推，功能照样被构建出来。

    它检查七个地方：

    • 代码库导航起来容易吗？
    • 一个 自动化检查 能抓住这类问题吗？
    • 有没有一份 编码规范 供评审者执行？
    • 全局的 AGENTS.md?
    • 工具经济健康吗，有没有工具在浪费 token？
    • 指令与引导文件里有没有 空转指令（no-ops） ？（“写整洁、可读的代码”改变不了任何行为。删掉它。）
    • 智能体拥有它所需的全部信息吗？

    最重要的是检查和规范。凡是 机械性 的违规，一律配一条确定性检查：自定义 lint 规则、pre-commit hook 或 CI 任务，如此而已。 CODING_STANDARDS.md 只留给 判断题 。检查会失败；Markdown 文件里的一句话不会。一个毫无护栏（guardrail）的仓库，本身就是一条发现。

    所以这个循环是：发现一个错误，运行 /retro，让这个错误下次无从发生。你的 AGENTS.md 会随着时间越变越短，而不是越长。

    /retro 是人在回路的。你从它的清单里挑选之前，它什么都不会改，清单按严重程度排序。用你自己的判断：有些发现对你无关紧要。大多数人问我怎么把它自动化。不要。自动化的 retro 会找出误报、反复修误报，把你的仓库带向不该去的地方。不如在有空的时侯对一批会话抽样运行，或在智能体行为古怪的那次会话上运行。

    /ask-matt 现在把 /retro 放进主流程的最后一步，排在 /code-review之后。它还会把你引向 /retro 改造后 /diagnosing-bugs，追问怎样本可以防住这个 bug。

    移除： /resolving-merge-conflicts

    解决合并冲突是 harness 层面的事，不是技能的事。没有人会退出这件事，智能体不用专门技能也能处理进行中的 merge 或 rebase 冲突。没有东西替代它。它将从 Claude Code 插件、README 和 /ask-matt.

    在较弱的模型上你可能仍想要它。 归档文档页 仍然在线。把该技能复制进你的仓库即可。

    变更：技能改为调用 Skill 工具

    当一个技能使用另一个技能时，它现在会说 Call the Skill tool with "grilling"，而不是“运行 /grilling 技能“。用叙述性语句点名另一个技能，并不能可靠地加载它。这就是 /grill-with-docs被报告最多的问题的根源。新措辞也与 harness 无关，因为它不依赖 Claude Code 的 / 语法。

    技能不能调用用户调用的技能。所以当某个技能需要 /setup-matt-pocock-skills时，它会让你自己去运行。

    变更：若干小事

    • 六个技能恢复安装。 其中有一个未加引号的冒号出现在 description 的 to-spec, code-review, setup-matt-pocock-skills, writing-fragments, writing-shape 和 wait-what 字段里，导致 YAML 非法，于是 npx skills 把它们跳过了。已修复。
    • 不再用长破折号（em-dash）。 仓库里的每个长破折号都手工改写了。
    • /grilling 在每一轮的问题之间插入一条水平分隔线。
    • /domain-modeling 现在会在你讨论代码库术语，或编辑 GLOSSARY.md 或 ADR 时触发。
    • /diagnosing-bugs 不再在结尾移交给 /improve-codebase-architecture 。那一步很少触发。第 6 阶段现在只做清理。
    • /wait-what 会循着 GLOSSARY-MAP.md 找到对应的 GLOSSARY.md （在含有多个上下文的仓库里）。
