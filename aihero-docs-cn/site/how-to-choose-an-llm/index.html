    选型 LLM 前要问的 5 个问题

    了解为你的 AI 应用选对 LLM 的最佳方法：开源与闭源模型、成本、延迟以及托管选项。

    Matt Pocock

    选对模型是 AI 应用成败的关键。但这并不是一个容易的决定。

    这是一个艰难而多层次的决策，而且不是只做一次。你得 反复做出 这个决定，因为新模型会不断涌现，你的应用也会不断演进。

    我把这个决策拆成了几个关键问题，选模型时你需要问问自己。

    1. 该用开源模型还是闭源模型？

    你需要从两大类模型中做选择： 开源 和 闭源.

    开源模型

    开源模型可以自由下载和使用。不过，如果你想用它们构建应用，就需要自己托管并运行。

    开源模型可以跑在自己的硬件上，也可以跑在 AWS 或 Azure 这类云服务商上。

    要寻找开源模型， Open LLM Leaderboard 是个好去处。

    闭源模型

    闭源模型由公司掌控。使用需要付费，但它们由该公司托管，所以你不必操心自己运行的问题。

    目前世界上最强大的模型都是闭源的。但开源模型一直在进步。

    Chatbot Arena 是对比闭源与开源模型的好地方。

    模型提供商、API 提供商与自托管模型

    有两类公司为你托管模型供你使用：

    模型提供商（模型提供商s） 使用闭源模型。你为使用其模型付费，模型由公司托管。其中包括 OpenAI、Google、Anthropic、Deepseek 等众多公司。

    API 提供商（API providers） 托管开源模型，并收取使用费用。其中包括 Hugging Face、Groq 等。

    你也可以自托管模型。这是最灵活的选项，但也最昂贵。你需要为运行模型的硬件付费，并且要负责让它持续运转。

    2. 花费是多少？

    你为 LLM 使用付费的方式，取决于模型是否由你自己托管。

    按 token 计费

    大多数模型提供商按 token 计费。用的 token 越多，付得越多。最常见的表述是“每 100 万 token 的价格（cost per 1m tokens）”。

    你要付费的不只是 输入 token （你对模型说的话），还包括补全 token（completion tokens，即模型的回复）。

    这是一种传统的“按用量付费”模式——就像 serverless 平台按计算时长收费一样。token 是衡量模型使用量的合理指标。

    随着各公司争夺市场份额，token 价格正在全球范围内竞相探底。像 Helicone's 这样的价格对比网站，用来比价很实用。

    托管开源模型

    托管开源模型可能是更具性价比的选择。你不再按 token 付费，而是支付一笔固定的托管费用。

    这还有一个好处：你的数据完全由自己掌控。出于数据驻留和隐私方面的考虑，这一点可能很重要。

    不过，模型需要托管在强大的硬件上，这可能很贵。你需要权衡自托管模型的成本与使用 模型提供商.

    我的总体建议是从第三方 API 起步。它们最灵活，性价比也不错。之后如有需要，再转向自托管模型。

    3. 延迟有多重要？

    另一个需要考虑的重要特性是 延迟（latency）。延迟是模型响应查询所需的大致时间。快速响应在许多用例中都至关重要，能让你的应用对用户更有用。

    延迟受 模型大小 的影响——模型越小运行越快，但往往不够准确。

    延迟还受模型运行所在的 硬件 影响。更强大的硬件能让模型跑得更快。

    最后，它还受对模型所做的任何 推理优化 的影响。这有助于加速模型的推理过程。优化手段包括量化、蒸馏与并行化——这已略超出本文的讨论范围。

    测量延迟

    测量延迟时主要看两个指标：

    • TTFT：首 token 时间（Time to first token）：模型开始生成响应所需的时长
    • TPOT：单个输出 token 耗时（Time per output token）：模型生成每个 token 所需的时长

    4. 如何评估模型表现？

    成本和延迟固然重要，但如果模型完不成所需任务，它就毫无用处。

    一般来说，模型越小表现越差。更小的模型参数更少，可用来存储信息的空间也更小。

    公开基准测试

    模型表现是一个很难衡量的指标。要看着两个模型就断言哪个更好，极其困难。

    模型提供商（和开源项目）常用的做法是使用基准测试（benchmark）。这是衡量模型在特定任务上表现的标准化测试，可以给模型在翻译、摘要、问答或编码等任务上打分。

    基准测试是模型表现的早期参考。但始终存在提供商针对基准测试过拟合模型的风险：可能是模型在预训练时意外吞下了基准数据，也可能是组织内部为刷高基准分数施加的压力。

    在有些基准测试中，模型之间相互比较——由人来评判哪个模型的输出更好。 Chatbot Arena 就是一个典型的例子——想提早了解模型表现，值得一看。

    专用模型

    有些模型在特定任务上表现更好。这往往取决于模型的训练数据——如果在大量代码示例上训练过，它在编码任务上就会更强。许多领域都是如此：翻译、分类、摘要等等。

    如果你有专门的任务，值得寻找为该任务专用的模型。它们通常胜过通用模型，而且往往更小——因此更快、更高效。

    推理模型

    有些模型被专门设计为在给出回答前先停顿思考。它们属于 推理（reasoning） 类模型，这一趋势由 OpenAI 的 o1 开创。

    这类模型在需要前瞻规划和批判性思考的任务上往往表现更好，比如编码和数学题。它们还会用推理 token 输出自己的规划过程，实时流式展示给用户会很有用。

    不过，它们通常比普通模型更贵，响应也更慢。这是一种性能与延迟之间的权衡。

    评测（eval）

    真正评估模型的唯一办法，是在你的应用场景中测试它。这正是为你的系统构建评测如此关键的原因。

    评测（eval） 是一组你在自己系统上运行的基准测试。它们让你看到系统随时间是在改进还是退化。我们稍后会深入讨论。

    5. 我需要多大的上下文窗口？

    要寻找开源模型， 上下文窗口（context window） 是模型一次能看到的 token 数量。上下文窗口越大，模型生成下一个词时能利用的信息就越多。

    这一上限按 token 计数，输入和补全 token 都算在内。传给模型的输入过长（或强迫它生成过长的响应），可能触发 API 报错，或让它无法生成响应。

    上下文窗口的大小与模型生成文本的机制有关，因此与模型本身的设计绑定在一起。上下文窗口一直在变大。目前，Gemini 系列模型拥有最大的上下文窗口。

    由于所有模型的上下文窗口都是有限的，管理上下文窗口成了 AI 工程师的持久战。RAG 中的分块（chunking）等模式，就是为了把更多信息塞进上下文窗口而设计的。

    结论

    选模型时，这五个因素很重要：

    • 开源还是闭源
    • 成本
    • 延迟
    • 性能
    • 上下文窗口

    排行榜和基准测试是不错的起点。但真正评估一个模型是否适合你，唯一的办法是带着自己的评测（eval），在你的应用里做实验。
