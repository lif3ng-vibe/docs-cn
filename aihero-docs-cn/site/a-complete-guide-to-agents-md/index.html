    AGENTS.md 完全指南

    了解如何为 AI 编码智能体优化你的 AGENTS.md 文件。掌握渐进披露，让指令保持聚焦，最大化智能体表现。

    你是否曾为你 AGENTS.md 文件的大小感到担心？

    也许你真该担心。一个糟糕的 AGENTS.md 文件会让你的智能体困惑，变成维护噩梦，还会在每次请求中烧掉你的 token。

    所以你最好知道怎么修。

    AGENTS.md 是什么？

    一份 AGENTS.md 文件是你提交进 Git 的 Markdown 文件，用来自定义 AI 编码智能体在你仓库中的行为。它位于对话历史的最顶端，紧挨着 系统提示词（system prompt）.

    把它想成智能体基础指令与你的实际代码库之间的一层配置。这个文件可以包含两类指引：

    • 个人层面：你的提交风格偏好、你偏好的编码模式
    • 项目层面：项目是做什么的、你用哪个包管理器、你的架构决策

    这份 AGENTS.md 文件是开放标准，许多工具都支持——尽管不是全部。

    CLAUDE.md

    值得注意的是，Claude Code 并不使用 AGENTS.md ——它用的是 CLAUDE.md 。你可以在两者之间建符号链接（symlink），让所有工具保持一致：

    # Create a symlink from AGENTS.md to CLAUDE.md

    ln -s AGENTS.md CLAUDE.md

    为什么庞大的 AGENTS.md 文件是个问题

    有一个天然的反馈回路会让 AGENTS.md 文件危险地膨胀：

    1. 智能体做了你不满意的事
    2. 你加一条规则防止它
    3. 几个月里重复上百次
    4. 文件变成"泥球"

    不同的开发者加入互相冲突的意见，没人做过整体风格梳理。结果呢？一团无法维护的乱麻，实际还会损害智能体的表现。

    另一个罪魁祸首：自动生成的 AGENTS.md 文件。永远不要用初始化脚本自动生成你的 AGENTS.md。它们会往文件里塞满"对大多数场景有用"的东西，而这些本该通过渐进披露来提供。自动生成的文件追求大而全，不懂得克制。

    指令预算

    Humanlayer 的 Kyle 在他的 文章 中提到了"指令预算"的概念：

    前沿的思考型 LLM 能以不错的稳定性遵循约 150-200 条指令。小模型能兼顾的指令比大模型少，非思考型模型能兼顾的指令又比思考型模型少。

    你 AGENTS.md 文件里的每个 token 都会在 每一次请求时加载，不管它相不相关。这就造成一个严苛的预算问题：

    场景影响
    小而聚焦 AGENTS.md有更多 token 可用于任务相关指令
    大而臃肿 AGENTS.md留给实际工作的 token 更少；智能体会犯迷糊
    无关指令token 浪费 + 智能体分心 = 更差的表现

    综合起来，这意味着 理想的 AGENTS.md 文件应该尽可能小。

    过期文档毒化上下文

    大 AGENTS.md 文件的另一个问题是过期。

    文档很快就会过时。对人类开发者来说，过时文档很烦人，但人通常有足够的内在记忆去怀疑糟糕的文档。而对每次请求都读文档的 AI 智能体来说，过时信息会实实在在地 毒化 上下文。

    当你把文件系统结构写进文档时尤其危险。文件路径经常变。如果你的 AGENTS.md 写着"认证逻辑在 src/auth/handlers.ts"，而那个文件被重命名或移动了，智能体会自信满满地去错误的位置找。

    别记录结构，去描述能力。给出事物 可能 在什么位置的提示，以及项目整体形态。让智能体在规划时自己生成即时文档。

    领域概念（比如"organization"、"group"、"workspace"的区别）比文件路径稳定，写进文档更安全。但在快速演进的 AI 辅助代码库里，连它们也会漂移。下手要轻。

    精简庞大的 AGENTS.md 文件

    对写进这里的内容要狠心。把下面这些当作绝对底线：

    • 一句话项目描述 （相当于一条基于角色的提示）
    • 包管理器 （如果不是 npm；或者用 corepack 来做警告）
    • 构建/类型检查命令 （如果不是标准命令）

    说真的，就这些。其他一切都应该放到别处。

    一句话项目描述

    这一句话给智能体提供了关于 为什么 要在这个仓库里工作的背景。它锚定智能体做出的每一个决策。

    示例：

    This is a React component library for accessible data visualization.

    这就是地基。智能体现在明白自己的边界了。

    包管理器声明

    如果你在 JavaScript 项目里用的不是 npm，请明确告诉智能体：

    This project uses pnpm workspaces.

    不写这条，智能体可能默认用 npm ，生成错误的命令。

    Corepack 也很棒 你也可以用 corepack 让系统自动处理警告，为你省下宝贵的指令预算。

    使用渐进披露

    别把所有东西都塞进 AGENTS.md，改用 渐进披露（progressive disclosure）：只给智能体当下需要的东西，需要时再把它指向其他资源。

    智能体在文档层级里导航很快。它们对上下文的理解足以找到所需内容。

    把语言相关的规则移到单独文件

    如果你的 AGENTS.md 现在写着：

    Always use const instead of let.

    Never use var.

    Use interface instead of type when possible.

    Use strict null checks.

    ...

    把它移到一个单独的文件里。在你的根 AGENTS.md:

    For TypeScript conventions, see docs/TYPESCRIPT.md

    注意这里的轻描淡写：没有"always"，没有全大写强令，只有一句对话式的引用。

    好处：

    • 只有当智能体写 TypeScript 时才加载 TypeScript 规则
    • 其他任务（调试 CSS、管理依赖）不浪费 token
    • 文件保持聚焦，换模型也能通用

    嵌套渐进披露

    你还可以更进一层。你的 docs/TYPESCRIPT.md 可以引用 docs/TESTING.md。构建一棵可发现的资源树：

    docs/

    ├── TYPESCRIPT.md

    │   └── references TESTING.md

    ├── TESTING.md

    │   └── references specific test runners

    └── BUILD.md

        └── references esbuild configuration

    你甚至可以链接到外部资源：Prisma 文档、Next.js 文档等。智能体会高效地在这些层级间穿行。

    使用 Agent 技能

    许多工具支持"agent 技能"——智能体可以调用的命令或工作流，用来学习如何完成某件具体的事。这是 渐进披露（progressive disclosure）的另一种形式：智能体只在需要时才拉取知识。

    我们会在单独的一篇文章里深入讲 agent 技能。

    AGENTS.md 在 monorepo 中

    你不必只限于根目录的一个 AGENTS.md 。你可以在子目录放置 AGENTS.md 文件，它们会 与根层合并.

    这对 monorepo 很有用：

    什么放哪里

    层级内容
    根目录monorepo 的用途、如何在包之间导航、共享工具（pnpm workspaces）
    包包的用途、具体技术栈、包专属约定

    根目录 AGENTS.md:

    This is a monorepo containing web services and CLI tools.

    Use pnpm workspaces to manage dependencies.

    See each package's AGENTS.md for specific guidelines.

    包级 AGENTS.md （位于 packages/api/AGENTS.md):

    This package is a Node.js GraphQL API using Prisma.

    Follow docs/API_CONVENTIONS.md for API design patterns.

    任何一层都别超载。 智能体看到的是合并后的全部 AGENTS.md 文件。每一层都只写与该范围相关的内容。

    修复坏掉的 AGENTS.md ：试试这条提示词

    如果你开始为 AGENTS.md 文件感到不安，想把它重构成渐进披露式，试试把这条提示词复制给你的编码智能体：

    I want you to refactor my AGENTS.md file to follow progressive disclosure principles.

    

    Follow these steps:

    

    1. **Find contradictions**: Identify any instructions that conflict with each other. For each contradiction, ask me which version I want to keep.

    

    2. **Identify the essentials**: Extract only what belongs in the root AGENTS.md:

       - One-sentence project description

       - Package manager (if not npm)

       - Non-standard build/typecheck commands

       - Anything truly relevant to every single task

    

    3. **Group the rest**: Organize remaining instructions into logical categories (e.g., TypeScript conventions, testing patterns, API design, Git workflow). For each group, create a separate markdown file.

    

    4. **Create the file structure**: Output:

       - A minimal root AGENTS.md with markdown links to the separate files

       - Each separate file with its relevant instructions

       - A suggested docs/ folder structure

    

    5. **Flag for deletion**: Identify any instructions that are:

       - Redundant (the agent already knows this)

       - Too vague to be actionable

       - Overly obvious (like "write clean code")

    别把文件堆成泥球

    当你准备往 AGENTS.md里加东西时，问问自己它属于哪里：

    位置何时使用
    根目录 AGENTS.md与仓库里每一个任务都相关
    单独文件与某个领域相关（TypeScript、测试等）
    嵌套文档树可以按层级组织

    理想的 AGENTS.md 小而聚焦，并指向别处。它给智能体刚好够用的上下文以启动工作，同时留下通往更详细指引的面包屑。

    其他一切都放在渐进披露里：单独文件、嵌套的 AGENTS.md 文件，或技能。

    这让你的指令预算高效、智能体专注，也让你的配置在工具和最佳实践演进时经得起未来。
