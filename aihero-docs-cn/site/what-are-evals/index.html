    你的应用只会和它的评测（eval）一样好

    你怎么知道自己的 AI 应用是不是在产生幻觉？如何确保它输出的是你想要的东西？答案就是评测（eval）。

    Matt Pocock

    正如我们在 上一篇文章中所讨论的，用 LLM 做开发需要你对软件开发的基本认知来一次转变。你不再设计输入映射到可预测输出的确定性系统，而是在与本质上不可预测的概率性系统打交道。

    管理这种不确定性的关键工具就是评测。评测是 AI 工程师的单元测试。它是你从概率性系统中“驯”出可预测性的手段，也是任何 AI 应用走向生产环境不可或缺的一环。

    我们来拆解一下评测是什么，以及 AI 应用为什么如此需要它。

    为什么传统测试还不够

    传统软件测试依赖输入与输出之间的确定性关系。每个组件都有清晰的职责范围：

    但 LLM 驱动的系统不同。每个输入都要经过一个难以预测的复杂变换过程：

    在 AI 系统里，没有哪个改动是小事。它们的注意力与变换机制深不可测。蝴蝶的翅膀是“flaps”还是“Flaps”，都可能改变输出。说得委婉些，用它们构建健壮的系统需要格外小心。

    人工 QA 也不够

    快速做出一个令人眼前一亮的 AI demo 很容易。但把那个 AI 系统推进生产环境并不容易。

    具体来说，你很难判断自己对应用的改动究竟是在变好还是变坏。你改了一处，试几个自己偏爱的提示词，看看“感觉”是否更好。但这样工作很危险。

    在确定性软件里，“只靠人工 QA”通常行得通。你说“我加了一个新页面”，QA 团队就能严格测试新页面，并对之前的页面做冒烟测试。

    但在概率性系统里，这是致命的。当任何改动都可能影响整个系统时，你需要一种办法来判断系统是在变好还是变坏。

    对大型改动尤其如此，比如换用哪个模型，或者提示词的设计。

    评测（eval）

    关键在于自动化。每次改动应用，或每次底层模型变化时，我们都需要评估应用。

    传统的确定性系统

    在确定性系统里，自动化测试相对直接。你可以喂入一些输入，然后检查输出。

    const output = myNormalSystem(input);

    

    // Will fail if the output doesn't match

    assert(output === "my-desired-output");

    这些断言要么“通过”要么“失败”。通常，应用必须通过每一项测试，才算达到生产就绪。

    概率性系统

    但为 AI 编写这些测试就没那么直接了。

    假设你的应用生成文章。你想检查输出是否好到足以投产。你可能需要为以下方面编写断言：

    • 事实准确性：检查输出中的所有陈述是否属实
    • 文风：确保文本优雅、行文良好
    • 提示词保真度：确保输出切实对应用户的要求。

    这些是定性指标。它们不是通过/不通过的判定，而需要用一个 分数来表示。每次改动应用，你都需要知道这次改动让系统变好了 5%，还是变糟了 50%。

    这正是评测做的事——它给你一个分数，让你了解 AI 系统表现如何。

    评测的三种类型

    你可以在 AI 系统上运行三种主要类型的评测。

    确定性评测

    其中包括 确定性评测（deterministic evals），它们可以写成简单的断言。

    const article = writeArticleWithLLM(prompt);

    

    // Article should be more than 300 words long

    assert(article.length >= 300);

    

    // Article should be less than 2,000 words long

    assert(article.length <= 2000);

    这些是传统的通过/不通过检查。你会把各种各样的提示词送进系统，逐一检查它们是否通过这些测试。

    它们写起来简单，但只能覆盖你想评估内容的一个子集。

    人工评估

    对于更偏概率性的指标，你有两个选择。

    你可以用人工评估来检查系统是否表现正常。在早期数据不多的时候，这往往是唯一的选择。

    这既昂贵又耗时——但所有 AI 系统都会在一定程度上依赖人工输入。

    LLM 即裁判

    另一种技术是把提示词的结果交给另一个 LLM，让它充当 裁判（LLM as a judge）。这是目前非常流行的一种 AI 系统评估方式。

    假设你想确保应用说的是真话。你可以把系统的输出连同一些标准答案（ground truth）一起传给一个 LLM。

    关于这一点， Evalite 文档中有一个实际运用的例子。

    LLM 即裁判让某些评测成为可能——但代价不菲。运行 LLM 很贵，所以你需要仔细考虑以什么频率来跑。比如每次文件一变就跑一遍评测，成本会高得离谱。

    常见的策略是把评测拆成两组——一组较小的用于本地测试，另一组较大的每天运行一次。

    如何随时间改进评测？

    评测是你监测和改进 AI 系统的手段。这也意味着，你用来评估系统的数据集至关重要。

    你需要确保评测能代表系统在生产环境中会看到的数据。如果你在构建一个分类器，就要确保评测覆盖系统会遇到的全部边界情况。

    这意味着，在你的应用中内建可观测性与反馈系统至关重要。应用一旦部署，你的用户就是评判系统是否正常工作的裁判。点赞、点踩这类简单的反馈按钮，能为你提供关于系统表现的极有价值的洞察。

    数据飞轮

    Vercel 是 v0的缔造者，他们曾撰文写过 AI 原生飞轮（AI Native Flywheel）。他们阐述了评测在 AI 开发流程中的重要性。

    评测所需的最好数据来自你的用户。仔细观察用户如何使用你的应用，你就能建立起一个反馈回路，帮助自己随时间不断改进系统。举个例子：

    • A 用户让 应用“帮我构建一个有格调的 React 应用”
    • 你的应用 生成了一些 React 代码。但它没有让 UI 看起来“有格调”，反而在代码里用起了 class。
    • 用户对 这个回复点了踩。也许还会留言解释原因。
    • 你拿到提示词“帮我构建一个有格调的 React 应用”， 为它新建一条评测 ，并把它加进自己的评测套件。
    • 你 持续改进系统 ，直到它通过这条评测。
    • 你 重新部署。下一个命中这条提示词的用户，就会得到更好的回复。

    这就是数据飞轮的运转方式。仔细监测你的系统，并在其中构建反馈回路，就能确保系统持续改进。

    如何运行评测？

    运行评测的方法有很多。大量创业公司已经涌入这个领域，提供在线运行和查看评测的工具。

    Braintrust 是一个热门选择。他们提供了一个云平台，可用于运行评测、与团队共享结果，还有许多其他功能。你可以用他们的 SDK 以 TypeScript 编写评测。不过他们对评测设有速率限制——在你想要快速迭代时，这会让人恼火。

    我维护着一个名为 Evalite的库，它是一个轻量级评测运行器，基于 TypeScript 测试 runner Vitest.

    Evalite 的设计初衷是让你在本地运行评测。它没有捆绑云平台，所以你想跑多少次都可以。如果你刚刚起步，它是个不错的选择。

    评测在实践中如何运作

    不妨把一条评测想象成一个函数：

    const score = runEval({

      // 1. The prompts we'll test with

      data: [

        "Fish species in the Mediterranean",

        "Story of the first Moon landing",

        "Are Krakens real?",

      ],

      // 2. A function to generate outputs based

      // on our prompts

      task: async (topic) => {

        return generateArticle(topic);

      },

      // 3. The scorers we'll use to generate

      // the final score

      scorers: [

        // Checks if output is long enough

        length,

        // Uses an LLM to check if it's accurate

        factualAccuracy,

        // Uses an LLM to check writing style

        writingStyle,

      ],

    });

    

    // 4. A score between 0-100%

    console.log(score);

    我们传入一组提示词（1），接着传入要运行的任务（2），再传入用来给输出打分的方法（3）。

    最后，我们会拿到一个反映该函数表现如何的分数（4）。

    归根结底，这就是评测的本质。这个 API 大致借鉴了 Braintrust 的 autoevals 库.

    关键就是评测

    这张基于 Vercel AI 原生飞轮的图片，展示了评测对你的应用的影响。

    它们应当成为你反馈回路的中心。越多用户使用你的应用（分发），你就会得到越多数据（使用）。你可以用这些数据改进应用（数据），然后再跑一遍评测（评测）。

    这些评测让你能够应对新技术与新模型，并让你始终走在持续改进的路上。
