    它做什么

    grill-with-docs 就一份计划或设计对你展开访谈，直到你与 智能体 对它达成同一种理解为止，并且在此过程中把词汇和棘手决策写进你的仓库。它就是 grill-me 运行的那场访谈（一轮问题，然后等待，再下一轮），只不过对准了一个代码库。

    它是 有状态（stateful）的。其他每一个 追问（grilling） 类技能都把 会话 留在你脑子里；这一个却把文件留在磁盘上。一个术语敲定时，技能立刻把它写进 GLOSSARY.md ，而不是最后打包写入。当一个决策通过三道关卡，技能会把它写成一份 ADR。这就是全部差别，也是人们使用这项技能时大多数麻烦的来源。这些产物是真实仓库里的真实文件，所以它们可能在你期待时缺席，也可能在多个人同时写入时彼此漂移。

    何时使用

    使用方式是输入 /grill-with-docs，智能体不会自己主动调用它。

    在一次变更开始时、在一个仓库里使用它——此时计划还模糊，指称这件事的词还没定下来。它是单会话工具。追问类技能该用哪个，取决于你面前是什么：

    你手头的情况该用什么
    你根本不在一个工作目录里工作grill-me
    有一个仓库，且是一次会话就能谈定的变更grill-with-docs
    工作量大于一个会话的容量（全新构建、大型功能）wayfinder
    有一个完全没有领域文档的仓库，且没有特定的功能目标grill-with-docs，对准整个仓库而不是某次变更
    一个被别人脑子里的知识阻塞的决策to-questionnaire

    wayfinder 的分界归结为会话数量： /grill-with-docs 用于单会话规划， /wayfinder 用于多会话规划。

    前置条件

    这项技能会写进你的仓库，所以你得待在一个写入安全的地方。敲定的术语进入根目录的 GLOSSARY.md 词汇表，或相关上下文自己的 GLOSSARY.md，如果根目录的 GLOSSARY-MAP.md 把该仓库标记为多上下文。决策则进入 docs/adr/。这两样东西只会在技能需要时才创建。在第一个术语或决策敲定之前什么都不存在，所以你无需提前做任何设置。

    它还需要另外两个技能在场，因为它自己的 SKILL.md 只有一行，内容就是把工作委托给它们。 追问（grilling） 提供访谈， domain-模型ing 负责落笔。只安装 grill-with-docs 的话，你得到的是一个跑不起来的技能。

    纸面记录

    一场会话产出三样东西，它们的分量并不相同。

    敲定了什么落在哪里
    一个术语：项目对某个事物自己的叫法GLOSSARY.md，当场就地写入，敲定的那一刻就落笔
    一个难以逆转、缺少上下文会令人意外、且是真实权衡的决策下的一份 ADR docs/adr/
    你决定的其他一切只留在对话里，别处皆无

    让人栽跟头的是第三行。 GLOSSARY.md 只是一份词汇表。它不含实现细节、不含 规格（spec），也没有随手笔记。一份 ADR 需要同时满足全部三个条件，所以大多数决策不够格，大多数会话一份也不产出。一场会话得到一份更锐利的词汇表和零份 ADR，这正是设计之内的正常表现；但这意味着你们谈定的东西大部分只存在于 上下文窗口（context window） 里——也就是你们谈定它的那个窗口。把同一段对话交给 to-规格（spec） ，而不是 清空（clearing） 它。

    词汇表才是主要产出。这项技能构建的是领域语言：项目自己的词，一次性谈定，让你、智能体和同事们不必再各自琢磨。并不是所有人都认为这能提升智能体的表现。最有力的反对意见是：一个术语和它的大白话展开，从 模型那里得到的结果是一样的，这套词汇主要缩短的是共享它的人类之间的沟通。按这种观点，词汇表仍然有价值，但价值归人类。

    常见问题

    我该用这个还是 /wayfinder? 看范围。一次会话能谈定的都用这个；工作量超出一个会话时用 wayfinder ，它会先把工作绘成一张由决策 工单（ticket） 组成的地图。wayfinder 更慢也更笨重，在范围明确的功能上用它是最常见的错误。它不取代这项技能，而且可以让地图中适合追问的部分开一场追问会话。

    它跑了，但没有出现 GLOSSARY.md ，也没有任何 ADR 出现。 已知有两个原因。第一个是什么都不够格。ADR 需要全部三道关卡，一场没有产生新词汇的变更会话无东西可写。第二个是一个真实的缺陷。当这项技能在另一个编排层里运行（规格（spec） 驱动开发的包装器、多智能体框架、把它当作别人流水线里一步来调用的规则），用户报告写文件的那一半悄无声息地没有发生，而访谈照常进行。缺陷已提交，尚未修复。如果你处于那种环境，在信任会话产出之前先检查工作目录。

    它把所有问题一口气全抛出来，没有推荐答案，也从不提 GLOSSARY.md. 这是技能没能加载它的两个依赖。因为 SKILL.md 只有一行委托，一个没有接住 追问（grilling） 和 domain-模型ing 的智能体只能瞎猜追问是什么意思，于是你收到的是一口气全来、毫无结构的问题。部分加载更让人迷惑： grilling 加载了， domain-modeling 没加载，你就会得到一场没有纸面记录的好访谈。发生频率取决于模型与 用力度（effort） 档位，这是该技能被报告最多的问题。如果你怀疑发生了，直接问智能体它加载了哪些技能。

    我其他那些决策都去哪了？ 只存在于对话里。这是关于该技能最严重的公开抱怨。词汇表不是规格（规格（spec）），大多数答案得不到 ADR，也没有任何记录把每个敲定的答案与一份规格、一张工单和一个测试关联起来。后面的步骤会把精确的答案（顺序保证、反向要求、数值默认值）软化成更弱的散文，结果可能看起来完整，却丢掉了你真正决定的东西。目前，请保留会话并直接喂给 to-规格（spec）。然后对照你自己的回答重读那份规格，而不要假设它已经全部捕获。

    我能把它指向一个完全没有文档的既有仓库吗？ 可以。对一个没有 ADR、没有领域语言、也没有设计原则的代码库，这就是合适的技能：调用它，说“帮我给我的仓库写文档”。用户常常把它与 improve-codebase-architecture 搭配使用，用来构建或修复 GLOSSARY.md。要有心理准备去掌舵。它读代码并就发现的东西来问你，由你决定代码库里已有的词哪些才是对的。

    会话结束时我该做什么？ 技能的收尾消息常常是开放式的，这是一个已知问题。在主流程里，答案是 to-规格（spec），就在同一对话里进行。如果变更小到可以立刻构建，那就跳过它，直接 implement 。

    它为什么叫这个名字？ 没人对这个名字满意。有人公开提议把它改名为 grill-domain-model，这个名字描述行为更准确。目前毫无进展。如果改名真的落地，文档页会跟着改名，URL 也会变。

    生效判据

    • GLOSSARY.md 会 期间 逐个术语地持续变化，而不是最后一次性整坨出现。
    • 词汇表读起来是纯粹的词汇（你项目的词配紧凑定义），不含实现细节或规格式的散文。
    • 代码库能回答的问题，靠读代码库得到答案，而不是拿来问你。
    • 你得到的 ADR 很少甚至为零，而得到的那些，都是你不想再争论一遍的决策。
    • 它会挑战你用的某个词，因为你现有的词汇表对它的定义不一样。

    适用位置

    grill-with-docs 是主构建链条的头部：

    grill-with-docs → to-spec → to-tickets → implement → code-review → retro

    它位于任何东西被写成规格（规格（spec））之前。它产出共享的理解和敲定的词汇， to-规格（spec） 随后据此综合成文，无需再访谈你一遍。它的近邻是 grill-me（同一场访谈，但无仓库、无文件），以及 domain-模型ing（它所驱动的那套词汇表加 ADR 纪律）；两者都用 追问（grilling） 这个原语来做访谈。在它上游， wayfinder 负责绘制大到一个会话装不下的工作，并能把地图的一部分交回给它。当你拿不准哪个技能或流程合适时， ask-matt 会为你指路。
