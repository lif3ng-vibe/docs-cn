    S和castle 使用一套灵活的提示词系统。你写提示词，引擎负责执行——它不会强加任何关于工作流、任务管理或上下文来源的成见。

    提示词解析

    你必须且只能提供以下两者之一：

    1. prompt: "inline string" ——传入内联提示词，经由 RunOptions
    2. promptFile: "./path/to/prompt.md" ——指向具体文件，经由 RunOptions

    prompt 和 promptFile 互斥——同时提供两者是错误。如果两者都未提供， run() 会抛错并要求你提供其中之一。

    内联提示词（prompt: "..."）会原样传给智能体。 不做 {{KEY}} 替换，不做 !`command` 展开，也不内置注入 {{SOURCE_BRANCH}} / {{TARGET_BRANCH}} 。如果你需要把值插值进内联提示词，请在 JavaScript 里自己拼好字符串（`Work on ${branch}…`）。在内联提示词之外再传 promptArgs 是错误的——想用替换就改用 promptFile 。

    下文的替换与展开特性 只 作用于来自 promptFile.

    约定

    sandcastle init 会生成 .sandcastle/prompt.md ，而且所有模板都通过 promptFile: ".sandcastle/prompt.md"显式引用它。这只是约定，不是自动回退——S和castle 不会读取 .sandcastle/prompt.md ，除非你显式将其作为 promptFile.

    动态上下文： !`command`

    在提示词中使用 !`command` 表达式来拉取动态上下文。每个表达式都会在提示词发送给智能体之前，被替换为对应命令的 stdout。一条提示词里的所有表达式 并行 运行，以加快展开速度。

    命令 在沙箱内 运行，且要在 sandbox.onSandboxReady hook 完成之后才执行，因此它们看到的仓库状态与智能体相同（包括已安装的依赖）。

    # Open issues

    

    !`gh issue list --state open --label Sandcastle --json number,title,body,comments,labels --limit 100`

    

    # Recent commits

    

    !`git log --oneline -10`

    任何一条命令以非零码退出，运行都会立即报错失败。

    提示词参数： {{KEY}}

    在提示词中使用 {{KEY}} 占位符，把 promptArgs 选项中的值注入进来。这适合用不同参数在多次运行中复用同一个提示词文件。

    import { run } from "@ai-hero/sandcastle";

    

    await run({

      promptFile: "./my-prompt.md",

      promptArgs: { ISSUE_NUMBER: 42, PRIORITY: "high" },

    });

    提示词文件中：

    Work on issue #{{ISSUE_NUMBER}} (priority: {{PRIORITY}}).

    提示词参数替换在宿主机上进行，先于 shell 表达式展开，所以 {{KEY}} 占位符若出现在 !`command` 表达式中，会先被替换：

    !`gh issue view {{ISSUE_NUMBER}} --json body -q .body`

    A {{KEY}} 占位符找不到对应的提示词参数是错误。未被使用的提示词参数会产生警告。

    !`command` 展开只作用于提示词文件中编写的 shell 块。参数值里出现的任何 !`…` 模式都会被视为惰性文本——不会拿到宿主机 shell 上执行。因此可以放心地把用户撰写的内容（issue 标题、PR 描述、文档摘录）通过 promptArgs.

    内置提示词参数

    S和castle 会自动向每条提示词注入两个内置提示词参数：

    占位符值
    {{SOURCE_BRANCH}}智能体工作的分支（由分支策略决定）
    {{TARGET_BRANCH}}宿主机在 run() 调用时刻所处的活动分支

    在提示词里直接使用它们，不必通过 promptArgs:

    You are working on {{SOURCE_BRANCH}}. When diffing, compare against {{TARGET_BRANCH}}.

    把 SOURCE_BRANCH 或 TARGET_BRANCH 放进 promptArgs 是错误的——内置提示词参数不可覆盖。

    提前终止： <promise>COMPLETE</promise>

    当智能体输出 <promise>COMPLETE</promise>时，编排器会提前终止迭代循环。这是一个由你在提示词中写明、让智能体遵循的约定——引擎绝不会注入它。

    这对基于任务的工作流很有用：智能体完成即停，而不是把剩余的迭代全部跑完。

    你可以传入 completionSignal 给 run()来覆盖默认信号。它接受单个字符串或字符串数组：

    await run({

      // ...

      completionSignal: "DONE",

    });

    

    // Or pass multiple signals — the loop stops on the first match:

    await run({

      // ...

      completionSignal: ["TASK_COMPLETE", "TASK_ABORTED"],

    });

    在提示词中让智能体输出你选定的字符串（一个或多个），编排器检测到其中任何一个就会停止。匹配到的信号会存放在 result.completionSignal.

    完成信号之后的挂起进程

    智能体进程应当在发出完成信号后很快退出。当它派生的某个子进程——比如 gh或 git 子进程、长期存活的 MCP 服务器等——继承了智能体的 stdout 管道并保持打开时，父进程可能会在逻辑终点之后徘徊很久。这种情况若不处理，S和castle 会等满 idleTimeoutSeconds ，然后以 AgentIdleTimeoutError失败，智能体已经完成的提交也会被丢掉。

    实际上，一旦在输出缓冲中观察到完成信号，S和castle 就会换上一个较短的 完成超时（completion 调用时刻所处的活动分支out） （默认 60 秒）。超时一到，运行会带着“进程挂起”的警告成功返回； result.commits 和 result.completionSignal 都会像进程干净退出一样被填充。计时器在随后每一行输出时都会重置，因此信号之后尾随的数据——给ken 用量事件、终端 result 事件、某个结构化输出 <tag> ——仍会被捕获。

    进程干净退出总会赢下这场竞争，因此健康运行不会增加任何延迟。完成超时只在进程挂起时才起作用。

    用以下选项调整时间窗口： completionTimeoutSeconds:

    await run({

      // ...

      completionTimeoutSeconds: 30, // shorter grace window

    });

    这与 idleTimeoutSeconds相互独立。两者覆盖不同的阶段： idleTimeoutSeconds 在任何信号出现 之前 运行（智能体真的卡死 → 判失败）； completionTimeoutSeconds 在任何信号出现 运行，且要在 之后运行（进程挂起 → 带警告判成功）。参见 ADR 0019.

    结构化输出

    在提示词中使用 Output.object() 从智能体的 stdout 提取带类型、经 schema 校验的 JSON 载荷。智能体在你指定的 XML 标签内给出答案，S和castle 负责解析、校验并放到 result.output上返回。schema 可以是任何 St和ard Schema 校验器——下文示例使用 Zod，但 Valibot、ArkType 等也都同样可用。设计考量参见 ADR 0010 。

    import { run, Output, claudeCode } from "@ai-hero/sandcastle";

    import { docker } from "@ai-hero/sandcastle/sandboxes/docker";

    import { z } from "zod";

    

    const result = await run({

      agent: claudeCode("claude-opus-4-8"),

      sandbox: docker(),

      prompt: `Analyze the code, and output the result as JSON inside <result> tags.

        The result must match this schema:

        { summary: string; score: string }

      `,

      output: Output.object({

        tag: "result",

        schema: z.object({ summary: z.string(), score: z.number() }),

      }),

    });

    

    console.log(result.output.summary); // typed as string

    console.log(result.output.score); // typed as number

    Output.string({ tag }) 则把标签内容提取为纯字符串（去首尾空白，不做 JSON 解析）。两个辅助方法都要求 maxIterations 为 1 （默认值）。解析后的提示词必须包含所配置的起始标签字面量。

    当提取或校验失败时， run() 会抛出一个 StructuredOutputError。除此之外， tag, rawMatched, cause, commits, branch和 preservedWorktreePath等字段之外，该错误还带有 sessionId （以及 sessionFilePath，仅当会话被捕获时）——它们来自产出这份坏输出的那次运行。

    传入 maxRetries ，让 S和castle 替你打理重试循环。每次重试都会恢复同一个智能体会话，并回馈一段节省 给ken 的错误描述，让智能体无需重做工作即可重新输出修正后的标签。重试要求智能体提供方支持会话恢复（claudeCode, codex, pi）——若在 run() 上以 maxRetries > 0 调用不支持恢复的提供方（cursor, opencode, copilot）会立即抛错。

    const result = await run({

      agent: claudeCode("claude-opus-4-8"),

      sandbox: docker(),

      prompt: "Analyze the code and emit JSON inside <result> tags.",

      output: Output.object({

        tag: "result",

        schema: z.object({ summary: z.string(), score: z.number() }),

        maxRetries: 2, // 2 retries on top of the initial attempt

      }),

    });

    如果你需要手动驱动重试循环——例如自定义反馈提示词，或每次尝试轮换模型——就把 maxRetries 保持在默认值 0 ，然后自己恢复失败的会话：

    import { run, Output, StructuredOutputError } from "@ai-hero/sandcastle";

    

    try {

      return await run({ ...opts, output });

    } catch (e) {

      if (e instanceof StructuredOutputError && e.sessionId) {

        return await run({

          ...opts,

          output,

          resumeSession: e.sessionId,

          prompt: `Your previous output failed: ${e.message}. Re-emit it inside <${e.tag}> tags.`,

        });

      }

      throw e;

    }

    模板

    sandcastle init 会提示你选择沙箱提供方（Docker 或 Podman）、工单追踪器（issue tracker）（GitHub Issues、Beads 或 Cus给m（自定义））以及一个模板；模板会生成一套开箱即用的提示词和 main.mts ，适配特定的工作流。如果你项目的 package.json 包含 "type": "module"，该文件就会命名为 main.ts 。选择 Cus给m（自定义） 会把项目搭成一种“配置好之前故意跑不起来”的状态，外加一份 .sandcastle/SETUP_ISSUE_TRACKER.md 提示词，把它喂给你的编码智能体，由它就地编辑脚手架文件接上你自己的追踪器。共有五个模板可用：

    模板描述
    blank极简脚手架——提示词与编排都自己写
    simple-loop逐个挑选 issue 并关闭它们
    sequential-reviewer逐个实现 issue，每个之后都有一步代码评审
    parallel-planner规划可并行的 issue，在独立分支上执行，然后合并
    parallel-planner-with-review规划可并行的 issue，执行时逐分支评审，然后合并

    在 sandcastle init 过程中按提示选择模板，或者在一个全新仓库里重新运行 放进it 来试用其他模板。
