    sandcastle init

    生成 .sandcastle/ 配置目录并构建容器镜像。这是你在新仓库中运行的第一个命令。init 过程中你要选择一个沙箱提供方（Docker 或 Podman）——选择 Podman 会写入 Containerfile 而不是 Dockerfile ，并使用 sandcastle podman build-image 来执行构建步骤。

    Init 会依据 packageManager 字段或锁文件来检测宿主机的包管理器（npm、pnpm、yarn 或 bun），默认为 npm。如果模板的 main 文件引入了宿主机依赖——planner 模板会引入 Zod 来定义其 <plan> 输出 schema——当它尚未出现在你的 package.json中时，会提示你用该包管理器安装它。这样一来，第一条 npx tsx .sandcastle/main.ts 就不会以 ERR_MODULE_NOT_FOUND.

    每个交互式提示都有一个配套的 --flag ，因此整个 init 都可以非交互式运行（例如在 CI 或脚本化安装中）。当 stdin 不是 TTY 且缺少必需的旗标时，init 会快速失败并给出清晰的错误，而不是卡在提示上。

    选项必填默认值描述
    --image-name否sandcastle:<repo-dir-name>Docker 镜像名
    --agent否交互式提示要使用的智能体（claude-code, pi, codex, cursor, opencode, copilot)
    --model否智能体的默认模型要使用的模型（例如 claude-sonnet-4-6）。默认为智能体的默认模型
    --sandbox否交互式提示要使用的沙箱提供方（docker, podman)
    --template否交互式提示要生成的模板（例如 blank, simple-loop)
    --issue-tracker否交互式提示要使用的工单追踪器（issue tracker）（github-issues, beads, custom)
    --create-label否交互式提示true / false ——是否创建 Sandcastle 这个 GitHub 标签（仅在使用以下选项时生效： --issue-tracker github-issues)
    --build-image否交互式提示true / false ——是否立即构建沙箱镜像（搭配以下选项时会被静默忽略： --issue-tracker custom)
    --install-template-deps否交互式提示true / false ——是否安装模板的宿主机依赖（例如 zod ，planner 模板需要）

    创建以下文件：

    .sandcastle/

    ├── Dockerfile      # Sandbox environment (customize as needed)

    ├── main.mts        # Agent entry point (main.ts in an ESM package)

    ├── prompt.md       # Agent instructions

    ├── .env.example    # Token placeholders

    └── .gitignore      # Ignores .env, logs/, worktrees/

    若 .sandcastle/ 已存在则报错，以防止覆盖你的自定义内容。

    sandcastle docker build-image

    基于已有的 .sandcastle/ 目录重建 Docker 镜像。修改 Dockerfile 后使用此命令。在 Linux/macOS 上，构建会自动传入 --build-arg AGENT_UID=$(id -u) 和 AGENT_GID=$(id -g) ，使镜像中的 agent 用户与宿主机 UID 一致——这样无需在运行时 chown，就能避免镜像构建产物上的权限错误。

    选项必填默认值描述
    --image-name否sandcastle:<repo-dir-name>Docker 镜像名
    --dockerfile否—自定义 Dockerfile 的路径（构建上下文将是当前工作目录）

    sandcastle docker remove-image

    移除 Docker 镜像。

    选项必填默认值描述
    --image-name否sandcastle:<repo-dir-name>Docker 镜像名

    sandcastle podman build-image

    基于已有的 .sandcastle/ 目录构建 Podman 镜像。修改 Containerfile 后使用此命令。

    选项必填默认值描述

    --containerfile否—自定义 Containerfile 的路径（构建上下文将是当前工作目录）

    sandcastle podman remove-image

    移除 Podman 镜像。

    选项必填默认值描述
    --image-name否sandcastle:<repo-dir-name>Podman 镜像名

    RunOptions

    选项类型默认值描述
    agentAgent提供方—必填。 智能体提供方（例如 claudeCode("claude-opus-4-8"), pi("claude-sonnet-4-6"), codex("gpt-5.4"), cursor("composer-2"), opencode("opencode/big-pickle"), copilot("claude-sonnet-4.5"))
    sandboxS和box提供方—必填。 沙箱提供方（例如 docker(), podman(), docker({ imageName: "sandcastle:local" }))
    cwdstringprocess.cwd()宿主机仓库目录——作为 .sandcastle/ 各类工件与 git 操作的锚点。相对路径基于 process.cwd().
    promptstring—内联提示词（与 promptFile)
    promptFilestring—提示词文件路径（与 prompt）。解析基准是 process.cwd(), 而不是 cwd.
    maxIterationsnumber1最多运行的迭代次数
    hooksS和boxHooks—生命周期 hook（host.*, sandbox.*)
    namestring—本次运行的显示名称，会作为前缀出现在日志输出中
    promptArgsPromptArgs—键值映射，用于 {{KEY}} 占位符替换
    branchStrategyBranchStrategy随提供方的默认值分支策略： { type: 'head' }, { type: 'merge-to-head' }，或 { type: 'branch', branch: '…' }
    copyToWorktreestring[]—启动前要复制进沙箱的、相对于宿主机的文件路径（不支持搭配 branchStrategy: { type: 'head' })
    loggingobject文件（自动生成）{ type: 'file', path } 或 { type: 'stdout' }
    completionSignalstring | string[]<promise>COMPLETE</promise>智能体输出用来提前终止迭代循环的字符串或字符串数组
    idleTimeoutSecondsnumber600空闲超时（秒）——每次智能体输出事件都会重置
    completionTimeoutSecondsnumber60观察到完成信号之后、智能体进程尚未退出（进程挂起）时的宽限窗口（秒）。参见 完成信号之后的挂起进程.
    resumeSessionstring—按 ID 恢复先前的会话（适用于支持恢复的智能体）。与 maxIterations > 1不兼容。会话文件必须已存在于宿主机上。
    signalAb或tSignal—中止时取消运行。会终止仍在运行的智能体子进程并取消生命周期 hook；w或ktree 保留在磁盘上。拒绝原因为 signal.reason.
    timeouts超时设置—覆盖内置生命周期步骤的默认超时： copyToWorktreeMs (60 000), gitSetupMs (10 000), commitCollectionMs (30 000), mergeToHostMs (30 000).
    outputOutputDefinition—结构化输出定义（Output.object(…) 或 Output.string(…)）。需要 maxIterations === 1。参见 结构化输出.

    RunResult

    字段类型描述
    iterationsIterationResult[]逐次迭代的结果（用 .length 获取条数）
    completionSignalstring?匹配到的完成信号字符串，否则为 undefined （未触发任何信号时）
    stdoutstring智能体输出
    commits{ sha }[]运行期间创建的提交
    branchstring目标分支名
    logFilePathstring?日志文件路径（仅在写入文件记录日志时存在）
    outputT?带类型的结构化输出（仅当设置了 output 选项时才存在）

    IterationResult

    字段类型描述
    sessionIdstring?来自提供方流的智能体会话 ID，若无则为 undefined （提供方未输出会话 ID 时）
    sessionFilePathstring?已捕获会话 JSONL 的宿主机绝对路径，或 undefined （未开启捕获时）
    usageIterationUsage?最后一条助手消息的 给ken 用量快照，或 undefined （未开启捕获或提供方不支持用量解析时）

    IterationUsage

    字段类型描述
    inputTokensnumber消耗的输入 给ken
    cacheCreationInputTokensnumber用于创建提示词缓存条目的 给ken
    cacheReadInputTokensnumber从提示词缓存读取的 给ken
    outputTokensnumber生成的输出 给ken

    会话捕获

    在每一次支持恢复的提供方迭代结束后，S和castle 都会自动把智能体的会话文件从沙箱捕获到宿主机。Claude Code 会话存放在 ~/.claude/projects/<encoded-path>/<session-id>.jsonl；Codex 会话存放在 ~/.codex/sessions/YYYY/MM/DD/rollout-*-<session-id>.jsonl；Pi 会话存放在 ~/.pi/agent/sessions/--<encoded-cwd>--/<timestamp>_<session-id>.jsonl。所有提供方特有的 cwd 字段都会被改写为与宿主机仓库根目录一致，因此提供方原生的恢复命令可以直接使用。

    对于 Claude Code，任何 Agent工具或 Workflow工具的子智能体记录若写在 <session-id>/subagents/agent-*.jsonl ，都会随主会话一起捕获。子智能体捕获是尽力而为：单个记录失败只会记录一条警告，其余兄弟记录与主会话照常捕获。主会话捕获失败仍会导致运行失败（见下文）。

    会话捕获默认对 claudeCode(), codex()和 pi() 开启，可通过 captureSessions: false关闭。没有 sessionStorage 的提供方不会尝试捕获。捕获失败会导致运行失败。

    会话恢复

    传入 resumeSession 给 run() 即可在新的沙箱中继续之前的 Claude Code、Codex 或 Pi 对话：

    const result = await run({

      agent: claudeCode("claude-opus-4-8"),

      sandbox: docker(),

      prompt: "Continue where you left off",

      resumeSession: "abc-123-def",

    });

    你也可以从结果中继续最近一次捕获的会话：

    const first = await run({

      agent: codex("gpt-5.4"),

      sandbox: docker(),

      prompt: "Draft a plan",

    });

    

    const second = await first.resume?.("Now implement the plan");

    resume 只存在于支持恢复的提供方（Claude Code、Codex、Pi）的结果上——所以才用了可选链调用。

    在沙箱启动之前，S和castle 会校验会话文件已存在于宿主机上，并在改写 cwd 字段使其匹配沙箱侧路径之后，把它传进沙箱。Claude Code 接收 --resume <id>；Codex 接收 codex exec resume <id> （提示词通过 stdin 管道传入）；Pi 接收 --session <id>.

    约束条件：

    • resumeSession 与 maxIterations > 1 不兼容（在创建沙箱之前就会抛错）。
    • 提供方在宿主机上的会话文件必须存在（否则在创建沙箱之前就会抛错）。
    • 只有第 1 次迭代会收到恢复旗标；后续迭代（如有）都从头开始。
    • 不支持恢复的提供方会拒绝 resumeSession.

    会话分叉

    RunResult.fork(prompt, options?) 与 .resume()互为姊妹方法：它从最近捕获的会话继续，但保持父会话 JSONL 原样不动，并以新的会话 ID 写入子会话。其机制是智能体原生的分叉旗标—— claude --resume <id> --fork-session 对应 Claude Code， codex exec fork <id> 对应 Codex。

    分叉支持扇出式工作流：一次父运行可以作为多个独立子运行的起点：

    const parent = await run({

      agent: claudeCode("claude-opus-4-8"),

      sandbox: docker(),

      prompt: "Read the codebase and summarise the data model",

    });

    

    const [reviewA, reviewB] = await Promise.all([

      parent.fork?.("Review the migration plan", {

        branchStrategy: { type: "branch", branch: "review-a" },

      }),

      parent.fork?.("Audit the auth layer", {

        branchStrategy: { type: "branch", branch: "review-b" },

      }),

    ]);

    分叉只作用于会话。 --fork-session 和 codex exec fork 只会隔离智能体的会话 JSONL——它们并 而不是 不会隔离分支、w或ktree 或沙箱。安全的并发扇出（Promise.all([r.fork(a), r.fork(b)])）要求调用者给每个子运行指定不同的 branch 分支，方法是传入 branchStrategy: { type: "branch", branch: "..." }。默认的 head 和 merge-to-head 这两种策略 而不是 都不适合并发分叉： head 会让所有子运行共享宿主机工作目录，而 merge-to-head 则会让 git merge 在同一个 HEAD 上互相竞争。参见 ADR 0018.

    fork 只存在于带有 sessionStorage （Claude Code、Codex）的提供方结果上——所以才用了可选链调用。与 .resume() 相同的单次迭代与会话文件约束同样适用。

    ClaudeCodeOptions

    这个 claudeCode() 工厂接受一个可选的第二个参数，用于提供方专属选项：

    agent: claudeCode("claude-opus-4-8", { effort: "high" });
    选项类型默认值描述
    effort"low" | "medium" | "high" | "xhigh" | "max"—Claude Code 推理用力度（ef替换为t）（max 仅 Opus 支持）
    envRecord<string, string>{}由该智能体提供方注入的环境变量
    captureSessionsbooleantrue捕获智能体会话 JSONL 到宿主机，用于 claude --resume
    permissionMode"default" | "acceptEdits" | "plan" | "auto" | "dontAsk" | "bypassPermissions"—映射到 Claude 的 --permission-mode 旗标。设置后会替换 S和castle 在 AFK 运行时的默认 --dangerously-skip-permissions 。若想让 AI 按工具逐个批准/拒绝而不绕过权限，使用 "auto" 即可。

    CodexOptions

    这个 codex() 工厂接受一个可选的第二个参数，用于提供方专属选项：

    agent: codex("gpt-5.4", { effort: "high" });
    选项类型默认值描述
    effort"low" | "medium" | "high" | "xhigh"—Codex 推理用力度，经由 model_reasoning_effort
    envRecord<string, string>{}由该智能体提供方注入的环境变量
    captureSessionsbooleantrue捕获 Codex rollout JSONL 到宿主机以供恢复
    approvalsReviewer"user" | "auto_review"—映射到 Codex 的 approvals_reviewer 配置。当设为 "auto_review"时，会把 --dangerously-bypass-approvals-and-sandbox 替换为 -a on-request -s danger-full-access ，由评审智能体评估每一条审批提示。

    PiOptions

    这个 pi() 工厂接受一个可选的第二个参数，用于提供方专属选项：

    agent: pi("claude-sonnet-4-6", { thinking: "high" });
    选项类型默认值描述
    thinking"off" | "minimal" | "low" | "medium" | "high" | "xhigh"—Pi 推理用力度，经由 --thinking 旗标设置
    envRecord<string, string>{}由该智能体提供方注入的环境变量
    captureSessionsbooleantrue捕获 pi 会话 JSONL 到宿主机，用于 pi --session <id>

    提供方 env

    两类提供方—— 智能体提供方 和 沙箱提供方 ——都接受可选的 env: Record<string, string> 选项。这些环境变量会在启动时与 .sandcastle/.env 的解析输出合并：

    await run({

      agent: claudeCode("claude-opus-4-8", {

        env: { ANTHROPIC_API_KEY: "sk-ant-..." },

      }),

      sandbox: docker({

        env: { DOCKER_SPECIFIC_VAR: "value" },

      }),

      prompt: "Fix issue #42",

    });

    合并规则：

    • 提供方环境变量（智能体 + 沙箱）会覆盖 .sandcastle/.env 的解析输出中同名键的值
    • 智能体提供方与沙箱提供方的环境变量 不得重叠 ——只要存在任何一个同名键， run() 就会抛出错误
    • 如果不提供 env ，它默认为 {}

    环境变量也会自动从 .sandcastle/.env 和 process.env 解析——无需手动传给 API。所需的变量取决于 智能体提供方 （详见 sandcastle init 的输出）。
