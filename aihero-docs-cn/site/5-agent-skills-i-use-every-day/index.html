    我每天都在用的 5 个智能体技能

    用经过验证的工程技能驾驭 AI 代码质量：面向 Claude Code 智能体的提示词技巧、TDD、架构设计与规格（spec）工作流。

    我做工程师快十年了。眼下，流程比以往任何时候都重要。

    你手下有一支随时可以调用的工程师队伍，水平从中等到良好。但这些工程师有个致命缺陷：他们没有记忆，不记得自己以前做过什么。

    这意味着你需要极其严格、定义清晰的流程，才能让他们做出有用的活。作为开发者，你要不断引导你的智能体，让它们走在正道上。

    我的应对办法是创建了大量的智能体技能（skill）。我设计的每个技能都帮我把自己的流程编码进去，让 AI 每一次都有严格的路径可循：

    结果呢？AI 产出的代码质量大幅飙升。

    1. /grill-me：把想法充实成形

    阅读指南 · GitHub

    npx skills@latest add mattpocock/skills

    这是我最喜欢的技能。只有三句话，但影响力惊人。

    Grill Me 技能：

    就这个计划的方方面面毫不留情地采访我，直到我们达成共识。沿着设计树的每个分支走下去，逐一理解决策之间的依赖。最后，如果一个问题可以通过探索代码库来回答，那就去探索代码库。

    “设计树”的概念出自 这里 Design of Design ，作者是 Frederick P. Brooks。它的意思是：设计一样东西时，你需要沿着设计树的所有分支走下去。

    例如，你可能在设计一个搜索页，需要在高级搜索界面和简单文本框之间做抉择。如果选了高级搜索，就得想清楚所有的筛选器和排序方式。你不断沿着树走下去，直到完全理解自己的设计，再动手写代码。

    当我调用这个技能时，我想与 LLM 达成共识。Claude Code 处于 计划模式（plan mode）时往往很早就吐出一份计划，在我们真正互相理解之前就把文档生成了。而 grill me 技能会强制进行这场对话。

    在一次关于给我的课程视频编辑器添加功能的对话中，Claude 问了我 16 个问题。而这还算是一次比较短的 追问（grilling） 会话。我经历过持续近半小时、围绕极复杂的功能提出 30、40 甚至 50 个问题的追问会话。

    关键心得：技能不必很长也能产生影响。你只需要在正确的时机选出正确的词。

    2. /to-spec：从对话到文档

    阅读指南 · GitHub

    npx skills@latest add mattpocock/skills

    （这个技能曾叫 /to-prd。干的还是同样的活，名字更清楚了。）

    与 LLM 达成共识之后，我就调用下一个技能： /to-spec.

    这个技能让 LLM 把这份共识写成一份规格（spec）——也就是你可能熟悉的 PRD。关键在于，它 不会 来采访你。追问已经发生过了， /to-spec 只是把对话里已有的内容综合成文。

    工作流：

    • 探索仓库，让规格立足于代码的当前状态
    • 勾画出将在哪些接缝（seam）上测试该功能，并核对这些接缝符合你的预期
    • 从模板写出规格，并发布到项目的工单追踪器（issue tracker）

    任何规格的关键部分都是用户故事（user story）。它们借鉴敏捷方法论，用语言描述你期望的系统行为。

    3. /to-tickets：把终点拆解成旅程

    阅读指南 · GitHub

    npx skills@latest add mattpocock/skills

    （曾名 /to-issues.)

    规格描述的是终点。但你真正需要的是抵达终点的旅程。

    这正是 /to-tickets 技能做的事。它拿一份规格，把它变成一块看板，上面的工单可以各自独立认领。

    流程：

    1. 收集上下文——你们刚结束的对话，或你指定给它的规格
    2. 探索代码库
    3. 起草垂直切片 ——把规格拆成工单，快速逼出那些未知的未知

    这里 曳光弹（tracer bullet） 的比喻正适用于此。每个工单都是一条贯穿所有集成层的纤细垂直切片，而不是某一层的水平切分。

    这个技能还会建立工单之间的阻塞关系。例如，某个工单可能不被任何东西阻塞，因此可以独立认领。如果你有多智能体并行工作的设置，这就很有用。

    4. /tdd：提升代码质量

    阅读指南 · GitHub

    npx skills@latest add mattpocock/skills

    技能要怎么执行？怎么让实现坚如磐石、提升代码质量？

    用 TDD 技能。TDD 即测试驱动开发（Test-Driven Development），它强迫（或者说鼓励）智能体遵循红-绿（red-green）-重构循环。

    这个技能相当有分量。它包含关于重构、mock 以及何为深模块（deep module）的理念。 把 TDD 做好，一直是提升智能体产出最稳定有效的方式。

    工作流从确认需要哪些接口变更开始。当 AI 面对一个糟糕的代码库时，它看到的是许多细小、无差异的模块。但如果你把它重组为更大的模块、在上面留出薄薄的接口，AI 就能轻松得多地在其中穿行。

    然后这个技能会：

    • 确认要测试哪些行为
    • 为可测试性设计接口
    • 一次写一个测试（测试先行）
    • 实现代码让测试通过
    • 寻找重构候选

    让智能体执行红-绿-重构简直不可思议。它形成一个循环，一直持续到完成为止。

    5. /improve-codebase-architecture：让你的代码对智能体友好

    在 GitHub 上查看

    npx skills@latest add mattpocock/skills

    TDD 对你的代码库要求很高。在结构糟糕的代码库里，测试边界不清晰。该在哪测？在哪一层测？

    当你的代码库有清晰的模块边界时，测试就容易多了。

    这里 /improve-codebase-architecture 技能会自然地探索你的代码库，寻找困惑点：

    • 哪里理解一个概念要在许多小文件之间来回跳？
    • 哪里为了可测试性抽出了纯函数，而真正的 bug 却藏在调用方式里？
    • 哪里紧耦合的模块制造了集成风险？

    然后它会给出加深（deepening）机会的候选——把浅模块加深成深模块的机会。

    每周做一次，或在一轮密集开发之后做。随着你不断打磨代码库，你会发现智能体产出的质量在上升。

    如果你的代码库是垃圾，AI 也会在这个代码库里产出垃圾。

    以上是七个中的五个。其余的——grill-with-docs、domain-modeling、triage——以及更新日志都在 /skills.
