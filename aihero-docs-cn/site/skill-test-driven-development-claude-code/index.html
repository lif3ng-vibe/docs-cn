    我的技能让 Claude Code 的 TDD 水平大涨

    这是我的 TDD 技能：用红-绿-重构（red-green-refactor）与垂直切片，让 Claude 写出诚实的测试和真正的实现。

    最近几周，我一直用自己写的一个 TDD 技能来处理大部分非前端工作。

    它解决了我此前在 LLM 与测试上遇到的许多问题。

    想试试的话，在这里：

    npx skills add mattpocock/skills/tdd

    想要更详细的拆解，请往下看：

    问题所在：为什么 LLM 写不好测试

    当你让 LLM“写一个功能”时，它往往按 水平切分（horizontal slicing）的方式工作：先写完整个功能，再补测试。这有问题，因为你并没有真正验证这些测试测的确实是该测的东西。

    实际情形是这样的：

    水平切分（❌ 坏）垂直切片（✅ 好）
    RED：先写全部测试RED→GREEN：test1→impl1
    GREEN：再写全部代码RED→GREEN：test2→impl2
    REFACTOR：清理收尾RED→GREEN：test3→impl3

    核心问题： 批量写出的测试，测的是想象中的行为，而不是观察到的行为。

    当 LLM 一次性生成 10 个测试、然后再写实现去全部通过时，可能出好几件坏事：

    • 测试验证的是 mock，而不是真实的代码路径
    • 测试可能根本跑不起来，或者内置了短路逻辑
    • 当 LLM 的上下文快耗尽时，它可能直接改测试让它通过，而不是写真正的实现

    坏测试不只是评审问题，更是债务问题。你创建的每个测试都要像代码一样永远维护下去。不绑定实际行为、或与实现细节耦合过深的测试，会变成昂贵的负资产。

    解决方案：红-绿-重构（Red-Green-Refactor）的垂直切片

    我的 TDD 技能约束 Claude 以 垂直切片 （借助曳光弹 tracer bullets）的方式工作：

    ONE test → ONE implementation → repeat

    每一轮循环都回应你从上一轮学到的东西。因为代码刚出自你手，你清楚地知道哪些行为重要、该如何验证。

    三个阶段

    RED：写一个会失败的测试。就一个。

    GREEN：只写让该测试通过的最少代码。不做任何投机性实现。

    REFACTOR：全部测试通过后，清理重复并做简化。

    这一约束杜绝了作弊。测试先失败，LLM 就没法糊弄，只能写真正的实现。

    这项技能如何改变 Claude 的构建方式

    在真实功能上使用这种方法时，有趣的事情发生了：测试变成了 Claude 与自己代码的对话.

    每个测试都在向实现提出一个不同的问题：

    • “这个可观察的行为正常吗？”
    • “系统如何处理边界情况？”
    • “条件变化时会怎样？”

    这种追问让 Claude 在推进过程中不断了解自己的实现，而不是机械打勾。有时候，你写的测试会立即通过——不是因为它是浪费，而是因为实现已经足够健壮，能应对它。

    好测试与坏测试的分界

    我在技能里写了好测试与坏测试的细节——以下是我描述的内容：

    好测试

    好测试通过 公共接口来执行真实的代码路径，而不是纠缠实现细节。它们描述系统做什么（WHAT），而不是怎么做（HOW）。

    // GOOD: Tests observable behavior through the interface

    test("user can checkout with valid cart", async () => {

      const cart = createCart();

      cart.add(product);

      const result = await checkout(cart, paymentMethod);

      expect(result.status).toBe("confirmed");

    });

    好测试读起来像一份规格说明：“user can checkout with valid cart”（用户可以用有效购物车结账）准确告诉你存在什么能力。这类测试在彻底的内部重构后依然通过，因为它们不关心内部结构。

    坏测试

    坏测试是 与实现耦合的。它们 mock 内部协作者、测试私有方法，或者绕过接口用外部手段验证。

    // BAD: Tests implementation detail (mocking internals)

    test("checkout calls paymentService.process", async () => {

      const mockPayment = jest.mock(paymentService);

      await checkout(cart, payment);

      expect(mockPayment.process).toHaveBeenCalledWith(cart.total);

    });

    

    // BAD: Bypasses interface to verify (queries DB directly)

    test("createUser saves to database", async () => {

      await createUser({ name: "Alice" });

      const row = await db.query("SELECT * FROM users WHERE name = ?", ["Alice"]);

      expect(row).toBeDefined();

    });

    警报信号：重构时测试挂了，但行为并没有变。如果你重命名一个内部函数、测试就失败，那这些测试测的是实现，不是行为。

    关键区别

    好测试坏测试
    通过公共接口执行真实代码mock 内部协作者
    描述系统做什么测试它怎么实现
    在内部重构后原样通过行为没变却因重构而挂掉
    读起来像规格说明测试数据结构的形状
    聚焦用户可感知的行为用外部手段验证（数据库查询、调用次数）

    规划阶段（写任何代码之前）

    在技能里，我发现写任何代码之前先有一个规划阶段极其重要。我决定用这些问题来落实它：

    • 需要哪些接口变更？ 在新增或修改哪些函数、方法或 API？
    • 哪些行为最重要？ 你不可能什么都测。把关键路径和复杂逻辑排在边界情况之前。
    • 能否按深模块（deep module）来设计？ 深模块接口很小，内部却处理复杂逻辑。这让测试更简单，API 更干净。
    • 能否为可测试性而设计？ 函数应该接受依赖，而不是自己创建；应该返回结果，而不是制造副作用。

    用户对这些问题的回答越好，代码质量就越高。

    这对 Claude Code 用户为什么重要

    这项技能追求的不是完美的测试，而是 用强制约束换来的诚实测试.

    把 Claude 的工作组织成“一个测试、一个实现、循环往复”，你就能防止它：

    • 编写想象中的行为而不是观察到的行为
    • mock 内部实现、伪造测试通过
    • 一开始就过度设计解决方案
    • 写出与实现细节耦合的测试

    测试变得可信。你可以把工作的大块委托给 Claude——不只是代码评审，而是真正的功能构建——因为你知道测试是诚实的。

    而当你能信任测试，你就能信任代码。
