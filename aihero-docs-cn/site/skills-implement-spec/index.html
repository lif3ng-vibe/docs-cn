    /implement-规格（spec） 技能

    用并行子智能体一口气构建整份规格。

    Matt Pocock

    然后输入 /implement-spec （在你的编码智能体里）。

    它做什么

    implement-spec 接下一份 规格（spec） 和它的 工单 ，一趟运行把整件事落地。负责编排的 智能体 把每张工单交给一个实现者 子智能体 ，在各自的 git worktree 里干活；每条完工的分支被合并进一条 集成分支（integration branch），然后运行 code-review ，并解决各张工单。

    它把工单读成一张 任务图（task graph），不是一份清单。阻塞边决定什么能启动，所以任何时刻都存在一个 前沿（frontier） ——所有阻塞都已落地的工单集合——前沿上的每张工单同时运行。这就是与逐张处理工单的区别。定节奏的是图的形状，不是工单在追踪器上的顺序。

    什么时候用它

    调用方式是输入 /implement-spec，智能体不会自己主动调用它。

    你的处境该用
    一份已拆成带阻塞边的工单的规格，你想一趟运行把它落地/implement-spec
    一次一张工单，在你自己的 上下文窗口, 内推进，工单之间 清空（内推进，工单之间）implement
    一份还没拆成工单的规格to-工单 先行
    一小块没有真正图结构的工作implement 直接

    前置条件

    • 一个工单追踪器（issue tracker）。 技能从这个追踪器读取工单、并在其上解决工单，追踪器由 setup-matt-pocock-skills 配置。一个都没配置的话，它会停下来让你先跑那个技能，而不是瞎猜。
    • 带阻塞边的工单，形如 to-工单 所写。没有边，图就是平的，所有工单同时启动。
    • A harness ——要求能在后台运行子智能体，并给每个子智能体一个 git worktree。 这个技能存在的意义就是同时运行工单，所以在一次只跑一个子智能体的 harness 上，它只是一个更慢的 implement.

    集成分支

    所有东西都落在一条分支上。每个实现者：

    1. 开工前确认自己的 worktree 基于集成分支，
    2. 用 tdd构建自己的工单，红-绿（red-green）推进，一次一片，
    3. 报告完成之前先把集成分支顶端合并进自己的分支，让落地成为一次快进（fast-forward）。

    到底存不存在 PR，由追踪器决定。如果你的追踪器通过 PR 收尾工作，或者你要求一个，技能会在第一次合并后开一个草稿 PR，并在最后把它标记为 ready。否则运行停在集成分支上，每张工单按你的追踪器收尾工作的方式解决——对着本地 markdown 追踪器这完全可以离线工作。

    实现者通过 上下文指针（context pointers） （规格、工单、共享的勘探笔记、更早的提交）与编排者沟通，而不是粘贴长篇摘要。这让每个子智能体的提示词保持小巧，也给编排者的窗口留出装图的空间。

    常见问题

    这跟我自己对着每张工单跑 /implement 有什么不同？

    这个技能就是为了回答这个问题而存在的。它发布之前，人们不断自建轮子，一位用户这样描述需求：他想要“子智能体实现工单”，而不是“当一份规格可能包含超过 5 张工单时，逐个新建会话、让它们一张一张实现”。用 implement 的话，你是调度员：每张工单 会话 一场，之间清空，还得自己记着哪些工单已解除阻塞。 implement-spec 把这份差事交给一个编排会话。代价是工单落地时你不再逐张过目；最后评审集成分支。启动一次运行：清空上下文，输入 /implement-spec ，并给一个指向规格的指针（issue 编号或文件路径）。小改动、没有真正的图，就跳过它，直接用 implement 。

    它需要 GitHub 吗？我想让它停在分支上。

    不需要了，现在不用了。一位喜欢开发中版本的用户恰恰提过这个意见：“它最后会创建一个 PR，这需要 GitHub 这样的在线仓库。我希望它能离线做同样的事，停在所有工作合并进去的那条分支上。”现在运行以集成分支收尾。只有配置的追踪器通过 PR 收尾工作、或你主动要求时才会开 PR，所以在本地 markdown 追踪器上，运行结束时所有工单已解决、工作已合并到分支上。

    它的评审与修复循环跑了几个小时，或者一直“修”那些还没构建的工单。

    两种情况都发生在 code-review 被跑到技能指定那一个点之外的任何地方时。它拿整份规格对照代码，所以只有每张工单都落地之后才有意义。如果它在运行中途跑起来，每张未构建的工单都会被读成一次失败。智能体于是去构建那张工单，这又触发新一轮评审。到最后，技能会运行 code-review 一次，并把每条发现发给一个修复子智能体，但它还没说那次修复之后何时收手。一位用户报告过一个五工单特性，“评审与修复循环大约花了四个小时”。如果你看到第二轮全面评审开始，告诉它只对已修复的发现做聚焦检查然后停。要有心理准备：第一轮评审会找到真问题。运行的产出是一份草稿，由评审来完成它，不能拿去单独上线。

    它像 implement 那样驱动 tdd 吗？

    现在会了，虽然起初不会。运行开发中版本的用户注意到“实现者子智能体不继承 /tdd 指令”，于是从一张工单扩展到整份规格时，红-绿就停了。现在每个实现者都用 tdd构建自己的工单。仍然没有一个让你交互式敲定接缝的步骤—— implement 会话里才有那样的环节。想让接缝被钉死，就在规格或工单里写明它们。

    两个并行运行的实现者在同一个文件上撞车，或者给同一样东西起了不同的名字。

    worktree 不能消除冲突，只是把冲突推迟到合并时。从工单文本写出的阻塞边是对“每张工单会碰哪些文件”的猜测，两张“代码库不同部分”的工单仍然共享一份消息目录、一个配置注册表或一个类型。每个实现者只看到自己的工单和共享笔记，永远看不到对方的进行中工作，所以一位用户的 web 与 mobile 工单把同一个字符串加成了 blockedSince and blockedOn. 。当两张前沿工单碰同一个共享文件时，要么在它们之间加一条阻塞边让它们一先一后，要么让勘探笔记钉死每张工单添加的确切名字。

    被阻塞的工单永远不启动，哪怕阻塞它的工单已经合并。

    这是 GitHub 上的已知问题。追踪器的 blocked-by 计数只在阻塞者 关闭时才下降，而工单通常在 PR 合并时才关闭，那已是运行的终点。追踪器是初始图的正确来源，但在运行中途是过时的。让编排者自己去跟踪哪些工单已合并进集成分支，并据此计算前沿。

    它能取代 Sandcastle 或 AFK 脚本吗？

    不能。人们这么问是因为这些技能如今伸进了实现环节：“Sandcastle 还有用武之地吗？你的技能现在好像也能处理实现了。” implement-spec 让一个智能体在单个 harness 会话内负责编排，不需要基础设施，而且你能旁观和引导。对真正 AFK的工作，一个确定性循环（Sandcastle、一个 shell 脚本、一个 CI 作业）更快、更便宜、更可靠，因为没有智能体来做编排决策。

    一张工单的关键测试在它的 worktree 里被跳过了，它却报了绿。

    worktree 只装 git 跟踪的东西。读取 gitignore 的 fixture、本地数据库或凭据的测试在那里可能悄悄跳过。对验证依赖未跟踪材料的工单，让编排者改在主 checkout 里运行它。

    正常工作的标志

    • 只要图允许，就有多个实现者同时运行，而不是一个接一个。
    • 工单的最后一个阻塞者一落到集成分支，它就启动，而不是等整场运行结束。
    • 每张工单的轨迹都显示 tdd 在运行，代码之前有一个失败的测试。
    • 合入集成分支都是快进，而不是冲突解决。
    • 运行结束在一条分支上，所有工单已解决，PR 只在你追踪器想要时才有。

    它的定位

    implement-spec 是主链的构建步骤，是逐张运行 implement 的并行替代：

    grill-with-docs → to-spec → to-tickets → implement-spec → retro

    它的邻居是 to-工单——由它声明阻塞边，本技能将其读作任务图——以及 code-review——收尾之前，本技能会对整条集成分支运行后者。 ask-matt 在你不确定自己身处哪条流程时，是横跨全套技能的路由器。
