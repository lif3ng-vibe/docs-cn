    改进 LLM 应用的 17 种技术

    一份改进 LLM 应用的技术目录。

    Matt Pocock
    本页内容
    • 先试最简单的办法
    • 可以尝试的技术
    • 接下来
    • 延伸阅读

    一旦你清楚地理解了成功标准、选好了模型，并写出了一些基础评测（eval），就到了开始改进系统的时候。

    改进系统的过程归结为两件事：

    • 改进你的 反馈回路 （评测，eval）
    • 改进 性能 系统本身的

    我们已经看过如何改进你的评测。在本文中，我会概述改进系统的主要方法。

    但首先，聊聊改进系统时你需要具备的心态。

    先试最简单的办法

    我们已经看到，改进 AI 系统是一个 实验过程。你需要动手尝试、看看什么有效，然后迭代。

    改进系统的技术从简单便宜到复杂昂贵不等。调一调提示词？便宜。从零训练一个模型？贵得惊人。

    我把它称为复杂度地狱阶梯：

    关键是从阶梯顶端开始，只有把更简单的选项全部试穷尽了才往下走。简单的技术只需少量投入就能带来巨大提升。

    可以尝试的技术

    这份清单从最简单的技术排到最复杂的。从顶端开始，逐级往下。我为每种技术都附了延伸资源链接，可以了解更多细节。

    1. 你的第一条提示词

    问题：总得从某处起步。

    解决方案：下面是一些改进提示词的基本建议：

    • 清晰、直接、具体。
    • 把 LLM 想成一个才华横溢但非常新来的员工。
    • 记住，LLM 对你的规范、风格或指南一无所知。

    资源

    • Anthropic 的建议 是理解如何写好提示词的实用指南。
    • Anthropic 提示词库 是为你的用例探索优秀提示词的好途径。
    • OpenAI 文档 关于编写清晰指令。

    2. 基于角色的提示（role-based prompting）

    问题：你希望无论输入是什么，LLM 都以某种特定方式表现。

    解决方案：用基于角色的提示让 LLM 扮演某种人设。

    这可以多样到调整语气：

    You are a friendly support engineer. Answer in short, plain sentences.

    甚至口音：

    You are a concise British copy editor. Keep the answer dry and understated.

    或者引导 LLM 谈论某个特定话题：

    You are an AI engineering coach. Explain tradeoffs in terms of evals, latency, and cost.

    这是一种极其常见的技术，实现成本很低。通常在 系统提示词（system prompt）.

    资源

    • 我的视频： 系统提示词 （Vercel AI SDK）
    • Anthropic 文档 关于基于角色的提示
    • OpenAI 文档 关于让模型扮演人设

    3. XML 标签

    输入端的 XML 标签

    问题：你想在一条提示词里传给 LLM 多份信息。

    解决方案：使用 XML 标签。

    XML 标签有助于为提示词的不同部分提供分隔符。

    Anthropic 文档里的一个例子是财务报告：

    <documents>

      <document index="1">

        <source>2025 annual report</source>

        <document_content>Revenue increased 18% year over year...</document_content>

      </document>

      <document index="2">

        <source>Q1 investor update</source>

        <document_content>Gross margin improved after infrastructure costs fell...</document_content>

      </document>

    </documents>

    

    Using only the documents above, summarize the main business risks.

    输出端的 XML 标签

    问题：你希望 LLM 同时给出多种不同的输出。

    解决方案：告诉 LLM 根据不同的 XML 标签给出相应的输出。

    你也可以让 LLM 根据提示词中的 XML 标签给出不同的输出。这能让你更好地控制响应的结构。

    你可能想让 LLM 帮你审一篇文章。你可能希望它提供一份 <summary>、一份 <critique>，以及 <recommended_changes>.

    Review this article and respond using this exact structure:

    

    <summary>One paragraph summary</summary>

    <critique>What is unclear or unsupported</critique>

    <recommended_changes>Concrete edits to make next</recommended_changes>

    这项技术由 Anthropic 推广开来，不过大多数模型也都支持。

    资源

    • Anthropic 文档 关于在提示词中使用 XML 标签
    • OpenAI 文档 提到把 XML 标签用作分隔符

    4. 约束 LLM 的响应格式

    问题：你想严格约束 LLM 返回的文本，比如让它以 JSON 或单个词回复。

    解决方案：使用结构化输出或明确的格式指令。

    旧版本的 Claude 支持"预填充"（prefilling）assistant 消息来引导响应格式。从 Claude 4.6 起，预填充会返回 400 错误。现代的替代方案更好：

    结构化输出（Structured Outputs） （推荐）：大多数 LLM 提供商现在都支持结构化输出 schema，保证响应匹配特定的 JSON 形状。在 Vercel AI SDK 中，使用 generateObject 或 streamObject:

    const result = await generateObject({

      model,

      schema: z.object({

        sentiment: z.enum(['positive', 'neutral', 'negative']),

        summary: z.string(),

      }),

      prompt: 'Classify this customer feedback...',

    })

    系统提示词指令：对于更简单的约束，在系统提示词里告诉模型你想要的格式：

    Reply with exactly one of these labels: bug, feature-request, billing, or other.

    Do not include any explanation.

    这两种方法都比过去的预填充更可靠。结构化输出给你类型安全、经过校验的响应。当你需要特定形状的灵活文本输出时，系统提示词指令就够用。

    资源:

    • Anthropic：结构化输出
    • Vercel AI SDK：generateObject

    5. 结构化输出

    问题：你想让 LLM 返回结构化数据而不是纯文本。

    解决方案：使用结构化输出。

    结构化输出是让 LLM 以结构化格式（如 JSON）返回数据的方法。大多数 LLM 提供商都支持为想要的输出提供 JSON schema 描述。

    其中 Vercel AI SDK 是这方面特别好用的工具集。

    资源

    • Anthropic 文档 关于 JSON 模式

    6. 推理

    问题：LLM 在复杂的多步推理任务（比如编码或数学题）上表现不够好。

    解决方案：用思维链（chain-of-thought，CoT）提示让 LLM 逐步推理问题。

    思维链提示鼓励 LLM 一步步拆解问题，从而得到更准确、更细腻的输出。这项技术对需要复杂推理、分析或解决问题能力的任务特别有效。

    思维链提示有三种主要做法，由简到繁：

    1. 基础 CoT：在提示词里直接加一句"请一步步思考"。虽然简单，但缺乏对如何思考的指引。
    2. 引导式 CoT：为 LLM 的思考过程列出具体步骤。
    3. 结构化 CoT：使用像 <thinking> 和 <answer> 这样的 XML 标签，把推理过程与最终答案分开。

    思维链提示用速度换质量。LLM 必须处理并输出它的推理步骤，响应时间随之变长。这在实时应用中最要紧——聊天机器人需要快速响应，而代码评审工具可以花更长时间做细致分析。

    资源

    • Anthropic 文档 关于思维链提示
    • OpenAI 的建议 关于给模型时间思考再下结论

    7. 多样本提示（multishot prompting）

    问题：LLM 需要理解某种特定模式或格式，但单个例子不足以让它领会。

    解决方案：提供多个例子帮助 LLM 理解模式。

    多样本提示能取得接近微调（fine-tuning）的效果，却没有训练新模型的成本和复杂度。它的原理是给模型展示你希望它做什么的示例。

    直截了当——给几组输入和输出示例，模型就能学到模式。不需要训练数据或算力资源。

    这是一个写产品描述的实用示例：

    Write product descriptions in this style.

    

    Input: Noise-canceling headphones

    Output: Sink into your work with soft over-ear cushions and active noise cancellation that quiets the room around you. Great for deep focus, travel, and calls that need fewer distractions.

    

    Input: Standing desk

    Output: Move from sitting to standing in seconds with a sturdy desk that keeps your monitor, keyboard, and coffee exactly where you need them. Built for long workdays without locking you into one posture.

    

    Input: Running shoes

    Output: Light foam, breathable mesh, and a grippy sole make these shoes feel quick without beating up your feet. Perfect for daily miles, recovery runs, and the walk home after.

    

    Input: Coffee maker

    Output:

    看完这些示例后，模型学会用感官化语言写产品描述并聚焦卖点。之后你给它"Input: Coffee maker"，它就会生成风格相近的描述。

    多样本提示与零样本提示（zero-shot prompting）相对——后者只描述你想要什么，不给示例。

    资源

    • Anthropic 文档 关于多样本提示
    • OpenAI 文档 关于提供示例

    8. temperature

    问题：LLM 的输出要么太确定（无聊），要么太随机（不可靠）。

    解决方案：调整 temperature 参数来控制输出的随机性。

    你可以给 LLM 传一个 temperature 参数。它控制 LLM 输出的随机或确定程度。

    把 temperature 想成你的创意旋钮。写代码或需要精确事实时，设 0.0-0.3——这会让模型紧贴最可能的输出。一般聊天或创意写作，0.4-0.7 的中等档位比较均衡。头脑风暴或需要新鲜想法时，调到 0.8-1.2。

    更高的 temperature 意味着更有趣的输出，但也可能产生更多幻觉。我的总体建议是从保守值开始，只在需要更多变化时才调高。

    无论如何，这都是一种尝试成本相对低的技术。

    资源

    • OpenAI API 参考 解释了 temperature 如何影响 token 采样

    9. 工具调用（tool calling）

    问题：LLM 只能生成文本，无法直接与外部系统交互或在现实世界中执行动作。

    解决方案：让 LLM 可以调用特定的函数或工具，把它的能力扩展到文本生成之外。

    工具调用弥合了 LLM 内部能力与外部世界之间的鸿沟。它让 LLM 能执行发起 API 调用、访问数据库、操作文件等动作。LLM 描述它想做什么，系统用指定参数执行相应的工具。

    当你需要 LLM 与外部服务交互、执行系统操作，或访问不在其训练数据中的信息时，这种模式特别有用。它是构建更强能力 AI 应用的基础积木。

    你可以阅读 我的教程.

    资源

    10. LLM 调用链

    问题：单次 LLM 调用不足以完成复杂任务。

    解决方案：把任务拆成多个相互衔接的 LLM 调用。

    当你需要对同一输入执行多种专门操作时，试图在一条提示词里做完所有事往往效果不佳。每种操作可能需要不同的专长和侧重。

    这正是 LLM 调用链的用武之地。你不让一条提示词包办一切，而是把任务拆成专门化的步骤。每条提示词只专注任务的一个方面，它的输出成为链中下一条提示词的输入。

    以代码分析和修复生成为例。第一条提示词充当代码分析器，识别并归类代码中的问题，为每个问题提供上下文，形成结构化的分析。

    第二条提示词接着利用这份分析生成有针对性的修复，建立在对第一条提示词洞见的基础上。这种关注点分离让每条提示词都能针对自己的任务做优化，效果比在一条提示词里同时做两件事更好。

    这种模式还能用于许多其他场景：

    • 先分析文档结构，再生成摘要
    • 先找出辩论中的关键论点，再撰写一个平衡的回应
    • 先从研究中提取事实，再写给外行看的解释
    • 先找出代码中的 bug，再逐个生成修复

    资源

    • Anthropic 文档 关于提示词链

    11. RAG（检索增强生成）

    问题：你的 LLM 在编造事实，因为它访问不到所需的信息。

    解决方案：通过检索增强生成（RAG）让它访问真实数据。

    RAG 是一种让 LLM 的回答扎根于真实数据、减少幻觉的有力技术。每个 LLM 的训练数据都有截止日期——那天之后的事件或信息它无从知晓。它不必只依赖训练时学到的内容，可以按需查询新信息。

    给 LLM 喂数据主要有两种方式。网页搜索给你当前信息和公开知识；公司数据库和文档让你触及私有的、领域特定的信息。当你需要关于公司内部流程的答案，或想确保 LLM 的回答是最新的，这就特别有用。

    构建 LLM 应用时，RAG 不该是你的第一站。它给系统增加大量复杂度——你需要管理数据源、处理检索，还要确保上下文窗口不超限。

    12. 分块（chunking）

    问题：你想检索的信息太大，塞不进 上下文窗口（context window）.

    解决方案：把信息拆成更小、可管理的块。

    分块是 RAG 系统中的基础技术，把大文档拆成更小、更易处理的片段。目标是让每个块既有语义上的意义，又小到能装进模型的上下文窗口。

    分块的复杂度来自切分内容的多种方式。主要做法有：

    • 按 token：按 token 数量切分，确保不超模型限制
    • 按字符：按字符数切分，适合原始文本处理
    • 按句子：保留自然语言边界
    • 按段落：保留更大的语义单元
    • 语义边界：用嵌入（embedding）寻找自然断点
    • 文档结构：遵循文档格式（标题、章节等）

    分块之后，你需要为每个查询找出最相关的块。主要方法有：

    • BM25：一种查找精确词匹配的传统搜索算法，对技术术语和错误码特别好用
    • 嵌入（embeddings）：把文本转成向量，找出语义相近的块
    • 混合搜索：结合 BM25 与嵌入，效果更好
    • LLM 重排序：用另一个 LLM 仔细阅读并按相关性给块排序

    每种方法各有长处——BM25 擅长精确匹配，嵌入则捕捉语义。许多系统会组合多种方法以获得最佳效果。

    13. 智能体循环（agentic loops）

    问题：LLM 调用链对复杂任务太僵硬。它要求预先定义步骤和停止点，难以应对步骤数不可预测的开放问题。

    解决方案：把控制权交给一个能规划、执行并根据环境反馈调整的自主智能体。

    LLM 调用链使用预定义的步骤和停止点，这限制了它应对不可预测任务的能力。智能体循环把更多控制权交给 LLM——让它根据任务进展决定何时停止。智能体通过真实反馈学会何时该停。

    这样得到的系统更强大，因为它能适应不可预测的路径。它不是照着预定义步骤走，而是根据每次交互学习和调整。这让它对解法未知的复杂问题特别有效。

    这种自主性有代价——每一步的决策都会增加延迟。LLM 必须评估当前状态并选择最佳前进路径。这让智能体循环比 LLM 调用链慢，但更能处理复杂任务。

    这种模式适合：

    • 跨多个文件的复杂代码修改
    • 需要多个信息来源的调研任务
    • 路径不可预测的客户支持场景
    • 需要多个处理步骤的数据分析

    资源

    • Anthropic 的文章 关于构建高效智能体

    14. 并行 LLM 调用

    问题：你的 LLM 系统太慢，因为它一次只处理一个任务，制造了不必要的延迟。

    解决方案：并行运行多个 LLM 调用，同时处理相互独立的任务，大幅缩短总处理时间。

    让系统更快只有两条路：少做事，或者同时做多件事。当你需要独立处理多个任务时，并行运行 LLM 调用能大幅提升性能。

    任务相互独立、不依赖彼此结果时可以并行：

    • 分析多个文档
    • 生成内容的不同变体
    • 同时处理多个用户查询

    任务必须按顺序发生时不能并行：

    • 每一步都依赖上一步输出时
    • 严格保持顺序对最终结果至关重要时

    性能收益相当可观。一个系统顺序处理 10 份文档可能要 10 秒，而并行处理 2-3 秒就能完成。你应该随时寻找并行化的机会——即使在看似串行的系统里，也可能有可以并发处理的独立部分。

    15. 评估者-优化者（evaluat或-optimizer）

    问题：即便尝试多次，LLM 的回答仍达不到你需要的质量标准。

    解决方案：创建一个自动化循环——一个 LLM 生成回答，另一个评估并给出改进反馈。

    评估者-优化者工作流构建了一个自我改进的系统：两个 LLM 协同工作。第一个生成回答，第二个按具体标准评估。评估结果反哺生成过程，形成持续改进的循环。

    当你有明确的评估标准、且迭代改进能带来可衡量的价值时，这种模式特别有效。如果人的反馈确实能改善 LLM 的回答，而 LLM 又能提供相近质量的反馈，那就适合用它。

    这种模式在文学翻译等场景中表现出色——评估 LLM 能抓住译者起初可能漏掉的细微含义。它对需要多轮搜索和分析的复杂检索任务同样有力，由评估者决定是否需要继续搜索。

    资源

    16. LLM 路由

    问题：不同类型的查询需要不同的处理策略。

    解决方案：用一个 LLM 把查询路由到最合适的处理者。

    LLM 路由就像智能调度员，分析每条查询并把它发给合适的专门处理者。

    路由先分析每条查询，判断其类型和复杂度。客服系统可能把查询分为这些类别：

    基于这一分类，路由把查询接到合适的处理者，后者带有自己专属的指令和能力集。

    这种路由方式带来几个关键优势。它确保每条查询都由最合适的专门系统处理，从而提升准确性。它还让每个专门的 LLM 专注自己的领域，类似 LLM 链把复杂任务拆成专门步骤的做法。

    它还解决了 LLM 的一个根本限制——大多数模型只能处理有限数量的工具（通常不超过 30 个）。把查询路由给专门的处理者，就能构建一个实际上能处理无限工具的系统，因为每个处理者只需访问与自己相关的子集。

    不过，加入 LLM 路由会引入一个额外的串行步骤、增加延迟，因为每条查询都要先分析再路由到合适的处理者。

    17. 微调（fine-tuning）

    问题：LLM 的输出需要满足更简单技术无法达到的特定质量要求。

    解决方案：用你的专属数据微调一个基础模型，提升它在你用例上的表现。

    微调让你把现有模型改造成符合特定需求的样子。你可以从一组相对小的高质量示例数据集起步，它们精确示范了你想要的输出——无论是贴合品牌语气、处理专业术语，还是保持一致的格式。经过微调的小模型在你的特定任务上往往能胜过更大、更贵的模型。

    在成本和复杂度上，微调介于预训练和提示词工程之间。虽然它比从零训练一个模型便宜一个数量级，但每次微调运行都会产生额外成本。还存在过拟合到特定模型版本的风险，这会让未来切换到更新更好的模型变得更难。

    考虑微调的最佳时机，是你已经有了一套在用更简单技术运转的系统：用例已验证、真实数据已收集、模型表现需要改进的具体环节也已明确。此时微调就成了把系统表现再推进一步的优化手段。

    18. 下一个大事件

    AI 工程领域的发展速度惊人。每周都有新模型、新技术、新工具问世，号称要彻底改变我们构建 AI 系统的方式。跟上一切是不可能的，但你也不必。

    每一项新进展都得在你的系统里挣得自己的位置。问问自己："这让事情更简单还是更复杂？它在解决真实的问题吗？"最有价值的新进展能降低成本、提升性能，或让你的系统更易维护。

    AI 界的下一个大事件来了又走，但"简单"始终是可靠的指南针。用你自己的评测来试验新技术——对照你的具体用例和成功标准来检验。把注意力放在那些帮你以更低复杂度构建更有效系统的发展上。
