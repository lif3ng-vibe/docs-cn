    它做什么

    research 通过阅读掌握答案的来源来回答问题，然后在仓库里留下一份带引用的 Markdown 文件。它只从 一手来源（primary sources）取材：官方文档、源代码、规格（spec）、第一方 API。它会把每条论断追溯回拥有它的来源，所以只要 API 自己的文档查得到，它就不会照搬某篇博客文章对这套 API 的说法。

    它不会在对话里直接回答你。产出是一份文件，写在仓库本就存放这类笔记的地方，每条论断上都带一个链接。你得到的是一份可以对着它表态、交给另一个智能体、或随手扔掉的文档，而不是一个当 会话（session） 一结束就不复存在的答案。

    什么时候用它

    输入 /research，或者 智能体 会在任务变成查资料的跑腿活时自动调用它。

    当下一步是 查清一些事 ——对象在工作目录之外（第三方 API 如何表现、某份规格说了什么、某个版本宣称是否属实），而你又不想让读资料卡住自己的线程。你需要什么，决定了该用哪个技能：

    你需要什么该用
    一个决策正在等的外部事实research
    一个 与你 共同访谈做出的决策追问（grilling）
    一个要长期保留的架构决策，写进 GLOSSARY.md 和 ADRgrill-与你-docs
    想弄清某个方案在你的代码库里行不行prototype
    一份单个会话装不下的计划wayfinder

    与 research 之间 grill-with-docs 的分界线是 产出物的保质期（shelf life）。调研（research）产出的是短时效事实，比如这个库的 auth 机制截至本周的行为。ADR 记录的是你会保留的决策。如果你正在产出的是一个决策而非一个事实，那你是在 追问（grilling），而不是在做调研。

    委派出去的跑腿活

    阅读工作以一个 后台智能体（background 智能体）的身份在跑。它把每条论断追到一手来源、写出一份 Markdown 文件、再汇报回来，而你继续做自己的事。调研是你委派出去的跑腿活，不是你外包出去的思考。你拿到的是一份可以拿来追问、规划或设计的文档，决策仍由你来做。

    没有什么能阻止这个后台智能体再自己孵化一个后台智能体。这是该技能被记录得最充分的问题。

    文件放在哪由仓库决定，不是技能决定。它遵循仓库里已有的任何笔记存放约定；如果没有，就挑一个合理的位置并告诉你。每次运行只写一个文件。

    常见问题

    它孵化出了第二个调研智能体。这是应该发生的吗？

    不是。这是一个尚未修复的 bug： issue #530。该技能只让调用方拉起一个后台智能体，并不限制智能体类型。于是调用方孵化出一个 general-purpose 智能体，它拥有 Agent 工具和同一份指令，于是又照着执行了一遍。有报告者测得，一个调研任务在三次相互重叠的运行中总共耗掉约 450k token 。三次运行彼此重叠，而那个重复的运行半小时后才结束，用户根本看不见。Claude Code 之外也会发生：用户确认在 Codex 配 GPT-5.6-sol 时同样嵌套。目前没有已发布的修复。有用户给自己的安装副本打补丁，加了一行字，让已经是 子智能体（sub智能体） 的智能体自己动手干。这有帮助，但终究只是一句指令，不是结构性修复。调用该技能之后，盯住你的后台任务列表，把那个重复的停掉。

    相反的失败也会出现。如果你自己的全局指令禁止智能体把工作再委派出去，后台智能体会拒绝这个任务，技能就什么也不做，还不告诉你。

    文件该放在哪？该提交进 git 吗？

    技能把文件放在仓库本就存放笔记的地方，对此没有更多意见。社区的看法基本已成定局：留 ADR，不留调研文件。Discord 上一个讨论此问题的帖子说得最清楚：“ADR 要留。其他的东西，做完就归档或删掉，否则它们会变成工作的垃圾，一旦你偏离了当初的 spec/调研，还会毒化未来对仓库的读取。”调研文件记录的是写下那天为真的东西，过期的文件比没有更糟。权衡下来，这些文件不该进 git，也没有标准归宿。人们改用 Obsidian、一个独立的知识仓库，或工单追踪器。

    什么才算“高可信”的一手来源？谁说了算？

    由 模型 说了算。技能列出了合格来源的 类型 （官方文档、源代码、规格、第一方 API），但没有允许清单、没有域名校验、也没有核验环节。技能刚提出来时，这是最响亮的反对意见，至今没人公开回应过：“五个调研子智能体对着一堆垃圾信息，只会更快给你五个自信的错误答案。你到底怎么把关什么才算高可信来源？”你唯一的保护就是每条论断上的引用。随手点开两三条看看。如果落到的是对某样东西的转述而不是那样东西本身，这次运行就算失败了。

    后面的会话会复用前面那次运行的发现吗？

    不会。没有任何机制会自动加载过往的调研文件。文件会一直留在仓库里，直到某个人或某个技能指向它。这是这套设计早期受到的最有力质疑：“价值在于 markdown 变成智能体日后会重读的上下文，而不在抓取本身。一个只写一次的死文件，不过是一次花哨的搜索。”已发布的技能没有解决这个问题。实践中，只有你亲手把它喂给下一步它才有用：附到一份规格上、在追问会话里引用它，或者让一张 工单（ticket） 指向它。

    为什么不直接让智能体去读文档？

    可以，而且“去把文档读一遍”这样一句两行提示词，正是这个技能取代的旧做法。技能给了你两样提示词给不了的东西。它在后台运行，所以你会话的 上下文 始终保持干净。而且一手来源约束和带引用的文件产出每次都一样，不取决于你提示词怎么措辞。与 harness自带的深度调研模式相比，差别在文件和一手来源规则，不在搜索本身。如果一个小问题用两行提示词就能解决，那就用两行提示词。

    它什么时候停止阅读？

    该技能没有停止判据。由此产生两听起来相反、根因却相同的抱怨：有的智能体钻得实在太深，有的铺得很广却漏掉真正要紧的那个细节。一位从业者这么说：“深度调研技能有时钻得太深。而让智能体去做调研，通常又会漏掉关键细节。”范围得由你来定。一个窄的、可回答的问题（一个 API、一个行为、一个版本宣称）的效果远远好过“去调研一下 X”。

    /wayfinder 创建了调研工单。这些要我自己去解决吗？

    不用，现在它会替你发起。v1.1 之后尚未发布的改动里，绘制地图的会话会给每张调研工单孵化一个 /research 子智能体并行跑。每个都把发现记录在一条用完即弃的 research/<name> 分支上，并带上一个 上下文指针（上下文 pointer） ，指针来自工单。调研工单是 wayfinder“每会话一张工单”规则的唯一例外，因为它们是 AFK的：没有任何东西在等你。一个已知问题：事后删掉那条分支，会弄坏工单里的上下文指针。

    正常工作的标志

    • 你自己的会话继续推进。如果你坐在那儿看它读资料，那委派就没有发生。
    • 恰好出现一个新的后台任务。出现第二个名字几乎一样的，就是嵌套 bug。
    • 出现一个新的 Markdown 文件，就在仓库本就用来放笔记的目录里，智能体会告诉你路径。
    • 里面每条论断都带链接，随手点开两条，落到的是官方文档、规格或源文件本身，而不是谁对它的转述。
    • 只靠这份文件，你就能把卡住的决策做出来，不必自己回到那些来源。

    它的定位

    research 是一个随时可用的独立技能。它为思考型技能供给素材，不是构建链上的一步。你把它的文件 带进 这条流程。 追问（grilling） 之间 grill-与你-docs 在已经掌握事实时会问出更锐利的问题，而 to-spec 可以拿它来做综合。 wayfinder 是唯一直接调用它的技能。它用 /research 子智能体解决地图上的每张调研工单。想看整张地图，见 ask-matt.
