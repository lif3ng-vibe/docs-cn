    它做什么

    resolving-merge-conflicts 逐个 hunk 地处理进行中的 git 合并或变基，然后运行项目自己的检查，并以一次提交收尾整个操作。

    它拒绝把冲突当成文字问题。动一个 hunk 之前，它先把每一方追溯回它的 一手来源（primary source） （提交信息、PR、原始工单），所以它是在两个意图之间做选择，而不是在两段文字之间，并且只要兼容就双方都保留。不兼容时，它选择符合本次合并既定目标的一方，并讲明取舍。它不会发明新行为来掩盖冲突，也从不使用 --abort。它总是把合并带到一个完成的提交。

    什么时候用它

    输入 /resolving-merge-conflicts，或者 智能体 会在任务匹配时自动调用它。

    在 git 已经被它自己解决不了的冲突挡停时使用。它只管你眼前这场冲突，不管冲突前后的任何事：

    你的处境技能
    合并或变基进行到一半，工作区里有冲突标记本技能
    合并已完成，但有些东西莫名表现异常diagnosing-bugs
    规划怎么切分工作，让分支少撞车都不要：见下面关于并行工作的问题

    一手来源优先于 ours 和 theirs

    这个技能存在的意义，就是防止靠标志解决冲突： --ours, --theirs，或者动手删掉看起来不那么重要的那块，让标记消失、构建通过。这种解法在语法上可以无懈可击，却仍会悄悄丢掉某个人特意做的改动。

    没读过的意图你保不住。所以工作从历史开始（提交、PR、 工单（ticket）），然后才进入 diff。检查步骤的存在理由也一样。该技能会找出仓库自己的 自动化检查（automated check） 并在提交前运行，因为合并是 git 里最容易产出“两个分支都满足、谁的测试都过不了”的代码的地方。

    常见问题

    Claude Code 自己就能把冲突解决得挺好，为什么还需要一个技能？

    增值在“找到一手来源”和“运行反馈回路”这两步，否则你每次都得手动写进提示词。没人提示的智能体通常只凭 diff 就给出一个看似合理的解法，然后停在那里。技能的价值是它不许智能体跳过的两步：读一读每一方为什么存在，以及事后运行检查。相比一个好的 模型，这只是小提升，而且这是有意为之。已有读者预言：随着模型进步，这整个技能会变成一个空操作。

    为避免冲突，我是不是从一开始就该让并行的智能体别碰同一批文件？

    大多不必。把文件在并行任务之间划区隔离，代价大于收益，因为智能体处理合并冲突已经够好，这个权衡没有看起来那么严苛。唯一值得保留的纪律是先做大型重构。十条分支已经分叉之后大型重命名才落地，这种情况才会一直贵。

    一份关于并行 worktree 的用户报告有个注意点：当兄弟 会话（session） 各自在自己的树里构建工单时，往回合并最好由写出改动的那个会话来做，因为只有它已经知道意图。如果最后由一个智能体解决所有人的冲突，它就丢掉了 上下文 ，而这个技能的第 2 步随后还得重建它。

    为什么绝不用 --abort?

    中止会丢掉已做的解决工作，下次再试时还是同一场冲突，分毫未变。这个技能是为“合并终将发生”的场景写的。如果你已经决定不该发生，那是调用之前要做的决定，不是循环内部的分支。

    正常工作的标志

    • 解决过程中，智能体会向你引用提交信息、PR 或工单，而不只是 diff hunk。
    • 每个 hunk 最终要么保住双方的行为，要么带一条明确的注记，写明丢了什么、为什么丢。
    • 结果里不会出现任何两边分支上都没有的东西。
    • 智能体找到了 typecheck、测试和格式化，并 在提交之前 把它们跑绿，而不是等你发现东西坏了之后。
    • 你在干净的工作树上收尾，操作完整完成，包括多次提交的变基里余下的每一次提交。

    它的定位

    一个随时可用的独立技能，不依赖任何其他技能：git 卡住时开始，工作树干净并已提交时结束。它唯一真正的邻居是 diagnosing-bugs——当合并干净地解决了、合并进来的代码却表现异常时由它接管：那是诊断问题，不是冲突问题。它在主要的想法到交付流程之外，所以 ask-matt 是它前后步骤的地图。
