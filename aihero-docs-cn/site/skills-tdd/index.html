    /tdd 技能

    红-绿-重构（red-green-refact或）循环的规则。

    它做什么

    tdd 以测试先行的方式构建功能或修复缺陷：先写一个失败的测试，再写刚好能让它通过的代码，然后是下一个行为。它载有一套标准，让这个循环产出的测试值得保留：什么才算好测试、测试放在哪里、mock 是干什么用的，以及会让整个测试套件一文不值的三种反模式。

    它不会在你尚未认可的接缝（seam）上写任何测试。在任何测试存在之前，它会先列出打算在其上测试的公共边界，然后停下来等你确认。测试的用力度是有限的，这一步会把它花在关键路径上，而不是每个边缘用例上。 tdd 同时也是一份 参考，而不是驱动器。它载有这套循环的规则，而真正动手运行的是别的东西（你，或者 implement）负责运行 会话 ，把这些规则付诸应用。

    何时使用

    输入 /tdd，或者 智能体 会在任务匹配时自动调用它：以测试先行的方式构建功能或修复缺陷，或者当你说出“red-green-refact或”的时候。

    当你要构建一个有输入、有可观察输出的具体行为，并且希望测试在重构之后依然成立时，就用它。

    你的情况该去哪里
    有明确输入与输出的行为（业务逻辑、请求/响应契约、转换、校验）tdd
    行为还没敲定to-规格（spec），它同样会在写任何代码之前先敲定测试接缝
    真正的问题是接口的形状，而不是测试codebase-design
    你手上已经有 规格（spec） 或 工单（ticket） ，希望整个构建都替你跑完implement，由它驱动 tdd 跑完每一张工单
    配置、接线、粘合代码、类型标注、纯粹的 CRUD 委托这里没有合适的选择；见下文的未解缺口

    最后一行是一个真实存在的缺口。这项技能决定的是接缝放在 哪里 ，但其中没有任何东西决定 一项变更 究竟值不值得走这套循环。如果你在一个没有独立事实来源可供断言的变更上运行它，得到的测试只会复述实现。这正是该技能警告的同义反复（tautological）反模式，只是从另一个方向踩进去。它被记录为 issue #746，目前仍未关闭。在它关闭之前，这个判断由你自己来做，或者把规则写进你的 CLAUDE.md.

    前置条件

    codebase-design 需要先安装。 tdd 过去自带深模块（deep module）与接口设计的笔记；v1.0 删掉了它们，改用共享技能，而 tdd 现在使用它的接口设计词汇。除此之外没有别的前置；该技能是 无状态（stateless） 的，也不会自己写任何文件。

    循环本身，以及它运行的接缝

    这项技能建立在三个术语之上。

    红-绿（red-green）。 先写失败的测试，再只写刚好让它通过的代码。不要为下下一个测试写代码。没有重构阶段。该技能在 2026 年 6 月去掉了它，因为智能体几乎从不执行这一步，而且把评审与实现分成两个会话效果更好。重构属于 code-review.

    垂直切片（vertical slice）。 在一条接缝上写一个测试，然后写最小实现，然后重复。第一个循环是一发 曳光弹（tracer bullet） ，端到端地验证一条路径。反面是水平切分（h或izontal slicing）：先写全部测试，再写全部代码。批量写出的测试验证的是 想象出来的 行为。它们检查的是东西的形状，而不是用户实际做什么，还会在你理解实现之前就把你绑死在一种测试结构上。

    预先约定的接缝（seam）。 接缝是你观察行为、却不伸进内部去的公共边界。这条规则没有例外。任何测试都不放在未经确认的接缝上。在完整链条里，接缝早在 to-规格（spec）: "/tdd 被要求只在预先约定的测试接缝上工作， /code-review 则会检查所用接缝确实都是约定过的。”单独调用时， tdd 会直接来问你。

    它写出来就是要防止的三种反模式：

    反模式识别特征
    实现耦合（implementation-coupled）重命名一个内部函数，测试就挂了，尽管行为并没有变。mock 内部协作者、断言调用次数、用数据库查询而不是接口来验证。
    同义反复（tautological）期望值是用代码计算它的同一种方式算出来的，于是测试从构造上就必然通过。期望值必须来自别处：一个已知正确的字面量、一个算过的例子、规格（规格（spec））。
    水平切分（h或izontal slicing）一批测试在任何实现之前就已落地。

    mock 只用于系统边界：外部 API、时间、随机性，有时还有文件系统或数据库。绝不 mock 你自己的模块。

    常见问题

    它为什么不重构？描述里明明写着“red-green-refact或”。

    因为被移除的是重构步骤，而不是描述。移除是有意的。智能体几乎从不执行这一步，而且把实现和评审放进分开的会话效果更好。结果按教科书标准还算不算 TDD，远不如这套循环能不能产出更好的代码重要。触发短语与正文之间的不一致已作为 issue #589 提交，至今仍未关闭，所以“red-green-refact或”仍能作为触发该技能的短语使用。你得到的是红-绿（red-green），重构则放在 code-review.

    它让我选一条测试接缝，我完全不知道该选哪条。

    这是该技能被报告最多的摩擦点（issue #607）。提示只按名字列出候选接缝，对每条接缝能抓到什么、漏掉什么只字不提，所以你其实是在几个标签之间做选择。目前还没有发布修复。实用的变通办法是回答之前先让智能体讲清权衡：组件级接缝会漏掉集成接缝能抓到的什么，速度又慢多少。这也是整条链条要在 to-spec里预先敲定接缝的原因——在那里你看到的是整个功能，而不只是一条提示。

    它先写了实现再写测试，尽管技能明说先红。

    这确实会发生。有用户就这一点追问 模型 ，得到了一个异常诚实的回答：“我知道技能写着‘一次一个测试，看着它以正确的原因失败’。我读了。我只是回到了自己的老习惯。”该技能接受这一点。没有任何指令能让智能体 100% 遵守，而更严厉的措辞只会以微小收益为代价限制智能体的创造力。即使智能体没有严格照做，这套循环也值得跑，因为总体结果仍然更好。如果某个切片确实需要严格遵守，那就盯着运行过程，而不是指望技能自己去强制执行。

    它应该先写浏览器或端到端测试吗？

    通常不该，技能也不会阻止它。有用户报告智能体先写了一个 Playwright 测试，然后在一条漫长的循环里反复重跑，最后断定是 测试 坏了——而那个功能根本还没写出来。浏览器测试足够慢，慢到红-绿的反馈回路不再划算。请在你仓库的 CLAUDE.md 里写明：浏览器测试要等到行为能工作之后再写。

    常见疑问： /tdd 会不会取代 /implement，还是课程里的 /do-work?

    不会。 /tdd 只是记录方法论； /implement 则是一个简单的工作→反馈→提交循环，是 /do-work的直接替身。课程里原来的单步 /do-work 这一步，现在拆分到了 /implement, /tdd 和 /code-review之中。如果你在纠结该对一张工单运行哪一个，答案几乎总是 /implement.

    深模块与接口设计的指引去哪了？

    进了 codebase-design （v1.0 起），并做了泛化，让多个技能共用一套词汇。 refactoring.md 同期移除；重构现在是 code-review的职责，该技能带有 Fowler 的坏味道（smell）基线。

    它知道我其他的工单吗？

    不知道。对着一张工单运行时，它可能提出本属于兄弟工单的工作，因为它看不到 issue 图的其余部分（issue #129）。这不是 tdd的职责。把规格（规格（spec））连同工单一起传给它有帮助；而一开始就把工单切到合适大小更有帮助。

    生效判据

    • 在任何测试文件存在之前，它就停下来列出打算在其上测试的接缝，并等待确认。
    • 一个测试出现、变红、拿到刚好让它通过的代码，然后下一个测试才出现——而不是一批测试跟着一批代码。
    • 测试名读起来是能力（“用户可以用有效购物车结账”），而不是内部细节（“结账会调用 paymentService.process”）。
    • 断言里的期望值是能追溯到规格（规格（spec））的字面量，而不是按代码的算法重新算出来的值。
    • 重命名一个内部函数，测试套件里什么都不会坏。
    • mock 只出现在外部边界（支付 API、时钟），从不出现在你自己的模块周围。

    适用位置

    tdd 运行在主链条构建步骤的内部，它本身不是一个独立步骤：

    grill-with-docs → to-spec → to-tickets → implement → code-review → retro

    to-规格（spec） 预先敲定测试接缝， implement 驱动 tdd 逐张工单跑，而 code-review 则会在事后检查所用接缝确实都是约定过的，并接管 tdd 已不再负责的重构。它的另一个邻居是 codebase-design——接缝与深模块词汇的共同出处， tdd 用的就是它。你也可以单独使用这项技能：只要有具体行为要构建，又没有完整规格（规格（spec））在身。当你拿不准哪个技能适合你的情况时， ask-matt 会为你指路。
