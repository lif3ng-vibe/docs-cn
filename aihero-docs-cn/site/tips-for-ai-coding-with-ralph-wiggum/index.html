    使用 Ralph Wiggum 进行 AI 编码的 11 条技巧

    用 Ralph Wiggum 以自主循环的方式运行 AI 编码工具。11 条 AFK 编码技巧：范围界定、进度追踪、反馈回路，以及在你睡觉时交付代码。

    如果你正在使用这类 AI 编码 CLI： Claude Code, Copilot CLI, OpenCode，以及 Codex，那么本文就是为你准备的。

    大多数开发者以交互方式使用这些工具：给它一个任务，看着它干活，在它跑偏时出手干预。这就是"人在回路"（HITL）编码。

    但有一种新方法叫作 Ralph Wiggum。Ralph 会让你的 AI 编码 CLI 循环运行，让它自主处理一列任务。你定义要做什么，Ralph 想清楚怎么做——并一直干到完成为止。换句话说，这是长时间运行、自主、无需监督的 AFK 编码。

    这不是一篇快速上手指南。想快速跑起来，请阅读 Ralph 入门.

    1. Ralph 就是一个循环

    在过去一年左右的时间里，AI 编码经历了几个界限分明的阶段。我们先简单定义一下：

    氛围编程（vibe coding） 是指你让 AI 写代码而不怎么检查。你和 AI 一起"找感觉"，不加审视地接受它的建议。速度很快，但代码质量会打折。

    规划 是指在写代码之前先让 AI 做规划。在 Claude Code中，你可以进入 计划模式（plan mode） ，让 AI 在写代码之前先探索你的代码库并制定计划。这能提升质量，但你仍然受限于单个 上下文窗口（context window）.

    多阶段计划 会把大型特性拆成多个阶段，每个阶段在独立的上下文窗口中处理。你为每个阶段写不同的提示词（prompt）："实现数据库模式"，然后"添加 API 端点"，再"构建 UI"。这种方式的扩展性更好，但需要人持续参与来编写每条提示词。

    Ralph 则把一切简化了。你不必为每个阶段写新提示词，而是把同一条提示词放在循环里反复运行：

    # ralph.sh

    # Usage: ./ralph.sh <iterations>

    

    set -e

    

    if [ -z "$1" ]; then

      echo "Usage: $0 <iterations>"

      exit 1

    fi

    

    # For each iteration, run Claude Code with the following prompt.

    # This prompt is basic, we'll expand it later.

    for ((i=1; i<=$1; i++)); do

      result=$(docker sandbox run claude -p \

    "@some-plan-file.md @progress.txt \

    1. Decide which task to work on next. \

    This should be the one YOU decide has the highest priority, \

    - not necessarily the first in the list. \

    2. Check any feedback loops, such as types and tests. \

    3. Append your progress to the progress.txt file. \

    4. Make a git commit of that feature. \

    ONLY WORK ON A SINGLE FEATURE. \

    If, while implementing the feature, you notice that all work \

    is complete, output <promise>COMPLETE</promise>. \

    ")

    

      echo "$result"

    

      if [[ "$result" == *"<promise>COMPLETE</promise>"* ]]; then

        echo "PRD complete, exiting."

        exit 0

      fi

    done

    每次迭代会：

    1. 查看计划文件，了解要做什么
    2. 查看进度文件，了解已经做了什么
    3. 决定下一步做什么
    4. 探索代码库
    5. 实现该特性
    6. 运行反馈回路（类型、lint、测试）
    7. 提交代码

    这里的关键改进在于： 由智能体（agent）来选任务，而不是你.

    在多阶段计划中，每个阶段开始时都要由人来写一条新提示词。而在 Ralph 中，智能体会从你的 PRD 里挑选下一个要做的任务。你定义最终状态，Ralph 负责到达。

    我用 Ralph 给我的 AI Hero CLI 添加过测试，也为我的 课程视频管理器构建过特性。还有人 用它构建了完整的编程语言 。

    2. 先从 HITL 开始，再进入 AFK

    运行 Ralph 有两种方式：

    模式工作方式适用场景脚本
    HITL （human-in-the-loop，人在回路）运行一次，观察，随时干预学习、打磨提示词ralph-once.sh
    AFK （away from keyboard，离开键盘）以最大迭代次数循环运行批量工作、低风险任务afk-ralph.sh

    对 HITL Ralph，保留一个 ralph-once.sh 脚本，只跑单次迭代。它做的一切你尽收眼底，需要时就出手干预。

    对 AFK Ralph，一定要给迭代设上限。对随机性系统来说，无限循环是危险的。小任务我通常用 5-10 次迭代，大任务则用 30-50 次。

    HITL Ralph 类似结对编程（pair programming）。你和 AI 一起工作，在代码生成的同时进行评审。你可以实时引导方向、贡献代码，并共享对项目的理解。

    这也是学习 Ralph 的最佳方式。在放手之前，你会理解它在做什么、打磨你的提示词，并建立信心。

    一旦你的提示词足够可靠，AFK Ralph 就能带来真正的杠杆效应。让它跑着，你去干别的，跑完再回来。

    我写了一个小 CLI，在 Ralph 完成时通过 WhatsApp 通知我。这大幅减少了上下文切换。我可以全身心投入另一项任务。我的循环通常耗时 30-45 分钟，有时也会跑上几个小时。

    进阶路径很简单：

    1. 先用 HITL 学习和打磨
    2. 信任你的提示词后再进入 AFK
    3. 回来后评审提交

    3. 定义范围

    在让 Ralph 跑起来之前，你需要定义"完成"长什么样。这是从规划到需求收集的转变：你不再指定每一步，而是描述期望的最终状态，让智能体自己想办法到达。

    定义范围的几种形式

    为 Ralph 定义范围有很多方式：

    • 一份 Markdown 格式的用户故事列表
    • GitHub issue 或 Linear 任务 （后文详述）
    • 使用 beads

    我喜欢的一种做法来自 Anthropic 关于长时间运行智能体的研究。他们把 PRD 条目结构化为 JSON，每条带一个 passes 字段：

    {

      "category": "functional",

      "description": "New chat button creates a fresh conversation",

      "steps": [

        "Click the 'New Chat' button",

        "Verify a new conversation is created",

        "Check that chat area shows welcome state"

      ],

      "passes": false

    }

    任务完成后，Ralph 会把 passes 标记为 true 。这样 PRD 就既是范围定义，又是进度追踪器——一份活着的 TODO 清单，而不是瀑布式文档。

    为什么范围很重要

    你倒不 一定需要 一份结构化的 TODO 清单。你可以给 Ralph 一个模糊的任务——"改进这个代码库"——让它自己追踪进度。

    但任务越模糊，风险越大。Ralph 可能永远循环下去，找出无穷无尽的改进点。也可能走捷径，在你还没认为完工之前就宣布胜利：

    我曾用 Ralph 来提升我 AI Hero CLI的测试覆盖率。这个仓库有一些内部命令——被标记为内部，但实际面向用户（我自己就在用）。我希望所有命令都有测试。

    三次迭代之后，Ralph 报告："所有面向用户的命令都完成了。"但它完全跳过了内部命令。它自行认定这些命令不算面向用户，并把它们标记为覆盖率统计要忽略的对象。

    怎么解决？精确定义你想要覆盖的范围：

    要指定什么为什么能防止走捷径
    要包含哪些文件Ralph 不会无视"边界情况"文件
    停止条件Ralph 知道"完成"什么时候才是真的完成
    边界情况Ralph 不会自行认定某些事情不算数

    运行中途调整 PRD

    这种做法的一个好处：你可以在 Ralph 运行过程中进行调整。

    • 已经实现但不对？把 passes 改回 false，加上备注，再跑一次。
    • 缺了一个特性？哪怕循环正在进行，也可以添加新的 PRD 条目。

    你编辑的不是一份线性的多阶段计划，而是在描述另一种最终状态。Ralph 会到达那里。

    只要范围和停止条件都足够明确，Ralph 就知道什么时候该输出 <promise>COMPLETE</promise>.

    试一试

    使用计划模式，并为你的下一个特性创建一个 prd.json 文件。用下面这段提示词来生成结构化的 PRD 条目：

    Convert my feature requirements into structured PRD items.

    Each item should have: category, description, steps to verify, and passes: false.

    Format as JSON. Be specific about acceptance criteria.

    4. 追踪 Ralph 的进度

    我运行的每个 Ralph 循环都会生成一个 progress.txt 文件，直接提交进仓库。这一灵感来自 Anthropic 关于 长时间运行智能体 harness 的文章.

    这解决了一个核心难题：AI 智能体就像超级聪明的专家，任务一换就忘得一干二净。每个新的上下文窗口都从零开始。没有进度文件，Ralph 就得探索整个仓库才能了解当前状态。

    进度文件直接省掉了这种探索。Ralph 读完它，看到哪些已完成，然后直奔下一个任务。

    进度文件里写什么

    保持简单精炼：

    • 本次会话完成的任务
    • 做过的决定及其原因
    • 遇到的阻塞项
    • 改动的文件

    还可以加入刚完成的 PRD 条目、任何架构决策，以及给下一次迭代的备注。

    为什么提交很重要

    Ralph 应该在每个特性完成后提交。这能给后续迭代带来：

    • 一份干净的 git log ，清楚展示改了什么
    • 用 git diff 对比之前工作的能力
    • 出问题时有一个回滚点

    进度文件加 git 历史的组合，让 Ralph 无需在探索上烧 标记为ken 就能获得完整上下文。

    清理

    别一直留着 progress.txt 。冲刺结束后就删掉它。它是会话级的，不是永久文档。

    试一试

    在 Ralph 提示词中加入进度追踪：

    After completing each task, append to progress.txt:

    - Task completed and PRD item reference

    - Key decisions made and reasoning

    - Files changed

    - Any blockers or notes for next iteration

    Keep entries concise. Sacrifice grammar for the sake of concision. This file helps future iterations skip exploration.

    5. 使用反馈回路

    Ralph 的成败取决于反馈回路。你给它的回路越多，它产出的代码质量越高。

    反馈回路的类型

    反馈回路能捕获什么
    Type脚本 类型类型不匹配、缺少 props
    单元测试逻辑损坏、回归
    Playwright MCP 服务器UI bug、交互损坏
    ESLint / lint代码风格、潜在 bug
    pre-commit 钩子彻底拦下坏提交

    最好的配置是：全部通过才允许提交。测试还是红的，Ralph 就无法宣布胜利。

    为什么反馈回路很重要

    优秀的程序员不相信自己的代码，不相信外部库，尤其不相信同事的代码。他们会构建自动化和检查机制来验证自己交付的东西。

    这种谦逊造就更好的软件。AI 智能体同理。

    本文的每条技巧对人类开发者同样适用。反馈回路、小步前进、明确的范围——这些都不是 AI 专属技术，只是良好的工程实践。Ralph 让它们成为不可协商的硬性要求。

    试一试

    在 Ralph 提示词中加入明确的反馈回路要求：

    Before committing, run ALL feedback loops:

    1. TypeScript: npm run typecheck (must pass with no errors)

    2. Tests: npm run test (must pass)

    3. Lint: npm run lint (must pass)

    Do NOT commit if any feedback loop fails. Fix issues first.

    6. 小步前进

    你能获得反馈的速度就是你的速度上限。永远别冲出车灯照亮的范围。

    人类做大重构时可能一口吞下大块工作然后一路推完。测试、类型和 lint 一红就是几个小时。把工作切成更小的块意味着更紧凑的反馈回路——收到反馈之前要做的活更少。

    这对 Ralph 同样适用，但多了一条约束：上下文窗口有限，而且越填满 LLM 表现越差。这被称为 上下文腐坏（context rot） ——拖得越久，输出越蠢。

    权衡

    每次 Ralph 迭代都有启动成本。Ralph 要挑任务、探索仓库、收集上下文。这些 标记为ken 在每轮循环里都要花一次。

    如果你在做大型重构，肯定不希望 Ralph 每次迭代只重命名一个变量。但是：

    • 更大的任务意味着反馈频率更低
    • 更多的上下文意味着更低的代码质量
    • 更小的任务意味着更高质量，但进度更慢

    把握 PRD 条目的大小

    对 AFK Ralph，PRD 条目要保持小。你不盯着的时候，要让智能体处于最佳状态。

    对 HITL Ralph，可以把条目稍微放大一点，更快看到进展。但即便如此，也宁可偏小。

    一个重构条目可以简单到："修改某个函数的参数。验证测试和类型通过。"

    在提示词里引导 Ralph 控制步子大小。我的倾向：小步走。代码质量优先于速度——AFK 时尤其如此，反正那时速度也没那么重要。

    试一试

    在 Ralph 提示词中加入步子大小的指引：

    Keep changes small and focused:

    - One logical change per commit

    - If a task feels too large, break it into subtasks

    - Prefer multiple small commits over one large commit

    - Run feedback loops after each change, not at the end

    Quality over speed. Small steps compound into big progress.

    7. 优先处理高风险任务

    Ralph 自己挑任务。没有明确指引时，它常常会选列表里的第一项，或看起来最容易实现的东西。

    这和人类的行为如出一辙。开发者都喜欢速赢。但经验丰富的工程师知道，要先啃下硬骨头，免得简单工作把你埋进技术债里。

    技术探测（spike）与集成

    专注于 spike——那些你不知道结果会怎样的东西。按端到端的方式构建特性，而不是一层层来。尽早集成。

    如果有需要协同工作的模块，让 Ralph 先把它们集成起来。别等到冲刺结束才发现它们合不上。

    任务类型优先级原因
    架构工作高决策会波及整个代码库
    集成点高尽早暴露不兼容问题
    未知的未知高早失败好过晚失败
    UI 打磨低之后可以并行处理
    速赢项低随时都能插进来

    高风险任务用 HITL

    高风险任务需要更多人参与。早期的架构决策请用 HITL Ralph——这些任务产出的代码会一直留存，这里走的任何捷径都会波及整个项目。

    把 AFK Ralph 留到地基稳固之后。一旦架构得到验证、高风险集成跑通，就可以让 Ralph 无人监督地处理低风险任务。

    试一试

    在 Ralph 提示词中加入优先级指引：

    When choosing the next task, prioritize in this order:

    1. Architectural decisions and core abstractions

    2. Integration points between modules

    3. Unknown unknowns and spike work

    4. Standard features and implementation

    5. Polish, cleanup, and quick wins

    Fail fast on risky work. Save easy wins for later.

    8. 明确定义软件质量

    并非所有仓库都一个样。世面上很多代码是原型代码——demo、短命的实验、给客户的提案。不同仓库对质量的要求不同。

    智能体不知道自己身处什么样的仓库。它不知道这是一次性的原型，还是要维护多年的生产代码。你需要明确告诉它。

    要传达什么

    仓库类型怎么说预期行为
    原型"这是个原型。速度优先于完美。"走捷径，跳过边界情况
    生产环境"生产代码。必须可维护。"遵循最佳实践，补上测试
    库"公开 API。向后兼容很重要。"谨慎对待破坏性变更

    把这一点写进你的 AGENTS.md 文件、你的技能，或直接写进提示词。

    仓库说了算

    你的指令会和你的代码库竞争。当 Ralph 探索你的仓库时，它看到两个真相来源：你叫它做的事，和你实际做的事。一个只有几行指令，另一个却是几千行证据。

    你可以在提示词里写"永远不要用 any 类型"。但如果 Ralph 看到 any 遍布你现有的代码，它就会跟随代码库，而不是你的指令。

    智能体会放大它们看到的东西。糟糕的代码产出更糟糕的代码。低质量的测试产生不可靠的反馈回路。

    这就是软件熵——代码库随时间推移而退化的趋势。Ralph 会加速这一过程。人类可能一天提交一两次，Ralph 却能在几小时内往仓库里堆几十个提交。如果这些提交质量低下，熵会迅速累积。

    这意味着你需要：

    • 在放开 Ralph 之前保持代码库干净
    • 用反馈回路（lint、类型、测试）来执行标准
    • 让质量期望明确且可见

    试一试

    把质量期望加入你的 AGENTS.md 或 Ralph 提示词：

    This codebase will outlive you. Every shortcut you take becomes

    someone else's burden. Every hack compounds into technical debt

    that slows the whole team down.

    

    You are not just writing code. You are shaping the future of this

    project. The patterns you establish will be copied. The corners

    you cut will be cut again.

    

    Fight entropy. Leave the codebase better than you found it.

    9. 使用 Docker 沙箱

    AFK Ralph 需要编辑文件、运行命令、提交代码的权限。是什么阻止它运行 rm -rf ~？你不在键盘旁，根本无法干预。

    Docker 沙箱 是最简单的解决方案：

    docker sandbox run claude

    这会在容器里运行 Claude Code 。你的当前目录会被挂载，其他一概不会。Ralph 能编辑项目文件并提交——但碰不到你的主目录、SSH 密钥或系统文件。

    代价是：你的全局 AGENTS.md 和用户技能不会被加载。对大多数 Ralph 循环来说，这没什么影响。

    对 HITL Ralph，沙箱是可选的——反正你在盯着。对 AFK Ralph，尤其是过夜循环，沙箱是防范智能体失控的必要保险。

    10. 付费进场

    我被问得最多的一个问题是："这要花多少钱？"让 AFK Ralph 跑一整夜，肯定会产生巨额账单吧？

    给理财建议总让我不自在，尤其是对低收入地区的朋友。但 Ralph 花多少钱完全由你自行配置。

    HITL 仍然值得

    就算你从不跑 AFK Ralph，HITL Ralph 也比多阶段规划有显著优势。反复运行同一条提示词，比给每个阶段单独写提示词舒服多了。

    方式每阶段投入适用场景
    多阶段计划写新提示词一次性的大任务
    HITL Ralph重跑同一条提示词学习、打磨
    AFK Ralph设定后放手批量工作、自动化

    我用的是 Anthropic 5x Max 套餐，大约每月 90 英镑。AFK Ralph 我跑过几次，但大部分使用都是 HITL。

    为什么不用本地模型？

    我认为能在笔记本上运行的开源模型对 Ralph 来说还不够好。它们需要强大的 GPU，输出质量也不到位。在 AI 编码里，你得付费进场。

    黄金时代

    但要把这件事放到语境里看。未来几年，我们处在一个黄金时代：用 AI 做神奇的事可以比人类更快——但市场仍按人类工资付酬。市场还没有适应一个事实：我们都已能用上极其强大的 AI 编码工具。

    是的，你得花钱。但只要你愿意去取，回报就在那里。

    11. 打造属于你的 Ralph

    Ralph 只是一个循环。这份简单让它有无限的可配置性。下面是一些把它变成你自己的方法：

    更换任务来源

    本文示例用的是本地 prd.json。但 Ralph 可以从任何地方拉取任务：

    任务来源工作方式
    GitHub IssuesRalph 挑一个 issue 并实现它
    LinearRalph 从你的冲刺中拉取
    BeadsRalph 沿着 beadfile 逐项处理

    核心洞见不变：由智能体选任务，而不是你。你只是改变了这份清单存放的位置。

    改变产出方式

    Ralph 的每次迭代可以不直接提交到 main 分支，而是：

    • 创建分支并开一个 PR
    • 在现有 issue 下添加评论
    • 更新变更日志或发布说明

    当你有一堆 issue 等着变成 PR 时，这很有用。Ralph 分诊、实现并开出 PR，你在准备好之后评审。

    替代循环类型

    Ralph 不必非得清特性队列。下面是我一直在试验的一些循环：

    测试覆盖率循环：让 Ralph 盯着你的覆盖率指标。它找出未覆盖的行、编写测试，并不断迭代直到覆盖率达到目标。我用这个方法把 AI Hero CLI 的覆盖率从 16% 提到了 100%。

    重复代码循环：把 Ralph 接上 jscpd 来查找重复代码。Ralph 会识别克隆代码，重构成共享工具函数，并报告改了什么。

    Lint 循环：把 lint 错误喂给 Ralph。它逐个修复，并在迭代之间运行 linter 验证每个修复。

    熵循环：Ralph 扫描代码异味——未使用的导出、死代码、不一致的模式——并把它们清理掉。这是逆向的软件熵。

    任何能描述为"看看仓库、改进点什么、汇报发现"的任务都符合 Ralph 模式。循环不变，变的只是提示词。

    试一试

    试试这些替代循环提示词：

    # Test Coverage Loop

    @coverage-report.txt

    Find uncovered lines in the coverage report.

    Write tests for the most critical uncovered code paths.

    Run coverage again and update coverage-report.txt.

    Target: 80% coverage minimum.
    # Linting Loop

    Run: npm run lint

    Fix ONE linting error at a time.

    Run lint again to verify the fix.

    Repeat until no errors remain.
    # Entropy Loop

    Scan for code smells: unused exports, dead code, inconsistent patterns.

    Fix ONE issue per iteration.

    Document what you changed in progress.txt.
