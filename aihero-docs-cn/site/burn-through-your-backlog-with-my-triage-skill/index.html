    triage：把混乱的待办变成智能体可执行的工作

    了解如何使用 Triage 技能整理 GitHub issue，把零散想法变成智能体可执行的任务，高效管理待办工作。

    它做什么

    triage 会逐一处理你项目工单追踪器（issue tracker）上的 issue。它让每个 issue 在一个由 triage 角色 （一个分类角色和一个状态角色）组成的小状态机中流转。每个 issue 最终变成一份智能体可执行的简报、一个给报告者的具体问题，或一个记录了理由的已关闭 issue。

    它只用于 不是你自己创建的 issue。也就是原始 bug 报告、送上门的功能请求，或不请自来的外部 PR：从外部进入工单追踪器、保持报告者留下时原样的工作。 由 生成的工单 to-tickets 已经是智能体可执行的，所以再对它们跑 triage ，就是浪费之前的功夫。规则很简单： /triage 只处理外部进来的 issue，不处理你自己创建的 issue。

    它和手工打标签也不同：它先给出建议，然后等待。它会告诉你分类和状态的判断及理由，加上它在代码库里的发现，在你发话之前什么都不改。

    什么时候用它

    调用方式是输入 /triage ，然后用大白话描述你想要什么。 智能体 不会自己主动调用它。示例："给我看需要我关注的东西"、"我们看看 #42"、"把 #42 移到 ready-for-智能体"。

    你手上的东西该去哪里
    工单追踪器里塞满别人提交的原始报告/triage
    自己有个粗略想法，还没落笔grill-with-docs
    一段已有结论的对话，想变成 规格（spec）to-规格（spec）
    一份想拆成智能体可执行工单的规格to-tickets

    前置条件

    triage 会读写你的工单追踪器，所以 setup-matt-pocock-技能s 必须先配置好该追踪器及其标签词汇。下面的角色名是 规范名（canonical）。你追踪器里的标签字符串可能不同，setup 会提供映射。如果你的追踪器已经在用一模一样的规范名，就无需映射、无需配置。

    追踪器配置还决定外部 PR 是否算一种请求入口，以及谁算外部。该开关默认关闭，setup 也不再询问。要把 PR 纳入范围，请在 docs/agents/issue-tracker.md.

    状态机

    每个完成分诊的条目都恰好带一个分类角色和一个状态角色。分类有两种： bug （有东西坏了）和 enhancement （新特性或改进）。状态有五种：

    状态含义
    needs-triage你需要评估它。没有标签的 issue 通常先落在这里。
    needs-info等报告者回复。对方回复后回到 needs-triage 。
    ready-for-agent规格完整，附有智能体简报。 AFK 智能体可以直接接手。
    ready-for-human同样的简报，外加为什么智能体做不了：需要判断力、需要外部访问、需要手工测试。
    wontfix已关闭，理由已记录。

    以上就是全部词汇。每个条目恰好一个状态角色的规则让查询保持简单。状态也是这个 技能中被要求最多的地方。用户想要一个表示"已定规格但被另一个 issue 阻塞"的状态，一个 deferred 表示"等待未来触发器"的状态，以及一个表示终局的 implemented 状态。这些都没上线。见下面的常见问题。

    wontfix 有三种情况。区别很重要，因为只有其中一种会写入知识库：

    关闭原因会发生什么
    已经实现留一条评论指出该特性已存在的位置。不往 .out-of-scope/里写任何东西，因为这是已建成的特性，不是被拒绝的，在那里放文件会破坏去重检查。
    被拒绝的 bug礼貌解释，然后关闭。
    被拒绝的增强请求在 .out-of-scope/中放一个文件，从关闭评论链接到它，然后关闭。

    .out-of-scope/ 为每个被拒绝的 概念（concept）保存一份 Markdown 文件，而不是每个 issue 一份。每份文件是一篇简短的设计文档，不是数据库行。它记录拒绝了什么、为什么，并列出提出过该需求的每一个 issue。 triage 在评估任何东西之前会先读完整个目录。它按概念匹配，不按关键词，所以"夜色主题"能匹配 dark-mode.md。找到匹配时，它会给你看旧决定并问你是否仍然同意，而不是从头再争一遍这个请求。

    先核实再写简报

    在任何 追问（grilling）, triage 开始之前，它都会先核实主张是否成立。对 bug，它按报告者的步骤复现；对 PR，它检出分支并运行相关测试。然后报告三种结果之一：

    • 已确认，附代码路径。
    • 无法复现。
    • 细节不够，无从下手。这是最有力的 needs-info 信号。

    在同一轮里，它还会对代码库做另外两项检查。 冗余（redundancy） 检查会问该特性是否已经实现，按领域概念而非报告者的措辞来搜索。 既往拒绝（prior rejection） 检查会问 .out-of-scope/ 是不是已经说过不。两项检查都很便宜，任一命中就会产出 wontfix.

    这一整套工作成就一个关键产物： 智能体简报（智能体 brief）。这是一条结构化评论，由 triage 在 issue 移到 ready-for-agent时发布。 triage 发布之后，简报就是契约，原始报告只是背景。简报追求 耐久（durable） 而非精确，因为一个 issue 可能会在 ready-for-agent 里一待几周，而代码早已变化。所以简报写类型、签名和行为契约，绝不写文件路径或行号。一次确认过的复现，能让简报远比猜测有力。

    PR 就是带着代码的 issue

    如果追踪器把外部 PR 也当作请求入口，它们会走同一套状态机，用相同的分类、状态和流转。状态作用于 diff。 ready-for-agent 表示已附简报，智能体应该对代码迈出下一步。 ready-for-human 表示人可以合并它了。PR 上的简报描述的是对现有 diff 还剩什么要做，而不是如何从零造出这东西。

    发现视图只显示 外部 PR，因为协作者进行中的分支不算分诊工作。该过滤只作用于发现视图。如果你明确点名某个 PR， triage 都会处理，不管是谁写的。

    常见问题

    我跑了 /to-spec 和 /to-tickets，现在那些工单还没分诊地待在那里。我要对它们跑 /triage 吗？ 不用。它们已经是智能体可执行的。 to-tickets 发布它们时会打上 ready-for-agent 标签，所以 AFK 运行器无需再过一遍就能接手。遇到这个问题的用户跑过规格流程，看到输出上是 needs-triage ，而他们的 AFK 运行器把所有东西都忽略了。 triage 是外来工作的入口坡道（入口坡道（on-ramp））。规格流程是你自己发起工作的车道。两条路在 ready-for-agent汇合，不会更早。

    它 triage 现在还有用吗？既然有了 to-spec → to-tickets → implement 流程。 只有当你有外部来件时才有用。 triage 比那个流程更早出现，干的也是另一件事：处理别人提交的报告。如果你追踪器里的一切都出自你自己的规划，你很少会用到它。只要你维护任何公开的东西，或你的团队向你报 bug，工作就从这里开始。它的主要用武之地是接受外部贡献者提 issue 的开源仓库。

    智能体试图打 ready-for-agent 和 gh 却说标签不存在。 这是一个已知的未修复 bug：#616). setup-matt-pocock-skills 会把标签词汇写进 docs/agents/triage-labels.md，但不会在你的追踪器里创建标签。用 gh label create 或追踪器的 UI，自己一次性创建那五个状态标签和两个分类标签，报错即止。该 issue 链接到一个尚未合并的社区修复分支。

    五种状态不够用。blocked、deferred、implemented 怎么办？ 这是这个技能被提得最多的缺口。有三种形式：

    • 规格完整但要等另一个 issue 关闭的 issue（#139）。报告者说 ready-for-agent 在那里"技术上成立"但有误导性，于是智能体接手然后卡住。
    • 有意做但要等触发器的未来工作，目前还无法执行（#297).
    • 给"已实现、待验证"的终局状态。没有它，AFK 运行器可能把已完成的工单再次排队。

    阻塞的情况被承认是真实需求，但名字未定（blocked 还是 paused）。这些都还没上线。作为变通，人们在分类旁边加一个仓库本地的额外标签。状态槽里的值仍然准确，但技能并不知道这个额外标签。一个社区 fork 走得更远，加了 needs-slicing, tracking 和 effort 标签。能跑，但那属于那个 fork，不属于本技能。

    这和 /diagnosing-bugs? 这里的核实步骤刻意保持浅层。它回答"这是真的吗，大概在哪个位置"，不找根因。如果一个 bug 按报告者的步骤几分钟内复现不了，用 needs-info，或者用 diagnosing-bugs （如果你想现在就深入调查）。两个技能的文本目前都还没提到对方。有用户报告了这个缺口，仍未解决。

    我能让它对着整个待办队列跑起来吗？ 你可以这么要求，但要留意它读了什么。"给我看需要关注的东西"这一轮只是为 筛选（selection）做的廉价列表。你挑一个 issue，然后 triage 才收集它的完整 上下文 。如果你一次性对二十个 issue 这么干，智能体可能把那份廉价列表当作唯一证据而不告诉你。列表只返回 issue 正文，不含评论。有用户正好踩中这个坑：三个 issue 本来已有评论说"已修复，建议关闭"，结果三个都被写了新的智能体简报。做批量处理时，请明确要求它必须读每个 issue 的评论。

    它能配合 Linear 或 GitHub 它sues 以外的工具吗？ 可以。追踪器是配置项，不是硬编码假设。有人通过 linear CLI）、GitLab，以及 .scratch/下的纯 Markdown 文件来运行它。常见分工是：Linear 管 issue 和规划，GitHub 管代码和 PR。写"issue tracker"的技能就映射到 Linear，写"PR"的技能映射到 GitHub。本地 Markdown 追踪器有一个未修复的模板 bug：生成的文件可能把验收标准写两遍，一遍在顶层，一遍在智能体简报里（#200).

    正常工作的标志

    • 它碰过的每个条目都恰好带一个分类角色和一个状态角色，不会是零个，也不会是两个互相冲突的状态。
    • 它给出带理由的建议然后停下，不会擅自改掉标签继续走。
    • 在任何东西进入 ready-for-agent.
    • 它写的简报点名类型和行为，不含文件路径和行号。
    • 当你六个月前拒绝过的请求再次出现，它会告诉你并引用旧理由，而不是重新分诊一遍。
    • 它发布的每条评论都以 > *This was generated by AI during triage.*

    它的定位

    triage 是一个 入口坡道（on-ramp），不是主链路上的一步。主流程从你自己的一个想法开始（grill、规格（spec）、工单、实现、评审）。 triage 是外来工作的并行车道。两条车道终点相同：一个被打上 ready-for-agent 标签、附有简报的 issue。 implement 会接手它，就像接手来自 to-tickets的工单一样。当一个请求在 triage 能为它写简报之前还需要更多细节时， triage 它会运行 追问（grilling） 和 domain-modeling ，一次一轮问题，这样它会把决策随时记录到 GLOSSARY.md 和 ADR 里。当你不确定自己在哪条车道时， ask-matt 会给你指路。
