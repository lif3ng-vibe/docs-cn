# 内存问题分类与复现

## 1. 对内存问题分类

请勾选最符合实际观察到的内存行为的选项：

- [ ] 内存随流量增长（由 RPS 驱动）
- [ ] 流量没有增加，内存却在上涨
- [ ] LiteLLM 升级后内存增加
- [ ] 内存泄漏（内存随时间持续增长）
- [ ] 出现内存溢出（OOM）事件或 Pod 重启

---

## 2. 问题能否复现？

在将问题上报之前，请先确认内存或 OOM 问题能否在与生产部署一致的测试环境中复现。

如果能复现，请提供**详细的复现步骤**，以及相关的请求、工作负载或所用配置。
关于我们需要哪些信息的说明，请参阅 [LiteLLM 故障排查指南](../troubleshoot)。

---

## 3. 问题无法复现

如果内存或 OOM 问题在与生产环境一致的测试环境中无法复现，请提供：

1. **第 1、2 节的信息**
   - 内存/问题分类（第 1 节）
   - 复现尝试与环境详情（第 2 节）

2. 便于排查的**补充上下文**：
   - **工作负载**（Workload）：尖峰出现前及期间处理的真实请求样本，包括近期的任何配置变更。
   - **指标**（Metrics）：内存使用量、CPU 使用量、P50/P99 延迟，以及任何 Pod 重启或 OOM 事件。请尽可能附上指标的**截图**。
   - **日志 / 告警**（Logs / Alerts）：在尖峰**出现前及期间**捕获到的所有相关日志或告警；如手头有 OOM 报错或堆栈跟踪，请一并附上。

> 提供这些信息后，团队才能分析规律，把内存尖峰或 OOM 与流量、配置关联起来，并在内部尝试复现该问题。缺少这些信息，我们的工程师将没有足够的依据来排查问题。
