# 发布周期

LiteLLM 代理服务器（Proxy）遵循以下发布周期：

- `1.x.x-dev.N`（nightly，夜间版）：通过 CI/CD 的发布版本（无人工审查）。以 `1.x.x.devN` 的形式发布到 PyPI。
- `1.x.x-rc.N`（release candidate，候选版）：通过 CI/CD、[人工审查](https://github.com/BerriAI/litellm/discussions/8495#discussioncomment-12180711)、性能测试（待落地，即将实现），并为早期测试者留出 7 天问题提交窗口的发布版本。以 `1.x.xrcN` 的形式发布到 PyPI。
- `1.x.x`（stable，稳定版）：已通过上述全部环节的 `rc`，再经第二轮人工测试后晋升为稳定版。

生产环境中，建议将版本固定在最新的稳定版 `1.x.x` 上。

:::info[自 1.84.0 起版本命名方式变更]

`-stable` 与 `-nightly` 后缀已取消。稳定版现在是纯粹的 PEP 440 / SemVer 2.0 版本号（例如 `1.84.0`）；每周例行发布递增**次版本号**（MINOR）**，补丁号**（PATCH）则保留给热修复。Docker 同时发布裸版本号（`1.84.0`）与带 `v` 前缀（`v1.84.0`）两种标签，二者指向同一镜像；PyPI 只采用裸 PEP 440 形式（`1.84.0`，绝不会出现 `v1.84.0`）。以旧命名发布的版本（`v1.83.x-stable` 等）永久保留、始终可用。

新旧版本名的完整对照见 [LiteLLM 发布版本命名调整](https://docs.litellm.ai/blog//blog/cleaner-release-versions)。

:::

发布说明见[这里](https://github.com/BerriAI/litellm/releases)。

## 每周发布安排

每周都对同一条版本线执行同一套循环。第一份夜间（`dev`）构建通常在周二产出，开启下一个次版本号（例如 `1.86.0`），此后每一版构建都沿用这个基础版本号，直到它作为稳定版发布。周中还有第二份夜间构建，通常在周四。周六切出候选版（`1.86.0rc1`），进入约一周的早期测试者与 QA 窗口。再下一周的晚些时候（周五或周六），前一周的 `rc` 去掉后缀晋升为稳定版（`1.85.0rc1` 变为 `1.85.0`），内容与该 `rc` 完全相同，除非有修复被回移进来。因此每个周六都身兼两职：切出本周的 `rc`，同时把上周的 `rc` 转正为稳定版。

| 日期 | 发布内容 |
| --- | --- |
| 周二 | 第一份夜间 `dev` 构建；开启下一个次版本号（`1.86.0.dev1`） |
| 周四 | 第二份夜间 `dev` 构建，内容累加（`1.86.0.dev2`） |
| 周六 | 切出新 `rc`（`1.86.0rc1`）；上周的 `rc` 晋升为稳定版 |
| 下周二 | 下一条版本线的第一份夜间构建开启（`1.87.0.dev1`）；循环重新开始 |

如果周六的 `rc` 未通过 QA，就不会晋升；待修复合入后可能再切一个后续 `rc`，发布节奏由此继续推进。


## 常见问题（FAQ）

### LiteLLM 稳定版有固定的发布时间表吗？

稳定版每周发布一次（通常在周日）。每次例行发布的稳定版都会递增 MINOR 版本号：`1.84.0` → `1.85.0` → `1.86.0`。

### 次版本号（minor）递增与补丁号（patch）递增分别指什么？

自 `1.84.0` 起（见[版本命名博客文章](https://docs.litellm.ai/blog//blog/cleaner-release-versions)）：

- 次版本号（minor）递增：每周例行的稳定版发布（`1.84.0` → `1.85.0`）。这是常规发布节奏，可能包含新的向后兼容功能或数据库表。
- 补丁号（patch）递增：保留给当前稳定版的热修复（`1.84.0` → `1.84.1`）。
- 主版本号（major）递增：破坏向后兼容性（`1.x.x` → `2.x.x`）。

### 企业版支持

:::info[支持模式将于 2026 年 5 月 18 日变更]

随着 LiteLLM 不断发展，现有的专业支持模式已无法匹配我们的规模。我们正在转向一种新模式，核心是清晰、可预期地向客户传达何时能获得支持与变更。下文描述的模式即将废弃，新体系的细节将在未来几周敲定后公布。

:::

- 稳定版每周发布一次。新版本一旦可用，旧版本即不再提供支持。
- 如果出现主版本（MAJOR）变更（按 semver 惯例，例如 1.x.x → 2.x.x），上一个稳定版镜像最长可继续提供 90 天支持。
