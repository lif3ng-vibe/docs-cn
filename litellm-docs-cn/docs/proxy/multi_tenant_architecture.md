# 使用 LiteLLM 的多租户架构

## 概览

LiteLLM 的多租户（multi-tenancy），指的是用同一个代理服务器服务公司内部多个彼此独立的租户（组织、团队、部门），同时让它们的访问权限、花费和用量互不干扰。这个网关是通往所有 LLM 提供商的共享入口，每个请求都携带租户上下文，由它决定该请求能调用哪些模型、从哪个预算扣费、成本记在谁的账上。

只要不止一个团队共用一个 LLM 网关，就会遇到几个必须解决的问题。成本要归到正确的业务部门名下，而不是混在一起；访问权限要按租户区分，因为每个团队需要的模型、预算和速率限制（rate limit）都不同；管理权要能下放，让团队负责人无需平台级管理员权限就能管好自己的团队；这套架构还得能从几个用户平滑扩展到数万人，而无需推倒重来。

:::info[开源版与企业版]
团队和虚拟密钥（virtual key）在开源版中即可使用，仅靠团队也能充当你的顶层租户边界。组织（Organization）和组织管理员则在其上再加一层层级，属于企业版功能（[申请 30 天试用](https://www.litellm.ai/#trial)）。
:::

## 多租户层级

<TenancyDiagram />

LiteLLM 将租户关系建模为四层嵌套：组织包含团队，团队包含用户，密钥归用户和团队所有。每一层都是一个边界，既用于隔离，也用于花费归属。

- 组织是顶层的租户，可以容纳多个团队。[API 参考](https://docs.litellm.ai/api-reference/#/organization%20management)
- 团队是用户的集合，可以容纳多个用户。[API 参考](https://docs.litellm.ai/api-reference/#/team%20management)
- 用户属于团队（可以同时属于多个），并可拥有多个密钥。[API 参考](https://docs.litellm.ai/api-reference/#/Internal%20User%20management)
- 密钥用于认证请求，归属于某个用户、某个团队，或两者兼有。[API 参考](https://docs.litellm.ai/api-reference/#/key%20management)

### 组织

组织是最高层级的隔离单位，通常对应一个业务部门或一个地区。组织之间看不到彼此的数据和密钥；每个组织都有自己的预算和可用模型列表，并由自己的组织管理员管理，而这些管理员只管辖组织内部的团队。组织属于企业版功能。

### 团队

团队是一起协作的用户组成的逻辑分组，也是开源版中最主要的租户边界。团队有自己的预算和速率限制、自己的管理员、自己的模型访问控制，以及供共享工作负载使用的服务账号密钥（service account key）。团队一旦位于某个组织之内，就会继承该组织的约束：不能超出组织预算，也够不到组织不允许的模型。

### 用户

用户是归属于一个或多个团队、创建或使用密钥的个人。花费按用户逐一追踪，用户能做什么由其角色决定：从普通内部用户，到团队管理员和组织管理员，直至平台级的代理管理员。删除用户时，其个人拥有的密钥会被一并删除。

### 密钥（虚拟密钥）

虚拟密钥是认证请求并将其绑定到某个租户进行花费追踪的凭证。密钥可以只绑定用户、只绑定团队（即成员变动后依然有效的服务账号密钥），或同时绑定两者。各类密钥的完整说明及适用场景，见[服务账号](./service_accounts.md)。

## 角色与权限委派

隔离只有在管理权能沿同一层级下放时才真正成立。LiteLLM 提供两个层面的角色：全局角色（`proxy_admin`、`proxy_admin_viewer`、`internal_user`）作用于整个平台，范围角色（`org_admin`、`team_admin`）只授予对单个组织或团队的控制权。代理管理员创建组织并指派组织管理员；组织管理员在自己组织内创建团队并指派团队管理员；团队管理员管理本团队的成员和密钥，不碰其他任何东西，此外还能使用代理管理员为团队管理员开放的那部分团队设置（速率限制、预算、提升预算）。正是这条链路让平台能接纳成千上万的用户，而不必事事都经过中央管理员。完整的角色矩阵、各角色的能力以及可配置的团队成员权限，见[访问控制](./access_control.md)；内部用户如何加入并管理自己的密钥，见[内部用户自助服务](./self_serve.md)。

## 花费与预算

花费沿层级向上归集，因此每个请求的成本会同时归属到它的密钥、用户、团队和组织。预算可以在每一层设置，并且由外向内强制生效：团队预算不能超过组织预算，用户预算不能超过团队预算，只要请求路径上任何一层超支，请求就会被拦下。有了这套机制，共享实例才能做到按租户分摊成本和展示成本。跨层级预算的配置见[团队预算](./team_budgets.md)；花费如何归属与上报见[成本追踪](./cost_tracking.md)。

## 常见多租户模式

同样这四层结构可以对应几种现实中的组织形态。下面的例子展示层级如何映射到一个组织，并非配置指南。

### 企业部门

大型企业会给每个部门一个独立的租户。使用组织时，工程、市场、销售各自是独立的组织，每个组织下辖多个团队（后端、前端、机器学习等），各团队在部门总预算上限内管理自己的预算。在开源版中，同样的隔离只靠团队实现（比如工程后端团队、市场内容团队），代价是失去部门级的汇总视角，换取更扁平的结构。无论哪种方式，每个团队都有自己的预算，部门或团队负责人担任管理员，财务部门则保留跨部门的成本可见性。

### 环境隔离

同一家公司会把生产、预发布和开发环境拆成不同的团队，这样试验既不会烧掉生产环境的预算，也不会动摇生产的稳定性。生产和预发布依赖带严格速率限制和核准模型列表的服务账号密钥，开发环境则使用更宽松的用户密钥做测试。由于每个环境都有独立的预算和模型边界，开发流量永远花不到生产预算。
