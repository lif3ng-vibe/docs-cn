![OpenShell 系统架构：可信的监管器与网络隔离的沙箱工作负载相互分离，工作负载只能连接监管器。](/images/openshell-system-architecture.svg)

OpenShell 通过两种方式约束智能体的行为：一是对内核做插桩，在运行时对每次文件访问、系统调用与网络连接强制执行策略；二是用形式化验证在策略变更生效之前检查它将放行哪些访问。

- **内核级强制执行**。每个智能体都运行在隔离的沙箱中。内核控制限定它可访问哪些文件、可发起哪些系统调用，且每条网络连接在离开沙箱前都要经过策略检查。智能体永远接触不到真实凭据；OpenShell 只会把凭据添加到发往已批准端点的请求上。
- **经形式化验证的策略变更**。在策略变更获得批准之前，OpenShell 用形式化验证标记它将授予的高风险新访问，例如带着凭据触达新的主机或调用新的 API 方法，这类变更会等待人工审查。

**网关**（gateway）是控制平面：它管理沙箱的生命周期，并为最终用户与运维人员提供沙箱的连接与管理能力。创建沙箱时，**计算驱动**（compute driver）会预置一个**工作负载**（workload）和一个独立的**监管器**（supervisor），建立二者之间的受保护信道，并构筑隔离边界；**监管器**在启动**智能体**之前先确认该边界，随后回连网关，获取策略、凭据、日志与交互会话。

## 各组件的职责

| 组件 | 职责 |
|---|---|
| [**沙箱**](#沙箱边界之内) | 与智能体一同位于边界内侧。它拥有智能体的进程，知道每个请求来自哪个程序，应用进程控制，并将 TCP 与 DNS 流量转发给**监管器**。 |
| [外围网络围栏](/security/best-practices#默认拒绝出站) | 拒绝工作负载的一切网络出站，只放行它与**监管器**之间的受保护连接。每种运行时用自己的原生工具构建这道围栏。 |
| [**监管器**](#沙箱边界之内) | 位于边界的可信一侧。它依据策略检查请求、提供凭据、解析 DNS、打开已批准的连接，并维持与网关的链路。它通过统一的[隔离后端](/extensibility/isolation-backends)接口适配所有运行时，完成确认边界、启动智能体、执行命令、转发连接与查看网络请求等操作。 |
| [策略](/how-it-works/policies/overview) | 描述智能体可以触碰什么：文件、进程、网络目标、API 调用，以及提供商凭据可以发往何处。 |
| [提供商](/how-it-works/providers/overview) | 将服务名与存储的凭据关联起来。**监管器**只在策略允许的位置发放该凭据。 |
| [策略证明器](/how-it-works/policies/prover) | 运行在网关中，用形式化验证检查智能体提议的网络规则。它会标记诸如新增凭据可达范围、新增 HTTP 方法、访问云元数据端点等变更；任何发现都会阻断自动批准。它还以独立命令 `openshell-prover` 的形式提供，可在 CI 中针对某个边界检查策略。 |
| [网关](/how-it-works/gateways/overview) | 验证你的身份并记住沙箱的一切信息。它下发策略与设置、挂接提供商、决定谁能做什么，并协调进入沙箱的连接。 |
| [计算运行时](/how-it-works/sandboxes/runtimes) | 创建沙箱，启动**监管器**与工作负载，搭建二者之间的私有信道，并构建网络围栏。它回报状态，并在沙箱销毁时完成清理。 |

## 沙箱边界之内

**监管器**与**沙箱**（sandbox）分处边界两侧。**监管器**受信任并掌握决策权。**沙箱**与不受信任的智能体共处边界同一侧，因此它从不做策略决策，只上报智能体正在尝试的操作，交由**监管器**裁决。

**沙箱**以受管子进程的方式启动智能体，并提供 exec、终端流、信号、进程状态与回环转发。在当前的 Linux 后端中，工作负载使用单一非 root 身份且不持有任何 Linux capabilities。Landlock 限制文件系统访问；seccomp user notification 拦截网络操作。**沙箱**基于可信的进程观察结果识别发起调用的可执行文件。

![OpenShell 沙箱强制执行流程：网络隔离的沙箱与可信监管器分属两个边界，监管器信道是工作负载唯一被允许的出站路径。](/images/openshell-sandbox-enforcement.svg)

### 受控信道

**监管器**与**沙箱**之间通过 OpenShell Sandbox Protocol 通信：一条经双向认证的 HTTP/2 连接承载多条相互独立的流。传输方式由计算驱动选择：Docker 和 Podman 用 Unix 套接字，Kubernetes 用 TCP，MicroVM 用 vsock。认证与协议行为在所有传输上完全一致。**监管器**出示一个沙箱专属的凭据，详见[组件间的身份验证](#组件间的身份验证)。

![OpenShell Sandbox Protocol：可信监管器与网络隔离的沙箱之间由一条已认证的连接相连，其上划分出独立的控制流、DNS 流与逐连接 TCP 流。智能体只能经由沙箱抵达监管器。](/images/openshell-sandbox-protocol.svg)

每条 TCP 连接独占一条流并拥有各自的背压，因此慢速下载不会阻塞 DNS、exec 或进程控制。

| 保证 | **沙箱**如何提供 | **监管器**得到什么 |
|---|---|---|
| 进程所有权 | 以受管子进程运行智能体，并维护其进程与终端状态。 | 一组句柄，可用于等待、附加、发信号、exec 与停止智能体。 |
| 程序身份 | 从可信的 `/proc` 数据识别发起调用的程序。 | 每个请求背后真实的程序，而非智能体声称的路径。 |
| 网络中介 | 用 seccomp 拦截 TCP 建连与 DNS 查询并移交。 | 在发往任何目的地之前先等待策略决策的请求。 |
| 失败即关闭 | 在**监管器**确认之前挂起启动，连接断开时冻结智能体。 | 要么有短暂的重连窗口，要么得到一个已停止的工作负载。 |

综合起来，这意味着智能体无法在其控制被确认之前运行，信号与 exec 只会到达本沙箱的进程，智能体也无法绕过 TCP 或 DNS 中介。

### 网络请求的流转

1. 智能体发起 TCP 连接或 DNS 查询。
2. **沙箱**识别发起调用的程序。
3. 请求经 Sandbox Protocol 传往**监管器**。
4. **监管器**对照策略检查请求，并附加策略允许的凭据。
5. 若获允许，**监管器**建立真实连接并中继流量。

通往**监管器**的受控信道是工作负载唯一被允许的出站路径。外围围栏拒绝其余一切，因此智能体无法直接触达外部服务、网关、DNS 或其他私有地址。

## 各运行时如何构建边界

所有运行时遵循同一份契约，但各自使用手头已有的工具来安放**监管器**、将其连接到**沙箱**，并把网络围起来。

| 运行时 | **监管器**运行位置 | 与**沙箱**的通信方式 | 如何阻断直连出站 |
|---|---|---|---|
| Docker | 独立容器 | 驱动所辖卷上经认证的 Unix 套接字 | 工作负载容器关闭网络 |
| Podman | 独立容器 | 驱动所辖卷上经认证的 Unix 套接字 | 工作负载容器关闭网络 |
| Kubernetes | 独立 Pod | 带 mTLS 的私有 Service | NetworkPolicy 只允许**监管器** Service |
| VM | 宿主机上的一个进程 | 经认证的 vsock | 客户机没有网络设备 |

运行时的职责是构建边界并证明边界已经到位，它从不决定某个请求是否被允许。该决策始终属于共享的**监管器**与策略引擎，这正是同一份策略在任何地方行为一致的原因。

各运行时在就绪状态的汇报方式与所支持的功能上可以存在差异。每个运行时都会声明自己的能力，让网关了解它能做什么。

## 组件间的身份验证

三条连接把一个沙箱串联起来。网关是唯一签发凭据的组件，且每份凭据都精确对应一个沙箱。

![OpenShell 沙箱认证：计算驱动将引导凭据交给监管器，网关签发网关 JWT 与沙箱 JWT，监管器经 mTLS 向沙箱出示沙箱 JWT，而沙箱只持有网关的公钥。](/images/openshell-sandbox-authentication.svg)

| 连接 | 连接方 | 保护方式 |
|---|---|---|
| **监管器**到网关 | **监管器**向外拨号连接网关。 | 网关 JWT，网关启用 TLS 时走 TLS。 |
| **监管器**到**沙箱** | **监管器**经驱动的私有信道拨入工作负载。 | mTLS，外加沙箱 JWT。 |
| 智能体到**监管器** | 智能体从不直接连接。**沙箱**经由上述连接中继其流量。 | 由监管器到沙箱的信道覆盖。 |

**监管器**用其 CA 校验网关的 TLS 证书。用户客户端证书与私钥不进入**监管器**和工作负载；网关 JWT 用于认证监管器 RPC。

### 获取首个凭据

**监管器**需要一个初始凭据来证明自己属于哪个沙箱。获取方式取决于运行时：

- **Docker、Podman 与 MicroVM。** 驱动直接把初始令牌交给**监管器**，放在只有**监管器**能读取的文件中。
- **Kubernetes。** **监管器**出示其所在 Pod 的 ServiceAccount 令牌。网关在签发任何 JWT 之前，先请 Kubernetes 驱动验证该令牌，并确认 Pod 属于预期的沙箱。

无论哪种方式，网关都会先对照自己记录的沙箱信息核验声明，然后才返回凭据。

### 网关与沙箱 JWT

网关为沙箱的每次运行签发一对 JWT：

- **网关 JWT。** 随**监管器**对网关的每次调用一并发送。它只允许**监管器**所需的调用，例如获取策略、推送日志与中继会话。它不是用户凭据，无法管理其他沙箱。
- **沙箱 JWT。** 随**监管器**对**沙箱**的每次调用一并发送。**沙箱**只持有网关的公钥，因此它能校验令牌，却永远无法伪造令牌。

每个令牌只在自己的连接上有效。二者都绑定到一个沙箱以及该沙箱的一次运行，称为一个代（generation）。重启沙箱会开启新的一代，换用全新令牌与全新 TLS 证书，旧令牌随即失效。

### 续期与撤销

**监管器**把令牌保存在内存中，并在到期前同时续期两者。只有沙箱仍然存在时续期才会成功，因此删除沙箱即切断其**监管器**。

共享部署（如 Kubernetes）应设置 `gateway_jwt.ttl_secs`，让令牌会过期。本地单用户网关可以不设置，此时签发的令牌在沙箱本次运行的生命周期内一直有效。

### 智能体能看到什么

智能体与**沙箱**共处边界同一侧，因此**沙箱**手里没有任何值得窃取的东西：没有网关签名密钥，没有网关 JWT，也没有提供商凭据。它能验证对面确实是正确的**监管器**，却无法冒充一个**监管器**。

如果**监管器**断开连接，**沙箱**会冻结智能体。只有同一个**监管器**进程才能重连并恢复它。新的**监管器**无法接管正在运行的沙箱，即便持有有效凭据也不行。

## 与现有基础设施集成

OpenShell 能接入你已在使用的工具，包括容器运行时、调度器、机密存储、身份提供商、镜像流水线、存储与设备插件。网关与**监管器**定义 OpenShell 的行为，驱动则把这一行为翻译成你的平台能理解的形式，并把执行结果回报上来。这让平台相关的细节始终留在核心控制平面与策略模型之外。
