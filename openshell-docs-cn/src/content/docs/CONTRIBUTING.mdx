本指南介绍如何为 NVIDIA OpenShell 编写、修改与评审文档。如果你的代码改动影响用户可见行为，请在同一个 PR 中同步更新相关文档。

已发布的文档位于 `docs/`，导航定义在 `docs/index.yml`，`fern/` 包含站点配置、组件与主题资源。

## 使用智能体技能

如果你使用 AI 编码智能体（Cursor、Claude Code、Codex 等），仓库内置了自动化文档工作的技能。动笔前先使用它们。

| 技能 | 功能 | 使用时机 |
|---|---|---|
| `update-docs-from-commits` | 扫描近期提交中面向用户的变化并起草文档更新。 | 功能合入后、发布前，或查找文档缺口时。 |
| `build-from-issue` | 依据 GitHub issue 规划并实现改动，含文档更新。 | 处理有文档影响的 issue 时。 |

这些贡献者工作流位于 `.agents/skills/`，会自动遵循下文的风格指南。它们与 `skills/` 里的公开技能相互独立；公开技能帮助用户操作 OpenShell，无需克隆仓库即可安装。要使用贡献者技能，让具备仓库感知能力的智能体运行它（例如“把 v0.2.0 以来合入的所有内容补进文档”）。

## 何时更新文档

以下情形需要同步更新文档：

- 新增、删除或重命名了 CLI 命令或参数。
- 改变了默认行为或配置。
- 新增、删除、重命名网关 TOML 字段或驱动专属配置项，或修改其默认值。这类改动要更新 `docs/how-it-works/gateways/configuration.mdx`。
- 新增了用户可直接交互的功能。
- 修复了文档描述有误的缺陷。
- 变更了 API、协议或策略 schema。

## 在本地构建文档

使用本地 `mise` 任务做预览与校验；若已安装 Fern CLI，也可直接在 `fern/` 目录运行。

本地预览文档：

```shell
mise run docs:serve
```

运行非交互校验：

```shell
mise run docs
```

如果已安装 Fern CLI，等价命令是在 `fern/` 目录下执行 `fern docs dev` 与 `fern check`。

触及 `docs/**` 或 `fern/**` 的 PR 会由 `.github/workflows/branch-docs.yml` 校验；工作流能拿到 `FERN_TOKEN` 时还会生成预览。

## 写作约定

### 格式

- 已发布文档使用 `docs/` 下的 Fern MDX。
- 每页以 YAML frontmatter 开头。每页都必须有 `title` 与 `description`，按需补充 `sidebar-title`、`keywords`、`position` 等页面级元数据。
- SPDX 许可证头以 YAML 注释形式写进 frontmatter：

  ```text
  ---
  # SPDX-FileCopyrightText: Copyright (c) 2025-2026 NVIDIA CORPORATION & AFFILIATES. All rights reserved.
  # SPDX-License-Identifier: Apache-2.0
  title: "Page Title"
  ---
  ```

- 不要在正文重复页面标题作 H1。Fern 从 frontmatter 渲染标题。

### Frontmatter 模板

```yaml
---
# SPDX-FileCopyrightText: Copyright (c) 2025-2026 NVIDIA CORPORATION & AFFILIATES. All rights reserved.
# SPDX-License-Identifier: Apache-2.0
title: "Page Title"
sidebar-title: "Short Nav Title"
description: "One-sentence summary of the page."
keywords: "Generative AI, Cybersecurity, AI Agents, Sandboxing"
---
```

- `title` 决定页面标题与浏览器标签标题。
- `sidebar-title` 在完整标题过长时提供较短的侧边栏标签。
- `keywords` 是逗号分隔的字符串，用于页面元数据。
- `position` 控制经 `folder:` 条目发现的页面的排序。
- `slug` 可选用自文档根的完整路径覆盖页面 URL。

对 `docs/index.yml` 中的显式条目，保留 `page:` 字段，Fern 依赖它。页面定义了 `sidebar-title` 时，`page:` 取该值；否则取 frontmatter 的 `title`。

保持每个页面的 URL 与其在 `docs/` 下的文件路径一致（去掉 `.mdx`）。Fern 从导航标签与 slug 构建 URL，不基于文件路径，所以重命名页面时要同步重命名文件，并在 `fern/docs.yml` 里为旧 URL 补一条重定向。当导航标签无法产出文件名时，例如 `TypeScript` 会被 Fern 转成 `type-script`，在 `docs/index.yml` 的条目上设置相对 `slug:`。`mise run docs` 会运行 `mise run docs:nav`，在页面 URL 与文件路径不一致、导航标签与页面侧边栏名称不一致、页面缺失于导航、或重定向指向不存在的页面时失败。

### 页面结构

1. frontmatter 的 `title` 与 `description`，以及相关页面元数据。
2. 一两句话的开头，说明本页覆盖的内容。
3. 按任务或概念组织章节，使用 H2 与 H3。每节以一句引导读者定位的开场句开始。
4. 页面底部按需提供“下一步”，链接到相关页面帮助读者继续。

## 风格指南

写作方式：像给同事讲明白一件事。直接、具体、简洁。

### 语气与语调

- 用主动语态。“CLI 创建网关”，不用“网关由 CLI 创建”。
- 对读者用第二人称（你）。
- 用现在时。“命令返回错误”，不用“命令将返回错误”。
- 陈述事实。不要用“只需”“简单”“轻松”“当然”这类词弱化或粉饰。

### 应避免的模式

这些模式在 LLM 生成文本中很常见，会侵蚀技术读者的信任。评审时清除。

| 模式 | 问题 | 修法 |
|---|---|---|
| 滥用粗体 | 常规步骤里写“这是**关键**一步”。 | 粗体只用于 UI 标签、参数名与真正的警告。 |
| 到处的破折号 | “网关——它运行在 Docker 里——创建沙箱。” | 用逗号或拆成两句。破折号可少量使用，但每段不应出现多次。 |
| 堆砌形容词 | “OpenShell 提供强大、健壮、无缝的体验。” | 写它做了什么，而不是它有多好。 |
| 含糊副词 | “只需运行命令”或“你可以轻松配置……” | 去掉副词。“运行命令。” |
| 正文用表情符号 | “🚀 开始吧！” | 文档正文不用表情符号。 |
| 修辞问句 | “想保护你的智能体？看这里！” | 直接陈述目的。 |

### 排版规则

- 每句以句号结尾。
- CLI 命令、文件路径、参数、形参名与取值用 `code` 格式。
- 可复制的 CLI 示例用 `shell` 代码块。不要加 `$` 前缀：

  ```shell
  openshell gateway add http://127.0.0.1:18080 --local --name local
  ```

- 终端会话、日志输出与不应照抄的示例用 `text` 代码块。
- 结构化对比用表格。保持表格简单（不用嵌套格式）。
- 提示信息用 `<Aside type="note">`、`<Aside type="tip">`、`<Aside type="caution">` 这类组件，不用粗体文本。
- 页面确实受益时使用 `<Steps>` 与 `<Tabs>` 组件。
- 章节标题不要编号。写“部署网关”，不写“第 1 节：部署网关”或“第 3 步：验证”。
- 标题不要用冒号。写“部署与管理网关”，不写“网关：部署与管理”。
- 冒号只用于引出列表。不要把冒号当作分句的通用标点。

### 用词表

保持一致：

| 使用 | 不要使用 |
|---|---|
| gateway | Gateway（句首除外） |
| sandbox | Sandbox（句首除外） |
| CLI | cli、Cli |
| API key | api key、API Key |
| NVIDIA | Nvidia、nvidia |
| OpenShell | Open Shell、openShell、Openshell、openshell |
| mTLS | MTLS、mtls |
| snap（句首或标题大小写需要时作 Snap） | 把 Snap 当作固有专有名词 |
| YAML | yaml、Yaml |

## 提交文档变更

1. 按项目约定创建分支：`docs/<issue-id>-<short-description>/<github-username>`。
2. 完成修改。
3. 用 `mise run docs:serve` 本地预览。
4. 运行 `mise run docs`。
5. 按 [CONTRIBUTING.md 的 Choose Verification for the Change](https://github.com/NVIDIA/OpenShell/blob/main/CONTRIBUTING.md#choose-verification-for-the-change) 运行相应的格式、链接与内容检查。需要更大覆盖面时用 `mise run pre-commit`。
6. 以 `docs:` 作为约定式提交类型开 PR。

```text
docs: update gateway deployment instructions
```

如果文档变更伴随代码变更，两者放进同一个 PR，并沿用代码变更的提交类型：

```text
feat(cli): add gateway registration flag
```

## 评审文档 PR

评审文档时：

- 检查是否遵循上述风格指南。
- 留意 LLM 生成的痕迹（滥用粗体、到处破折号、填充词）。
- 验证代码示例准确且可运行。
- 确认交叉引用与链接未失效。
- 用 `fern docs dev` 预览页面，运行 `fern check`，条件允许时查看 `branch-docs.yml` 生成的 PR 预览。
