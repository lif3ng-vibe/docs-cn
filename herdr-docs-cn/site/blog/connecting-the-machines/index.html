把机器连起来

Herdr 的下一步，是把机器连起来。

Herdr 的下载量已超过 70 万，插件接近 1,000 个。它背后有一个庞大的社区，大家用它管理自己的智能体和本地机器。

Herdr 已经有 --remote，你可以接入一台远程机器。智能体一跑就是好几个小时，有时你会希望它们跑在一台 24/7 不断电的机器上。总不能只因为一个智能体还在干活，就让笔记本一直开着。

我想我们也开始把笔记本当作客户端来用，而不是依赖它承担全部算力。对我们很多人来说，与其花几千美元买一台随身携带的笔记本，不如把一台性能强劲的机器放在别处运行，这样更划算。你可以用一台 VPS，或在自己那套设备里放一台 Mac mini，或者两者都要。

但在此之前，每台机器都需要一个单独的 Herdr 客户端，通常开在不同的终端标签页里。你得记住每个智能体跑在哪台机器上，再在这些标签页之间切换查看。这就是瓶颈所在。

几个月来一直有人在请求这个功能。得益于 Herdr 的插件系统和一些了不起的贡献者，社区已经有了一些变通方案。但 Herdr 本身的设计并不支持这种用法。

为什么花了更久

tmux、Zellij 这类多路复用器并不支持用一个 TUI 客户端去管理跨机器的独立服务器。这曾是一个小众场景。智能体正在改变这一点。如今我们想在任何地方运行智能体，并在自己所处之处控制它们。

Herdr 本来就有客户端和服务器，但一个客户端只能接入一台服务器。你在 Herdr 里看到的一切都渲染在那台服务器上。要把多台服务器纳入这套架构，要么让一台服务器聚合所有连接，要么改变 UI 所在的位置。

我希望由客户端把这些机器汇聚到一起，同时每台服务器继续运行自己的终端和智能体。这意味着要改变 Herdr 本身的构建方式。这就是它比我预期花了更久的原因。

在 0.9 中，Herdr 的外层 UI 改为在客户端渲染。服务器仍然拥有自己的会话，并提供终端视图。客户端现在可以把这些独立的服务器汇聚到同一个 TUI 里，而不是接入某台服务器的整个界面。

随着我们持续把客户端与运行时解耦，这也为后续更多性能优化留出了空间。

给它你的 SSH 目标，那台机器的工作区、标签页和智能体就会与本地的一起出现在同一个 Herdr TUI 里。切换机器无需再开另一个客户端。断开连接之后，智能体仍在各自的机器上继续运行。

目前，这些机器需要能通过 SSH 访问。它们可以在你的局域网里，可以通过互联网访问，也可以通过 Tailscale 这类工具连接。很多开发者本来就有这样的环境。

设置细节可以在连接机器文档中找到。

这是 Herdr 多机支持的第一个版本。TUI 现在可以把你的机器汇聚到一起，但智能体 CLI 仍然只在单台服务器内工作。它还看不到你其他机器上运行的智能体。

我也希望 CLI 能跨机器工作，这样即使智能体跑在不同的服务器上，它们也能彼此发现并协作。跨机器的智能体协作，正是我想在此基础上构建的方向之一。

我想在加入所有这些功能之前先发布它，这样我可以从真正在用它的人那里获得反馈。告诉我还缺什么、你在哪里遇到了问题。这会帮我决定接下来做什么。

迈向 1.0

这次更新之后，我想让连接这些机器变得更方便。你不应该需要操心 SSH，也不应该去折腾复杂的网络设置。通过一个 Herdr 账户，随时随地连接任何机器，都应该轻松易行。

无论是沙箱、虚拟机、远程服务器，还是你自己那套设备里的一台机器，都应该能装上 Herdr 并连接到你的其他机器。

这正是 Herdr Cloud 登场的地方。它没赶上这个版本，但它是下一块缺失的拼图。

目标是只用一条命令就把你的机器连接起来，再也不用操心如何访问它们。Herdr Cloud 将为这些连接提供中间层。终端流量会在你的机器与你的 Herdr 客户端之间端到端加密。

机器仍然由你自己提供。Cloud 负责把机器连接起来，并不替你托管智能体。

让 Herdr 掌管跨机器的终端和智能体会话，也带来了更多可以在此之上构建的有趣方向。我想在更远的将来探索的一件事，是在机器之间迁移智能体会话，让你不必在开始工作之前就先决定它住在哪里。这需要的不仅仅是把机器连起来，但随着 Herdr 逼近 1.0，这正是我在思考的那类用例。

现在，你可以用 0.9 通过 SSH 连接你的机器。如果想试试下一块拼图，欢迎加入 Herdr Cloud 候补名单。
