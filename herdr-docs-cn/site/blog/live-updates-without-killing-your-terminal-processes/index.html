实时更新，不杀你的终端进程

Herdr 可以在更新过程中替换自身服务器，同时保持窗格进程存活。

实时交接（live handoff）作为实验性的可选更新路径随 Herdr 0.6.3 发布。面向用户的行为请参见实时交接文档。

终端复用器（terminal multiplexer）的本职，就是保护长时间运行的工作不被中断。你启动一个服务器，在窗格里运行 shell 和各种工具，断开客户端，稍后重连，工作仍在继续。

但更新复用器本身，往往会破坏这一切。

对 tmux 和 Zellij 这类工具来说，这很正常。它们成熟、稳定，核心职责变化缓慢。如果 server/client 协议发生变化，常规做法是继续用旧服务器，直到你有机会重启它。虽然恼人，但通常可以接受。

Herdr 面临的问题不同。它固然是终端复用器，但也是一个 AI 开发工作区。它还很新：我在几个月前发布了它，如今在 GitHub 上有 2.6k 星标，按 GitHub release 统计已有超过 15k 次下载。

它频繁获得针对智能体检测（各家实验室都在用各自糟糕的方式构建自己的 CLI、插件和钩子，这难道不酷吗？）、终端行为、远程工作流、worktree、移动端使用、更新流程和集成的修复。用户不应该被迫在拿到这些修复与杀掉运行中会话里的每个窗格之间二选一。

Herdr 需要像应用一样更新，同时像终端复用器一样保住进程。

更新难题

常驻型终端复用器通常至少有两个组成部分。

服务器持有会话：窗格状态、PTY、读取器、写入器、布局、缓冲区、套接字以及子进程的生命周期都归它所有。客户端主要是通向该服务器的视图与输入通道。

当新二进制改变了 client/server 协议，新客户端可能就无法与旧服务器通信。重启服务器可以解决这个问题，但也有杀死窗格进程的风险。对终端复用器而言，这是最糟糕的更新路径。

这并不只是 Herdr 的问题。我四处查过，因为原以为早有人解决了它。

Zellij 上有多个长期悬而未决的 issue，说的都是升级之痛：升级后会话看似丢失、用户无法连接旧版本创建的会话、请求提供 upgrade-session 流程，以及请求从旧版本导入会话。见 zellij#1255、zellij#2943、zellij#3371、zellij#3420、zellij#3449 与 zellij#4305。Zellij 0.44 加入的向前兼容 client/server 支持能让未来的客户端连接仍在运行的旧会话，但这仍不等于在保留存活 PTY 的同时替换正在运行的服务器。

tmux 也有同一类版本错位问题。用户会碰到协议不匹配的错误，实际可行的做法是重启 tmux、推迟更新，或在有条件的平台上用旧二进制通过 /proc/<pid>/exe 连接。见 tmux#99、tmux#2189、tmux#4356 与 tmux#4890。

据我所知，主流终端复用器都无法在保持任意存活窗格进程接入的同时，就地替换服务器二进制。

这是个小突破，但是货真价实的突破。

关键细节在于 PTY 的归属权

乍一听，这个问题像是进程迁移。但并不是——那会难得多。

Herdr 并不移动子进程，而是转移这些进程已挂在其上的终端的归属权。

每个窗格进程与 PTY 的 slave 端通信，Herdr 的服务器持有 master 端。如果最终的 master FD 消失，子进程可能失去 I/O、收到 HUP 或直接退出。但如果 master FD 保持存活，由新服务器接管读写，子进程根本不需要知道服务器已经换人。

这就把问题从“移动进程”变成了“转移已打开的文件描述符，并围绕它们重建运行时归属权”。

在 Unix 上，这可以借助 SCM_RIGHTS 实现：一个进程可以通过 Unix socket 把已打开的文件描述符发给另一个进程。

交接过程

最终形态是一场双服务器事务。

旧服务器并不是把状态一丢就听天由命。它会进入交接模式，拒绝新的变更操作，断开客户端，并暂停每一个待转移的 PTY 读取器。这一暂停确认至关重要：同一时刻只允许一个服务器主动读取某个 PTY。如果两个服务器读同一个 master，输出就可能被错误的运行时偷走。

读取器暂停后，旧服务器按 Herdr 常规方式捕获会话快照。这之所以可行，是因为 Herdr 早已把纯应用状态与运行时归属分开：AppState 可以序列化，而窗格运行时、PTY 句柄、读取器、写入器和检测循环都是独立的运行时对象。

随后旧服务器创建交接清单（manifest），并把复制出的 PTY master FD 发送给新服务器。

新服务器校验清单，核对预期的协议与版本，接收 FD，恢复 AppState，围绕收到的 PTY master 构建导入的窗格运行时，绑定常规的 Herdr 套接字，然后报告就绪。

只有到那时旧服务器才提交。提交之前的任何失败都会回滚到旧服务器；提交之后，新服务器接管窗格，旧服务器退出，且不向窗格进程组发送任何信号。

这条提交边界就是安全线。

Herdr 为什么能做到

Herdr 早已备齐了所需的部件，这主要归功于早前的架构选择。

状态模型与运行时归属是分离的。工作区、标签页、窗格、标签、焦点、布局和智能体元数据存放在可序列化的状态里；PTY、子进程句柄、读取线程、写入路径、尺寸调整状态和检测器则存放在运行时对象里。

服务器/客户端边界是明确的。Herdr 本就拥有常驻服务器、可重连的客户端、本地套接字、命名会话、远程接入流程，以及成文的会话状态路径。因此可以新增一个隐藏的导入模式，而不是围着实时升级重写整个应用。

终端引擎也为视觉连续性出了力。Herdr 用 libghostty-vt 管理窗格终端状态。对普通主屏窗格，旧服务器可以导出近期的 ANSI 历史，新服务器在开始读取后续 PTY 字节之前先灌入这段历史。进程存活并不依赖这一点，但它让 shell 和开发服务器在重连后看起来毫无间断。

全屏终端应用则是另一回事。对 nvim、btop、htop 这类备用屏窗格，Herdr 不伪造重放。它们的进程能在交接中存活，但视觉状态只能尽力而为，直到应用自行重绘。这是诚实的取舍。

不变量

发送 FD 比让事务安全容易多了。

规则如下：

  • 同一时刻，每个 PTY 只允许一个服务器读取
  • 每个被转移的读取器必须在快照与重放捕获之前确认暂停
  • 提交之前，任何失败都要保证旧服务器存活并继续持有窗格
  • 提交之后，旧服务器不得以破坏性方式丢弃已转移的运行时
  • 任何失败路径都不得关闭最终的 PTY master FD
  • 智能体恢复不得在实时交接期间运行
  • 备用屏窗格必须保持存活，且不假装它们的屏幕内容被完整序列化过

实现已在 Linux 和 macOS 上用 shell 窗格、一个 Python HTTP 服务器、btop 和 nvim 做过测试。HTTP 服务器在交接全程持续响应请求；shell 窗格在交接后照常接受输入；全屏 TUI 保持存活并尽力重绘。

这不是什么

这不是 checkpoint/restore。它不能在重启后幸存，不能跨机器迁移进程，不能保留任意的进程内存，也不能让未来的每一次内部状态变更自动兼容。

它是一次同机 Unix 交接：运行中的窗格进程仍挂在它的 PTY slave 上，旧 Herdr 服务器把 PTY master 移交给新 Herdr 服务器。变的是服务器二进制，窗格进程照常运行。

这为什么很酷

Herdr 用户开着的往往恰恰是不该随手重启的那类工作：编码智能体、开发服务器、shell、REPL、SSH 会话、调试会话、长时间构建和本地实验。

终端复用器应该让这类工作更安全，而不是让更新显得危险。

窗格里的进程完全不必知道发生过一次更新。
