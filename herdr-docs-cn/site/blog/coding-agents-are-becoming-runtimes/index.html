编码智能体正在成为运行时

编码智能体 CLI 正在成为开发者基础设施。项目指令、生命周期状态、钩子（hooks）与终端运行时需要共享的契约。

编码智能体（coding agent）最初只是能改代码的聊天界面。如今，它们栖身于仓库、终端、编辑器、CI 任务、远程机器、移动端壳层、多路复用器（multiplexer）和各类自定义封装之中。它们读取项目指令（project instructions），运行命令，请求权限，派生子智能体（subagent）；它们暂停、恢复、压缩上下文，也会失败、自愈，并在开发者去做别的事情时继续工作。

这就是运行时行为。

模型可以是专有的，托管 API 可以是专有的，订阅也可以由实验室按需要随意定价。这一部分属于打造模型的那些公司。

但运行在开发者终端里的 CLI 属于开发者环境的一部分。它比邻而居的是 shell、语言服务器、包管理器、测试运行器、终端、编辑器和多路复用器。无论厂商是否为此做过规划，开发者都会把它与自己其余的工具组合起来使用。

这正是整个行业需要更加谨慎的地方。

这种漂移我们并不陌生

软件世界里，同一个理念碎裂成互不兼容的文件与惯例的地方已经太多了。

JavaScript 有 package.json，接着是一层层包管理器的 lockfile 与工作区格式。Rust 有 Cargo.toml，其可预测性令人耳目一新。Python 则先后经历了 requirements.txt、setup.py、setup.cfg、Pipfile、poetry.lock、pyproject.toml，以及同一个 TOML 文件里各工具专属的配置段。编辑器有各自的设置，CI 系统有各自的 YAML，格式化工具和 linter 又各自添上一份小契约。

其中一些是自然的，工具本就各司其职。

但代价是真实的。每个仓库都变成一张重叠惯例的地图，每个新工具都得弄清楚哪个文件才算数、哪个说了算、哪个是遗留却仍在生效。

智能体 CLI 还足够年轻，我们有机会避免其中最糟糕的版本重演。

项目指令是最鲜明的例子。AGENTS.md 正试图为编码智能体提供一个可预期的统一位置来读取仓库指引。它自称"一种引导编码智能体的简单、开放格式"，并称已有超过 60,000 个开源项目在使用。

其形态很简单：

Claude Code 依然停留在CLAUDE.md，而非 AGENTS.md上。官方给出的变通办法，是创建一个引入 AGENTS.md 的 CLAUDE.md，或者把一个文件符号链接到另一个。

这个变通办法确实管用，而标准的漂移正是这样开始的。

先是多出一个额外的文件，然后每个智能体都有了原生文件，接着每个仓库都长出一层兼容层，最后团队不得不花时间让重复的意图保持同步。

没有人会因为仓库里有两个指令文件而丢掉生产数据库。代价更小，却也更绵延不断：意图重复、指引过时，以及每个工具都必须再学一遍的新惯例。

终端是共享的界面

围绕访问权限与第三方工具，另一场争论正在进行。

编码智能体让按 token 计费有了截然不同的体感。一次聊天会话可能很贵，而一个编码智能体可以运行工具、读取文件、循环执行、派生工作，烧掉多得多的上下文。于是各实验室开始出售带用量限制的订阅：有的明文规定，有的是软性限制，有的按小时计，有的按周算，有的从外部根本无从推断。

接着，开发者开始做开发者一贯会做的事：把模型接进自己偏好的工具里。

这正是 Claude 生态成为一个有益案例的地方。人们通过 OpenClaw、OpenCode 等第三方工具使用 Claude 订阅，Anthropic 则进行了反击。如今 Anthropic 在文档中写明：Claude Code 可使用 Pro 与 Max 订阅，而Claude 付费计划与 API 访问是相互独立的产品。Anthropic 还为程序化调用与第三方 Agent SDK 用途单独引入了Agent SDK 积分（credit）。Zed 对实际效果的总结很到位：第一方 Claude 用量与第三方智能体或 SDK 用量，如今取自不同的池子。

Anthropic 有权做出这个决定。API 是他们的，订阅条款也是他们的。算力很贵，而第一方交互式 CLI 的经济模型，与通过 SDK 或协议适配器运行的任意程序化工具并不相同。

开发者工具层面的疑问依然存在：开发者真正拥有的到底是什么——是订阅、API 开销、模型访问权，还是智能体工作的那个运行时？

当智能体在终端里运行时，它就不再只是一种托管产品体验，而是开发者环境中的一个进程。开发者会把这个进程放进 Herdr、Zed、tmux、SSH 会话、CI 任务、容器和脚本里。他们会监督它、调度它，并围绕它搭建工作流。

终端正是所有权被共享的地方。

这并不意味着厂商失去了打造第一方体验的权利，而是意味着 CLI 这一层界面需要稳定的契约，因为它已经成为了其他工具所依赖的基础设施。

钩子只是症状

钩子展现出同样的张力。

多数严肃的智能体 CLI 如今都有钩子、插件或扩展，这是好事。问题在于，"钩子"一词几乎可以指代任何东西。

有的钩子是策略闸门，有的只是通知；有的修改工具调用，有的注入上下文，有的只观察消息；有的在会话边界触发，有的包裹在工具前后运行，却错过了中断、权限裁决，也提供不了外部监督者真正需要的那个精确状态。

这一点很重要，因为智能体的工作早已不是一次请求加一次响应。编码智能体有生命周期。

对外部工具而言，最小的生命周期很小：

具体的形态也可以很小：

权限提示、失败的工具调用、被打断的生成、自动化评审、子智能体交接、等待用户——这些都需要汇入同一个条理清晰的地方。

Claude Code 有一套严肃的钩子系统，Codex 也有自己的一套形态。两者都不简单，但每个智能体仍在各自划定边界。钩子界面可以很强大，却依然提供不了可移植的生命周期契约。

OpenCode 更接近编排工具所需要的形态。它的插件文档暴露出 session.idle、session.status、session.error、permission.asked、permission.replied 这样的会话级事件。

至于 pi，它把可扩展性当成一个更宏大的系统来对待。它的扩展文档描述的 TypeScript 扩展可以订阅生命周期事件、注册工具、添加命令、拦截行为、渲染 UI、持久化状态，并能从本地扩展目录热加载。

这些设计值得称道，因为它们把智能体当成了其他工具能够理解的东西。

Herdr 从下层看到的景象

Herdr 位于智能体之下。

它掌管终端窗格，维持进程存活，让开发者可以在多个智能体之间切换、检视它们、恢复会话，并把多个智能体进程当作一个工作区来操作。

站在这一层看去，运行时漂移看得一清二楚。

Herdr 最早真正管用的智能体检测路径是屏幕读取。如果某个智能体在终端里画出了"working"、"waiting for approval"或"done"，Herdr 就能读出终端状态，给窗格归类。

这与人类看到的画面一致，所以有用；但智能体 UI 一变，它就失效。如果修复只能写进 Herdr 二进制里，用户就得为此升级整个 Herdr，才能认出一个新的提示符或状态行。

另一个诱人的信号是终端活动。

真实的智能体很快就会打破这种推断。加载动画可以不停重绘，而真正要紧的状态是被阻塞；权限提示可以静止不动，却偏偏是窗格里最重要的事；子智能体可以热闹非凡，而父会话正在干等。

终端活动只是证据，生命周期才是更强的信号。

Herdr 现在会在智能体暴露信号的地方采用更好的信号，把屏幕证据留作兜底，并提供可热加载的检测清单（manifest），让兼容性修复不必总是伴随一次新的 Herdr 更新。这是面向当今生态的实用桥梁，而持久的契约应当来自智能体本身。

运行时支持应当公开可见

Herdr 可以用两大类方式支持智能体。

有些智能体暴露出可靠的生命周期信号，它们可以获得经验证的生命周期支持。

另一些智能体则需要观测式检测：借助终端输出、屏幕证据、清单和启发式规则。这也能运转良好，但前提是 UI 行为始终可辨认。

Herdr 会把这些内容发布成一份按智能体划分的支持矩阵：哪些智能体暴露经验证的生命周期信号，哪些智能体需要观测式检测。

这种区分应当公开，因为它对所有人都有帮助。

用户得到诚实的预期，智能体作者得到一个目标，工具构建者得到一套共同词汇，而整个生态会奖励那些把自身运行时状态暴露得干净利落的智能体。

智能体可以保留各自的插件系统，同时把那些本就不该成为产品差异点的部分标准化。

把乏味的部分标准化

采用一种可预期的项目指令格式。暴露一个小而整的生命周期契约。让权限状态可观测，让中断状态可观测。把状态绑定到实际运行中的那个会话。写清文档，说明外部工具可以依赖什么。

要在模型、UX、规划、上下文管理、速度、定价、安全和品味上继续竞争。

不要在"仓库是否需要五个指令文件"上竞争。

不要在"外部工具能否判断一个智能体是否被阻塞"上竞争。

不要逼每个终端运行时都去逆向工程其他所有终端运行时。

编码智能体正在成为基础设施。打造它们的公司仍然拥有自己的产品，但开发者拥有自己的环境。

Herdr 正是立足这一位置构建的。终端是这些智能体真正运行的地方，运行时这一界面属于开发者的工作流——无论厂商是否有意为之，它们都在共享这个空间。

智能体应当让自己的基础契约可见、持久，并且乏味。

然后，我们其余的人才能放手去构建。
