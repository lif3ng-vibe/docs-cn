十个智能体，三个客户端，CPU 降低 95%

Herdr 不再播放侧边栏动画、绘制不可见的窗格，也不再在鼠标移动时重绘未变化的帧。最繁忙的会话获益最大。

在以不必要的渲染为主的负载中，Herdr 服务器与其所有已连接客户端的总 CPU 占用下降了 89% 到 95%。渲染器仍以同样的速度运行——只是 Herdr 现在让它画的帧更少了。

节省随会话规模增长。单个智能体配单个客户端时，总 CPU 占用下降了 91%；十个智能体在后台产出输出、再配三个客户端时，则下降了 95%。服务器每跳过一帧，每个客户端也就少了一帧要序列化、传输并应用。

这三处改动都不是靠性能分析器（profiler）找到的。第一处始于一桩抱怨，并给了我们一条规则：动起来，就应该意味着有什么东西变了。

转轮动画先是抱怨，然后才是开销

Herdr 的职责是告诉你哪个智能体需要你。你同时跑着五个、十个、二十个智能体，而侧边栏就是你判断该往哪看的依据。

于是每个工作中的智能体都配了一个转轮动画（spinner）。这在当时看起来理所当然：动就意味着活着，一个正在思考的智能体就该看起来在思考。

可跑上二十个智能体，就有二十个东西同时在动，说的全是同一件事，却没一个能告诉你"需要你的正是它"。工作区列表早已用彩色圆点承载状态，侧边栏不过是同一信息的嘈杂版本。用户告诉了我们，我们也认同。

第一个修复把转轮的重绘隔离到状态矩形内：服务器不再每个节拍都重建窗格内容，而是复用客户端已保留的帧，打上更小的补丁再发送。我们已把转轮做到了近乎最便宜的程度，然后还是把它删掉了。这首先是一个设计决定，CPU 的节省只是副作用。

工作状态现在是一个静态的彩色标记。进入状态时依然立即渲染，变化发生的那一刻仍会抓住你的目光；停留在状态中则不再调度任何动画。

这处设计改动省下的 CPU 超出我们的预期。转轮靠定时器唤醒服务器，渲染状态表面，比较并准备帧，序列化后发给每个已连接客户端，再让每个客户端应用它。只要有任何智能体在工作，这一套就大约每秒发生八次，哪怕屏幕其余部分纹丝不动。

删掉转轮，这一整条链路也随之消失：定时器、动画截止期限、扫描有没有哪个工作区含着工作中窗格的轮询、仅为动画而设的渲染原因，以及帧补丁。master 分支不再产生任何计划内的动画帧。屏幕上只有一个智能体工作、再无其他内容时，Linux 上的 CPU 占用从 1.467% 降到 0.133%，macOS 上从 3.280% 降到 0.265%。

同一条规则，用在你看不见的输出上

同一条规则也适用于没人看得见的窗格输出。

窗格产生输出时，PTY 读取器会置起一个共享标记，表示有事发生。这样能高效合并唤醒，却丢掉了来源窗格的信息：等服务器取到标记时，已经分不清该窗格在不在屏幕上。后台智能体往一个没人查看的标签页里写入，仍会为每个已连接客户端产出帧。

跳过渲染不会丢输出。字节早已解析完毕，终端状态、回滚缓冲（scrollback）、光标、OSC 元数据和智能体检测都保持最新；切到那个标签页时，按当前状态渲染即可。在来源映射不明的情况下，Herdr 把窗格当作可见处理——因为跳错的代价是屏幕陈旧，而渲错的代价只是多花一点 CPU。

鼠标移动不该重绘未变化的帧

过去每个鼠标事件都上报"视图变了"。指针在窗格上的移动会转发给窗格内的应用，但 Herdr 自己的帧在前后通常一模一样。以每秒 60 个移动事件计，这意味着每秒约 60 次服务器渲染加 60 帧客户端绘制——只为把同一幅画画上六十遍。

Herdr 现在会追踪自己的哪些模式响应悬停：全局菜单、上下文菜单和导航器。在这些模式之外，单纯的移动不再触发任何重绘，事件仍像从前一样原样抵达窗格。

基准测试对两端都做了计数。每一轮测量中，无论哪个版本，1,680 个移动数据包都全部发出，且全部 1,680 个都抵达了窗格。0.7.5 版为此每秒发出约 56 到 60 帧；master 分支一帧未发。Linux 上的 CPU 占用从 9.450% 降到 0.667%。

为什么三处改动省出了九成

跳过一次服务器渲染，也就同时跳过了帧的准备、序列化、传输，以及每个已连接客户端中的帧处理。

客户端越多，节省成倍放大。十个静默工作窗格配一个客户端时改善了 78%；同样十个窗格配三个客户端时改善了 91%。

在 0.7.5 上，给会话加入隐藏的后台输出，在 Linux 上要付出 8.7 个 CPU 点，macOS 上是 12.7。而在 master 分支上，同样的活动只花 0.2 和 0.6——大致就是读取并解析这些字节的价格，此外再无别的。

优化帮不上忙的地方

五十个窗格、其中四十九个以 60Hz 写入，约合每秒 2,940 次终端更新。每一次仍要从 PTY 读取并解析进终端状态，因为正是这一步保证了你切换过去时窗格内容是正确的。压制帧，压不掉终端仿真。

这一场景在 Linux 上改善了 23.6%，macOS 上是 9.1%。在你正盯着看的窗格中以 60Hz 产生可见输出，Linux 上改善了 33.9%，macOS 上是 2.7%。空闲场景在两个版本上都贴着测量下限，根本不配拿到任何百分比。

这次优化瞄准的是不必要的渲染。输出密集的场景依然由 PTY 读取和终端解析主导。

测量方法

我们在独立的 Linux 和 macOS 机器上，把官方 0.7.5 发布二进制与带哈希的 master 构建作对比，每个操作系统各得到 54 个隔离观测。每轮运行都使用全新的命名会话、固定 86×47 终端中的真实已连接客户端、5 秒预热与 21 秒采样。文中数字均为 Herdr 服务器加上所有已连接客户端的总 CPU 占用。

每个关键的 CPU 结果我们都配了一个行为计数器：侧边栏每秒的计划帧数、后台输出的隐藏来源跳过次数、鼠标移动的精确包送达计数。单独一个 CPU 数字可以有一打种解释；配上对应机制计数器的 CPU 数字，就没那么好辩驳了。

这是已发布版本与 master 的对比，因此期间的其他变更与构建环境差异也包含在对比之内。性能分析器的证据与上述机制高度吻合，但并非每一个 CPU 点都能归到某一次提交上。

这项工作始于用户抱怨侧边栏太闹腾，此外还有不少缺陷报告和性能报告，来自那些运行着远比我们的测试更离奇会话的用户。请继续反馈，也感谢每一位帮助 Herdr 变得更好的人。
