## 摘要

OpenRig v0.3.3 是一次可用性 + 如实性发布。两个新的顶层 CLI 动词落地（`rig archive`/`rig unarchive` 与 `rig add`/`rig add-member`），多个长期痛点就此清退（大负载启动投递、以连字符开头的 `send_text`、cmux 0.64.x 兼容性、按名称的 `rig down`、黄金路径发现），三处如实性呈现面得到收紧，不再把含糊的结果误分类为成功（`rig send --verify` 送达结果、Codex 恢复门槛、`rig whoami` peers 契约）。For You 信息流获得一轮按异常管理的打磨（下钻到终端、决策带排序、一键批准）。切片 13 的确定性发布呈现面解析器 + 技能绑定索引作为产品代码交付，服务于自动功能发布（auto-feature-rollout）系统。

0.3.3 包含一个新迁移：`042_rig_archive`（`ALTER TABLE rigs ADD COLUMN archived_at TEXT` + `idx_rigs_archived`）。只追加、非破坏，不重构 rigs 行。既有的 v0.3.2 数据库在首次 `rig daemon start` 时完成升级。

## 本版包含内容

- **大启动文件传输**（slice 16）——超过 100KB 的 `TmuxAdapter.sendText` 负载现在经由每次调用独立的 tmux 缓冲区（`load-buffer` + `paste-buffer -d -r`）传输，而不是内嵌进单条 `send-keys -l` argv。清除了 Linux 上大体积按席位启动包的 >128KB 静默启动失败类问题（`MAX_ARG_STRLEN`）。`-r` 保留原始 LF，使多行包不会在每个换行处提前提交；结尾那一个 C-m 仍由调用方单独提交。小负载仍使用原样的内联 `send-keys -l` 命令。成功与粘贴出错两条路径上都会清理临时文件 + 缓冲区；每次调用使用唯一名称，因此并行 `rig up` 的席位不会相互碰撞。
- **`send_text` 内联连字符哨兵**（slice 17）——内联 `tmux send-keys -t <t> -l <text>` 现在携带 `--` 选项结束哨兵，因此任何以 `-` 开头的内容（尤其是 `---` YAML frontmatter——按席位包的常态）不会被 tmux 解析成标志。slice 16 的大负载/缓冲路径本就免疫（内容经由文件传输，从不经过 argv），未做改动。对非连字符内容不产生任何影响。
- **cmux 0.64.x 兼容性**（slice 18）——cmux 0.64.x 更名了呈现面标识符（`list-panels --json` 的行携带 `ref` 而不是 `id`）。传输层的 `surface.list` 归一化器重映射了数组键，但没有处理行键，因此在新版 cmux 下 `surface.sendText` 静默失败。修复方式是新增 `normalizeSurfaceRow` 辅助函数，从 `ref ?? surface_ref ?? surface_id ?? id` 解析句柄，对每一行做归一化而不取决于数组键。同一解析顺序同时服务 cmux 0.64.x 与 0.63.x——无需版本协商垫片。适配复用代码已有的、用于工作区行与 create/split 句柄的同一模式。
- **`rig archive` 归档入口**（slice 19）——新的顶层命令 `rig archive <rigId>` + `rig unarchive <rigId>`。归档是非破坏性的：rig 行保留，设置 `archived_at`，并触发 `rig.archived` 事件。默认读取排除已归档条目（列表不出现意外内容）；`rig ps --include-archived`、`?includeArchived=true` 与 `?archived=only` 可把它们重新纳入。UI 在 localhost 主机节点下新增一个惰性加载、可折叠的 "Archive" 区块，由单独的 archived-only 查询供数。对 archived-only 名称执行 `rig up <name>` 会被如实拒绝，错误指向 `rig unarchive`——没有静默恢复，也没有静默滑过。针对运行中/降级 rig 的归档守卫会呈现三段式事实/后果/动作错误，并接受 `--force` 覆盖。UI 查询失效端到端消费 `rig.archived` / `rig.unarchived` 事件：在一个窗口执行 CLI 归档，会响应式刷新另一处已挂载的 UI。
- **`rig add` / `rig add-member`**（slice 24）——面向 `add_member` converge 操作的新的顶层命令。从 YAML/JSON 成员片段文件向运行中 rig 的既有 pod 添加成员。构建在新的 converge 主干（`Op` union + differ + `convergeOp`）之上，CLI 是 converge 接口之上的命令式语法糖（不是绕过）。守护进程路由 `POST /api/rigs/:rigId/pods/:podNamespace/members` 将 `AddMemberOutcome` 代码映射到 HTTP（404 / 409 / 400 / 201）。MCP 工具 `rig_add` 同步发布。同一 slice 还收紧了边（edge）校验：非数组 `edges` 会被拒绝（而不是静默丢弃）；edge kind 对照从 `rigspec-schema.ts` 导出并被复用（而非复制）的规范 `VALID_EDGE_KINDS` 集合校验，因此 `rig add` 的边共享既有图形契约。
- **`rig down` 接受名称或 ID**（slice 22）——v0.2.0 时代的 `rig down <name>` HTTP 404 注意事项就此退役。解析器现在先拉取 `/api/rigs/summary?includeArchived=true`，跨全部 rigs 做 id 匹配（已归档 id 仍会进入拆除），然后仅对 ACTIVE rig 做名称匹配。同名的 active+archived 对解析到 active rig；archived-only 名称不按名称解析。打包的 `openrig-user` 技能（specs 源 + assets/plugins 副本 + `_canonical` 镜像）与 `down.ts` 解析器注释均已更正以反映真实行为。历史 CHANGELOG / v0.3.1 / v0.3.2 发布说明保持原样——bug 在那些版本确实存在。
- **如实的 Codex 恢复门槛**（slice 21 FR-2）——除非原生恢复探测证明席位确实已恢复，`verifyResumeLaunch` 不再返回 `ok:true`。未解决的操作者动作门槛（无法自动关闭的更新、信任、模型选择）与始终无法到达 `resumed` 的有界轮询，现在返回 `ok:false` 且 `recovery: attention_required`，并附最后 12 行窗格证据，路由进既有的 `HarnessLaunchResult` -> 启动编排器 `startupStatus: attention_required` -> `ps`/`status` 投影——不新增状态机。可正常工作的自动关闭路径保留（可跳过的更新门槛仍会自动关闭并继续走向成功）；只有未解决的门槛才会响亮失败。解决了 herder 暴露出的 04.3 干净 VM `kernel_state bootstrap_failed` 失败模式。
- **`rig send --verify` 如实送达结果**（slice 99.0.6.3）——此前的 `Verified: no` 把两种实质不同的状态折叠成一种：消息已送达（文本已粘贴 + Enter 已提交，两者都成功）但发送后捕获与 TUI 重绘发生竞态；以及消息根本没有送达。谨慎的智能体在每次发送后都要承担一次手动 `rig capture` 往返；粗心的智能体把 no 读作失败并重复发送。现在三种结果在响应中被具名：
  - `delivered` —— 校验成功。
  - `rendered-unconfirmed` —— 文本 + Enter 都成功，但捕获无法再次确认（重绘竞态，或捕获抛出异常）。已送达但不可再确认，并非失败。
  - `failed` —— 传输本身失败。
  旧式 `Verified: yes/no` 行逐字保留（供解析器使用）；新增的 `Delivery:` 行承载具名结果，并在中间情形附带 `rig capture <session>` 确认指引。`--json` 自动透传该字段。
- **`rig whoami` peers 契约**（slice 99.0.6.1）——此前 `peers[]` 字段可被读成"有向边的子集"或"主机清单"；两者都不是。现在契约会以带内方式明确陈述：`peers[]` 是本 rig 的名单，排除自身（构建自 `rig.nodes`、仅做自排除——不加边/状态/绑定过滤）；`edges{}` 是有向图；`rig ps --nodes` 是包含自身与存活状态的清单。仅为附加式澄清——行为与形状不变。`WhoamiResult` 新增必需的 `peersNote` 字段承载上述三条指引；CLI 的 Peers 表头保留字面 `Peers:` 前缀（已随产品发布的测试对它做 grep），并追加带内说明。
- **按名称实例化工作流**（slice 04.1）——`rig workflow instantiate <built-in-name>`（例如 `conveyor`、`basic-loop`）此前以 `spec_file_missing` 失败，因为 instantiate 把裸名称直接喂给 `WorkflowSpecCache.readThrough`（后者把参数当作字面文件路径）。只有原始 sourcePath 可用——一条违背全新操作者目标的隐形路径：发现呈现面宣传了你随后却用不了的名称。`WorkflowRuntime.instantiate` 现在先按名称在预置规格缓存中解析传入标识符，只有没有具名规格匹配时才回退到字面 sourcePath。缓存原样返回所存路径（不重新从源码树推导），保留 `dist/builtins` 生产布局。
- **引导式黄金路径状态澄清**（slice 04.2）——新操作者黄金路径说 `rig workflow list` 会显示预置内建项，但 `rig workflow list` 列出的是工作流实例；内建/规格发现呈现面是 `rig workflow specs`（内建项带 `(built-in)` 标记）。在 `workflow instantiate <name>` 之前按序执行的全新操作者被指向了错误的命令。已在 `docs/reference/getting-started.md` 与 CLI 的 `goldenPathNextSteps()` 第 4 步中更正。
- **For You 按异常管理**（slice 20）——仅基于既有信号的信息流交互 UX（0.4.0 的注意检测层未动）：
  - **下钻到终端**——新增 `FeedCardTerminalDrill`，通过在 `GET /api/sessions/:sessionName/preview` 上复用 `TerminalPreviewPopover`，直接从卡片打开已解析 source/author 会话的终端预览。如实的表述框架——"terminal preview" / "captured snapshot, not live"，从不宣称存活状态；当没有会话可解析时，下钻以禁用状态渲染并带如实标题，而不是渲染一个空终端。
  - **决策带排序**——稳定的两带划分，在既有的最新优先比较器内把"需要动作 + 审批"卡片提升到进度/观察/已交付之上。不是排名引擎（无评分、不改卡片）。在单一的 Feed 合并消费缝上应用。
  - **一键批准（仅 approve）**——`VerbActions` 新增附加式 `oneClickVerbs` 属性。APPROVE 点击直接提交；deny/route 仍是选择+确认。纵深防御：属性类型收窄到 `Extract<MissionControlVerb, "approve">`，误用即编译错误；运行时 `ONE_CLICK_SAFE_VERBS` 允许列表在调用点拒绝强转的 `"deny"`/`"route"`。复用同一个 `performSubmit` 变更路径（乐观回执与持错行为完全一致）。
- **CLI 发布呈现面解析器**（slice 13.1）——确定性的 TypeScript Compiler API 提取器，在两个 git ref 上遍历 `packages/cli/src/commands/*.ts` 中的 Commander 注册，输出新增命令、新增标志与移除/改名呈现面的结构化发布呈现面差异。同时解析两种 Commander 习惯用法（链式内联子命令与工厂间接）。输出注册名称（`rig-policy.ts` 呈现为 `policy`）；选项名称 token 仅取自 `.option()` 的 arg[0]，模板字面量描述不会丢掉选项。读取按每个 ref 一次 `git cat-file --batch` 批量完成（快、离线、确定）。三段式如实失败形状；绝不会静默输出空差异。0.3.3 尚未将其注册为 `rig` 动词（另行决策）——该模块是产品代码，带封闭的测试夹具（含一个 v0.3.1..v0.3.2 实例样例）。
- **技能 <-> CLI 呈现面绑定索引**（slice 13.2）——确定性的离线查找，把发布呈现面差异关联到"本次发布影响哪些技能"。与 slice 13.1 解析器组合；与调用方式无关。实现已批准的 join 语法：双向按组件前缀匹配（因此 `up` 不会匹配 `update`）；为守住"零漏报"下限而采取保守的过纳入偏好。绑定索引中弃用 `--version`（规范语法只含命令路径，不含全局标志）；技能正文仍以散文形式记载 `rig --version`。随附从语料派生的 v0.3.2 受影响技能回归夹具。

## 用户可感知的变化

### `rig archive` 与 `rig unarchive`

新的顶层命令。归档是非破坏性的：rig 行保留，设置 `archived_at` 时间戳，并触发 `rig.archived` 事件。

```
rig archive <rigId> [--force] [--json]
rig unarchive <rigId> [--json]
```

`rig unarchive` 总是安全（无 `--force`、无守卫）。对运行中或降级 rig 执行 `rig archive` 会呈现三段式事实/后果/动作错误，并接受 `--force` 覆盖。

默认读取排除已归档 rig：

```
rig ps [--include-archived]
GET /api/rigs/summary?includeArchived=true
GET /api/rigs/summary?archived=only
GET /api/ps?includeArchived=true
```

`rig ps` 用 `*` 标记已归档行并渲染图例。`--include-archived` 标志经跨主机 argv 透传。

对 archived-only 名称执行 `rig up <name>` 会被如实拒绝，错误指向 `rig unarchive`（没有静默恢复，没有静默滑过）；`--json` 形式发出 `rig_archived`。

UI 在 localhost 主机节点下呈现惰性加载、可折叠的 "Archive" 区块。该区块由单独的 archived-only 查询（`useArchivedRigs`、`?archived=only`）供数，而不是对默认列表做客户端过滤。`rig.archived` / `rig.unarchived` 事件驱动全局查询失效（`["rigs","summary"]` + `["rigs","summary","archived"]` + `["ps"]`），因此一次 CLI 归档会响应式刷新其他已挂载的 UI。

### `rig add` 与 `rig add-member`

面向 `add_member` converge 操作的新的顶层命令。从 YAML/JSON 成员片段文件向运行中 rig 的既有 pod 添加成员：

```
rig add <rigId> <podNamespace> <member-fragment-path> \
    [--json] [--rig-root <root>]
```

成员片段容忍裸成员或 `{ member }` 包装。字段名遵循规格的 snake_case 形状（`id`、`runtime`、`agent_ref`、`profile`、`cwd` 等）。可选的 pod 局部 `edges`（`{from, to, kind}` 数组）会一路保留到 converge 操作：

- 存在但不是数组的 `edges` 会被拒绝（不会静默丢弃）：CLI 打印清晰错误并在 POST 前以退出码 1 退出；路由返回 400 `validation_failed`；领域层也返回 `validation_failed` 作为纵深防御。
- edge `kind` 对照从 `rigspec-schema.ts` 导出并被复用（而非复制）的规范 `VALID_EDGE_KINDS` 集合校验。`kind: nonsense` 返回 400 `validation_failed` 并列出合法集合；不持久化任何边。

守护进程路由：`POST /api/rigs/:rigId/pods/:podNamespace/members`。结果 -> HTTP 映射：`rig_not_found` / `pod_not_found` -> 404；`member_conflict` -> 409；`validation_failed` / `preflight_failed` -> 400；成功 -> 201（响应体含每节点启动状态）。MCP 工具 `rig_add` 同步发布。

### `rig down` 接受名称或 ID

`rig down <name>` 现在可用了。v0.2.0 时代的 `rig down <name>` HTTP 404 注意事项就此退役。

```
rig down <rigId-or-name> [--delete] [--json]
```

解析器语义：

- 先拉取 `/api/rigs/summary?includeArchived=true`，然后：
- 跨全部 rigs 做 id 匹配（已归档 id 仍会进入拆除）；
- 仅对 ACTIVE rig 做名称匹配（`archivedAt == null`）。

同名的 active+archived 对解析到 ACTIVE rig（无歧义）。archived-only 名称不按名称解析（请改用 id，或先执行 `rig unarchive`）。

### 内联 `send_text` 连字符哨兵（slice 17）

内部的 tmux `send_text` 路径现在在用户提供的内容之前携带显式 `--` 选项结束哨兵，tmux 不再把以 `-` 或 `--` 开头的内容解析成自己的标志参数。作为 slice 16 大负载传输修复的配套：

```
rig send <session> "content with -- dashes or - hyphens"
```

现在按字面送达，智能体无须再转义或绕开以连字符开头的内容（尤其是按席位启动负载中的 `---` YAML frontmatter）。这是 `packages/daemon/src/adapters/tmux.ts` 中的守护进程侧适配器修复；`rig send` CLI 呈现面本身不变。

### `rig send --verify` 送达结果

`--verify` 响应现在显式具名结果：

- `delivered` —— 校验成功。
- `rendered-unconfirmed` —— 文本 + Enter 都成功，但发送后捕获无法再次确认（TUI 重绘竞态，或捕获抛出异常）。消息已送达；只是渲染不可再确认。
- `failed` —— 传输本身失败。

旧式 `Verified: yes/no` 行逐字保留（供解析器使用）；新增的 `Delivery:` 行承载具名结果，并在 `rendered-unconfirmed` 情形附带 `rig capture <session>` 确认指引。`--json` 透传 `outcome` 字段。

退出码：`delivered` 与 `rendered-unconfirmed` 退出 0；中间情形既不粉饰为成功也不粉饰为失败。`failed` 以非零退出，HTTP 映射不变。工作中 / wait-for-idle 拒绝有意不携带结果（什么都没有发送；拒绝不是一次失败的送达）。

### `rig whoami --json` peers 契约

`peers[]` 是本 rig 的名单，排除自身。它不是有向边的子集，也不是主机清单。

- 要看有向图，读 `edges{}`。
- 要看包含自身与存活状态的清单，用 `rig ps --nodes`。

`WhoamiResult.peersNote` 以带内方式承载该契约。CLI 的 Peers 表头保留字面 `Peers:` 前缀（已发布的解析器对它做 grep），并追加指向 `edges` 与 `rig ps --nodes` 的说明。`peers[]` 的名称与形状不动；这只是附加式澄清。

### 按名称实例化工作流

`rig workflow instantiate <name>` 现在可端到端解析内建名称：

```
rig workflow instantiate <name-or-source-path> [--cwd <path>] [--json]
```

内建名称（`conveyor`、`basic-loop` 等）先按名称在预置规格缓存中解析；字面源路径仍是未匹配名称的回退（两者都不匹配时如实 404）。这清除了发现/使用的分歧——`rig workflow specs` 宣传的名称 `rig workflow instantiate` 此前无法消费。

### 引导式黄金路径发现呈现面

新操作者黄金路径现在指向正确的发现动词：

- `rig workflow specs` 列出内建/预置工作流规格（带 `(built-in)` 标记）。在 `rig workflow instantiate <name>` 之前用它来发现名称。
- `rig workflow list` 列出工作流实例（由规格创建）。对全新操作者为空。

已在 `docs/reference/getting-started.md` 与 CLI 的 `setup` 黄金路径文案中更正。

### For You 按异常管理

基于既有信号的信息流交互 UX（0.4.0 的注意检测层未动）：

- **下钻到终端预览**——每张卡片底部带一个下钻入口，经 `GET /api/sessions/:sessionName/preview` 打开已解析 source/author 会话的终端预览。标注为 "terminal preview" / "captured snapshot, not live"——从不宣称存活状态。没有会话可解析时以如实标题禁用。
- **决策带排序**——在既有的最新优先比较器内，"需要动作 + 审批"卡片提升到进度/观察/已交付之上。稳定的两带划分；不是排名引擎。
- **一键批准**——APPROVE 点击直接提交；deny 与 route 仍是选择+确认。编译期 + 运行时守卫防止一键路径用于非 approve 动词（`ONE_CLICK_SAFE_VERBS = {"approve"}`）。

## 运维/安装注意项

升级已发布的 CLI 之后：

```bash
npm install -g @openrig/cli@0.3.3
rig --version    # 预期输出 0.3.3
rig daemon stop
rig daemon start
```

迁移 `042_rig_archive` 会在升级后首次启动守护进程时自动应用。内容是 `ALTER TABLE rigs ADD COLUMN archived_at TEXT` 加 `idx_rigs_archived`——只追加、非破坏，不重构/重建/删除 rigs 行。既有行不受影响。

新的 `rig archive` 呈现面：守护进程层默认读取仍排除已归档 rig。没有 rig 被归档时行为不变。`rig ps --include-archived`、`?includeArchived=true` / `?archived=only` 查询参数以及 UI 的惰性 Archive 区块会把已归档 rig 重新纳入。

新的 `rig add` 呈现面：成员片段文件是使用 rig 规格 snake_case 字段名的 YAML 或 JSON 文档（与 `RigSpec` pod 成员相同的撰写格式）。MCP `rig_add` 工具接受相同的片段形状。

关于 `rig down <name>`：此前文档记载的、在调用 `rig down` 前先手工解析 rig id 的智能体变通方法，不再需要这一步。基于 id 的形式照常工作，行为不变。
