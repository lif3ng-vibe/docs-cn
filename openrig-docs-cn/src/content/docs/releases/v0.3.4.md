## 摘要

OpenRig v0.3.4 是一次恢复 + 韧性发布。两个新的顶层 CLI 动词落地（`rig start` 与 `rig reconcile-session`）；`rig up` 从默认全新会话转为默认恢复原会话，以 `--fresh <seats...>` 作为显式的按席位自愿启用；恢复状态呈现面把每种如实结果折叠进一套具名的五词状态词汇（five-term vocabulary，`resumed` / `fresh-primed` / `awaiting-decision` / `attention_required` / `failed`），贯穿 `rig up` / `rig restore` / `rig ps`；周期快照调度器作为事件驱动快照与拆除快照之下的崩溃保险底线交付。同一版本还清退了一批长期恢复痛点：工作舱感知（pod-aware）的窄启动不再把节点留在死胡同，而是通过 `rig launch` 提供节点粒度的托管部分恢复；卡住的 `attention_required` 席位现在通过证据门槛的 `rig seat clear-attention` 清除，而不是手改 SQLite；Codex profile-v2 预检不再把无效 TOML 误分类为旧版配置原因；cmux 启动就绪门会如实呈现部分工作区状态；缓慢的 Codex 恢复不再被误分类。

0.3.4 没有新的模式变更迁移。既有的 v0.3.3 数据库在新守护进程上运行 `rig daemon start` 即完成升级。

## 本版包含内容

- **`rig start`**（slice 01）——新的顶层恢复入口。一条命令串起守护进程启动、内核就绪等待、可恢复候选列举、选择器或无头标志选择，以及逐 rig 的恢复 + 对账。不重写底层任何东西：它只编排既有原语。标志 `--last`、`--all`、`--rigs <names...>`、`--json`。候选列举与执行都以 id 为准，指向 `/api/rigs/:id/up`（同名 rig 类永远不会触达按名称的 `/api/up` 路由）。
- **`rig up` 默认恢复原会话**（slice 02）——`rig up <existing-rig>` 现在默认恢复原会话。`--fresh <seats...>` 成为操作 B（operation B，有意的全新预备）的显式按席位自愿启用项。此前默认是全新预备（fresh-prime）；智能体必须额外知道如何另行请求恢复。席位级结果使用下文的五词状态词汇；`awaiting-decision` 是守护进程无法恢复且操作者未选择全新时的如实的零会话状态。
- **`rig reconcile-session`**（slice 03）——新的顶层命令。把一个存活的、手工恢复的规范会话重新接回其持久化节点——不启动、不重启、不杀进程、不重放启动流程、不按恢复菜单、不压缩、不向窗格键入任何内容。这是"我手工恢复了席位，守护进程仍然显示它已下线"的修复。同一节点 id，不重新键控；如实报告投影漂移；绝不宣称会话连续性。
- **`rig up --plan` 只读恢复预览**（slice 04）——`rig up <existing-rig> --plan` 返回以五词状态词汇为键的只读恢复预览，并带如实的异步超时。不做变更；守护进程无法证明可恢复时，不会静默宣称可恢复。
- **五词恢复状态词汇**（slice 06）——此前 2-3 词的折叠式模型被替换，覆盖 `rig up`、`rig restore` 与 `rig ps`：
  - `resumed` —— 原会话连续性已证实。
  - `fresh-primed` —— 有意的全新预备（操作 B）；启动了全新会话而不是恢复。
  - `awaiting-decision` —— 守护进程无法恢复且操作者未选择全新；零会话启动。这是如实的零会话状态，不是静默失败。
  - `attention_required` —— 席位存活或被搁置但需要操作者动作（认证门槛、模型选择菜单、信任提示、卡住的恢复）。绝不是 `failed`。
  - `failed` —— 启动传输本身失败。
- **Codex Profile-V2 预检**（slice 07）——针对携带配置档案（profile）的启动与恢复呈现面的档案加载检查。旧版档案检测收窄为仅匹配旧版专有模式（`contains legacy`、`[profiles.<name>]`、`cannot be used while.*legacy`、`legacy profile selector`）；此前对 `failed to load configuration` 的宽泛匹配还会命中无效 TOML 的 stderr，给出错误的迁移提示。无效 TOML 现在呈现真实的解析原因（最多 3 行 stderr）并附 TOML 有效性提示。
- **cmux 启动就绪**（slice 08）——启动路径不再静默产出部分的 cmux 工作区。当 cmux 以预期窗口/窗格的子集启动时，席位会呈现如实的部分工作区状态，并提供一键打开缺失项的入口，而不是被报告为干净启动。
- **周期快照**（slice 09）——`snapshots.periodic` 配置族加上守护进程侧的 `PeriodicSnapshotScheduler`。每个启用的 rig 按间隔捕获 `auto-periodic` 快照，仓库按保留数量修剪。这提供了真正的崩溃保险底线——`auto-periodic` 与 `auto-pre-down` 在同一恢复选择器中按新鲜度竞争（较新者胜出），因此拆除快照之间的守护进程崩溃不再损失任意多的生命周期状态。最近快照/底线在 `rig ps` / status 中呈现。
- **`rig seat clear-attention`**（slice 10）——`rig seat` 上的新子命令。带证据门槛、操作者背书、有审计记录的对账，把卡住的 `attention_required` 席位恢复为 `ready`。取代此前席位卡住时智能体会求助的手改 SQLite / 伪造清除模式。审计行记录清除者、来源状态、证据路径以及任何操作者背书；`--reason <text>` 是绕过证据门槛的操作者背书覆盖项。
- **节点粒度的托管部分恢复**（slice 11）——`rig launch <rigId> <nodeRef>` 与 `rig launch <rigId> --seats <a,b>` 通过编排层按逻辑 id 重启单个席位或子集。清退 v0.3.x 时代的 `pod_aware_launch_unsupported` 死胡同以及丢失按席位控制能力的"改用 `rig up`"变通方法。被保留（held）的席位携带 `held-reason`；失败目标呈现为 `failed (liveness unknown)`；已在运行的席位只报告，不重启。
- **缓慢 Codex 恢复分类修复**（slice 13）——针对缓慢恢复的 Codex 会话的内部分类微调：此前 `verifyResumeLaunch` 会把确实在恢复、只是缓慢的席位误分类。现在经同一个五词状态词汇正确分类。
- **工作舱感知的 Claude 恢复选择菜单**（slice 05 rev1）——0.3.3 切片 21 FR-2 的后续：`ClaudeCodeAdapter.verifyResumeLaunch` 现在把 Claude 恢复选择菜单视同 Codex 未解决门槛情形处理——立即返回 `recovery: attention_required` 与最后 12 行窗格证据，绝不发送数字选择键击，也绝不让循环超时沦为泛化失败。

## 用户可感知的变化

### `rig start`——恢复入口

新的顶层命令。启动守护进程、等待内核、列出可恢复 rig，并通过既有原语执行恢复 + 对账：

```
rig start                            Interactive: daemon + kernel + pick-and-restore
rig start --last                     Headless: restore all rigs that were last running
rig start --all                      Headless: restore all rigs with restore-usable snapshots
rig start --rigs <name> [<name>...]  Headless: restore only the named rigs
rig start --json                     JSON output for agents
```

列举与执行都以 id 为准，指向 `POST /api/rigs/:id/up`。同名 rig 作为独立候选呈现；选择会把候选的 `rigId` 端到端携带，因此按名称的 `/api/up` 路由永远不会被咨询（恢复路径中不再出现 `ambiguous_name` 409）。

`rig start` 只做编排；不发明新的恢复语义。逐 rig 的恢复调用与 `rig up <existing>` 使用的 `/api/rigs/:id/up` 相同，席位级结果也携带同一个五词状态词汇。

### `rig up`——默认恢复原会话

`rig up <existing-rig>` 默认恢复原会话。`--fresh <seats...>` 是有意全新预备（操作 B）的按席位自愿启用项：

```
rig up <existing-rig>                       Resume original sessions (default)
rig up --existing <name> --fresh dev-impl   Deliberately fresh-prime dev-impl only
rig up <existing-rig> --plan                Read-only restore preview (no mutation)
```

- 原会话成功恢复的席位报告 `resumed`。
- 被纳入 `--fresh` 的席位报告 `fresh-primed`。
- 守护进程无法恢复且操作者未选择全新的席位报告 `awaiting-decision`——零会话启动。无头调用者会看到显式提示 `rig up --existing <source> --fresh <logical-id>`；TTY 调用者在任何全新预备注动之前会收到逐席位的 `[y/N]` 提示。
- 存活或被搁置但需要操作者动作的席位（认证门槛、模型选择、信任提示、卡住的恢复）报告 `attention_required`——绝不静默重分类为 `failed`。
- 只有传输级失败才报告 `failed`。

此前默认全新的行为已移除。如果某个工作流依赖隐式全新，请显式点名 `--fresh <seats...>`。

### `rig up --plan`——只读恢复预览

```
rig up <existing-rig> --plan [--json]
```

返回恢复计划但不做变更：每个节点的预期动作（恢复 / 全新预备 / awaiting-decision）、计划将消费的快照，以及变更前是否会捕获当前状态。计划路径带如实的异步超时——当预览无法在期限内完成时，响应会如实说明，而不是宣称一份干净的计划。

### `rig reconcile-session`——接入手工恢复的会话

新的顶层命令。在规范 tmux 会话内手工恢复席位（如 `claude --resume <id>` / `codex resume <id>`）之后使用：守护进程仍显示该席位已下线。对账把存活进程绑定到它自己的持久化节点并更新投影，使 `rig ps` / 拓扑 / `rig send` / `rig capture` / 队列路由恢复正常。它绝不启动、不重启、不杀进程、不重放启动、不按恢复菜单、不压缩、不向窗格键入。

```
rig reconcile-session <session>                                   Auto-resolve target node
rig reconcile-session <session> --rig <rigId> --node <logicalId>  Disambiguate
rig reconcile-session <session> --no-launch                       Explicit (default mode)
rig reconcile-session <session> --json                            JSON output for agents
```

`--rig` 与 `--node` 必须成对提供（用于消歧）。同一节点 id，不重新键控。对账无法证明的部分会作为投影漂移报告（未证实元数据字段的清单）；会话连续性作为状态字符串报告，绝不宣称已证实。

### 五词恢复状态词汇

`rig up`、`rig restore` 与 `rig ps` 上的席位级状态字段现在取五个值之一：

| 状态 | 含义 |
| --- | --- |
| `resumed` | 原生恢复探测证实了原会话连续性。 |
| `fresh-primed` | 操作者自愿选择有意的全新预备（操作 B）；启动了全新会话。 |
| `awaiting-decision` | 守护进程无法恢复且操作者未选择全新。零会话启动。 |
| `attention_required` | 席位存活或被搁置但需要操作者动作（认证、模型选择、信任、卡住的恢复）。 |
| `failed` | 启动传输本身失败。 |

`awaiting-decision` 是新引入的，取代了此前零会话结果被误报为成功或失败的模式。`attention_required` 覆盖更广的"存活但卡住"类；存活或被搁置的席位绝不会报告为 `failed`。

### `rig seat clear-attention`——有审计记录的卡住席位恢复

`rig seat` 的子命令。带证据门槛、操作者背书、有审计记录的对账，把卡住的 `attention_required` 席位恢复为 `ready`：

```
rig seat clear-attention <session>
rig seat clear-attention <session> --reason "<operator attestation>"
rig seat clear-attention <session> --json
```

- 不带 `--reason` 时，清除要求席位确实回到干净状态的证据（守护进程侧门槛）。
- `--reason <text>` 是操作者背书覆盖项；审计行逐字记录背书字符串。
- 输出：`Cleared <session>: <from> -> ready (<clearedBy>)`。审计日志记录会话、来源状态、门槛或背书，以及操作者地址。

取代此前手改 SQLite / 伪造清除的模式。席位的节点 id 不变。

### 节点粒度的托管部分恢复

`rig launch` 在运行中的 rig 上通过编排层支持单席位与子集重启：

```
rig launch <rigId> <nodeRef>                Single seat (logical id or node id)
rig launch <rigId> --seats <a,b,c>          Subset (comma-separated logical ids)
rig launch <rigId> --seats <a,b> --hold-reason "<text>"  Reason for held non-targets
rig launch <rigId> --seats <a,b> --json
```

- 单目标：`POST /api/rigs/:rigId/nodes/:nodeRef/launch`。
- 子集：`POST /api/rigs/:rigId/nodes/launch-subset`。分别报告 `launched`、`held`（带原因）、`alreadyRunning` 与 `failedTargets`（存活性未知）——部分结果绝不折叠。

清退 `pod_aware_launch_unsupported` 死胡同与"改用 `rig up`"变通方法。对运行中的 rig 做逐席位或逐子集重启时使用 `rig launch`；`rig up <existing>` 仍是整 rig 恢复入口。

### 周期快照

事件驱动快照与拆除快照之下的崩溃保险底线。新的 `snapshots.periodic` 设置族：

| 键 | 默认值 | 含义 |
| --- | --- | --- |
| `snapshots.periodic.enabled` | `true` | 总开关 |
| `snapshots.periodic.interval_seconds` | `300` | 每个启用的 rig 的快照间隔 |
| `snapshots.periodic.retention_keep` | `10` | 每 rig 的 `auto-periodic` 保留数量 |

快照以 `auto-periodic` 类型捕获；仓库按每个 rig 的 `retention_keep` 修剪。恢复选择把 `auto-periodic` 与 `auto-pre-down` 对称处理——两者中较新者胜出，因此拆除快照之间的守护进程崩溃不再损失任意多的生命周期状态。最近快照/底线在 `rig ps` / status 中呈现，操作者一眼可见底线。

通过设置存储（`rig config set ...`）调整，或直接使用默认值；调度器在守护进程启动时读取，并把 `snapshots.periodic.enabled = false` 视为总开关。

### Codex Profile-V2 预检

携带配置档案的启动与恢复呈现面上的档案加载检查，现在能如实区分它看到的是哪一种失败：

- **旧版档案检测收窄**：只匹配 `contains legacy`、`[profiles.<name>]`、`cannot be used while.*legacy` 与 `legacy profile selector`。此前对 `failed to load configuration` 的宽泛匹配还会命中无效 TOML 的 stderr。
- **无效 TOML 呈现解析原因**：最多 3 行 stderr（如 `expected newline`），并附 TOML 有效性提示，而不是指向 `[profiles.<profile>]` 的错误迁移提示。

认证拒绝投影路径不变；这是预检判别器中的分类修复。

### cmux 启动就绪

cmux 启动路径不再静默产出部分工作区。当 cmux 以预期窗口/窗格的子集启动时，席位会呈现如实的部分工作区状态，并提供一键打开缺失项的入口，而不是被投影为干净启动。

### 缓慢 Codex 恢复分类

`verifyResumeLaunch` 中针对缓慢但确实在恢复的 Codex 会话的内部分类微调。此前缓慢路径会经未解决门槛分支被误分类；现在经同一个五词状态词汇正确分类，并在就绪探测证实时到达 `resumed`。

### 工作舱感知的 Claude 恢复选择菜单

0.3.3 切片 21 FR-2 的后续。`ClaudeCodeAdapter.verifyResumeLaunch` 现在把 Claude 恢复选择菜单视同 Codex 未解决门槛情形处理：在内层轮询循环与最终探测退出路径上都立即返回 `recovery: attention_required` 与最后 12 行窗格证据。绝不发送任何数字选择键击。

## 应停止使用的模式

这些模式在 0.3.4 中被清退。请停止使用它们；下面点名的替代路径才是受支持的方式：

- **停止**把 `rig up <existing-rig>` 当作默认全新。默认已是恢复原会话。当目标是有意的全新预备（操作 B）时使用 `--fresh <seats...>`。
- **停止**把卡住或被搁置的席位读作 `failed`。存活或被搁置的席位携带 `attention_required`；只有传输本身失败才是 `failed`。如实的零会话状态是 `awaiting-decision`，不是 `failed`。
- **停止**为逐席位重启而求助于 `pod_aware_launch_unsupported` 变通方法或"改用 `rig up`"。使用 `rig launch <rigId> <nodeRef>` 或 `rig launch <rigId> --seats <a,b>`。
- **停止**手改 SQLite 或伪造清除卡住的 `attention_required` 席位。使用 `rig seat clear-attention <session>`（证据门槛）或 `rig seat clear-attention <session> --reason "<背书>"`（操作者背书、有审计记录）。
- **停止**仅依赖事件驱动或拆除快照保障崩溃安全。周期快照调度器是底线；可按需调整 `snapshots.periodic.interval_seconds` / `snapshots.periodic.retention_keep`。
- **停止**把无效 TOML 归类为旧版配置问题。Codex profile-v2 预检现在呈现真实的 TOML 解析原因；旧版检测要求旧版专有模式。
- **停止**通过重启整个 rig 来恢复手工恢复的会话。使用 `rig reconcile-session <session> --no-launch`——不重启、不写入输入、同一节点 id。
- **停止**把部分的 cmux 工作区投影为干净启动。启动就绪门会如实呈现部分状态，并提供一键打开缺失项的路径。

## 运维/安装注意项

升级已发布的 CLI 之后：

```bash
npm install -g @openrig/cli@0.3.4
rig --version    # 预期输出 0.3.4
rig daemon stop
rig daemon start
```

0.3.4 没有新的模式变更迁移。`snapshots.periodic.*` 设置带有内置默认值（`enabled=true`、`interval_seconds=300`、`retention_keep=10`）；无需操作者动作即可获得崩溃保险底线。

从 npm 全新安装 v0.3.4 的操作者可立即完整使用新呈现面。升级既有主机的操作者遵循上述标准守护进程重启流程；0.3.4 的主机升级流程另行排序，不是全新安装的先决条件。

新的 `rig start` 呈现面：它编排既有原语（守护进程 + 内核 + 逐 rig 的 `/api/rigs/:id/up`）。选择器默认 TTY 交互；无头标志 `--last`、`--all` 与 `--rigs <names...>` 覆盖脚本化恢复。

关于 `rig up` 默认恢复原会话：任何隐式依赖全新预备为默认的智能体或脚本，现在必须显式点名 `--fresh <seats...>`。五词状态词汇作用于响应；把 `awaiting-decision` 视为无头场景的"操作者需要决定"结果，而不是错误。

关于 `rig seat clear-attention`：当席位确实已恢复时，优先使用证据门槛清除。`--reason <text>` 覆盖项是有审计记录的操作者背书路径；背书字符串逐字落入审计行。

关于周期快照：变动频繁的 rig 可把 `snapshots.periodic.interval_seconds` 调低，更长的恢复窗口可把 `snapshots.periodic.retention_keep` 调高。默认的 5 分钟间隔 + 10 份快照保留是一条平衡的底线。
