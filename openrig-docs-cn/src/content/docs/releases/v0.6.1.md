title: "OpenRig 0.6.1 — 首次使用修复与统一的求助路径"
---

OpenRig 0.6.1 改进了首次使用指引、Codex 就绪检测与链接 worktree 的启动，提供单一的求助路径，并为拉取请求增加回归检查。

## 从已安装版本获取帮助

让智能体阅读：

```sh
rig context get help
```

[帮助指南](/reference/help/)汇集了环境检查、安装与重启症状、权限、实例布局以及逐级求助（escalation）。其链接的参考指南也随包附带。如果 OpenRig 无法安装或 `rig` 无法运行，可在线查阅 [openrig.dev/help/agents](https://www.openrig.dev/help/agents)，或阅读已安装的 `@openrig/cli` 包中的 `daemon/docs/reference/help.md`。需要帮助时可发邮件至 **hello@openrig.dev**；无需 GitHub 账户。

这是 [#113](https://github.com/mvschwarz/openrig/pull/113) 中加入的权威指南，入口来自 README 与智能体启动指引。

## 读取已编目项目的执行视图

```sh
rig view show execution --project <catalog-id> --mission <mission> --json
```

CLI 现在会把所选项目与任务（mission）转发给既有的守护进程解析器，后者使用该项目配置的 missions 根目录。此前该视图只能使用默认工作区。省略 `--project` 时保持既有行为。这并不会增加从当前目录推断项目的功能。感谢 [@dajiaohuang](https://github.com/dajiaohuang) 贡献 [#105](https://github.com/mvschwarz/openrig/pull/105)。

## Codex 就绪与捆绑指引

- 启动/恢复检查现在能识别 Codex 的 `»` 对话提示符，包括关闭钩子审查面板后出现的全新提示符。带编号的选择菜单仍需注意。感谢 [@dajiaohuang](https://github.com/dajiaohuang) 贡献 [#111](https://github.com/mvschwarz/openrig/pull/111)。
- 捆绑的 Vault skill 现在拥有有效的 frontmatter，并为随版本发布的 skill 头部增加了回归检查（[#115](https://github.com/mvschwarz/openrig/pull/115)）。
- 历史开发证据已从公开源码树中移除（[#118](https://github.com/mvschwarz/openrig/pull/118)）。已退役的 `spike/tui-drivability` 原型也已移除（[#119](https://github.com/mvschwarz/openrig/pull/119)）；随版本发布的 TUI 保持不变。

## 身份读取与 Codex 启动

- **非 UTC 主机上的启动时刻比较**：把 SQLite 不带时区的启动时间戳按 UTC 解析。身份与上下文用量读取器随后把观测与实际的 generation 启动时间进行比较，避免时区偏移错误地拒绝当前观测或接受较早观测。感谢 [@Coder8124](https://github.com/Coder8124) 贡献 [#124](https://github.com/mvschwarz/openrig/pull/124)。
- **自定义 Codex 状态行**：当会话头部已滚出屏幕、且状态行在其他字段之后放置大小写混合的模型名时，也能识别交互式会话。未解决的信任、钩子、更新与模型选择门控保持原样。这只是识别改进；[#116](https://github.com/mvschwarz/openrig/issues/116) 中提到的另一个过期恢复警告行为未在本版修复。感谢 [@Hexgunner69](https://github.com/Hexgunner69) 报告问题，感谢 [@Aummadour](https://github.com/Aummadour) 提供来自截屏的回归用例（收录于 [#125](https://github.com/mvschwarz/openrig/pull/125)）。
- **链接的 Git worktree**：Codex 全新启动现在会解析 worktree 的 Git 目录与公共 Git 目录，而不是把它的 `.git` 文件当作目录。恢复/分叉参数与权限模式不变。感谢 [@mgall-ibizdigital](https://github.com/mgall-ibizdigital) 在 [#121](https://github.com/mvschwarz/openrig/issues/121) 中报告、复现并给出建议做法，该问题已由 [#126](https://github.com/mvschwarz/openrig/pull/126) 处理。

## 拉取请求上的回归检查

[#117](https://github.com/mvschwarz/openrig/pull/117) 新增八个测试作业：构建与包文件检查、类型检查、仓库检查、四个独立的 daemon/CLI/TUI/UI 测试套件，以及一个已安装环境的队列持久化（queue-durability）场景。后者检查一次正常运行、一次故意引入的 lost-baton 失败和一次健康恢复。漏掉该植入失败的检查者无法通过。

该工作流使用 Node 22，构建/仓库/已安装场景作业使用 Linux runner，四个包测试套件使用 macOS runner。它不运行全部十一个历史场景种子，也不认证每个平台、提供商或带认证的原生智能体工作流。

## 升级与兼容性

Node.js 22 和 24 仍是受支持的版本；Node 20 不受支持。此维护版本不引入任何依赖、engine、权限模式或数据库迁移变更。更新既有实例时，请遵循既有的[升级流程](/releases/https:/github.com/mvschwarz/openrig/blob/main/_canonical/core/openrig-upgrade/SKILL/)。

各包的身份信息及其对每个已发布工件执行的检查，随对应的 [GitHub release](https://github.com/mvschwarz/openrig/releases) 记录。这些源码笔记不认证每个平台或带认证的原生工作流。横跨全新启动、恢复与分叉的原生权限执行仍保留 0.6.0 记录的验证边界。

Slack 应用清单/安装协助与 Rig Stream 分类仍为**实验性**。本版没有为它们作出任何新的真实应用、提供商运行、准确率或可靠性声明。既有的 Slack 连接器并非实验性。保留的边界参见 [0.6.0 的已知限制](/releases/v0.6.0/#已知限制)。
