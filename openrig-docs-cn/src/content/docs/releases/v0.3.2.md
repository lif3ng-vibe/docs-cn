## 摘要

OpenRig v0.3.2 交付了 Rigbundles 这一第一类的跨原语打包机制，将工作区 + 工作流操作者呈现面转为 GA，落地一轮 4 个缺陷的 `rig up <starter>` 痛点修复，交付一轮 5 项修复的协作 + 首用户设置修复轮（slice 21），从守护进程源码与测试中清除内部底座路径，把 `ConceptCard` 接到成形的数据源上，并为 For You 增加服务端优先级窗口。

没有破坏模式（schema）的迁移。既有的 v0.3.1 数据库会在首次 `rig daemon start` 时完成升级（新增迁移 `041_rig_policy`，用于新的操作者上下文模式绑定表——`CREATE TABLE`，对既有数据无影响；绑定行由操作者在运行时创建）。

## 本版包含内容

- **Rigbundles 一等公民**（slice 05）——五种内容类型（skills + plugins HYBRID + workflow_specs + context_packs + agent_images）的跨原语打包，端到端路由。`rig bundle create` 自动检测作者的 `bundle.yaml`，以双侧路径收容与符号链接逃逸保护来 vendoring 声明的内容，并输出带完整性哈希的清单。`rig bundle install` 把每种内容类型路由到 `$OPENRIG_HOME` 下的规范库，并保持消费侧扫描可见性。`rig bundle inspect` 将跨原语内容字段作为一等字段呈现。CLI 安装超时上调（原 5 秒上限对 tmux 会话引导式安装来说太短）。
- **工作区 + 工作流 GA**（slice 01）——面向操作者的呈现面加固。`rig workspace validate --max-files` 严格整数正则；`rig workflow project --exit` 枚举守卫；在 `client.post` 之前返回三段式错误，让早期失败更清晰；校验器路径上新增 14 个判别测试。
- **`rig up <starter>` 痛点修复轮**（slice 22）——解除全新 0.3.1→0.3.2 安装上首页快速启动的阻塞。四项有界修复：
  - 启动前失败呈现为 HTTP 4xx（`cycle_error` / `preflight_failed` / `validation_failed` / `service_boot_failed`）——此前是裸 500。
  - 启动前失败不再留下孤儿 rig 记录——实例化器重排序 + 回滚路径 + compose 拆除顺序收紧。
  - 路径形式的 `rig up <install-internal-spec>` 将 `cwd` 默认为调用者目录（消除路径形式与裸名形式调用之间的分歧）。
  - `walkYamlFiles` 跳过标准噪声目录（`.worktrees`、`node_modules`、`.git`、`dist`、`.turbo`、`.next`）+ 启动时清理过期的 `workflow_specs` 行，并带安装根保留守卫（因此随产品交付的内置规格能在清理中幸存）。
- **协作 + 首用户设置修复轮**（slice 21）——五项有界后续修复：
  - FR-1：在 `core/openrig-user/SKILL.md` 中呈现协作模型的上手直觉（`rig send` 与 `rig queue` 与 `rig queue handoff` 的取舍 + §1b 学说）。
  - FR-2：首用户工作区 + 工作流设置教学内容（技能 + 文档）。
  - FR-3：MISSION_NOTES 持久模式强化（模板 + codemap 约定 + 经由 `rig scope mission create` 的 scope 原语自动脚手架）。
  - FR-4：队列人机工学——`rig queue create --body-file <path>`（用 `-` 表示 stdin）消灭了多行正文经反引号-shell 损坏的整类问题；一等公民的 `--mission` / `--slice` 标志组合进标签；`lastNudgeResult` 措辞修正；关闭与验收的区别已有文档。
  - FR-5：`rig workspace doctor` 子命令——7 项检查的工作区就绪诊断（工作区根、missions 文件夹、文件允许列表、守护进程对齐、守护进程重载、可选切片文档、MISSION_NOTES 是否存在）。
- **守护进程测试底座路径清理**（slice 14）——从 4 处守护进程源码 + 10 个测试文件中清除内部团队的底座路径形状。钩子常量去重。受跟踪的源码/测试呈现面上的隐私类问题关闭。
- **`ConceptCard` 数据源**（slice 17）——接入成形的 backlog 候选；自 0.3.1 顺延的叙事适配器补全现已完成。
- **For You 优先级窗口**（slice 20）——服务端注意查询（方案 3）：SQL 谓词下推、精确匹配的注意正则、队列派生卡片的关闭（dismissal）记录按字符串键控。
- **操作者上下文模式绑定**（slice 09）——新的 `rig policy` 命令呈现面，配套守护进程侧的强类型原语存储（迁移 `041_rig_policy`）。六种模式（`sleep | desk | mobile | away | focus | debug`）绑定到四个 scope 层级（`global_host | rig | workstream | qitem`），采用先复述再确认的姿态，脚本无法在没有显式 `--confirm` 的情况下静默应用绑定。引用（citation）、生效模式解析与 `defaults` 命令补齐整个呈现面。
- **scope 树原语**（slice 12）——新的 `rig scope` 命令，按 `conventions/scope-and-versioning` 操作底座 scope 树（任务、切片、子切片）。任务层（`ls` / `show` / `create`）+ 切片层（`ls` / `show` / `create` / `ship` / `close` / `move`）命令。自动向任务 frontmatter 铸造稳定的点分 ID（dot-ID）；任务模板包含 `release` / `placeholder` / `mission-notes`。

## 用户可感知的变化

### Rigbundles 一等公民

`rig bundle` 现在提供第一类的跨原语打包：

```
rig bundle create <spec> -o <path>
    [--name <n>] [--bundle-version <v>] [--include-packages <refs...>]
    [--rig-root <r>] [--notes <text>]
    [--min-daemon-version <ver>] [--min-cli-version <ver>] [--json]
rig bundle inspect <path> [--json]
rig bundle install <path>
    [--plan] [--yes] [--target <root>]
    [--skip-version-check] [--force] [--json]
rig bundle history [--rig <name>] [--since <iso>] [--json]
```

安装时路由的内容类型：`skills`、`plugins`（hybrid）、`workflow_specs`、`context_packs`、`agent_images`。每种类型都落入 `$OPENRIG_HOME` 下各自的规范库；消费侧扫描可见性得以保留。

作者的 `bundle.yaml` 清单在存在时会被自动检测。vendoring 采用双侧路径收容（源与目标）与符号链接逃逸保护。完整性哈希记录在打包清单中。

`install` 上的 `--skip-version-check` 与 `--force` 是操作者显式覆盖项，分别针对安装时守护进程/CLI 兼容性门槛与安装时冲突门槛（不建议日常使用；这些覆盖项用于已知无风险的操作者场景）。

`rig bundle history` 读取 `~/.openrig/bundle-audit.jsonl`——记录每次安装的审计台账——并支持按目标 rig 名称与最早安装时间过滤。

### 工作区 Doctor（`rig workspace doctor`）

针对守护进程解析出的工作区的 7 项检查就绪诊断：

```
rig workspace doctor [--workspace <path>] [--strict] [--json]
```

检查项：工作区根、missions 文件夹、文件允许列表、守护进程对齐、守护进程重载、可选切片文档、MISSION_NOTES 是否存在。

默认退出码：仅在 `fail` 时非零。`--strict` 使 warn-or-fail 也返回非零。CLI 会用操作者 shell 环境中的 `OPENRIG_FILES_ALLOWLIST` 做叠加覆盖，因此即使守护进程环境未变，诊断也能反映操作者预期的允许列表。

### 队列人机工学

`rig queue create` 接受来自文件或 stdin 的正文，并暴露第一类的任务/切片 scope：

```
rig queue create --source <s> --destination <d> \
    (--body <text> | --body-file <path>) \
    [--mission <id>] [--slice <id>] \
    [--priority <p>] [--tier <t>] [--tags <csv>] \
    [--target-repo <name>] [--no-nudge] \
    [--expires-at <iso>] [--id <qitemId>] [--json]
```

`--body-file -` 从 stdin 读取。`--mission <id>` / `--slice <id>` 转换为 `mission:<id>` / `slice:<id>` 标签（可与 `--tags` 组合）。

### 操作者上下文模式绑定（`rig policy`）

```
rig policy set <mode> [--scope <scope>] [--qualifier <id>] \
    [--<field> ...] [--evidence <citation>] \
    [--confirm] [--bearer <token>] [--json]
rig policy show [--json]
rig policy effective [--rig <id>] [--workstream <id>] [--qitem <id>] [--json]
rig policy cite [--rig <id>] [--workstream <id>] [--qitem <id>]
rig policy unset <scope> [qualifier] [--bearer <token>] [--json]
rig policy defaults [--json]
```

不带 `--confirm` 时 `set` 仅做复述（CLI 回显拟议绑定并以 `exit 2` 退出，脚本无法静默应用）。

六种模式：`sleep | desk | mobile | away | focus | debug`。四个 scope：`global_host | rig | workstream | qitem`。`rig | workstream | qitem` scope 必须提供 `--qualifier`，`global_host` 则显式拒绝它。

操作者编辑动词（`set --confirm`、`unset`）需要操作者 bearer 令牌（`--bearer` 或 `OPENRIG_AUTH_BEARER_TOKEN` 环境变量）。

### scope 树原语（`rig scope`）

```
rig scope slice ls    [--mission <m>] [--state <s>] [--json]
rig scope slice show  <slice-path> [--mission <m>] [--json]
rig scope slice create <mission> <slug> [--template <k>] [--title <t>] [--json]
rig scope slice ship  <slice-path> <release-mission> [--mission <m>] [--json]
rig scope slice close <slice-path> --reason <r> [--note <t>] [--mission <m>] [--json]
rig scope slice move  <slice-path> <dest-mission> [--mission <m>] [--json]
rig scope mission ls  [--json]
rig scope mission show <mission> [--json]
rig scope mission create <name> [--template <k>] [--id <dot-id>] [--title <t>] [--json]
```

顶层选项 `--workspace <path>` 覆盖工作区根（否则从 `cwd` 或 `$OPENRIG_WORK_ROOT` 推断）。

### `rig up` 痛点修复

```
rig up <source> [--plan] [--yes] [--cwd <path>] [--target <root>] [--existing] [--json]
```

- 启动前失败现在返回结构化的 HTTP 4xx（`cycle_error` / `preflight_failed` / `validation_failed` / `service_boot_failed`），而不是裸 500。
- 失败的启动不再在磁盘上留下孤儿 rig 记录。
- 路径形式调用将 `cwd` 默认为调用者目录。
- `--existing` 跳过库规格名称解析，直接把 `<source>` 当作既有 rig 名称。

### MISSION_NOTES 持久模式（slice 21 FR-3）

`rig scope mission create` 默认从 `conventions/mission-notes/TEMPLATE.md` 自动生成 `MISSION_NOTES.md` 脚手架；`--no-mission-notes` 可退出（少见）。该约定把工作区技能 + 规范模板中记载的持久模式模型固化下来，让每个任务都自带统一的"心头首要事项"记录呈现面。

## 运维/安装注意项

升级已发布的 CLI 之后：

```bash
npm install -g @openrig/cli@0.3.2
rig --version    # 预期输出 0.3.2
rig daemon stop
rig daemon start
```

迁移 `041_rig_policy` 会在升级后首次启动守护进程时自动应用。它是无破坏性的 `CREATE TABLE`，对既有数据无影响；绑定行由操作者在运行时通过 `rig policy set --confirm` 创建。

新的 `rig policy` 呈现面：默认无、自愿启用。未设置绑定时没有行为变化。撰写前可先用 `rig policy defaults` 查看推荐的每模式 6×7 + 默认 scope 映射。

新的 `rig scope` 呈现面：对工作区默认只读（`ls`/`show`）；撰写动词（`create`/`ship`/`close`/`move`）按所述方式操作底座 scope 树。使用 `--workspace <path>` 覆盖解析出的工作区根。

## 已知限制 / 0.3.3 顺延项

- **Slice-05 Item-3 子 scope 顺延至 0.3.3**：智能体/端口/托管应用冲突检测（Item 4.3）；更广的安装进既有 rig 路径验收（Item 4.4）；用于安装时覆盖 rig 名称的 `--target-name` CLI 标志。设计取决于 CLI 呈现面决策（破坏性改名 vs 增量新标志）。
- **Slice-21 FR-4(d) 已接受队列状态模式顺延至 0.3.3**：新的 `accepted` 队列状态是一次模式模型变更；按既定的发布分诊哲学顺延。
- **上手旅程 + 实战强化顺延至 0.3.3**：切片 04（new-user-journey）、08（hooks-elite）、10（rig-self）、11（personal-rig）在收尾时已物理移入 `release-0.3.3` 任务树。
- **工作区符号链接对齐**：守护进程侧工作区解析器与操作者符号链接工作区根的对齐是 slice-21 FR-5 QA 提出的后续项；对 0.3.2 不构成阻塞。
- **Slice-13 权限阻断路由架构继续搁置**：全面放行（big-green-light）以操作者评审为门槛；仅限 `rigx-experimental`；不拆分顺延至 0.3.3（保持搁置）。
- **`rig down <name>` 仍返回 HTTP 404**——v0.3.2 中按名称拆除仍无法通过守护进程 down 路由解析；请改用 `rig down <rigId> --delete`。作为已知问题顺延。
- **`rig view list/show --json` 标志不一致**——包装层路由路径上的标志骨架仍在；直接调用时守护进程的 `view show <name>` 路由能正确返回 JSON（依据 v0.3.1 切换证据）。变通方案：现阶段使用人类可读输出。既定目标是在包装层修复。
