## 摘要

OpenRig v0.4.0 是一个"默认 token 高效 + 恢复能力收尾"版本。五个智能体日常高频调用的读取命令（`rig ps`、`rig whoami`、`rig queue list`、`rig restore-check`、`rig context`）从默认全量输出翻转为默认精简输出，并保留显式的 `--full` / `--all` 选择性开启；`rig queue list` 采用对齐 docker/kubectl 的读取命令语法（`-a` 查历史，`-A` 查跨 rig 广度，`-o json|wide` 指定编码，`--mine` / `--source` / `--destination` 限定范围）。`rig seat clear-attention` 的覆盖面扩展到 v0.3.4 已发布但未能触及的 restoreOutcome 派生投影失步一类。`rig scope mission|slice create` 现在能可靠地生成 `PROGRESS.md`，并新增 `progress` 更新动词，让智能体通过命令更新进度，而非手工编辑 markdown。

在这些用户可见的默认值背后：守护进程（daemon）侧的负载来源去重（`rig ps` 的 `recoveryGuidance` 不再逐节点重复，`contextUsage` 在列表负载中变为精简形态）随切片 26 发布，因此即便是 `--full` 与 UI 消费方也不再为此付费；实时智能体终端取代只读的 3 秒快照视图（切片 01）；多主机自用实测（dogfooding）夯实了 `--host` 标志的跨主机故事（切片 02）；Agent Images 库新增"立即分叉"入口与行元数据（切片 07）；关注/活动检测在整站 UI 更充分地消费 `agentActivity` 真值（切片 09）；技能级联来源与新鲜度获得新的只读 `rig skill audit` 呈现面（切片 10）；身份重构基础落地了守护进程与 CLI 共同消费的通用身份类型（切片 11）；`rig scope` 进度轨道将 mission/slice 树、`PROGRESS.md` 与 Project UI 重新连通（切片 15）；Codex resume 保留发起席位的审批姿态，恢复出的席位运行生命周期命令时不再触发隐式拒绝（切片 17）；active/idle 节点状态环变得可靠（切片 18）；拓扑图视图中的对角线幽灵在源头修复（切片 21）；收敛修复 P1（For-You 演练的 captured/live 契约）与 P2（守护进程测试框架 WebSocket 注册）作为收尾阻塞的 bug 修复切片 24 落地。

现有的 v0.3.4 数据库在新守护进程上运行 `rig daemon start` 即可升级。迁移均为增量式（additive）。

## 本版包含内容

### 新增顶级 CLI 动词与新子命令

- **`rig skill audit`**（切片 10）——新的只读命令 + 守护进程呈现面（`/api/skills/audit`、discovery、镜像漂移检测、skills 路由）。报告技能级联的来源审计结果——缺失 / 过期 / 自引用 / 日期无效 / 镜像漂移——覆盖 canonical → 产品镜像 → hub cwd → 已安装插件这条级联链。当镜像漂移证据不可用时，防止 CLI 出现假绿灯（v0.3.4 的 wrap-gate AC-3 差点带着这种失败模式发布）。与现有的 `scripts/mirror-skills.mjs` 防护机制组合使用。
- **`rig scope mission progress` / `rig scope slice progress`**（切片 33）——新的 `progress` 动词，通过命令面以确定的方式追加 / 设置 / 更新 `PROGRESS.md` 条目，取代手工编辑的 markdown。写入 OpenRig PROGRESS UI 页面所读取的规范结构。

### 默认精简的读取命令（token 效率族）

- **`rig ps`——默认精简 + `--full` + 默认当前 rig + `-A`/`--all-rigs`**（切片 25 + 34）——默认输出每个节点的精简 TL;DR（会话、rig、活动状态与原因、assigned/pending 计数；仅身份恢复要点）。`--full` 返回完整记录（字节等价的原始形态）。**切片 34——广度默认翻转为当前 rig**（取自 `OPENRIG_SESSION_NAME` 的 `@<rig>` 后缀），以对齐 docker/kubectl 风格的 `rig queue list` 语法：`-A`/`--all-rigs` 提供跨 rig 广度；`--rig <name>` 覆盖默认的当前 rig；`--session <sess>` 进一步收窄。全状态仍为默认（依 orch-lead 的裁决：ps 呈现的是拓扑/就绪度，其中 stopped/recoverable/attention 才是可行动信号——不像 queue-list 的可行动集合是 active 条目）。`--active` / `--running` 仍是可选的 active 状态过滤器。从根上终结了一次约 77,000 token 的"瞄一眼状态"事故，以及一枚舰队规模的无上限默认输出炸弹。**Resume token 安全**：`--full` JSON 现在输出 `resumeTokenPresent`（布尔值）而非 resume token 本身的值，orch 的一眼扫视不会意外泄漏 token 材料。
- **`rig ps` 负载来源去重**（切片 26）——守护进程节点列表负载从源头裁剪：`recoveryGuidance` 不再在每个节点上序列化为近乎雷同的模板化文字（改为顶层的按引用取用 guidance 映射，4 个现有消费方仍能解析它）；`contextUsage` 在列表负载中是精简摘要（完整遥测仍可通过 whoami / detail 查询按节点获取）。约 7 个 contextUsage UI 消费方与 4 个 recoveryGuidance 消费方完成迁移，无回归。即便是 `--full` 与 UI Project 视图，也不再为冗余的逐节点数据块付费。
- **`rig whoami`——默认精简 + `--full`**（切片 27）——`rig whoami` 与 `rig whoami --json` 默认仅返回身份恢复要点（`identity` / `peers` 名称 + sessionNames / `edges` 的方向性 kind 与 to.sessionName / `transcriptPath`）。`--full`（别名 `--verbose`）返回今天的完整负载，包括 `contextUsage`、`commands`、`peersNote`、`runtimeContext`。请求精简形态时，守护进程跳过 `contextUsageStore` 查询与 `runtimeContext` 构建。智能体每次启动后以及每次压缩恢复后运行的第一条命令，成本从约 909 token 降到约 192 token。
- **`rig queue list`——active 前沿默认精简 + 读取命令语法**（切片 28 + 32）——`rig queue list`（无标志）仅返回 active 状态（`pending` / `in-progress` / `claimed` / `blocked` / `handed-off`；不含 `done` / `canceled`）、当前 rig 广度、精简行（id、state、source→destination / current-owner、handed-off / blocked 时的 closure_reason / closure_target、mission、slice、tier / priority、age / updated_at、短标题、封顶的 tags）。四个正交轴可组合：
  - **`-a` / `--all`**——在当前广度内纳入 closed/done 历史（docker 风格的 `-a` 轴：历史）。
  - **`-A` / `--all-rigs`**——扩展到跨 rig 广度（kubectl 风格的 `-A` 轴：广度）。
  - **`--full`**——为所选范围追加 body / chain-of-record / 完整 tags / 流转历史（字段广度轴）。
  - **`-o json|wide`**——编码，默认精简。`-o json` 并不意味着完整 body（精简 JSON 是 token 安全且机器可解析的）；`--full -o json` 才返回完整 JSON。
  - `--mine` 仅返回调用者自己的条目；`--destination <s>` / `--source <s>` 用于显式限定范围。聚合跨 rig + 全历史的裸无范围全量输出（在真实主机上约 64,000 token）作为默认值退役——改由 `-A -a --full` 选择性开启。
- **`rig restore-check`——摘要 + not-ready 默认 + `--full`**（切片 29）——默认输出摘要计数（total / ready / not-ready / error-degraded）以及仅 not-ready 的席位（每个精简一行：席位 + 就绪原因）。`--full` / `--json` 返回今天的跨舰队完整逐席位就绪状态。精简形态下，守护进程对 ready 席位跳过逐席位明细组装（计算判定、省略明细）。`--rig <name>` / `--as <me>` 用于收窄。终结读取命令面上实测最大的炸弹（约 79,000 token）。
- **`rig context`——默认精简摘要 + `--full`**（切片 30）——默认输出精简的上下文摘要（常见用途所需的少数几个字段）；`--full` / `--json` 返回完整的当前负载。精简形态下守护进程跳过昂贵的聚合。杠杆效应低于切片 28/29，但让读取命令面在升级后保持"默认精简"的连贯性。

### 恢复与弹性收尾

- **`rig seat clear-attention` 覆盖派生投影失步**（切片 16）——v0.3.4 发布的 `clear-attention` 仅以 `session.startupStatus` 为门条件。第一次真实生产使用（主机切换遗留的 `advisor-lead@kernel` 投影）暴露了这一缺口：当某席位 `startupStatus=ready` 且 `sessionStatus=running`，但携带 `restoreOutcome=failed` / `continuityOutcome=failed` 时，守护进程会派生 `lifecycleState=attention_required`，而该命令以 `{ok:false, code:not_in_attention}` 拒绝执行。v0.4.0 的 `clear-attention` 现在能覆盖两类——startupStatus 驱动的关注（此前已发布）与 restoreOutcome 派生的投影——沿用同样的证据门控审计行，以及同样的操作者自证式 `--reason <text>` 覆盖。
- **Codex Resume 保留审批姿态**（切片 17）——恢复出的 Codex 席位现在带着与全新 Codex 启动相同的权限 / 审批姿态回归。此前恢复出的席位在运行已发布生命周期命令时，会撞上"需要审批但审批已禁用"的隐式拒绝且无路可走。针对 0.4.0 弹性集合锚定的有界 bug 修复；在 GS1 Studio 采集期间浮出水面。

### UI 与拓扑呈现面

- **真实（可交互）终端**（切片 01）——UI 中每个席位的终端变为可交互。点进一个席位，直接对智能体输入（shared-pane；"手扶在方向盘附近"）；对本地主机席位退役只读的 3 秒快照视图。借助一个全局的 **`LiveTerminalRegistry`**（封顶并发存活的终端数：配置键 `ui.terminal.max_live_terminals`、环境变量 `OPENRIG_UI_TERMINAL_MAX_LIVE_TERMINALS`）与**渐进式多存活**交互模型（用户正在看的地方存活：焦点弹窗 / 原位网格展开 / 节点详情面板；其余地方为静态磨砂缩略图），由 `LiveTerminalProvider` 协调，满足 rig 高度"全部终端"视图（约 20–30 个 pane 同时打开）的性能约束。拓扑网格中的原位多存活 + 跨焦点 / 弹窗 / 网格 / 节点详情呈现面的统一磨砂样式。远程席位终端随 0.4.1 发布（需要守护进程间传输）。
- **真实终端会话代理**（切片 38）——发布关键可靠性修复，依据创始人 2026-06-21 的真实自用暴露的问题。旧架构为每个视图各自打开一条 WebSocket，且每条 WebSocket 都对同一个 pane 启动自己的 tmux `pipe-pane`；tmux 每个 pane 只允许一条 pipe-pane，于是打开同一会话的第二个实时视图会**抢走第一个的输出**——在一个可见终端里打字，回显却出现在另一个标签页。v0.4.0 的架构：由守护进程持有的 **`TerminalSessionBroker`**，以规范的 `sessionName` 为键——每个会话一条 tmux pipe-pane、N 个 WebSocket 订阅者、输出扇出、会话级种子与供迟来订阅者使用的共享回滚缓冲环、明确的输入所有者语义（聚焦视图有资格发送输入），以及最后一个订阅者离开或会话死亡时的诚实清理。`terminal-ws` 现在是一个薄的代理订阅者；它不再为每条连接持有 pipe-pane。**尺寸策略 = 规范固定几何**：broker 将 tmux pane 固定在 Claude/Codex TUI 的最优网格（120×40）；订阅者用 CSS 让自身容器适配 / 滚动它，绝不发送 tmux resize。单一稳定的事实来源，零尺寸争抢，TUI 始终以最优宽度渲染。
- **统一静态 / 实时终端组件**（切片 39）——静态缩略图与实时 xterm 现共享同一个 `StaticTerminalPlate` 组件与同一套镜像几何（缩略图 / 镜像用 90×27；broker 的实时流为 120×40——缩略图是对该实时流的 fit-to-container 投影）。不透明镜像渲染 + 静态行回归修复 + 网格原位多存活 + 图形 / 表格弹窗。缩放视图上的实时终端选区现在使用 fontSize 缩放（而非 CSS transform），文本选区能落在正确的字符格上。几何注释清扫不改变行为，但清除了让后续修改犯迷糊的过期注释。
- **Agent Images 库打磨**（切片 07）——Agent Images 库 UI 为可克隆镜像新增 `Fork now` 动作（组合现有的 add-member 端点与 `session_source.mode: "agent_image"`）、轻量行元数据（version、token、fork-count、last-used），以及嵌套失败渲染（嵌套的 `failed` / `attention_required` 结果渲染为红色失败而非绿色成功）。镜像缺少 `sourceCwd` 时 Fork-now 隐藏 / 禁用；确认路径要求一个运行时匹配且携带 `agentRef` + `profile` 的同级席位；不会凭空虚构 fallback cwd。
- **关注 / 活动检测——精锐档**（切片 09）——在 UI 与操作者呈现面上更充分地消费 0.3.4 落地的 `agentActivity` 真值。Needs-input 突出度、状态驻留时间、活动汇总 POST-18。
- **拓扑图形视图幽灵渲染修复**（切片 21）——仪表盘拓扑 / 图形视图中节点背后的对角线幽灵伪影已在源头修复。启动视频评审套件中的每一次图形视图捕获都有它；表格视图本就无幽灵。启动视频 + 仪表盘的主打呈现面。
- **可靠的 active/idle 节点状态**（切片 18）——点亮 / 熄灭的活动环此前已发布；本切片补上 `DOT→terminalActive` 回退并移除死代码 `pane_silence_flag` 派生。旗舰视频 F1 的信号层。

### scope 自动化

- **`rig scope` PROGRESS.md + README 脚手架**（切片 33）——`rig scope mission create` 与 `rig scope slice create` 现在会生成规范的 `PROGRESS.md`（OpenRig PROGRESS UI 页面解析的结构），外加一个带正确 frontmatter、符合约定的 README，参照 `conventions/scope-and-versioning/README.md`。修复新建 mission + slice 完全缺失 `PROGRESS.md` 的 bug。`rig scope ... progress` 更新动词以确定的方式追加 / 设置 / 记录进度条目——智能体通过命令更新进度（构造上即 UI 合法），而不是手工编辑 markdown 并逐渐漂移。
- **`rig scope` stage / verified / reconcile 动词**（切片 35）——`conventions/scope-and-versioning` §2 的成熟度词汇（`stage` + `verified`）改为通过命令强制执行，而非手工编辑 markdown。与切片 33 的 PROGRESS.md + 脚手架组合，让 `rig scope` 成为确定性的约定执行者。
  - `rig scope <slice|mission> stage <id> <new-stage>`——确定性地设置 `stage`（wip / provisional / established / canonical / superseded / retired）。`superseded` 必须提供 `--successor <id>`（否则拒绝）；`retired` 会警告"不要使用"；非法 stage 会被拒绝并给出合法集合。
  - `rig scope <slice|mission> verified <id> --against "<source>"`——在 frontmatter 中盖上 `verified: <今天> against <source>`。`--against` 为强制——纯时间戳会被拒绝（防过期的拱顶石：恰是纯时间戳让过期的追踪器一边撒谎一边显得新鲜）。覆盖先前的 verified 行。
  - `rig scope <slice|mission> reconcile <id>`——幂等修复动词：回填缺失的 `PROGRESS.md`、规整强制 frontmatter（`id` / `stage` / `verified`），并修复 id 注册幽灵（`id:null` / 重复前缀工件）。可安全重复运行。
  - `rig scope <slice|mission> create` 现在会写入强制的 `stage`（默认 `wip`）与一个 `verified` 占位，新工件不再缺失它们。
  - `rig scope <slice|mission> show` 由（stage × verified）派生读取时的有效可靠性投影：`verified` 过期的 `canonical` 会以实际 `provisional` 上报（推导值，不落库）。为 UI + 智能体提供自校正信号。
- **scope 支撑的进度轨道**（切片 15）——把 scope 树、启动技能、`PROGRESS.md` 轨道与 Project UI 警告连成一个连贯的工作流。来自 0.3.4 发布审计（mission/slice 树已存在 + 队列流量丰富，但仪表盘依赖的 `PROGRESS.md` 呈现面缺失或未被充分利用）。与切片 33 成对——切片 33 发布命令；切片 15 发布使用它的工作流。

### 收尾缺陷修复

- **Wrap 收敛修复**（切片 24）——0.4.0 收敛深度评审产出的收尾阻塞 bug 修复切片。两个狭窄的真实终端集成缺陷：**P1** For-You 终端演练混用了 captured / live 契约（跨切片 01↔09 接缝）；**P2** 守护进程测试框架被无条件的 Node WebSocket 注册打断（套件失败 51→411）。两者皆为收尾前的阻塞项，依创始人裁定（"真正的收敛 bug 以 0.4.0 bug 修复切片的形式在 wrap 前落地"）。评审者未发现更广的跨切片连贯性缺陷——收敛是干净的。

## 用户可感知的变化

### 新呈现面（用这些）

- **读取命令默认精简**：`rig ps`、`rig whoami`、`rig queue list`、`rig restore-check`、`rig context`。同样的广度，小得多的默认负载。需要全量输出时用 `--full`（queue list 用 `-A -a --full`）。
- **`rig queue list` 语法（对齐 docker / kubectl）**：
  ```
  rig queue list                      # active、精简、当前 rig
  rig queue list -a                   # 再加 closed/done 历史
  rig queue list -A                   # 跨 rig 广度（同 kubectl 的 -A）
  rig queue list --full               # 再加 body + chain-of-record
  rig queue list -o json              # 精简 JSON（token 安全）
  rig queue list --full -o json       # 完整 JSON
  rig queue list --mine               # 仅调用者自己的条目
  rig queue list --destination <s>    # 发往 <s> 的条目
  rig queue list --source <s>         # 由 <s> 发出的条目
  rig queue show <qitemId>            # 完整单个条目（kubectl describe 式）
  ```
- **`rig skill audit`**——技能级联的只读审计。检测 canonical → 产品镜像 → hub cwd → 已安装插件链条上的缺失 / 过期 / 自引用 / 日期无效 / 镜像漂移。当镜像漂移证据不可用时，防止 CLI 假绿灯。
- **`rig scope ... progress`**——确定性的 `PROGRESS.md` 更新。通过命令面追加条目、设置状态、记录里程碑；UI 读取的正是命令写入的同一规范结构。

### 应停用的用法

- **停用把 `rig ps --nodes --json` 当随手状态检查的假设**。随手检查是精简默认；全量输出是 `--full`。逐节点 `recoveryGuidance` 近似雷同文案的重复已退役；列表负载中的逐节点完整 `contextUsage` 已退役（请改用单节点 / whoami / detail 查询）。
