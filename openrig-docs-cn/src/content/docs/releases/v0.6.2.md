选择你的提供商，给一位成果负责人在仓库里安排一个有用的改动，再让第二个智能体检查结果。OpenRig 0.6.2 新增了 first-project 的多种选择、更清晰的权限指引，并修复了 bundle 安装与智能体投递方面的问题。

## 小团队与一个有用的成果

[首次使用指南](/reference/getting-started/)以三种配方（recipe）提供同样的负责人与检查者工作流：

| 团队 | 配方 |
| --- | --- |
| 两个 Codex 智能体 | `first-project` |
| 两个 Claude Code 智能体 | `first-project-claude` |
| Claude 负责人与 Codex 检查者 | `first-project-mixed` |

使用你已有的账号即可；未使用的提供商不需要事先安装或登录。Codex 席位保留 `gpt-6-astra`；Claude 席位使用原生的已配置默认模型。启动前请检查模型访问权限。自动内核启动仍会从可用的已认证提供商中独立做出选择。

智能体引导的安装只询问一次：是否允许 OpenRig 命令而不再反复弹出权限提示，建议选择 **Yes**。显式回答 Yes 表示授权在个人项目 scope 应用原生 `rig` 命令规则，除非你选择用户级 scope。回答 No 或不作答则设置保持不变。该许可规则（allowance）包含生命周期与配置命令，但不授予一般的 shell 访问，也不更改沙箱与网络设置。指南涵盖这些规则的应用、检查与撤销；bootstrap 不会静默应用它们（[#147](https://github.com/mvschwarz/openrig/pull/147)）。

## bundle 文件留在你安装它们的位置

schema 版本 2 的 bundle 现在会把验证过的内容复制到 `--target` 并从那里启动，使相对工作目录与智能体引用在临时解包目录被删除后仍然可用。bundle 路径处若存在内容不同的文件，会在复制前报 `target_conflict`；内容相同的文件可以复用。

不带 `--target` 时，`rig up <file>.rigbundle` 会安装到你的当前目录，因此请从你想要的项目文件夹运行它。

`rig bundle create|inspect|install` 与本地 `rig up --target` 都以你的当前目录解析相对路径。文件仍然位于守护进程所在主机上；这不是上传。安装即启动 rig。旧版 version-1 行为与独立的 `--cwd` 覆盖保持不变。参见 [bundle 指南](/reference/rig-bundle/#cli-命令面)（[#146](https://github.com/mvschwarz/openrig/pull/146)）。

## 投递与恢复诊断

tmux/主机重启后的托管启动会保留具名的启动目标，而不会把它与旧的裸 pane 绑定混淆。既有的身份检查仍适用于每次写入。感谢 [@diaztunjano](https://github.com/diaztunjano) 报告 [#141](https://github.com/mvschwarz/openrig/issues/141)，该问题已由 [#151](https://github.com/mvschwarz/openrig/pull/151) 处理。真实的重启与断电恢复仍受下文验证边界的约束。

现在，如果探测到的前台是已知的裸 shell，而此刻本应有智能体运行时在运行，消息投递会予以拒绝，从而使消息不会被当作 shell 命令输入。仅终端的席位仍接收文字；无法读取或未知的前台保留既有的提示性行为（[#150](https://github.com/mvschwarz/openrig/pull/150)，修复 [#142](https://github.com/mvschwarz/openrig/issues/142)）。

## 社区修复

- **本地发送者身份**：把以本守护进程自身 host ID 修饰的发送者识别为其本地席位，避免错误的归属拒绝。外来 host 修饰与目的地处理保持不变。感谢 [@korallis](https://github.com/korallis) 贡献 [#135](https://github.com/mvschwarz/openrig/pull/135)，感谢 [@Yi-111-a](https://github.com/Yi-111-a) 在 [#137](https://github.com/mvschwarz/openrig/pull/137) 中提供补充用例，经 [#144](https://github.com/mvschwarz/openrig/pull/144) 收录。
- **终端与状态细节**：用可打印分隔符解析 tmux 窗口字段（[#101](https://github.com/mvschwarz/openrig/pull/101)）；把未请求的健康状态与读取失败区分开（[#102](https://github.com/mvschwarz/openrig/pull/102)）；为 Codex 钩子信任使用原生 realpath（[#103](https://github.com/mvschwarz/openrig/pull/103)）；把已知的 Claude/Codex 运行时提示传给 Herdr（[#106](https://github.com/mvschwarz/openrig/pull/106)）；把缺失的全新启动上下文或适配器报告为需要注意（[#107](https://github.com/mvschwarz/openrig/pull/107)）；接受数字形式的 Claude 限流重置时间戳（[#108](https://github.com/mvschwarz/openrig/pull/108)）。感谢 [@dajiaohuang](https://github.com/dajiaohuang)。
- **Pi 输入与可移植性检查**：在 `TERM=dumb` 下保留行编辑能力，并修正测试中关于 macOS 路径与时区的假设。感谢 [@shravansumanthanan](https://github.com/shravansumanthanan) 贡献 [#123](https://github.com/mvschwarz/openrig/pull/123)。
- **配置的恢复路径**：restore-check 使用已配置的 shared-docs 根目录。这并不会修复 [#130](https://github.com/mvschwarz/openrig/issues/130) 中的全部问题。感谢 [@jbaehova](https://github.com/jbaehova) 贡献 [#139](https://github.com/mvschwarz/openrig/pull/139)。
- **Anthropic 网关**：在已配置的提供商认证环境变量转发中允许 `ANTHROPIC_BASE_URL`。感谢 [@FenjuFu](https://github.com/FenjuFu) 贡献 [#143](https://github.com/mvschwarz/openrig/pull/143)。
- **终端认证维护**：复用共享的令牌比较辅助函数。感谢 [@Sunil56224972](https://github.com/Sunil56224972) 贡献 [#145](https://github.com/mvschwarz/openrig/pull/145)。

## 升级与验证边界

Node.js 22 和 24 仍受支持；Node 20 不受支持。此维护变更不添加任何依赖、engine 或数据库迁移变更。请遵循[既有升级流程](/releases/https:/github.com/mvschwarz/openrig/blob/main/_canonical/core/openrig-upgrade/SKILL/)。

已安装环境的首次使用与重启/断电验证仍待完成。源码与回归检查不能确立原生权限执行，也不能确立重启后带认证团队的恢复。

Slack 应用清单/安装协助与 Rig Stream 分类仍为实验性，本版没有新的真实应用或提供商运行方面的验证。既有的 Slack 连接器并非实验性。参见[保留的限制](/releases/v0.6.0/#已知限制)。
