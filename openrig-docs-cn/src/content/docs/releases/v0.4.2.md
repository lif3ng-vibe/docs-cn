## 摘要

OpenRig v0.4.2 是一个针对性热修复，解决 CLI `daemon-status` 探测在 `rig daemon start` / 重启后紧随其后的假阴性窗口。在 0.4.1 的构建上，探测在 `getDaemonStatus` 的每个分支各只发起一次 `/healthz` fetch；若守护进程进程已启动但 HTTP 监听器尚未开始接受连接，这次单发探测会输掉竞态，`rig daemon status` 便会误报"Daemon not running" / "healthz failed"——即便 `/healthz` 实际正在返回 `200`。

修复将 `getDaemonStatus` 的三个 `/healthz` 分支包进一个状态探测局部的有界 settle：最多 5 次尝试、200ms 退避，构造上即为硬性封顶。真正宕机时仍会在全部尝试上失败，并在预算耗尽后如实上报 stopped / unhealthy——绝不掩盖，也绝无无界等待。`fetchDaemonProbe` 与 start / stop / checkPid 的时序均未改动。

## 变更内容

- **`rig daemon status` 不再在守护进程启动后监听器绑定的窗口内假报阴性**。探测在报告 stopped 之前最多以短退避重查 5 次，因此一个仍在绑定监听器的健康守护进程会被解析为 running / healthy，而不是误报宕机。
- **真实宕机的上报行为不变**。若守护进程确实没有运行，全部尝试都会失败，探测会在有界预算耗尽后上报 stopped 或 unhealthy——不悬挂，不掩盖。

## 涉及文件

- `packages/cli/src/daemon-lifecycle.ts`——三个探测分支（pid-alive 的 `/healthz`、no-state 的 `/healthz`，以及注入式探测包装器）现统一走 `probeHealthzWithSettle`。
- `packages/cli/test/daemon-lifecycle.test.ts`——聚焦探测层测试：先瞬断后健康会 settle 为 running / healthy；pid-alive 但从不应答保持 `healthy: false`；真实宕机在硬性封顶预算耗尽后上报 stopped。

## 行为与兼容性

- **无 CLI 呈现面变更**。所有命令、标志与参数与 `0.4.1` 完全一致。
- **无守护进程 / 数据库 / 迁移变更**。迁移状态与 `0.4.1` 相同；本版本不随版任何新的 schema 迁移。
- **无依赖变更**。`package-lock.json` 仅随版本号提升刷新。

现有的 v0.4.1 数据库不受影响。升级只需 `npm install -g @openrig/cli@0.4.2`（或一次包刷新）加上守护进程运行中的一次常规 `rig daemon` 重启。
