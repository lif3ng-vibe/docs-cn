title: "OpenRig v0.6.0 — 陌生人也能用起来"

版本 **0.6.0** 的变更内容。发布状态与日期记录在 [GitHub release](https://github.com/mvschwarz/openrig/releases/tag/v0.6.0) 与 npm 上。

OpenRig 0.6.0 要求 Node.js 22 或 24。它新增了按席位的权限选择、面向手工输入席位的按席位输入保护（typing guard），以及一步在 Herdr 中打开整个 rig 的方式。它还修复了 Pi 席位活动上报，并澄清了内核 starter 的运行时选择。

本版还包含两项**实验性**特性：Slack 应用清单与安装协助，以及默认关闭的可选流式分类器（Jev with Rig Stream）。它们可能不完整，或在你环境中无法工作。参见[报告实验性问题](#报告实验性问题)。

## 破坏性变更：Node.js 22 或 24

OpenRig 0.6.0 只支持 Node.js 22 和 24，并使用 better-sqlite3 13，后者要求 Node 22 或更新版本。Node 20 不再受支持：安装检查会拒绝它并给出解释。Node 26 与其他版本未经测试。

如果你在 Node 20 上运行 OpenRig，请先切换 Node，再在新 Node 下重新安装 CLI。现有数据留在原处；守护进程会重新打开同一个数据库并就地应用待执行的迁移。参见[迁离 Node 20](https://github.com/mvschwarz/openrig/blob/main/README/#moving-off-node-20)。

OpenRig 运行在 macOS 或 Linux 上。原生 Windows 暂不支持，WSL2 也未经测试。在 Apple silicon 的 Mac 上请使用 Node.js 22（参见[兼容性历史](/releases/v0.5.15/#已知的兼容性限制)）。

## 按席位选择权限

`rig seat set-permissions <seat> --mode <mode> --reason <text>` 为席位未来的启动记录一次可审计的权限选择：`floor`、`full_bypass`，或 `inherit`（清除覆盖）。Codex 的 `full_bypass` 现在传入 `-s danger-full-access -a never`，因此它同时绕过审批与沙箱。`auto` 等其他 Claude Code 模式只有在该席位托管（managed）的 Claude 可执行文件声明支持时才会被接受；OpenRig 在选择时与启动时各检查一次，检查失败即拒绝且没有回退。

该选择不会重启席位，也不会改变其当前进程、历史、规则或钩子。`rig seat status` 显示所选模式与最近一次启动参数；两者都不能证明原生权限行为，因此在依赖之前请检查运行中的会话。rig 级策略移到 `rig policy permissions list|show|current|apply`；旧的 `rig policy` 动词仍作为别名保留。参见[权限指南](/reference/getting-started/#逐席位权限模式)。

## 保护需要手工输入的席位

`rig seat set-typing-guard <seat> --enabled true --reason <text>` 会暂停向该席位自动输入的一切终端输入，即使提示符为空也不例外。消息与唤醒被保存在发件箱（outbox）中而不被输入；用 `rig seat held-messages <seat>` 读取它们，审核后用 `rig seat retire-held-message <seat> <id> --reason <text>` 撤销（retire）处理。关闭保护后允许新的发送；它绝不重放已保留的消息。

保护默认关闭，其他席位保持自动送达。依赖它之前，请等待 `rig seat status <seat>` 报告其已生效。它覆盖 OpenRig 自身的输入路径，而不是直接向终端写入的其他工具。`rig seat set-typing-guard --help` 列出保留上限。

## 实验性：Slack 应用清单与安装协助

`rig slack manifest` 打印 Slack 应用清单，供你在自己的工作区创建应用时使用。它在任何守护进程或令牌出现之前离线运行；`--url` 打印带预填清单的 Slack 创建应用链接，`--json` 列出每个所请求的 scope 及其理由。在 Slack 尚未配置时，TUI 的 Connections 页面会显示同一链接。OpenRig 在此不托管应用、不打开浏览器、也不接收令牌。

该清单与 [Slack 安装指南](/reference/slack-app-setup/)均为实验性。指南中的创建步骤依照 Slack 的清单文档编写，尚未在真实应用创建中得到确认：我们没有观察到 Slack 会预填哪些字段，也没有见到完整的授权 scope 集合。令牌与私有 env 文件仍需你手工创建。既有的 Slack 连接器及其 `rig slack setup`、`verify`、`enable`、`disable` 与 `status` 命令并非实验性；`setup` 与 `status` 现在也会指引你到该清单。`rig slack verify` 只检查基线 scope，因此 READY 结果并不证明附件与提及功能可用。

## 在 Herdr 中打开整个 rig

在 TUI 中，rig 的详情视图带有一个 `term ▸ rig <name>` 链接，且命令栏接受 `terminal <view>`。配合 Herdr，rig 的每个运行中席位都会在一个以该 rig 命名的工作区中打开，每个标签页最多容纳 16 个席位（cmux 保持自身限制）。只有当 OpenRig 能确认 rig 自己的标签页已打开时，空的起始标签页才被关闭；否则保留它，并在结果中说明。未运行的席位报告为 absent 或 degraded，而不是已打开。

## 首次使用与兼容性修复

- Pi 席位活动上报现在携带席位占用者（occupant）的 generation，守护进程只在该 generation 与席位当前占用者匹配时才接受。缺失、较早或来自其他席位的 generation 的上报会被拒绝，而不是归到该席位名下。
- 内核 starter 的摘要现在会说明它何时显示库预览，解释运行时变体是自动选择的，并指向实际运行中的席位。
- 若所装 Codex 支持，Codex 席位以 `--no-daemon` 启动，使每个席位的工具在自己的 app-server 中运行，而不是共用一个守护进程。OpenRig 在每次启动前检查支持情况，检查失败则拒绝启动。
- 用 `rig scope` 创建的任务（mission）与切片在其 manifest 缺少 `metadata` 块时，不再导致就绪读取器失败。
- 0.5.16 中加入的为 Claude Code 托管块选择 `CLAUDE.local.md` 的功能原样收录。

## 实验性：流式分类（Jev 与 Rig Stream）

OpenRig 0.6.0 包含一个可选的实验性机制：让分类器席位通过 OpenRouter 调用 Jev，为 Rig Stream 观测打标签。它可能不完整或无法工作。默认处于关闭状态；启用时作用于一个本地配置文件：

```sh
rig project experimental status --config ./experiment.json --json
rig project experimental enable --config ./experiment.json --max-requests 3 --timeout-ms 10000 --json
rig project experimental disable --config ./experiment.json --json
```

启用不会启动任何处理、采集、守护进程或智能体。工作只发生在分类器席位运行一条前台命令 `rig project wake … --experiment ./experiment.json` 时，它允许 1–20 次请求（默认 3 次）且从不在后台重试。运行需要该进程环境中存在 `OPENROUTER_API_KEY`，并把所选条目的文本、taxonomy 问题、scope ID 与 roster 目的地发送给 OpenRouter。禁用会停止后续调用并丢弃迟到的结果；Ctrl-C 可取消本次运行，但已转发的请求可能仍被计费。

这些标签仅供参考。它们没有经证实的准确率或校准过的置信度，且本版没有为它们添加任何投递、看门狗（watchdog）或路由消费方。`rig project experimental capture` 将同一客户端用于既有的影子采集（shadow-capture）归档，`rig project shadow-status`、`shadow-drain` 与 `shadow-stop` 管理采集，采集需要单独配置的守护进程启动；`rig project shadow-stop` 负责停止它。taxonomy 格式、请求限制与错误处理参见[流式分类](/reference/stream-classifier-worker/)。

## 已知限制

- 按席位权限：发布前未验证横跨全新启动、恢复（resume）与同席位分叉（fork）的带认证原生权限执行。status 输出与启动参数不能证明所选模式的实际生效权限；请检查运行中的会话。
- Slack 清单与安装协助（实验性）：按已发布步骤在真实工作区创建应用、Slack 的预填字段与完整授权 scope 集合均未观察验证。
- Herdr：请检查 rig 在你的 Herdr 版本中是否按预期打开。
- Pi：来自已安装 Pi 席位的活动上报尚未端到端验证。
- 流式分类（实验性）：已安装环境下的运行与真实 OpenRouter 访问未经验证，其输出可能不完整或错误。不作出任何准确率或生产可靠性声明。
- [#17](https://github.com/mvschwarz/openrig/issues/17) 中关于 Codex 钩子信任对话框的报告未被复现，本版也未改变它。
- Node 26 与奇数号的 Node 版本不受支持、未经测试。

## 验证范围

发布准备工作记录在 [#109](https://github.com/mvschwarz/openrig/pull/109)。一次常规的候选 tarball 安装在全新 macOS 15.7.3 ARM64 VM 上通过，使用 Node.js 22.22.1 与真实的 npm postinstall。检查覆盖了 better-sqlite3 13.0.3、全部 89 个迁移、数据库写入与关闭/重开，以及正常的无认证守护进程启动与关闭。

更早的 Node 24 候选检查覆盖了已安装 SQLite、迁移与由分配驱动的垃圾回收。相关安装与数据库机制并未改变。那次安装使用的是分阶段的离线 postinstall，并非全新机器安装。由于宿主资源紧张，未执行全新 Node 24 VM 安装。

这些检查并未确立带认证的首个智能体启动、全新 Linux 或 Windows 安装、无编译工具的安装，或从 npm 注册表下载的安装。最终工件将单独绑定到合并后的发布提交。
