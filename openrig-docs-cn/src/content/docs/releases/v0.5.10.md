---
title: "OpenRig 0.5.10 — 可解释的系统健康"
---

OpenRig 0.5.10 让集群健康可以被检视，而不把观察本身变成另一种工作负担。智能体与操作者可以在 CLI 和 TUI 中查询同一批有界、携证据的发现，把不确定的模式交给智能体诊断，并在项目策略要求时将经过验证的人工请求路由出去。本发布还让撰写好的任务（mission）上下文在工作流等待中全程携带，生命周期的推进不再依赖编排器记得那套仪式。

## System Health

- **在你真正拥有的 scope 上检视健康。** `rig health` 支持当前席位、稳定的席位 ID、一个 rig 或本地实例。每条发现都保留其类别、严重级、状态、置信度、来源窗口、新鲜度、规则、证据、策略版本与最小可行的下一次检视。空输出明确地不宣称健康。
- **在终端 UI 中看到同一真相。** 实例、rig 与席位视图暴露紧凑的健康摘要、HEALTH 列表与发现下钻，底层正是 CLI 所用的同一批规范记录。不存在第二套评分，也没有仅属于 TUI 的健康权威。
- **不依赖会话记录情绪来检测高置信度的运维故障。** 确定性探测器覆盖进程、治理与上下文信号，例如队列放大、权限边界流量与上下文压力。稳定的回合（episode）身份、来源边界、新鲜度与显式的无法判定状态，防止缺失或过期的证据被读作健康。
- **让智能体诊断代码无法裁决的情况。** 可选启用的健康策略可以为仪式放大呈现一份有界的调查包。被指派的智能体可以在包之外检视、记录带署名的处置意见，并且只在配置的策略与连接器就绪时才请求人工通知。诊断流量会被排除在其自身探测器的输入之外。

## 耐久的生命周期与人工触达

- **让撰写的任务上下文穿越工作流等待。** 任务可以在 `mission.yaml` 中选择一个显式的边界工作流；编译会纳入项目与任务 manifest 加上声明的上下文引用。等待步骤可以按有界的指数退避重新呈现同一份包，保持同一个待办义务（obligation）而不是批量制造替换行。
- **从撰写的组件与波次中选择 SDLC 关怀。** 随附的角色与工作舱（pod）指引遵循项目与任务的选择，而不是从席位名称推断一条"构建到 QA 到评审"的链条。角色容量不会制造门禁。
- **通过已登记的投递通道触达人类。** 已登记的 `<entityId>@external` 地址暴露就绪状态与下一次检视。经过验证的队列创建在检查回执之前就持久化请求，而已投递、待处理、失败与无法判定的结果彼此可区分。直接回复经由关联的队列线程返回，而不是被改写成终端输入。

## 运维/安装注意项

- Root、CLI、守护进程与 Web UI 包版本升至 `0.5.10`。终端 TUI 保持独立的 `0.1.0` 版本。
- 本发布在 `0.5.9` 迁移头之外不新增数据库迁移。模式状态只需正常的守护进程重启；运行时采纳仍是操作者的独立决策。
- 健康列表与解释是只读的。自动诊断在策略显式启用之前处于关闭状态，且没有任何探测器会自动重试、改路由、重启、编辑 scope 或改变生命周期状态。
- 人工投递需要一个已登记的地址以及一个已配置、已启用且就绪的连接器。连接器的安装或验证本身不会发送消息。

## 已知限制

- 随附的确定性探测器域为进程、治理与上下文。行为与认知层面的结论仍归为带署名的智能体判断，而不是不透明的评分。
- System Health 只观察有界的留存记录。不受支持、被截断、过期、矛盾或不可得的输入保持无法判定；没有发现并不等于系统健康。
- 任务边界工作流携带上下文与调度，但证据、发布与激活的判断仍归智能体。守护进程不解读 Markdown 回执，也不凭空发明下一个任务。
- Slack 只是人工投递的连接器之一，并非寻址契约本身；已投递回执只证明连接器接受了消息，不证明有人阅读。
