---
title: "OpenRig v0.5.14 — 更清晰的导航、任务进度与人工通知"
---

OpenRig 0.5.14 让打开或刷新后的阅读更可预期，把面向人工的请求与信息性更新区分开来，并将实例设置与健康状态归拢到更容易找到的位置。

## 进入并持续阅读

不带参数的交互式 `rig` 在确认存在运行中的 rig 后进入常规 TUI。没有运行中 rig 的实例仍保留启动选择器。在检测缓慢或未经验证时，Help、Skip 和 Local 始终可用；即使用户已经选择了别的路径，迟到的观测也不会夺走导航。

页面区分初次加载、成功的空结果、刷新与失败。在页面与 rig 切换期间导航器保持可用。所选页面加载时，先前已读的页面可以带着原有 scope 标签继续显示；这些先前内容没有可操作目标。同 scope 的刷新会保留有用内容，并显示上一次读取时间与 Retry。失败的 Feed 来源保留自身数据，同时健康的同级来源照常更新。已确认的拒绝、空结果与移除会清空受影响的内容，迟到的回复无法替换当前所选内容。首次访问保留导航与本地反馈。Topology 先提供 rig 选择，然后先读取该 rig，再呈现与它无关的 fleet 细节。终端名称先于详细的就绪状态与预览可用。

Projects 将格式有误的任务（mission）与切片（slice）来源以本地错误的形式继续显示，同时健康的相邻来源保持可读。修正受影响的来源并刷新后，其内容即可恢复，且不会把它的解析错误片段显示在不相关的工作之上。

可选的阻塞项说明独立加载，因此说明不可用时不会掩盖队列的主要事实，也不会改动已记录的人工接收者。Fleet 读取在各阶段共享同一个请求耗时预算，当远程来源失败时保留本地结果。重复的 proof-policy 与送达回执读取避免重复劳动，同时较晚的读取仍观察当前输入。这些变更降低的是实测工作量；并不由此建立延迟保证。

选择性恢复与启动期事件索引在保留事件历史与投影结果的同时，减少了清单读取的工作量。私有的查询重放并不据此建立一般性的实时响应时间保证。

终端目录复用一次清单读取，而不重复相同的全局扫描。实测结果与之等价且查询工作更少；这并非一般性的延迟保证。既有的保存视图发现、被动预览与主动发起的 Herdr Open 仍然可用。

## 完成请求与静默更新

面向人工的通知把显式的决策请求与信息性更新区分开来。请求携带完整的简报与所请求的动作；相关的补充细节可以继续留在其线程中。超出支持上限的内容会被拒绝并要求作者修正，而不是静默丢失关键文字。随版本发布的撰写指引要求人工简报简洁而完整。

信息性 FYI 不需要动作或回复，也不产生审批义务。送达完成与人工决定相互独立。部分送达或含义不明的送达仍可区分，重试/回复追踪让每个请求及其线程各自独立。未显式声明意图的既有调用方仍保持决策类行为。

## 查找请求与实例健康

六个顶层条目是 **Topology、Specs、Projects、Terminals、Feed 和 System**。Feed 明确覆盖实例与所有人工接收者。**Human requests** 显示接收者与相关 scope；**Updates** 包含已确认送达的 FYI，与既有的成果及健康更新并列。送达义务关闭后，已送达的 FYI 仍保留在有上限的历史中。阅读不等于审批。Feed 的 Explorer 包含这些类别，条目显示在内容窗格中。Specs 的 kind 分组与 Derived 终端视图默认折叠、显式展开；Saved 视图保持醒目。加入 Saved 成员仍需专门设置，打开终端视图也仍是显式动作。

System 打开后首先显示实例 **Health**，其后是 **Configuration** 与 **Connections**。上下文的 Health、全局 Help 以及兼容的直接命令仍然可用，包括 `attention`、`needs`、`feed`、`config` 和 `connections`。

## 理解任务进度

Projects 在两种终端宽度下都把已完成成果、当前工作与负责人、阻塞项、下一依赖和切片框排在流程说明之前。被接受的必需证明（proof）判定决定切片成果；在 mission 报告成果完成之前，所有切片成果必须完整。仅凭证据附件、静默活动或交接并不能接受证明。重新打开或已指派的未完成工作保持打开状态，即使没有未指派的下一个切片也是如此。

实际托管与计划归属仍然分开。已撰写的生命周期与发布和成果完成相互独立；未知的所有权或资格保持未知。窄屏保留完整的第一个框，其余内容滚动显示。

## 运维注意项与验证边界

根包、CLI、守护进程（daemon）与 web UI 的版本均为 0.5.14；终端 TUI 仍为 0.1.0。Node 要求不变。Migration 081 为队列记录添加了显式 intent 与补充细节。迁移头现在是 `084_inventory_event_indexes`，新增三个选择性清单读取索引；083 新增两个评审读取索引。Migration 082 为已归档的队列流转（transitions）记录添加可空的 identity 来源（provenance）。归档保留已记录的值，并拒绝无法承载这些值的归档 schema；遗留的未知值保持为 null。共享历史、RECENT 与 OWNER/回执读取器现在包含已归档记录，因此即使在命令或 TUI 代码未变之处，其结果也可能变宽。仅靠迁移不会重建此前丢失的元数据。获得授权采用时，请使用受支持的升级与连续性流程。

私有综合评审在 140×42 与 80×24 下演练了已安装的旅程，包括进入、刷新、来源失败、scope 身份、详情/Back、保存终端的 Open 以及通知关联。一个最初的 Feed 来源失败缺陷被保留在证据中并已修复，随后独立复核。负责人候选的原生证据与评审者针对未变更父守护进程运行的子 TUI 仍是相互独立的观察。

后期的操作者检查暴露了干扰性的导航与误导性的任务概览。修正后的私有综合评审覆盖新导航、组织项与原生任务状态。其中错误的 NEXT 完成发现被保留、修复并在两种宽度下独立复核。这些私有结果仍限于所演练的旅程与环境。

9 月 14 日接受的 VM 检查显示：加载普遍在 0–2 秒之间并偶有超时，此外还覆盖了格式、图标颜色与默认视图。该观察结果并非一般性的延迟或可用性保证。后来对同一候选的恢复保留了会话，但并未确立持久的响应性修复。

- 间歇性读取超时依然存在。继承而来的 CLI 健康检查时限可能在发出队列请求之前就把守护进程报告为无响应，即使直接请求能够成功。该缺陷未在本版修复；偶发的服务器延迟也仍未归因。
- 较早的通知检查使用了受控的 HTTP 响应与合成回复。后来一次真实的单消费者 Slack 演练确认了 decision/detail/FYI 的完整发布与回复关联；操作者确认了在手机上收到并阅读。该观察并未确立 OS 推送行为或所有客户端的表现。
- 终端提供商证据覆盖一次性的 Herdr 成员。其他提供商、远程与父宿主行为不因本次评审而确立。
- Saved Build watch 发现已在 VM 中演练并记录其原生判定。该观察并不确立一般性的导航响应性。
- 并发的默认 TUI 客户端仍受既有的编程式控制套接字限制。测试中套接字各不相同并不证明一般性的多客户端隔离。
- 版本与包检查不会重复开发旅程，也不会确立新的整体源码、全平台或不熟悉产品的人工使用者可用性结果。
- 观察到的关闭排空超时、已记录的配置保留不确定性以及此前一次 `recorder_write_failed` 观察均未声称已解决。恢复证据仍与常规进入验证相区别，并不确立整个系统的健康。
- 历史源码扫描发现保留其已记录的处置结论；变更路径扫描干净不代表全源码扫描干净。
- 捆绑的 Workflow Specs（包括 `basic-loop`）在升级改变安装目录后可能从发现结果中消失，即使其 YAML 完好无损。发现问题的修复被明确推迟到 0.5.14 之后；本版不包含相应修复。
