---
title: "v0.5.6 — 世界搭建即上下文工程"
---

OpenRig 0.5.6 发布上下文系统的下一层，让长时运行的智能体变得持久，并让发给人类的消息变得可信。三大主题：席位赖以运行的上下文是结构化、带标签、可核验的；智能体席位现在可以在没有人工管理交接的情况下，活得比自己的上下文窗口更久；一切路由给人类的内容都携带送达证明。

## 上下文系统：结构化、带标签、可核验

- **mission 安装**。一套成文的五层约定（`docs/reference/mission-install.md`），用于把项目上下文安装进席位：各个部件、它们的排布、席位自身所处的位置、当前契约，外加一个"自行推导增量"步骤，用以证明安装内容是被消化而不是被扫过一眼。
- **设定（lore）路由**。席位在本地学到的东西会路由进可寻址的 rig 本地设定包（lore pack）（`docs/reference/lore-routing.md`）——自诞生起就携带成熟度阶段，且在结构上被排除于一切随附发布内容之外。
- **分类学贯穿全局**。进入 `rig context` 的每个包都携带其类别——WORLD / LORE / SKILLS / MISSION——并在列表中呈现；未打标签的包会遭到响亮拒绝。
- **断言可核验的公共世界包**。公共上手包以原子（atom）形式撰写，其中每条断言都携带一个可能失败的检查，校验器随包发布——公共内容因此不会悄然腐坏。
- **一份完整、可自我检索的技能索引**。技能路由器的索引现在覆盖全部已随附技能集，可以通过它自己传授的路由检索到，并携带一个复现测试，使覆盖缺口始终能被发现。
- **对随附内容把关实质**。对每个打包文件（包括 bundle 与 npm 呈现面）运行一次全呈现面审查，作为一项具名的发布步骤；本发布随附的 5,316 个打包文件全部通过。

## 连续性：寿命超越自身上下文窗口的席位

- **智能体规格中的连续性策略**。`compaction_strategy` 现在是活的配置，有四种模式：`default-compaction`、`managed-compaction`、`handover` 与 `apprentice-handover`。模式适用于 Claude 席位（正向运行时匹配——Codex 席位保持其原生行为），并通过与智能体规格其余部分相同的 spec-default < profile < member 优先级链解析。
- **学徒交接，自动化**。声明 `apprentice-handover` 的席位会得到两个预伏触发器：临近其上下文阈值时，系统创建一个全新的继任席位并执行其上手安装；更临近窗口边界时，系统为负责执行换任的席位铸造一个有归属的交接工作项。执行席位是声明式配置（策略上的 `mechanic:`）——绝不从拓扑推断，缺少时会响亮拒绝预伏。
- **托管压缩配诚实恢复**。`managed-compaction` 模式下的席位会收到压缩前的准备提醒（在窗口关闭前存入你的状态），并在配置的恢复完成后收到一条持久回执，记录这次恢复实际找回了多少可用上下文——那种"静默重新填满窗口而非找回宽度"的恢复因此可见。
- **上下文用量触发器成为原语**。`rig watchdog` 新增用量阈值条件：当某个席位的上下文用量越过按席位校准的阈值时，触发任意命令。连续性模式构建于其上；你自己的自动化也可以。

## 人类层：可证明的送达

- **不再有静默落空（fall-through）**。一个统一的目的地解析器对每次派发分类：绑定终端的席位走终端；已注册人类与虚拟席位经网关路由；任何内容都不会落进注定无法成功的终端查找。未注册的外部地址会得到结构化、带讲授的拒绝。
- **工作项上的送达回执**。每次网关投递都把回执原子地写进队列行：`posted`（附消息时间戳与频道）、`transport-failed`（附报错），或——可推导得出——`never-posted`。`rig queue undelivered` 现在先查这本台账，只返回真实的失败。"这条消息送到了吗？"读一次即有答案。
- **通知级别，一套词汇**。队列流转在写入时按 `RECORD` < `NOTICE` < `ALERT` 分级——需要人类决策的是 `ALERT`；系统仪式性事件是 `NOTICE`；其余归入持久记录。两个独立旋钮分别配置投递的最低级别与打断的最低级别。
- **送达规则引擎**。存储的每个人类偏好与可用性，决定每类消息如何送达。`off` 偏好只压制打断——绝不压制持久记录、投递或回执。离开（away）时间窗把例行消息延迟为摘要（4 小时与每日两种），并在构造上保证恰好一次送达：持久的阶段性标识、重试直到拿到真实回执、且各摘要结构上互不重叠。
- **在 Slack 中拖入的文件变成工作**。文件或图片上传会落地为一个工作项，文件被转移到本地存储并按路径引用——经认证的下载、大小受限、逐文件失败会点名标出，且任何 URL 或 token 都不会写进行。被已注册人类阻塞的搁置（park）会自动进入告警路径，并在每个阶段恰好投递一次。

## 运维层面的诚实

- 被限速的席位在其宣布的重置时刻恰好收到一次定时唤醒。
- 持有已认领在途工作却闲置的席位会被系统唤醒，消费经仲裁的活动事实源——每次搁置阶段恰好唤醒一次。
- Refocus 状态以席位当前占用者为键；全新占用者绝不会继承前任的基线。
- `rig ps` 把已认领的在途工作计入分派工作。
- 空正文的发送会被拒绝；未知的守护进程 API 路由返回 JSON 404。
- 卡滞巡检的发现项在关闭后停止重新铸造；跨主机监护核验会持久完成，而不是无限刷新。
- 阻塞物处置已统一：一个助手（helper）、跨主机关闭如实记录、投递发生在事务提交之后。
- rig 展开与序列化对得到的输入保真：`session_source` 版本、`services` 与成员覆盖项都能经受往返；fork 会转发 model、role、restore policy 与 label。
- `rig view show execution` 在读取时推导"谁在构建什么、接下来是什么"，以及每个条目的完成梯队（locked / built / reviewed / folded / adopted）——未知一律呈现为 INDETERMINATE，绝不会呈现为空闲或完成。

## 流程与参考文档

- SDLC 约定文档现在是一份组件菜单：按 mission 从简单流、浪潮（wave）模型或严格叠加层中选择，以规划严谨度为可调旋钮。四份完整参考随附于 `docs/reference/`：`planning-dial.md`、`wave-sdlc.md`、`release-boundary.md` 与 `product-management-pass.md`，另有 `mission-install.md` 与 `lore-routing.md` 加入。

## 升级注意事项

- 三个数据库迁移在守护进程启动时自动应用：`074_context_usage_watchdog`、`075_context_usage_watchdog_generation` 与 `076_owner_notification_levels`。无须任何人工步骤。
- 上下文包：随附 41 个（此前为 39 个）。
- 送达默认值刻意全开（`NOTICE` 及以上投递，`ALERT` 及以上打断）。请用两个旋钮按实测流量下调，而不是预先过滤。
- 连续性模式按席位自愿开启（opt-in）；未配置的席位与今天的行为完全相同。
