## 摘要

OpenRig v0.2.0 是一大步跨越。它交付了由守护进程支撑的持久化协作层——流（stream）、队列（queue）、项目（project）、视图（view）、看门狗（watchdog）监管以及工作流运行时——同时带来重新设计的恢复体验、智能体启动器（agent-starter）注册表、跨主机操作，以及一大批生命周期与恢复强化修复。这是漫长内部强化周期之后的首次公开发布，因此相对 v0.1.12 的变化幅度很大。

## 本版包含内容

- 全新的守护进程自有协作层：`rig stream`、`rig queue`、`rig project`、`rig view`、`rig watchdog` 与 `rig workflow`。
- 智能体启动器（agent-starter）注册表，让 RigSpec 成员可以引用具名的启动预备条目（`starter_ref`），而不必将其内联。
- 全新的 restore-packet 命令呈现面，用于跨运行时捕获智能体会话数据包。
- 新增成员级启动源模式：`session_source: { mode: rebuild }` 与 `session_source: { mode: fork }`。
- 跨主机操作：`rig ps`、`rig whoami`、`rig send` 与 `rig capture` 接受 `--host`，以进行基于 SSH 的 shell-out 调用。
- Claude Code 与 Codex 托管会话在生命周期、恢复与运行时真实性方面的大量改进。
- 十六个新的 SQLite 迁移（021 → 036），支撑新的协作、视图、看门狗与工作流表，另有一些可观测性与配置档案（config-profile）方面的补充。

## 用户可感知的变化

### 新增协作命令

一组全新的 `rig` 命令提供了由守护进程支撑的持久化协作呈现面：

- `rig stream` —— 发出并查询流条目；可通过 SSE 订阅。
- `rig queue` —— 创建、认领、交接并关闭队列条目。包含 `handoff`、`handoff-and-complete`、`update`、`show`、`list`、`whoami`、`inbox-drop`、`inbox-absorb`、`outbox-drop` 与 `outbox-collect`。
- `rig project` —— 将已分类的工作条目归入持久化项目，具备分类器租约/存活/回收语义。
- `rig view` —— 查询协作状态上的内置与自定义视图；通过 SSE 消费变更事件。
- `rig watchdog` —— 调度周期性与条件性作业，采用守护进程原生监管。
- `rig workflow` —— 运行多步工作流，带有持久化的轨迹记录与 workflow-keepalive 作业。

这些命令的状态持久化在 OpenRig 守护进程的 SQLite 数据库中，可通过守护进程 API 观察，并在更新时发出 `view.changed` 及相关 SSE 事件。

### 新增 `starter_ref` 成员字段

`rig up` 现在接受 RigSpec 成员上的 `starter_ref`。守护进程会在启动时从 `agent-starters/` 注册表解析该具名条目，并将其内容合并进席位按工作目录（per-cwd）生成的指导文件（Claude 为 `CLAUDE.md`，Codex 为 `AGENTS.md`）。包含凭据标记的输入会被拒绝，并返回脱敏后的拒绝信封。`starter_ref` 与同一成员上的内联 `session_source` 互斥；在 plan-mode 下，对终端运行时与 fork 组合会在前置阶段即被拒绝。

### 新增 `session_source` 模式

成员现在可以声明：

- `session_source: { mode: rebuild }` —— 在每次物化（materialize）时从一组具名工件重建成员。
- `session_source: { mode: fork }` —— 启动时从既有来源分叉（fork）出新成员。

### Restore-packet 命令呈现面

全新的 `rig restore-packet` 命令族用于跨运行时捕获可恢复的会话数据包。它包含针对 Claude 与 Codex 会话记录的解析器与脱敏处理、模式（schema）校验、数据包写入，以及读取/校验流程。另有一个 `rig restore-check` 命令用于恢复就绪检查。

### 跨主机操作

`rig ps`、`rig whoami`、`rig send` 与 `rig capture` 现在接受 `--host <ssh-host>`，以针对远程机器执行。CLI 通过 SSH 向外层 shell 发起调用；调用之前远程机器上无需常驻任何智能体或守护进程。

### 生命周期、恢复与运行时真实性改进

- 新的生命周期分类：`recoverable`、`degraded` 与 `attention_required`。Codex 认证拒绝现在会端到端地呈现为 `attention_required`。
- 当不存在 auto-pre-down 快照时，`rig up <rigName>` 会回退到手动快照，因此该路径下的启动不再静默失败。
- 恢复现在有显式的尝试 ID（attempt id），运行时真实性的对账机制可防止过期状态伪装成存活状态。
- Codex 恢复现在通过原生探测（probe）验证窗格（pane）；`rig expand` 的恢复指引会指向收缩再加扩展（shrink+re-expand），而不是尝试启动一个注定失败的 rig。
- `rig ps --fields` 现在按层级使用允许列表（allowlist）拒绝未知键。`rig ps` 还支持 `rigName` 别名与有界输出模式。

### 守护进程启动的智能体现在可直接运行 `rig`

此前，由守护进程启动的 Codex 席位需要显式的 `OPENRIG_HOME`/`OPENRIG_PORT` 环境变量，以及 PATH 上非默认的二进制路径。现在由守护进程启动的席位可以直接使用 `rig`，智能体与操作者无需再为每个席位做环境变量上的腾挪就能使用标准 CLI。

### Watchdog 帮助、队列执行者推断及其他小修复

- `rig watchdog --help` 现在会列出 workflow-keepalive 作业类型。
- 未显式指定执行者时，`rig queue` 会从托管会话推断执行者。
- CLI bin 在构建之间保留可执行位。
- Chatroom wait 测试夹具在时间上是稳定的（在净化环境下 `chatroom wait` 测试不再抖动）。

## 运维/安装注意项

升级已发布的 CLI 之后：

```bash
npm install -g @openrig/cli@0.2.0
rig --version    # 预期输出 0.2.0
```

你需要重启守护进程，以加载新的模式（schema）与行为：

```bash
rig daemon stop
rig daemon start
```

守护进程会在首次启动时对它的 SQLite 数据库应用 021-036 迁移。按约定迁移只能向前；如果需要回滚，请从快照恢复守护进程数据库，并在重启前把守护进程二进制换回上一个构建。如果想要一条干净的回滚路径，请在升级后首次启动守护进程之前先给数据库拍快照：

```bash
cp ~/.openrig/openrig.sqlite ~/.openrig/openrig.sqlite.pre-v0.2.0.bak
```

如果你的受管控制面环境中还有进行中的 rig 在运行，请把守护进程重启规划为一个升级窗口。升级本身很直接，但守护进程的停止/启动会中断活跃的 SSE 消费者以及任何进行中的 `rig up` 流程。

## 已知限制

- 新的协作呈现面（`rig stream`、`rig queue`、`rig project`、`rig view`、`rig watchdog`、`rig workflow`）由守护进程支撑。宿主守护进程必须为 v0.2.0 才能提供这些功能；较旧的守护进程不会暴露这些命令，并且可能静默忽略成员上诸如 `starter_ref` 这类可选启用（opt-in）字段。
- `runtime: claude` 不是合法的 RigSpec 运行时写法；Claude 托管席位应使用 `runtime: claude-code`。这是运行框架（harness）/规格语法问题，而非产品限制，但它曾让操作者感到意外。
- 看门狗策略与工作流规格持久化在守护进程数据库中。目前还没有一等公民的 CLI 用于批量编辑自定义看门狗策略；后续版本会带来更好的人机工学。
- Phase E 的呈现面（协作层的护栏、渲染与引导（steering））被有意推迟到未来的产品泳道（PL-006/PL-007/PL-008），不属于 v0.2.0。
- 生命周期分类比以前更真实，但 OpenRig 仍没有一套完全显式的、基础设施级的状态机。部分恢复路径仍依赖启发式方法，而非完善的提供商原生原语。

## 已执行的验证

- 在 Node 22 下、剥离 OpenRig 环境变量后的净化全量 CLI 测试套件：56 个文件 / 794 个测试通过。
- 根目录 `npm run build` 与 `npm run build:package` 通过。
- 在 Mode 3 隔离虚拟机下的真实智能体自用（dogfood）测试：虚拟机本地的 OpenRig 守护进程/状态，以及真实的 OpenRig 托管 Claude Code 与 Codex 席位；纯 Claude、纯 Codex 与 Claude→Codex 混合路径均通过新的 `rig queue`、`rig stream`、`rig workflow` 与 `rig watchdog` 呈现面端到端演练。
- 在虚拟机本地从源码全局安装 `@openrig/cli`，`rig --version` 报告预期版本，托管席位直接运行 `rig`。
