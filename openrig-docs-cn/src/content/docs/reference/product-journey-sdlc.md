title: "产品旅程 SDLC 组件"
---

这是一份用于构建最小完整用户成果的可复用菜单。任务或切片只选择其工作所需的组件，并在 mission/slice YAML 中记录它们的顺序。这**不是一种模式、一条流水线、一种拓扑、一种 rig 形态，也不是一套强制门禁**。若不存在任何组合，使用 `sdlc-conventions.md` 中的轻量 Part A 流程。

## 狗屋与月球基地

**狗屋**（doghouse）是用户要的那个真实产品成果。**缺门**（missing door）是一种实现：内部可能打磨得很光鲜，却无法完成其基本的用户职责。**月球基地**（moon base）是指精密复杂的机器——常是守卫、抽象、证明仪式、安全表演或流程脚手架——消耗了大部分投入，却没让狗屋能用。

按此顺序使用这条披露阶梯：

1. 用一句话点名狗屋，不使用流程词汇。
2. 在欣赏内部之前，先经由公开呈现面演练它的门。
3. 修复最小的缺失产品接缝。
4. 仅当证据表明下一层正在造成可见失效时，才考虑更深的机器。
5. 移除或拒绝任何不保护、不交付某个被点名用户成果的东西。

同样的纪律既适用于新任务，也适用于抢救一个已漂移的任务。在新任务中，它防止月球基地；在抢救中，它查明是否还剩一个可用的狗屋，并把不该被继续携带的机器与之分开。

## 组件契约

下列每个组件都陈述：

- **何时适用**——接纳它的证据。
- **何时跳过**——不运行它的最省理由。
- **输入**——负责的智能体实际必须读或观察什么。
- **动作**——被执行的有界工作。
- **输出**——交给下一个组件的工件或可观察结果。
- **停止**——防止组件自我扩张的边界。
- **下一步**——常规后继；YAML 可以选择另一条显式边。

组件 ID 是稳定地址。其文字描述可以改进，而不迫使 mission YAML 变更。

## 组件目录

### context.fresh-start

- **何时适用**：先前上下文可能携带过时的架构、结论或实现惯性。
- **何时跳过**：当前智能体能从一手来源独立陈述用户成果、起始候选与边界。
- **输入**：身份、project/mission/slice YAML，以及选定的地址。
- **动作**：将选定上下文载入一个全新会话，或从活源重新定向当前会话。清空席位需要其单独的连续性决策；选择本组件并不构成授权。
- **输出**：一段话的就绪声明，点名角色、用户成果、起始候选与边界。
- **停止**：不要仅因为旧队列传说存在就去重构它。
- **下一步**：`intent.recover` 或 `journey.choose`。

### intent.recover

- **何时适用**：工作已存在，但可能已偏离其原始用户意图。
- **何时跳过**：这是绿地工作，且只有一个当前、无歧义的意图。
- **输入**：最早的权威意图、其后的 mission/slice 规格、候选代码，以及观察到的用户行为。
- **动作**：把需求与后来的规划者加工区分开；识别仍需的最小成果集合与显式反目标。
- **输出**：一份简明的打捞地图：保留、待检、不再需要——其本身绝不是破坏性裁决。
- **停止**：不要把此前的审查强度或沉没成本当作产品价值。
- **下一步**：`journey.probe`。

### journey.choose

- **何时适用**：新任务有意图，但还没有被验证过的产品路径。
- **何时跳过**：`intent.recover` 已经点名下一个最小成果。
- **输入**：权威意图与当前的公开产品呈现面。
- **动作**：选定一条端到端用户旅程，其完成可提供独立价值。
- **输出**：一个可观察成果，外加其最小可信的公开探测。
- **停止**：只选一个成果；相邻能力属于另一次组合。
- **下一步**：`journey.probe`。

### journey.probe

- **何时适用**：永远适用，在产品代码被添加或被抢救之前。
- **何时跳过**：绝不跳过；把探测缩小规模即可。
- **输入**：真实用户操作的公开 CLI、API、UI 或其他呈现面。
- **动作**：运行最小的一次性端到端旅程，并检查其效果，而不只是退出状态。
- **输出**：无需改代码即 PASS，或一个具体、用户可见的缺口并保留证据。
- **停止**：一段通过的旅程不授权投机性的加固。
- **下一步**：PASS 即完成；否则 `depth.look-below` 或 `build.minimal-gap`。

### depth.look-below

- **何时适用**：公开失效复现、跨越组件边界、与更低层状态相矛盾，或表面修补将重复下层已拥有的逻辑。
- **何时跳过**：失效是局部的、已被理解、可在公开接缝处无重复地修复；唯一论据是"更健壮"时也跳过。
- **输入**：一个观察到的公开失效，以及直接负责的接缝。
- **动作**：只向**下一层**下降；陈述因果假设，点名将证伪它的低层观察，然后检查或探测那一层。
- **输出**：三种深度决定之一：
  - `LOCAL`——修复公开接缝；
  - `BELOW`——修复被点名的承重接缝，并重放公开旅程；
  - `HOUSEKEEPING`——在改动产品代码之前，先修复环境/数据/拓扑卫生。
- **停止**：每次准入只允许一次下降。第二次下降需要新证据与新陈述的假设。"顺便"、泛化的预防以及无关清理都在范围之外。
- **下一步**：`build.minimal-gap`、`research.before-build`，或内务处理。

本组件是平衡点。拒绝向下一层看，会产生表面补丁与反复缺陷；没有证据门禁就向下看，会产生月球基地。目标是第一道承重接缝，不是最深可能的解释。

### research.before-build

- **何时适用**：因果假设依赖一个不稳定的外部事实，或一个无法本地推导的产品契约。
- **何时跳过**：源码、运行时状态与公开探测已确立机制。
- **输入**：一个可回答的不确定性，及其决策后果。
- **动作**：只获取足以决定实现形态的一手证据。
- **输出**：决定、引用来源、剩余不确定性。
- **停止**：当实现决定已获支撑，研究即告结束。
- **下一步**：`build.minimal-gap`。

### build.minimal-gap

- **何时适用**：失败的旅程与因果接缝均已确立。
- **何时跳过**：`journey.probe` 已通过，或发现属于内务而非代码。
- **输入**：用户可见缺口、深度决定、既有接缝，以及显式边界。
- **动作**：添加最短的、可读的改动来完成旅程，复用既有产品接缝。
- **输出**：一个干净的候选，以及聚焦的证据表明失效因所述原因而改变。
- **停止**：除非成果离了它就无法工作，否则不引入新框架、新安全层、新 schema、新抽象或相邻动词。
- **下一步**：`qa.public-journey`。

### qa.public-journey

- **何时适用**：一个候选宣称完成了完整的用户成果。
- **何时跳过**：集成之前绝不跳过；仅在未选择独立性时，构建者方可就极小改动自行持有本项。
- **输入**：确切的候选、原始公开探测，以及边界。
- **动作**：在一次性上下文中从用户呈现面运行旅程；检查结果状态与部分失效行为。
- **输出**：CLEAR，或一个具体的不匹配。
- **停止**：QA 不重新设计产品，也不强求未被选择的仪式。
- **下一步**：`review.scope-maintainability`，或回到 `build.minimal-gap`。

### review.scope-maintainability

- **何时适用**：该成果被选定要接受独立评审。
- **何时跳过**：组合刻意把低风险改动留在轻量单智能体路径内。
- **输入**：确切的候选、意图、公开 QA 证据，以及基线 diff。
- **动作**：评判正确性、可读性、必要性、对既有接缝的复用，以及公开旅程——而非内部代理指标——是否可用。
- **输出**：CLEAR，或一个有边界的源码/产品发现。
- **停止**：评审者不得仅因先前评审发现过问题就棘轮式加严；评审产品，而非仪式。
- **下一步**：`integrate.one-outcome`，或回到 `build.minimal-gap`。

### integrate.one-outcome

- **何时适用**：一个成果被选定的证据已齐备。
- **何时跳过**：候选未通过检查，或其基线已发生不兼容移动。
- **输入**：确切的候选身份，以及被选定的 QA/评审结果。
- **动作**：集成最小的连贯成果，并让无关候选保持分离。
- **输出**：干净的规范源（canonical source），其中多包含一个用户成果。
- **停止**：不要因为共享一个发布标签就批量打捞无关内容。
- **下一步**：`runtime.adopt`，或下一次 `journey.choose`。

### runtime.adopt

- **何时适用**：成果需要安装运行时证明或迁移证明。
- **何时跳过**：源码级证明已足够，且没有活体行为变化。
- **输入**：干净的规范提交、回滚边界，以及运行时 SOP。
- **动作**：构建/打包/安装确切的提交，原子切换，并验证健康与连续性。
- **输出**：确切的存活版本，以及保留的回滚点。
- **停止**：采用（adoption）即部署，不是更改拓扑或数据的许可。
- **下一步**：`qa.installed-smoke`。

### qa.installed-smoke

- **何时适用**：`runtime.adopt` 已运行，或打包/路径解析属于产品声明的一部分。
- **何时跳过**：没有已安装工件或运行时行为在范围内。
- **输入**：确切的存活版本，以及一次性的公开旅程。
- **动作**：演练已安装的命令路径，核验效果与清理。
- **输出**：安装运行时 CLEAR，或一个具体的不匹配。
- **停止**：不要把冒烟测试扩大为全舰队监控。
- **下一步**：完成该成果，或回到 `build.minimal-gap`。

## 组合规则

1. `project.yaml` 可以声明项目默认值；`mission.yaml` 可以选择目录并为该任务覆盖这些默认值。
2. `slice.yaml` 为该切片选择或覆盖组件。
3. 边是显式数据。数组顺序只是呈现，不是依赖。
4. 选择诚实适配该工作的最少组件。
5. 组件可由与其相邻组件相同的席位持有，除非独立性是该组合刻意要求的属性。
6. YAML 描述工作；它不是强制执行引擎，不产生任何自动门禁。

仓库地址示例：

```yaml
sdlc:
  catalog:
    root: repository
    address: docs/reference/product-journey-sdlc.md#component-catalog
  components:
    - id: journey.choose
      owner: planner
    - id: journey.probe
      owner: qa
    - id: depth.look-below
      owner: builder
      admission: evidence-gated
    - id: build.minimal-gap
      owner: builder
    - id: qa.public-journey
      owner: qa
  edges:
    - from: journey.choose
      to: journey.probe
    - from: journey.probe
      to: depth.look-below
      when: public failure needs causal discrimination
    - from: journey.probe
      to: build.minimal-gap
      when: local gap is already established
    - from: depth.look-below
      to: build.minimal-gap
      when: decision is LOCAL or BELOW
    - from: build.minimal-gap
      to: qa.public-journey
```

仓库地址从 `git rev-parse --show-toplevel` 解析。在上下文库之外，`path#h2-slug` 与 `path#h2-slug/h3-slug` 地址请使用 `loading-addressable-markdown` 技能。

## 组合示例

### 绿地产品旅程

`context.fresh-start → journey.choose → journey.probe →
build.minimal-gap → qa.public-journey → review.scope-maintainability →
integrate.one-outcome`

仅当探测满足其准入规则时才加入 `depth.look-below`。新任务不需要抢救考古。

### 漂移任务的抢救

`context.fresh-start → intent.recover → journey.probe →
depth.look-below? → build.minimal-gap → qa.public-journey →
review.scope-maintainability → integrate.one-outcome`

问题不是"哪些旧提交能过评审"，而是"哪个必需的用户成果可用、什么阻碍下一个成果、多少代码能完成它"。

### 反复出现的跨层缺陷

`journey.probe → depth.look-below → research.before-build? →
build.minimal-gap → qa.public-journey → qa.installed-smoke?`

复现只准入一次因果下降。它不授权全面重写平台。

## 解析选定路径

在全新开始、恢复或新指派时：

1. 用 `rig whoami --json` 推导身份。从指派/工作区绑定解析项目的工作根；`rig config get workspace.root` 定位已配置的工作树，它可能与该席位的代码检出不同。
2. 读取 `project.yaml` 及其项目权威上下文。顺着其任务根找到被指派的 `mission.yaml`，再顺着其组合引用找到当前生效的 `slice.yaml`。读取这些记录点名的当前意图与验收文件。不要从旧的上手包或文件夹的新旧程度来挑任务。
3. 按顺序解析 SDLC 选择：项目默认值、任务默认值，然后是当前生效切片的显式选择/覆盖。更窄的显式选择取代更宽的组件列表；它不会追加每一级祖先的门禁。遇到可寻址的波次图，依循其成员构成、评审模型与边界；显式的具名切片例外只适用于该切片。
4. 只读取被选中的组件与额外的可寻址上下文。仓库引用从代码仓库根解析；已安装引用从 `$OPENRIG_HOME/reference` 解析；上下文包（context pack）引用用 `rig context get`。对 Markdown 的 `#section` 地址，使用 `loading-addressable-markdown`，而不是载入整本无关的手册。当任务的证据需要时扩大调查：地址映射是起点，不是搜索上限。
5. 简要陈述用户成果、当前角色、候选、选定路径与下一个完成边界。没有组合即采用 `sdlc-conventions.md#a1-the-flow-in-one-pass` 中的轻量 Part A 流程。不要为了有一个组合而撰写组合，也不要因为那些角色存在就铸造 QA、守卫、评审、锁定或证明门禁。极小改动上构建者可以自行验证整个成果；独立评审只在被选择时发生。

被引用的文件缺失是一个被点名的缺口，不是"没有选择"的证据。检查，或请负责人来消解有分量的歧义；不要从一条被显式选定的严格路径悄悄回落。负责人可以为点名的工作显式修订选择；把该决定记录在工作的权威位置。作为事实声明，当前的命令/源码现实高于过时的 YAML：记录不匹配，重新推导，并保持 scope 与观察到的状态之间的区分。

启动叠加层、角色指引、可用席位、旧模式名称与历史包都不能给这一选择增加步骤。它们只供给能力。技能在被选定的工作需要时载入；没有测验、没有逐文件 ACK 门禁、也没有普遍预载要求。

## 空白智能体启动

在挑选工作之前，先遵循上文的**解析选定路径**。对一条成文波次，按其局部纪律构建并验证每个切片，并在需要处串行集成；当成文波次边界到来时请求一次独立评审。不要在等待期间启动逐切片评审。被单独选定的严格切片保留其点名的检查。评审发现佐证的是有边界的修复，而不是让下一轮的流程自动加码。
