> **唯一事实来源**：本文档是 SDLC 约定的现行 SSOT。脚手架模板、咨询式的 scope 审计、`mission-slice-sop` 技能与随附的引导 overlay 都指向这里——它们不得整篇复述本文档（复述正是漂移的温床）。

OpenRig 是一座由人类从高空驾驭的软件工厂。人类记录意图；智能体把意图变成计划，把计划变成构建，把构建变成证明。TUI 把磁盘上已成文的工作投射出来，并且在选定了归属的证明策略之处，从已记录的裁决推导就绪状态。这些编写约定**对智能体是咨询式/失效开放的（fail-open）**：审计只记录与建议；谁有资格裁决，由所选的证明策略另行管辖。


## 如何阅读本文档——两个部分，其中只有一个是默认

| | 适用条件 | 内容 |
|---|---|---|
| **PART A——简单 SDLC** | **始终适用。这是默认。** | 工件约定、比例原则、咨询式审计、诚实护栏 |
| **PART B——严格 overlay** | **仅当人类操作者、或转达该决定的编排者，把重流程指派给一件具名的工作时** | 证明契约格式、两把锁、C1 证明投放、被锁定的角色契约 |

**不得自行为自己选择 Part B**。如果你认为某项工作配得上它，用一句话说明理由，然后继续按 Part A 进行，直到另行通知。Part A 对应 `mission-slice-sop` 技能；Part B 在下文定义，仅在获指派时适用。


## 组件菜单——本文档是一份菜单，不是一条流水线

SDLC 由**逐任务（mission）挑选的组件**组装而成，而不是一条强制的单一流程。本文档描述这些组件并给出建议；每个任务（或运行它的团队）按阶段挑选。同一阶段可以存在多个有效选项——选定其一不会废弃其余。下文没有任何内容会删除或覆盖既有组件。

| 阶段 | 目前可用的组件 |
|---|---|
| **产品/任务准备** | **产品管理工序（product-management pass）**——规划之上的那一层，在规划者接触任务之前由顾问/PM 席位运行。构建是一条有损压缩流水线（PM 意图 → 规划者规格 → 构建者代码）；内容不会因邻近而自动向下渗透，因此这道工序以原始来源为根据，综合出唯一一份记录在案的 scope，把负责人的决策整理到决策就绪（decision-ready），在计划时刻铸造切片，把完整设计契约内联（INLINE）存入每个含设计的规格（负责人原话逐字、已定决策、证据、完成的形状、反目标），从规格本身路由出完整阅读清单与互联网调研指派，为每个切片的规划拨盘档位附上理由，并以最狭窄的下游读者身份重读每份规格。衡量标尺：仅凭 SPEC.md 及其显式路由到的内容，就能让一个不具备作者上下文的读者复现该意图。完整参考：`product-management-pass.md`。 |

# PART A——简单 SDLC（始终适用）

## A1. 一遍过完的流程

```
intent (what is this for, what does done look like)
      → build it
      → test it with your own eyes
      → record honestly what you verified, and what you did NOT
      → hand off (rig queue handoff) or stop
```

在完成时验证整个成果，而不是每步增量都走一遍评审链。对微小的变更，构建者可以自行持有这项检查。独立 QA/评审只在项目/mission/slice 组合或显式的负责人指派选中它时运行；对 wave 而言，在其成文的边界处运行。可用的角色绝不增加门禁。权威查阅入口是 `product-journey-sdlc.md#resolve-the-selected-path`。交付工作时，要带着证据证明其承诺的用户成果确实可用。

对发布任务而言，`mission.yaml` 还要在构建工作开始之前点名 Git 策略：哪条分支/ref 是累积集成真相、其基线是什么、以及该真相何时与 main 对账。持续集成到 main，与先折叠发布线再做一次显式合并，两者都有效；让这个选择保持隐式则不行。

**更重的流程——证明契约、plan-lock、C1 投放、proof-lock——属于 PART B，未经指派不生效**。

## A2. 切片工件约定（UI 投射什么）

每个切片目录包含：

- **`SPEC.md`**——唯一一个成文的节点文件。其 frontmatter 携带 `intent:`，并可携带 `depends_on:` 作为兄弟工作节点 ID 的列表；`depends_on` 为兄弟节点排序，而仅按路径的上下文追溯绝不跟随它。正文以三个约定章节开头，顺序与标题一字不差：
  - **`## Intent`**——所记录的意图，逐字原文。UI 把这段文字投射为 INTENT 区块。
  - **`## Mini-requirements`**——简明、一眼可读的需求层级（编号列表）。这是人类操作者的第一个结构化抓手；审批从这里开始。
  - **`## Proof contract`**——承诺交付物的复选框清单（见 §3）。UI 的 DELIVERED 区块把每一项与其证明配对。
- **`PROGRESS.md`**——切片的验收清单：持久的 mission/slice 级待办，在验收时勾选。进行中的步骤留在工作智能体自己的 todo 工具里。
- **`PROOF.md`**——留存的证明摘要，与 `SPEC.md` 的证明契约显式配对。
- **`proof/`**——证明工件目录。经策展的权威证据经由 `rig proof` 携有效 C1 头落入此处（§5）。

旧式的 `README.md`、`IMPLEMENTATION-PRD.md` 与约定确立之前的目录树无限期保持可读。新脚手架不创建也不镜像它们，修复是增量的：绝不删除、重命名或改写旧字节。

当归属 scope 选择 `proofPolicy.judges` 时，用 `rig proof judge` 在契约条目上记录一次可归属的接受、拒绝或撤回决定，用 `rig proof show` 读取自切片、mission 直至项目逐级推导的就绪状态。由最近的切片、mission 或项目策略选出有权裁决者；`rig proof --help` 说明设置、选择器与证据要求。一次更正会保留历史与无关裁决，不去编辑祖先的状态清单。工件可以标明非代码工作，而不必伪造一个提交。证据采集（`proof add`）、策略接受、更高层成果裁决与发布是彼此独立的。这个可选组件不会选择 Part B，也不会增加强制评审门。

三个章节投射进 UI 的单一评审结构：**INTENT → PLAN → DELIVERED** 的垂直堆叠。缺章节的切片仍然可以渲染（投射退化为一个灰显的"—"，绝不虚构内容）——但它在评审中不顶用。

## A3. 诚实护栏（公开呈现面 + 引注哈希）

### 公开仓库呈现面要读起来像产品工程

提交信息、代码注释与 markdown/文档都是**公开仓库呈现面**：它们面向的读者既接触不到、也不关心这些工作在内部如何被治理。两条规则，**只向前**（不为此改写既有历史）：

- **不逐字引用内部言论**，尤其是带情绪或沮丧色彩的。引用决策的*技术内容*，绝不引用人，也绝不引用做出决策时的心情。
- **不用治理框架来表述**。写这个变更做了什么、为什么就其本身而言是正确的——而不是谁裁定了它、谁批准了它、或它过了哪道内部门。"守卫在锁定时触发，因为一个占位符本会满足联接"是产品工程。"X 在 Y 门裁定了此事"则是内部治理泄漏进公开工件。

检验标准：项目之外的读者应能在不知道任何内部角色、席位或流程名称的情况下据此行动。这与署名和语气上的原则同源，只是施加对象不同。

### 引注哈希要说明它覆盖了什么

作为证据提交的哈希，只有在读者知道它对哪些字节取值时才是可校验的。**随哈希一并说明覆盖范围**，以下两种形式之一：

- **整文件**——并明确说明，包括**末尾换行符**是否在被哈希的字节之内；或
- **文件 + 精确的区段定义**——区段是*定义的一部分*，而不是去哪里找的提示。

两个诚实的人对同一工件取哈希可能得到不同摘要，而谁都没有错（例如，一个对 frontmatter 块取值，一个对整文件取值）。覆盖范围让被引注的哈希可校验，而不只是唬人。

**以路径 + 锚点为权威，整文件哈希只用来给引注标注日期**。地址在合法的内容变更之后仍然成立；摘要则不然。

## A4. 当实施发现意图建立在不存在的东西之上

切片的意图只能在其假设成立的范围内被兑现。有时实施会发现一个已锁定的意图所依赖的功能**并不存在**——不是缺了细节，而是缺了能力。

**诚实的回应是把雄心向下修正到现实所能支撑的程度，并把缺失的功能点名为一项独立的工作**。把切片标记为 **PARTIAL**，并写一份文档，向下游读者讲清准确的经过：

1. 意图要求了什么（引用被锁定的原文）
2. 实际交付了什么，以及如何按效果验证
3. **什么没有交付以及确切原因**——在源头点名每一项缺失的能力，并给出证明其缺席的文件与行号
4. 交付不覆盖什么，直白陈述——夸大自身覆盖面的场景或特性，比根本不存在更糟
5. **基于你此刻所知划定范围的后续切片**，包括你认为它们应属哪个发布——在发现时刻握有上下文的智能体，是这个题目永远会有的最有学识的读者，下游规划者不应被迫重新发现其中任何一点

**不可接受的做法**：悄悄缩小主张；悄悄扩张切片去补建缺失能力；或在缩水的面上宣布胜利，却仍沿用原切片的名字。**在切片内部补建缺失的部分本身就是 scope creep**。发现它们并把它们路由出去，才是切片在正常工作——而一个暴露出真实产品缺口的切片，已经产出了比它原定功能更有价值的东西。

不要在这上面过度工程化。全部目标就是给下一个读到它的人一个准确的经过。

## A5. 有弹性的中段（比例原则——不铸造仪式）

SDLC 有且只有三个固定的捕获点：**意图** → 一份**成比例的结构化需求** → **证明**。中间的一切都有弹性。对小切片（一个 bug 修复、一篇调研笔记）而言，迷你需求本身就可以是全部规格——约定章节必须在场，切片才能投射，但其内容随工作规模伸缩。门是对"从意图到交付"这一解压过程的无损性检查，不是文书作业。脚手架生成章节；它绝不能铸造仪式。

## A6. 审计（咨询式、失效开放——永远如此）

`rig scope audit`（以及 `rig workspace validate` / `doctor` 中的咨询行）检查这些约定：章节标题在场、证明契约格式良好、`proof/` 工件携带有效 C1 头、UI 切片引用了设计稿。每一条发现都**只记录与建议——它绝不阻塞任何写入路径，也绝不把退出语义变成门**。未知就报告为未知，而不是失败。

## A7. 知识住在哪里（四个指针）

- **本文档**——SSOT。
- **脚手架**：`rig scope slice create` 为每种模板类型生成 `SPEC.md` + `PROGRESS.md` + `PROOF.md` + `proof/`；`rig scope mission create` 生成一份带意图的 `SPEC.md` + `NOTES.md`。核心只生成这种模式中立的形态；模式插件经扩展接缝添加更丰富的材料，而不是教核心学会某种模式。
- **技能**：`mission-slice-sop` 传授 **Part A** 这一轻量默认。**Part B** 在下文定义，仅在获指派时适用——绝不可自选。
- **引导**：随附的智能体 overlay 在启动时把新席位指向该技能与本文档。

# PART B——严格 overlay（仅限指派）

> **进入条件**：以下内容**仅当**人类操作者——或显式转达该决定的编排者——把重流程指派给一件**具名**的工作时才适用。若你没有接到指派就到了这里，停下来，改用 Part A。
>
> **护栏**：锁**有两把，且只有两把**。这里没有任何内容授权对同一工作再来一轮门禁、对文档/注释/测试/夹具设门、或请同伴来把关你自己亲眼就能验证的东西。**砍轮次，绝不砍检查**。当呈现面变化时，档位要**重新选择**。

## B0. 获指派流程的一遍过

```
intent → mini-requirements + proof contract → (UI slices: mockups)
      → plan-lock (rig scope slice approve --scope spec)
      → build the LOCKED set
      → QA: mockup ↔ delivered VISUAL compare
      → proof drops (rig proof add <slice> …)
      → proof-lock (rig scope slice approve --scope delivery)
```

## B1. 证明契约格式

`## Proof contract` 是一份 markdown 复选框清单；每一项是一个承诺的交付物，写成可观察的结果：

```markdown
## Proof contract

- [ ] The consolidated `rig ps` default renders all rigs with a rollup footer — captured.
- [ ] UI: the slice review tab renders the three-section stack — screenshot vs the locked mockup.
```

- 每一项（按条目文本或 1 起始索引）联接到为其作证的证明工件——DELIVERED 区块渲染的正是这个配对，人类因此不必在几十个工件里翻找哪个证明了什么。
- **UI 交付物携带一份计划中的设计稿**（`plannedRef`）：规划智能体产出设计稿并把它附到锁定集上。锁定集中没有设计稿的 UI 切片就是一份不完整的计划。非 UI 切片（后端、技能、markdown）没有设计稿也没有 `plannedRef`——这不是缺口，也不是门。
- QA 没有真正验证过的交付物在 UI 中显示为 `unverified`/`missing`——可见，但绝不硬阻塞。

## B2. 两把锁（随产品发布的动词——不是新机器）

两枚深思熟虑的印章，都由同一个随产品发布的动词写入（`rig scope slice approve`，一条守护进程侧的写入路径：frontmatter 印章 + 只追加的审计行同时落地）：

- **Plan-lock（计划锁）**：`rig scope slice approve <slice> --scope spec`——"规格与我的意图相符；被构建的就是这套工件。"它把 `SPEC.md`（以及计划中的设计稿，如有）钉死，与文件夹中其余一切区分开。
- **Proof-lock（证明锁）**：`rig scope slice approve <slice> --scope delivery`（默认 scope）——最终的"此事已完成"签核；触发冻结。

批准就是冻结/签核——**绝不**等于证明为绿。证明为绿需要一条已记录的裁决（一份 C1 证明工件，§5）；批准印章的存在并不断言工作已被证明。`--on-behalf-of` 诚实地记录委托关系（行动者仍是真正发起调用的会话）。

## B3. 证明投放与 C1 头（封闭集）

证明工件经由随产品发布的动词落入 `proof/`：

```bash
rig proof add <slice> \
  --artifact-type qa \
  --verdict PASS \
  --candidate-sha <the-proven-tip> \
  --money-evidence "one line of money evidence" \
  --file <artifact.md> \
  --evidences "1,3" \
  --media "walk.webm,panel.png" \
  --self-check "I looked at the captures; they show the claim"
```

C1 头的五个必填字段：`slice`、`candidate_sha`、`artifact_type`、`verdict`、`money_evidence`。两份**已批准的封闭集**（扩展其中任何一份都是约定变更，不是局部编辑）：

- `artifact_type`: `guard | qa | rev1-r1 | rev1-r2 | adjudication`
- `verdict`: `CLEAR | BLOCKING | CONCERNING | PASS | NOT-CLEAR`

`candidate_sha` 是联接键：该工件所评判的已证明候选顶端。`--evidences` 点名这次投放覆盖哪些证明契约交付物（条目文本或 1 起始索引）——这个引用填充计划↔交付配对。`--self-check` 是智能体记录下的断言：它确实看过证据。`--media` 点名这次投放所背书的经策展媒体文件（相对切片的 `proof/` 目录——同处一地，绝不绝对路径）；组合器把它们投射进 DELIVERED 条目的证明集。校验发生在投放时刻；审计（§6）为经其他路径到达的工件兜底。**不经投放就把文件手工放进 `proof/` 是反模式**：交付物在 DELIVERED 视图中保持未配对且 `unverified`——要附加媒体，永远通过一次投放的 `--media`。

## B4. 角色契约（让结构自我执行的机制）

- **规划智能体**：逐字编写意图、迷你需求与 `## Proof contract`（每个 UI 交付物带上其设计稿 `plannedRef`）；产出设计稿；锁定计划（`--scope spec`）。
- **构建智能体**：只针对锁定集构建；看设计稿，而不只是规格文本。
- **QA 智能体（拥有比对职责）**：对每个交付物——加载锁定的 `plannedRef`，在测试/演示环境中产出真实工件，**做视觉比对**，经由一次证明投放记录裁决 + 备注，并**策展**权威证明集。差异超出细枝末节时：修复后让另一个智能体复审，或附理由退回——绝不把一个原始差异直接升级给人类。没有记录在案比对的证明投放会让交付物保持 `unverified`——肉眼可见。

**策展规则**：主证明集是智能体所背书的、经策展的"现在它长这样"权威证据——有边界，与交付物 1:1（或少量对一）映射。修复循环的完整工件历史留在 `proof/` 里，再往下一层钻取，绝不进主视图。反模式：一堆只追加的堆积物，人类分不清哪个是最终版、哪个已被取代。

## Scratch 守护进程的密封性：scratch 守护进程打开的库就是你点名的那个

scratch 守护进程的启动会**剥除继承环境中的 `OPENRIG_DB`，并在 scratch 的 `OPENRIG_HOME` 之下点名一个显式的 scratch 数据库路径**——两半都做，每次启动都做：

```bash
env -u OPENRIG_DB \
  OPENRIG_HOME="$SCRATCH_HOME" \
  OPENRIG_DB="$SCRATCH_HOME/openrig.sqlite" \
  node <daemon entry> …
```

一个继承来的集群数据库抵达 scratch 守护进程，**无论结果如何都是运行框架缺陷**——scratch 上下文读取或写入了它从未拥有的状态，而是否有什么肉眼可见地坏掉，靠的是运气，不是密封性。

**让这条规则保持诚实的判别器**：显式设置的 `OPENRIG_DB` 仍按设计**获胜**（`daemon-db-path.ts`）——深思熟虑的分路径配置依然合法且不受影响。这条规则管辖的是**向 scratch 上下文的继承**——那里没有任何人做过任何决定：剥除你没有选择的，然后做出选择。
