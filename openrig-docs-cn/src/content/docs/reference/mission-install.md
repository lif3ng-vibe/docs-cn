一名加入工作的智能体需要两次安装。**世界安装**（world install）教会它现在所处的系统——这里是什么地方、该如何行事、能做什么。**任务安装**（mission install）则教会它项目——在建的是什么、如何走到今天、如今立于何处、哪些是分内之事。本文档是后半部分的约定，适用于任务树所能容纳的任何项目：软件、一本书、账目、研究。

**无法帮到你的那位读者，写下了这份约定**。一个刚刚启动或刚刚清空的智能体无法拉取上下文——它不知道存在什么，因此无从发问。以下每条规则皆由此推出：安装由已经掌握项目的人**代智能体组装并推送**，一件接一件。

## 何时执行一次任务安装

- 一个全新席位加入一个任务。
- 一次占用者交接：继任者继承席位，然后领取项目。
- 一次发布或阶段边界：每个延续席位都在新的前沿上重新灌注上下文。
- 一次项目切换：一个席位从一个任务移往另一个任务。

永远在世界安装之后进行。任务安装预设读者已置身于系统之中。

## 五个层

每次安装都由这些层按此顺序组装而成。它们是骨架，不是剧本——深度档位（见下文）决定给定席位获得每层的多少内容。

1. **构件**（PIECES）——已撰写的历史与设计：解释项目如何走到今天的工件。按地址从任务树中组装而来，每件都携带其源路径与内容哈希。绝不转述改写。
2. **编排**（ARRANGEMENT）——各构件如何连接。这是唯一一层内容不存在于磁盘其他任何地方的东西：一份由曾掌握这项工作的人撰写的回顾（recap），说明是什么把构件连接起来、什么可信任、什么取代了什么。若尚无编排文档，撰写一篇便是准备安装工作的一部分——那是分派者（dispatcher）的知识，沉淀存档。
3. **位置**（POSITION）——该席位具体学到并掌握的东西：其积累的经验文件与最近一次回顾。位置对该传承谱系私有；它只被安装，从不发布。
4. **契约**（CONTRACT）——当前计划与未决决定。这是变动最快的一层，因此每件契约构件都必须自带 `updated-at`，任何在组装时未重新推导的事实都要带上显式的 `UNVERIFIED` 标记。一份过时的计划比一份缺失的计划更具误导性。
5. **自推导差异**（DERIVE-YOUR-OWN-DELTA）——走读的最后一件构件指定一份**推导清单**：接收方（installee）必须自行重新推导的易变事实，每条都以推导它的那条命令的形式给出（绝不作为记下来的数值）。接收方执行这份清单，并写出一份**带日期的差异记录**（delta）——即安装未曾言明、如今为真的事实——作为其第一件工件，安放在席位回顾之旁。正是这一层把一次简报变成一次仪表校验。

## 两种深度档位

- **规划类席位获得 FULL 深度**：横跨全部五层的完整有序阅读集，终点是当前工作指针（当前计划自身的下一项）。
- **执行类席位获得 HIGH-ALTITUDE 深度**：少数几次可寻址阅读——项目框架、统辖性的 scope 契约、来源索引、操作手册——外加第 5 层。切片级深度刻意更晚到达，随每条被路由的工作项而来，其自身规格以完整的设计契约开篇。

处境（fresh、handover、boundary、switch）决定各层的子集；席位类别决定深度。不要把所有东西发给所有人。两条不变式在每一深度上都成立：**编排层绝不被跳过**（正是它告诉读者该信任谁），以及**没有匹配工件的档位槽位绝不在安装时现写**——用一份派生得到的清单填上（把它加进推导清单），或者留空并明说。

## 投递规则

- **推送，且代智能体组装**。分派者组装，接收方接收。每条消息一件构件，分节奏进行，构件之间留出消化的余地——把同样的字节串联倾倒出去，无论内容如何都是失败的投递。
- **默认指针走读**：对已完成世界安装的席位，每条分节奏的消息点明要读的工件，并把这次阅读框定为该席位自身下一项任务的前置。席位自行执行阅读；阅读即是安装。
- **仅当席位无法阅读时才字节走读**（没有文件访问权、跨机投递）：此时走读携带字节，分件进行，绝不一次性成块。
- **在消费重要的场合，每件都索要一句回应**：一句话说明这件构件给读者改变了什么。无声的走读是未经核实的投递。
- **指针可以精确到章节**。当一个文件把安装内容与参考材料混在一起时，指针指明要读哪些章节、哪些章节属于参考；读者的回应则指明实际读了哪些章节。若两个消费者持续需要不同的子集，拆分文件更好。

## 任务选定的执行组件

一个任务可以携带 `mission.yaml`，一个切片可以携带 `slice.yaml`，作为工作编排的地址映射。存在时，把 `mission.yaml` 安装进编排（ARRANGEMENT）层，把当前生效的 `slice.yaml` 安装进契约（CONTRACT）层。先读任务文件；切片可以收窄或覆盖任务的默认值。

可复用组件目录位于仓库的 `docs/reference/product-journey-sdlc.md` 与已安装的 `$OPENRIG_HOME/reference/product-journey-sdlc.md`。带 `root: repository` 的目录从 `git rev-parse --show-toplevel` 解析；可寻址的 H2/H3 章节请使用 `loading-addressable-markdown` 技能。

在接收方认领工作之前，要求一句就绪声明，点名：**角色；用户成果；起始候选；边界**。被选中的组件 ID 与显式边负责编排工作；它们不扩大范围，不创造模式，也不强制门禁。如果不存在任何组合，`mission-slice-sop` 中的轻量 Part A 流程即已完备——缺席不是铸造 YAML 的理由。

## 组装，而非生成

安装**组装的是已撰写、带出处的工件，绝不在安装时生成总结性散文**。生成的摘要是第二个会漂移的来源，既不可信任也无法核验；撰写的构件自带来源。安装中唯一现场创作的地方是编排层——而那是可问责之人写下的沉淀知识，被保存、被复用，而非每次安装重新生成。

## 排除规则

任务树会不断累积**只作参考、绝不入装**的材料：事故残留、被取代的规划、会话记录存档、为存证而留下的死胡同。安装继承的是**清理后**的视图——当前的真相，加上编排层对来路的交代。被排除的材料仍然可寻址；编排可以指向它，但走读绝不携带它。准备安装时，对每个候选构件分类：安装内容，还是参考。拿不准，就是参考。

## 第 5 层验证循环

第 5 层是一个序列，不是建议。全部执行：

1. 分派者走读的最后一件构件指定推导清单——每条易变事实配对推导它的命令——**并点名差异记录的准确目标路径**（全新席位还没有可依傍的回顾；去处由分派者决定，接收方不得猜测）。
2. 接收方执行每一条命令，并在指定路径写入带日期的差异记录。
3. 分派者核验工件**确实存在**（而非声称存在）。
4. 由第二位读者——除接收方之外的任何人——检查差异记录的**事实**。当项目里只有分派者与接收方时，由分派者执行事实检查，且差异记录要写明这次检查是自查的——一次诚实的降级，明说出来，绝不沉默。
5. 事实性错误触发一轮重新推导：接收方重跑命令、改正、重新封存差异记录。这一轮修正本身就是价值，而非开销：它在一个动作里既核验了消费，又校准了仪表。

一条**没有推导命令**的易变事实——只有人类或外部方能裁定的那种——同样要上清单，标注 `UNVERIFIED` 并附上显式的求问指引；差异记录将它以未决状态继续携带，而不是悄悄采用某个数值。

没有落地、经检查的差异记录的安装不算完成。那只是一次广播。

## 忠实度法则

只存在于对话中的设计细节必须在**铸造时沉淀**。当真实的设计曾填满一整场讨论，而工作项的规格只留下一行意图，那就是 20:1 的压缩——从它出发去构建，正确只能靠巧合。因此本约定点名了沉淀设计的所在：工作项自己的**设计契约块**（design-contract block），或其旁的 DESIGN-INPUT 文件。第 1 层构件指向那份全忠实度记录，而绝不指向被压缩后的意图行。

## 边界

**任务安装止步于任务根**。它之上的一切——更广的系统是什么、团队的形态、文化——都属于先行的世界安装。向上追溯项目根之上是另一件工具、另一个问题。一次安装，一棵树。

## 用随附机制组装

这些层从既有的呈现面组装而来；不需要任何新机制：

- 构件与契约：一份 `--mission` 授权横跨任务及其全部切片——`rig context profile <pack-ref> --situation <fresh|handover|post-compaction> --mission <mission>` 会组装可寻址章节，逐件携带来源与内容哈希。`--situation` 标志必填，且它是与深度档位**彼此独立**的输入：situation 决定适用哪份组合菜单（全新启动、占用者交接、压缩后恢复）；FULL 与 HIGH-ALTITUDE 决定席位类别获得每层的多少内容。两者独立选择。
- 具名的安装档位把这一独立的深度/顺序选择显式化。`rig context profile world-public --situation fresh --runtime codex --profile codex-coverage
  --rig <rig> --seat <seat> --mission <mission> --slice <slice> --json` 是不涉及投递的检视：它会在任何内容抵达席位之前，报告选中的档位、按序排列的阶段、确切的构件、token 估算、内容哈希与来源溯源。`codex-coverage` 档位的顺序是 bootstrap → 具体的 project/mission/role/task → coverage map；`guided` 保留更完整的已撰写走读，单独可选。两者都从同一张源图里选取。
- 位置：`--rig`/`--seat` 授权用于供应该席位的经验文件与回顾。
- 运行时：`context profile` 与 `context work-install` 都接受 `--runtime claude-code`（别名 `claude`）或 `--runtime codex`。档位组合保留 `claude` 清单/输出键；技能投射保留 `claude-code`。档位默认值取自 `OPENRIG_RUNTIME`，否则为 Claude；work-install 需要该标志才能检视或应用技能。
- 投递：`rig walk <seat> --through-profile world-public --profile <profile>
  --situation <situation> ...` 应用已检视过的档位；`--through <files> --pace <interval>` 仍是最原始的字节走读路径。点名可寻址读取的分节奏发送则充当指针走读。
- 差异记录：席位回顾旁的一份带日期 markdown 文件；通过读取它来核验。

当这些动词不可用时（另一套工具链、一个纯文件系统），约定依然成立：复制带源路径的可寻址章节来组装，分节奏投递，指定推导清单，要求差异记录。

## 任何项目的快速上手

1. 给任务的工件分类：安装内容还是参考（排除规则）。
2. 撰写或更新编排文档——各构件如何连接、什么可信任。
3. 给每件契约构件标上 `updated-at`；把未经推导的事实标注 `UNVERIFIED`。
4. 选择档位：规划类选 full，执行类选 high-altitude。
5. 若任务/切片 YAML 选定了执行组件，就在相应的层纳入这些文件及其可寻址的目录章节。
6. 组装带来源的有序构件清单；分节奏投递，指针优先。
7. 以推导清单收尾；要求带日期的差异记录；核验存在性；由第二位读者核对事实；出错即重新推导。

任何类型的项目都适配这套流程：以一本书为例，构件是大纲的历史与文风决定，编排是各稿之间的关系，位置是这位编辑席位的经验，契约是带日期的当前章节计划，推导清单则是"数一遍章节数，读最新的编辑批注，报出今天的字数"——这些是新人智能体必须亲手触达、而非径直相信的事实。
