通过 Chrome DevTools Protocol 连接已有的浏览器：

```bash
# 先启动 Chrome：google-chrome --remote-debugging-port=9222

# 连接一次，之后的命令无需 --cdp
agent-browser connect 9222
agent-browser snapshot
agent-browser tab
agent-browser close

# 或在每条命令上传 --cdp
agent-browser --cdp 9222 snapshot
```

会话保持附加状态直到 `agent-browser close`。之后不带连接 flag 的命令仍作用于同一浏览器，就像再次传了 `--cdp` 一样。若该浏览器消失，命令会失败，而不会启动本地浏览器。

若调试端口尚未打开，`connect` 与 `--cdp` 会最多等待 2 秒再失败。

## 远程 WebSocket URL

通过 WebSocket URL 连接远程浏览器服务：

```bash
# 连接远程浏览器服务
agent-browser --cdp "wss://browser-service.com/cdp?token=..." snapshot

# 适用于任何兼容 CDP 的服务
agent-browser --cdp "ws://localhost:9222/devtools/browser/abc123" open example.com

# 带认证的 CDP WebSocket（如 Cloudflare Browser Rendering）
agent-browser --cdp "wss://api.cloudflare.com/.../devtools/browser" \
  --cdp-headers '{"Authorization":"Bearer YOUR_API_TOKEN"}' snapshot
```

`--cdp` flag 接受两种形式：

- 端口号（如 `9222`），通过 `http://localhost:{port}` 本地连接
- 完整 WebSocket URL（如 `wss://...` 或 `ws://...`），用于远程浏览器服务

当服务在 WebSocket 握手而非 URL 上做认证时，使用 `--cdp-headers`（或 `AGENT_BROWSER_CDP_HEADERS`）。它接受一个值为字符串的 JSON 对象，会在 HTTP 发现（`/json/version`、`/json/list`）与 WebSocket 握手时发送，URL 与端口号皆然。它与 `--headers` 相互独立，后者设置的是页面请求的 HTTP 头。

对 `https://` 的 CDP URL，发现过程保持输入的加密性：请求走 `https://`/`wss://`，凭据绝不会明文发送，也不会回退到不加密的协议。只在可信网络上对 `http://`/`ws://` 目标使用 `--cdp-headers`。

根 WebSocket 端点接受带或不带显式斜杠的查询串，因此 `wss://browser-service.com?token=...` 与 `wss://browser-service.com/?token=...` 都可用。

## 自动连接

使用 `--auto-connect` 自动发现并连接运行中的 Chrome，无需指定端口：

```bash
# 自动发现开启了远程调试的 Chrome
agent-browser --auto-connect open example.com
agent-browser --auto-connect snapshot

# 或通过环境变量
AGENT_BROWSER_AUTO_CONNECT=1 agent-browser snapshot
```

自动连接按以下方式发现 Chrome：

1. 从默认用户数据目录读取 Chrome 的 `DevToolsActivePort` 文件并连接其 WebSocket 端点；对旧版 Chrome 再用 HTTP 发现（`/json/version`、`/json/list`）
2. 回退到探测常见调试端口（9222、9229）

Chrome 144+ 在首次连接时会弹出远程调试权限提示。自动连接最多等待 20 秒以获批准。若届时提示仍未处理，命令会失败并提示你批准后重试，不会弹出第二个提示。

适用于：

- Chrome 144+ 通过 `chrome://inspect/#remote-debugging` 启用了远程调试（使用动态端口）
- 你想零配置地连接现有浏览器
- 你不想追踪 Chrome 用的是哪个端口

## 标签页固定

当多个会话通过 CDP 共享一个浏览器时，每个会话都记得自己绑定的标签页（按 CDP target id，跨守护进程重启持久化）。重启后的守护进程会重新附加到该会话自己的标签页，而不是接管当前活动的标签页——在共享浏览器中那通常是别的会话的。

传入 `--pin-tab`（或设置 `AGENT_BROWSER_PIN_TAB=1`）可以让绑定变为严格模式：

```bash
# 两个智能体共享一个 Chrome，各自固定到自己的标签页
agent-browser --session agent1 --cdp 9222 --pin-tab open https://site-a.com
agent-browser --session agent2 --cdp 9222 --pin-tab open https://site-b.com
```

启用 `--pin-tab` 后：

- 无绑定地附加时会打开新标签页，而不是接管已有标签页
- 若绑定的标签页被关闭，命令会以 `tab_gone` 错误失败，而不是悄悄操作别的标签页。JSON 响应携带 <code>"code": "tab_gone"</code>、<code>data.targetId</code> 与可选的 <code>data.lastUrl</code>
- 该状态下 `tab list`、`tab new` 与 `tab <ref>` 仍然可用，智能体可以通过绑定新标签页恢复
- 其他会话或用户打开的标签页绝不会抢走固定会话的活动标签页
- 固定标签页的会话运行期间，其他会话无法用 `tab <ref>` 抢占；切换会以 `tab_locked` 失败并指明属主

该 flag 对会话具有粘性：传一次，之后的命令都保持严格语义。守护进程重启保留固定；显式 close 会释放它，让其他会话可以接管该标签页，而下一次固定命令会再次固定。传 `--no-pin-tab` 可显式重新关闭。多会话工作流见[会话](/sessions)，按 CDP target id 引用标签页见[命令](/commands)。

结构化的 <code>lastUrl</code> 只对已脱敏的 HTTP(S) URL 与 <code>about:blank</code> 输出。HTTP(S) URL 会去掉凭据、查询串与片段，<code>data:</code> 等不透明 URL 则直接省略。批量 JSON 在 <code>result</code> 下暴露该恢复对象。

重新运行共享标签页的脚本（如 #1530 的复现用例）时，请为每个会话的第一条命令加上 `--pin-tab`。不加的话，`open` 会刻意保留旧行为、导航共享的活动标签页，原脚本仍会冲突。会话用 `--auto-connect` 而非 `--cdp` 附加时规则相同。

## 配色方案

通过 CDP 连接时，可用 `--color-scheme` 设置持久偏好：

```bash
agent-browser --cdp 9222 --color-scheme dark open https://example.com
agent-browser --cdp 9222 snapshot  # 保持深色模式
```

也可通过配置文件或环境变量全局设置：

```bash
AGENT_BROWSER_COLOR_SCHEME=dark agent-browser --cdp 9222 open https://example.com
```

## 使用场景

可用来控制：

- Electron 应用
- 开启远程调试的 Chrome/Chromium
- WebView2 应用
- 远程浏览器服务（通过 WebSocket URL）
- 任何暴露 CDP 端点的浏览器

## 云提供商

使用 `-p` flag 连接云浏览器提供商或已配置的 `browser.provider` 插件，而不是启动本地浏览器：

```bash
agent-browser -p browserbase open https://example.com
```

各内置提供商的安装与配置见[提供商](/providers/browser-use)章节：[Browser Use](/providers/browser-use)、[Browserbase](/providers/browserbase)、[Browserless](/providers/browserless)、[Kernel](/providers/kernel) 与 [AgentCore](/providers/agentcore)。
