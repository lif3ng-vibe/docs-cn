Openship 明明白白地告诉你每份数据存在哪，这正是自托管值得信赖的原因。自己运行 Openship 时，你的数据就放在**你自己的机器或服务器上**的数据库里——而且随时可以把全部数据打进一个文件带走。把它想成一只属于你的文件柜：柜子是你的，钥匙是你的，想搬走整个柜子也不必问任何人。

## 你的数据存在哪（自托管）

本地与服务器项目——连同它们的全部部署、域名、环境变量和日志——只存在于你实例的数据库中。这些项目的任何信息都不会发往 Openship Cloud。如果你从不连接云账号，你的实例就是完全独立的。

Openship 依据你的配置选择数据库：

| 模式 | 何时使用 | 数据存放位置 |
|---|---|---|
| **PGlite（内嵌）** | 未设置 `DATABASE_URL` 也未设置 `POSTGRES_*`——零配置默认项，桌面应用用的就是它 | 磁盘上的一个文件夹（一整套 PostgreSQL 集群，无需单独的服务器进程） |
| **PostgreSQL 服务器** | 你设置了 `DATABASE_URL` 或 `POSTGRES_*` / `PG*` 变量——Docker Compose 自托管的典型方式 | 你的 Postgres 服务器（Openship 用普通连接池连接） |

**PGlite** 是编译后能*在* Openship 进程内部运行的 PostgreSQL——同样的 SQL、同样的表，却不需要安装或看护任何数据库服务器。Openship 里的每个仓库层和服务都只面对同一个统一的数据库类型，因此它既不知道、也不关心底下跑的是两者中的哪一个。

<Callout title="内嵌数据库在磁盘上的位置">
默认情况下，PGlite 把数据存在 **`~/.openship/data`**（在你的项目文件夹之外，因此永远不会被提交进 git）。设置 **`PGLITE_DATA_DIR`** 可以放到其他任何位置。Docker Compose 自托管时，你通常会用 `DATABASE_URL`（或 `POSTGRES_HOST` / `POSTGRES_PASSWORD`）让 Openship 直连一个真正的 Postgres。完整选项参见[安装](/docs/getting-started/installation)。
</Callout>

## 云项目住在云端

云项目以 Openship Cloud 为权威。你的实例不留影子副本，读写都经由网关完成。这套分工如何运作、为何永远不会有需要对账的分歧副本，参见[以云为源](/docs/architecture/cloud-as-source)。

## 零锁定：全量导出与导入

自托管实例拥有自己的数据，因此 Openship 允许**所有者**把*整个*实例倾倒成一个 JSON 文件，再装载进另一套安装。换机器、大改动前备份、把一组项目交给队友，都靠它——没有专有格式，没有导出申请，也没有等待。

三个入口任选其一：

| 入口 | 操作方式 |
|---|---|
| **控制台** | **设置 → 实例**中的**导出**与**导入**卡片（仅限自托管、所有者） |
| **CLI** | `openship system data-transfer export` 与 `openship system data-transfer import` |
| **API** | `POST /api/system/data-transfer/export` 与 `POST /api/system/data-transfer/import` |

### 文件里有什么

导出内容涵盖实例里的每张表——用户、项目、部署、域名、服务器、设置等等。机密信息（环境变量值、访问令牌、SSH 凭据、备份目标密钥、Webhook 密钥）在数据库中静态存储时就是*加密*的。导出时它们**绝不会以原始密文形式留在文件里**：Openship 会把每个机密单独取出，将整组机密封装进一个单独的包，用**你自设的口令**（passphrase）上锁。口令会经过缓慢、抗内存的密钥派生（scrypt），包本身用 AES-256-GCM 封装，因此只有持有口令的人才能打开。导入时，目标安装会**用它自己的**密钥重新加密每个机密。

<Callout title="口令可选——但请先读这段" type="warn">
**跳过**口令，导出文件就**完全不携带机密**——导入后你得手动重新录入环境变量和凭据。**设置**了口令，就要保管好：口令是打开密封机密的唯一钥匙，口令输错（或遗失）无法找回。它会在*任何数据写入之前*校验，因此口令不对时导入会干净地中止。
</Callout>

### 导入模式

导入时，你可以选择它与现有内容如何合并：

- **替换**（wipe）——清空实例，整文件装载。这会替换当前用户和会话，因此导入后控制台会重新加载，用导入的数据为你登录。这是默认模式。
- **合并**——只插入尚不存在的行，并且**只**为实际新增的行重新还原机密，因此目标侧已有的行绝不会被覆盖。

### 把实例搬到新机器

<Steps>

<Step>

### 从旧安装导出

打开**设置 → 实例**，在**导出数据**卡片里设置口令（输入两遍确认），然后按**导出并下载**。浏览器会保存一个 `openship-export-…json` 文件。终端里则是：

```bash
openship system data-transfer export --passphrase 'your-secret' --out openship-export.json
```

</Step>

<Step>

### 在新安装上导入

在新机器上安装 Openship，以所有者身份登录，然后前往**设置 → 实例**，按**从文件导入……**。选择文件、输入同一口令、为干净的搬迁选择**全部替换**，然后确认。或者用 CLI：

```bash
openship system data-transfer import --file openship-export.json --passphrase 'your-secret' --mode wipe
```

</Step>

<Step>

### 完成

新实例现在拥有你的项目、设置，以及（如果你用了口令）你的机密——已用新安装的密钥重新加密。原先指向旧机器的一切仍指向旧机器，准备好了就重新部署。

</Step>

</Steps>

<Callout title="导入大小限制" type="info">
导入端点接受最大 **500 MB** 的文件。更大的导出意味着实例非常庞大——请改用下面的单项目搬迁来拆分，或导入到一个完整的 PostgreSQL 后端实例。
</Callout>

## 搬迁单个项目

不必搬动整个实例也能迁走一个项目：

- **上迁**（本地 → 云端）：项目数据复制到云端，然后删除本地行。
- **搬回**（云端 → 本地）：反过来。

一个项目永远只在一个地方，因此永远不会有需要对账的分歧副本。

## 桌面应用如何守护本地数据目录

桌面应用运行着与无头自托管完全相同的 Openship API 和内嵌数据库，只是打包成了一个可点击的应用。以下几点保护着磁盘上的数据安全：

- **单实例锁**。PGlite 是单进程的——如果两个进程同时打开同一个数据目录，数据库会损坏。打开之前，Openship 会原子性地占住目录旁边（绝不在里面）的一个 `<data-dir>.lock` 文件。第二个实例会稍等片刻，然后带着明确的报错退出，而不是抢着挤进去。锁在崩溃后能自愈（死进程的锁在下次启动时回收），并且拒绝打开被*另一台机器*锁住的目录，因此同步文件夹不可能悄悄把它弄坏。
- **仅限 localhost**。内置的 API 和控制台绑定到 `127.0.0.1`（环回地址）上由应用在启动时挑选的端口，而不是固定的公开端口。应用自身不会把数据目录里的任何东西暴露到网络。
- **私有的数据文件夹**。数据库位于应用自己的按用户数据目录（由操作系统为该应用指定），与任何项目检出相互独立。
- **机密静态加密**。机密列用一把从每安装密钥派生的密钥加密；该密钥由应用一次性生成，并以仅所有者可读的文件权限保存。

<Callout title="你的数据不会被锁死在桌面应用里" type="info">
桌面版数据库与其他自托管是同一格式，因此上面的**导出**流程可以把它搬到服务器、Docker 栈或另一台桌面，全程无需任何转换。
</Callout>
