Openship 可以在三个不同的地方运行你的应用。把做好的应用想象成一顿饭：你可以在**自家厨房**（本机）烹饪并上桌，可以把菜谱寄给**朋友家的厨房**（你自己的服务器），也可以交给一家**替你烹饪上桌的餐厅**（Openship Cloud）。菜是同一道——变的只是厨房。

厨房在部署时挑。Openship 称之为**部署目标**（deploy target），一共恰好三种：

| 目标 | 运行在哪 | Openship 如何触达 |
|---|---|---|
| **Local** | Openship 自身所在的那台机器 | 直连——不经过网络跳转 |
| **Server** | 你自己的机器（一台 VPS，或塞在柜子里的主机） | 通过 **SSH**（安全的远程连接） |
| **Cloud** | Openship Cloud，由它替你运行 | Openship 的托管 API |

<Callout title="随时可以反悔">
部署目标是每次部署时选的。今天先部署到笔记本上试一试，明天再把同一个项目重新部署到真正的服务器或云端——应用本身什么都不用改。
</Callout>

## 两种运行方式：沙箱或直跑

对两个自托管目标（local 与 server）来说，Openship 还会决定应用在这台机器上*以何种方式*运行。这就是**隔离模式**（isolation mode），共有两种：

- **沙箱**（Docker）——应用跑在一个**容器**里：一个封闭的盒子，有自己的文件和依赖，与机器上的其他一切隔离开。这是默认选项。
- **直跑**（bare）——应用作为普通进程直接在机器上运行，没有盒子围着。更轻量，但会共享机器的环境。

所有地方都默认沙箱，因为隔离带来的好处值这点开销，而且开销本身微乎其微。直跑真正派上用场的场合只有一种：机器特别小——内存大约 **2 GB 以下**——容器引擎会和应用抢内存。这时 Openship 会在你选择直跑时给出提示，而不是自作主张替你切换。

<Callout title="直跑的应用如何保持运行" type="info">
直跑（bare）的应用由机器自己的进程监督器守护——Linux 上是 **systemd**，macOS 上是 **nohup**——崩溃或机器重启后都会自动拉起。沙箱应用则由 Docker 守护。
</Callout>

## 先构建，再交接

无论目标是什么，每次部署都按同样的顺序跑**同样的两个阶段**。

<Steps>

<Step>

### 构建——把源码变成可运行的东西

构建流水线永远执行同样的步骤：**prepare → clone → install → build**。

- **Prepare** 负责准备环境（安装工具链、传输本地文件）——这一步单独计时，首次设置不会虚增你的构建耗时。
- **Clone** 拉取你的代码（部署本地文件夹时跳过——文件已经在那儿了）。
- **Install** 执行你的安装命令（如 `npm install`）。
- **Build** 执行你的构建命令（如 `npm run build`）——应用不需要构建时跳过。

</Step>

<Step>

### 部署——启动新版本并把流量切过去

构建成功后，Openship 启动新版本、等它就绪、把你的网址指向它，然后才停掉旧版本。对沙箱和云应用来说，这一切**零停机**完成：旧版本会一直服务到流量切换的那一刻，因此在那之前出任何差错，旧版本都毫发无损。参见下文[零停机与自动回退](#零停机与自动回退)。

</Step>

</Steps>

<Callout title="构建在哪里跑是另一个独立选择">
*构建发生在哪*与*应用运行在哪*是两回事。部署到服务器（或云）时，你可以在**本机**——运行 Openship 的那台机器——上构建，只把最终产物传到目标；也可以**在部署目标上**构建。Openship 会根据你的框架给出建议——对多数技术栈是**本机**——你可以每次部署时改，也可以在**设置**里保存默认值。当本机是性能更强的那台时，在本机构建更快，还能让目标 VPS 免去重活；当 Openship 所在机器资源有限时，在目标上构建更合适。云模式下，构建默认在云工作区进行；不过自托管机器也可以本地构建、只上传产物。
</Callout>

## 三个目标，逐一细看

<Tabs items={['Local', 'Your server', 'Openship Cloud']}>

<Tab value="Local">

**Local** 把你的应用跑在安装 Openship 的那台机器上——在桌面应用或单机上试东西再合适不过。

- **沙箱**直接与机器的 Docker socket 通信。
- **直跑**在机器上运行进程，用 systemd 或 nohup 守护。

网址与 HTTPS 由同一台机器上 Openship 内建的路由处理（参见[路由与证书](#路由与证书)）。

</Tab>

<Tab value="Your server">

**Server** 把你的应用跑在你自己拥有的机器上，通过 **SSH** 连接——就是你在终端里用的那种安全连接。服务器只需添加一次——在**服务器**页面，或在部署流程里直接**添加你自己的服务器**——Openship 会与它保持一条池化连接，后续部署复用同一条链路，不必每次重新拨入。

- **沙箱**通过 SSH 隧道驱动远程机器的 Docker 引擎。
- **直跑**通过同一条 SSH 连接在服务器上执行 shell 命令。

路由和证书工具都装在*你的*服务器上，流量绝不会绕道 Openship。

<Callout title="还没有服务器？" type="warn">
如果选择了 Server 目标但还没添加机器，部署界面会提供**添加你自己的服务器**，当场就能通过 SSH 接入一台——服务器也可以随时在**服务器**页面管理。参见[部署到你自己的服务器](/docs/guides/custom-servers)。
</Callout>

</Tab>

<Tab value="Openship Cloud">

**Cloud** 把整件事交给 Openship Cloud——构建、运行、路由、HTTPS 全由它包办。你的应用开箱即得一个免费的 `your-app.opsh.io` 地址，还可以再绑自定义域名。

自托管的 Openship 实例本身**并不**运行云流水线；云项目由 Openship Cloud 直接处理。唯一的例外是“在这边构建、在那边运行”的路径：你自己的机器可以构建应用，再把最终产物上传到云工作区运行。

</Tab>

</Tabs>

## 路由与证书

应用跑起来之后，总得有东西把访客引到它那儿，并提供 HTTPS。

- **自托管**（local 与 server）用 **OpenResty**（nginx Web 服务器的一个发行版）路由请求，用 **certbot** 从 **Let's Encrypt** 免费签发 HTTPS 证书并自动续期。
- **云**把路由、HTTPS 和静态文件托管都交给 Openship Cloud 的边缘——无需安装，也无须续期。

绑定自己的域名、验证 DNS、管理证书，参见 [Domains API](/docs/api/domains) 与[添加自定义域名](/docs/guides/custom-domains)。

## 零停机与自动回退

部署阶段会根据新版本能否与旧版本**并肩**运行而调整策略：

- **沙箱与云应用可以重叠**。每个版本有自己的容器或工作区，于是 Openship 先启动新版、检查无误、切换流量，*然后*才停掉旧版。切换之前任何环节失败，旧版本都毫发无损——继续服务，失败的部署就当没发生过。
- **直跑应用无法重叠**，因为新进程需要占用旧进程握着的同一个固定端口。于是 Openship 先停旧进程、再启新进程，若新进程失败，会把旧进程重新拉起来兜底。端口换手期间，这条路有一段不可避免的短暂空窗。

<Callout title="每台机器同一时间只跑一个部署" type="info">
同一台机器上的部署用锁串行化，两个项目同时部署也不会互相踩踏路由配置或共享状态。
</Callout>
