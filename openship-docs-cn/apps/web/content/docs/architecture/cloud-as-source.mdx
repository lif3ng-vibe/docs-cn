title: 以云为源
description: 云项目归 Openship Cloud 所有，你的自托管实例只是它前面的网关——以及项目如何迁上云端、又如何搬回家。
---

当一个项目跑在 **Openship Cloud**（我们的托管服务）上时，云端就是唯一真实的那份拷贝——即**权威**（canonical）所有者。它的记录、部署、域名、环境变量和日志全部存在云端，构建和生命周期也由云端驱动。你的自托管实例**不留任何本地副本**，而是扮演**网关**（gateway）——一个薄薄的透传层，把针对该项目的请求转发给云端，再把答案递回给你。

不妨把它想成你家街口的邮箱。信并不存在邮箱里，邮箱只是把信往来于真正的邮局之间。你的实例就是邮箱，Openship Cloud 就是邮局。

<Callout title="只需记住一条规则">
一个项目只住在**一个地方**——要么全在本地，要么全在云端，绝不各占一半。这就是本页背后的全部思想。
</Callout>

## 是网关，不是镜像

Openship 刻意不为同一个项目保存两份拷贝。镜像意味着两个权威源头，会不断漂移、需要反复对账——而且你机器上的一个 bug 就可能损坏云端数据。网关则避开了这一切：根本无物可同步，因为永远只有一份拷贝。

你的控制台和 CLI 仍然**只与本地的 API 通信**。当请求针对的是云项目时，网关悄悄把它转发给上游，再把响应原样流式传回——无论项目在本地还是云端，体验完全一致。

<Callout title="本地的权限检查依然先行" type="info">
转发**不会**绕过你的规则。本地权限面（permission plane）会检查调用者的角色与访问权，把每一通调用都把关在*代理发生之前*。过了这关，网关才会转发请求。
</Callout>

## 网关如何判断项目住在哪

对每个项目维度的请求，本地 API 按下面的顺序决定“由我自己的数据库伺候，还是转发给云端”：

1. **源提示**。控制台的项目列表会给每行打上 `local` 或 `cloud` 标记，并在后续请求里带上这个提示（`X-Project-Source` 请求头）——这是快车道，不查数据库。
2. **本地查找**。没有提示？只要项目 id 在你本地数据库里存在，它就是本地的。
3. **云连接**。本地没有这条记录，但你的组织关联了云账号？那它就是云项目，请求被转发。
4. **否则，未找到**——与陌生人的项目 id 得到同样的 `404`，什么都不泄露。

转发时若连不上云端，你会收到带 `CLOUD_UNREACHABLE` 代码的 `503`——而不是 `404`。这个区别很重要：项目*确实*存在，只是云端暂时失联。

## 全队共用一个云身份

云连接属于**组织所有者**，不属于每个人。网关转发调用时，以所有者的 Openship Cloud 会话完成鉴权（在服务端从加密存储中读取——Cookie 或令牌绝不会从浏览器发出）。

所以队友们**不需要**各有各的云账号。你的本地实例决定*谁有权*执行操作（按其角色判断），然后以所有者身份代理该操作。因为连接归组织所有，每个成员看到的“已连接”状态和云工作区列表都一模一样。

## 上迁：把项目送上云端

**上迁**（promote）把一个本地项目挪到 Openship Cloud 上，让云端成为它的权威之家。底层实现上，它会把这个项目的整个**子图**（subgraph）——项目行加上挂在它上面的一切（部署、域名、环境变量等）——复制到云端，然后删除本地行，不留任何影子副本。

它有两种触发方式：

- **生于云端**（自动）。当你把一个还在本地的项目部署到云端*并让云端来构建*时，Openship 会**先**上迁项目，再在上游执行部署——因此从第一次云部署起，它就是云权威的。如果上传失败，上迁会在**任何本地内容被拆除之前**停止，项目保持原样。（选择*在本机构建*是唯一的例外——参见[对云项目，你的机器还做什么](#对云项目你的机器还做什么)。）
- **显式转移**。你也可以按需通过 CLI 或 API 上迁（参见[自己动手](#自己动手)）。

<Callout title="自动部署跟着项目上云" type="info">
上迁会保留项目的 GitHub Webhook（网络回调）。上迁之后，向仓库 `git push` 会被转发到云端副本并在*那里*触发重新部署——自动部署照常工作，你这边什么都不用改。搬回则反转这一切：推送重新由本地处理。
</Callout>

<Callout title="本地加密的密钥不会原样带上" type="warn">
用**你实例自己的**密钥加密的值（机密环境变量）云端无法解密，因此会在上迁时被剥离。项目上云之后，请在云项目里重新录入这些密钥。
</Callout>

## 搬回：把项目拉回家

**搬回**（bring-home）是反向操作：从云端导出项目的子图，恢复进你的本地数据库，清除项目的云连接，然后把云端残留的行拆除，以免将来上迁时撞车。从这一刻起，项目重新成为本地权威，对其 GitHub 仓库的推送也改由本地处理，不再转发。

<Callout title="如今搬回搬动的是什么">
搬回搬动的是项目的**数据**。重新接好自定义域名的 DNS、把应用的容器重新拉起来，这些是运维的后续步骤，不属于数据传输本身。
</Callout>

## 对云项目，你的机器还做什么

对归云端所有的项目，你的本地实例**零**编排——只有一个可自行选择的例外：**本地构建、上传产物**。如果你选择“在本机构建”，你的机器会用它自己的凭据构建应用，并把结果上传到某个 Openship Cloud 工作区去运行。这种情况下项目保持本地权威，*不会*被上迁。其余一切——路由、TLS、运行容器——都归云端。运行时目标如何选定，参见[运行时模型](/docs/architecture/runtime-model)。

## Openship Cloud 自身又如何

这里有一种漂亮的对称：**在云服务上，每个项目本来就是“本地权威”**——上游再无可转发之处。两侧跑的是同一份代码；当网关*就是*云端时，它直接把“本地”解析为自身，因此任何请求都不会兜回自己身上打转。

## 自己动手

上迁和搬回是仅限自托管的操作，由 `project:admin` 权限把守。你的组织还必须先**连接到 Openship Cloud**——未连接的组织发起转移会被拒绝。

```bash
# 把本地项目上迁到 Openship Cloud
openship project transfer <projectId> to-cloud

# 把云项目搬回本实例
openship project transfer <projectId> to-self-hosted
```

对应的 API 路由是 `POST /api/projects/:id/transfer/to-cloud` 和 `POST /api/projects/:id/transfer/to-self-hosted`。上迁时，如果复制上传顺利完成、但本地清理没能完成，会返回部分成功（`207`），以便你重试清理——此时云端副本已经是权威版本。

<Callout title="转移可能返回的错误" type="warn">
- **`412`**——你的组织尚未连接 Openship Cloud。
- **`409`**——项目已经在目标一侧，*或者*云端残留副本/名称冲突挡住了上迁。Openship 绝不覆盖另一份拷贝，而是请你清理或改名后重试。
- **`502`**——云端受理了调用，但转移本身在上游失败了。
</Callout>
