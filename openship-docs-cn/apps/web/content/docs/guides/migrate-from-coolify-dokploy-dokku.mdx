已经在 **Coolify**、**Dokploy** 或 **Dokku** 上运行应用了？在 Openship 上你不必重建它们。Openship 会**扫描你服务器上已在运行的 Docker 容器并原样接管**——复用当前正在运行的镜像，不重新构建；同一台服务器上也不需要移动数据。这是一个有引导的一键导入，导入期间你的工作负载持续提供服务。

<Callout title="一个让一切与众不同的理念">
这里的其他平台都只能部署**新**工作负载。Openship 则可以指向一台服务器上**现有**的运行中容器，读取它们的域名和卷，并把它们接管过来——包括从 Coolify/Dokploy/Dokku 手中接管 `:80/:443` 反向代理，且可安全回滚。
</Callout>

## 导入是如何工作的

Openship 把这次迁移建模为一条简短且可逆的流水线：

1. **扫描** *（只读——不做任何更改）*——Openship 通过 SSH 枚举服务器上的**所有**容器、卷和网络（不只是它自己的），读取它们的 compose 配置，并按发布端口把你现有代理的 vhost 关联到每个容器，从而恢复其**当前域名 + SSL**。
2. **接管** *（仅记录）*——它会创建一个镜像现有运行容器的 `services` 项目。每个被接管的服务都携带容器**当前的镜像，且没有构建上下文**，因此 Openship 原样重跑当前运行的内容，**从不重新构建**。服务导入时**不对外暴露**，因此导入时路由不受影响。
3. **接管边缘** *（稍后、可选、可回滚）*——当你添加域名时，Openship 会记录旧代理的状态，将其停用，安装自己的 **OpenResty** 边缘，并重新注册你的 vhost 与证书。如果任何一步失败——或服务器中途重启——它会自动回滚。
4. **切换** *（可选、需确认）*——只有你明确指示时，它才会停止并移除*旧*容器。你的源卷绝不会被触碰。

## 开始之前

<Callout type="warn" title="扫描期间保持旧代理运行">
在扫描*之前*不要停掉 Coolify/Dokploy/Dokku 的代理——Openship 要从它那里读取你现用的域名和证书。稍后你会让它退役，而那一步 Openship 会替你完成（并且可以回滚）。
</Callout>

- 迁移**仅限自托管**，需要对源服务器（服务器到服务器迁移时还包括目标服务器）的 `server:write` 权限。
- **先通过 SSH 把源服务器接入 Openship**（Servers → Add server）。全程你的应用及其代理保持运行。
- 你随时可以安全地停掉旧平台的**控制面应用**——运行中的应用容器及其代理并不依赖它。但在接管步骤之前请让*代理*保持运行。

## 迁移一台服务器（分步操作）

<Steps>

<Step>
### 连接服务器并扫描

通过 SSH 添加服务器，然后开始导入。Openship 以只读方式扫描并列出发现的内容——每个容器及其恢复出的域名、端口和卷。（在大型或较慢的服务器上，请使用流式扫描，以免客户端超时。）

</Step>

<Step>
### 选择工作负载（三步向导）

向导按**选择 → 关联源 → 域名**进行。你的反向代理（Traefik / Nginx / Caddy 等）会被**自动排除**在工作负载集合之外，并原样保持运行——导入期间 Openship 绝不会接管或盲目停止它。

继续之前请先查看检测到的代理和发现通知。Traefik 路由既按发布端口也按容器的私有网络地址匹配，因此服务不需要主机端口也能保住自己的域名。导入的环境变量值保存在每个服务的 **Environment**（环境变量）标签页中。在“原样复用”模式下，编辑会保存下来，留待下次环境重应用或重新部署时生效；现有容器继续以当前值运行。
</Step>

<Step>
### 选择卷策略——这决定了停机时间

这是关键的选择：

- **原样复用** *（同一台服务器，默认）* → **attach-live（活跃挂载）**：运行中的容器被原样接管，其记录从活跃容器重建，复用当前镜像。不移动、不重建。**→ 零停机**。
- **复制**或**任何服务器到服务器迁移** → **部署路径**：为做一次一致的卷复制，原容器会被停止，然后验证一次全新部署至“就绪”。**→ 存在真实的停机窗口**（轮询最长约 20 分钟）。

<Callout type="info" title="相信策略本身，而不是横幅提示">
预览可能保守地对零停机的复用场景也提示“停机”。**原样复用**策略对工作负载而言是真正的零停机——容器从始至终不会停止。
</Callout>
</Step>

<Step>
### 接管域名与边缘

当迁移包含域名时，Openship 会在迁移过程中准备目标边缘。它会显示哪些现有站点属于所选项目和服务，并在替换代理前请求确认。选择 **Migrate sites & take over**（迁移站点并接管）会记录旧配置、在 `:80/:443` 上安装 OpenResty，并导入现有站点和证书，包括所选项目之外的站点。如果接管失败，Openship 会尝试恢复之前的代理并报告恢复结果。

所选域名会关联到迁移后的服务，并从活跃容器重新应用。现有证书会被复用，待验证的会立即重试。无法复现的路由会在发现通知中报告；接管之前请先审阅。如果路由或 TLS 仍需处理，迁移会保留一条警告，且不会自动移除旧的部署集容器。

<Callout type="info" title="唯一一次短暂中断">
采用原样复用时，你的容器持续运行。当 `:80/:443` 从旧代理切换到 OpenResty 时，请求可能短暂中断。复制和跨服务器迁移还有上述的停机时间。
</Callout>

</Step>

<Step>
### 验证，然后切换并移除旧平台

确认一切都通过 Openship 提供服务后，执行**切换**（需显式操作，并用令牌确认）：它只停止并移除*旧*部署集容器——**绝不触碰你的源卷**。满意之后，把 Coolify/Dokploy/Dokku 彻底移除；这台机器从此归 Openship 管。

<Callout title="切换之前先验证" type="warn">
切换会**停止并移除旧工作负载**，因此在 Openship 管理的应用完全健康之前不要执行：它能加载并服务流量、你的**数据完好无损**（登录、打开一条记录、检查卷/上传和数据库）、每个服务都处于 `RUNNING` 状态。切换会让你的**源卷保持不动**，所以旧的部署集会留作后备，直到你确信无疑。如果有任何不对劲——数据缺失、服务起不来、路由/TLS 不对——**不要切换**；让旧容器继续运行，并[在 GitHub 上提 issue](https://github.com/oblien/openship/issues)，我们会帮忙。
</Callout>
</Step>

</Steps>

## 服务器到服务器迁移

把整个套栈从一台主机搬到另一台是同样的流程，只是数据以流式传输：

- 具名卷和可移动的应用数据挂载直接以 **A → B** 流式传输（同一守护进程：`tar → tar` 复制；跨守护进程：gzip 流）。系统路径（`/proc`、`/sys`、`/var/lib/docker`、socket 等）绝不复制。
- Openship **拒绝覆盖目标上非空的同名卷**，因此你不会误伤数据。
- 服务器到服务器迁移总是走**部署路径**（存在停机窗口），而且**无法迁移本地构建的镜像**——它们在 B 上没有可拉取的镜像仓库，因此应在当前服务器上**原样接管**它们。

## 为什么架构与众不同

有两点值得了解，因为它们是 Openship 真正区别于其他平台的地方：

- **可编程的 OpenResty 边缘**。路由运行在 OpenResty 上，配备**数据库驱动、无需重载的逐路由规则引擎**——逐路由速率限制、IP/CIDR + 国家 + user-agent 封禁、方法/CIDR/国家白名单和防盗链保护——实时推送到共享字典，**无需重载 Nginx，也不需要 Redis**，另有内置的请求/带宽分析和实时日志流。Coolify 和 Dokploy 暴露 Traefik 中间件，Dokku 暴露 Nginx 模板，都能近似实现这些规则；Openship 的差异在于它是一套托管式、免重载、逐路由的界面——**而非**在协议层做得更多（参见下文的坦诚提醒）。
- **真正的桌面模式**。Openship 提供一个**原生桌面应用**，可在其上运行整个控制面——API、控制台、内嵌数据库、进程内任务——**绑定在你自己机器的回环地址上**，仅向同机（经内核验证）的调用方授予免登录访问，且**退出后不留任何后台进程**。这是隔离、单机驱动你服务器的方式；常开的 `openship up` CLI 服务是另一种独立模式。

## 坦诚的对比

这四个都是开源、基于 Docker 的自托管 PaaS 工具，大部分基线能力是共有的。我们不会假装不是这样——**为差异而迁移，而非为基线能力**。

**共同的基础能力（四家都有）**：git-push / Webhook 自动部署 · Dockerfile 构建 · Let's Encrypt TLS 自动签发与续期 · 一键数据库 · 定时 S3 备份 · 基于 SSH 的多服务器 · REST API + 作用域令牌 · CLI · 回滚 · 按事件的通知 · **以及官方 MCP 服务器**（Coolify 的只读，Dokploy 的覆盖完整 API，Openship 的可写）。“有 MCP 服务器”**不是**切换的理由。

**全貌**——差异项以**粗体**标出；`✓` 内置 · `~` 部分/手动/付费 · `✗` 不提供。凡对手领先之处（Coolify 的 280+ 应用目录、Dokploy 的 HTTP/3、Dokku 默认零停机、buildpack 广度），都如实标注。

站得住脚的迁移理由是那些粗体行：**接管正在运行的东西**、**带着数据在服务器之间搬迁套栈**、**离开而无锁定**（仅移除记录的退出只删掉 Openship 的记录，你的应用和数据继续在你的机器上运行，以后还能重新导入）或**把整个实例迁入 Openship Cloud 并能迁回**、**接管你现有的代理**、**可编程边缘**、**内置邮件服务器**，以及**自托管 + 云端混合**——云端目标真正运行你的工作负载（不像托管控制面那样仍依赖你自己的服务器）。其他三家都无法接管运行中的套栈、带着数据搬迁、或把它原样运行着交还给你——每次“迁移”都是手工 rsync 加重新部署，或一个社区脚本。

还有两点是结构性的，而非功能勾选项。**桌面模式没有常驻守护进程**——控制面只在你打开应用时才在笔记本上运行，后台不会驻留任何耗费资源的进程；其他三家都需要一台全天候运行的控制面服务器。而且在该模式下**你的源码绝不会上传到控制面**：桌面应用直接从磁盘读取你的文件夹，或目标服务器用你转发的凭据从 Git 克隆，因此代码从磁盘或 Git 直达服务器。Coolify 在 Coolify 服务器上克隆，Dokploy 接收 zip 上传，Dokku 接收 `git push`——无论哪种，你的代码都会先落在一台长期运行的控制面机器上。（对自托管的 Openship 实例而言，取舍与它们相同——这一优势是桌面模式特有的。）

## 坦诚的提醒

- **零停机的适用范围很窄，并非万能**。只有**同服务器“原样复用”导入**才是真正的零停机。同服务器“复制”和**每一次**服务器到服务器迁移都会为一致的副本停止原容器，并验证一次全新部署（最长约 20 分钟）——存在真实的停机窗口。OpenResty 安装期间，边缘接管会短暂中断 `:80/:443`。
- **边缘是可编程的访问规则 + 分析——不是 CDN，也不是 WAF**。没有 HTTP/3、没有 brotli、也没有响应缓存层；规则是内置规则集（封禁 / 允许-拒绝 / 防盗链 / 方法 / 速率限制），不是 ModSecurity/OWASP CRS。它也仅限自托管——托管云项目经由云端边缘路由，那里的规则覆盖仍不完整。
- **邮件服务器是真正的邮件服务器**。它是货真价实的 Postfix + Dovecot 套件——因此 DNS/DKIM/SPF 配置、送达率和日常邮件运维都要你自己打理。其他平台则干脆不提供邮件功能来回避这一点。
- **目录广度不是卖点**。Coolify 的 280+ 一键服务是这里最大的目录；Openship 领先的是*迁移与边缘*，而不是模板数量。
