import { Step, Steps } from 'fumadocs-ui/components/steps';

可以把已部署的应用想象成一间租来的房间。有两件事决定它的成本和访客的体验：**房间有多大**（它获得多少 CPU、内存和磁盘），以及**灯是常亮**还是没人在时熄灭（休眠模式）。本指南教你如何设置这两者。

这两项设置都不会改动你的代码——它们只改变应用背后机器的运行方式。随时可以调整。

<Callout title="前置要求">
- 一个已部署过的项目（还没有的话，参见[你的第一次部署](/docs/getting-started/first-deployment)）。
- 若要用 CLI 示例，需已安装并登录 `openship` 命令。
- CLI/API 部分要用的**项目 ID**。运行 `openship project list` 可找到它。
</Callout>

## 两项设置通俗版

- **资源**——机器的大小：你的应用获得多少 **vCPU**（算力）、多少 **RAM**（工作内存）和多少**磁盘**（存储）。越大越快、一次能处理越多，但成本也越高。
- **休眠模式**——应用空闲时会发生什么：
  - **Auto Sleep**（自动休眠，默认）——没人使用时应用停止，下一个请求到来时唤醒。运行成本更低，且 Openship 会瞬间唤醒它，访客无需等待。
  - **Always On**（常开）——应用永不停止。可用性最高，但它全天候运行（并计费）。

<Callout title="我该选哪种休眠模式？" type="info">
从 **Auto Sleep** 开始。它是推荐的默认值，适合绝大多数应用。只有确有理由时才切换到 **Always On**——例如有必须持续运行的后台任务，或应用无法忍受沉寂一段时间后第一个请求的短暂唤醒。
</Callout>

## 设置资源

部署到 **Openship Cloud** 时，资源规格位于**部署页面**上一个叫 **Power**（算力）的版块中；对任何已有项目则位于 **Machine Power**（机器算力）卡片（Configuration 标签页；多服务项目在 Services 标签页）。也可以通过 API 设置。

<Callout title="自托管：默认不设限" type="info">
自托管容器**不设上限**，除非你主动设定——机器本身就是天花板，因为那是你自己的硬件。只有当你刻意想给容器封顶时才选择一个档位（或 **No limits**，即默认）。非零值会对照**目标机器的真实容量**校验，因此一台 64 GB 的机器可以给容器 64 GB。

构建同样不设限。给构建封顶需要通过下文的 `build` 字段显式选择，而且通常只在小机器上有用——否则一次无上限的生产构建可能拖垮整台主机。

Openship Cloud 则相反：工作区按量计量、必须选定规格，因此那里没有“不设限”选项，未设置的项目会回退到 **Low** 档。
</Callout>

### 发起部署并选择 Openship Cloud

像平常一样开始部署。走到“想部署到哪里？”的选择时，挑选 **Openship Cloud**。旁边会出现 **Power**（算力）版块——选机器大小就是在这里。

### 选一个规格

从现成规格中选择一个。每个都显示其 vCPU、RAM 和磁盘：

| 规格 | vCPU | RAM | 磁盘 |
|---|---|---|---|
| **Micro** | 0.25 | 256 MB | 4 GB |
| **Low** | 0.5 | 512 MB | 8 GB |
| **Medium** | 1 | 1 GB | 16 GB |
| **High** | 2 | 2 GB | 32 GB |

如果都不合适，选 **Custom**（自定义）并输入自己的 vCPU、RAM（MB）和磁盘（GB）。

<Callout title="拿不定主意？" type="info">
较小的应用和业余项目用 **Micro** 或 **Low** 就很舒服。**Medium** 适合大多数生产应用。只有高流量或构建缓慢时才考虑 **High**。规格以后可以再改，所以从小档起步。
</Callout>

</Step>

<Step>

### 部署

完成部署。你的应用就按所选规格运行。

</Step>

<Tab value="Project settings">

任何已有项目都有一张 **Machine Power** 卡片。单应用在 **Configuration** 页下；多服务（compose）项目则在 **Services** 标签页，因为这类项目没有单应用的 Configuration。

卡片头部显示目标机器检测到的容量，并提供以下选项：

- **No limits**（不设限）——自托管默认。容器获得整台机器。
- **Micro / Low / Medium / High**——与 Openship Cloud 相同的预设。超出机器容量的预设会置灰显示，而不是被悄悄忽略。
- **Custom**（自定义）——输入自己的 vCPU 和 MB。任一字段填 `0` 表示该维度不设限，因此可以只封顶内存而让 CPU 自由。

限制在容器**重建**时生效，因此变更后要重新部署才会起效。卡片上会就地提示这一点。每次部署还会记录它应用的限制（`Resource limits: 2 vCPU · 4 GB`，或 `no limits (machine capacity)`），因此封顶绝不会隐形。

compose 项目中的单个服务可以覆盖项目级值——参见[逐服务限制](#逐服务限制compose)。

</Tab>

<Tab value="API">

用 `PATCH` 请求项目的 resources 端点即可更新已有项目的资源。所有路径都位于你实例的 `/api` 之下（例如 `https://your-host/api/...`）。认证使用 `Authorization` 头中的个人访问令牌——可在 **Settings → Tokens** 创建，或用 `openship token create`。完整的令牌模型参见[认证](/docs/security/auth)。

你可以设置 **production** 规格（在线应用运行所用的），以及单独的 **build** 规格（编译应用的临时机器）。规格以 `cpuCores`、`memoryMb` 和 `diskMb` 给出。

```bash
curl -X PATCH https://your-host/api/projects/PROJECT_ID/resources \
  -H "Authorization: Bearer $OPENSHIP_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{
    "production": { "cpuCores": 1, "memoryMb": 1024, "diskMb": 16384 },
    "build":      { "cpuCores": 2, "memoryMb": 2048, "diskMb": 16384 }
  }'
```

也可以发送 `{"tier": "medium"}` 代替具体数字，或（自托管时）发送 `{"tier": "unlimited"}` 来移除上限。

`0` 表示**不设限**。非零 `cpuCores` 至少为 0.25，`memoryMb` 至少为 128；上限是目标机器自身的容量，而不是固定数字——因此大型自托管机器可以完全用满。`diskMb` 范围为 64–204800，且仅由云端工作区强制执行。每个字段都是可选的——只发送你想改的。

`GET /api/projects/PROJECT_ID/resources` 读取当前值，同时报告检测到的机器 `capacity`（天花板）和 `requiresLimit`（云端为 true，那里不允许不设规格）。

</Tab>

</Tabs>

## 逐服务限制（compose）

在多服务项目中，项目级值作用于**每个**服务容器——这是按容器分别施加的上限，而不是在它们之间分配的预算。

单个服务可以覆盖它。Openship 会读取 compose 文件自带的限制（两种写法都认），并**逐字段**地覆盖项目值——因此只声明了内存的服务会保留项目的 CPU 设置：

```yaml
services:
  api:
    image: my/api
    mem_limit: 4g          # short form
    cpus: 2
  worker:
    image: my/worker
    deploy:                # swarm form — also honored
      resources:
        limits:
          memory: 8G
          cpus: "1.5"
```

同样的覆盖也可以在 `openship.json` 中以声明式写入，位于 [`services[].resources`](/docs/reference/openship-json#servicescompose) 下。

<Callout title="被接管的容器保留其限制" type="info">
导入现有 Docker 容器时会读取它实际运行时带的上限——包括你用 `docker update --memory` 手工施加的——因此接管不会悄悄重置它们。
</Callout>

## 设置休眠模式

休眠模式有两个取值：`auto_sleep`（默认）和 `always_on`。可从 CLI 或 API 设置。

<Tabs items={['CLI', 'API']}>

<Tab value="CLI">

```bash
# 让应用在空闲时休眠（默认，最省钱）
openship project sleep-mode PROJECT_ID auto_sleep

# 让它全天候运行
openship project sleep-mode PROJECT_ID always_on
```

不知道项目 ID？`openship project list` 会显示每个项目及其 ID。

</Tab>

<Tab value="API">

```bash
curl -X POST https://your-host/api/projects/PROJECT_ID/sleep-mode \
  -H "Authorization: Bearer $OPENSHIP_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{ "sleep_mode": "always_on" }'
```

`sleep_mode` 必须是 `auto_sleep` 或 `always_on`。（也可以在设置资源时一并发送 `sleepMode` 字段到 `PATCH /api/projects/PROJECT_ID/resources` 来修改。）

</Tab>

</Tabs>

<Callout title="休眠模式针对的是运行中的服务器" type="info">
休眠模式对拥有运行进程的应用（服务器或 API）才有意义。纯静态站点没有可休眠的东西——它只是被服务的文件——因此该设置在那里没有可见效果。
</Callout>

## 故障排查

<Callout title="资源取值被拒绝" type="error">
超出目标机器的上限会被拒绝，并给出真实数字，例如 `Memory limit 8192 MB exceeds the machine's 2048 MB`。调低数值，或用 `0` / `unlimited` 档移除上限。低于可行下限的非零值也会被拒绝（`at least 0.25 cores`、`at least 128 MB`）。如果 Openship 无法连上机器读取其容量，则完全不设天花板——你发送的值会被原样接受。
</Callout>

<Callout title="休眠模式命令被拒绝" type="warn">
模式必须严格是 `auto_sleep` 或 `always_on`——其他一律不行。检查拼写（两者都用下划线），并确认项目 ID 无误。`openship project list` 可以同时确认这两点。
</Callout>

<Callout title="我改成了 Always On，成本涨了" type="info">
这是预期行为——**Always On** 让机器 24/7 运行。如果不需要持续可用，用 `openship project sleep-mode PROJECT_ID auto_sleep` 切换回去，应用空闲时又会休眠。
</Callout>
