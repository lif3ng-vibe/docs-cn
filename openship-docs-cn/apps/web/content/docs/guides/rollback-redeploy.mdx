每个项目都保存自己的部署历史——就像文档的版本历史。如果新部署出了问题，你不必惊慌也不必翻代码：把项目翻转回一个正常的版本即可。而当你只想把同样的东西再跑一次——修完补丁之后，或想捡取最新提交——那就是重新部署。本指南两者都讲，还会介绍如何“固定（pin）”一个好版本，让它永远在那里供你回退。

<Callout title="前置要求">
- 一个在 Openship 中至少部署过一次的项目。
- 没有其他要求——回滚和重新部署都作用于你已有的部署。
</Callout>

## 找到部署历史

打开你的项目并点击 **Deployments**（部署）标签页。你会看到两样东西：

- 顶部是 **Deploy Latest Changes** 卡片，带一个 **Redeploy Project**（重新部署项目）按钮——用于再次发布。
- 其下是**历史**：该项目的每一次部署，最新在前，各占一行。

使用列表下方的翻页控件浏览更早的部署。搜索和状态筛选作用于整个历史，包括其他页上的部署。

每行显示版本（如 `v3`）、状态、提交信息，以及标明该版本所处状态的小标签：

- **Active**（活跃）——当前在线并为你的站点提供服务的版本。
- **Snapshotted**（已留快照）——Openship 仍保存着该版本完成的构建，回滚到它可完全跳过构建。
- **Pinned**（已固定）——该版本被永久保底，永远不会被清理（下文详述）。

## 回滚到正常的版本

<Steps>

<Step>

### 打开你想回去的版本

在历史中找到最后一个正常的行。如果它带 **Snapshotted** 标签，说明 Openship 仍保存着其构建，回滚将几乎瞬间完成；如果没有，仍然可以回滚——Openship 会替你重新构建该版本的提交。无论哪种情况，菜单项都是同一个。

点击该行上的 **⋮**（三个点）菜单。

</Step>

<Step>

### 选择“Rollback to this version”

按 **Rollback to this version**（回滚到此版本）。Openship 会告诉你它将走两条路线中的哪一条——

> 即时恢复——复用该版本保留的镜像，无需重建。

——如果该构建已被清理，则是：

> 重新构建——该版本的镜像已不在主机上，因此会重新构建其提交。

并提醒你无论哪种方式回滚的效果：

> 此操作只恢复应用代码。数据库和卷数据保持不变。

确认后，Openship 会把该版本作为新条目带回你的历史。回滚不会抹掉任何东西：你离开的那个版本仍在列表里，这样你也能用同样的方式再次切换回去。

</Step>

</Steps>

<Callout title="为什么回滚很快——而且对你的数据是安全的" type="info">
当该版本的构建仍在服务器上时，回滚不会重建任何东西——Openship 直接再次发布保存的构建。由此带来三件事：

- **快，且不会长时间中断**。无需等待全新构建；站点几秒内恢复，而不是构建所需的数分钟。
- **它恢复的也是那个版本的设置**，而不是今天的。该版本运行时的环境变量、端口、卷和资源限制会随之一并回来。
- **只有代码会变**。你的数据库和所有已保存的文件（卷）原封不动。回滚回退的是应用，不是你的数据。

如果构建已被清理，Openship 会改为重新构建该版本的提交。较慢——要跑一次真实的构建——但结果相同，因此回滚永远不会是死路。
</Callout>

<Callout title="回滚选项是灰色的" type="warn">
只有两种情况会禁用它：该版本已经是 **Active**（你正在用它），或者它从未健康地完成过。构建被清理不再禁用回滚——Openship 会改为重建提交。

如果某个版本既没有保存的构建、也没有可用于重建的提交（比如一次性手动部署），菜单会如实说明。想让某个版本永远可以即时恢复，就**固定**它——见下文。
</Callout>

<Callout title="多服务与静态项目" type="info">
- **多个服务**？只有缺少构建的服务会被重建。部署从未触及的服务继续用它已有的镜像运行——因此回滚应用代码不会重启你的数据库。
- **静态站点**？恢复的是该版本保存的文件；不涉及镜像。
</Callout>

## 重新部署（再跑一次）

重新部署会再次构建并发布你的项目。推送修复之后，或想让在线站点捡取最新提交时，就用它。

在 **Deployments** 标签页上按 **Redeploy Project**。Openship 拉取部署分支的最新提交，复用项目当前的设置和环境变量，并创建一个新版本。没有设置页面——直接开跑，并把你带到构建页面观看。

按钮旁的小箭头（⌄）展开几个额外选项：

- **Refresh env**（刷新环境变量）——重新部署，让应用捡取你刚做的环境变量改动。
- **Rebuild all**（全部重建）——重建每个服务，而不只是文件有改动的那些。该选项仅对多服务项目出现（单应用项目本来总是重建整个应用）。

<Callout title="重建某个特定的旧提交" type="info">
想回到过去的某次部署，用其所在行的 **Rollback to this version**——能复用保存的构建就复用，不能就重建提交，你无需关心是哪种。

想*强制*从源码重建某个特定提交（即使其构建仍被保存），用终端：`openship deployment redeploy <id> --use-existing-commit`（见下文）。
</Callout>

## 多少个版本保持可即时恢复

打开 **Project → Advanced → Rollback history**（项目 → 高级 → 回滚历史）设置保留构建产物的历史部署数量上限。默认为 **5**，继承自实例默认值，除非你设置了项目级覆盖。磁盘用量信息仅供参考；它们不会改变这个上限。部署向导中也有同样的设置。

除这个窗口外，活跃部署和已固定的部署始终保留。多服务部署只算一次，即使它需要多个镜像。把上限设为 **0** 则只保留活跃和固定的发布。

清理在部署完成时、你保存上限时、以及取消固定部署时运行。定时任务 **Deployment artifact cleanup**（部署产物清理）会重试失败的清理并核对现有历史；你也可以在 Jobs 里手动运行。清理会等待所有正在运行的部署 worker 结束。

更早的行仍留在历史中，但其构建产物被回收后会失去 **Snapshotted** 标签。仍被活跃、固定或窗口内部署需要的镜像或文件树会留在主机上，直到最后一个保留引用过期。运营方管理的镜像和第三方镜像仓库的镜像不会被移除。

回滚会检查实际可用的东西。已过期的源码构建可以从其记录的提交重建；镜像发布可以从其记录的引用重新拉取。没有可重启 supervisor 单元的裸主机从源码重建。既没有可用产物、也没有可复现源的发布无法恢复。

## 固定版本让它永远在场

如果有一个你总想瞬间切回去的已知良好版本，就**固定**（pin）它——固定版本豁免于上述清理，也不占用保留窗口。

在部署行的 **⋮** 菜单中选择 **Pin**（固定）。该版本即豁免于清理，并在保持固定期间始终可以即时回滚恢复。以后想解除，再次打开菜单选择 **Unpin**（取消固定）。

<Callout title="值得知道" type="info">
每个项目最多可固定 **10** 个部署。在尝试有风险的东西之前，先固定上一个可靠的发布——这样回滚永远只差一次点击，且无需重建。
</Callout>

## CLI

以上所有操作都可以从 CLI 完成。先列出部署拿到它们的 ID：

```bash
# 列出该项目的部署（最新在前）。"active" 列标出当前在线的那一个。
# 在已关联的项目文件夹内运行，或用 --project <project-id> 指定其他项目。
openship deployment list

# 查看某个部署的详情（状态、提交、url、是否已固定）
openship deployment get <deployment-id>
```

然后按 ID 对其操作：

```bash
# 回滚到之前的某次部署（传入你想回去的那个部署的 ID）
openship deployment rollback <deployment-id>

# 基于一次已有部署重新部署——捡取其分支上的最新提交
openship deployment redeploy <deployment-id>

# ……或改为重建该部署的确切提交，而不是最新提交
openship deployment redeploy <deployment-id> --use-existing-commit

# 固定一次部署使其永不被清理（加 --off 取消固定）
openship deployment pin <deployment-id>
openship deployment pin <deployment-id> --off
```

<Callout title="技巧" type="info">
只想发布整个项目的最新提交（相当于终端版的 **Redeploy Project**），在项目文件夹运行 `openship deploy` 即可。想重跑历史中*特定*的一次部署时，才用 `openship deployment redeploy`。
</Callout>

## 故障排查

<Callout title="“This deployment is already active”" type="error">
你正试图回滚到已经在线的版本。从历史中选*另一*行——当前正在服务的那个标着 **Active**，不能回滚到它自己。
</Callout>

<Callout title="“Only successful deployments can be rolled back to”" type="warn">
你只能回到健康完成的版本。失败或被取消的部署不是有效的恢复目标——选择最后一行状态为 ready/deployed 的部署。
</Callout>

<Callout title="回滚后站点看起来还是不对" type="warn">
记住回滚只改**代码**——它从不碰你的数据库或已保存的文件。如果问题出在一次糟糕的数据变更或迁移上，回滚代码不会消除它。你需要从备份恢复数据或直接修复。
</Callout>
