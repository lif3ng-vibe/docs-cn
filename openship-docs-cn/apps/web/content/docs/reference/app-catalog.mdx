**应用**（App）是一个 JSON 文件，把一次部署包装成一键式、聚焦的体验。不用再建项目、为每个容器加服务、手写把它们连起来的镜像和环境变量、跨两个服务生成并配对数据库密码、然后钻进原始的环境变量标签页里改一个设置——你只需点开应用、填一张短表单、部署。

所以应用**不是新的运行时**。它是普通[多服务部署](/docs/guides/compose-multi-service)之上的一层元数据：一个无仓库的 `services` 项目，标记为 `isApp`。底下是同一台引擎，用户的路却短得多。本页记录你能编写的每个字段。要真正提交一个应用，参见[添加应用](/docs/guides/add-an-app)。

加上 `$schema` 一行，编辑器就能自动补全并内联校验：

```json
{
  "$schema": "https://openship.io/app.schema.json",
  "id": "it-tools",
  "name": "IT-Tools",
  "description": "A handy collection of developer and sysadmin utilities.",
  "kind": "template",
  "logo": "it-tools",
  "category": "other"
}
```

它是 **JSON，不是 JSONC**——不能有注释，不能有尾逗号。

<Callout title="未知键会被忽略，而不是拒绝">
校验器会剥掉它不认识的键，而不是报错。这是刻意的：正是因此，新的应用定义才能装在旧版 Openship 上，也正是因此，目录的增长永远是增量的。代价是**字段名拼错了会无声失败**——发布的 schema 和服务端都会把它丢弃而不报告。所以留着 `$schema` 那行，让编辑器帮你补全字段名，别凭记忆敲。
</Callout>

## 两种类型

| `kind` | 作用 |
|---|---|
| **`template`** | 实例化条目中定义的 `services`（一个后端加它的数据库、一个 CMS 加它的数据库……），经 compose/services 路径部署。这是常见情形。 |
| **`flow`** | 开通流程已有专属向导（例如邮件栈）。条目只是通过 `flowHref` 指向那个向导，**不会**实例化服务。 |

### 服务资源默认值

当栈里各组件需要不同规格时，声明 `resources`。在云上，安装器把每份规格保存为该服务正常的资源设置。自托管服务保持不设上限，除非运维另行配置。重新打开或重试失败的安装时，缺失的规格会在一个事务里补齐，同时保留显式设置的服务与项目资源、文件、环境变量和机密。目录更新不会改变已部署应用的规格，也不会改动已固化的部署快照。

在云上，启用的服务共享一个工作区。其 CPU 是各服务限额之和向上取整，内存包含给 Docker 和操作系统预留的 512 MB，磁盘取各服务磁盘请求的最大值，下限 8 GB。源码构建会额外预留资源。Oblien 执行命名空间的每工作区与总量限额；模板无法抬高限额，也不能赠送点数。

Supabase 的规格申请 4 vCPU、8 GB 内存、40 GB 磁盘的工作区，依据其[公开的系统要求](https://supabase.com/docs/guides/self-hosting/docker#system-requirements)。按当前正式目录，它符合 Team 套餐的每工作区限额。已有的分配、更严格的已保存报价或显式的服务覆盖，仍可能导致不同的分配。依赖目录更新之前，请先部署支持资源规格的 API 版本；旧安装器会忽略这个可选字段。

## 构建镜像

多数服务**拉取**预构建的 `image`。有些不行：上游提供的基础镜像还需要打进去额外的包和一个开通用的入口点——Neon 的计算节点是最典型的例子。这类服务改设 `build` 而不是 `image`。它是一个内联的 Docker 构建上下文，Openship 在部署时将其物化，并在部署主机上走常规 compose 构建流水线完成构建。用 build 就无需再覆盖入口点：Dockerfile 自己设置 `ENTRYPOINT`。

每个服务**恰好设置** `image` 或 `build` 之一。两者皆无（没东西可跑）与两者都有（含糊不清）都会被拒绝——`service "<name>" must set exactly one of image|build`。

### COPY 路径要加上服务名前缀

这是作者最先搞错的规则。每个可构建服务都会物化到一个**以服务名命名**的子目录下，同处一个共享构建上下文中，`docker build` 以共享根目录作为上下文运行。因此 COPY/ADD 的源路径相对于根目录，而不是相对于服务自己的子目录：

```dockerfile
# service "compute", with files: [{ "path": "compute.sh", ... }]
COPY compute/compute.sh /shell/compute.sh   # ✅ prefixed with the service name
COPY compute.sh /shell/compute.sh           # ❌ COPY source not found → build fails
```

`files[].path` 相对于服务自己的子目录；COPY 时写作 `<service-name>/<path>`。

### 取值与构建参数

`{{config:KEY}}` 占位符会在安装时于 `dockerfile` 和每个 `files[].content` 中解析，与 `environment` 值中的解析完全一致——因此生成的机密或安装步骤的答案都能流进构建。

**没有 `args` 映射**。Dockerfile 声明的构建 `ARG` 由项目的构建环境变量供给：运行时把每个环境变量作为 `--build-arg` 传入。把值声明成普通的 `environment` 条目（或 `configField`），再在 Dockerfile 里用 `ARG` 引用即可。

<Callout title="构建发生在部署主机上">
大的基础镜像在哪里部署就在哪里构建。小主机上，重型构建——Neon 的计算节点要拉取数百 MB 的基础镜像——可能很慢或受内存所限。这个成本是应用固有的，与 Openship 无关。
</Callout>

## 两套字段体系

最常见的编写错误就是把两者搞混。声明环境变量的地方有**两处**，按*角色*划分：

| | `configFields` | `settings` 且 `installStep: true` |
|---|---|---|
| 用途 | **机器**生成或派生的环境变量 | 向导渲染的**人工**输入 |
| 是否渲染为表单输入？ | **否**——服务端解析 | **是**——文本、下拉、数字…… |
| 典型用途 | `generate: "secret"` / `"jwt"`、`generateGroup` | 一个名称、一个开关、一个选中的选项 |

要让用户**亲手填写**的，就是 `installStep` 设置——不是 `configField`。`configFields` 只用于运维永远不用敲的值。

### 表单布局

分组与字段宽度由目录控制。控件、间距、颜色和响应式行为由控制台提供，用的是与已装应用设置相同的表单渲染器。字段仍在 `settings` 里只定义一次；只有 `installStep: true` 的字段出现在安装时。

对 Convex 这类紧凑安装，在顶层加上：

```json
{
  "installLayout": {
    "settings": "split"
  }
}
```

`split` 把可编辑的项目名和安装字段放进两张相邻卡片，可用宽度过小时纵向堆叠。字段标签足以标识每个输入，无需额外的卡片标题。适合 Convex 的 Name 与 Instance name 这类小表单。

`single` 把项目名和安装字段合进一张卡片。`grouped` 保留独立的项目名卡片，并把每个可见的设置组连同其标签与描述一起渲染。空组会被略去。不设 `installLayout` 时，维持原有的独立项目名卡片和单张纵向设置卡片。重新打开草稿时，项目名保持隐藏，其余设置占满整宽。

`columns` 默认 `1`。适合并排的字段设为 `2`；可用宽度过小时表单会把它们堆叠，包括控制台导航占去更多空间的时候。分组模式下，组自身的 `columns` 覆盖安装默认值。该组设置在安装之后同样生效。给长文本域这类字段设 `fullWidth: true` 可横跨两列。字段顺序遵循目录；条件显示与高级折叠仍然适用。

这些可选提示会随目录 API 返回，供渲染方使用。它们不改变环境变量值、必填校验或路由，旧客户端可以直接忽略。请在目录 JSON 里使用这些受支持的提示，而不要用 CSS 类或可执行的布局表达式。

### 输出来源

输出的 `source`（以及每个变体的 `source`）必须匹配下面三种形式之一：

| 形式 | 解析为 |
|---|---|
| `env:<service>:<KEY>` | 该服务上对应的环境变量值 |
| `publicUrl:<service>` 或 `publicUrl:<service>:<port>` | 该服务的公开 URL，可指定具体路由 |
| `template:…` | 组合字符串，内嵌 `{{env:svc:KEY}}` 占位符 |

其他任何写法都过不了校验，且 `<service>` 部分必须是已声明的服务。

## endpoints

安装向导要问你的事——每个端口怎么访问。完全省略 `endpoints` 时，Openship 会为每个暴露服务按其声明的每条路由派生一个公开 `http` 端点。

默认值在每个部署目标上都顺着应用的预期用途：

- 仪表板、API 这类公开 HTTP 端点，默认以**域名**路由起步。
- 数据库这类裸 TCP 端点，默认**仅内网**，除非其 `scope` 为 `public`。
- 显式 `defaultMode` 在 `allowedModes` 范围内覆盖这些默认值。用于“仅端口 API”这类取舍。本地或内网 HTTP 端点默认仅端口访问。

云连接只选择域名提供方：已连接时是托管的免费域名，未连接时是自定义域名。它不会把公开界面切成仅端口路由。自定义域名仍需主机名和 DNS 配置。用户可以选择其他允许的模式；草稿里保存的选择优先于全新安装的默认值。

## 主机要求

`minResources` 描述应用建议的主机容量。上游文档给出有分量的要求时再声明，比如多服务分析栈需要 8 GB。它不设置容器限额。

```json
{
  "minResources": { "memoryMb": 8192, "cpuCores": 4 }
}
```

在自托管目标上，安装器和部署预检会把这些建议与目标机 Docker 守护进程的读数（`NCPU`、`MemTotal`）做比较。不足会显示警告，但绝不阻止首次安装或重新部署。读不到容量就视为未知，不推断为不足。10% 的容差考虑的是整机出售时内存取整、操作系统又占去一部分的情况。

在云上，安装器会对照组织套餐核查实际的工作区分配，包括服务覆盖和临时构建资源。装不下时会提供升级。高级安装仍可用来调整配置。部署在排入队列前会再次核查当前套餐，提供方在分配工作区时也会实时执行命名空间容量限制。

[`GET /apps/catalog/{id}/host-fit`](/docs/api/apps) 开放这份预览。传入 `projectId` 可把已有草稿保存的资源设置纳入计算。预览不会修改项目、分配资源，也不会授予部署额度。

## management

覆盖已装应用的管理方式。

| 取值 | 效果 |
|---|---|
| `{ "kind": "schema" }` | 用 `settings` 渲染精选设置表单。 |
| `{ "kind": "custom", "href": "/emails" }` | 改为把用户送往一个专属界面。 |

省略时 Openship 自行推断：有 `settings` 就 `schema`，否则用原始项目标签页。

## 占位符

安装时解析。可用于 `environment` 值、`files[].content` 和 `connection` 输出：

| 占位符 | 解析为 |
|---|---|
| `{{publicUrl:<service>}}` | 该服务的公开 URL。加 `:<port>` 指定具体路由。 |
| `{{config:<KEY>}}` | 按键取的生成配置值——例如 `generate: "secret"`。 |

## 本地化字符串

若干纯展示字段既接受普通字符串，也接受内联的多语言映射：

```json
{ "title": { "en": "Creating the admin key", "ar": "إنشاء مفتاح المدير" } }
```

适用于 `prepare[].title`、`prepare[].description`、`requires[].label`、`connection.firstLogin.username` / `password` / `note`、`connection.guide.intro` / `useHint`、`connection.outputs[].sourceLabel` 和 `variants[].label`。

## 校验

除字段类型之外，还有这些**引用**检查在入口处运行——精选应用与自定义应用一视同仁——悬空引用会立刻失败，而不是拖到部署时：

- 每处 `service` 引用都必须解析到已声明的服务——涉及 `configFields`、`prepare`、`endpoints`、`files`、`settings[].fields` 和 `connection.outputs[].service`。
- 每处 `connection.outputs[].source` 和 `variants[].source` 都要匹配 `env:<service>:<KEY>`、`publicUrl:<service>[:<port>]` 或 `template:…`。
- 每条 `provides[].outputRefs` 都要指名一个真实存在的 `connection.outputs[].id`。
- 每个 `jwtSecretGroup` 都要与已声明的 `generateGroup` 匹配。
- `flowHref` 以 `/` 开头——绝不可能是外部 URL。
- `category` 必须是七个允许值之一。

## 稳定性与版本

目录 JSON 是**稳定、带版本的公开 API**。增长是增量且向后兼容的：新的可选字段和新的枚举成员默认沿用既有行为，同一个 schema 版本内字段绝不改作他用或删除。

<TypeTable
  type={{
    minEngine: { type: 'string (semver)', description: '核心版本旋钮。安装本应用所需的最低 Openship 版本。把它设为引入该定义当前所用能力的那个发布版本。' },
    schemaVersion: { type: 'number', description: 'JSON 形态修订号，默认 1。实例会拒绝自己看不懂的更新形态。只有真正破坏形态的变更才提升它。' },
  }}
/>

**每个应用一个文件——绝不要编写多个版本**。仓库里永远只有最新的那一份文件。较旧的实例继续用它自己构建时打包的那份副本。当实例比应用的 `minEngine` 更旧时：

- 该应用**已随包附带** → 继续提供打包副本，并可能提示有更新可用；
- 该应用**是全新面孔** → 目录显示引导性的 *Requires Openship ≥ X* 卡片，客户端与服务端都拒绝安装。绝不会无声无息地消失。
