进入 Openship 的每个请求都要过同一道闸——**权限面**（permission plane），它只回答一个问题：*这个人能对这个资源做这件事吗*？把它想成大楼的前台：你的门禁卡写明你能到哪些楼层，而前台每一次都会查验，不是只在进门时看一次。

访问由三样东西共同决定：资源属于哪个**组织**、你在该组织中的**角色**，以及——对限制最严的角色——你被授予了哪些具体**授权**（grant）。

<Callout title="只有一道闸，没有旁门" type="info">
任何 API 路由忘记声明权限，Openship 都拒绝启动。不存在“不小心裸奔”的路由——安全默认在启动时强制执行，而不是留给评审去抓。
</Callout>

## 组织

**组织**（organization，简称 org）是拥有一切的容器：项目、服务器、域名、备份、计费。你是一个或多个组织的**成员**，你的访问*按组织*决定——你是某个组织的所有者，丝毫不说明你在另一个组织里的角色。

发起请求时，Openship 从 `X-Organization-Id` 头（控制台和其他 API 客户端都会设置）判断你指哪个组织，退而求其次则用你会话的默认组织。每个资源都带着自己的 `organization_id`，因此平台总能把一个项目或域名追溯到拥有它的组织，并在那里核查你的成员身份。

## 四种角色

你在组织中的角色决定了你的基线访问权。从大到小：

| 角色 | 能做什么 |
|---|---|
| **owner** | 一切，包括**计费**。通常是创建组织的那个人。 |
| **admin** | **计费之外**的一切——包括管理成员与邀请、读取审计日志。 |
| **member** | 对**除计费和审计日志外的所有资源**拥有完整访问——读、写，**还能删**。不能管理其他成员。 |
| **restricted** | **默认毫无权限**。只能访问被明确授予的具体资源。 |

<Callout title="owner 与 admin，说人话">
**owner** 握着钱袋子的钥匙——套餐、付款、退订。**admin** 打理日常：能邀请队友、部署、加域名、读审计日志，但碰不了计费。**member** 是值得信任的干将，交付活儿，但不管理团队、也看不到计费。**restricted** 上来时钥匙串是空的，钥匙一把一把地发。
</Callout>

<Callout title="标准角色天生粗糙（beta）" type="warn">
owner、admin、member 按资源**类型**分级，不按动作分级：member 对项目、服务器、部署、域名、任务和环境变量都有读、写、**删**的权限——除了管人和审计日志，与 admin 无异。按**动作**（读/写/管理）和按**资源**的限制，只有通过 **restricted** 角色和下文所述的**限范围访问令牌**才能实现。把 member 和 admin 当作可信、近乎平级的角色来对待；需要真正的最小权限时，就用 restricted 成员或限范围令牌。标准角色的细粒度授权仍在完善中。
</Callout>

## 权限标签：`resource:action`

底层实现上，每条路由声明一个简短的标签，命名一个资源和一个动作，如 `project:read` 或 `domain:write`。子资源会加中间一段——`project:service:write` 意为“编辑项目内的某个服务”。

**动作**是动词，与 HTTP 方法对应：

| 动作 | HTTP 方法 | 含义 |
|---|---|---|
| `read` | `GET`（单个资源） | 按 id 查看单个东西。 |
| `write` | `POST` / `PUT` / `PATCH` | 创建或修改某个东西。 |
| `admin` | `DELETE`（及其他破坏性动作） | 移除、重置或以其他方式销毁它。 |
| `list` | `GET`（集合） | 列出组织里的东西——不带具体 id。 |

在 [API 参考](/docs/api)里，每个端点旁都标着这些标签，你随时知道一次调用执行的是哪个动作。

## restricted 成员与资源授权

**restricted** 成员是最有讲究的一种。他们从零权限起步。要让他们能做任何事，owner 或 admin 要给他们**授权**（grant）——一条条小记录，写明“这个人可以对*那个*资源 `read` / `write` / `admin`”。

每条授权列出这些级别中的一个或多个。Openship 检查动作时，高级别同时满足低级别：

- **read**——查看与列出资源。
- **write**——创建与修改（也满足 `read` 检查）。
- **admin**——删除与全面管理（也满足 `write` 和 `read`）。

授权通过资源 id 指向某个资源，或用通配符 `*` 表示*组织中该类型的每一个资源*。于是，项目上的通配 **write** 授权让人能部署到所有项目，而单个项目 id 则把他限定在仅此一个。

### 授权沿树向下

你授权给顶层资源，访问权会**沿它的树继承下去**——不必逐个授予子资源：

| 授权给…… | ……同时覆盖 |
|---|---|
| **项目** | 它的部署、域名、服务和环境变量 |
| **备份目标** | 它的备份策略、执行与恢复 |
| **服务器** | 该服务器上的终端访问和运行时操作（日志、重启、启动/停止） |
| **邮件服务器** | 网页邮箱、品牌定制与邮件设置 |

### 可以授予什么

资源选择器提供这些可授予的类型：

| 类型 | 覆盖范围 |
|---|---|
| **项目** | 应用及其内部的一切（部署、域名、环境变量）。 |
| **服务器** | 已连接的机器及其运行时/终端访问。 |
| **邮件服务器** | 邮件托管与网页邮箱。 |
| **备份目标** | 备份存放之处及其执行记录。 |
| **计费** | 套餐与付款（owner 级专属领地）。 |
| **审计日志** | 谁做了什么的记录。 |
| **GitHub 组织** | 一次 GitHub 安装下的每个仓库。 |
| **GitHub 仓库** | 单个仓库。 |

<Callout title="你会看到哪些类型" type="info">
选择器会适应你的实例。**自托管**实例显示服务器和邮件服务器；**Openship Cloud** 则在相应位置显示计费。项目、备份目标、审计日志和 GitHub 两边都有。
</Callout>

## 邀请成员并设置角色

团队管理位于**设置 → 团队**。

<Steps>

<Step>

### 打开邀请对话框

前往**设置 → 团队**，按**邀请成员**。输入对方的邮箱地址。

</Step>

<Step>

### 选择角色

选择 **Member**、**Admin** 或 **Restricted**。（owner 是组织创建者的角色——邀请对话框里发不出去这个角色。）

- **Member** 和 **Admin** 一加入即获得相应访问权。
- **Restricted** 会在右侧打开资源选择器，你从中精确勾选这次邀请解锁什么。

</Step>

<Step>

### 发送邀请

Openship 发出含加入链接的邮件。受邀者接受后，其成员身份即创建，待生效的授权随之应用。之后随时可以在团队列表里该成员那一行放宽或收紧 restricted 成员的授权。

</Step>

</Steps>

## 访问令牌遵循同一套规则

脚本、CLI 和 AI 智能体用的是**个人访问令牌**（可吊销的按用户密钥，以 `Authorization: Bearer opsh_pat_...` 发送）。令牌解析出你的用户和组织，然后遵守与浏览器会话一模一样的权限模型。

令牌可以从两个方向收紧：

- **只读**——令牌拒绝一切变更操作（`POST`/`PUT`/`PATCH`/`DELETE`）。
- **限范围**——令牌携带*自己的*授权，被视为 **restricted** 主体，恰好限于这些授权之内，**哪怕你是 owner**。限范围令牌绝做不了超出其范围的事。

<Callout title="限范围令牌越不过它的授权" type="warn">
这是有意为之：把一枚限范围的只读令牌交给脚本或智能体，它最坏也就是读一读你授予的那几个资源——无论你自己的账号权力有多大。
</Callout>

## 被拒时显示为“未找到”

当你试图碰不允许碰的东西时，Openship 返回 **404 Not Found**，而不是 403 Forbidden。

<Callout title="为什么是 404 而不是 403？" type="info">
403 会悄悄确认资源*存在*——只是你看不见。404 什么都不透露。这防的是 **IDOR**（不安全的直接对象引用——靠猜 id 来探测你不该知道其存在的资源）。如果某个项目 id 不属于你，平台表现得就好像它压根不存在。
</Callout>
