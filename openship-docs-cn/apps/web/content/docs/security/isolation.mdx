title: 隔离
description: Openship 如何把部署与项目彼此隔开——独立容器、每项目专属的网络与卷，以及强制执行的资源限制。
---

把你的 Openship 服务器想象成一栋公寓楼。你部署的每个应用都有自己的单元：自己的入户门、自己的电表、自己的信箱。邻居闯不进你的单元，一个吵闹的租户也抽不干整栋楼的电。本页讲解 Openship 在你的应用之间砌起的墙——每堵墙是什么，以及在各种运行时上有多结实。

## 先划定归属

在任何东西跑起来之前，访问就由**组织**（拥有项目的管理工作区）和**项目**划定。每个 API 请求都要过一道权限检查，客户端给的组织 id 只有在你确实是成员时才被采信。因此一个团队绝不可能列出、部署或拆掉另一个团队的项目。那道控制面边界在[权限模型](/docs/security/permissions)里讲；本页其余部分讲的是部署上线之后，应用之间*在运行时*的那几堵墙。

Openship 在主机上创建的每样东西，都用 Docker **标签**（label，贴在容器上的键值对）盖上了所属项目和部署的戳：

- `openship.project`——归哪个项目所有。
- `openship.deployment`——由哪次具体部署创建。
- `openship.service`——属于哪个服务（多服务 compose 项目用）。
- `openship.build`——哪个构建会话产出了构建镜像，半途而废的构建产物也能被回收。

有了这些标签，Openship 才能可靠地找到并只清理自己的资源——比如回收一次中途失败的部署留下的容器，而丝毫不碰机器上的其他东西。

## 每次部署一个容器

在 **Docker** 运行时上，每次部署都跑在自己的**容器**里——一个沙箱化的盒子，有自己的文件系统、进程和网络视图，由 Linux 内核把它与主机、与其他容器隔开。容器命名有规律，两个永远不会撞名：

| 对象 | 命名模式 |
|---|---|
| 单应用部署 | `openship-<project>-<deployment>` |
| compose 项目里的一个服务 | `openship-<slug>-<service>` |
| 项目网络 | `openship-<slug>` |
| 项目范围的命名卷 | `openship-<slug>-<name>` |

单应用容器发布在**随机主机端口**上，由 Openship 内建的路由（**OpenResty**，基于 nginx 的反向代理）把流量转发过去——因此没有任何东西暴露在可预测的端口上，别的应用抢不到、也撞不上。

## 每项目专属网络

对有多个服务的项目（比如一个 Web 应用加一个数据库），Openship 会创建一个私有的**桥接网络**（bridge network）——一条只有挂上来的容器才能用的虚拟局域网——命名为 `openship-<slug>`。该项目里每个服务都加入其中，可以用服务名互相访问，比如 `http://database:5432`。

因为每个项目拿到的都是**自己的**网络，一个项目里的服务无法按名字访问另一个项目里的服务。服务也只有明确要求时才对外面的世界开端口——否则只有项目网络内的兄弟服务能连到它。

<Callout title="名字是项目私有的" type="info">
两个不同的项目可以都有一个叫 `api` 或 `db` 的服务而互不冲突——每个名字只在各自项目的网络内解析。
</Callout>

## 每项目专属卷

**命名卷**（named volume）是一块由 Docker 在重启之间保管的托管磁盘（数据库用它，数据才能在重新部署后幸存）。坑在于：如果两个项目都申请一个字面上叫 `postgres_data` 的卷，原版 Docker 会把*同一块*盘发给它们——悄无声息的跨项目数据混染。

Openship 给每个命名卷加上项目前缀来杜绝此事：`openship-<slug>-<name>`。都声明了 `postgres_data` 的两个项目拿到的是两块永不接触的独立磁盘。绑定挂载（bind mount，你指定的某个具体主机路径）与匿名卷则原样保留。

<Callout title="更早的服务与命名冲突" type="warn">
在卷作用域机制之前创建的服务保留其原始裸卷名。为了保护它们，如果某个卷名已被另一个项目的容器占用，Openship 会拒绝部署**新**项目，并提示你改名——因此任何部署都不可能悄悄认领别人项目的数据。
</Callout>

## 资源限制

每次部署都会领到一份预算，一个应用饿不死其他应用。预算有三部分：

- **CPU**（`cpuCores`）——小数核数，如 `0.5`、`1`、`2`。
- **内存**（`memoryMb`）——以 MB 计的硬上限。
- **磁盘**（`diskMb`）——以 MB 计的可写磁盘。

运行中应用的默认预算是 **1 核、512 MB 内存、5 GB 磁盘**。构建会拿到更大的预算（最高 **4 核与 8 GB**），因为打包器都是吃内存大户，之后运行中的应用再落回生产体量。你可以在项目设置里改预算，范围是：CPU `0.25`–`4`，内存 `128`–`8192` MB，磁盘 `64`–`204800` MB。

预算执行得多严取决于运行时。在 Docker 上，**内存是硬上限**——越界容器即被杀掉重启——而 **CPU 是相对权重**：争抢时 `2` 核应用大约能拿到 `1` 核应用两倍的 CPU 时间，但机器空闲时谁都可以用上闲置部分。

## 各运行时横向对比

Openship 有三种方式运行你的应用，隔离强度各不相同。选一个与你部署位置相符的标签页。

<Tabs items={['Docker', 'Server (no Docker)', 'Cloud']}>

<Tab value="Docker">

隔离最强。每次部署都是独立容器，具备：

- 与主机、与其他应用的内核级隔离，
- 硬性**内存**上限与 **CPU** 权重，以及
- 路由前置的随机发布端口——绝不是会被别的应用抢走的固定端口。

多服务（compose）项目在此之上还有**每项目私有网络**和**项目范围的命名卷**。只要 Docker 可用，这就是推荐的运行时。

</Tab>

<Tab value="Server (no Docker)">

没有 Docker 的主机上，Openship 把你的应用**直接作为进程**运行，由 systemd（Linux）或轻量的 `nohup` 兜底（macOS）守护。每次部署有自己的发布目录和自己的受守护进程（Linux 上是名为 `openship-<deployment>.service` 的专用 systemd 单元）。

这更轻量，但墙更薄：进程**共享主机的文件系统、网络和用户**，而且这种模式**不**强制 CPU 或内存上限。systemd 还额外提供崩溃自动重启与重启后存活；`nohup` 兜底则没有。

<Callout title="没有 Docker 时隔离更弱" type="warn">
裸进程共享主机且不受资源上限约束，共享的裸主机上只运行你信任的应用，多租户场景一律优先选择 Docker 运行时。
</Callout>

</Tab>

<Tab value="Cloud">

在 Openship Cloud 上，每次部署运行在自己隔离的云**工作区**里——独立实例，不是共享机。你选一个规格档位，对应具体的 CPU / 内存 / 磁盘：

| 档位 | CPU | 内存 | 磁盘 |
|---|---|---|---|
| micro | 0.25 | 256 MB | 4 GB |
| low | 0.5 | 512 MB | 8 GB |
| medium | 1 | 1 GB | 16 GB |
| high | 2 | 2 GB | 32 GB |

**自定义**档位可以填精确值。云与自托管如何保持隔离，参见[本地与云的边界](/docs/security/cloud-boundary)。

</Tab>

</Tabs>
