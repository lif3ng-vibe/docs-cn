Openship 有几扇不同的前门，但都通向同一个地方。就像添置一台新家电：你可以拿起即插即用的快装线（安装脚本），用已有的工具自己拆箱（npm），买开箱即用的整装版（桌面应用），或者把它永久接进你的工作间（Docker Compose）。选适合你的那种——以后随时可以换。

<Callout title="该选哪一个？">
- **只想在自己的机器上快速试一试**？用**安装脚本**。
- **已经装好 Node.js 和 npm 了**？用 **npm** CLI。
- **想要一个完全不用终端的图形界面应用**？装**桌面应用**。
- **在 VPS 或服务器上运行并希望它常驻**？（推荐）用 **Docker** 安装——可以用下面的 **Docker Compose** 技术栈，也可以用 CLI（`openship up`，在 Linux VPS 上**默认就是 Docker/Compose**）**。裸机**（bare）安装（不用 Docker，内置数据库）也完全受支持——参见 [Compose 与裸机模式](#运行-openship)。
</Callout>

## 安装

<Tabs items={['Install script', 'npm', 'From source (dev)', 'Desktop app', 'Docker Compose']}>

<Tab value="Install script">

最快的方式。一条命令即可安装 `openship` 命令——这是一个自包含、经校验和验证的包，运行在 **Node** 之上：系统 Node 足够新就直接用，否则只为 Openship 拉取一份官方 Node 构建，绝不碰你的全局工具。无需配置 Node 或 npm。

```bash
curl -fsSL https://get.openship.io | sh
```

在 **Windows** 上，请改在 PowerShell 中运行：

```powershell
irm https://git.openship.io/windows | iex
```

<Callout title="锁定版本" type="info">
想安装特定版本而不是最新版？把 `OPENSHIP_VERSION` 设置在执行脚本的 `sh` 上——而不是 `curl` 上——例如 `curl -fsSL https://get.openship.io | OPENSHIP_VERSION=0.1.9 sh`。（`VAR=… curl … | sh` 这种前缀写法只对 `curl` 生效，管道后面的 `sh` 看不到该变量。）
</Callout>

<Callout title="装完找不到 openship 命令？" type="info">
安装器已把 Openship 的 bin 文件夹加入你的 `PATH`。如果 shell 仍找不到 `openship`，请新开一个终端——或在 macOS/Linux 上运行 `export PATH="$HOME/.openship/bin:$PATH"`——然后重试。
</Callout>

完成后你就会拥有 `openship` 命令。接着前往下方的[运行 Openship](#运行-openship)。

</Tab>

<Tab value="npm">

已经有 **Node.js 22 或更新版本**和包管理器？用你顺手的那一个全局安装 CLI：

```bash
npm i -g openship
```

```bash
pnpm add -g openship     # pnpm
yarn global add openship  # yarn
bun add -g openship       # bun
```

这样得到的就是与安装脚本相同的 `openship` 命令。前往[运行 Openship](#运行-openship)。

<Callout title="Node 版本偏旧？CLI 会主动提出修复" type="info">
这是唯一一条运行在**你自己的** Node 上的安装路径——上面的安装脚本会自己解决运行时（runtime：系统 Node 达到 22+ 就用，否则自动下载一份）。

如果你在更旧的 Node 上运行 `openship`，它不会直接拒绝。它会先找找这台机器是否已下载过 Node 22 并静默使用；如果没有，它会提议拉取一份官方 Node 22（约 50 MB，经校验和验证）到 `~/.openship/runtime`，且**仅供 Openship 使用**——你的系统 Node 原样不动。之后的运行会自动使用它，所以只会询问一次。

非交互环境（CI、置备脚本）？`OPENSHIP_VENDOR_NODE=1` 表示不经询问直接接受该提议；`OPENSHIP_VENDOR_NODE=0` 表示拒绝。低于 Node 20 时 CLI 完全无法运行，若未设置这两个变量之一，它会停下来并说明原因；Node 20 或 21 则警告后继续。
</Callout>

<Callout title="升级 Node 后 openship 命令不见了？" type="info">
版本管理器（nvm、fnm、volta）按 **Node 版本**分别保存全局包，因此安装更新的 Node 后，CLI 仍留在旧版本那边，`openship` 就从 `PATH` 上消失了。在新版本上重新安装即可：

```bash
npm i -g openship
```
</Callout>

</Tab>

<Tab value="From source (dev)">

想预览尚未发布的构建——某个分支、标签，或领先于下个发布的 `main`？这会**从源码**构建 CLI（与 `bun dev` 相同的方式），并安装为一个**独立的 `openship-dev` 命令**：

```bash
curl -fsSL https://get.openship.io/dev | sh
```

用 `OPENSHIP_REF`（默认 `main`）选择分支/标签——同样要设置在执行脚本的 `sh` 上而不是 `curl` 上，否则管道后面的 `sh` 看不到它：

```bash
curl -fsSL https://get.openship.io/dev | OPENSHIP_REF=my-branch sh
```

从源码构建的版本与生产安装**完全隔离**——拥有自己的主目录（`~/.openship-dev`）、自己的令牌/端口/数据和开机服务——绝不会碰你的生产版 `openship`。用法与普通 CLI 相同，只是名字叫 `openship-dev`：

```bash
openship-dev            # 交互式设置 + 管理面板
openship-dev up         # 本地运行
openship-dev update     # 拉取最新源码并就地重建（无需等待 npm 发布）
```

<Callout title="这是开发/预览构建" type="warn">
该构建未经签名验证（没有签名的发布产物），编译控制台需要实打实的内存和 CPU——配置太低的机器可能 OOM。它需要 **Bun** 和 **git**。这不是生产路径；生产环境请用上面的安装脚本或 npm。卸载命令：`rm -f "$(command -v openship-dev)" && rm -rf ~/.openship-dev`。
</Callout>

</Tab>

<Tab value="Desktop app">

桌面应用把整套东西——API、控制台和数据库——打包成一个在你自己机器上运行的应用。不需要服务器，也不需要 Docker：非常适合本地开发，以及直接从磁盘上的文件夹部署。

如果已装好 CLI，一条命令即可拉取并启动它：

```bash
openship install
```

或直接下载对应系统的安装包：

- **macOS** — [Apple Silicon](https://github.com/oblien/openship/releases/latest/download/Openship-arm64.dmg) · [Intel](https://github.com/oblien/openship/releases/latest/download/Openship-x64.dmg)
- **Windows** — [Openship-win32-x64.zip](https://github.com/oblien/openship/releases/latest/download/Openship-win32-x64.zip)
- **Linux** — [Openship.AppImage](https://github.com/oblien/openship/releases/latest/download/Openship.AppImage)

也可以前往[下载页面](/download)获取。

在 **Linux** 上，先给 AppImage 加上可执行权限，再启动它——无需安装器，也无需 root：

```bash
chmod +x Openship.AppImage
./Openship.AppImage
```

<Callout title="AppImage 需要 FUSE" type="info">
大多数 Linux 发行版已自带。如果 AppImage 无法启动，要么安装 FUSE（Debian/Ubuntu 上 `sudo apt-get install -y libfuse2`），要么以自解压方式运行：`./Openship.AppImage --appimage-extract-and-run`。
</Callout>

</Tab>

<Tab value="Docker Compose">

想自己在服务器上运行这些容器？自托管技术栈位于 **`docker/docker-compose.yml`**，会直接**拉取**已发布的镜像（来自 GitHub Container Registry）——不需要任何构建工具。在仓库根目录下运行：

```bash
git clone https://github.com/oblien/openship.git
cd openship
cp .env.example .env          # 然后编辑其中的密钥
docker compose --env-file .env -f docker/docker-compose.yml up -d
```

它会运行五个服务：**Postgres**、**Redis**、**API**（`:4000`）**、控制台**（`:3001`），以及 **:80/:443** 上的 **OpenResty 边缘**——一个以 host 网络模式运行的容器，负责路由和 Let's Encrypt TLS。API 会挂载宿主机的 Docker socket，从而能把你要部署的应用构建并运行为宿主机容器**。仅限 Linux**（边缘服务需要 host 网络）；macOS/Windows 请改用 CLI（`openship up`）。

启动完成后，在浏览器打开 `http://localhost:3001` 即可进入控制台。

<Callout title="拉取式部署——锁定版本" type="info">
该技术栈拉取的是已发布的镜像（`ghcr.io/oblien/*`），因此无需构建即可启动。在 `.env` 中固定 `OPENSHIP_VERSION`（例如 `0.2.3`）可获得可复现的升级，然后执行 `docker compose --env-file .env -f docker/docker-compose.yml pull` 和 `… up -d`。若想改为从源码构建，追加 `-f docker/docker-compose.build.yml … up -d --build`。
</Callout>

<Callout title="先编辑 .env" type="warn">
启动技术栈**之前**，先把 `.env.example` 复制为 `.env` 并填好其中的密钥。若要从其他机器访问，还需设置 `OPENSHIP_PUBLIC_URL`（如果在反向代理之后，再加 `TRUST_PROXY=true`）——否则控制台能打开但登录会被拒绝。
</Callout>

<Callout title="这条路不会配置主机控制" type="warn">
`openship up` 会替你开通容器到宿主机的 SSH 通道；自己运行这个文件则不会。技术栈本身能正常启动、部署也能工作，但涉及宿主机本身的操作——`:80`/`:443` 接管、邮件引擎、来自应用目录（app catalog）且配置文件需写入宿主机的应用——在你完成开通之前都会拒绝执行。五个手动步骤见 `.env.example` 中 **Host operations from the container** 一节，故障表现与验证方法见[故障排查 → 主机控制通道](/docs/troubleshooting/host-channel)。
</Callout>

<Callout title="仓库根目录的 docker-compose.yml 是另一个文件" type="info">
仓库**根目录**下的 compose 文件是 SaaS / 从源码运行的**控制面**（control plane）——它从源码构建并承载官网，没有边缘服务，也不挂载 Docker socket。它**不是**用来自托管你的应用的。要自托管，请用上面的 `docker/docker-compose.yml`（或直接 `openship up`）。
</Callout>

</Tab>

</Tabs>

## 运行 Openship

如果你安装的是 CLI（安装脚本或 npm），最快的起步方式是**引导式设置**——运行：

```bash
openship
```

不带参数运行 `openship`，它会一步步引导你：选择私有或公开、填写你的域名（如果公开），以及**管理员姓名、邮箱和密码**。随后它会完成部署、创建管理员账号，并打印登录 URL。这是搭建新实例的推荐方式。

想跳过问答？`openship up` 会直接启动同一个后台服务：

```bash
openship up
```

<Callout title="Compose 与裸机模式——自动选择" type="info">
无论怎么启动，在**装有 Docker 的 Linux** 上，Openship 都会安装容器技术栈（Postgres、Redis、API、控制台，以及 :80/:443 上的 OpenResty 边缘——与上面 Docker Compose 标签页里相同的技术栈），从而能**把部署的应用托管在这台机器上**并配上域名和 TLS。这是 **VPS 上的推荐模式**，也是 CLI 在该环境的默认选择。其他环境（macOS、Windows，或没有 Docker 的 Linux）则安装为带内置数据库的单个轻量进程——一个常驻的控制面，可把应用部署到服务器或云端。两种模式都完全受支持；要强制指定，运行 `openship up --compose` 或 `openship up --bare`。
</Callout>

无论哪种方式，Openship 都作为**开机自启、崩溃后自动重启的后台服务**运行——就像一辆总会回到车场的配送卡车。API 运行在 `:4000`，控制台运行在 `:3001`；裸机模式下由内置数据库支撑（Compose 模式则是 Postgres + Redis）。CLI 实例始终需要登录——要么是你在 `openship` 设置中创建的管理员，要么是直接运行 `openship up` 时在控制台里注册的第一个账号。

```bash
openship stop              # 停止服务——不会重启，重启机器后也不会再起来
openship up --foreground   # 改为附着在本终端前台运行（一次性；Ctrl-C 停止）
openship up --no-ui        # 只运行 API，不启动控制台
openship uninstall         # 移除 Openship 及其数据（见下文）
```

### 主机控制（加固）

控制面可以操作它所运行的那台机器：从现有代理手里腾出 `80`/`443` 端口、读取宿主机配置、扫描监听端口、打开宿主机 shell。在 Compose 安装中，这条通道是一把**指向宿主机的 SSH 密钥**，由 `openship up` 生成并授权给执行命令的用户（通过内部的 `host.docker.internal` 桥接访问，绝不走公网 IP）。

<Callout title="它可能只是名义上存在" type="warn">
生成了密钥、写入了地址，不等于通道真的可用，而且这种差异在安装时不会暴露。真正决定它的是宿主机上的两件事：一个 **sshd** 在容器可达的地址上监听，以及一条允许容器到宿主机流量的防火墙规则——这个地址是宿主机本地的，流量会经过默认拒绝的 `ufw` 所在的 `filter/INPUT` 链，而每个已发布端口都被 DNAT 处理、绕开了这条链。于是可能出现技术栈显示健康、宿主机操作却全部失效的情况。`openship up` 会真正探测这条通道并主动提供防火墙规则；`openship doctor` 稍后可复查。如果你是自己运行 `docker/docker-compose.yml` 完成安装的，这些都不会替你开通——手动步骤见 `.env.example`。无论哪种情况，修复方法与由此产生的故障都在[故障排查 → 主机控制通道](/docs/troubleshooting/host-channel)。
</Callout>

你也可以选择不给：

```bash
openship up --no-host-control
```

设置之后：不会生成或挂载主机密钥，宿主机操作会以明确的错误拒绝执行，这台机器也不再作为部署目标出现（"This Server" 消失）。它**有意只做成 CLI 选项**——如果做成控制台里的开关，恰恰是它要防的东西就能碰到它。

**如何选择**

| 你的机器 | 建议 |
|---|---|
| 把应用部署到**自身**（最常见的单机安装） | **保持主机控制开启**。`:80/:443` 接管、宿主机端口扫描和宿主机终端都依赖它。 |
| 只管理**远程**服务器 | **`--no-host-control`**。在这里毫无收益，还能关掉一条通往宿主机 root 的捷径。 |
| 与不容有失的工作负载同机运行 | 用 `--no-host-control`，并把控制台挡在公网之外（设置 `OPENSHIP_BIND_ADDR`，或放在你自己的代理 + 认证之后）。 |

<Callout title="这是纵深防御，不是隔离" type="warn">
API 还会挂载宿主机的 **Docker socket**，因为构建和运行你的应用离不开它。对任何能接触到它的人来说，挂载的 socket 等同于宿主机 root——这是每个自托管部署平台都在做的权衡。`--no-host-control` 移除的是*裸露在外的捷径*（宿主机 shell 按钮和磁盘上的密钥），并不会把控制面沙箱化。请把控制台访问当作宿主机访问来对待，没有可信代理就不要把它暴露到公网。
</Callout>

### 卸载 Openship

`openship stop` 停止 Openship 但保留一切——数据库、已签发的证书和边缘配置都还在，`openship up` 可以从上次中断的地方继续。要彻底移除：

```bash
openship uninstall                 # 先询问；移除技术栈、数据、镜像和 ~/.openship
openship uninstall --keep-data     # 只移除运行中的技术栈，保留数据库 + 证书
openship uninstall --keep-images   # 不删除 Openship 容器镜像
openship uninstall --yes           # 跳过确认（用于脚本）
```

有两样东西它有意不动，因为自托管机器通常是多用途共用的：

- **你已部署的应用继续运行**。移除控制面并不会停掉它创建的容器——`docker ps` 仍能看到它们。想让它们也消失，请先删除对应的项目。
- **不做任何清理**（prune）。只会按精确标签移除 Openship 自己的三个镜像和本技术栈的卷；你的其他镜像、卷和容器原样保留。

<Callout title="如果 Openship 接管了 80/443 端口" type="warn">
如果安装时 Openship 迁移过现有的代理，卸载会释放这些端口，但不一定能把原先的服务重新拉起来——一次完成的接管不会留下任何记录。请自行重新启用你的代理（`sudo systemctl enable --now nginx`，或 caddy / apache2）。它的配置从未被修改过。
</Callout>

<Callout title="--foreground 是干什么用的" type="info">
`openship up` 在你关闭终端后仍会继续运行。`openship up --foreground` 正相反：它留在你的终端里，按下 Ctrl-C 就停止。适合快速的一次性运行，或用于无法安装后台服务的系统。
</Callout>

底层实现上，`openship up` 会向操作系统的服务管理器注册，从而在重启后依然存活：

- **Linux**——一个 **systemd** unit（以 `--user` 运行并启用 linger，或以 root 运行时用 system unit）。
- **macOS**——一个在登录时加载的 **launchd** agent。
- **Windows**——登录时触发的**计划任务**（尽力而为；在这个系统上 `openship up --foreground` 或桌面应用是更可靠的选择）。

<Callout title="找不到服务管理器？" type="warn">
在没有 systemd 的 Linux 机器上，`openship up` 无法安装持久服务。请改用 `openship up --foreground`，或使用 Docker Compose 技术栈实现常驻。
</Callout>

### 全自动无人值守安装（headless）

单独运行 `openship up` 只会安装*服务*本身——第一个管理员要在控制台中创建（或通过交互式的 `openship` 向导）。加上 `--non-interactive`（别名 `--yes`）和相应的安装参数，即可**全程无问答**地置备一台机器——包括管理员账号，以及在支持情况下的域名。非常适合 CI、cloud-init 或脚本化的机器群。

管理员引导和 `byo` / `free` / `none` 域名步骤在**两种**安装方式（Compose 和裸机）上都可用。唯一的差异是受管的**自定义**域名（由 Openship 自己签发 Let's Encrypt 证书），只为裸机安装接好——见下文。

**裸机安装**（`--bare`，内置数据库，不用 Docker）——Openship 管理宿主机上的 OpenResty，因此 `--domain-kind custom` 可以端到端地置备证书：

```bash
OPENSHIP_ADMIN_PASSWORD='a-strong-password' openship up --bare --non-interactive \
  --admin-email you@example.com --admin-name "You" \
  --domain-kind custom --hostname ops.example.com \
  --acme-email you@example.com --edge takeover
```

**Compose 安装**（装有 Docker 的 Linux 上的默认方式）——边缘服务以容器运行，支持裸机安装的全部域名类型，包括 `custom`。如果现有代理占着 `:80/:443`，`--edge` 可预先回答如何处理它（`migrate` 先把它的站点导入 Openship 的边缘；`takeover` 则停掉它，其站点随之停止服务）：

```bash
OPENSHIP_ADMIN_PASSWORD='a-strong-password' openship up --non-interactive \
  --admin-email you@example.com --admin-name "You" \
  --domain-kind custom --hostname ops.example.com \
  --acme-email you@example.com --edge migrate
```

- **管理员**——`--admin-email`（必填）+ 可选的 `--admin-name`。密码来自 `--admin-password`，更推荐用 **`OPENSHIP_ADMIN_PASSWORD`** 环境变量（environment variable，避免留在 shell 历史里）。幂等：重复运行会重置现有管理员的密码而不是报错。两种方式都可用。
- **域名**——`--domain-kind`：
  - `byo`——用你自己的反向代理顶在前面（`--hostname`，或从 `--public-url` 推导）。两种方式都可用。
  - `custom`——Openship 的边缘为 `--hostname` 签发 Let's Encrypt 证书；`--acme-email` 和 `--edge migrate|takeover|cancel` 预先回答 `:80/:443` 接管问题。两种方式都可用：API 会依据 `OPENSHIP_EDGE_MODE` 选择宿主机 OpenResty 或容器边缘，因此无论哪种方式 CLI 发出的调用都相同。
  - `free`——一个 `<slug>.opsh.io` 子域名（`--slug`）。**要求这台机器已连接到 Openship Cloud**（免费域名的连接是一个交互式浏览器步骤）——先完成连接，再运行无人值守安装，或改用 `byo`。
  - `none`（未提供域名参数时的默认值）——没有公网域名的私有机器。

任何缺失或非法的参数都会以非零码退出并给出精确的报错信息，因此可以放心写进脚本。证书签发会流式输出进度（全新域名上 ACME 可能需要一分钟），并且是尽力而为：即使没有完成，安装也会成功并说明原因，随后在后台和下次启动时重试。加 `--dry-run` 可在不实际置备的情况下预览将要安装的服务。

## 打开并确认一切正常

本地实例跑起来之后，在浏览器中打开控制台：

```bash
openship open
```

也可以直接在终端里检查 API 健康状况：

```bash
openship status
```
