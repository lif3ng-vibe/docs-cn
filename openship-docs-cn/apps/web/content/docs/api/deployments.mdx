部署（deployment）会构建并发布项目所配置的源。使用本页面提交构建、查看进度、处理决策、重新部署或回滚。要处理生成的文件与文件夹上传，请从[源文件](/docs/api/sources)开始。

在所选提供方支持的前提下，这些操作适用于自托管与 Cloud 部署。
[Cloud 作用域要求](/docs/api/sdk/compatibility#cloud)仍然适用。

## 部署 Git 项目

重新部署一个已关联的项目，从其 Git 源拉取。如果要部署**本地文件夹**，请使用以 [`/build/access`](#deploy-wizard-buildaccess) 收尾的上传流程。

```ts
  branch: "main",

```

```bash
  -H "Authorization: Bearer $OPENSHIP_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"projectId":"proj_123","branch":"main"}'
```

## 提交已上传的构建 [#deploy-wizard-buildaccess]

Git 项目则传入 `projectId` 与可选的 `branch`。返回 `{ success, deployment_id, project_id }`。

</Tab>

```bash
  -H "Content-Type: application/json" \
  -d '{"projectId":"proj_123","branch":"main","buildStrategy":"server"}'
```

</Tab>
</Tabs>

## 等待、决策与取消

部署提交会在工作负载就绪之前返回 ID。读取持久化的构建状态来判断是否成功。SDK 的 `deployment(id)` 句柄在状态之上增加了轮询与归一化的结果。

<Tabs items={['SDK', 'REST API']} groupId="api-transport" persist>
<Tab value="SDK">

```ts
const outcome = await ship.deployment("dep_123").wait({ timeoutMs: 120_000 });
if (!outcome.success) throw new Error(outcome.message ?? outcome.status);
```

</Tab>
<Tab value="REST API">

```bash
curl "$OPENSHIP_URL/api/deployments/dep_123/build" \
  -H "Authorization: Bearer $OPENSHIP_TOKEN"
```

</Tab>
</Tabs>

REST 请求返回一个状态快照；部署运行期间请轮询它。SDK 会等待直到到达终态或需要决策。`ready` 与 `no_changes` 都算成功。失败、取消、部分失败与被拒绝的情况需要显式处理。

`wait()` 返回 `status`、`success`、`decisionPending` 与 `cancellationPending`，可能附带可选的 `prompt`、`message` 或 `warning`。不提供 `onPrompt` 回调时，只要还有决策待处理就会返回 `action_required`。要接入你自己的决策 UI：

```ts
import type { PromptPayload } from "openship";

export async function waitWithDecisions(
  deploymentId: string,
  chooseAction: (prompt: PromptPayload) => Promise<string>,
) {
  return ship.deployment(deploymentId).wait({
    timeoutMs: 120_000,
    onPrompt: chooseAction,
  });
}
```

返回 prompt 提供的某个 action ID。REST 调用方把所选的 action 以
`{ "action": "<offered-id>" }` 提交到 `POST /api/deployments/:id/build/respond`。

中止或超时会停止等待观察。要取消执行，请调用 `deployments.cancel(id)` 并检查随后的状态。取消请求可以在工作收尾期间保持待处理；它不会回滚已经创建的发布。

</Tab>

```bash
  -H "Authorization: Bearer $OPENSHIP_TOKEN"
```

</Tab>

REST 返回 Server-Sent Events。SDK 事件包含事件名与序列化数据；
[`consumeDeploymentEvents()`](/docs/api/sdk/utilities#部署辅助工具) 可解码日志分块。
在游标仍可用时，可用 `since` 从已知的事件游标处恢复。跨 worker 重启的持久化重放尚未实现。流结束不代表部署成功；请读取状态。

## 重新部署

<Tabs items={['SDK', 'REST API']} groupId="api-transport" persist>
<Tab value="SDK">

```ts
const submitted = await ship.deployments.redeploy("dep_123", { useExistingCommit: true });
console.log(submitted.deployment_id);
```

</Tab>
<Tab value="REST API">

```bash
curl -X POST "$OPENSHIP_URL/api/deployments/dep_123/redeploy" \
  -H "Authorization: Bearer $OPENSHIP_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"useExistingCommit":true}'
```

</Tab>
</Tabs>

重新运行构建。默认会解析分支上的最新 commit（即自动重新部署语义）；
发送 `{ "useExistingCommit": true }` 则按原始部署所用的确切 commit 重新构建。

## 回滚与固定

回滚（rollback）把此前某次部署的产物/commit 恢复为活动发布。固定（pin）把一次部署标记为受保护，使其不被回滚窗口的清理回收——`POST /:id/pin` 默认为
`{ "pinned": true }`；发送 `{ "pinned": false }` 可解除固定。

```
POST /api/deployments/:id/rollback
POST /api/deployments/:id/pin
```

## 部分失败的 Compose 部署：保留或拒绝

当多服务（compose）部署中部分服务成功、部分失败时，部署会停在 `partial_failure` 且 `decision: pending`（"需要操作"）状态。需要显式解决：

- **保留**（Keep）接受已成功的部分，其余服务维持此前的版本。
- **拒绝**（Reject）把已变更的服务回滚到之前的状态。

```
POST /api/deployments/:id/keep
POST /api/deployments/:id/reject
```

## SSL 状态与续期

两个接口都在 JSON 请求体中携带域名。`/ssl/status` 是无副作用的探测（用 `POST` 只是为了让主机名随请求体传输）；`/ssl/renew` 会重新签发证书。

```
POST /api/deployments/ssl/status
POST /api/deployments/ssl/renew
```

## 错误

<Callout title="400 — 请求错误/操作失败" type="warn">
缺少必填字段（`domain is required`、`source must be 'github' or 'local'`），或无法执行操作（例如取消一个已结束的部署，或对一个未处于等待决策状态的部署执行 keep/reject）。响应体携带 `{ success: false, error }`。
</Callout>

<Callout title="403 — cloud 模式下的本地源" type="error">
`source: "local"` 的 `prepare`（或文件夹部署）在 Openship Cloud 上不可用——那里没有宿主机文件系统。请改用 Git 源。
</Callout>

<Callout title="针对单个部署路由的 404" type="error">
该 `:id` 不属于你的组织（或已被删除）。用 `GET /api/deployments` 列出，即可获得
有效 ID。
</Callout>
