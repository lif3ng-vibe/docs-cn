**服务**（service）是项目内的一个可运行单元：docker-compose 编排里的一个容器，或 monorepo 中的
一个子应用。两者存在同一张表里（以 `kind` 区分），因此该 API 覆盖服务的列出与编辑、
从 `docker-compose` 文件同步服务、启动/停止/重启容器、
化解 compose 漂移，以及设置按服务维度的环境变量。在控制台上对应一个项目的
**Services** 标签页；在终端上则对应 [`openship service`](/docs/cli/projects)。

这些操作可在受支持的自托管与 Cloud 服务商上使用。固定的组织
作用域需要一条兼容的 Cloud 直连；参见 [Cloud 兼容性](/docs/api/sdk/compatibility#cloud)。

服务与部署的响应会把非空的 `buildArgs` 值打码为 `••••••••`，与
`environment` 一样。这同样适用于保留的部署快照与 Compose 漂移预览。空字符串
保持为空，`null` 仍表示从构建环境继承。写入时，回显掩码表示
保留该键的存量值；没有存量来源就直接发送的掩码会被丢弃。`buildArgs` 始终是整个 map 的
替换：省略某个键即移除它，或发送 `{}` 清空整个 map。

对字面量 build args，响应还包含以参数名为键的 `buildArgsFingerprints`。轮换某个字面值之后，把服务写入响应中的指纹与同一服务在部署历史（`meta.composeServices[]`）或构建状态（`composeServices[]`）中的指纹对比。
指纹相同表示存储的字面值一致；轮换会改变指纹，
但不会返回任何一侧的值。这些值是按项目、服务名与参数键限定范围的 HMAC-SHA256 值，
因此无法离线计算，也无法跨服务比较。轮换实例的认证密钥
同样会改变它们。

指纹描述的是已存储的构建配置，而不是正在运行的容器。继承（`null`）与
插值得到的参数没有指纹，因为其生效值取决于构建环境。
快照在内部为回滚保持完整；既有历史在读取时打码，不需要迁移。

源扫描默认同样会打码构建参数。带 `includeEnv: true` 的授权编辑扫描
才会包含源里的值，以便部署表单能编辑它们；它需要写权限，且对 GitHub 源还需具备读取仓库完整内容的权限。

## 在项目间共享服务

一个服务可以留在其所属项目中，并同时连接到多个其他项目。这复用
既有实例及其数据。在控制台中，打开该服务并选择 **Use in a project**，或在消费方的 Services 标签页选择 **Add service → Connect existing**。共享服务
会连同其源项目一起展示；属主可以看到每个服务被哪些项目使用。

用既有的项目连接 API 创建这些链接：

```ts
const { outputs } = await ship.projects.getAppConnection("source_project");
const output = outputs.find(item => item.sourceServiceId === "svc_database");
if (!output?.value) throw new Error("Configure and deploy the source database first.");

await ship.projects.connectBundle("consumer_project", {
  sourceProjectId: "source_project",
  items: [{ outputId: output.id, envKey: "DATABASE_URL" }],
  mode: "internal",
});
```

调用者需要对同一组织中两个项目的写权限。私有服务连接
要求同一服务器上的 Docker 项目。凭据存为机密环境变量，在消费方的常规部署中从源侧刷新。断开连接只移除该项目的链接；
源服务与其他消费方保留。删除共享服务或其所属项目之前，先断开所有消费方。

## 添加服务

服务行是一个联合类型：`kind: "compose"` 使用容器字段（image、build、ports……），而
`kind: "monorepo"` 使用子应用构建字段（rootDirectory、framework……）。两组字段都被接受
且均可选；`kind` 决定哪一组是事实来源。未知键会被拒绝。

```ts
const result = await ship.services.create("proj_123", {
  name: "db",
  kind: "compose",
  image: "postgres:16",
  ports: ["5432:5432"],
});
console.log(result);
```

</Tab>

## 更新服务

所有字段均可选——只发送要变更的部分。接受与创建相同的 compose 与 monorepo 字段，
**唯独不接受 `kind`**：切换一行的 kind 是破坏性操作，应改为删除该服务并
以新的 kind 重新创建。

有两个字段是**合并**（merge）到存量值上而不是替换它——`environment` 与 `advanced`，
即该端点以键为单位的 map：

| 你发送 | 结果 |
| --- | --- |
| 键不存在 | 保留存量值 |
| `{"KEY": "value"}` | 只设置该键；其余键不受影响 |
| `{"KEY": null}` | 移除该键 |
| `{"environment": null}` | 移除所有变量 |
| `{"environment": {}}` | 无任何变化 |

读回的环境值以 `••••••••` 打码（`GET /:serviceId` 永不返回明文）。回显哨兵值即
保持该值不变，或发送真实字符串替换它。**省略键绝不等于删除**——删除必须显式写 `null`。要从外部读取值，请用[揭示环境值](#揭示环境值)。

其余所有字段都会整体替换存量值，包括 `ports`、`volumes`、`dependsOn` 与
`publicEndpoints`，因此这些字段要发送完整列表。

## 从 docker-compose 同步

显式地用提供的已解析服务整体替换 Compose 服务配置，新增或更新行并移除列表中缺失的服务。CLI 的 `service sync` 命令在提交该请求之前会先读取并校验
文件。常规重新部署会自动把仓库变更与已保存的覆盖项合并；
它们不需要这个整体替换操作。

```
POST /api/projects/:id/services/sync
```

## 化解 compose 漂移

这些端点用于处理旧版本保存的待审审核。现在常规重新部署会保留
显式覆盖并自动应用其他源变更，旧审核记录随之清除。接受一条旧版审核会应用源配置，同时保留已保存的环境值。

```
POST /api/projects/:id/services/:serviceId/drift/accept   # accept source config, preserve saved env
POST /api/projects/:id/services/:serviceId/drift/keep     # keep your edits, stop flagging
```

## 环境变量

`GET .../environment` 返回生效的已保存配置：共享的项目
值、Compose 值与服务覆盖。每一行都标注来源，机密
已打码。默认取活动部署的环境，在首次部署前则取 production。加 `inspectRuntime=true` 即与自有的
Docker 容器比对；检查失败时响应仍保留已保存的变量。

```ts
const state = await ship.services.getEnvironment("proj_123", "svc_456", {
  inspectRuntime: true,
});
console.log(state.status, state.changedKeys);
```

部分编辑用 `PATCH .../env`。在 `upserts` 中只发送要改的覆盖项，
在 `deletes` 中发送显式移除。既有覆盖必须带读取时返回的 `sourceId`；
`null` 表示新建一条覆盖。过期的 ID 会返回
`ENVIRONMENT_CHANGED`，请求不会被应用。

```ts
const currentEnvironment = await ship.services.getEnvironment("proj_123", "svc_456");
await ship.services.mergeEnvVars("proj_123", "svc_456", {
  environment: currentEnvironment.environment,
  upserts: [{
    key: "LOG_LEVEL",
    value: "info",
    sourceId: currentEnvironment.variables.find(row => row.key === "LOG_LEVEL")?.sourceId ?? null,
  }],
  deletes: [],
});
```

`GET .../env` 只列出服务覆盖行（机密值打码）。
`PUT .../env` **整体替换**某个环境的这些覆盖——发送你想保留的每一条
覆盖。这两个端点都不代表继承而来的 Compose 层或
共享项目层。

```
GET /api/projects/:id/services/:serviceId/env
PUT /api/projects/:id/services/:serviceId/env
GET /api/projects/:id/services/:serviceId/environment
PATCH /api/projects/:id/services/:serviceId/env
```

### 揭示环境值

加 `source: "effective"` 可从完整的已保存视图中揭示指定的值。
做恢复时，用 `source: "runtime"` 并带上运行时检查返回的 `containerId`，以及 `recoverableKeys` 中的名称。恢复范围排除镜像默认值
与 OpenShip 中已保存的键。它返回值但不落盘；
用 `mergeEnvVars` 保存选定的恢复值。容器发生变化时返回
`ENVIRONMENT_RUNTIME_CHANGED`。

控制台使用同一个环境编辑器。导入的 Compose 值立即可见；**演示模式（Demo mode）**
像 IP 地址那样对它们做模糊处理。已保存的值初始打码，点击行的眼睛图标只揭示该行的值。
**Show values** 是揭示全部已保存行的显式操作。揭示不会保存或覆盖
配置。

SDK 与 REST 请求可指定 1–500 个键，每个最长 512 个字符。只返回所请求键中实际存在的那些。读取打码后的配置并不等于获得揭示它的权限。

这读取已保存的 Compose 配置，并要求服务写权限。加
`environment: "production"`、`"preview"` 或 `"development"` 可以改为读取该服务在该
环境下的变量。

对导入编辑器，可在初始扫描时一并请求值。这样编辑器打开时无需第二次源读取：

| 来源 | SDK | REST API |
| --- | --- | --- |
| Git 或本地扫描 | `deployments.prepare({ ...prepareInput, includeEnv: true })` | `POST /api/deployments/prepare` 配合 `includeEnv: true` |
| 上传的快照 | `sources.scan("session_123", { includeEnv: true })` | `POST /api/projects/folder/scan/session_123` 配合 `{ "includeEnv": true }` |
| 本地目录 | `projects.scanLocal({ path: "/srv/app", includeEnv: true })` | `POST /api/projects/scan` 配合相同的请求体 |

普通扫描保持打码状态。`includeEnv: true` 要求该扫描的写权限，对 Git 还要求
整仓内容读取权限。本地路径仅限自托管。演示模式只改变浏览器
显示，不改变 API 权限或返回的值。

## 错误

<Callout title="400 —— 请求体无效" type="warn">
载荷未通过校验（未知键、类型错误，或某值超出长度限制）。未知键
会被直接拒绝——对照上文的表逐一检查字段名。创建时，`kind: "monorepo"` 的服务必须
携带 `rootDirectory`。
</Callout>

<Callout title="服务维度路由返回 404" type="error">
该 `:serviceId` 不属于这个项目（或已被删除），或项目 `:id` 不在你的
组织。用 `GET /api/projects/:id/services` 列出该项目的服务以获取有效 id。
</Callout>
