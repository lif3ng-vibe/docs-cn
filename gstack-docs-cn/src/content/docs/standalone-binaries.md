title: "独立二进制工具"
---


在 slash command 技能之外，gstack 还为不适合放进会话的工作流提供了一批独立 CLI：

| 命令 | 功能 |
|---------|-------------|
| `gstack-model-benchmark` | **跨模型基准测试**——把同一条提示词分别跑过 Claude、GPT（经 Codex CLI）和 Gemini，比较延迟、token 数、成本，以及（可选的）LLM 评审模型质量分。按提供商自动探测认证，不可用的提供商干净跳过。输出为表格、JSON 或 markdown。`--dry-run` 只校验旗标和认证，不消耗 API 调用。 |
| `gstack-taste-update` | **设计品味学习**——把 `/design-shotgun` 的采纳与拒绝写入一份持久的按项目品味档案。每周衰减 5%。结果回灌到后续的变体生成，让系统学会你实际会选什么。 |
| `gstack-factory-scorecard` | **工厂计分卡**——经 `gh` 从 GitHub 读取一个仓库一个时间窗（默认 7 天）内的发布数据：已合并 PR（编队内 vs 外部）、前置时间（创建 → 合并、首条 READY 评论 → 合并）、门禁运行及其已知成本、红灯列车比例、不稳定事件（付费重跑与免费套件重试）、issue 开闭比、切出的 release。产出 Markdown 表格加 CSV，每行附计数规则以及顶尖工厂之一的参考值；`/retro` 第 7.5 步会运行它。只读，不产生付费工作。[指南](/recommended-harness/#工厂计分卡)。 |
| `gstack-egress` | **出站回执审计器**——gstack 发起的每次出站发送都会在发送前向 `~/.gstack/security/egress.jsonl` 写入一条防篡改、哈希链式的回执。`list` 列出 gstack 尝试发送了什么、发往哪台主机；`grants` 列出长期授权设置以及撤销每项授权的确切命令；`verify` 重新计算哈希链，发现篡改即退出码 3（能抓出改动、重排和链中删除；截断或删除台账本身不在范围内——它是取证日志，不是防篡改存储）。 |
| `gstack-context-bill` | **Token 物料清单**——只读、离线地审计一套已安装技能树的 token 开销：每个会话都要支付的常驻 frontmatter，对比按调用计费的 SKILL.md 与强制引用。`--diff` 比较两棵树，`--budget` 强制上限，`--exact` 启用 Anthropic `count_tokens`（会把树内计费 `.md` 文件的文本、链接的 gstack 检出目录或 gstack 的渲染目录发送到本机之外；凡符号链接够得着的其他内容只点名并估算，部分估算的账单标注 `mixed`；先写出站回执，回执写不进去就退回离线估算）。 |
| `gstack-code-intelligence` | **代码智能提供商选择器**——把 GBrain、Sourcebot 和 Graphify 包进同一个接口：`options`/`status` 查看有哪些可用，`select` 选定其一，`index`/`search` 加以使用，`suggest` 判断是否应在此触发一次性索引提议。该提议只在大仓库触发（1,000+ 个被跟踪文件；拒绝会被持久记住）。非本地的提供商在未记录逐仓库授权（`consent <repo> yes\|no`——查询文本属于仓库派生内容）之前一律拒绝索引*或搜索*，逐仓库信任策略中的拒绝与只读层级无论授权与否都否决写类操作，且每次出站发送都写出站回执。完全可选——什么都没选时，gstack 回退到 grep。 |
| `gstack-verify-gate` | **验证停止钩子（需主动开启**）——拦住 Claude Code 的回合，直到项目声明的验证命令通过为止（被拦着重新进入 3 次后会放行并给出响亮的仍然红灯警告，而不是无限循环）。在 CLAUDE.md 里一行声明：`<!-- gstack:verify: bun test -->`。钩子绕过权限系统，因此声明的命令在你逐仓库信任一次（`gstack-verify-gate --trust`）之前绝不运行；改动命令会使信任失效，需重新授予，每次授予都记入审计日志。`./setup` 绝不会替你注册——用 `gstack-settings-hook add-event --event Stop --command ~/.claude/skills/gstack/bin/gstack-verify-gate --source verify-gate` 开启，用 `gstack-settings-hook remove-source --source verify-gate` 移除。 |
| `gstack-memorable` | **Memorable 回忆桥（需主动开启，第三方，仅限 Claude Code**）——让 Claude Code *经由 gstack* 接入外部 [Memorable](https://memorable.sh) CLI，而不是走厂商自己的安装器，钩子因此获得 gstack 的保证：显式授权键（`memorable_recall`，默认关闭，`gstack-egress grants` 可见）、每次交出提示词都写失败即关闭的出站回执（`gstack-egress list --sink memorable-recall`）、HIGH 级秘密预扫描、对返回内容的信任封套与 8 KiB 上限、厂商进程的白名单环境与进程组隔离，以及干净卸载。`enable` 在稳定安装位置注册钩子，超时 5 秒，绝不运行厂商自己的授权命令；`disable` 先撤销门禁，再按身份移除条目，即使 Claude Code 已剥掉标签也能移除；`status` 只读。gstack 绝不安装 Memorable，其二进制发送什么属于厂商声明，与 gstack 无关。目前尚不支持 Windows。[完整指南](/memorable-workflow-memory/)。 |
| `gstack-decision-trail` | **决策轨迹**——向一次运行的 TSV 轨迹追加一行（时间戳、阶段、决策、理由、证据、结果），让评审者不必翻会话记录就能读到选了什么、为什么。表头只写一次，只追加不修改，单元格压平成一行，以 `=`、`+`、`-` 或 `@` 开头的单元格会被加引号，电子表格无法把它当公式执行。`start <file> <run-id>` 在共享轨迹上开启一次运行的区段（幂等；`start` 被保留为阶段名），`--run <id>` 在该 start 行不是最新一行之前拒绝追加。移植自 pstack 的 `log.sh`（MIT，NOTICE.md）。[规则](https://github.com/garrytan/gstack/blob/main/docs/unattended.md#the-decision-trail)。 |
| `gstack-worktree-audit` | **worktree 审计**——只读表格，列出主 worktree 之外的每个 git worktree，按体积从大到小：大小、存在时长、是否已并入基线、`clean`/`clean,ignored:<n>`/`wip:<n>`/`scratch:<n>`、`pushed`/`ahead<n>`/`no-remote`/`detached`、经 `gh` 查到的其分支上的 PR（忽略 fork PR）、其中最新的 Claude Code 会话，以及归类桶（目录已消失的未锁已注册 worktree 记 `prunable`，加锁或 `broken` 的记 `review`，其余为 `hold-wip`、`hold-open-pr`、`verify-recent-chat`，仅当干净的树已并入基线、或其 PR 已关闭/已合并且每个提交都已推送时记 `safe`，否则记 `review`）。`-b origin/<branch>` 设定基线，`--no-fetch` 跳过对基线 ref 的尽力拉取（它唯一的写操作）。绝不删除。移植自 pstack 的 `worktree-audit.sh`（MIT，NOTICE.md）。[指南](https://github.com/garrytan/gstack/blob/main/docs/CONTRIBUTOR_REFERENCE.md#auditing-conductor-worktrees)。 |
| `gstack-clean` | **逐仓库 `.gstack/` 清理**——在仓库内运行，预览能从该仓库 `.gstack/` 目录回收什么；加 `--apply` 才执行。它会删除超过 7 天的 `tmp/codex-*` 临时文件，把 browse 日志（`browse-console.log`、`browse-network.log`、`browse-dialog.log`、`browse-daemon.log`、`browse-startup-error.log`）在超过 1 MB 后截到最近 256 KB，仅在 `--audit-days N` 时裁剪 `browse-audit.jsonl`。它绝不触碰 `browse.json`、`session-state.json`、`chromium-profile/`、`browser-skills/` 或 `browse-states/`，守护进程运行时跳过 browse 文件、codex 运行时跳过 `tmp/`，并且在以下情况拒绝执行（退出码 3）：不在 git 仓库内、`.gstack` 是符号链接、`BROWSE_STATE_FILE` 指向别的目录、该目录属于/包含/位于 gstack 状态根目录之内。`--json` 打印一个带版本号的对象。退出码 0 完成，1 某个动作失败（重跑安全），2 用法错误，3 拒绝。[错误码](/troubleshooting/#gstack-clean-usage)。 |
| `gstack-wtree` | **工作树指纹**——打印磁盘上实际内容的内容哈希（以 stat 缓存播种的临时索引，比完整重哈希省约 40 倍；未跟踪的源码计入，gitignored 的草稿不计）。相同内容在 commit、rebase、amend、squash 之后指纹依旧相同——正是它把评审和测试证据绑定到内容而非提交 SHA 上。 |
| `gstack-review-log` | **评审通过回执**——`--start <skill>` 在 diff 评审前捕获工作树指纹；`'<JSON>' --finish <token>` 消费那张一次性、限定仓库/分支/技能范围的回执。绑定要求起止内容一致，且评审者报告 `completed:true` 与 `converged:true`；它不是"模型读过源码"的独立证明。`--check-shared-libs <token>` 从 stdin 读一条当前发现（JSON），把此前的 Skip 决定对照实际分支、捕获与合格的原始源码 blob 核查。证明缺失或不安全时（包括没有记录器版本覆盖的旧记录）返回 `reusable:false`。最终评审记录会自行计算共享代码指纹与覆盖率，而不是相信提交上来的证明。 |
| `gstack-review-read` | **评审新鲜度**——输出带计算字段 `review_freshness.status` 与 `reason` 的评审记录：diff 评审为 CURRENT、STALE 或 UNVERIFIED。`/ship` 和 `/land-and-deploy` 使用同一评级；单凭提交吻合绝不为 diff 评审背书。[仪表盘规则](/skills/#评审就绪仪表盘)。 |
| `gstack-evidence` | **验证证据台账**——`run --label <lane> -- <cmd>` 透明包裹任意测试命令（子进程退出码原样透传），并记录什么在哪个工作树指纹上运行（未 gitignore 的已跟踪与未跟踪文件，扣除仓库根部未跟踪的 `.bun/` 目录——Bun 可能在运行期间创建它）；运行期间文件发生变动的 run 不记指纹、改记最多五条变更路径，`check` 会在其 STALE 原因中点名。`check` 以 `--expect-cmd`、`--max-age` 与 `--allow-paths` 绑定，为每个标签评级 FRESH/STALE/MISSING。标签在存储与查询时会把 `A-Za-z0-9._-` 之外的每个字符替换为 `_`，所以 `pnpm lint` 与 `pnpm_lint` 指向同一行。`carried` 列出当前树上评级为 FRESH 的来自 CI 的行，发布回执将其记为 `ci_carried`。/ship 与 /land-and-deploy 引用新鲜证据而非重跑测试套件。每次运行的日志权限 0600、上限 2MB、30 天后清理；台账与日志在设计上只留在本机。 |
| `gstack-flaky` | **面向任意 JUnit 运行器的不稳定测试重跑**——`run --junit <file.xml> -- <command>` 运行你的测试命令（Playwright、`bun test`、jest、vitest、pytest），当失败测试不超过 `--max-reruns`（3）个且运行器自身没有重试时，把整条命令重跑一次（`--rerun-scope test` 可选择只重跑失败的测试）。先失败又在重跑中通过的测试记为不稳定通过（flaky pass）：整体运行保持绿灯，每条不稳定通过或失败重跑各有一行脱敏记录进入台账（`GSTACK_FLAKE_LEDGER_JUNIT`，默认 `<state root>/flake-ledger-junit.jsonl`）。报告缺失或格式错误、运行器崩溃或被杀，永远不会算通过。`quarantine add|renew|release|check|report` 维护 `.gstack/quarantine.json`：被隔离的测试仍会运行，最多获得 3 次整命令尝试，只有整次全绿才算通过，且从不计入通过数（`run --base <ref>` 从基线分支读取该注册表）。`ids --junit <file>` 打印报告中的测试 id。退出码 0 通过，1 有测试失败，2 用法错误，3 没有可用报告。[指南](https://github.com/garrytan/gstack/blob/main/docs/flaky.md)。 |
| `gstack-pr-wait` | **PR 事件守望器**——`gstack-pr-wait <pr> [--repo owner/name] [--until green\|ready\|any-change] [--interval 20] [--timeout 60] [--exclude CHECK,...]` 经 `gh` 轮询单个 pull request，每个真实事件在 stdout 打印一行（某项检查失败并附链接、全部检查结束、作者以外的人发了评论或评审、评审机器人在 head 上完成、基线移动且其新提交触及本 PR 的文件、BEHIND 或 DIRTY、已合并或已关闭），进度走 stderr，这样监视器按事件而非定时唤醒 agent。`green` 以 head 上的每项检查为门禁（咨询型机器人的评审从不等待，其检查与任何检查一样参与门禁），与 `gstack-ci-gate` 一致；基线分支要求的检查（rulesets 与经典分支保护）在出现之前一律视为 pending，绝不因缺席而算绿；两次相同的轮询确认检查集合完整；`--exclude` 像 `gstack-ci-gate --exclude` 那样把指定的非必需检查排除在判定之外（必需的检查名会被拒绝并照常门禁）。条件满足退出码 0，需要人工介入或 `--timeout` 到期退出码 1（`PR_WAIT_BLOCKED`），输入错误、同一 PR 出现第二个守望器或本地错误退出码 2（`PR_WAIT_REFUSED`）。状态存于 `<state root>/pr-wait/`，基线 6 小时后丢弃。评审机器人是可配置的：`gstack-config set pr_wait_gating_bots greptile,macroscope`、`pr_wait_advisory_bots coderabbit`（咨询型机器人只报告、从不等待）。`/land-and-deploy` 第 3 步就是对它的一次调用。设计移植自 tstack 的 pr-wait（MIT，Theo Browne；NOTICE.md）。[退出码](/troubleshooting/#gstack-pr-wait)。 |
| `gstack-review-bots` | **评审机器人评论**——`fetch [--pr <n>]` 把 `pr_wait_gating_bots` 与 `pr_wait_advisory_bots` 中每个机器人（仅限 Bot 账号，全部分页，经 `gh`）的每条根级行评论、会话评论和最新评审正文读入一个私有目录并按机器人计数，否则打印 `REVIEW_BOTS: skip` 或 `REVIEW_BOTS: error`（绝不给出假的零）。`record --dir <dir> --id <comment id> --type fix\|fp\|already-fixed --category <category>` 向项目级与全局 `review-bot-history.md` 追加一条分诊结论，机器人和文件取自被抓取的评论。`/review` 第 2.5 步与 `/ship` 第 10 步会运行它。[分诊参考](https://github.com/garrytan/gstack/blob/main/review/greptile-triage.md)。 |
| `gstack-issue-guard` | **工单文本信任封套**——抓取 GitHub issue/PR 文本（`issue <n>`、`pr-body`、`pr-comments` 或 `--stdin`），装进带标签的封套，让 agent 把它当数据对待：注入形态的行即使经过全角与不可见字符伪装也会被打上标签，伪造的封套横幅会被拆除。gstack 中每一处工单文本入口都经它路由，由 CI 扫描器强制执行。 |
| `gstack-ios-qa-daemon` | **iOS QA 守护进程**——Mac 侧中间人，经 USB CoreDevice 把 agent 与已连接的 iPhone 或 iPad 接起来。默认只听回环地址；`--tailnet` 开启面向 Tailscale 的监听器，能力层级按身份放行。通过在 `~/.gstack/ios-qa-daemon.pid` 上 flock 保证单实例。见 [docs/howto-ios-testing-with-gstack.md](/howto-ios-testing-with-gstack/)。 |
| `gstack-ios-qa-mint` | **iOS 白名单管理器**——tailnet 白名单的属主授权 CLI。`grant`/`revoke`/`list` 直接操作 `~/.gstack/ios-qa-allowlist.json`（权限 0600）。远程 agent 绝不自动加白；这是显式意图的通道。 |
| `gstack-ios-qa-regen` | **iOS 桥接再生器**——确定性地安装权威 DebugBridge 包，生成类型化的状态访问器，并记录所装 gstack 版本。源码变更或升级后重跑安全。 |

私有的付费 CSO 评测生产器（producer）是一份打包契约，不是普通的 `bun run build` 产物。在 macOS 或 Linux 上，发布操作员在与 `bun run build:cso` 相同的干净构建会话中，用文档规定的 Bun 加固旗标编译 `cso-eval-producer`，再把它与 `gstack-cso-launcher`、`gstack-cso-core`、`gstack-cso-watchdog` 和隐藏的 `.gstack-cso-generation` 清单一起，安装成一个 root 属主、不可写的五工件单元。生产器拒绝 root 执行、可写/符号链接/不完整的安装，以及未经评审的提供商 CLI 版本；每张回执绑定全部五个工件的哈希，收集端会拒绝来自不同单元身份的回执。参见[干净生产器流程](https://github.com/garrytan/gstack/blob/main/test/fixtures/cso-eval/README.md#trusted-five-artifact-producer-unit)。付费生产器评测在 Windows 上仍不可用，因为分离式 watchdog 没有 Windows 构建。

每个生产器得到一份策展过的单单元源码副本，目录封到 `0555`、文件封到 `0444`，并附带事前/事后的一致性、Git 与权限位检查。Claude 得不到源码 add-directory，因为 add-directory 是一个沙箱写根，Claude Code 的 bubblewrap 会在那里留下一个空的 `.mcp.json` 挂载点。它的 Bash 在 Claude Code 的沙箱内运行，唯一例外是 `--allowed-tools` 点名的那个精确的启动器绝对路径——它像对用户一样在沙箱外运行。启动器就是那里的边界。它以固定白名单替换自身环境，只用本地 Docker Unix socket，并把每个目标放进加固容器运行。生产器通过 `--settings` 传入该策略（启用沙箱、不可用即失败、无非沙箱回退、不自动放行，且 `excludedCommands` 只点名启动器）。除非生成的参数与环境恰好携带该策略，否则拒绝启动 agent（`CLAUDE_PRODUCER_SANDBOX_POLICY_MISMATCH`）。`CLAUDE_CODE_SUBPROCESS_ENV_SCRUB` 保持未设置，因为它会把启动器强推回沙箱。其余所有 Bash 命令都被 `--allowed-tools` 拒绝，Write 被限制在提供商工作目录和 `cso-home` 内。Gemini 得不到源码工作目录或 include 目录。Codex 在技术上确实拿到了对那份精确策展源码根的只读文件系统访问，因为受信任的辅助程序继承了 Codex 权限配置；其私有提供商工作目录和精确的 `cso-home` 工件目录是仅有的写根，其余每个根路径依旧被拒，且生产器提示词要求经辅助程序访问源码。这是针对一份不可变公共夹具的评测隔离，并不是在声称 Codex 无法直接读到那份夹具。

把每个完成单元的回执连同 `state/cso-home/security/cso/` 一起复制到受信任的裁决主机。回执条目是相对该目录的有序路径，绑定每个保留文件的大小和 SHA-256，外加一个聚合清单哈希。提供商的 home、设置、会话与凭据放在各自的一次性目录里，单元结束后删除；它们永不属于保留的工件树。裁决者在信任报告或修复包之前，必须对照回执对传输来的树重新哈希。

| 生产器宿主 | 日常/静态单元 | 综合目标执行 |
|---|---|---|
