Astryx 由 Meta 内部设计系统生长而来，这段出身在国际化的处理上也能看出来。多数内部工具面向英语员工以英文交付，翻译与从右到左支持很少成为优先事项。组件带着硬编码的英文字符串和从左到右的假设，因为在内部没人要求别的。

开源改变了受众。触发点来自发布后的社区：一位发布阿拉伯语和库尔德语应用的开发者提交提案，指出多个组件把面向用户和辅助技术的字符串硬编码为英文，且无从覆盖。表格排序标签、分页控件、Calendar 的月份名。他们的应用被卡住了，变通办法只能是 fork 组件来改几个词。他们给出了修复，但我们想坐下来做一次更全面的审视。

在此之前，我职业生涯里相当大一部分时间都在做本地化，所以这项工作出现时我主动请缨。那些坑我熟悉：字符串长度随翻译变化、复数化的假设、字符串拼接让语序不同的语言难以翻译。从右到左语言尤其棘手，会打破布局假设。距离我上次真正琢磨这些问题已有多年，于是在敲定设计之前，我借助 AI 助手重新调研了现代 i18n 格局——标准如今长什么样、流行的 React 库沉淀了什么方案。

## 为什么我们没有直接引入 i18n 框架

顺理成章的做法是接上一个成熟的运行时，比如 `react-intl`、Lingui 或 i18next。这样构建成本最低，但意味着 Astryx 背上更多依赖包袱。硬依赖某一个运行时会增加包体积，还与已经标准化了其他方案的团队冲突，他们要么两套并行，要么换掉自己的。

于是我们把格式与框架分离。我们采用 ICU MessageFormat——现代 i18n 字符串格式——以 `intl-messageformat` 为格式化器（藏在一个小适配器后面）。已经在跑 `react-intl` 或兼容栈的使用者可以把自家字符串交给 Astryx。这让接触面保持极小：一个携带 locale 的 provider，一个读取翻译的 Hook，内置英文默认值。组件零配置即可渲染，采用可以渐进。

我们[发起了一个 RFC](https://github.com/meta/astryx/issues/3641)，先立下一些初始约束，并在迭代中不断提炼。例如：我们考虑过把每个 locale 做成独立包，甚至为每个组件配独立字符串集以支持代码分割。分析后发现要交付的字符串体量（压缩后约 2KB）撑不起这些复杂度，最终定为核心里一个 en.json。其他一些初始"要求"也在我们发现其实不需要之后被移除或简化。

## 复数如今已是被解决的问题

复数看起来容易，实则很容易做错，因为英语允许你作弊。应用常常用 `1 item(s)` 这样的标签，或计数不为 1 就追加一个 "s" 的代码。它够用，直到要翻译时——英语的复数形式并不通用。阿拉伯语有六种。俄语和波兰语有四种。日语只有一种。`one`/`other` 的假设根本撑不起来。

好消息是（不久前这还不成立）平台现在能处理这件事了。ICU MessageFormat 让字符串声明自己的复数情形，`Intl.PluralRules`（一个由 CLDR 数据支撑、支持广泛的浏览器 API）知道每个数字在每个 locale 下取哪种形式。所以不必手写复数逻辑再出错，字符串只需列出情形，让运行时去挑：

```text
Go back {step, number} {step, plural, one {page} other {pages}}
```

![一个结果计数字符串在俄语下以计数 1、2、5 渲染。只用英语 one/other 规则的朴素版本，每个计数都显示同样的错误词尾（"результаты"）；使用俄语 one/few/many/other CLDR 类别的正确版本，显示三种不同词尾：результат、результата、результатов。](/blog/internationalizing-astryx/russian-plurals.png)

用这种方式表达复数还有一个额外好处：情形以数据声明而非烙进正文，某份翻译缺了一种形式——或悄悄只保留了英语的形式——就不只是错，而是_可检测的_。开始批量翻译后，这一点非常重要。

## 从右到左，以及躲开 linter 的 bug

就算全部译成阿拉伯语，布局还是从左到右的话，UI 照样是坏的。多数 RTL 支持是机械性的：用 `margin-inline-start` 这类 CSS 逻辑属性替代 `margin-left`，设置 `dir="rtl"`，让浏览器镜像布局。lint 规则可以强制这一点，我们也确实做了。

真正漏网的是组合性 bug。促使我们打造专用工具的例子是这个：

```css
inset-inline-start: 0;
transform: translateX(-50%);
```

每一行单独看都合法。linter 看到一个逻辑 inset，放行。但两行合起来先把元素锚定在逻辑起始边，再用一个物理 transform 平移它——而 transform 在 RTL 下不翻转。在 `dir="rtl"` 下，元素会错开自身宽度落在错误一侧。没有任何坏 token 可以 grep。bug 活在交互里。

图标以同样的方式出错。你可以在 JS 里换字形来镜像一个尖角号，或在 CSS 里翻转它。两种做法单独都行。同一元素上两个都做，它们相互抵消，箭头方向就错了。同样，两个决定单独看都合理。

![RTL 下 Astryx Calendar 选中日期区间的修复前后对比。修复前，区间高亮是直角矩形，因为它的物理圆角属性不随翻转变化；修复后，它是一个圆滑的胶囊形，两端落在正确的阅读方向边缘。](/blog/internationalizing-astryx/calendar-rtl-before-after.png)

静态分析对这类问题天然乏力，因为每个属性单独看都正确。所以我们构建了 [RTL 审计：把每个组件 story 在两个方向各渲染一次并比较几何](https://github.com/meta/astryx/pull/4517)。对每个绝对定位元素，它在 LTR 下测量相对父级的 X 中心，再以 RTL 渲染一次，检查元素是否在容差内镜像到对侧。本该翻转却没翻的元素立刻现形；翻转了两次、该动却没动的图标也无所遁形。

难点是把大约 1,300 个定位元素上的误报压下去。通宽的条带没有有意义的左右之分；已经居中的元素镜像后与自身重合。朴素的几何检查会把两者都标为失败。我们对这些情况反复迭代，为退化父级、满幅元素和已居中子元素加了守卫，直到审计除真实回归外保持安静。现在它在 CI 里运行，捕获 linter 看不见的方向性 bug。

值得记住的教训是：抵达生产的 RTL bug 很少是一个多余的 `left`——它们是各自合法、组合起来出问题的片段，所以可靠的检查是渲染后的几何，而不是静态规则。

## 播种 29 种语言

机器就位后，我们手里有约 250 条字符串和一个有 29 种空语言槽位的 [Crowdin](https://crowdin.com/project/astryx) 项目。放在过去，接下来就该等了——翻译随贡献者认领语言慢慢滴进来。LLM 让我们改为直接点火：先为全部 29 种语言生成一轮扎实初稿，再让社区从那里打磨。

这里一个深思熟虑的格式选择收到了回报。我们选的词表格式让每条字符串都带一个 `description`——说明它在哪里、如何被使用——正是因为我们预期这些上下文会带来更好的翻译。比如 Dialog 关闭按钮的备注写道："Close" 指关闭对话框，不是关闭"附近"。这层上下文本意是给人类译者的，结果发现 AI 译者同样高度依赖它：两者拿到的都是字符串_加上_意图，而不是一个干巴巴、只能猜的词。

接着我们让两个模型互相对抗。一个负责生成；一个确定性校验器把每个候选都送进 Astryx 运行时使用的同一个 ICU 解析器，直接拒绝丢占位符或缺复数类别的候选。但校验器只判结构，所以另一个不同的模型来审阅语义、语域与习语——抓到规则抓不到的东西，比如按钮标签在该用祈使式的语言里被译成了名词（"closing" 而不是 "close"）。希伯来语把这个问题暴露得最清楚；修好它之后又浮现出更多同类问题。

结果是今天 29 种语言全部完成播种并可渲染。需要说明：我们仍然相信一位熟练的人类译者会胜过机器——所以这些是起点，不是定论，纠错与贡献都非常欢迎。

## 尚待解决的事

Astryx 的 i18n 还没"完工"。有几个问题依然真实存在。PowerSearch 仍从使用方提供的片段组装部分短语，这限制了这些短语在各语言里的语法水平。我们的伪 locale 对字符串长度的膨胀还不够激进，无法冲出所有窄布局故障。平台侧，服务端渲染翻译、复用使用方既有运行时的适配器，都还是进行中的设计工作。我们还在追查一类新错误：截断与 IME 不兼容。非常感谢社区帮我们发现并追踪这些问题。

Astryx 现在会说 29 种语言，且双向可读。设好 locale，设好 `dir`，它就能工作（更多信息见我们的[国际化指南](https://astryx.atmeta.com/docs/internationalization)）。如果你会说其中某种语言，看到可以更好的翻译，[Crowdin 项目](https://crowdin.com/project/astryx)向你敞开。
