我们[发布 Astryx](/blog/introducing-astryx) 时，把它定位为一个 AI 友好、完全可定制且零依赖的设计系统。这篇文章是它背后的技术故事——Astryx 究竟是什么，Meta 内部催生它的问题，它由哪些系统构成，以及我们如何制作和评估变更。每个系统我们都会在后续文章里单独深入。

## Astryx 是什么？

Astryx 是一个组件库，交付预编译 CSS 和带类型的 React 组件——150+ 个无障碍组件、品牌级主题定制、深色模式、模板与 CLI，构成一个内聚的系统，基于 React 与 StyleX 构建，目前处于 beta。

```css
@import '@astryxdesign/core/reset.css';
@import '@astryxdesign/core/astryx.css';
@import '@astryxdesign/theme-neutral/theme.css'; /* Pick a theme */
```

```tsx
import {Button} from '@astryxdesign/core/Button';
import {Stack} from '@astryxdesign/core/Stack';
import {Card} from '@astryxdesign/core/Card';

<Stack gap="md">
  <Card>
    <Button variant="primary">Save</Button>
  </Card>
</Stack>;
```

**它的几点独特之处**

- **内部开放**。组件为任意层级的组合而生，不会被锁在封闭的顶层 API 后面。你会用到的构建单元直接导出；需要更深入时，swizzle 会把组件的完整源码——连同内部模块——弹出（eject）到你的项目里归你所有。
- **不靠包装就能定制**。主题是一组 CSS 自定义属性覆盖与组件样式覆盖，由配置生成并与系统兼容。设计师可以独立维护它；开发者永远不需要 fork 或包装组件源码来改变外观。
- **开箱即用或从源码构建**。引入预构建样式表即可完成接入；或从 TypeScript + StyleX 源码构建，让打包器只保留你实际用到的组件——为最小体积输出准备的一等路径。
- **同样为 AI 助手而建**。API 与文档的形态由"LLM 实际如何使用这个库"的度量塑造，工程师读到的同一份参考材料，AI 助手也能通过 CLI 获取。

## Meta 内部的问题

Meta 靠成千上万个内部工具运转，它们分布在不同组织，由需要它们的团队自行构建；公司的文化也积极鼓励"没有工具就自己造一个"。但对任何单个工具的投入都分散在各组织之间，于是构建者们在一个又一个工具里重复造着同样的组件——日期拾取器、表格、表单。所有人都在为此买单：终端用户背负着"每个产品都稍有不同"的认知负担，构建者把时间耗在重复发明轮子上，公司则一遍又一遍维护同一个组件。

我们构建最初的系统，是作为一个团队可以在其上构建的公共 UI 框架，而不是每次从零开始。想法很简单——共享问题只解决一次，让构建者把时间花在产品真正独特的部分。它为公司提供了内部工具共享的 UI 语言，让跨工具协作与共享成为可能，并且——由于内部工具要解决的问题范围极广——在各种用例中积累了大量复杂、久经实战的组件。八年间，它成长为 Meta 使用最广、规模最大的设计系统，支撑着 13,000+ 个产品，其中约一半的更新由构建者社区自己贡献。这份广度与真实使用正是 Astryx 得以立足的基础。

AI 改变了构建 UI 的经济学。助手在处理 TypeScript、流行 OSS 库、现代浏览器原语这类分布内、开源的标准技术时效率大增，而内部系统三者皆不是。与此同时，我们想在最新浏览器技术上完成现代化、开放多得多的定制能力，并让系统从设计之初就 AI 友好，而不是事后补装。AI 也改变了我们能做到的事：同样的杠杆让构建变容易，也让整体重写乃至开源，对我们这样规模的团队触手可及。

Astryx 就是那套内部系统在开源技术栈上的重建——现代浏览器特性、不靠包装的定制能力，以及一个同时支撑人类与 AI 和这个库交互的内建文档系统。它保留了八年规模化沉淀下来的广度、约定与组织知识，甩掉了拖住它的束缚。

## 系统构成

Astryx 是少数几个可组合的系统。

**分发**。Astryx 有两种交付方式。简单路径是单个预构建样式表——引入后直接用组件，零构建配置。进阶路径从 TypeScript + StyleX 源码构建，打包器只包含你引入组件的样式（在我们的参考应用里约为完整样式表的三分之一），并精确控制 Astryx 样式与你自有样式的层叠关系。

**主题系统**。主题定制是设计师把 Astryx 变成"自己的"的地方。主题是一份声明式配置——颜色、排版、动效、间距、逐组件微调——改一个值即可同时更新所有组件。除了调整 CSS 变量，Astryx 主题还能直接定制组件与组件部件，并引入自定义变体。浅色与深色一起处理；主题可以实时切换，或编译为生产用静态文件；目前已有 7 套现成主题随库发布。

**阶梯式定制路径**。控制权按明确定义的台阶逐级上升：原样使用组件 → 调整主题 token → 通过类名应用自己的样式 → 用自己的 CSS 深入干预 → 或彻底弹出源码收为己有。每一级都以更多责任换取更多控制。

**CLI 伴侣**。CLI 是操作界面——浏览文档、初始化脚手架、构建主题，以及在有变化时运行自动升级。对 AI 助手来说，它也是比长篇文档或网络搜索更可靠的学习方式，因此助手用的 API 与人用的完全一致。我们让系统的人类体验与 AI 体验保持同步。你在这个文档站里看到的文档、示例与模板，AI 都能通过 CLI 获得。

**Vibe tests**。一套内建的评估装置，度量人和 AI 用 Astryx 实际构建的效果如何。变更让系统变得难用时，我们靠它发现；设计争论，我们靠证据而不是观点来裁决。

## 原则

几条原则把整个系统维系在一起。它们是 Astryx 向构建者做出的承诺。

**指引优先于强制**。组件给你的是能力，而不是与你对抗的护栏。设计主张写进文档和示例；你传什么值，组件就渲染什么。系统负责引路，不做警察。

**强大且成文的约定**。每个组件遵循同样的命名、prop 与组合规则，且都有完整文档。学会几个之后，其余的都似曾相识；人和 AI 都能预测一个陌生组件的行为。

**人与 AI 同属一套系统**。API、约定、文档与 CLI 一体设计，让人和 AI 助手以同样的方式、参照同样的资料构建。我们发现二者相互增强：每一处让 AI 更容易使用 Astryx 的改动，也让人更容易使用。

**用度量赢得结论**。我们测试约定，而不是断言约定。我们把相互竞争的方案同时摆到人和 AI 面前，度量什么真正有效，让数据裁决争论——然后松开手握着结论，一旦新情况证明它错了就回头修正。

我们与 AI 以及 Astryx 自身一起构建和维护 Astryx。仓库治理、文档审计与 vibe test 运行都有 AI 协助，我们自己的工具也跑在我们发布的组件上。进入 core 的任何代码——包括 AI 协助的代码——都经过团队的人工评审。

## 名字的由来

Astryx 读作 asterisks，取自 _ad astra per aspera_——"穿越坎坷，抵达星辰"。"X" 是对出身的致意：xDesign，这些想法发源的团队。而星号（asterisk）是那个代表一切的符号——那条原来至关重要的脚注，那个把系统维系在一起的占位符。

我们选了一个承载这项努力初心灵魂的名字。我们不想固着于它今天做什么，而是它在这样一个节奏越来越快、变化不断的技术世界里可能成为什么。

## 开源

Astryx 以 MIT 许可证开源，目前处于 beta。

```bash
npm install @astryxdesign/core @astryxdesign/theme-neutral
npm install -D @astryxdesign/cli
```

Astryx 之所以存在，是因为 Meta 内部有一群构建者，八年间贡献修复、标记边界情况、塑造了这个系统——它懂的东西，很多是从他们那里学来的。现在它向更广的社区开放。我们以松散、开放且格外用心的方式构建它，也打算继续这样构建下去。欢迎来到 Astryx。
